# Радити

Радити (raditi.ru) — сервис для малого бизнеса: владелец пишет в веб-чат или Telegram, что поменять на сайте, и AI-агент меняет его сайт — в MVP на WordPress, дальше на 1С-Битрикс и других CMS. Контент правится прямо на сайте со снимком для отката, код — через git-репозиторий сайта (наша Gitea или GitHub/GitLab клиента): ветка, PR, «Применить», выкладка с бэкапом, проверкой и автооткатом. Окружение у сайта одно — прод.

## Правила, которые нельзя нарушать

1. **Хранилища — в России, модели — по подпискам Codex и Kimi.** База, S3, логи, снимки и журналы платформы — только у российских провайдеров. Задания, сообщения и файлы клиента, код и содержимое его сайта обрабатывают модели OpenAI (США) через подписки ChatGPT для Codex CLI и Moonshot AI через подписки Kimi Code (юрлицо и страна — по заключению юриста) — решение владельца от 28.09.2026. Других провайдеров моделей нет: GigaChat, Yandex AI Studio и Cloud.ru убраны. Сообщения и файлы клиента сначала записываются в PostgreSQL и S3 в России; прямого пути «браузер → провайдер модели» нет. В работе платформы к провайдерам ходит только шлюз подписок (роль `llm`) через узел выхода за рубежом; тела запросов нигде не пишутся. Для штатной разведки P3.0 (§21) на одноразовой `spike-1` разрешены временный `CODEX_HOME/auth.json` отдельного тестового аккаунта и очищенная запись синтетических обменов `record-proxy`; после неё — выход с отзывом токенов, удаление временных каталогов и ВМ. Решением владельца от 29.09.2026 отдельно разрешена локальная проверка на его текущей подписке Codex: только синтетика, изолированный временный `CODEX_HOME` без `auth.json`, существующий файл входа читает только `record-proxy` по `RECORD_CODEX_AUTH`, без копирования, повторного входа, обновления и отзыва токенов или `logout`. При истёкшем токене либо 401 на подписочном маршруте проверка останавливается; локальный отказ побочного `/disabled/…` не считается отказом подписки. Kimi в этой проверке не участвует; локальный результат не подтверждает удалённый `egress-1` и канал из России, не закрывает P3.0 или P3. Решением владельца от 04.10.2026 продукт переходит на одну оболочку и одну модель: OpenCode с GLM по подписке GLM Coding Plan на Z.ai; Codex, Kimi и всё, что обслуживает только их, убирается. Переход идёт отдельным PR по плану `docs/research/2026-10-opencode-glm/pivot-plan.md` (G0–G9): сначала OpenCode с GLM проходит те же стенды через шлюз платформы (роль `llm`, новый бэкенд), затем удаляется прежнее; до этого код, стенды и это правило описывают подписки Codex и Kimi. Решение владельца от 05.10.2026 (ответы на вопросы плана — `pivot-answers.md` в том же каталоге; где они расходятся с планом, верны ответы): ключ плана GLM — тестовый и локальный, он остаётся в корневом `.env` как `ZAI_API_KEY`, и скрипты и стенды могут брать его из окружения, в том числе загружая корневой `.env`; значение не печатается и не попадает в аргументы процессов, логи, записи, репозиторий и песочницу, а агентам читать `.env` инструментом чтения по-прежнему нельзя (запрет в `.claude/settings.json`). На стадии MVP у сервисов платформы — web, `core`, `mcp`, `llm`, раннер — один набор переменных окружения; в продуктовом пути ключ плана читает только роль `llm` — из Vault `subs/`, куда его кладёт импорт `subscriptions:login` (запись импорта `--backend zai-coding` и объявление `ZAI_API_KEY` в `.env.example` и `turbo.json` появились в G2). К `api.z.ai` роль `llm` ходит напрямую: узел выхода для Z.ai не нужен, а возможность идти через него остаётся настройкой роли для других провайдеров (прямой путь появится в G4, сейчас без прокси роль наружу не ходит). Детерминированные стенды, тесты и CI идут на фейке провайдера и ключа не получают. Живой режим (появится в G6) — явная команда стенда: не в CI, только синтетика, ключ — из окружения. Проба 04.10.2026 и шаг плана об окне квоты после простоя 05.10.2026 ходили к `api.z.ai` с машины владельца, только с синтетикой; скрипты пробы в каталоге исследований — запись того, как получены наблюдения, не инструмент. Предложение «Настоящие подписки в обычном dev не используются» («Команды») остаётся о подписках Codex и Kimi: ключ плана GLM dev получает из `.env`, а класс данных вне production остаётся `synthetic`. До нового гейта 152-ФЗ с получателем Z.ai на этой модели идут только синтетические данные; план по условиям Z.ai личный, и что использует production — API с оплатой за токены или письменное соглашение с Z.ai — открытый вопрос П15 (spec §20). Данные клиентов и production-секреты запрещены; в репозиторий попадают только проверенные очищенные материалы. Персональные данные третьих лиц — посетителей, авторов комментариев и заявок, клиентов сайта — агенту не передаются (§11). Данные клиентов уходят провайдеру только после гейта 152-ФЗ (§18): `issue` не выдаёт ключ хода рабочему пространству с реальными данными без записи в `cross_border_clearances` для этой оболочки. Никаких других зарубежных API с данными клиентов.
2. **Секреты — только в Vault.** В базе — `credential_refs` (путь в Vault), в коде, логах, S3 и Git — никогда. Форма доступов пишет в Vault и не умеет читать обратно. Сервисы входят по AppRole со своими политиками (§15). Токены подписок — только в Vault mount `subs/` (`max_versions=1`, `cas_required`). Читает и обновляет их только роль `llm`, импорт пишет и не читает обратно, удаляет — только политика admin. В песочницу, на песочную ВМ и `egress-1`, в `turn_assignments.plan`, логи и метрики они не попадают. Локально ключи сервисов можно держать в `.env`; тестовые подписки живут в OpenBao (`subscriptions:login`), не в `.env`. Узкие исключения для штатной разведки P3.0 и разрешённой 29.09.2026 локальной проверки — правило 1; они не распространяются на обычный dev, прод и проверку владельца P3 со своим OpenBao. Ещё одно узкое исключение — допущение стадии MVP по решению владельца от 05.10.2026 (правило 1): тестовый локальный ключ плана GLM на Z.ai лежит в корневом `.env` как `ZAI_API_KEY`, и у образов сервисов платформы один набор переменных окружения. В песочницу, логи и репозиторий этот ключ не попадает никогда.
3. **Прод один.** Код попадает на сайт только после «Применить»: бэкап → выкладка → проверка → автооткат. Контент меняется сразу, но перед правкой — снимок в `raditi-artifacts`; «Отменить» работает 7 дней (§7, §10, §11).
4. **Опасное — только через `request_approval`.** Удаление страниц, смена темы, плагины, настройки оплаты, массовые правки (больше 20 объектов). Пользователи и заказы сайта агенту недоступны.
5. **Песочница.** Задача — логическая сессия, контейнер — на один ход; в `awaiting_user` и `awaiting_approval` контейнера нет, сессия лежит в `raditi-sessions`. Docker + gVisor (`runsc`, systrap): dockerd от root, в контейнере uid 10001, read-only rootfs, cap-drop ALL, no-new-privileges, 2 vCPU, 4 ГБ, 512 процессов, 20 минут на ход; граница изоляции — gVisor. Сеть — internal без DNS и интернета, единственный выход — `sandbox-gw` с белым списком путей к шлюзу подписок (роль `llm`) и MCP-шлюзу. Долгоживущих секретов внутри нет, presigned-ссылок S3 тоже: файлы кладёт и забирает хост, коммит и push делает доверенная сторона (§8, §14).
6. **Пайплайн агент не меняет.** Выкладка — только обязательным пайплайном (в Gitea — workflow из `platform/ci`; для GitHub и GitLab клиента — открытый вопрос §20). Дифф агента отклоняется, если трогает пути CI (`.gitea/`, `.github/`, `.gitlab-ci.yml`, `.gitlab/`, `.forgejo/`, `.woodpecker*`, `.drone.yml`, `Jenkinsfile`, `bitbucket-pipelines.yml`, `.circleci/`), `.gitmodules` или `SiteAdapter.protectedPaths()` (§10).
7. **Квоты и кошелёк — через `credit_ledger`.** Резерв в `credit_holds` при постановке в очередь: на тарифе с квотой — одна правка, на «Оплате за действие» — сумма резерва по классу модели. Списание при `done` (на «Оплате за действие» — цена по `pricing_rules` из `token_usage` шлюза подписок по опубликованным учётным ставкам, не больше резерва; оценки по вине платформы не выставляются), возврат резерва при `failed` и `cancelled`. На тарифе с квотой порог допуска новых запросов попытки по учётным ставкам — 135, 285 и 735 ₽ для `light`, `standard` и `heavy`; шлюз учитывает оценочные резервы. Пока порог держит бюджет ключа хода: `issue` сверяет его с потолком класса или с резервом «Оплаты за действие» и с резервом первого вызова, а расход прежних ключей той же попытки считает нулём — общий расход попытки появится в P12. Перерасход уже допущенных запросов берёт платформа (§17). У каждой записи — ключ идемпотентности. Уточнение и «Изменить» — не новая задача, «Отменить» бесплатно (§17).
8. **Агент-агностичность.** Ядро знает только порты из `packages/domain`: `AgentDriver` и общие события (`started`, `message`, `command`, `file_change`, `tool_call`, `question`, `usage`, `completed`, `failed`), `SandboxProvider`, `TurnExecutor`, `TurnCredentialSource`, `TurnAssignmentStore`, `SiteLeaseStore`, `LlmBackend`, `GitProvider`, `SiteAdapter`, `SecretStore`, `ObjectStorage`, `JobQueue`. Никаких `if (driver === 'codex')`, `if (backend === 'openai-chatgpt')`, `if (provider === 'github')` или `if (cms === 'wordpress')` вне адаптера (§8, §13).
9. **Деньги — Decimal.** Цены показываем в ₽ с НДС. Суммы клиента — `Decimal(12,2)` и `Decimal(14,2)`; учётные ставки моделей — ₽ за 1 млн токенов с НДС, `Decimal(14,6)`, с историей (`effective_from`) и ставкой НДС `Decimal(5,4)`, утверждаются раз в квартал; стоимость аккаунта подписки — ₽ в месяц, `Decimal(12,2)`, с историей; себестоимость — `Decimal(18,10)`; наценка — `Decimal(8,4)`. Округление HALF_UP до копеек — один раз на действие. В DTO и API деньги — строки.
10. **Клиенту — по-русски и на «вы».** Без жаргона и английских терминов; `client_message` уходит клиенту как есть и проходит zod-схему итога хода (§8).

## Как писать код

- **Порты и адаптеры.** `packages/domain` — ядро: `DomainError`, порты и zod-схемы общих событий и итога хода; бизнес-логика со временем переезжает сюда. domain не зависит ни от одного пакета репозитория.
- Адаптеры реализуют порты и зависят только от domain: `db`, `storage`, `vault`, `git-providers`, `sandbox-providers`, `agent-drivers`, `llm-backends` (с P3), `site-adapters`, `yookassa`, `mail`, `telegram`. Реализации одного порта — в одном пакете: `git-providers` — gitea, github, gitlab; `sandbox-providers` — docker; `agent-drivers` — codex, kimi, opencode, qwen (opencode — драйвер G3 перехода на Z.ai, реализован локально, его строка в базе выключена до переключения продукта, G8; qwen — код P1, выключен, в продукт не входит); `llm-backends` — openai-chatgpt, kimi-code, zai-coding; `site-adapters` — wordpress, bitrix.
- Выше адаптеров — сервисы (`auth`, `notifications`), транспорт (`trpc`) и `ui`. Приложения (`web`, `orchestrator`, `e2e`) — точка сборки: создают адаптеры и подставляют их в порты. Зависимости только вниз, пакеты не импортируют приложения; слои проверяет dependency-cruiser.
- `observability` — сбоку от слоёв, только серверный код приложений: health, метрики, bearer-токен, `errorMessage` и `throttledLogger`. Зависит только от domain и `@prometheus-io/client`; импортируют его только приложения. Чистые помощники без ввода-вывода, нужные и доверенному коду (`withTimeout`, разбор env: `parseEnv`, `envVar`, `envProblems`, `Env`), — в domain.
- Пакеты называются `@repo/<имя>`.
- zod на всех границах: вебхуки, tRPC, итог хода агента, события драйверов.
- Деньги в коде — Decimal (decimal.js), не `number`. В DTO и API — строки с фиксированным числом знаков (`toFixed`), их проверяют zod-схемы.
- Новая переменная окружения — сразу в `.env.example` и в `globalEnv` в `turbo.json`. Переменные, которые подставляет только compose app-ВМ (`APP_DOMAIN`, `ACME_*`, образы и т. п.), — в `infra/app/env.example`: приложения их не читают.
- Ошибки домена — `DomainError`, как в AnyNote.
- Статусы задачи — только из §7: `queued`, `preparing`, `running`, `awaiting_user`, `awaiting_approval`, `deploying`, `verifying`, `done`, `failed`, `rolled_back`, `cancelled`.
- Бакеты — `raditi-inbox`, `raditi-sessions`, `raditi-logs`, `raditi-artifacts`, `raditi-backups`, `raditi-platform` (§14).
- Метрики — `@prometheus-io/client`. В метки не кладём `task_id`, `user_id` и другие идентификаторы; Prometheus — не источник для биллинга.
- Тесты рядом с кодом (Vitest). Всё, что трогает деньги, квоты, Vault, выкладку и откат, — только с тестами.
- Применённые миграции не редактируем: изменения схемы и CHECK-ограничений — следующей миграцией с сохранением данных.
- Миграция, команды которой должны примениться вместе (например, `DROP` и `ADD` одного ограничения), оборачивается в `BEGIN` и `COMMIT`: `prisma migrate deploy` отправляет файл по одной команде, каждую в своей транзакции. Проверка файла одним запросом через `pg` этого не показывает.
- Коммиты — Conventional Commits на английском (релизы собирает semantic-release), по одной задаче из roadmap.
- Язык: общение и документы — русский; код, идентификаторы и комментарии — английский; тексты интерфейса — русский.

## Как работать в этом репозитории

Решение владельца от 30.09.2026: всю реализацию и проверки вести локально. До выкладки на облачные серверы пройти полный локальный e2e с настоящим WordPress: задание → агент → правка → «Применить» → бэкап → выкладка → проверка → откат; для контента — снимок и «Отменить». Критерии — `infra/dev/site-verify/README.md`. Подготовительный `pnpm verify:site` проверяет страницу и её восстановление, полный продуктовый гейт остаётся открытым до подключения платформы. Облачные проверки P3.0/P14 и M10 отложены до успешного полного прохода.

1. Перед задачей прочитай её строку в `docs/plan/roadmap.md` и указанные разделы spec.
2. Задача трогает больше трёх файлов — сначала план, потом код.
3. Похожий код сначала ищи в `../AnyNote` (агент `anynote-scout`) и адаптируй под правила выше, а не копируй вслепую.
4. В конце — `pnpm typecheck && pnpm lint && pnpm test` для затронутых пакетов и `pnpm check-architecture`.
5. Перед коммитом — `/spec-check`.
6. Если решение меняется — обнови `docs/spec.md` и скажи об этом в ответе.

## Локальная разработка на macOS

gVisor работает только на Linux. На Mac песочница запускается с `SANDBOX_RUNTIME=runc`; изоляцию под `runsc` проверяй в Linux-ВМ (OrbStack, Colima, Lima) или на dev-сервере. Код раннера не должен зависеть от runtime — он приходит из конфигурации.
