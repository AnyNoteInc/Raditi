# Радити

Радити (raditi.ru) — сервис для малого бизнеса: владелец пишет в веб-чат или Telegram, что поменять на сайте, и AI-агент меняет его сайт — в MVP на WordPress, дальше на 1С-Битрикс и других CMS. Контент правится прямо на сайте со снимком для отката, код — через git-репозиторий сайта (наша Gitea или GitHub/GitLab клиента): ветка, PR, «Применить», выкладка с бэкапом, проверкой и автооткатом. Окружение у сайта одно — прод.

Проверяет ключ хода (его выдаёт `core` вместе с выбором аккаунта пула), подставляет ключ аккаунта — ключ плана или ключ API, держит бюджет ключа хода (с потолком попытки его сверяет `issue` в `core`; расход по нескольким ключам одной попытки — P12), пишет расход из ответов провайдера в `llm_calls` и `token_usage`; к провайдерам ходит через узел выхода `egress-1`, когда задан его прокси, — тогда через него идут все провайдеры; без прокси — сама и только к провайдеру, чей бэкенд объявил, что узел ему не нужен (Z.ai). - Команды оператора биллинга — `pnpm --filter orchestrator billing:refund -- <orderId> --reason "…" [--end-subscription] [--take-credits] [--refunded-in-cabinet]`, `billing:stop-renewal -- <email> --reason "…"`, `billing:refunds-needed`, `billing:settle-payment -- <paymentId>` либо `-- --order <orderId> --not-found --reason "…"`, `billing:rates -- --file <rates.json> --reason "…" [--effective-from <момент ISO со смещением>] [--confirm-exposure] [--confirm-mixed-models]`. Окружение задаётся явно (`APP_ENV`, `DATABASE_URL`; для обращений к магазину — `YOOKASSA_*`; для проведения платежа — ещё `APP_URL`), `.env` не читается; описание — в начале `apps/orchestrator/src/billing/operator-cli.ts`. `billing:rates` — единственное, что пишет учётные ставки моделей (`llm_model_prices`) и курс кредита (`credit_rates`): строки ставок из файла и одна строка курса записываются с одним моментом начала, одной транзакцией. Перед записью команда печатает, что курс значит для платформы: учётную стоимость каждого тарифа и пакета и её долю в цене, не потраченные кредиты пакетов и подарков в рублях, шаги попытки против предела ключа хода и «кредитов за 1 млн токенов» по включённым моделям. `--confirm-exposure` нужен, когда учётная стоимость тарифа выше половины его цены или курс меняется больше чем на 10%, `--confirm-mixed-models` — когда у включённых моделей одного класса разные ставки. Ей нужны только `APP_ENV` и `DATABASE_URL`; сама она не запускается, сидами курс и ставки не заполняются: первую строку утверждает владелец (spec §17, «Учётные ставки»); файл ставок профилей `zai-api` по курсу ЦБ на 17.10.2026 с маржой 30% и курсом кредита 6,00 ₽ — `infra/billing/rates/2026-10-17-zai-api.json` (П85), в базу окружения он не записан.
- `pnpm --filter orchestrator verify:snapshots` — локальная интеграционная проверка P1 на SeaweedFS + OpenBao из `.env`: временные синтетические данные, без моделей; свой Transit-ключ и S3-объекты удаляются после проверки. С G7 стенд идёт на образцовом драйвере `opencode` и двух файлах его сессии; без корневого `.env` — так же, как `verify:runner` ниже.
- `pnpm --filter orchestrator verify:runner` — гейты 2 и 3 P2: `core` на этой машине (локальная инфраструктура из `.env`), раннер в Linux-ВМ под gVisor (Colima). Семь сценариев: два полных хода с restore; `kill -9` `core`, раннера и обоих сразу; отмена хода до выдачи `prepare` и сразу после неё; падение `core` после контрольной точки без раннера; падение `core` до выдачи `prepare`. Образы собираются в демоне ВМ; переменные `P2_RUNNER_*` и повтор — `docs/plan/03-p2-verification.md`. Всё созданное удаляется. Синтетический агент стенда с G7 идёт на драйвере `opencode`: печатает строки `opencode run --format json`, пишет базу сессии и её журнал и на втором ходе требует строку первого в обоих файлах (отчёт P2 описывает прежнего синтетического агента). Пакетная команда читает корневой `.env`; без него скрипт запускается напрямую — `node scripts/verify-runner.mjs` в `apps/orchestrator` после `pnpm --filter orchestrator build` — с явным окружением над одноразовыми PostgreSQL, SeaweedFS и OpenBao: переменные и порядок — `docs/plan/47-common-scenarios-zai.md`, «`verify:runner`, `verify:snapshots`, `verify:transport`» (П47).
- `pnpm verify:edge` — сквозная проверка края app-ВМ: сборка образов web и orchestrator, Traefik выпускает сертификаты у локального Pebble, web отвечает по HTTPS, core снаружи и из сети web не виден, API раннеров — HTTP только на частном адресе, тела запросов к API ограничены на краю и в web; `-- --no-build` — без пересборки образов, `-- --renewal` — плюс продление, `-- --real-address` — только в CI с `userland-proxy: false`. Порты 18080, 18443, 18083 и 15000 на `127.0.0.1` должны быть свободны; результаты — `docs/plan/04-edge-verification.md`.
- Health: web `/api/health`, orchestrator `/health` — публично только status; подробности web и core — с `Authorization: Bearer $METRICS_TOKEN`, MCP и `llm` всегда только status. Метрики — `/api/metrics` и `/metrics` с тем же токеном (у `mcp` метрик нет, у `llm` — на своём порту :8084).

## Правила, которые нельзя нарушать

1. **Хранилища — в России, модель — GLM на Z.ai.** База, S3, логи, снимки и журналы платформы — только у российских провайдеров. Задания, сообщения и файлы клиента, код и содержимое его сайта обрабатывает сейчас одна модель — GLM на Z.ai (стенды и синтетика — по плану GLM Coding Plan; production — API с оплатой за токены, П15), в одной оболочке — OpenCode CLI (решение владельца от 04.10.2026; прежние оболочки и их провайдеры удалены 11.10.2026, G8). Других провайдеров моделей сейчас нет; моделей для агентов может стать больше, пока — только GLM на Z.ai с настоящим ключом (владелец, 17.10.2026). Юрлицо и страна получателя не установлены: по открытым источникам договор международного z.ai заключается с JINGSHENG HENGXING TECHNOLOGY PTE. LTD. (Сингапур), а страна, где обрабатываются запросы, не названа (`docs/research/2026-10-opencode-glm/zai-terms.md`, 05.10.2026) — это найденные сведения, а не заключение юриста. Сообщения и файлы клиента сначала записываются в PostgreSQL и S3 в России; прямого пути «браузер → провайдер модели» нет. К провайдеру ходит только шлюз подписок (роль `llm`): к `api.z.ai` — напрямую, когда прокси узла выхода не задан (решение владельца от 05.10.2026, П2), через узел — когда задан; тела запросов нигде не пишутся. Данные клиентов уходят провайдеру только после гейта 152-ФЗ с получателем Z.ai (§18); до него на модель идут только синтетические данные, а `issue` не выдаёт ключ хода задаче с классом данных `client` без действующей записи в `cross_border_clearances` для провайдера её модели. План по условиям Z.ai личный, поэтому production использует API Z.ai с оплатой за токены (`https://api.z.ai/api/paas/v4`) — решение владельца от 16.10.2026 (П15, spec §20); его бэкенд `zai-api` сделан 17.10.2026 ([отчёт 52](docs/plan/52-zai-api-backend.md)); стенды и синтетика идут и на плане, а в production включается только `zai-api`, и запись `cross_border_clearances` — только для него (П79). Решение П15 гейт 152-ФЗ не закрывает: получателя и страну устанавливает юрист (П1). В обычном dev настоящий план не подключён: сервисы платформы `ZAI_API_KEY` не читают, роль `llm` берёт ключ только из Vault `subs/`, куда его кладёт импорт оператора, а детерминированные стенды, тесты и CI идут на синтетическом Z.ai. Если ключ плана из `.env` импортирован в dev — это допускает решение владельца от 05.10.2026 к П14, — гейт такую работу не остановит: вне production кабинет создаёт рабочие пространства с классом `synthetic`, а для них `issue` записи в `cross_border_clearances` не спрашивает. Поэтому в dev и на стендах — только синтетические сайты, задания и файлы; настоящий сайт клиента к ним не подключается (spec §18, «Гейт 152-ФЗ»; spec §20, «Класс данных вне production»). Живой режим стендов — `--live` у `pnpm verify:llm-gateway` (в том числе `--live --api` — на API с оплатой за токены) и `pnpm verify:agent-content` — единственный разрешённый путь к настоящему GLM вне продукта: только синтетика, только этими командами вручную, с пределом запросов провайдеру, никогда в CI. Ключ живого режима, в том числе `--live --api`, — `ZAI_API_KEY`: настоящий ключ общего с production аккаунта Z.ai с небольшим балансом для проверок; живая проверка API идёт на нём по решению владельца от 17.10.2026 — это прямое исключение из запрета production-секретов на стендах ниже, других переменных ключа Z.ai нет. Скрипты пробы 04–05.10.2026 в `docs/research/2026-10-opencode-glm/scripts` тоже обращаются к `api.z.ai` с ключом из `PROBE_KEY_FILE`, но предела запросов у них нет: это записанная история разведки, а не путь проверок. Данные клиентов и production-секреты в dev, на стендах и в проверках запрещены; записи обменов попадают в репозиторий только очищенными (`infra/dev/llm-verify/sanitize-samples.mjs`). Персональные данные третьих лиц — посетителей, авторов комментариев и заявок, клиентов сайта — агенту не передаются (§11). Никаких других зарубежных API с данными клиентов.
2. **Секреты — только в Vault.** В базе — `credential_refs` (путь в Vault), в коде, логах, S3 и Git — никогда. Форма доступов пишет в Vault и не умеет читать обратно. Сервисы входят по AppRole со своими политиками (§15). Ключ аккаунта пула — ключ плана или ключ API — только в Vault mount `subs/` (`max_versions=1`, `cas_required`): кладёт его команда оператора `subscriptions:login` (импорт пишет и не читает обратно), читает только роль `llm` — её политика в `subs/` одно чтение, — удаляет только политика admin при выводе аккаунта. В песочницу, на песочную ВМ и `egress-1`, в `turn_assignments.plan`, логи и метрики он не попадает: в песочницу идут только ключ хода и токен MCP. Локально ключи сервисов можно держать в `.env`. Исключение — допущение стадии MVP по решению владельца от 05.10.2026 (П9): тестовый ключ Z.ai лежит в локальном корневом `.env` как `ZAI_API_KEY`; по решению владельца от 17.10.2026 это настоящий ключ общего с production аккаунта с небольшим балансом для проверок, он работает и на пути плана, и на пути API. Сервисы платформы эту переменную не читают; живой режим стендов берёт её из своего окружения и передаёт значение только на stdin импорта в свой одноразовый OpenBao. Тот же ключ берёт живая проверка API `--live --api` (решение владельца от 17.10.2026, П77): других переменных ключа Z.ai нет. Значение не печатается и не попадает в аргументы процессов, логи, записи, репозиторий и песочницу; агентам читать `.env` нельзя (`.claude/settings.json` запрещает инструменту чтения, но не командам оболочки — запрет держится на этом правиле). Тем же решением у сервисов платформы — web, `core`, `mcp`, `llm`, раннер — на стадии MVP один набор переменных окружения.
3. **Прод один.** Код попадает на сайт только после «Применить»: бэкап → выкладка → проверка → автооткат. Контент меняется сразу, но перед правкой — снимок в `raditi-artifacts`; «Отменить» работает 7 дней (§7, §10, §11).
4. **Опасное — только через `request_approval`.** Удаление страниц, смена темы, плагины, настройки оплаты, массовые правки (больше 20 объектов). Пользователи и заказы сайта агенту недоступны.
5. **Песочница.** Задача — логическая сессия, контейнер — на один ход; в `awaiting_user` и `awaiting_approval` контейнера нет, сессия лежит в `raditi-sessions`. Docker + gVisor (`runsc`, systrap): dockerd от root, в контейнере uid 10001, read-only rootfs, cap-drop ALL, no-new-privileges, 2 vCPU, 4 ГБ, 512 процессов, 20 минут на ход; граница изоляции — gVisor. Сеть — internal без DNS и интернета, единственный выход — `sandbox-gw` с белым списком путей к шлюзу подписок (роль `llm`) и MCP-шлюзу. Долгоживущих секретов внутри нет, presigned-ссылок S3 тоже: файлы кладёт и забирает хост, коммит и push делает доверенная сторона (§8, §14).
6. **Пайплайн агент не меняет.** Выкладка — только обязательным пайплайном (в Gitea — workflow из `platform/ci`; для GitHub и GitLab клиента — открытый вопрос §20). Дифф агента отклоняется, если трогает пути CI (`.gitea/`, `.github/`, `.gitlab-ci.yml`, `.gitlab/`, `.forgejo/`, `.woodpecker*`, `.drone.yml`, `Jenkinsfile`, `bitbucket-pipelines.yml`, `.circleci/`), `.gitmodules` или `SiteAdapter.protectedPaths()` (§10).
7. **Квоты и кошелёк — через `credit_ledger`.** Резерв в `credit_holds` при постановке в очередь: на тарифе с квотой — одна правка, на «Оплате за действие» — сумма резерва по классу модели. Списание при `done` (на «Оплате за действие» — цена по `pricing_rules` из `token_usage` шлюза подписок по опубликованным учётным ставкам, не больше резерва; оценки по вине платформы не выставляются), возврат резерва при `failed` и `cancelled`. На тарифе с квотой порог допуска новых запросов попытки по учётным ставкам — 135, 285 и 735 ₽ для `light`, `standard` и `heavy`; шлюз учитывает оценочные резервы. Пока порог держит бюджет ключа хода: `issue` сверяет его с потолком класса или с резервом «Оплаты за действие» и с резервом первого вызова, а расход прежних ключей той же попытки считает нулём — общий расход попытки появится в P12. Перерасход уже допущенных запросов берёт платформа (§17). У каждой записи — ключ идемпотентности. Уточнение и «Изменить» — не новая задача, «Отменить» бесплатно (§17). С 11.10.2026 резерв и списание в `@repo/billing` идут в кредитах (решение владельца от 10.10.2026, срезы M5.27a и M5.27b): резерв раскладывается по счетам в порядке тариф → подарок → пакет, списывается только выполненная задача — от расхода токенов и не больше резерва. Числа этой механики (шаги, минимум, границы) — значения по умолчанию из проекта, владелец их не подтверждал, поэтому фразы этого правила о «правке» выше не переписаны; действующее описание — spec §17, «Правила списания», текст на замену — в плане биллинга перед «Состоянием срезов».
8. **Агент-агностичность.** Ядро знает только порты из `packages/domain`: `AgentDriver` и общие события (`started`, `message`, `command`, `file_change`, `tool_call`, `question`, `usage`, `completed`, `failed`), `SandboxProvider`, `TurnExecutor`, `TurnCredentialSource`, `TurnAssignmentStore`, `SiteLeaseStore`, `LlmBackend`, `GitProvider`, `SiteAdapter`, `SecretStore`, `ObjectStorage`, `JobQueue`. Никаких `if (driver === 'opencode')`, `if (backend === 'zai-coding')`, `if (provider === 'github')` или `if (cms === 'wordpress')` вне адаптера (§8, §13).
9. **Деньги — Decimal.** Цены клиенту — в ₽, без НДС: продавец — самозанятая (решение владельца от 04.10.2026); чеков 54-ФЗ нет, объект `receipt` в платёж ЮKassa не передаётся, о чеках и «с НДС» в текстах для клиента не пишем — кроме оферты и связанных с ней юридических текстов: там чек из «Мой налог» назван обязанностью исполнителя словами AnyNote, вне продукта, а о НДС сказано только «не облагается» (оставить ли чек в оферте, владелец не подтверждал; вопрос юристу — `apps/web/content/legal/README.md`). НДС остаётся только в учётных ставках моделей — это расходы платформы. Суммы клиента — `Decimal(12,2)` и `Decimal(14,2)`; учётные ставки моделей — ₽ за 1 млн токенов с НДС, `Decimal(14,6)`, с историей (`effective_from`) и ставкой НДС `Decimal(5,4)`, утверждаются раз в квартал; стоимость аккаунта подписки — ₽ в месяц, `Decimal(12,2)`, с историей; себестоимость — `Decimal(18,10)`; наценка — `Decimal(8,4)`. Округление HALF_UP до копеек — один раз на действие. В DTO и API деньги — строки.
10. **Клиенту — по-русски и на «вы».** Без жаргона и английских терминов; `client_message` уходит клиенту как есть и проходит zod-схему итога хода (§8).

## Как писать код

- **Порты и адаптеры.** `packages/domain` — ядро: `DomainError`, порты и zod-схемы общих событий и итога хода; бизнес-логика со временем переезжает сюда. domain не зависит ни от одного пакета репозитория.
- Адаптеры реализуют порты и зависят только от domain: `db`, `storage`, `vault`, `git-providers`, `sandbox-providers`, `agent-drivers`, `llm-backends` (с P3), `site-adapters`, `site-connections`, `yookassa`, `mail`, `telegram`. Реализации одного порта — в одном пакете: `git-providers` — gitea, github, gitlab; `sandbox-providers` — docker; `agent-drivers` — opencode, единственный драйвер; `llm-backends` — zai-coding и zai-api, два описания одного адаптера Z.ai; `site-adapters` — wordpress, bitrix.
- Выше адаптеров — сервисы (`auth`, `notifications`, `billing`), транспорт (`trpc`) и `ui`. Приложения (`web`, `orchestrator`, `e2e`) — точка сборки: создают адаптеры и подставляют их в порты. Зависимости только вниз, пакеты не импортируют приложения; слои проверяет dependency-cruiser.
- `observability` — сбоку от слоёв, только серверный код приложений: health, метрики, bearer-токен, `errorMessage` и `throttledLogger`. Зависит только от domain и `@prometheus-io/client`; импортируют его только приложения. Чистые помощники без ввода-вывода, нужные и доверенному коду (`withTimeout`, разбор env: `parseEnv`, `envVar`, `envProblems`, `Env`), — в domain.
- Пакеты называются `@repo/<имя>`.
- zod на всех границах: вебхуки, tRPC, итог хода агента, события драйверов.
- Деньги в коде — Decimal (decimal.js), не `number`. В DTO и API — строки с фиксированным числом знаков (`toFixed`), их проверяют zod-схемы.
- В коде биллинга (`packages/domain/src/billing`, `@repo/billing`, роутер `billing`, компоненты и письма) `credit` — только существительное и только единица клиента «кредит»: счета `credit_tariff` и `credit_pack`. Платёж не «credited», а «applied» (`applyFirstPayment`, `applyPackPayment`); кредиты начисляются (granted), откладываются (held), списываются (charged), возвращаются (returned) и сгорают (expire). Кредиты провайдера модели «кредитом» без пояснения не называются: в документах — «кредиты плана» (план GLM Coding Plan на Z.ai, П31; в истории — «кредит Codex»), в новых идентификаторах — `providerCredits…`. Таблицы `credit_holds` и `credit_ledger` имена сохраняют (spec §17, «Слова»).
- Новая переменная окружения — сразу в `.env.example` и в `globalEnv` в `turbo.json`. Переменные, которые подставляет только compose app-ВМ (`APP_DOMAIN`, `ACME_*`, образы и т. п.), — в `infra/app/env.example`: приложения их не читают.
- Ошибки домена — `DomainError`, как в AnyNote.
- Статусы задачи — только из §7: `queued`, `preparing`, `running`, `awaiting_user`, `awaiting_approval`, `deploying`, `verifying`, `done`, `failed`, `rolled_back`, `cancelled`.
- Бакеты — `raditi-inbox`, `raditi-sessions`, `raditi-logs`, `raditi-artifacts`, `raditi-backups`, `raditi-platform` (§14).
- Метрики — `@prometheus-io/client`. В метки не кладём `task_id`, `user_id` и другие идентификаторы; Prometheus — не источник для биллинга.
- Тексты о лимитах страницы берут из `apps/web/src/components/billing/task-notice.ts` (выбор по `newTask.reason` из ответа сервера), числа-примеры и фразы блока «Как считаются кредиты» — из `credits-examples.ts`; своих условий «хватает ли кредитов» компоненты не пишут. Фикстуры компонентов считают ответ сервера настоящим `newTaskVerdict` (`taskCreditsFor` в `components/billing/testing.ts`).
- Личное рабочее пространство в продукте создаёт `ensurePersonalWorkspaceWithGift` из `@repo/billing`, а не `ensurePersonalWorkspace` из `@repo/db` напрямую: вместе с пространством начисляется подарок при регистрации. Новый код, который может создать личное пространство, вызывает её же.
- Тесты рядом с кодом (Vitest). Всё, что трогает деньги, квоты, Vault, выкладку и откат, — только с тестами.
- Фикстуры биллинга для тестов других пакетов — `@repo/billing/testing` (в том числе вызов модели: `token_usage` со всем, чего требуют его внешние ключи). Импортируют модуль только тестовые файлы и код `apps/e2e`, который тестовый целиком, — правило dependency-cruiser `billing-testing-only-in-tests`. Строка `credit_rates` и включённая модель принадлежат всей базе: тест, который их фиксирует, идёт только на одноразовой базе (`RADITI_GATEWAY_DB_TESTS=1`), а тест чтения пишет их в транзакции, которая откатывается. Тесту, которому нужен зафиксированный резерв, курс фиксировать не нужно: `placeReserve(db, placement)` (метод `billingFixtures.reserve`) ставит резерв штатной `placeCreditHold` под курсом, который пишется и удаляется в той же транзакции (`underPrivateCreditRate`); `settleTaskCharge` — проводящая половина списания — берётся из этого же модуля. Такие тесты идут и на общей базе.
- Тест, который читает файл вне своего пакета — из корня репозитория или из другого пакета, — называет этот файл в `inputs` задачи `test` в `turbo.json` (`$TURBO_ROOT$/…`, рядом с `$TURBO_DEFAULT$`): иначе `pnpm test` и `pnpm gates` вернут из локального кэша turbo прежний зелёный результат после правки одного этого файла. Так названы `.env.example` и оферта (`apps/web/content/legal/public-offer.md`); контракт — `infra/app/ci.test.mjs`.
- Тест или стенд `apps/orchestrator`, которому всё равно, чей драйвер и чей бэкенд, берёт id из `apps/orchestrator/src/testing/ids.ts` (`sampleDriverId`, `sampleBackendId`, `sampleProviderSlug`, `sampleProviderModelId`, `sampleModelSlug`, `sampleRoutePath`); тест поведения одного адаптера называет адаптер сам. В пакетах и `infra` образцовые id — литералы `opencode`, `zai-coding`, `glm-5.3`. Паре, которой нужны два разных id драйвера, второй — `otherDriverId` из того же файла: id вне списка, который место со схемой отклоняет. Тесту роли `llm`, которому нужен второй адаптер (чужой маршрут, повтор заголовка, узел выхода), его даёт синтетический адаптер самого теста, а не второй настоящий. Продуктовый код `src/testing` не импортирует — это держит правило dependency-cruiser `orchestrator-product-no-testing`.
- Id драйвера или бэкенда, ушедший из списков `agentDriverIds` и `llmBackendIds`, отвергается схемой там, где сохранённая строка читается обратно как работа, — протокол раннера, план хода, политика выдачи ключа, ссылка на снимок и его манифест, — и читатель такой строки отвечает постоянной ошибкой домена (`BAD_REQUEST` или `CONFLICT`), а не необработанным `ZodError`. Строки с таким id остаются историей: читатель истории (доверенный возврат правок, сборщики, здоровье пула) на них не падает, сиды их не создают и не трогают.
- Применённые миграции не редактируем: изменения схемы и CHECK-ограничений — следующей миграцией с сохранением данных.
- Миграция, команды которой должны примениться вместе (например, `DROP` и `ADD` одного ограничения), оборачивается в `BEGIN` и `COMMIT`. Остановку (`RAISE EXCEPTION` в блоке `DO $$ … $$`) ставят перед `BEGIN` — так сделано в `20261010180000_billing_credit_amounts` и `20261011090000_switch_to_opencode`: Prisma 7.10 шлёт файл миграции одним запросом и после сбоя пишет ошибку в `_prisma_migrations` тем же соединением — исключение внутри открытой транзакции оставляет соединение в оборванной транзакции, запись Prisma падает, и оператор видит «current transaction is aborted» вместо сообщения миграции (измерено 11.10.2026 на файле с `BEGIN`; по замеру ревью G8 одним запросом уходит и файл без `BEGIN` — `docs/plan/48-removal.md`, «Миграция»). Прежняя фраза этого правила — «`prisma migrate deploy` отправляет файл по одной команде, каждую в своей транзакции» — с этой версией Prisma не воспроизводится. Остановка применённой миграции B6 (`20260929130000_subscription_gateway`) поднята внутри `BEGIN`: по устройству файла (прогона не было) её сообщение останется только в логе PostgreSQL; применённые миграции не правятся (П50).
- Коммиты — Conventional Commits на английском (релизы собирает semantic-release), по одной задаче из roadmap.
- Язык: общение и документы — русский; код, идентификаторы и комментарии — английский; тексты интерфейса — русский.

## Как работать в этом репозитории

Решение владельца от 30.09.2026: всю реализацию и проверки вести локально. До выкладки на облачные серверы пройти полный локальный e2e с настоящим WordPress: задание → агент → правка → «Применить» → бэкап → выкладка → проверка → откат; для контента — снимок и «Отменить». Критерии — `infra/dev/site-verify/README.md`. Подготовительный `pnpm verify:site` проверяет страницу и её восстановление, полный продуктовый гейт остаётся открытым до подключения платформы. Облачные проверки P14 и M10 отложены до успешного полного прохода (P3.0 снят переходом на одну оболочку, П6).

1. Перед задачей прочитай её строку в `docs/plan/roadmap.md` и указанные разделы spec.
2. Задача трогает больше трёх файлов — сначала план, потом код.
3. Похожий код сначала ищи в `../AnyNote` (агент `anynote-scout`) и адаптируй под правила выше, а не копируй вслепую.
4. В конце — `pnpm typecheck && pnpm lint && pnpm test` для затронутых пакетов и `pnpm check-architecture`.
5. Перед коммитом — `/spec-check`.
6. Если решение меняется — обнови `docs/spec.md` и скажи об этом в ответе.
