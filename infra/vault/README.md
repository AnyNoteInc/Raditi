# Vault: локальная настройка и политики

Здесь находятся политики и явная настройка mounts: KV v2 для ключей хода (`turns/`) и ключей аккаунтов подписки (`subs/`), KV v2 `kv/` для доступов сайтов и карт контактов, Transit `transit/` для ключей рабочих пространств. Клиент `packages/vault` использует готовые mounts и политики; runtime их не создаёт. AppRole в проде, MFA оператора, vault-agent, аудит и ВМ Vault остаются P7/M10.

По указанию владельца от 30.09.2026 работа и проверки идут локально. До сквозного теста приложения с настоящим локальным сайтом выкладки в облако нет. Проверка ниже закрывает часть B5, но сама по себе ещё не является этим сквозным тестом.

## Политики

| Политика | Разрешения |
| --- | --- |
| `core-turns` | `create`, `read`, `delete` на `turns/data/*`; `read`, `update`, `list`, `delete` на metadata. Запись данных один раз: права `update` нет. `undelete` и отдельный endpoint `destroy` явно запрещены |
| `llm-subscriptions` | Только `read` на `subs/data/*`: роль `llm` читает ключ аккаунта и ничего не пишет — без создания, замены, metadata и удаления. Новый ключ и его замену записывает команда оператора (`subscriptions-writer`) |
| `subscriptions-writer` | `create`, `update` данных, `read` metadata ради версии CAS; чтение ключа запрещено |
| `subscriptions-admin` | `delete` metadata и `update` endpoint `destroy`; чтение ключа и metadata запрещено |
| `mcp-content` | Роль `mcp`. `read` на `kv/data/sites/+/wp` — только доступ WordPress, без `ssh`, `ftp`, `git`, `db` и `browser`, без записи. `read` на `kv/data/previews/+/wp` и `…/browser` — пароль приложения WordPress предпросмотра и секретный путь его браузера (план 53, Р21, Р24), без переменных сайта. `create`, `read`, `update` на `kv/data/content-masks/*` и `delete` на `kv/metadata/content-masks/*` — карта контактов задачи. `update` на `transit/datakey/plaintext/ws-*` и `transit/decrypt/ws-*` — ключ данных снимка контента |
| `core-transit` | Роль `core`, вместе с `core-turns`, `core-site-import` и `core-release`. `update` на `transit/datakey/plaintext/ws-*` и `transit/decrypt/ws-*` — ключ данных снимка хода |
| `sites-writer` | Доверенный шаг подключения сайта и web. `create`, `update` на `kv/data/sites/*`, `read` на `kv/metadata/sites/+/*` ради версии CAS; прочитать доступ обратно нельзя. Тем же правом web пишет переменные сайта `kv/sites/<siteId>/env/<NAME>` и удаляет их записью-надгробием (ниже); на `kv/metadata/sites/+/*` — ещё `create`, `update` с единственным разрешённым параметром `max_versions` = `"1"`: у переменной хранится одна версия, а «Удалить проект» (25.10.2026) перезаписывает каждый доступ и переменную сайта надгробием, которое остаётся единственной версией |
| `workspace-provisioner` | Web вместе с `sites-writer` — ключ рабочего пространства перед первой задачей (`task.create`, `transitEnsureKey`; план 57, Б32) — и доверенный шаг подключения сайта на стендах. `update` на `transit/keys/+` с единственным разрешённым параметром `type=aes256-gcm96` — создание ключа рабочего пространства; ни одного пути под ключом |
| `core-site-import` | Роль `core`, вместе с `core-turns`, `core-transit` и `core-release`. `read` на `kv/data/sites/+/ftp`, `…/ssh`, `…/git` и `…/db` — доступы, с которыми мастер подключения копирует файлы сайта и читает структуру базы. Без `wp` и `browser`, без записи, удаления, metadata и списков |
| `core-release` | Роль `core`, вместе с тремя политиками выше (план 53, Р13, Р24, Р29, Р35). `read` на `kv/data/sites/+/wp`, `kv/data/sites/+/env/*` и `kv/data/platform/gitea-org-owner` — доступ плагина для выпуска, переменные сайта для предпросмотра и агента, токен владельца организации Gitea. `create`, `read`, `update`, `delete` на `kv/data/previews/*` и `read`, `update`, `list`, `delete` на `kv/metadata/previews/*` (`update` — только `custom_metadata`, как у `core-turns`: `kvCreateOnce`) — секреты предпросмотров. `update` на `sys/wrapping/wrap`, `sys/wrapping/lookup` и `auth/token/revoke-accessor` — одноразовая обёртка доступа попытки выпуска. Токенов и политик не создаёт |

У политик нет путей к `ops/` и настройкам mounts; путей `sys/` и `auth/` нет ни у одной, кроме трёх названных у `core-release` (это проверяет `bootstrap.test.mjs`). Каждая политика называет только свои mounts: список разрешённых mounts на политику проверяет `bootstrap.test.mjs`. Обновление metadata ключа хода и секрета предпросмотра принимает только `custom_metadata`: runtime не может менять `max_versions`, `cas_required` или `delete_version_after` отдельного ключа. Metadata ключа сайта — доступа или переменной — web меняет одним параметром: `max_versions` со значением `"1"`.

### Политики контента

- **Transit у роли `mcp` — как в проверенном коде.** Снимок контента берёт ключ данных у `ws-<workspaceId>` — того же ключа, которым `core` шифрует снимки ходов. Поэтому каждая из двух ролей разворачивает ключ данных, обёрнутый другой; проверка это показывает. Оставить так или завести отдельное семейство ключей — вопрос владельцу (spec §20); до ответа политика совпадает с кодом. Путей к `transit/keys/*`, `export`, `encrypt`, `rewrap` и `datakey/wrapped` у ролей нет.
- **Карта контактов остаётся в `kv/content-masks/…`.** У `kv/` настройки сервера по умолчанию: прежние версии хранятся (по документации OpenBao — до 10), CAS не обязателен. Прежняя версия карты читается ролью `mcp` до удаления metadata; `DELETE kv/metadata/content-masks/…` убирает все версии сразу. Отдельный mount с `max_versions=1` и `cas_required` — решение P7.
- **Прежние доступы сайта тоже хранятся.** После замены доступа `kv/sites/<siteId>/wp` его прежняя версия читается ролью `mcp` (`?version=N`), а у `sites-writer` нет права её убрать: удаление версий и metadata ему закрыто. Убирает их оператор — или «Удалить проект»: web ставит ключу `max_versions` = `"1"` и пишет надгробие, и прежние версии уходят. Это следствие тех же настроек `kv/` и то же решение P7.
- **`workspace-provisioner`.** OpenBao 2.7 принимает создание ключа Transit как `update` (право `create` даёт 403). Путь — `transit/keys/+`: сам ключ и ничего под ним, поэтому `rotate`, `config` (и без параметров), `trim`, `soft-delete-restore`, `import_version` и остальные пути под ключом — 403. До 23.10.2026 путь был `transit/keys/ws-*`: glob покрывает и пути под ключом, и токен web (Б32) мог повернуть любой ключ `ws-*` и отменить мягкое удаление, которым оператор выключил ключ. Закрыть их запретом при glob нельзя — проверено на OpenBao 2.7.0: `transit/keys/ws-*/*` не действует (`*` внутри пути OpenBao читает буквально), а `transit/keys/+/*` и `transit/keys/+/+` проигрывают `ws-*` — приоритет у правила, у которого первый `+` или `*` стоит дальше от начала пути; `required_parameters` тоже не помогает: запросы под ключом проходят и с параметром `type`. Цена `+` — имя ключа сервер больше не проверяет: токен может создать ключ с другим именем, но только типа `aes256-gcm96`, неэкспортируемый и неудаляемый, и ни одна роль им не пользуется — у `core-transit` и `mcp-content` пути только `ws-*`. Имя `ws-<uuid>` проверяет клиент (`transitEnsureKey`) до запроса. Ограничение параметров закрывает другой тип ключа, `exportable`, `derived`, `allow_plaintext_backup` и импорт своего ключа (`import` — путь под ключом, материал ключа — тоже параметр). Повторное создание мягко удалённого ключа отвечает ключом как есть: он остаётся выключенным. Удаление (`DELETE` ключа и `soft-delete`), чтение, список, `export` и `backup` требуют других прав или лежат вне пути.
- **Ключи рабочих пространств bootstrap не создаёт.** Ключ `ws-<workspaceId>` создаёт web под `workspace-provisioner` до транзакции первой задачи рабочего пространства (повтор ключ не меняет; план 57, Б32), на стендах — и доверенный шаг подключения сайта. Обращение к Transit без ключа отвечает HTTP 400; роли `core` и `mcp` ключ не создают.

`core-turns` удаляет все версии через `DELETE turns/metadata/<name>` при окончательной уборке. Это отличается от запрещённого endpoint `turns/destroy/<name>` для выборочного уничтожения версий. После удаления metadata такой путь технически снова свободен; запрет повторного выпуска уже закрытого хода обеспечивают журнал и fence шлюза, которые подключаются в B10/P12.

### Политика импорта сайта

- **Политика постоянная и сайт не ограничивает.** `+` в пути — любой сайт: под `core-site-import` читаются четыре вида доступа каждого сайта, а не только того, который подключается. Токен на один сайт потребовал бы права выпускать токены, которого у политик нет. Сужение — в коде роли `core`: читатель доступов мастера подключения отказывает, если сайт не в статусе `onboarding` или этап не выполняется этим процессом (spec §15). Оставить так до production или вынести импорт в отдельную роль со своей AppRole — вопрос владельцу (spec §20).
- **Роль `mcp` эти доступы не читает.** `mcp-content` по-прежнему открывает только `wp`. Доступ к базе данных открыл бы пользователей и заказы сайта, которые агенту недоступны, а `mcp` — процесс, до которого дотягивается песочница. Отказ на `…/db` и `…/git` проверка ниже получает ответом сервера.
- **Прежние версии доступа читаются.** После замены доступа его прежняя версия по тому же пути читается ролью `core` (`?version=N`), а `sites-writer` убрать её не может — те же настройки `kv/`, что и у `wp`.
- **Секреты без ссылок.** Мастер пишет доступы в Vault до строк в базе, а удалить записанное не могут ни `sites-writer`, ни `core`. Если создание сайта отклонено уже после записи, в `kv/sites/<id>/…` остаются секреты, на которые не ссылается ни одна строка `credential_refs`: строка лога `site_connection_orphan site=<id>` называет сайт; удаляет оператор. Так же остаётся секрет прежнего вида, когда при замене доступа меняется вид источника (например, FTP на SFTP). `DELETE kv/metadata/sites/<id>/<вид>` убирает все версии сразу, после этого чтение отвечает «ключа нет».
- **Health.** После первого чтения доступа сайта health роли `core` проверяет и `kv/`. У политики только пути с `+`, без префикса; запрос `sys/internal/ui/mounts/kv` принимает и такой токен — проверено на OpenBao 2.7.0.
### Политика выпуска и предпросмотров

- **Обёртка вместо токена выкладки.** Доступ попытки выпуска (токен API выпуска и ключ данных бэкапа) уходит в задание выкладки одноразовой обёрткой `sys/wrapping/wrap` на 30 минут (план 53, Р29). `core` создаёт её, видит, вскрыта ли она (`sys/wrapping/lookup` отвечает 400 после вскрытия, отзыва или срока), и отзывает её по accessor (`auth/token/revoke-accessor`). Вскрывает обёртку только её собственный токен: своим токеном `core` её не вскроет (`sys/wrapping/unwrap` у политики нет — 403), задание вскрывает её без учётных данных Vault. Политик и токенов на сайт `core` во время работы не создаёт: `auth/token/create` и `sys/policies/acl` ему закрыты.
- **Отзыв по accessor не сужен до обёрток.** OpenBao отзывает по `auth/token/revoke-accessor` любой токен, чей accessor известен; accessor-ы чужих токенов `core` не узнаёт — `auth/token/lookup-accessor` и `lookup-self` ему закрыты. Отзыв уже вскрытой или истёкшей обёртки отвечает 200 с предупреждением «No token found with this accessor», клиент считает это отзывом. Запрос самого токена обёртки к чужому пути (например, `sys/wrapping/rewrap`) получает 403 и тратит обёртку: она одноразовая для любого запроса (проба на OpenBao 2.7.0, 17.10.2026).
- **`sys/wrapping/lookup` OpenBao 2.7.0 принимает и без токена** (та же проба); политика всё равно называет путь, клиент спрашивает со своим токеном.
- **Срок обёртки ограничивает клиент.** Сервер принял обёртку на 999 999 999 секунд; `createVaultSecretStore().wrap` принимает от 1 до 3600 секунд и всегда шлёт заголовок `X-Vault-Wrap-TTL` (без него сервер отвечает 400).
- **Переменные сайта удаляются надгробием и хранят одну версию.** Значение — `{"value":"…"}` в `kv/sites/<siteId>/env/<NAME>`; удаление — запись с CAS `{"removed":"<ISO 8601>"}`, которую читатели считают отсутствием переменной (`siteEnvVarSecret`, `siteEnvVarTombstone`, `siteEnvVarValueOf` из `@repo/domain`). Права удалять версии и metadata у `sites-writer` нет и для переменных не добавлено: иначе web смог бы стирать и доступы сайта. Вместо этого web перед каждой записью ставит ключу `max_versions` = 1 (`kvWrite(path, data, { cas, maxVersions: 1 })`): OpenBao удаляет прежнюю версию этой же записью, и заменённое или удалённое значение не читает никто, `core` тоже (`?version=N` — 404). Значение параметр получает строкой `"1"`: `allowed_parameters` OpenBao 2.7.0 сравнивает с числом из JSON ни одно значение списка не совпадает, число 1 получает 403 (проба 17.10.2026). Ограничение, поставленное после записи, действует со следующей записи. Правило чтения metadata у `sites-writer` поэтому записано как `kv/metadata/sites/+/*`, а не `kv/metadata/sites/*`: из двух правил одной политики, у которых подстановка начинается на одном месте, OpenBao берёт то, у которого меньше `+` (порядок приоритета из документации), и правило переменной уступило бы правилу без `+`; при равном числе `+` выигрывает более длинное. Обратно web значение не читает.
- **Секреты предпросмотра — собственность `core`.** Пароль приложения WordPress предпросмотра (`kv/previews/<previewId>/wp`) и секретный путь браузера (`…/browser`) пишет `core` — `kvWrite` с CAS или `kvCreateOnce` (metadata — только `custom_metadata`), читает роль `mcp`; пароли базы предпросмотра (`…/db`, пользователь и root; ответ владельца от 19.10.2026) `core` пишет при первой сборке с базой, отдаёт среде предпросмотров при каждой сборке и загрузке семени и удаляет вместе с предпросмотром — роль `mcp` их не читает; удаление metadata убирает все версии. `LIST kv/metadata/previews` отдаёт `core` все предпросмотры с секретами — для уборки уничтоженных.
- **Токен владельца организации Gitea** (`kv/platform/gitea-org-owner`, `{"v":"1","token":"…"}`) пишет оператор; читает только `core` (`giteaOrgOwnerToken` из `@repo/git-providers`). Ни одна другая политика его не открывает.

- **AppRole `core` получает политику до первого импорта.** Bootstrap записывает политику и роли не меняет: в `token_policies` роли, настроенной раньше, её добавляет оператор. Без неё чтение доступа — 403, клиент входит заново, а health роли `core` отвечает degraded («Vault KV mount kv/ is not available»), хотя ключи хода и Transit работают: `kv/` уже отслеживается, а у токена нет в нём ни одного пути. Токен, выданный до изменения роли, политику не получает; health восстанавливается с новым входом процесса — после перезапуска, истечения токена или ещё одного отказа в чтении, который сбрасывает токен.

## Явная настройка локального OpenBao

`bootstrap.mjs` принимает только числовой loopback-адрес. Токен оператора поступает со stdin и не выводится; `.env` и существующие токены скрипт не ищет и не читает. Передавайте токен из собственного безопасного источника через stdin, а не аргумент командной строки:

```sh
node infra/vault/bootstrap.mjs --address http://127.0.0.1:8200
```

Скрипт ждёт на stdin одну строку токена и EOF. В терминале stdin имеет обычное эхо, поэтому для ручного ввода токена используйте собственный инструмент ввода без эха или защищённый pipe. С `--wait` скрипт после чтения токена до 30 секунд ждёт, пока только что запущенный сервер ответит на `sys/health` статусом 200; пустой токен отклоняется сразу, без ожидания.

### Dev-OpenBao из `pnpm infra:up`

Сервис `vault` в `infra/dev/docker-compose.yml` работает в dev-режиме: хранилище в памяти, без тома. `pnpm infra:up` после `docker compose up -d` вызывает `pnpm vault:bootstrap`: root-токен dev-контейнера (`docker compose exec -T vault printenv BAO_DEV_ROOT_TOKEN_ID`) уходит через pipe в `bootstrap.mjs --address http://127.0.0.1:8200 --wait`, в аргументах и выводе его нет. Повторный запуск ничего не меняет. Отдельно шаг запускается командой `pnpm vault:bootstrap`, если контейнер `vault` уже работает.

Пересоздание контейнера (`pnpm infra:down`, перезапуск Docker) стирает mounts, политики и все секреты, а строки `subscription_accounts`, `llm_keys` и `credential_refs` в PostgreSQL и снимки в S3 остаются. Тогда bootstrap пишет, какие mounts он создал заново и что с ними потеряно: ключ каждого аккаунта подписки нужно импортировать заново (`subscriptions:login`), доступы сайтов и карты контактов — записать заново, ключи рабочих пространств — создать заново; снимки, обёрнутые прежними ключами, прочитать уже нельзя. Пока KV mount отсутствует, чтение и LIST на нём выглядят как «ключа нет»; поэтому health ролей `core`, `mcp` и `llm` проверяет каждый KV mount, с которым процесс уже работал, запросом `sys/internal/ui/mounts/<mount>` со своим токеном, и при пропаже mount или доступа к нему отвечает degraded. Так же health проверяет `transit/` — с первого обращения процесса за ключом данных. Отсутствие самого ключа `ws-…` health не видит: прав на `transit/keys/*` у ролей нет, ошибку даёт сам вызов.

Создаются только отсутствующие mounts:

| Mount | Настройки |
| --- | --- |
| `turns/` | KV v2, `max_versions=1`, `cas_required=true`, `delete_version_after=25m` |
| `subs/` | KV v2, `max_versions=1`, `cas_required=true`, автоматическое удаление отключено |
| `kv/` | KV v2, настройки сервера по умолчанию; скрипт их не задаёт и не проверяет |
| `transit/` | Transit; ключи скрипт не создаёт |

Повторный запуск проверяет конфигурацию существующих `turns/` и `subs/`, тип существующих `kv/` и `transit/` и обновляет десять политик. Существующие mounts не выключаются, не пересоздаются и не перенастраиваются; записи, ключи и metadata не меняются. Несовместимый тип, версия или конфигурация останавливают настройку до первого изменения и требуют отдельного разбора оператором. Настройки `kv/` (история версий, обязательный CAS) spec пока не задаёт — это решение P7; существующий `kv/` с любыми настройками и ключами скрипт оставляет как есть.

Включение mount и его настройка — два запроса. Только что включённый KV v2 mount несколько мгновений обновляется и отвечает на запись конфигурации HTTP 400; скрипт повторяет её до 20 раз с паузой 250 мс. Если прошлый запуск прервался между двумя запросами, mount остаётся с настройками OpenBao по умолчанию (`max_versions=0`, `cas_required=false`, `delete_version_after=0s`). Повторный запуск донастраивает такой mount на месте, только если в нём нет ни одного ключа (`LIST <mount>/metadata` отвечает 404); mount с ключами по-прежнему требует разбора оператором.

Клиент сначала записывает данные с `cas=0`, затем `custom_metadata`. Предварительное создание metadata превращает следующую запись данных в `update`, которого у `core-turns` нет. При повторе клиент читает живую запись, возвращает `exists` и чинит metadata; мягко удалённую версию он не заменяет. Ожидаемый в этой ветке ответ 403 не сбрасывает кэшированный токен AppRole: повтор не делает нового входа; отозванный токен сбрасывает следующее за ним чтение.

`custom_metadata` клиент проверяет до записи данных по правилам сервера, иначе секрет остался бы без metadata: не больше 64 ключей, ключ до 128 байт UTF-8, значение от 1 до 512 байт, только печатные символы (буквы, метки, цифры, пунктуация, символы и обычный пробел — `unicode.IsPrint` в Go).

Каждое строковое значение KV v2 — не длиннее 32 768 символов, имя поля — до 128 символов. Более длинное значение клиент отклоняет при записи до любого сетевого запроса (`packages/vault/src/kv.ts`); ответ чтения с таким значением считается ошибкой. Остальные лимиты клиента считаются в байтах: запросы и обычные ответы (AppRole, Transit, запись) — 64 КиБ, чтение KV и metadata — 1 МиБ, LIST — 16 МиБ. Больший предел чтения учитывает данные вместе с custom metadata, служебную обёртку и возможное шестикратное расширение строк при JSON-экранировании. LIST получает полный снимок префикса, затем сортирует ключи и применяет `after`/`limit` на клиенте; уменьшение страницы не уменьшает сетевой ответ. Каталоги больше 16 МиБ требуют разбиения по префиксам. Превышение любого предела отменяет чтение и возвращает ошибку, а не неполный список.

Через 25 минут версия `turns/` перестаёт читаться, но мягкое удаление не удаляет её физически из хранилища и старых снапшотов. Окончательная уборка удаляет metadata со всеми версиями; это отдельный шаг шлюза.

## Проверка на настоящем локальном OpenBao

```sh
node --test infra/vault/*.test.mjs
node infra/vault/verify-local.mjs
```

Unit-тесты входят в корневой `pnpm test:infra`. Живая проверка запускается отдельно и требует **уже загруженный** образ `ghcr.io/openbao/openbao:2.7.0`; `--pull=never` запрещает загрузку. Docker должен использовать локальный Unix socket или named pipe: TCP/SSH endpoints и удалённый context отклоняются до запуска контейнера. Часы демона не должны опережать часы хоста: `kvMetadata` считает версию удалённой, сравнивая `deletion_time` сервера с часами клиента, и сразу после мягкого удаления отвечает «не удалена», пока часы клиента не догонят. На Docker Desktop проверка проходит; на Colima, где часы ВМ шли впереди на 0,1–0,2 с, она падает на шаге «soft delete returns no data and retains a tombstone». Чтение данных от часов не зависит: удалённую версию сервер сам отдаёт как 404.

Создаётся один контейнер с уникальным именем и меткой владения, in-memory storage и случайным loopback-портом. OpenBao запускается обычным сервером, затем инициализируется и разблокируется через HTTP API. Случайные root token, unseal key, временные токены политик, токены обёрток, RoleID и SecretID трёх AppRole остаются в памяти процесса; их нет в аргументах Docker, окружении контейнера, конфигурации, файлах и выводе. Все credentials в проверяемых записях синтетические.

Проверяются реальные ACL и HTTP-ответы, CAS и конфликт версий, уничтожение первой версии `subs/` после второй записи, запрет чтения импортом подписок, отказ роли `llm` в записи, metadata и удалении `subs/`, write-once до окончательной уборки, мягкое удаление, LIST, срок версии `turns/` 25 минут и повтор настройки без изменения данных. До первой настройки проверка оставляет `turns/` включённым и ненастроенным, как после прерванного запуска: с ключом внутри bootstrap отказывает, ничего не меняя, а пустой mount донастраивает. Серверные пределы `custom_metadata` проверяются прямыми запросами: 65 ключей, значения 513 байт и пустое, перевод строки, неразрывный пробел и ключ 129 байт отклоняются, границы принимаются. Через настоящий `createVaultSecretStore` дополнительно проверяются порядок data → metadata, восстановление прерванной записи, версия при чтении, tombstone, страницы LIST, CAS и удаление всех версий; metadata на границах сервера и отказ до любого запроса при её нарушении; три повтора `kvCreateOnce` под AppRole с одноразовым SecretID — ровно один вход; health со своими токенами всех политик, root и AppRole — после выключения `subs/` он отказывает у пользователей `subs/` и восстанавливается после повторного bootstrap.

Права контента проверяются так же, ответами сервера:

- **Mounts.** `transit/` чужого типа останавливает bootstrap до первого изменения: `subs/` и `kv/` не созданы, политики не записаны. После настройки `kv/` — KV v2 с настройками по умолчанию, `transit/` — Transit.
- **`workspace-provisioner`.** Создаёт ключ `ws-<id>`, повтор его не меняет; ключ не экспортируемый и не удаляемый. Отказ: `rotate`, `config`, `trim` и `soft-delete-restore` — без параметров и с параметром `type`; другой тип (и у ключа с другим именем), `exportable`, `derived`, `allow_plaintext_backup`, `config` с параметрами, `import` и `import_version` с материалом ключа, чтение, удаление, `soft-delete`, список, `export`, `backup`, `restore`, ключ данных, `encrypt`, доступы сайта в `kv/` (`wp` и четыре вида импорта). Ключ с другим именем создаётся (имени сервер не проверяет) — неэкспортируемый, и роли `core` и `mcp` получают на нём 403. Ключ, мягко удалённый под root, отказывает роли `mcp` (400); `soft-delete-restore` и `rotate` под `workspace-provisioner` — 403, повторное создание отвечает 200, а ключ остаётся выключенным, с одной версией. После восстановления и ротации под root прежний ключ данных разворачивается, новый получает версию 2. Через клиент: токен web (`sites-writer` и `workspace-provisioner`) создаёт ключ `transitEnsureKey` дважды — версия одна, роль `core` берёт с ним ключ данных; ключ данных, чтение, `export`, список, `config` (с параметром и без), `rotate`, `trim`, `soft-delete`, `soft-delete-restore` и удаление web — 403, имя не `ws-<uuid>` адаптер отклоняет до запроса, `sites-writer` без `workspace-provisioner` — 403.
- **`sites-writer`.** Запись `kv/sites/<siteId>/wp`, `…/ftp`, `…/ssh`, `…/git` и `…/db` с `cas=0`, чтение данных каждого из пяти видов — 403, чтение metadata — версия, устаревший CAS — 400, замена с верным CAS (`wp` и `db`). Отказ: список, изменение и удаление metadata (`max_versions` у `wp` — тоже), удаление данных, `destroy`, карты контактов, `kv/platform/…`, `turns/`, `subs/`, Transit.
- **AppRole `mcp` (`mcp-content`).** Вход по RoleID и одноразовому SecretID, у токена ровно одна политика. Карта контактов: создание с `cas=0`, проигранная гонка — 400, чтение с версией, замена, устаревший CAS — 400, удаление metadata — и у root нет ни metadata, ни первой версии. Чтение `kv/sites/<siteId>/wp` с версией; прежняя версия доступа после замены тоже читается. Отказ: `…/ssh`, `…/ftp`, `…/db`, `…/git`, `…/browser`, путь глубже `wp`, запись и удаление доступа, metadata и списки сайтов, metadata и список карт, мягкое удаление, `delete`, `undelete`, `destroy`, `kv/platform/…`, `kv/config`, `turns/`, `subs/`, `ops/`, `sys/mounts`, выпуск токена. Transit: ключ данных и его расшифровка; отказ на `transit/keys/*` (чтение, создание, удаление, `config`, `rotate`, список), `export`, `backup`, `encrypt`, `rewrap`, `datakey/wrapped` и на ключ с именем без `ws-`. Рабочее пространство без ключа получает 400, и ключ при этом не появляется.
- **AppRole `core` (`core-turns`, `core-transit`, `core-site-import` и `core-release`).** Ключ данных и расшифровка, запись ключа хода тем же токеном, чтение доступа `wp` (под `core-release`). Ключ данных, обёрнутый ролью `core`, разворачивает роль `mcp`, и наоборот. Отказ: доступ сайта `browser`, карты контактов, `transit/keys/*`, `export`, `encrypt`, чужое имя ключа, `subs/`, `ops/`. Токены `core-turns`, `llm-subscriptions`, `subscriptions-writer` и `subscriptions-admin` по отдельности не получают ни ключа данных, ни доступа сайта (`wp` и четыре вида импорта), ни карты.
- **`core-site-import`.** AppRole `core` и токен одной этой политики отвечают одинаково. Чтение `kv/sites/<siteId>/ftp`, `…/ssh`, `…/git` и `…/db` с версией; прежняя версия заменённого доступа `db` тоже читается. Отказ: `…/wp` (токену одной политики; роль читает его под `core-release`), `…/browser`, сам путь `kv/data/sites/<siteId>`, путь глубже вида, списки сайтов, доступ другого сайта на запись, `kv/platform/…`, `kv/config`; для каждого из четырёх видов — запись (POST и PATCH), удаление данных, `subkeys`, чтение, изменение и удаление metadata, список под путём вида, `delete`, `undelete`, `destroy`. Токен одной политики не получает ещё и карту контактов, ключ хода и список `turns/`, `subs/`, ключ данных и расшифровку Transit, `transit/keys/*`, `ops/`, `sys/mounts` и выпуск токена.
- **Клиент под AppRole.** Через `createVaultSecretStore`: роль `core` берёт и разворачивает ключ данных и читает четыре доступа импорта тем же единственным входом; роль `mcp` ведёт карту (`kvRead`, `kvWrite` с CAS, конфликт, `kvDestroyAll`), читает доступ WordPress, берёт и разворачивает ключ данных — один вход. Health роли `mcp` видит `kv/` и `transit/`, роли `core` — `turns/`, `transit/` и, после чтения доступа сайта, `kv/`, каждая под своими политиками. Повторный bootstrap при работающих `kv/` и `transit/` их не трогает: доступ сайта остаётся той же версии, ключ рабочего пространства разворачивает прежний ключ данных. Политика `mcp-content`, из которой убраны пути Transit, даёт тот же отказ health роли `mcp` при работающем mount — тем же входом; повторный bootstrap записывает политику заново, и право возвращается. После выключения `transit/` health ролей `core` и `mcp` отказывает («Vault Transit mount transit/ is not available»), у остальных хранилищ — нет; повторный bootstrap возвращает mount, health восстанавливается, а обращение за ключом отвечает 400: ключа рабочего пространства больше нет. Отказ в доступе `…/ssh` роли `mcp` и `…/browser` роли `core` клиент возвращает как 403, а не как «ключа нет».
- **Выпуск и предпросмотры (`core-release`).** Web (`sites-writer`) ставит переменной `kv/sites/<siteId>/env/<NAME>` `max_versions` = `"1"` (и повторно — без изменений), пишет её с `cas=0`, читает её версию и предел из metadata и пишет надгробие с верным CAS; чтение значения (и прежней версии), `max_versions` `"2"`, `"0"` и числом 1, `cas_required`, `delete_version_after`, `custom_metadata`, PATCH metadata, `max_versions` у `wp` и `db`, удаление данных и metadata, `delete`, `destroy`, список переменных, секреты предпросмотра, токен владельца Gitea и обёртка — 403. AppRole `core` и токен одной `core-release`: секреты предпросмотра создаются, заменяются с CAS, читаются, получают `custom_metadata`, metadata и списки предпросмотров читаются, удаление metadata убирает все версии; `max_versions` (числом и строкой), `cas_required` и `delete_version_after` секрета предпросмотра — 403; надгробие переменной, токен владельца Gitea и доступ `wp` читаются, прежнее значение переменной — 404: его больше нет. Обёртка: без заголовка срока — 400; с ним — `wrap_info` с токеном, accessor, сроком 1800 и `creation_path` `sys/wrapping/wrap`, без данных в ответе; `lookup` — срок и путь; `unwrap` своим токеном — 403, обёртка после этого жива; вскрытие её токеном отдаёт данные, второе вскрытие и `lookup` — 400; отзыв вскрытой — 200; отзыв живой — 204, после него вскрытие и `lookup` — 400; `rewrap` живой — 403, и она остаётся. Отказ `core`: запись и список политик, `auth/token/create` и `create-orphan`, `auth/token/revoke`, `lookup-accessor`, `lookup-self`, `sys/mounts`, `subs/`, `…/browser`, запись `wp`, переменной и токена владельца, metadata переменной и токена владельца, другие пути `kv/platform/`. Роль `mcp` читает оба секрета предпросмотра; отказ: другой вид секрета, запись, удаление, metadata (чтение и `custom_metadata`) и список предпросмотра, переменные сайта, токен владельца, обёртка, отзыв. Остальные девять политик не получают ни обёртки, ни отзыва, ни токена владельца; секрет предпросмотра — только `mcp-content`, переменную — только `sites-writer` (запись).
- **Клиент выпуска.** Через `createVaultSecretStore`: роль `core` оборачивает доступ попытки на 1800 секунд и видит его невскрытым (`lookupWrapping`); хранилище без учётных данных, как у задания выкладки, вскрывает его один раз, второй раз — `null`, и `lookupWrapping` — `null`; отзыв вскрытой обёртки проходит; живая обёртка после `revokeAccessor` не вскрывается; обёртка на 1 секунду через 2,5 секунды не вскрывается. Роль `core` читает надгробие переменной, токен владельца Gitea и доступ `wp`, ведёт секрет предпросмотра с CAS, пишет секрет браузера один раз (`kvCreateOnce`: «создан», затем «уже есть», `custom_metadata` на месте, роль `mcp` его читает) и удаляет его со всеми версиями, роль `mcp` читает секрет предпросмотра — каждая одним входом AppRole. Web пишет переменную, её замену и надгробие с CAS и `maxVersions: 1`: после замены первая версия — 404, после надгробия — вторая; `maxVersions: 2`, чтение и удаление всех версий — 403. Токен одной `core-release` оборачивает, смотрит и отзывает; токены `core-site-import`, `mcp-content` и `sites-writer` обернуть не могут (403), `mcp-content` не читает переменную (403).
- **Клиент под токеном `core-site-import`.** Читает доступ `db` с версией, и его health видит `kv/`, хотя у политики только пути с `+`. Чтение `…/wp`, чтение metadata, запись и удаление всех версий клиент возвращает как 403. Доступ, который оператор удалил через metadata, пропадает со всеми версиями: клиент отвечает «ключа нет», прежняя версия — 404.
- **Клиент под AppRole `core` без политики импорта.** Третья AppRole — с `core-turns` и `core-transit`, как роль, настроенная до этой политики. Чтение доступа — 403; после него health отвечает «Vault KV mount kv/ is not available», а ключ хода читается — уже вторым входом. Когда роль получает политику, health с прежним токеном отказывает по-прежнему, чтение — 403 и сбрасывает токен; следующее чтение входит третий раз и получает доступ, health восстанавливается.

Регрессии лимитов проверяют запись ровно 64 КиБ со строками `<>&` и точное чтение после серверного JSON-экранирования, а также каталог из 1500 ключей с ответом больше 64 КиБ и обходом всех страниц без потерь. Каталог создаётся с ограничением 16 параллельных записей внутри того же одноразового контейнера.

При успехе выводится только сводка: образ, число проверок и флаги. Контейнер удаляется в `finally`; удаление допускается только при совпадении собственной метки. Уже работающие сервисы, mounts, тома и контейнеры проверка не меняет.
