# Vault: локальная настройка и политики

Здесь находятся политики и явная настройка mounts: KV v2 для ключей хода (`turns/`) и ключей аккаунтов подписки (`subs/`), KV v2 `kv/` для доступов сайтов и карт контактов, Transit `transit/` для ключей рабочих пространств. Клиент `packages/vault` использует готовые mounts и политики; runtime их не создаёт. AppRole в проде, MFA оператора, vault-agent, аудит и ВМ Vault остаются P7/M10.

По указанию владельца от 30.09.2026 работа и проверки идут локально. До сквозного теста приложения с настоящим локальным сайтом выкладки в облако нет. Проверка ниже закрывает часть B5, но сама по себе ещё не является этим сквозным тестом.

## Политики

| Политика | Разрешения |
| --- | --- |
| `core-turns` | `create`, `read`, `delete` на `turns/data/*`; `read`, `update`, `list`, `delete` на metadata. Запись данных один раз: права `update` нет. `undelete` и отдельный endpoint `destroy` явно запрещены |
| `llm-subscriptions` | Только `read` на `subs/data/*`: роль `llm` читает ключ аккаунта и ничего не пишет — без создания, замены, metadata и удаления. Новый ключ и его замену записывает команда оператора (`subscriptions-writer`) |
| `subscriptions-writer` | `create`, `update` данных, `read` metadata ради версии CAS; чтение ключа запрещено |
| `subscriptions-admin` | `delete` metadata и `update` endpoint `destroy`; чтение ключа и metadata запрещено |
| `mcp-content` | Роль `mcp`. `read` на `kv/data/sites/+/wp` — только доступ WordPress, без `ssh`, `ftp` и `browser`, без записи. `create`, `read`, `update` на `kv/data/content-masks/*` и `delete` на `kv/metadata/content-masks/*` — карта контактов задачи. `update` на `transit/datakey/plaintext/ws-*` и `transit/decrypt/ws-*` — ключ данных снимка контента |
| `core-transit` | Роль `core`, вместе с `core-turns`. `update` на `transit/datakey/plaintext/ws-*` и `transit/decrypt/ws-*` — ключ данных снимка хода |
| `sites-writer` | Доверенный шаг подключения сайта. `create`, `update` на `kv/data/sites/*`, `read` на `kv/metadata/sites/*` ради версии CAS; прочитать доступ обратно нельзя |
| `workspace-provisioner` | Доверенный шаг подключения сайта. `update` на `transit/keys/ws-*` с единственным разрешённым параметром `type=aes256-gcm96` — создание ключа рабочего пространства |

У политик нет путей к `ops/`, настройкам mounts и аутентификации. Каждая политика называет только свои mounts: список разрешённых mounts на политику проверяет `bootstrap.test.mjs`. Обновление metadata ключа хода принимает только `custom_metadata`: runtime не может менять `max_versions`, `cas_required` или `delete_version_after` отдельного ключа.

### Политики контента

- **Transit у роли `mcp` — как в проверенном коде.** Снимок контента берёт ключ данных у `ws-<workspaceId>` — того же ключа, которым `core` шифрует снимки ходов. Поэтому каждая из двух ролей разворачивает ключ данных, обёрнутый другой; проверка это показывает. Оставить так или завести отдельное семейство ключей — вопрос владельцу (spec §20); до ответа политика совпадает с кодом. Путей к `transit/keys/*`, `export`, `encrypt`, `rewrap` и `datakey/wrapped` у ролей нет.
- **Карта контактов остаётся в `kv/content-masks/…`.** У `kv/` настройки сервера по умолчанию: прежние версии хранятся (по документации OpenBao — до 10), CAS не обязателен. Прежняя версия карты читается ролью `mcp` до удаления metadata; `DELETE kv/metadata/content-masks/…` убирает все версии сразу. Отдельный mount с `max_versions=1` и `cas_required` — решение P7.
- **Прежние доступы сайта тоже хранятся.** После замены доступа `kv/sites/<siteId>/wp` его прежняя версия читается ролью `mcp` (`?version=N`), а у `sites-writer` нет права её убрать: удаление версий и metadata ему закрыто. Убирает их только оператор. Это следствие тех же настроек `kv/` и то же решение P7.
- **`workspace-provisioner`.** OpenBao 2.7 принимает создание ключа Transit как `update` (право `create` даёт 403), а glob `ws-*` покрывает и пути под ключом. Ограничение параметров закрывает опасное: `config` с любым параметром (`exportable`, `deletion_allowed`, `min_decryption_version`), `trim`, другой тип ключа, `derived`, импорт своего ключа (`import`, `import_version` — материал ключа тоже параметр). Удаление (`DELETE` ключа и `soft-delete`), чтение, список, `export` и `backup` требуют других прав или лежат вне пути. Действуют только два запроса без параметров: `rotate` и `soft-delete-restore`; `config` без параметров ничего не меняет, `import` с одним `type` сервер отклоняет сам. Ротация добавляет версию и ничего не ломает: `min_decryption_version` остаётся 1, прежние ключи данных разворачиваются. `soft-delete-restore` отменяет мягкое удаление: ключ, который оператор выключил, снова выдаёт и разворачивает ключи данных. Закрыть эти два запроса запрещающим правилом с `+` (`transit/keys/+/rotate`) нельзя: OpenBao отдаёт приоритет правилу, у которого glob стоит дальше от начала пути; `required_parameters` тоже не помогает — оба запроса проходят и с параметром `type`. Замена на `transit/keys/+` закрывает все пути под ключом, но разрешает создать ключ с любым именем. Всё это проверено на OpenBao 2.7.0.
- **Ключи рабочих пространств bootstrap не создаёт.** Ключ `ws-<workspaceId>` создаёт доверенный шаг подключения сайта под `workspace-provisioner`. Обращение к Transit без ключа отвечает HTTP 400, runtime ключ не создаёт.

`core-turns` удаляет все версии через `DELETE turns/metadata/<name>` при окончательной уборке. Это отличается от запрещённого endpoint `turns/destroy/<name>` для выборочного уничтожения версий. После удаления metadata такой путь технически снова свободен; запрет повторного выпуска уже закрытого хода обеспечивают журнал и fence шлюза, которые подключаются в B10/P12.

## Явная настройка локального OpenBao

`bootstrap.mjs` принимает только числовой loopback-адрес. Токен оператора поступает со stdin и не выводится; `.env` и существующие токены скрипт не ищет и не читает. Передавайте токен из собственного безопасного источника через stdin, а не аргумент командной строки:

```sh
node infra/vault/bootstrap.mjs --address http://127.0.0.1:8200
```

Скрипт ждёт на stdin одну строку токена и EOF. В терминале stdin имеет обычное эхо, поэтому для ручного ввода токена используйте собственный инструмент ввода без эха или защищённый pipe. С `--wait` скрипт после чтения токена до 30 секунд ждёт, пока только что запущенный сервер ответит на `sys/health` статусом 200; пустой токен отклоняется сразу, без ожидания.

### Dev-OpenBao из `pnpm infra:up`

Сервис `vault` в `infra/dev/docker-compose.yml` работает в dev-режиме: хранилище в памяти, без тома. `pnpm infra:up` после `docker compose up -d` вызывает `pnpm vault:bootstrap`: root-токен dev-контейнера (`docker compose exec -T vault printenv BAO_DEV_ROOT_TOKEN_ID`) уходит через pipe в `bootstrap.mjs --address http://127.0.0.1:8200 --wait`, в аргументах и выводе его нет. Повторный запуск ничего не меняет. Отдельно шаг запускается командой `pnpm vault:bootstrap`, если контейнер `vault` уже работает.

Пересоздание контейнера (`pnpm infra:down`, перезапуск Docker) стирает mounts, политики и все секреты, а строки `subscription_accounts`, `llm_keys` и `credential_refs` в PostgreSQL и снимки в S3 остаются. Тогда bootstrap пишет, какие mounts он создал заново и что с ними потеряно: ключ каждого аккаунта подписки нужно импортировать заново (`subscriptions:login`), доступы сайтов и карты контактов — записать заново, ключи рабочих пространств — создать заново; снимки, обёрнутые прежними ключами, прочитать уже нельзя. Пока KV mount отсутствует, чтение и LIST на нём выглядят как «ключа нет»; поэтому health ролей `core`, `mcp` и `llm` проверяет каждый KV mount, с которым процесс уже работал, запросом `sys/internal/ui/mounts/<mount>` со своим токеном, и при пропаже mount или доступа к нему отвечает degraded. Так же health проверяет `transit/` — с первого обращения процесса за ключом данных. Отсутствие самого ключа `ws-…` health не видит: прав на `transit/keys/*` у ролей нет, ошибку даёт сам вызов.

Создаются только отсутствующие mounts:

| Mount | Настройки |
| --- | --- |
| `turns/` | KV v2, `max_versions=1`, `cas_required=true`, `delete_version_after=25m` |
| `subs/` | KV v2, `max_versions=1`, `cas_required=true`, автоматическое удаление отключено |
| `kv/` | KV v2, настройки сервера по умолчанию; скрипт их не задаёт и не проверяет |
| `transit/` | Transit; ключи скрипт не создаёт |

Повторный запуск проверяет конфигурацию существующих `turns/` и `subs/`, тип существующих `kv/` и `transit/` и обновляет восемь политик. Существующие mounts не выключаются, не пересоздаются и не перенастраиваются; записи, ключи и metadata не меняются. Несовместимый тип, версия или конфигурация останавливают настройку до первого изменения и требуют отдельного разбора оператором. Настройки `kv/` (история версий, обязательный CAS) spec пока не задаёт — это решение P7; существующий `kv/` с любыми настройками и ключами скрипт оставляет как есть.

Включение mount и его настройка — два запроса. Только что включённый KV v2 mount несколько мгновений обновляется и отвечает на запись конфигурации HTTP 400; скрипт повторяет её до 20 раз с паузой 250 мс. Если прошлый запуск прервался между двумя запросами, mount остаётся с настройками OpenBao по умолчанию (`max_versions=0`, `cas_required=false`, `delete_version_after=0s`). Повторный запуск донастраивает такой mount на месте, только если в нём нет ни одного ключа (`LIST <mount>/metadata` отвечает 404); mount с ключами по-прежнему требует разбора оператором.

Клиент сначала записывает данные с `cas=0`, затем `custom_metadata`. Предварительное создание metadata превращает следующую запись данных в `update`, которого у `core-turns` нет. При повторе клиент читает живую запись, возвращает `exists` и чинит metadata; мягко удалённую версию он не заменяет. Ожидаемый в этой ветке ответ 403 не сбрасывает кэшированный токен AppRole: повтор не делает нового входа; отозванный токен сбрасывает следующее за ним чтение.

`custom_metadata` клиент проверяет до записи данных по правилам сервера, иначе секрет остался бы без metadata: не больше 64 ключей, ключ до 128 байт UTF-8, значение от 1 до 512 байт, только печатные символы (буквы, метки, цифры, пунктуация, символы и обычный пробел — `unicode.IsPrint` в Go).

Каждое строковое значение KV v2 — не длиннее 32 768 символов, имя поля — до 128 символов. Более длинное значение клиент отклоняет при записи до любого сетевого запроса (`packages/vault/src/kv.ts`); ответ чтения с таким значением считается ошибкой. Остальные лимиты клиента считаются в байтах: запросы и обычные ответы (AppRole, Transit, запись) — 64 КиБ, чтение KV и metadata — 1 МиБ, LIST — 16 МиБ. Больший предел чтения учитывает данные вместе с custom metadata, служебную обёртку и возможное шестикратное расширение строк при JSON-экранировании. LIST получает полный снимок префикса, затем сортирует ключи и применяет `after`/`limit` на клиенте; уменьшение страницы не уменьшает сетевой ответ. Каталоги больше 16 МиБ требуют разбиения по префиксам. Превышение любого предела отменяет чтение и возвращает ошибку, а не неполный список.

Через 25 минут версия `turns/` перестаёт читаться, но мягкое удаление не удаляет её физически из хранилища и старых снапшотов. Окончательная уборка удаляет metadata со всеми версиями; это отдельный шаг шлюза.

## Проверка на настоящем локальном OpenBao

```sh
node --test infra/vault/*.test.mjs
node infra/vault/verify-local.mjs
```

Unit-тесты входят в корневой `pnpm test:infra`. Живая проверка запускается отдельно и требует **уже загруженный** образ `ghcr.io/openbao/openbao:2.7.0`; `--pull=never` запрещает загрузку. Docker должен использовать локальный Unix socket или named pipe: TCP/SSH endpoints и удалённый context отклоняются до запуска контейнера. Часы демона не должны опережать часы хоста: `kvMetadata` считает версию удалённой, сравнивая `deletion_time` сервера с часами клиента, и сразу после мягкого удаления отвечает «не удалена», пока часы клиента не догонят. На Docker Desktop проверка проходит; на Colima, где часы ВМ шли впереди на 0,1–0,2 с, она падает на шаге «soft delete returns no data and retains a tombstone». Чтение данных от часов не зависит: удалённую версию сервер сам отдаёт как 404.

Создаётся один контейнер с уникальным именем и меткой владения, in-memory storage и случайным loopback-портом. OpenBao запускается обычным сервером, затем инициализируется и разблокируется через HTTP API. Случайные root token, unseal key, временные токены политик, RoleID и SecretID двух AppRole остаются в памяти процесса; их нет в аргументах Docker, окружении контейнера, конфигурации, файлах и выводе. Все credentials в проверяемых записях синтетические.

Проверяются реальные ACL и HTTP-ответы, CAS и конфликт версий, уничтожение первой версии `subs/` после второй записи, запрет чтения импортом, отказ роли `llm` в записи, metadata и удалении `subs/`, write-once до окончательной уборки, мягкое удаление, LIST, срок версии `turns/` 25 минут и повтор настройки без изменения данных. До первой настройки проверка оставляет `turns/` включённым и ненастроенным, как после прерванного запуска: с ключом внутри bootstrap отказывает, ничего не меняя, а пустой mount донастраивает. Серверные пределы `custom_metadata` проверяются прямыми запросами: 65 ключей, значения 513 байт и пустое, перевод строки, неразрывный пробел и ключ 129 байт отклоняются, границы принимаются. Через настоящий `createVaultSecretStore` дополнительно проверяются порядок data → metadata, восстановление прерванной записи, версия при чтении, tombstone, страницы LIST, CAS и удаление всех версий; metadata на границах сервера и отказ до любого запроса при её нарушении; три повтора `kvCreateOnce` под AppRole с одноразовым SecretID — ровно один вход; health со своими токенами всех политик, root и AppRole — после выключения `subs/` он отказывает у пользователей `subs/` и восстанавливается после повторного bootstrap.

Права контента проверяются так же, ответами сервера:

- **Mounts.** `transit/` чужого типа останавливает bootstrap до первого изменения: `subs/` и `kv/` не созданы, политики не записаны. После настройки `kv/` — KV v2 с настройками по умолчанию, `transit/` — Transit.
- **`workspace-provisioner`.** Создаёт ключ `ws-<id>`, повтор его не меняет; ключ не экспортируемый и не удаляемый. Отказ: другой тип, `exportable`, `derived`, `allow_plaintext_backup`, имя без `ws-`, `config` с параметрами, `import` и `import_version` с материалом ключа, чтение, удаление, `soft-delete`, `trim`, список, `export`, `backup`, `restore`, ключ данных, `encrypt`, `kv/`. `rotate` и `soft-delete-restore` проходят; после ротации прежний ключ данных разворачивается, новый получает версию 2. Ключ, мягко удалённый под root, отказывает роли `mcp` (400) и после `soft-delete-restore` под `workspace-provisioner` снова работает.
- **`sites-writer`.** Запись `kv/sites/<siteId>/wp` и `…/ssh` с `cas=0`, чтение данных — 403, чтение metadata — версия, устаревший CAS — 400, замена с верным CAS. Отказ: список, изменение и удаление metadata, удаление данных, `destroy`, карты контактов, `kv/platform/…`, `turns/`, `subs/`, Transit.
- **AppRole `mcp` (`mcp-content`).** Вход по RoleID и одноразовому SecretID, у токена ровно одна политика. Карта контактов: создание с `cas=0`, проигранная гонка — 400, чтение с версией, замена, устаревший CAS — 400, удаление metadata — и у root нет ни metadata, ни первой версии. Чтение `kv/sites/<siteId>/wp` с версией; прежняя версия доступа после замены тоже читается. Отказ: `…/ssh`, `…/ftp`, `…/browser`, путь глубже `wp`, запись и удаление доступа, metadata и списки сайтов, metadata и список карт, мягкое удаление, `delete`, `undelete`, `destroy`, `kv/platform/…`, `kv/config`, `turns/`, `subs/`, `ops/`, `sys/mounts`, выпуск токена. Transit: ключ данных и его расшифровка; отказ на `transit/keys/*` (чтение, создание, удаление, `config`, `rotate`, список), `export`, `backup`, `encrypt`, `rewrap`, `datakey/wrapped` и на ключ с именем без `ws-`. Рабочее пространство без ключа получает 400, и ключ при этом не появляется.
- **AppRole `core` (`core-turns` и `core-transit`).** Ключ данных и расшифровка, запись ключа хода тем же токеном. Ключ данных, обёрнутый ролью `core`, разворачивает роль `mcp`, и наоборот. Отказ: доступы сайтов, карты контактов, `transit/keys/*`, `export`, `encrypt`, чужое имя ключа, `subs/`, `ops/`. Токены `core-turns`, `llm-subscriptions`, `subscriptions-writer` и `subscriptions-admin` по отдельности не получают ни ключа данных, ни доступа сайта, ни карты.
- **Клиент под AppRole.** Через `createVaultSecretStore`: роль `core` берёт и разворачивает ключ данных тем же единственным входом; роль `mcp` ведёт карту (`kvRead`, `kvWrite` с CAS, конфликт, `kvDestroyAll`), читает доступ WordPress, берёт и разворачивает ключ данных — один вход. Health роли `mcp` видит `kv/` и `transit/`, роли `core` — `turns/` и `transit/`, каждая под своими политиками. Повторный bootstrap при работающих `kv/` и `transit/` их не трогает: доступ сайта остаётся той же версии, ключ рабочего пространства разворачивает прежний ключ данных. Политика `mcp-content`, из которой убраны пути Transit, даёт тот же отказ health роли `mcp` при работающем mount — тем же входом; повторный bootstrap записывает политику заново, и право возвращается. После выключения `transit/` health ролей `core` и `mcp` отказывает («Vault Transit mount transit/ is not available»), у остальных хранилищ — нет; повторный bootstrap возвращает mount, health восстанавливается, а обращение за ключом отвечает 400: ключа рабочего пространства больше нет. Отказ в доступе `…/ssh` клиент возвращает как 403, а не как «ключа нет».

Регрессии лимитов проверяют запись ровно 64 КиБ со строками `<>&` и точное чтение после серверного JSON-экранирования, а также каталог из 1500 ключей с ответом больше 64 КиБ и обходом всех страниц без потерь. Каталог создаётся с ограничением 16 параллельных записей внутри того же одноразового контейнера.

При успехе выводится только сводка: образ, число проверок и флаги. Контейнер удаляется в `finally`; удаление допускается только при совпадении собственной метки. Уже работающие сервисы, mounts, тома и контейнеры проверка не меняет.
