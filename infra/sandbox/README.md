# Песочная ВМ: образы и доверенные процессы

`Dockerfile` собирает цели: `runtime` (образ песочницы с OpenCode CLI), `gateway` (`sandbox-gw` — `gateway.mjs` и прокси выхода переменных клиента), `network-guard` (`network-guard.mjs` и `host-firewall.mjs`), `watchdog` и `client-egress` (прокси выхода предпросмотра). Правила песочницы — spec §8 и правило 5 `CLAUDE.md`.

## Раннер песочной ВМ

`docker-compose.yml` ВМ поднимает `watchdog` и, с профилем `runner`, раннер: приложение `apps/runner` забирает ходы у API раннеров `core` и управляет Docker этой ВМ. Образ раннера — `RUNNER_IMAGE`, собирается из `apps/runner/Dockerfile` (`turbo prune runner`; без `git` и `gitleaks` — git хода работает внутри песочницы; код раннера не достаёт базу, Redis, Vault и S3):

```sh
docker build --platform linux/amd64 -f apps/runner/Dockerfile --target runtime -t <реестр>/raditi/runner .
```

- Образ у раннера свой (`apps/runner/Dockerfile`), образ `core` ему не нужен: переменной `ORCHESTRATOR_ROLES` больше нет, и production-раннер с ней не стартует. Поэтому compose песочной ВМ и образ раннера меняют вместе: образ после разделения со старым compose (он задавал эту переменную) не запустится, а прежний образ без неё — тоже (требует её); откатывают оба сразу. Токен ВМ выпускает скрипт `scripts/runner-token.mjs` из этого же образа (`infra/app/README.md`, «Токены раннеров»).
- Окружение раннера — `RUNNER_CORE_URL`, `RUNNER_TOKEN_FILE`, `RUNNER_CORE_CA_FILE`, `RUNNER_S3_ORIGIN`, `RUNNER_MAX_TURNS` и `SANDBOX_*`; из своего `.env` compose ВМ берёт `RUNNER_CORE_URL`, `RUNNER_CORE_CA_FILE`, `RUNNER_S3_ORIGIN`, образы и адреса шлюза песочницы, а `RUNNER_TOKEN_FILE`, `RUNNER_MAX_TURNS` и `SANDBOX_RUNTIME` задаёт сам. В production раннер не стартует с любой другой переменной, кроме системных, `APP_ENV` и `NODE_ENV`: на ВМ не должно быть платформенных секретов (`apps/runner/src/config.ts`).
- Портов раннер не открывает и к PostgreSQL, Redis, Vault и S3 со своими ключами не ходит: снимки хода он переносит по временным ссылкам S3, которые присылает `core`, и только на origin из `RUNNER_S3_ORIGIN`.
- Выкладка — сначала `core`, потом `RUNNER_IMAGE` на песочных ВМ; откат — наоборот (`infra/app/README.md`, «`core` и раннеры»).

## Прокси выхода переменных клиента

[План 53](../../docs/plan/53-chat-preview-release.md), Р13 (ответ владельца: «агенту и предпросмотру, оба в сеть»). Переменная клиента ведёт только к `host:port` из своего списка; путь туда — только через прокси выхода `client-egress.mjs`, не через код шлюза `sandbox-gw`.

Правила прокси, одни в обоих местах:

- только `CONNECT` к `host:port` из списка (`ALLOWED_HOSTS`, JSON), сверка точная, без учёта регистра; запрос простого HTTP — 405, ничего не пересылается;
- в списке — только DNS-имена: ни IP-литералов в любой записи (`127.1`, `0x7f.1`, `2130706433`), ни `localhost`, `*.localhost`, `*.internal`, `host.docker.internal` и других локальных зон — то же правило, что у формы (`parseEgressHost` в `@repo/domain`);
- имя разрешается заново при каждом соединении, внутри прокси; если хотя бы один адрес непубличный — RFC 1918, loopback, link-local и адрес метаданных, CGNAT, ULA, multicast, `0.0.0.0/8`, IPv4 в IPv6, NAT64, адреса документации, подсети интерфейсов самого прокси (мост Docker, сеть предпросмотра) и подсети платформы `SANDBOX_EGRESS_REFUSED_SUBNETS`, — отказ 403;
- соединение идёт на проверенный адрес, второго разрешения имени нет: подмена ответа DNS между проверкой и соединением ничего не даёт;
- по туннелю идёт только TLS, чей ClientHello называет (SNI) ровно хост из `CONNECT`, без учёта регистра: у хоста на общем входе (CDN, общий хостинг) те же адреса, что у любого другого сайта там. Пока ClientHello не пришёл целиком (10 с), на ту сторону не уходит ни байта; без SNI, с другим именем, с двумя именами, с зашифрованным ClientHello (ECH, ESNI) или не TLS — туннель закрывается (`forbidden_sni` в логе, имя из ClientHello в лог не пишется). Подмену заголовка `Host` внутри TLS на CDN, которые её допускают, это не закрывает: хост, за которым много чужих сайтов, остаётся каналом;
- не больше 32 туннелей, 10 с на имя и соединение, 5 минут простоя; в логе — хост из списка, исход, время и байты, но не то, что прислал клиент, и не пути.

Где работает:

- **Ход агента.** Когда у политики сети хода есть `egress` (переменные, которые клиент открыл агенту с согласием, рабочее пространство не класса `client`), `sandbox-gw` поднимает второй слушатель на `SANDBOX_EGRESS_PORT` (3128) своего адреса; принимает он только адрес песочницы, а под `runc` сторож сети (`network-guard.mjs`) открывает этот порт рядом с портом шлюза. Без `egress` слушателя нет. Значения переменных идут файлами в tmpfs (`TurnCredentialValues.envValues`, пары `ИМЯ\0значение\0` в `env.0`, `env.1`, …: все 64 значения сайта по 8 КиБ помещаются); обёртка драйвера OpenCode читает их, удаляет и пишет скрипт для `BASH_ENV` (значения в `$'…'`): значения и `HTTPS_PROXY` получают только команды инструмента `bash`, процесс OpenCode — лишь путь скрипта. Когда CLI кончился, обёртка маскирует значения в базе сессии (`secure_delete`, `VACUUM`, слияние WAL) и сверяет файлы снимка побайтно; исполнитель хода (локальный и раннер) маскирует их в выводе агента до разбора и отказывает архиву home, в котором значение осталось. `NO_PROXY` — адрес шлюза и loopback, так что маршруты модели и MCP идут как прежде.
- **Предпросмотр.** Контейнер `egress` среды предпросмотра (`PREVIEW_EGRESS_IMAGE`, цель `client-egress`) — двудомный: сеть предпросмотра и мост по умолчанию. Отказ всем непубличным адресам, подсетям своих интерфейсов и подсетям платформы — главный барьер между предпросмотром и службами хоста.

Подсети платформы (`SANDBOX_EGRESS_REFUSED_SUBNETS`) на песочной ВМ:

- в production обязательны: раннер со шлюзом песочницы без них не стартует; compose передаёт переменную раннеру, раннер — каждому `sandbox-gw` (`EGRESS_REFUSED_SUBNETS`);
- в списке — публичные адреса всех машин платформы (app-ВМ, песочные ВМ, узел выхода, Vault, Gitea, S3 и реестр, если они на своих адресах), по одному `/32` или подсетью провайдера: имя клиента, указывающее на такой адрес, иначе прошло бы туннелем с моста Docker мимо правил периметра;
- при выкладке (M10) runbook ВМ сверяет список с адресами из инвентаря; предпросмотры на раннерах получат ту же переменную (`createDockerPreviewRuntime({ egressRefusedSubnets })`).

Сборка образа прокси предпросмотра (digest локальной сборки на каждой машине свой):

```sh
docker build -f infra/sandbox/Dockerfile --target client-egress -t raditi-client-egress:local .
docker image inspect --format '{{index .RepoDigests 0}}' raditi-client-egress:local
```

Проверки:

- `node --test infra/sandbox/client-egress.test.mjs` — таблица «разрешить / отказать»: имя, разрешённое в 127.0.0.1, 10.x, 169.254.169.254, ULA и в смесь публичного с частным; смена ответа DNS между соединениями; соединение только на проверенный адрес; простой HTTP; чужой клиент; ClientHello с чужим именем, без имени, с ECH, не TLS и разрезанный на мелкие записи; пределы и лог;
- `RADITI_DOCKER_TEST_IMAGE=… SANDBOX_GATEWAY_IMAGE=… SANDBOX_NETWORK_GUARD_IMAGE=… pnpm --filter @repo/sandbox-providers exec vitest run src/gateway/gateway.integration.test.ts` — настоящая песочница: `https://example.com/` через `sandbox-gw:3128` доходит, остальное — 403 или 405, `https://example.org/` в туннеле к `example.com:443` (`curl --connect-to`) закрывается на ClientHello, без прокси наружу ничего;
- `pnpm verify:preview-network` — строки «PHP предпросмотра → прокси выхода» ([README стенда](../dev/preview-verify/README.md));
- `pnpm verify:opencode`, сценарий 13 — команда инструмента `bash` настоящего OpenCode видит переменные и прокси, CLI — нет, в базе сессии значение замаскировано.
