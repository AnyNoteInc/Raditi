# Локальная проверка настоящего сайта

```sh
node infra/dev/site-verify/verify-site.mjs
```

Этот проход поднимает настоящий WordPress и MariaDB, создаёт синтетическую опубликованную страницу, сохраняет её содержимое, меняет текст через WP-CLI, проверяет изменение HTTP-запросом к публичной странице, восстанавливает снимок и проверяет возврат исходного текста. Применяются существующие запреты WordPress MCP и защита путей диффа из `packages/site-adapters` и `packages/domain`. Команды создания и установки выполняет только доверенная подготовка стенда; правка и чтение страницы проходят через узкий список разрешённых команд этого теста.

Это **проверка основы работы с реальным сайтом**, а не полный e2e продукта. Здесь нет задания в чате Радити, вызова модели, настоящего MCP-шлюза, аренды сайта, S3, git, кнопки «Применить» и пайплайна выкладки. Локальный снимок содержимого не является полным бэкапом сайта или проверкой продуктового семидневного отката.

01.10.2026 добавлен отдельный проход:

```sh
pnpm verify:mcp-content
```

Он дополняет основу настоящими PostgreSQL, S3, OpenBao и защищённым HTTP MCP. Доверенная подготовка устанавливает узкий MU-плагин, создаёт отдельный application password и синтетические объекты хода. Проверяются маскирование контактов, зашифрованный снимок до записи, публичная правка, повтор после перезапуска, `restore`, обратный откат двух правок, конфликт с внешней правкой и восстановление после потерянного ответа по квитанции WordPress. Дополнительно проверяются атомарное сохранение продуктового `TaskTurn`, откат перед подготовкой исполнителя и повтор после частичного отката двух страниц через супервизор; выдача ключей и исполнитель в этом сценарии синтетические. [Сохранённый ход и замена](../../../docs/plan/27-p6-task-turn-undo.md). Штатная роль MCP по умолчанию объявляет только `site_info`; профиль контента включает `MCP_CONTENT_PROFILE=local`, в production он запрещён. Образы сервисов данных закреплены в `apps/orchestrator/scripts/verify-agent-supervisor.mjs`, все сервисы одноразовые, опубликованные endpoints только на loopback. Для этого прохода нужен локальный Docker с уже имеющимися образами: Docker Desktop, а на хосте Linux — обычный Docker; модель и подписка не вызываются. [Границы и результат](../../../docs/plan/26-p6-wordpress-content.md).

С 04.10.2026 роль `mcp` стенда работает без root-токена OpenBao. Стенд выполняет `infra/vault/bootstrap.mjs` (mounts и политики), создаёт AppRole `mcp` с политикой `mcp-content` и три токена с узкими правами: `sites-writer`, `workspace-provisioner` и наблюдателя стенда (только чтение метаданных `kv/content-masks/`). Доверенный шаг подключения — сам стенд: ключ Transit рабочего пространства создаёт токен `workspace-provisioner`, доступ сайта в `kv/sites/<siteId>/wp` пишет токен `sites-writer` (CAS, обратно не читает), в `credential_refs` остаются путь и версия. Роль собирается из конфигурации профиля: свой клиент S3 с одним бакетом артефактов, Vault под AppRole, шлюз сайта — штатный resolver (`credential_refs` → Vault → адаптер по стеку). Процесс роли не получает ни root-токен, ни пароль приложения. Единственный тестовый шов — обёртка над штатным resolver: она проверяет порядок «снимок → запись» и теряет подтверждение записи. Root-токен остаётся у запускающего скрипта и нужен только для подготовки сервера. [Отчёт](../../../docs/plan/33-mcp-role-content-resolver.md).

В CI этот проход выполняет workflow `wordpress-content.yml`: сначала загружает образы, закреплённые в `apps/orchestrator/scripts/verify-agent-supervisor.mjs` и `verify-site.mjs` (сам стенд образы не скачивает), затем запускает `pnpm verify:mcp-content`. Workflow стартует при изменении плагина `infra/wordpress`, этого стенда, модулей MCP и пакетов, которые они используют (`site-adapters`, `db`, `storage`, `domain`, `vault`, `observability`). Синтаксис плагина (`php -l`) проверяет обязательный job `gates` в `ci.yml`. На GitHub workflow ещё не выполнялся: его нужно подтвердить после отправки ветки.

Дополнительный сценарий проверяет capture/ready после сбоя, отрицательную квитанцию после реального deadline, отказ задержанному запросу и очистку S3, квитанций сайта и всех версий карты Vault после потери подтверждений. Даты только собственных синтетических записей сдвигаются для проверки семидневного срока; журнал сохраняется. [Восстановление и очистка](../../../docs/plan/28-p6-content-recovery-retention.md).

02.10.2026 в тот же проход добавлен блок `content-fidelity.mjs`: сайт хранит ровно то, что подтверждают квитанция и снимок. Он работает через настоящий адаптер `WordpressPublishedContentGateway` под паролем приложения администратора.

- Текст с `%` (проценты, `width:100%`, ссылки с URL-кодированием, `%s`) после правки и после отката совпадает побайтно в ответе плагина, в строке WordPress и на публичной странице. Проверяется и откат правки, которая сама `%` не содержала.
- Предел 32 КиБ считается по байтам UTF-8 JSON-состояния, одинаково на сайте и на платформе: состояние ровно в 32 768 байт с кириллицей, косой чертой, кавычками и U+2028 читается и пишется, на байт больше — отказ с причиной `size`. Страница, выросшая сверх предела в админке, даёт `CONTENT_TOO_LARGE`, а не «сайт недоступен».
- Правка не теряет разметку молча. Текст агента всегда сохраняется после фильтра WordPress (`wp_kses_post`, `sanitize_text_field`), даже под администратором. Если фильтр убрал бы или изменил что-то в новом значении или в заменяемом поле (iframe, form, script, обработчики, протоколы вне списка WordPress вроде `viber://`, табуляция внутри значения `style`), плагин отказывает с причиной `markup` и ничего не пишет. Иная запись тех же тегов (` />`, кавычки, сущности, пробелы и `;` между объявлениями `style`) потерей не считается. Остальные поля такой страницы правятся и откатываются, поле с виджетом не переписывается. Сравнение по смыслу требует WordPress 6.5 и новее; на более старом допускается только побайтное совпадение с результатом фильтра.
- Срок записи не зависит от часов сервера сайта: адаптер передаёт остаток срока `ttlMs`, плагин измеряет только время самого запроса. `deadlineAt` остаётся идентификатором операции и с часами сайта не сравнивается. Истёк ли срок для `reconcile` и `forget`, решает платформа (`ttlMs` ≤ 0). Удаление квитанции (`forget`) сдвигает ограждение сайта за эпоху этой операции: её исходный запрос, даже дошедший с опозданием, записать страницу уже не может. Если строки ограждения на сайте ещё нет (все записи были отклонены до транзакции), `forget` создаёт её, как `write` и `reconcile`, а не отказывает навсегда.
- После UPDATE строка перечитывается в той же транзакции. Если база сохранила другой текст (колонка `utf8mb3` и эмодзи), запись откатывается с причиной `storage`, квитанции нет.

Сценарий автора (`content-permissions.mjs`) проверяет отказ вместо очистки и то, что автор без `unfiltered_html` правит и откатывает только те поля, которые его права позволяют восстановить.

Этот проход проверяет протокол контента через настоящий MCP. Продуктовые кнопки, запуск агента через чат, полный бэкап, выкладка и откат кода остаются частями полного e2e-гейта ниже.

04.10.2026 добавлен стенд-склейка ниже очереди:

```sh
pnpm verify:agent-content
```

Настоящие CLI (Codex 0.158.0 и Kimi 2.1.1 в образе песочницы) правят страницу этого же одноразового WordPress одной цепочкой: аренда сайта и продуктовое назначение → ключ хода из настоящего `issue` → `sandbox-gw` → роль `llm` на фейке подписки → штатная роль `mcp` с контентным профилем → плагин. Модель сценарная (`content_edit`, `content_forbidden` в `infra/dev/llm-verify/fake-subscriptions.mjs`), подписки не используются. WordPress и MariaDB — из `compose.yml` этого каталога, с тем же переходом на loopback; PostgreSQL, OpenBao, S3, фейки и прокси выхода — стек `infra/dev/llm-verify`. Роль `mcp` здесь штатная: процесс `node dist/main.js` с `ORCHESTRATOR_ROLES=mcp` и `MCP_CONTENT_PROFILE=local`, AppRole `mcp` (политика `mcp-content`), доступ сайта — из OpenBao по ссылке `credential_refs`. Процесс запускается с `NODE_ENV=production`, чтобы корневой `.env` не читался; `APP_ENV` остаётся `test`. Наблюдения стенда вынесены из роли в два его собственных промежуточных узла: перед `/mcp` (метод JSON-RPC, имя инструмента, статус) и перед WordPress (счётчики по маршрутам плагина и проверка «снимок в S3 до отправки записи»). Сайт в базе и в секрете записан по адресу второго узла.

Проверяется:

- `tools/list` роли принят каждым CLI; Kimi объявляет инструменты провайдеру, Codex 0.158.0 держит их внутри своего `exec`;
- зашифрованный снимок лежит в бакете артефактов стенда (`snapshots/<siteId>/<id>.json`) к моменту отправки записи на сайт и расшифровывается в исходный текст;
- публичная страница отдаёт новый текст, контакт посетителя модель видит только маркером;
- на повторённый ключ — одна строка журнала, одна квитанция плагина, один снимок;
- запрещённый маршрут и запись без ключа не оставляют строк журнала и запросов к сайту, ход завершается;
- вторая аренда сайта не выдаётся;
- ключа хода, токена MCP и контакта нет в запросах провайдеру, событиях CLI, логах и SQL.

Единственный флаг — `--no-build`. [Отчёт и наблюдения](../../../docs/plan/30-agent-content-stand.md). В CI стенд запускает workflow `agent-content.yml`; на GitHub он ещё не выполнялся и не подтверждён до отправки ветки.

После успеха, ошибки, SIGINT или SIGTERM, в том числе повторного, стенд удаляет свои проекты Compose (`raditi-p3verify-…` и `raditi-site-verify-…`), процессы ролей и временные каталоги. После SIGKILL остатки узнаются по этим префиксам. Роль `mcp` слушает только `127.0.0.1`. На Linux узел стенда перед `/mcp` слушает адрес шлюза моста Docker (к хосту `sandbox-gw` ходит через мост), а не `0.0.0.0`; на Linux этот путь ещё не выполнялся.

Стенд закрывает критерий «изменение страницы через реальный MCP» только ниже очереди и на сценарной модели: задания через интерфейс, очереди, «Отменить» и расчётов в нём нет.

Нужны Node 26.10, установленные зависимости монорепозитория, работающий локальный Docker с Compose и уже загруженные образы. Скрипт разрешает только локальный сокет Docker (`unix://` или `npipe://`); удалённые TCP/SSH endpoints отклоняются до обращения к серверу:

| Компонент | Закреплённый образ |
| --- | --- |
| WordPress | `wordpress:7.1.2-php8.3-apache@sha256:8ae73d594a154e30b112e8d085afbc0895acf7651d8f53ef63aefb42e30822d5` |
| MariaDB | `mariadb:11.4.13@sha256:70cc072b29b4a89ae07abb2d4da2c64678a7f2dfe092751bb51c87d67dc1338b` |
| WP-CLI | `wordpress:cli-2.12.0-php8.3` |
| Локальный HTTP-переход | `alpine/socat@sha256:68b28fed1e6f5dc5cc7574315284573d89a655b0bc528720be4164f36b998680` |

Скрипт никогда не скачивает образы. Если точного тега WP-CLI нет, допускается уже имеющийся образ `wordpress@sha256:2b5e9d4d3e51909dca1aaa4732e9f5e5bf0377c2114dbd8ff39f060bff202586`: его версия проверяется в контейнере без сети и должна быть строго `WP-CLI 2.12.0`. Изменяемый тег `wordpress:cli-php8.3` при запуске не используется. WordPress также должен подтвердить версию `7.1.2` после установки.

Каждый запуск получает случайное имя Compose-проекта, собственные сети и два тома. WordPress, MariaDB и WP-CLI находятся только во внутренней сети, без внешнего выхода. Docker не публикует порты контейнера, у которого есть только внутренние сети, поэтому отдельный малый socat-контейнер соединяет внутреннюю сеть с обычной сетью Docker и передаёт TCP только на фиксированный `wordpress:80`. Только этот переход публикует HTTP на случайном порту `127.0.0.1`; база не публикуется. Ни один шаг теста не обращается к внешним HTTP-адресам. Автообновления, cron и внешние HTTP-вызовы WordPress отключены. Существующий `raditi-dev`, его тома и сайты не используются.

Пароли случайные и одноразовые. Файл конфигурации и снимок создаются в отдельном временном каталоге с правами `0700`; файлы — `0600`. Вывод содержит названия проверок, без паролей, содержимого страниц и вывода WP-CLI. Скрипт не читает `.env`, данные реального сайта, токены подписок или облачные настройки. После успеха, ошибки, SIGINT или SIGTERM удаляются только ресурсы собственного Compose-проекта и временный каталог. Как и у других CLI-проходов, SIGKILL не даёт выполнить очистку: оставшийся проект узнаётся по префиксу `raditi-site-verify-`; перед ручным удалением нужно выбрать именно его.

## Локальное подключение сайта

04.10.2026 добавлены доверенная команда подключения и её стенд:

```sh
node infra/dev/site-verify/connect-local.mjs --site <идентификатор сайта>
pnpm verify:site-connect
```

Сайт, созданный в кабинете через «Новый проект», остаётся в статусе `onboarding`: роль `mcp` его не допускает. Команда `connect-local.mjs` делает такой сайт пригодным для хода. Это подготовка стенда, а не продукт: она работает только вне production и только с PostgreSQL, OpenBao, Gitea и WordPress на loopback. Мастер подключения (M4), упаковка плагина и выбор «плагин или SSH/FTP» ею не решаются.

Что делает команда, по порядку:

1. Проверяет всё до первого изменения: сайт есть, его адрес — loopback, стек — WordPress, рабочее пространство — `synthetic`, статус — `onboarding` или `active`; ссылки на доступ и репозиторий, если они уже есть, такие, какие примет роль `mcp`.
2. Устанавливает WordPress, если он не установлен (пароль администратора создаёт WP-CLI, команда его не видит).
3. Если установка привязана к другому сайту (или ни к какому), удаляет `raditi_content_epoch` и квитанции `raditi_content_call_*`: иначе после пересоздания базы платформы при сохранённых томах сайта каждая запись нового сайта получала бы `fenced` — аренда нового сайта начинается с эпохи 1, а плагин помнит прежнюю. Установку, привязанную к другому сайту той же базы, команда не отнимает. При неизменной привязке ограждение не трогается.
4. Создаёт пароль приложения администратора (прежний пароль команды удаляется) и пишет доступ в `kv/sites/<siteId>/wp` токеном политики `sites-writer` с CAS: `cas = 0` для нового секрета, текущая версия — для существующего. Затем сохраняет строку `credential_refs` с версией секрета. Формат секрета проверяет схема адаптера сайта. Доступ не переписывается, если привязка не меняется, а строка называет текущую неудалённую версию секрета.
5. Привязывает плагин к сайту платформы (опция `raditi_content_site_id`) — последним шагом на стороне WordPress, когда доступ этой установки уже сохранён. Запуск, прерванный раньше, оставляет установку непривязанной, и следующий запуск пишет доступ заново.
6. Создаёт ключ `transit/keys/ws-<workspaceId>` токеном политики `workspace-provisioner`.
7. Создаёт в Gitea приватный репозиторий `sites/site-<siteId>` с первым коммитом и строку `git_repositories`.
8. Переводит сайт в `active` функцией `activateSite` (`packages/db/src/site-activation.ts`): переход выполняется, только если у сайта есть ссылка на доступ названного адаптером вида и репозиторий.

Повторный запуск ничего не меняет. Прерванный запуск доводится следующим: доступ, который нельзя прочитать обратно, заменяется новой версией. Секреты команда не печатает и не передаёт аргументами.

Чего команда не умеет:

- проверить, что записанный ранее пароль приложения ещё действует: при неизменной привязке доступ остаётся «без изменений», даже если пароль удалили в админке. Чтобы команда выпустила новый, удалите опцию `raditi_content_site_id` (WP-CLI) и запустите её снова — вместе с привязкой сбросятся эпоха и квитанции;
- сбросить ограждение при неизменной привязке: если базу платформы восстановили из более раннего дампа с тем же сайтом, эпоха плагина окажется выше эпохи аренды и записи получат `fenced`. Выход тот же — удалить опцию привязки и запустить команду;
- работать параллельно с собой на одном сайте: два одновременных запуска удаляют пароли приложений друг друга.

Окружение задаётся явно, env-файлы команда не ищет и не читает:

| Переменная | Значение |
| --- | --- |
| `APP_ENV` | `development` или `test`; `production` — отказ |
| `DATABASE_URL` | PostgreSQL на loopback; строка с параметром `host` или `hostaddr` отклоняется |
| `VAULT_ADDR` | числовой loopback-адрес OpenBao, например `http://127.0.0.1:8200` |
| `CONNECT_SITES_WRITER_TOKEN_FILE` | файл с токеном политики `sites-writer` |
| `CONNECT_WORKSPACE_PROVISIONER_TOKEN_FILE` | файл с токеном политики `workspace-provisioner` |
| `GITEA_URL` | Gitea на loopback, только `https:` |
| `GIT_CA_FILE` | CA сервера Gitea, если он свой |
| `CONNECT_GITEA_TOKEN_FILE` | файл с токеном Gitea, которому разрешено создавать репозитории в организации `sites` (области `write:organization` и `write:repository`) |
| `CONNECT_COMPOSE_PROJECT` | проект Compose с профилем `site`; по умолчанию `raditi-dev` |
| `SITE_WPCLI_IMAGE` | образ WP-CLI, если точного тега `wordpress:cli-2.12.0-php8.3` локально нет |

Файлы токенов — собственные обычные файлы с правами `0600`, абсолютные пути. WP-CLI команда запускает в сервисе `wpcli` профиля `site` (`docker compose run --rm --no-deps --pull never`): сайт и его базу она не запускает и не пересоздаёт, поэтому профиль `site` должен быть поднят заранее (`pnpm infra:up`). Если профиль не поднят, команда откажет (`SITE_NOT_RUNNING`), но Compose успеет создать пустой том `sitefiles` проекта.

Профиль `site` в `infra/dev/docker-compose.yml` для этого изменён: тип окружения `local` (WordPress принимает пароли приложений по HTTP), cron, обновления и внешние HTTP-вызовы выключены, как в одноразовом стенде; плагин `infra/wordpress/raditi-content.php` смонтирован в `mu-plugins` только на чтение в сервисы `site` и `wpcli`. До привязки плагин отклоняет все запросы.

Ограничение: dev-Gitea из того же compose отвечает по HTTP, а команда, как и git ходов, принимает только `https:`. На dev-инфраструктуре команда остановится на проверке `GITEA_URL`, пока у dev-Gitea нет TLS или владелец не разрешил HTTP на loopback (spec §20). Сейчас команду выполняет стенд.

**Стенд `pnpm verify:site-connect`.** Одноразовые PostgreSQL, S3, OpenBao и Gitea 1.27.3 (HTTPS с CA стенда); WordPress, MariaDB и WP-CLI — профиль `site` того же dev compose под собственным именем проекта `raditi-site-connect-…` на случайном порту loopback. Контейнеры и тома `raditi-dev` стенд не трогает. Проверяется:

- до подключения роль `mcp` отвечает на токен хода 401; команда отказывает при `APP_ENV=production`, базе не на loopback и `http:`-адресе Gitea;
- после команды: WordPress установлен и привязан, секрет версии 1 в OpenBao с полями `v`, `origin`, `username`, `applicationPassword`, одна строка `credential_refs` с тем же путём и версией, ключ рабочего пространства, репозиторий с первым коммитом (Gitea называет его приватным, без токена он не виден), сайт `active`;
- штатная роль `mcp` (`node dist/main.js`, `MCP_CONTENT_PROFILE=local`, AppRole `mcp`) читает и правит страницу: доступ сайта она получает только из OpenBao по ссылке, которую оставила команда; публичная страница отдаёт новый текст;
- повторный запуск не меняет ни базу, ни OpenBao, ни Gitea, ни сайт;
- база платформы пересоздана, тома сайта сохранены: до нового подключения запись под эпохой 1 получает `fenced`; после команды эпоха и квитанции сброшены, сайт привязан к новой строке, роль правит страницу под эпохой 1;
- токенов, паролей и паролей приложений нет в выводе команды и в логе роли.

Образы стенд не скачивает. Локальные образы WordPress и MariaDB берутся по тегам dev compose и сверяются с закреплёнными digest; если точного тега WP-CLI нет, берётся тот же проверенный запасной образ, что у `verify-site.mjs`. После успеха, ошибки, SIGINT или SIGTERM, в том числе повторного, стенд удаляет свой проект Compose с томами, контейнеры `raditi-gitea-verify-…` и `raditi-p4-supervisor-…` и временный каталог. После ошибки остаётся закрытый файл диагностики в каталоге `raditi-site-connect-diagnostic-…` временной папки; его путь стенд печатает. Workflow GitHub Actions для этого стенда нет. [Отчёт](../../../docs/plan/36-local-site-connect.md).

## Обязательный гейт перед облачной выкладкой

По указанию владельца от 30.09.2026 вся реализация и проверка идут локально. Выкладка на облачные серверы допускается после успешного **полного** локального e2e на настоящем WordPress. Успех этого подготовительного прохода и имеющийся `apps/e2e/tests/smoke.spec.ts` этого гейта не закрывают.

- [ ] Поднять всю платформу и синтетический WordPress локально, без облачных сервисов и клиентских данных.
- [ ] Через интерфейс Радити отправить задание и увидеть события настоящего агентского хода.
- [ ] Для контента: снимок в `raditi-artifacts` до правки → изменение страницы через реальный MCP → проверка публичного текста → «Отменить» → проверка восстановления. Проверить повтор вызова без двойной правки, аренду и отказ запрещённому инструменту.
- [ ] Для кода: агентская ветка и проверенный дифф → PR → «Применить» → полный бэкап → выкладка на локальный WordPress → проверка публичной страницы.
- [ ] Внести контролируемую неисправность, проверить отказ верификации и автоматический откат из бэкапа; проверить ручное «Отменить» и итоговое состояние задачи.
- [ ] Сохранить воспроизводимые команды и отчёт о полном проходе. Только после этого переходить к облачной выкладке.

Локальный WordPress для этого прохода (профиль `site`, `http://localhost:8080`) добавляется через «Новый проект» в кабинете: при `APP_ENV`, отличном от `production`, форма принимает локальные и частные адреса, а сайт попадает в рабочее пространство класса `synthetic`. Вставлять строку `sites` скриптом больше не нужно. Адрес вводится вместе со схемой: без неё форма подставит `https://`. В production такой адрес отклоняется с кодом `SITE_ADDRESS_NOT_PUBLIC`.

Недостающие этапы на момент создания стенда:

| Этап | Что необходимо для полного прохода |
| --- | --- |
| P3, P4, P5 | Подключённый шлюз подписок, ключи хода и запуск настоящих CLI в образах песочницы; B4 пока даёт чистые доменные правила. Стык «ключ хода → CLI → `sandbox-gw` → роли `llm` и `mcp` → плагин» проверяет `pnpm verify:agent-content` (на фейках подписок, ниже очереди) |
| P6 | Исполняемый MCP со списком разрешённых команд, снимками/restore в S3, журналом и идемпотентностью, проверкой эпохи аренды и маскированием данных |
| P8 | Реальный Gitea-провайдер, обязательный pipeline бэкап → выкладка → проверка → откат и события workflow |
| P10 | Рабочие `WordPressAdapter.detect/deployVars/backup/verify/agentGuide`; сейчас эти методы — заглушки |

До выполнения этих пунктов полный гейт остаётся открытым. Локальная реализация может продолжаться без облачной выкладки.

## Результат локального прохода

30.09.2026 `node infra/dev/site-verify/verify-site.mjs` завершился с кодом `0` на локальном Docker: WordPress `7.1.2`, MariaDB `11.4.13`, WP-CLI `2.12.0` из проверенного запасного дайджеста. Прошли установка, проверки существующей политики, реальная публичная HTTP-страница, снимок до изменения, видимость нового текста и восстановление исходных полей и текста. После прохода отсутствие контейнеров, сетей и томов собственного проекта проверено по его Compose-метке. Временный каталог удалён.

При первом запуске обнаружено, что Docker не создаёт host bindings для контейнера только во внутренней сети. Добавление фиксированного TCP-перехода решило это ограничение; WordPress и база сохранили внутреннюю сеть. Этот результат закрывает только проверку основы сайта. Полный пользовательский e2e и облачная выкладка остаются впереди.
