# Стенд биллинга и поддельная ЮKassa

Здесь две вещи из [плана биллинга](../../../docs/plan/37-billing-plan.md): стенд `pnpm verify:billing` (срез M5.15) — весь денежный путь на собранных web и `core` — и поддельная ЮKassa `fake-yookassa.mjs`, которую поднимают этот стенд, браузерные проверки `pnpm --filter e2e test:billing` и тесты. Настоящего магазина нет, деньги не списываются.

## Стенд `pnpm verify:billing`

```sh
pnpm verify:billing                          # собрать и пройти все сценарии
pnpm verify:billing -- --no-build            # без сборки: только если дерево не менялось
pnpm verify:billing -- --only refund,checkout  # только названные сценарии
pnpm verify:billing -- --no-build --keep     # оставить стенд поднятым до Ctrl-C
```

Одна команда поднимает одноразовые PostgreSQL, Redis и OpenBao, поддельную ЮKassa, синтетический сайт WordPress на SFTP-сервере стенда, web и приложение `core` из сборок и ведёт продукт снаружи: как клиент, как ЮKassa и как оператор. Она не читает `.env` репозитория, не трогает dev-инфраструктуру и чужие контейнеры и удаляет всё своё при любом исходе, в том числе по Ctrl-C, SIGTERM и SIGHUP (закрытый терминал, оборванная SSH-сессия). После `kill -9` убирать некому: это делает следующий запуск, см. «После аварийной остановки». Данные синтетические, секреты случайные и живут в памяти и в каталоге запуска.

На каждую проверку печатается строка `PASS <сценарий>: <что проверено>`, на сценарий — итог с числом проверок и временем, в конце — `PASS billing stand: 26 of 26 scenarios, N checks` и `PASS pnpm verify:billing in N s`. Полный проход — около трёх минут: сборка от 15 секунд (повторная) до минуты (с нуля), сценарии две с половиной минуты.

### Что нужно

- Node 26.10 (`nvm use`), pnpm 12.6, `git` и `rsync` в `PATH`; на macOS ещё `lsof` (есть в системе) — им стенд узнаёт рабочий каталог процесса, оставшегося от убитого запуска.
- Около 2 ГБ под `$TMPDIR`: там живёт приватная копия дерева с `node_modules` и сборками.
- Локальный Docker (удалённые endpoint отклоняются) с тремя уже загруженными образами. Стенд ничего не скачивает и без них останавливается на проверке «The pinned image … is missing locally». Загрузить их один раз:

  ```sh
  docker pull postgres:17.11-alpine3.24@sha256:b0f9560a2de083e2cc7382e75f808c7381a32852a7ec49117deedb300e552b24
  docker pull redis:8.10.2-alpine@sha256:3811787313eba226a2ef38658c6ccb91cd5e110edc89c37767de373120a0e5a0
  docker pull ghcr.io/openbao/openbao:2.7.0@sha256:71156a1c6623a5fa3f5e61b0c6a8ead0faf0df29a778339188443551995d1315
  ```

- Свободных фиксированных портов не нужно: все порты выбирает система, всё слушает только `127.0.0.1`.

### Разбор отказа

Первая несошедшаяся проверка печатает `FAIL <сценарий> («строка плана»): …` с ожидаемым и увиденным либо с тем, чего стенд ждал и что видел последним (`waited 30 s for: … / last seen: …` — строка заказа или подписки, темы писем клиента, счётчики). Ниже идут строки журналов web и `core` с начала упавшего сценария (не больше 400 на процесс), затем стенд убирает за собой и выходит с кодом 1.

Каталог запуска при этом удаляется, поэтому журналы web и `core` упавшего запуска целиком сохраняются отдельно — путь печатает строка `LOGS of the failed run, whole (web, core): …`. По умолчанию это `$TMPDIR/raditi-billing-verify-logs-<запуск>`, другой каталог (абсолютный путь вне репозитория) задаёт `BILLING_VERIFY_LOG_DIR`. В журналах синтетические клиенты и одноразовые ссылки уже удалённой базы; случайные секреты запуска в них затёрты. Прерванный запуск (Ctrl-C) журналов не оставляет. Сохранённые журналы стенд сам не удаляет: `rm -rf "$TMPDIR"/raditi-billing-verify-logs-*`.

С `--keep` стенд остаётся поднятым и после упавшего сценария — в том состоянии, в котором сценарий остановился; `core` при этом продолжает тикать, так что всё, чему пришёл срок, он доделает. Войти клиентом сценария нельзя: пароли клиентов случайные и нигде не печатаются. Чтобы посмотреть страницы, зарегистрируйте нового клиента через форму на адресе web из напечатанной подсказки — ссылка подтверждения почты будет в журнале `core`.

### Сборки: приватная копия дерева

Web и `core` собираются не в репозитории, а в копии рабочего дерева в `$TMPDIR/raditi-billing-verify-build` (переменная `BILLING_VERIFY_BUILD_DIR` задаёт другой абсолютный путь; каталог внутри репозитория отклоняется). В репозитории в это время может идти `next dev` другой сессии: он держит блокировку Next в `apps/web` и следит за всем деревом, а `next build` писал бы в тот же `apps/web/.next`. Сборка Docker-образов, как в `pnpm verify:edge`, отпала по двум причинам: она идёт минуты, а не секунды, и процессы стенда должны стоять на loopback хоста рядом с подделкой, что у контейнеров на Docker Desktop и на Linux устроено по-разному.

- Копия — это `git ls-files -co --exclude-standard`, перенесённый `rsync`: всё отслеживаемое и новое, что git не игнорирует. `.env`, `node_modules` и сборки репозитория в неё не попадают; файлы, удалённые из дерева с прошлого запуска, удаляются и из копии по списку прошлого запуска. Список пишется дважды — перед копированием (прежний вместе с новым) и после него, — поэтому запуск, умерший посередине, не оставляет в копии файлов, о которых следующий не знает.
- В копии по порядку: `pnpm install --frozen-lockfile --prefer-offline`, `pnpm --filter @repo/db db:generate`, `pnpm --filter core build`, `pnpm --filter web build` — шаги двух Dockerfile без Docker. Окружение сборки — только `PATH`, `HOME`, `CI` и `NEXT_TELEMETRY_DISABLED`: `next build` ничего не читает, переменных `NEXT_PUBLIC_*` в репозитории нет, так что порты стенда не попадают ни в одну сборку.
- Копия остаётся между запусками (около 2 ГБ вместе с `node_modules`), её и использует `--no-build`. Из копии идут не только сборки: `core` и команды оператора загружают оттуда исходники пакетов, оттуда же применяются миграции и сиды. Удалить её можно в любой момент, пока стенд не запущен: `rm -rf "$TMPDIR/raditi-billing-verify-build"`.
- **`--no-build` после изменения дерева отклоняется.** Законченная сборка оставляет в копии отметку `.raditi-billing-verify/built`: время и sha256 по списку файлов дерева (путь, размер, время записи). `--no-build` сверяет отметку с деревом и при расхождении останавливается: `--no-build is refused: the tree has changed since the copy was built at <время>: N files (first: …); run the stand without --no-build`. Так же он отвечает копии без отметки (сборка была прервана) и копии, в которой правили сами файлы (`the copy itself has been changed …`: их размер и время записи сверяются с отметкой). Иначе сценарии из дерева прошли бы на продукте прошлого запуска и напечатали `PASS` про код, который не исполнялся. При совпадении время сборки названо в строке `PASS builds of the private copy reused (--no-build): built at …`. Сами сборки (`dist`, `.next`) в отметку не входят: копию, которую правили и вернули руками, пересоберите обычным запуском.
- `BILLING_VERIFY_STALE_COPY=allow` вместе с `--no-build` пропускает это расхождение — только для мутационных проверок самого стенда: продукт намеренно ломают в отдельной копии (`BILLING_VERIFY_BUILD_DIR`), пересобирают в ней то, что стенд запускает, и смотрят, заметят ли сценарии поломку. Такой запуск печатает `WARNING … THE COPY IS NOT THE TREE` и помечает последнюю строку `ON A STALE COPY`: о дереве он ничего не доказывает. Без `--no-build` и с любым другим значением переменная отклоняется.
- С копией работает один запуск: рядом лежит замок `raditi-billing-verify-build.lock` с номером процесса. Замок появляется сразу с номером (каталог готовится в стороне и переименовывается), так что замок запуска, который только стартует, нельзя принять за брошенный. Замок процесса, которого уже нет, перехватывается; второму одновременному запуску нужен свой `BILLING_VERIFY_BUILD_DIR`.

### После аварийной остановки

Ctrl-C, SIGTERM и SIGHUP стенд обрабатывает сам. После `kill -9` или падения машины остаются три контейнера, осиротевший web (процесс `next-server`, слушает свой порт), каталог запуска и замок копии. Следующий запуск стенда убирает это сам, до того как взять замок, и печатает по строке на каждый такой запуск:

```
SWEPT run 0123abcd, whose stand (pid 4242) is gone without cleaning up: containers raditi-billing-verify-0123abcd-postgres, raditi-billing-verify-0123abcd-redis, raditi-billing-verify-0123abcd-vault; processes web (pid 4250); its run directory; its lock of the build copy
```

Он берёт только то, что принадлежит мёртвому запуску по его записи `run.json`: контейнеры с меткой `io.raditi.billing-verify=<запуск>`; записанные процессы, которые ещё живы **и** чей рабочий каталог лежит в копии этого запуска (номер процесса, доставшийся с тех пор кому-то другому, не трогается); каталог запуска; замок, если в нём номер умершего стенда. Запуск, чей стенд жив, — параллельный со своей копией или оставленный через `--keep` — не трогается. По имени стенд ничего не выбирает.

Вручную — когда ни один запуск стенда не идёт — то же самое:

```sh
docker ps -a --filter label=io.raditi.billing-verify       # контейнеры стенда, чужих здесь нет
docker rm -fv <имена из этого списка>
lsof -a -d cwd -c node | grep raditi-billing-verify-build  # процессы, работающие в копии
kill <их номера>
find "$TMPDIR" -maxdepth 1 \( -name 'raditi-billing-verify-run-*' -o -name 'raditi-billing-verify-new-*' \
  -o -name 'raditi-billing-verify-build.lock*' \) -exec rm -rf {} +
```

Именно так, а не `pkill next-server`: `next dev` другой сессии в этом же репозитории называется так же, и отличает его только рабочий каталог. Если копия была задана через `BILLING_VERIFY_BUILD_DIR`, в `grep` и в пути замка подставьте её. Сборка, осиротевшая после `kill -9` (`pnpm … build`, `next build`), заканчивается сама за минуту; новый запуск до этого лучше не начинать.

### Окружение `core`

Конфигурация `core` (`apps/core/src/config/config.ts`) шире биллинга. Стенд даёт ей наименьшее честное окружение:

- **настоящие одноразовые сервисы** там, куда `core` подключается: PostgreSQL и Redis (BullMQ, relay outbox, письма);
- **значения-заглушки** там, где `core` только разбирает настройки при старте: `S3_*` и `VAULT_*` указывают на `127.0.0.1:9`, где никто не слушает. К S3 и Vault `core` обращается только в ходе агента и в проверке `/health`; ходов здесь нет, а `/health` честно отвечает `degraded` с `s3` и `vault` — стенд проверяет в нём `database` и `redis`;
- `TURN_EXECUTOR=local` без `SANDBOX_*` и без `GITEA_*`: Docker при старте не опрашивается, git не настроен, ходы не идут. Первый импорт файлов нового сайта (очередь `site-import`) `core` берёт и сразу завершает `failed` с кодом `repository_not_configured` — раньше, чем прочитал бы доступ из Vault; сценарий `signup-gift` проверяет, что импорт — не задача и кредитов не трогает;
- `NODE_ENV=production`, чтобы `core` не искал `.env`, и `APP_ENV=test`, чтобы принимались адрес подделки и уведомления с loopback;
- `SENDSAY_API_KEY` не задан: письма не уходят, а пишутся в журнал `core` строкой `[mail] not sent …` с темой, адресом и ссылками.

Web получает базу, магазин подделки, `YOOKASSA_WEBHOOK_ALLOWLIST=127.0.0.1,::1` и OpenBao стенда — `VAULT_ADDR`, `VAULT_ROLE_ID` и `VAULT_SECRET_ID` роли `sites-writer`, без корневого токена: «Добавить проект» пишет туда доступ к файлам нового сайта и прочитать его обратно не может. Redis и S3 ему не заданы — их читают только `/api/health` и аватары.

`YOOKASSA_AUTOPAYMENTS` стенд не задаёт: вне production переключатель по умолчанию `on`, и web, и `core` работают с включённым автопродлением. Магазин без одобренных автоплатежей изображает сама подделка — командой `autopayments` в сценарии `autopayments-not-approved`.

### Как идут сценарии

- **Клиент** регистрируется через `POST /api/auth/sign-up/email` с обоими согласиями, открывает ссылку из письма «Подтвердите адрес почты» — её стенд берёт из журнала `core`, то есть письмо прошло outbox, relay, BullMQ и почтовый модуль — и дальше вызывает процедуры tRPC по HTTP с cookie сессии. У каждого клиента свой адрес в `X-Forwarded-For`, как его подставил бы обратный прокси: лимит регистраций считается по адресу.
- **Сайт** клиент добавляет так, как ведёт мастер «Добавить проект», — единственным путём, которым продукт создаёт сайт, а с первым сайтом — рабочее пространство и подарок (`addSite` в `scenario-kit.mjs`): `siteConnection.checkBasics` («Основные данные»), `siteConnection.checkSource` без ключа сервера — ответ `host_key_unknown` с отпечатком, который назвал SFTP-сервер стенда, и ни одной попытки входа на сервер, — тот же вызов с подтверждённым ключом и `project.create` без базы данных с новым `requestKey`. Перед созданием web сам ещё раз проверяет файлы по сети и пишет доступ в Vault.
- **ЮKassa** — подделка: клиент «нажимает» кнопки её страницы оплаты, сценарий управляет ею через `/__control` (отказ банка, ответ 500, медленный банк, придержанные и поддельные уведомления, возврат «из кабинета»).
- **Оператор** запускает команды `apps/core/scripts/billing-*.mjs` из копии с окружением, заданным явно, — все пять, включая `billing:rates`; файл курса для неё стенд пишет в каталог запуска.
- **Письма** читаются так, как их получает адресат. Почтовый модуль `core` без `SENDSAY_API_KEY` пишет в журнал только тему, адрес и ссылки, а данные письма продукт не хранит: relay стирает их из строки outbox при публикации, доставленное задание сразу уходит из Redis — в них бывают одноразовые ссылки. Поэтому стенд держит в своей базе зеркало: триггер `AFTER INSERT` копирует каждую строку outbox очереди `notifications` в таблицу `stand_letter_mirror` в той же транзакции, ничего в строке не меняя. Текст письма по строке зеркала даёт почтовый модуль копии: маленькая программа (`LETTER_READER` в `stand.mjs`) передаёт строку в `deliverNotification` — функцию, которую вызывает обработчик очереди в `core`, — с транспортом, который письмо не отправляет, а возвращает. Каталог уведомлений, проверка данных и шаблоны при этом те же, что в `core`; базы, магазина и сети программа не видит.
- **Время** двигается правкой дат в базе стенда одной командой `UPDATE`: конец периода вместе с началом и якорем (продукт принимает только конец периода, отстоящий от якоря на целое число месяцев) и вместе с периодом заказа, которым этот период оплачен (`orders.period_start`, `period_end`: продукт пишет период подписки и период заказа одной транзакцией, и «Использование» находит квоту периода по заказу — подписка, сдвинутая без заказа, стояла бы в периоде, которому ничего не начислено, и страница отказала бы), `orders.created_at` для разбора зависших заказов, `past_due_since` для срока просрочки. Проходы планировщика делают остальное. Период «закончился» — значит час назад: то, что продукт считает от конца периода, и то, что он считает от текущего момента, расходятся на час, а проверки «от текущего момента» допускают минуту.
- Каждый такой сдвиг оставляет отметку о письме на прежней дате, поэтому перед списанием `core` пишет письмо заново — уже для сдвинутого конца. Обычный путь без единой правки после письма идёт в `renewal-in-real-time`: письмо за секунды до конца периода, период заканчивается по часам, списание — по этому письму.
- **Проход планировщика можно остановить.** Сценарий `renewal-waits-for-notice` на время убирает планировщик прохода писем из очереди `billing` (остальные проходы идут) и возвращает его точно таким, каким его зарегистрировал `core`, — в своём `finally`; если сценарий упал раньше, это делает запуск сценариев.
- **Ожидания** — опрос базы с дедлайном: строка `waited N s for: …` называет, чего ждали и что видели последним — строку заказа или подписки, темы писем клиента. Там, где нужно убедиться, что ничего _не_ произошло, стенд ждёт, пока `core` завершит нужные проходы, начатые после этого момента, — по завершённым заданиям очереди `billing` в Redis.
- После каждого сценария проверяется, что планировщику ничего не осталось (нет подписок к письму, списанию или окончанию и нет незавершённых заказов), что web ни одно уведомление о платеже заказа не назвал «unknown», что баланс каждого счёта кредитов в базе равен сумме его журнала, а счетов у рабочего пространства три — тарифа, подарка и пакета — либо ни одного, что каждому рабочему пространству подарок начислен ровно один раз — 35 кредитов на счёт подарка под ключом его пользователя, без заказа, с одной записью аудита, — что у каждого заказа продления (`renew.…`) последнее письмо его подписки, записанное раньше заказа, называет его тариф, сумму и конец периода, — при отказе печатаются заказ и все найденные письма — и что «Тарифы», «Оплата» и «Использование» каждого клиента сценария показывают то, что лежит в базе; клиенту без рабочего пространства страницы показывают подарок обещанным, пока под ключом пользователя в журнале ничего нет. Там, где сценарий сверяет остатки (`ledgerHolds`), целый подарок — это ещё и журнал из одной строки: подарок, который сгорел и был начислен заново, дал бы то же число и не прошёл бы.
- **Страницы против базы.** Вместе с остатками сверяется ответ о новой задаче, который несут «Тарифы» и «Использование»: сколько кредитов можно потратить (подарочные — всегда, тарифа и пакета — только при оплаченном тарифе) и сколько из них можно потратить сейчас (кредиты тарифа — не больше дневного лимита плана), сколько отложено, 5 кредитов на старт, день оплаченного тарифа — ни один кредит тарифа сегодня не потрачен, остаток дня равен лимиту плана (или свободному остатку счёта тарифа, если он меньше); без тарифа дневного лимита нет; тот же день стоит на шкале тарифа «Использования»; и шкала периода: её части сходятся с начисленным, а «осталось» равно свободному остатку счёта тарифа. Сам ответ тоже выводится из базы: пока в `credit_rates` нет действующего курса, задача не принимается ни у кого (`rate_missing`), а с курсом принимается у каждого, кто может потратить пять кредитов, — в стенде это все: задач никто не ставит, подарок не тратится. Клиент, у которого пяти кредитов нет, — отказ проверки, а не «задачу не приняли». Курс утверждает сценарий `credit-rate`, второй по порядку: первый сценарий заканчивается с паузой на страницах, остальные — с ответом по остаткам; запуск `--only` без этого сценария идёт без курса. Ещё сверяется, что «Тарифы» продают то, что лежит в таблице `plans`, а в ней — 300, 800 и 2 500 кредитов в месяц, 50, 100 и 300 кредитов в день и пакет из 100, и что таблицы «Точного расчёта» нет: ни у одной включённой модели нет ставки.
- **Письма против базы.** Каждое письмо «Оплата прошла», «Оплата не прошла» и «Тариф закончился», записанное за сценарий, читается целиком и сверяется с базой: «Начислили 300 кредитов на этот период» — с суммой строки начисления этого заказа в журнале, «пакет из 100 кредитов» — со строкой начисления пакета, «Кредитов из пакета осталось: 100» — со свободным остатком счёта пакета, а фраза о том, принимаются ли новые задачи, — со свободным остатком счёта подарка. Числа берутся из журнала и счетов, не из данных письма; слова стенд пишет сам. Письмо, которое говорит другое, печатается целиком.

### Правила сгорания

Таблица «Правила сгорания в одном месте» [проекта модели кредитов](../../../docs/research/2026-10-credits/credits-design.md) (раздел 4.4): что событие делает с каждым из трёх счетов. Каждое правило, кроме правила о резерве (о нём — под таблицей), — проверка сценария, которая сравнивает журналы всех трёх счетов целиком.

| Событие | Сценарий | Тариф | Подарок | Пакет |
| --- | --- | --- | --- | --- |
| Продление | `renewal-success` | Остаток сгорел, начислена новая квота | Одна строка начисления | Одна строка начисления |
| Оплата в просрочке | `renewal-declined` | То же | То же | То же |
| Тариф закончился: не продлён | `pack-and-period-end` | Остаток сгорел | На месте, тратится | На месте, ждёт тарифа |
| Тариф закончился: семь дней без оплаты | `past-due-expires` | То же | То же | То же |
| Тариф закончился: возврат с `--end-subscription` | `refund` | То же, под ключом оплаченного периода | То же | Оба пакета целы |
| Возврат пакета с `--take-credits` | `refund` | Не тронут | Не тронут | Снято сто кредитов этого пакета, второй пакет цел |

Правило о резерве, возвращённом или не использованном после конца периода, стенд не достигает: резервов до P12 никто не ставит.

### Чего стенд не доказывает

- Поведение настоящей ЮKassa: проверена подделка. Её возвраты проходят сразу, поэтому возврат в статусе `pending` и возврат, отменённый ЮKassa, покрыты только тестами `packages/billing`.
- Резервы и списания кредитов задачами: до P12 их никто не создаёт, и стенд их не подделывает записью в базу. Поэтому «доступный остаток» здесь всегда вся квота, история «Использования» пуста, а из ответов о новой задаче стенд видит два: паузу без курса (`rate_missing`) и «задача принимается». Отказы по остаткам, дневному лимиту и границе неоплаченной работы, шкала через продление с резервом и история с суммами проверены тестами `packages/billing` на PostgreSQL; страницы с израсходованными кредитами — браузерным прогоном `test:billing`, где резерв и списание делают функции продукта, вызванные из фикстуры.
- Порядок, в котором тратятся счета, — тариф, подарок, пакет: его показывает только списание. Стенд видит порядок лишь там, где от него зависит, что можно потратить (без оплаченного тарифа — один подарок). Перестановку подарка и пакета в распределении списания ловят тесты `packages/domain` и `packages/billing` и тот же браузерный прогон.
- Запрос без ответа вовсе (поведение `timeout`): клиент ЮKassa ждёт 30 секунд, потерянный ответ стенд изображает ответом 500.
- Страницы в браузере и их тексты — это `pnpm --filter e2e test:billing`: страницы настроек рисует браузер, по HTTP приходит только заготовка. Стенд сверяет с базой ответы, из которых страница строит предложения, и тексты писем. Письмо стенд читает не из почтового ящика: текст строит почтовый модуль копии по строке зеркала; что `core` при доставке делает то же самое, стенд знает по теме, адресу и ссылкам в его журнале.
- Пороги пяти минут, часа, двенадцати часов, трёх и семи дней достигаются правкой дат, а не ожиданием; по часам идут только восемь секунд сценария `renewal-in-real-time`.
- Лимит сайтов тарифа (`project.create` и шаг «Основные данные» мастера) — его показывает браузерный прогон `test:billing` — и «Оплата за действие».
- Импорт файлов сайта в репозиторий, экран «Настраиваем сайт» и проверки доступа сверх одного SFTP-сервера с паролем — это `pnpm verify:site-import` и тесты `packages/site-connections`, `packages/trpc`; здесь сайт нужен только как то, с чем появляются рабочее пространство и подарок. Трата подарка: до очереди задач его никто не расходует, поэтому на счёте подарка всегда все 35 кредитов.
- Таблицу «Точного расчёта»: ставки моделей стенд не утверждает и ни одну модель не включает, поэтому `billing:rates` идёт с пустым списком ставок.
- Продукт с `YOOKASSA_AUTOPAYMENTS=off`: стенд поднимает один web, и переключатель у него включён. Что при выключенном платёж уходит без `save_payment_method`, а автопродление не предлагается и не включается, проверяют тесты `packages/billing` (`autopayments.test.ts`, `fake-shop.test.ts`), роутера и компонентов web.

### CI

`.github/workflows/billing.yml` запускает стенд на изменения web, приложений платформы (`apps/core` и остальные из списка путей workflow), пакетов и самого стенда. Журналы упавшего запуска стенд оставляет в `BILLING_VERIFY_LOG_DIR` (`${{ runner.temp }}/billing-logs`), и шаг с `if: failure()` выгружает их артефактом `billing-logs` на семь дней. Workflow новый: впервые он выполнится, когда ветка будет отправлена на GitHub, до этого стенд проверен только локально на macOS с Docker Desktop.

## Поддельная ЮKassa

`fake-yookassa.mjs` — синтетический сервер вместо `https://api.yookassa.ru/v3`.

Сервер слушает только `127.0.0.1`, всё хранит в памяти и сам обращается только по адресу уведомлений, который тоже должен быть на loopback. Учётные данные никуда не пишутся: запросы запоминаются без заголовка `Authorization`, в stdout попадает одна строка готовности.

### Запуск

Из сценария стенда или теста:

```js
import { startFakeYookassa } from './fake-yookassa.mjs'

const fake = await startFakeYookassa({
  shopId: '123456',
  secretKey: 'test_synthetic-key',
  webhookUrl: 'http://127.0.0.1:3100/api/webhooks/yookassa', // необязательно
})
// fake.apiUrl — значение YOOKASSA_API_URL; fake.controlUrl — команды стенда; fake.close()
```

Отдельным процессом — магазин берётся из окружения, как у web и `core`, в аргументах ключа нет:

```sh
YOOKASSA_SHOP_ID=123456 YOOKASSA_SECRET_KEY=test_synthetic-key \
  node infra/dev/billing-verify/fake-yookassa.mjs --port 4010 \
  --webhook-url http://127.0.0.1:3000/api/webhooks/yookassa
```

Процесс печатает `{"ready":true,"port":4010}` и останавливается по SIGINT или SIGTERM. `--port 0` выбирает свободный порт, `--forwarded-for <адрес>` задаёт адрес отправителя уведомлений (по умолчанию `127.0.0.1`).

Web и `core` смотрят на подделку через четыре переменные (вне production; в production две последние отклоняются при старте):

```sh
YOOKASSA_SHOP_ID=123456
YOOKASSA_SECRET_KEY=test_synthetic-key
YOOKASSA_API_URL=http://127.0.0.1:4010/v3
YOOKASSA_WEBHOOK_ALLOWLIST=127.0.0.1
```

Пятая, `YOOKASSA_AUTOPAYMENTS` (`on` или `off`), говорит продукту, одобрены ли магазину автоплатежи. Вне production её можно не задавать — тогда `on`; с `off` продукт не отправляет `save_payment_method` и не предлагает автопродление. Что это за переключатель и что спросить у ЮKassa — [памятка владельцу](../../../docs/plan/51-yookassa-shop-setup.md).

### API

Basic-аутентификация магазином и ключом, заданными при старте; иначе 401 `invalid_credentials`.

| Запрос | Что делает |
| --- | --- |
| `POST /v3/payments` с `confirmation` | Платёж `pending` со ссылкой на страницу подделки `/pay/{id}` |
| `POST /v3/payments` с `payment_method_id` | Списание сохранённым способом оплаты: сразу `succeeded` |
| `GET /v3/payments/{id}` | Текущее состояние платежа |
| `POST /v3/payment_methods` | Привязка без платежа (`bank_card` или `sbp`): `pending` со ссылкой на `/pay/{id}` |
| `GET /v3/payment_methods/{id}` | Текущее состояние способа оплаты |
| `POST /v3/refunds` | Возврат: сразу `succeeded`, не больше остатка платежа |
| `GET /v3/refunds/{id}` | Возврат |

- **`Idempotence-Key`** обязателен у каждого POST. Повтор ключа возвращает первый ответ — и отказ 400 тоже; в журнале запросов у повтора `replayed: true` и `sameRequest` — совпало ли тело. Ключи живут до команды `forget-idempotence-keys` (настоящая ЮKassa хранит их 24 часа).
- **Способ оплаты сохраняется**, только если платёж создан с `save_payment_method: true`. Его идентификатор равен идентификатору платежа, как в документации ЮKassa.
- **Строже настоящей ЮKassa, намеренно:** объект `receipt` отклоняется (продавец — самозанятая), `capture` должен быть `true`, подтверждение — только `redirect`.

### Магазин без одобренных автоплатежей

Команда `autopayments` с `{"enabled": false}` превращает подделку в магазин, которому ЮKassa ещё не одобрила автоплатежи. Такой магазин отвечает `403` с телом `{"type": "error", "id": "…", "code": "forbidden", "description": "Магазин не имеет права на проведение операции"}`; `{"enabled": true}` возвращает право.

| Запрос | Ответ | Откуда известно |
| --- | --- | --- |
| `POST /v3/payments` с `save_payment_method: true` | 403 `forbidden` | Настоящий магазин AnyNote, 13.05.2026 (коммит `72b6774`): так ответил магазин с верными ключами |
| `POST /v3/payments` без поля `save_payment_method` | Платёж создаётся и оплачивается, способ оплаты не сохраняется | Тот же магазин: платёж в такой форме был принят и оплачен |
| `POST /v3/payments` с `save_payment_method: false` | Как без поля | **Допущение.** На настоящем магазине не проверено нигде: AnyNote явное `false` не отправляет |
| `POST /v3/payment_methods` | 403 `forbidden` | **Допущение:** привязка без платежа тоже требует права на автоплатежи |
| `POST /v3/payments` с `payment_method_id` | 403 `forbidden` | **Допущение:** автосписаний на магазине без права никто не проводил |
| Любой `GET` и `POST /v3/refunds` | Как обычно | Допущение: чтение и возврат права на автоплатежи не требуют |

Отказ даётся «на входе», как при неверном ключе: `Idempotence-Key` не запоминается, поведение из очереди не тратится. Поэтому когда право возвращают, тот же ключ создаёт платёж. Как настоящая ЮKassa поступает с ключом отклонённого запроса, неизвестно.

### Страница оплаты

`GET /pay/{id}` — страница с кнопками «Оплатить» и «Отказаться» (у привязки — «Привязать» и «Отказаться»). Нажатие меняет статус и отправляет покупателя на `return_url` ответом 303 — как настоящая ЮKassa, при любом исходе; результат магазин узнаёт через API. «Отказаться» отменяет платёж с причиной `expired_on_confirmation`, привязку переводит в `inactive`.

### Уведомления

После смены статуса подделка один раз отправляет `{type: "notification", event, object}` на адрес уведомлений: `payment.succeeded`, `payment.canceled`, `payment_method.active`, `refund.succeeded`. Повторов нет. У запроса заголовок `X-Forwarded-For` с одним адресом: web берёт адрес отправителя из него. Без заголовка сервер Next подставит адрес соединения (127.0.0.1 или ::1), поэтому в списке адресов локального стенда нужны оба.

### Команды стенда

`GET /__control/state` — платежи, способы оплаты, возвраты, очередь поведений и журнал доставки уведомлений. `GET /__control/requests` — принятые запросы API. Остальные команды — `POST /__control/<команда>` с JSON.

| Команда | Тело | Что делает |
| --- | --- | --- |
| `behaviour` | `{target, behaviour, reason?, party?, processed?, times?, delayMs?}` | Ставит поведение в очередь: его получит следующий платёж (`times` — несколько следующих) |
| `complete` | `{paymentId \| paymentMethodId, outcome?, reason?, party?}` | Завершает ожидающий платёж или привязку: `succeed` (по умолчанию) или `cancel` |
| `webhooks` | `{enabled}` | Отправлять уведомления или придерживать |
| `notify` | `{paymentId \| paymentMethodId \| refundId, forwardedFor?, event?, object?}` | Отправляет уведомление сейчас; `forwardedFor` — «с» другого адреса, `event` и `object` — поддельное тело |
| `save-anyway` | `{enabled}` | `payment_method.saved: true` у платежа с `save_payment_method: false` (покупатель сам поставил галочку на форме ЮKassa) |
| `autopayments` | `{enabled}` | `false` — магазин без одобренных автоплатежей: см. «Магазин без одобренных автоплатежей» |
| `card` | `{last4?, card_type?, first6?, expiry_month?, expiry_year?, issuer_country?}` | Карта следующих оплат и привязок |
| `forget-idempotence-keys` | `{}` | Забывает ключи идемпотентности |
| `settle` | `{}` | Отвечает, когда все отправленные уведомления доставлены или не удались |
| `reset` | `{}` | Стирает всё, кроме магазина и адреса уведомлений |

`target` у `behaviour`: `saved` (по умолчанию) — платежи с `payment_method_id`, `payment` — платежи со страницей оплаты.

| Поведение | Платёж сохранённым способом | Платёж со страницей |
| --- | --- | --- |
| `succeed` | Сразу `succeeded` (так и без команды) | «Оплатить» → `succeeded` (так и без команды) |
| `cancel` | Сразу `canceled` с `cancellation_details` (`reason`, по умолчанию `general_decline`; `party`, по умолчанию `payment_network`) | «Оплатить» → `canceled` с этой причиной |
| `stay-pending` | Остаётся `pending`, пока не придёт `complete` | «Оплатить» возвращает покупателя, платёж остаётся `pending` |
| `http-500-once` | Запрос выполнен, ответ — HTTP 500; повтор с тем же ключом возвращает созданный платёж | То же |
| `timeout` | Запрос выполнен, ответа нет; повтор с тем же ключом возвращает созданный платёж | То же |

С `processed: false` запрос `http-500-once` и `timeout` не выполняется вовсе: платёж не создаётся, ключ не запоминается.

`delayMs` (до 60 000) — медленный банк, с любым поведением: запрос выполняется и получает ответ только через это время. Ключ идемпотентности занят сразу, поэтому повтор того же ключа во время задержки дожидается первого запроса и получает его ответ, а не второй платёж.

### Чего нет

Списков платежей и возвратов, двухстадийной оплаты и отмены платежа через API, чеков, виджета и QR-кода, повторной доставки уведомлений, ограничений частоты. Возврат всегда успешен. Подделка не заменяет сверку с настоящим тестовым магазином перед подключением боевого: что в ней подтверждено настоящим магазином, что нет и какие девять проверок сделать руками в первый день — [памятка владельцу](../../../docs/plan/51-yookassa-shop-setup.md).
