# Стенд шлюза подписок

`pnpm verify:llm-gateway` — синтетическая проверка шлюза подписок с настоящим закреплённым OpenCode CLI, одноразовыми PostgreSQL и OpenBao, без подписки пользователя. Первый состав стенда и его ограничения описаны в [отчёте B13](../../../docs/plan/20-p3-synthetic-gateway.md); что стало с каждой его проверкой при удалении прежних оболочек — в [отчёте G8](../../../docs/plan/48-removal.md).

Инструменты разведки P3.0 на настоящем провайдере (`record-proxy.mjs`, `local-spike.mjs`, `backend-adapter.mjs`) удалены в G8 вместе с адаптерами прежних провайдеров. Их порядок и итоги остались в истории: [spike.md](../../../docs/research/2026-09-subscriptions/spike.md) и отчёты 13 и 14 в `docs/plan`.

Как стенд запускает CLI:

- **Образ** — production-среда агента (`infra/sandbox/Dockerfile`, цель `runtime`, CLI из lock-файла); `cli.Dockerfile` только добавляет `cli.mjs` и проверяет версию `npm ls`. Три образа стенда — `raditi-p3verify-runtime`, `raditi-p3verify-cli` и `raditi-p3verify-guard` — прогон без `--no-build` собирает под одной меткой, по умолчанию `b13`. Переменная `RADITI_VERIFY_IMAGE_TAG` называет другую метку: так прогон берёт образы другой сборки и не трогает прежние (`RADITI_VERIFY_IMAGE_TAG=g8 pnpm verify:llm-gateway --no-build`). Это переменная стенда, приложения её не читают; тот же выбор действует у `pnpm verify:agent-content`.
- **Ходы как в продукте.** Конфигурация, `AGENTS.md`, MCP-сервер и продолжение сессии берутся из `prepare` и `command` драйвера OpenCode и проходят проверки исполнителя хода (`preparedFilesSchema`, отсутствие ключей в файлах, env и argv). Секреты ложатся в tmpfs `/run/raditi/secrets`. Ходы идут через `sandbox-gw`, роль `llm` с политикой тела и маршрут `/mcp` (`apps/orchestrator/scripts/verify-llm-zai.mjs`).
- **MCP** — синтетический сервер в `fake-subscriptions` (порт 8788 только во внутренней сети стенда). Список инструментов — production-профиль роли `mcp` (`site_info` из собранного `McpToolsController`, схема — как у mcp-nest; `productionMcpTools` в `apps/orchestrator/scripts/verify-llm-mcp-tools.mjs`), токен — MCP-токен хода из `issue`.
- **Общие сценарии идут один раз, на группе Z.ai** ([отчёт G7](../../../docs/plan/47-common-scenarios-zai.md), часть 2). Сценарии платформы — границы протокола, сбои внутри потока, барьеры падений, бюджет, пул и вывод аккаунта (`verify-llm-protocol.mjs`, `verify-llm-gateway-stream.mjs`, `verify-llm-crashes.mjs`, `verify-llm-lifecycle.mjs`) — получают одну группу: её id, формы сырого запроса и то, как синтетический провайдер изображает нужный сценарию ответ, — данные модуля `verify-llm-zai-forms.mjs`. Имён провайдеров и CLI в самих сценариях нет. Группу собирает `verify-llm-zai.mjs` и вызывает их после «смены ключа плана», до итоговой проверки того, что дошло до провайдера и песочницы. Группа API Z.ai после неё общих сценариев не повторяет (П46): они проверяют роль, а не бэкенд. То, что шло на аккаунтах прежних провайдеров, ушло в G8 вместе с ними.
- **Ошибки внутри потока** (`verify-llm-gateway-stream.mjs`) идут ходами драйвера группы, то есть с настройками повторов production. Провайдер отвечает объектом `error` внутри начатого потока (сценарий `stream_error` синтетического Z.ai с кодом таблицы решения 9). Окончательный отказ должен завершить ход после одного запроса к провайдеру и оставить в `llm_keys.last_refusal` свой вид; кратковременный остаётся повторяемым, и ход завершается со вторым запросом.
- **Настоящая роль `mcp` вместо синтетического сервера** — стенд `pnpm verify:agent-content` ([отчёт](../../../docs/plan/30-agent-content-stand.md)). `startVerificationStack({ content: true })` передаёт `sandbox-gw` адрес роли на хосте (`VERIFY_MCP_UPSTREAM`, по умолчанию прежний `http://fake-subscriptions:8788`) и добавляет S3 для снимков (профиль Compose `content`), AppRole `mcp` с политикой `mcp-content` и токены `sites-writer`, `workspace-provisioner` и `core-transit` (доступ сайта, ключ рабочего пространства и чтение снимка самим стендом — без root-токена). Роль запускается штатно, из сборки: `node dist/main.js` с окружением одной роли (`apps/orchestrator/scripts/verify-agent-content-role.mjs`), а не через `startWorker` ([отчёт](../../../docs/plan/33-mcp-role-content-resolver.md)). Модель ведут сценарии фейка `content_edit` (чтение страницы, запись с ключом идемпотентности, та же запись ещё раз, итог) и `content_forbidden` (один вызов `wp_rest`, который платформа должна отклонить: чтение чужого маршрута либо, при заданном `body`, запись без ключа). `{{contact}}` в тексте правки заменяется первым маркером контакта из разговора: фейк, как модель, переносит маркер и ничего не придумывает. `verify:llm-gateway` профиль и параметр не включает и остаётся прежним.
- **Рукописной конфигурации CLI в стенде нет:** все ходы идут через драйвер — `cli.mjs` исполняет только то, что подготовил драйвер (`runPrepared`), и одиночный запрос из контейнера CLI (`request`).
- **Синтетический Z.ai** (`fake-zai.mjs`, переход на OpenCode и GLM, [отчёт G2](../../../docs/plan/41-zai-backend.md)) — два адреса плана GLM Coding Plan: чат `POST /api/coding/paas/v4/chat/completions` и квота `GET /api/monitor/usage/quota/limit`, — и чат API с оплатой за токены `POST /api/paas/v4/chat/completions` (П15). Кадры и ответы повторяют записи `docs/research/2026-10-opencode-glm/samples`, коды ошибок — таблицу решения 9 плана перехода (статусы у неизмеренных кодов — допущение, константа `ZAI_ERROR_STATUS`). Фейк встроен в `fake-subscriptions.mjs`: запросы на эти два пути обслуживает он; имя `api.z.ai` есть в сертификате, в псевдонимах сети `providers` и в списке прокси стенда.
  - Управление — `POST /zai` управляющего порта с телом `{reset?, scenario?, quota?, key?, apiKey?, balance?}`; чтение — `GET /zai` или ключ `zai` в `GET /state`; общий `POST /reset` сбрасывает и его.
  - Сценарии чата: `text`, `tools` (вызовы инструментов: `calls` — один раунд, `rounds` — список раундов; номер раунда — число шагов с инструментами после последнего сообщения пользователя; после последнего раунда и на запрос без `tools`, каким CLI просит сжать контекст, — текст; с `filler` ответ с вызовом сначала «думает» заданное число байт — CLI возвращает рассуждение шага со следующим запросом хода, и так стенд получает запрос больше, чем принимает шлюз), `finish` (любой `finish_reason`), `error` (код и статус, `retryAfter`, `failures` — только первые N запросов; дальше обычные ответы с текстом сценария и обычным расходом), `stream_error` (объект `error` после первого кадра начатого потока; `error` со статусом и без кода — объект ошибки, который кода не называет: так, по словам третьей стороны, API отвечает на слишком частые запросы, записи нет) и «враждебные» ответы для проверок шлюза: `envelope200`, `plain200`, `no_usage`, `no_done`, `done_only`, `no_finish`, `no_finish_no_done`, `empty`, `cut`.
  - Сценарии стенда `verify:agent-content` (G5, [отчёт](../../../docs/plan/44-agent-content-opencode.md)): `content_edit` — чтение страницы, запись с ключом идемпотентности, та же запись ещё раз, текст; `content_forbidden` — один вызов, который платформа должна отклонить (чтение заданного маршрута, а с `body` — запись без ключа), затем текст. Параметры — `route`, `idempotencyKey`, `body`. Что именно просит модель, описывает `content-scenario.mjs`, общий с `fake-subscriptions.mjs`; раунд выбирается тем же правилом, что у `tools`. Вызывается функция, которую CLI объявил для инструмента MCP `wp_rest`: закреплённый OpenCode называет её `<сервер>_<инструмент>`, в записи `34-run-c-mcp` это `raditi_wp_rest`. Если такой функции в запросе нет или их две, либо правке нужен маркер контакта, а в разговоре его нет, фейк отвечает 400 и ничего не выдумывает.
  - `delayMs` задерживает поток после его первого кадра: ответ начат, вызов у роли открыт. На этом стоят сценарии падений (роль убита посреди потока, клиент ушёл, ключ отозван, база на паузе) и параллельные вызовы сценариев бюджета.
  - Квота живая: окно пяти часов не начато, первый запрос его начинает (`remaining` на единицу меньше, `currentValue` ещё 0 — как в записях 60 и 62), каждый следующий — один кредит. `quota.fiveHour.exhausted` исчерпывает окно (чат отвечает 429 с кодом 1308), `idle` возвращает в «не начато», `resetInMs` задаёт сброс, `mode: 'broken'` и `mode: 'envelope'` отдают нечитаемый ответ и конверт HTTP 200.
  - В записях запросов нет значений заголовков с учётными данными: только признак `credential` (`plan-key`, `api-key`, `other`, `none`) и имена заголовков. `counters.chat` считает запросы обоих путей чата; путь назван в записи.
  - Ключей плана два, принимается один: `key: 'rotated'` заставляет фейк отказывать первому ключу (401 на пути чата, конверт с кодом 401 на пути квоты) и принимать второй, `SYNTHETIC_ZAI_ROTATED_KEY`; сброс возвращает первый.
  - **API с оплатой за токены.** Ключи двух предложений синтетический мир держит раздельными, чтобы проверить ключ на пути чужого предложения; настоящий ключ Z.ai работает на обоих путях (решение владельца от 17.10.2026, П83). Ключ API — `SYNTHETIC_ZAI_API_KEY` и следующий за ним `SYNTHETIC_ZAI_ROTATED_API_KEY`, принимается один (`apiKey: 'rotated'`). Путь API отвечает тем же потоком и тем же расходом, что путь плана (успешный ответ API не записан — допущение), и окон не двигает: исчерпанное окно плана ему не мешает. `balance: 'empty'` — у аккаунта нет денег: каждый запрос ключа API получает 1113 под HTTP 429 с `application/json; charset=UTF-8`, как в записи 21, до чтения тела; `balance: 'funded'` — пополнен; так фейк стартует и так после сброса, а `empty` ставят только сценарии, которые проверяют 1113. Ключ одного предложения на пути другого тоже получает 1113: ключ плана на пути API — запись 21, ключ API на пути плана — допущение. Чужой ключ — 401, без ключа — 1001. Путь квоты отвечает ключу API конвертом записей 10, 10b и 14 с кодом и текстом записи 21 (`{code: 1113, msg, success: false}`, HTTP 200): ответ не записан, а проба ключа API (spec §20, П66) читает любой конверт, который не называет отклонённый ключ, как ключ, который провайдер принимает. Живой прогон с `--api` проверяет это первым.
  - Отдельным процессом: `node infra/dev/llm-verify/fake-zai.mjs --tls-key <файл> --tls-cert <файл>` печатает `{ready, port, controlPort}`. Так его запускает интеграционный тест роли `llm` (`apps/orchestrator/src/llm-gateway/gateway.integration.test.ts`, `pnpm verify:db`).
- **Группа Z.ai стенда** (`apps/orchestrator/scripts/verify-llm-zai.mjs`, [отчёт G4](../../../docs/plan/43-zai-gateway-stand.md)) — группа плана: с G7 она несёт все общие сценарии. Задачи, ключи хода и ход настоящего CLI через драйвер она берёт из `verify-llm-zai-harness.mjs`, общего с группой API. Настоящий OpenCode 1.18.34 запускается только через `prepare` и `command` драйвера; рукописной конфигурации OpenCode в стенде нет.
  - Путь: песочница → `sandbox-gw` → роль `llm` → фейк Z.ai **напрямую**. Роль перезапускается без четырёх переменных `LLM_EGRESS_*` и с `LLM_BACKEND_URL_ZAI_CODING=https://localhost:<порт>`: порт TLS фейка опубликован на loopback, в сертификате фейка есть имя `localhost`. Один ход до этого идёт через прокси стенда: заданный прокси остаётся путём ко всем провайдерам.
  - Аккаунт создаёт команда оператора `subscription-login.mjs --backend zai-coding --plan lite` с синтетическим ключом на stdin, тоже без прокси. Строки провайдера, профиля `glm-5.3-standard` и стендовой ставки включает скрипт; строку драйвера `opencode` он не включает, а утверждает, что её включили миграции и сиды; окна пишет только проба.
  - Домашний каталог драйвера OpenCode в контейнере CLI — tmpfs (`/agent-home/opencode`), как весь `/agent-home` в песочнице: обёртка драйвера закрывает каталоги конфигурации правами 0555, а смонтированный с рабочей машины каталог Docker Desktop этих прав не соблюдает. Родитель рабочей копии `/workspace` — тоже tmpfs: обёртка держит там файлы OpenCode сайта, пока идёт CLI. Перед каждым ходом в домашнем каталоге остаются только два файла базы сессии — как после восстановления снимка.
  - Роль `llm` перезапускается между сценариями, которым нужна её чистая память: паузы аккаунта и правило «одна проба на аккаунт в пять минут» живут в процессе.
  - Общее со стендом `verify:agent-content` вынесено в `apps/orchestrator/scripts/verify-llm-zai-setup.mjs`: два предложения Z.ai как данные (`ZAI_OFFERS`: бэкенд, метка `--plan`, маршрут `sandbox-gw` и базовый адрес CLI — помощник ядра `llmGatewayBaseUrl`, путь фейка, ключи), окружение роли без прокси (переменная стенда каждого объявленного источника — у обоих предложений она одна, `LLM_BACKEND_URL_ZAI_CODING`), команда оператора и импорт ключа, включение строк провайдера, профиля и ставки и утверждение о строке драйвера `opencode`, которую включают миграции и сиды, очистка домашнего каталога OpenCode между ходами.
- **Группа API Z.ai** (`apps/orchestrator/scripts/verify-llm-zai-api.mjs`, П15) идёт после группы плана, на аккаунте другого провайдера (`zai-api`), так что пулы друг друга не видят. Восемь проверок:
  - импорт ключа настоящей командой `subscription-login.mjs --backend zai-api --plan payg` в одноразовый OpenBao стенда при пустом балансе (П75): проба ключа на пути квоты его принимает, чужой ключ отклоняет, окон никто не пишет, секрет читает только роль `llm`;
  - допуск аккаунта без окон: ни `issue`, ни первый вызов ключа не спрашивают окна — и тогда, когда у аккаунта есть пустой снимок десятиминутной давности;
  - ход настоящего OpenCode через `sandbox-gw` по маршруту `/zai/paas/v4/chat/completions`: инструмент, итог, только путь и ключ API, расход каждого вызова в `llm_calls` и `token_usage` ровно один раз и равен записям CLI; ключ API на маршруте плана — 403 `raditi_backend` без запроса провайдеру;
  - пустой баланс (1113): окончательный отказ `subscription_limit` в одном запросе, долговременная пауза 5 минут в `cooling_until`, строка `{"event":"llm_pool_health","reason":"balance_exhausted","checks":1}` в логе роли и ни одной пробы; новая задача ждёт;
  - второй пустой баланс за сутки — пауза 15 минут; после паузы и пополнения аккаунт снова выбирается, и ход идёт;
  - отклонённый ключ — `auth`: одна проба ключа подтверждает, `needs_relogin`, `--relogin` с новым ключом возвращает аккаунт;
  - 1302 — кратковременный отказ, OpenCode повторяет после паузы и доходит до итога; 429 без кода — тоже кратковременный, без пробы;
  - до провайдера не дошло ничего от ключа хода, заголовков сессии и cookie, ни одного запроса на путь плана; ключей провайдера нет в песочнице; ни один окончательный отказ не приглашает CLI повторить запрос.
- **Живой режим** — те же два стенда на настоящем GLM: раздел «Живой режим: настоящий GLM через шлюз» в конце этого файла.

## Проверки

`pnpm test:infra` запускает синтетические тесты; ни подписки, ни ключа плана они не требуют.

`sanitize-samples.mjs` — единственный путь, которым записи пробы перехода на OpenCode и GLM попадают в `docs/research/2026-10-opencode-glm`: команды `scan`, `copy` и `check`, правила и пределы — в шапке скрипта и в [README каталога исследований](../../../docs/research/2026-10-opencode-glm/README.md), «Как записи очищены». Скрипт работает по форме и ключа не требует. `sanitize-samples.test.mjs` проверяет правила на синтетических значениях и при каждом прогоне — весь каталог исследований: в записях нет заголовка вне разрешающего списка, нигде нет строки вида ключа, bearer-значения, токена MCP платформы и неочищенного идентификатора. Находка секрета выводится правилом, строкой и длиной, без единого знака значения.

Для стенда B13: `fake-subscriptions.test.mjs` проверяет синтетический MCP (только зарегистрированный токен хода, токен не попадает в состояние), управляющий порт — он отделён от порта провайдера, и его сброс убирает и состояние провайдера, и регистрацию хода — и остановку процесса по сигналу; то, чем отвечает сам синтетический провайдер, проверяет `fake-zai.test.mjs`; `cli.test.mjs` — что подготовленный драйвером ход попадает в контейнер только через stdin `docker exec`, пути файлов и секретов ограничены `/agent-home` и `/run/raditi/secrets`, а образ CLI собирается из production-среды агента; `stack.test.mjs` — что прокси выхода стенда пускает роль `llm` по отпечатку сертификата.

Уборка стенда B13 не полагается на права хоста. На обычном Linux файлы, которые CLI записал в смонтированные каталоги, принадлежат uid 10001 контейнера, и пользователь хоста не может их ни перечислить, ни удалить. Поэтому `close()` сессии сначала очищает `/agent-home` и `/workspace/repo` изнутри контейнера (`docker exec … find … -delete`), затем удаляет контейнер и каталог. Если контейнера уже нет или хост всё же получил отказ, каталог очищает одноразовый контейнер того же образа от root без сети, после чего хост удаляет его; так же удаляется каталог всего стенда. Сбой такого контейнера — ошибка уборки, а не молчаливый пропуск. Это проверяют `cli.test.mjs` (порядок вызовов Docker, недоступный хосту подкаталог) и `stack.test.mjs`. На Docker Desktop запасной путь не срабатывает; на обычном Linux порядок подтверждён отдельной проверкой с настоящими uid 1001 и 10001, а полный проход стенда на раннере GitHub (Linux, x64) — job `verify-llm-gateway` workflow `llm-gateway.yml` — прошёл 11.10.2026 ([отчёт G8](../../../docs/plan/48-removal.md), «Прогон на GitHub»).

## Живой режим: настоящий GLM через шлюз

Тот же путь, что у детерминированных стендов, — песочница → `sandbox-gw` → роль `llm` → провайдер, — но в его конце настоящий GLM на `api.z.ai`, к которому роль ходит сама, без узла выхода, как в продукте ([отчёт G6](../../../docs/plan/45-zai-live.md)). Модели уходит только синтетика: выдуманные промпты и страница одноразового WordPress. В CI режим не запускается: ни один workflow не называет `--live` и переменную ключа `ZAI_API_KEY` (`infra/app/ci.test.mjs`), а сам стенд отказывает при заданном `CI`. Репетиции (`--rehearsal`) с G7 идут в CI шагами после детерминированного прохода того же job — четыре в `llm-gateway.yml` (с `--api` — с 17.10.2026), одна в `agent-content.yml`, все с `--no-build`: сборку и образы оставляет детерминированный проход. Ключ им не нужен, переменная `CI` репетиции не мешает; набор шагов закрепляет тот же `infra/app/ci.test.mjs`.

Ещё два флага: `--no-build` (не пересобирать orchestrator; образов живой режим не собирает никогда — их собирает детерминированный прогон) и `--keep=<абсолютный каталог вне репозитория>` — записать обмены, которые видел наблюдатель стенда, чтобы перенести нужные в репозиторий через `sanitize-samples.mjs`. Обмены записываются и у прогона, который не прошёл или был прерван, — после поиска ключа по ним в памяти и только если его там нет: разбор неудачи не должен стоить ещё одного живого прогона.

**Ключ плана.** Стенд читает `ZAI_API_KEY` из своего окружения один раз, в самом начале, и сразу удаляет переменную — до запуска любого другого процесса. Значение уходит одним путём: на stdin команды оператора `subscription-login.mjs --backend zai-coding`, которая кладёт его в одноразовый OpenBao стенда. Его нет ни в аргументах, ни в окружении ролей, контейнеров CLI и синтетических сервисов, ни в файлах. Флага с файлом ключа нет.

**Ключ API** (`--api`). Та же переменная `ZAI_API_KEY` и тот же порядок — решение владельца от 17.10.2026 (П77): один ключ Z.ai работает на обоих путях, и для живой проверки API владелец назвал ключ общего с production аккаунта, у которого есть баланс. Стенд читает переменную один раз и сразу удаляет, значение уходит только на stdin `subscription-login.mjs --backend zai-api --plan payg`. Флаг `--api` есть только у стенда шлюза и только с `--live` или `--rehearsal`; с `--measure` и `--results` он не сочетается — замеры считают кредиты окон плана, у API их нет.

Запуск: переменная `ZAI_API_KEY` должна быть в окружении команды `pnpm verify:llm-gateway --live` (так же `pnpm verify:llm-gateway --live --api` и `pnpm verify:agent-content --live`) — из оболочки, где она уже экспортирована. Значение в командной строке не набирайте: оно останется в истории оболочки. Стенд можно запустить и как `node --env-file=<файл> <скрипт стенда> --live` — способ, который называет spec §20, П9: рабочие процессы ролей (`workers.mjs`) получают окружение из двух имён и аргументы Node без `--env-file` и `--env-file-if-exists`, так что файл окружения стенда им не передаётся. Оболочка и `pnpm`, запустившие стенд, держат переменную, пока он идёт.

**Отказ запуска** (код возврата 2, ничего не отправлено провайдеру сверх импорта и первой пробы): нет ключа в окружении или он не похож на ключ; задано `CI`; в окружении есть подмена адреса, прокси или переключатель CA (`LLM_BACKEND_URL_*`, `LLM_EGRESS_*`, `LLM_UPSTREAM_CA_FILE`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_USE_SYSTEM_CA`, `NODE_EXTRA_CA_CERTS`, `NODE_USE_ENV_PROXY`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, флаги CA в `NODE_OPTIONS`); после импорта снимок окон аккаунта, записанный пробой роли (`subscription_accounts.limit_windows`), показывает окно пяти часов выше 50 % или неделю выше 80 % либо окна неизвестны. Первые три отказа случаются до запуска чего бы то ни было. Так 17.10.2026 был отклонён первый живой запуск `--api`: `NODE_TLS_REJECT_UNAUTHORIZED` пришла в оболочку из профиля пользователя; второй запуск шёл как `env -u NODE_TLS_REJECT_UNAUTHORIZED pnpm verify:llm-gateway --live --api`. Прирост окна пяти часов больше 5 процентных пунктов за прогон — прогон не пройден. У прогона с `--api` окон нет: шагов плана — отказа по окнам, снимка окон, прироста окна, чтения квоты в конце — он не делает, и запаса на последнее чтение квоты у его счёта нет.

**Что проверяет прогон с `--api`.** То, чего до 17.10.2026 не показывала ни одна запись и что решения П15 приняли допущениями (прогон 17.10.2026 подтвердил всё — ниже):

- импорт проходит на пробе ключа — `GET /api/monitor/usage/quota/limit` с ключом API отвечает конвертом, который не называет отклонённый ключ (П66); если Z.ai отвечает иначе, прогон кончается на импорте строкой `The import of the API key (the probe of the key on the monitor path) failed…` — одного запроса хватает, чтобы это узнать;
- первый ключ хода выдаётся без запроса провайдеру и без записи окон;
- где приходит расход ответа API — в кадре с `finish_reason` или отдельным кадром после него: прогон сообщает это строкой отчёта (`usage in the finish chunk k of n`, `usageAtFinish` в `streamSummary`) и на этом не падает — счётчик роли читает обе формы;
- два хода без инструментов на уровнях `low` и `max` одной модели (профили `glm-5.3-light` и `glm-5.3-heavy` провайдера `zai-api`) насчитывают разное число `reasoning_tokens`: уровень профиля доходит до API. Эти два хода идут до четырёх ходов приёмки: прогон их должен, поэтому они первыми берут бюджет запросов, и ни один из них не встаёт между ходом «текст» и его продолжением;
- каждый запрос провайдеру — проба импорта либо вызов ключа хода: сверх вызовов роль ничего не спросила.

**Живой прогон с `--api`** запускается вручную — из оболочки, где `ZAI_API_KEY` уже экспортирован: `pnpm verify:llm-gateway --live --api`. Ключ — тот же, что у живого режима плана: ключ общего с production аккаунта Z.ai, у которого есть баланс для проверок (решения владельца от 17.10.2026, П77 и П83). Худший случай прогона — 20 запросов по 7–40 тысяч токенов входа и до 32 000 токенов выхода каждый, около 4 $ по публичной цене GLM-5.3. В CI такой прогон не запускается (правило 1). Если баланс всё же кончится, прогон не ломается молча: вызов получает 1113, и ход кончается отказом `subscription_limit`.

**Прогон 17.10.2026** — код 0, 82 с из 600, 10 запросов провайдеру из 20 (сторож не отклонил ни одного), 10 проверок, OpenCode 1.18.34 на настоящем API. Запустил руководитель задачи с ключом, который владелец передал в чате. Импорт прошёл на пробе ключа (П66); аккаунт без окон допущен без запросов провайдеру при выдаче ключа хода; уровни `low` и `max` насчитали 27 и 126 токенов рассуждения (П82); в каждом ответе расход пришёл в кадре с `finish_reason`; итог валиден во всех четырёх ходах приёмки по обоим чтениям; расход `llm_calls` (9 завершённых вызовов) равен записям CLI; кодов провайдера и сигналов нет; ключа нет ни в одном из десяти мест, где его ищет стенд. Не проверены 1113 на настоящем пустом балансе, параллельность ключа API, пределы частоты, коды 1308–1317 на API и ключ плана под `zai-api`. Ключ побывал в чате и в командной строке запуска, поэтому владельцу рекомендуется перевыпустить его в консоли Z.ai. Числа по ходам — [отчёт 52](../../../docs/plan/52-zai-api-backend.md), «Живая проверка».

**Профиль роли `llm`** (`verify-llm-worker.mjs`, `roleProfileProblems` в `live.mjs`). В живом профиле процесс роли не стартует с тем, что запрещено production (`egressConfigFromEnv(…, 'production')` самого продукта): `LLM_UPSTREAM_CA_FILE`, любая `LLM_BACKEND_URL_*`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_USE_SYSTEM_CA`, `NODE_USE_ENV_PROXY`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, флаг CA в `NODE_OPTIONS` — в конфигурации, которую передал стенд, и в настоящем окружении и аргументах процесса; сверх списка продукта — `NODE_EXTRA_CA_CERTS` в любом значении (сама роль в production пропускает одно: файл CA Vault по пути профиля app-ВМ, `PRODUCTION_VAULT_CA_FILE`; у живого стенда OpenBao без TLS, и лишний CA ему не нужен), заданный прокси и роль без сторожа запросов. Синтетический профиль прежний: только фейки на loopback и синтетический CA. Оба закрепляет `live.test.mjs`.

**Стек.** В живом стеке нет ничего, что могло бы ответить от имени провайдера: `stack.mjs` поднимает сервисы поимённо — PostgreSQL, OpenBao, `sandbox-gw` и S3 (стенд контента) либо `synthetic-mcp` (стенд шлюза: MCP-сторона `fake-subscriptions.mjs --mcp-only`, без слушателя TLS, без псевдонима `api.z.ai`, без тома сертификатов). Фейки провайдеров, прокси стенда и сертификаты не создаются.

**Предел запросов** не зависит от поведения CLI и модели и держится тремя линиями:

1. Потолок вызовов на ключ хода самой роли (`LLM_MAX_CALLS_PER_KEY`: 5 в приёмке шлюза, 8 в приёмке контента, 2 и 9 в замере, 1, 2 и 3 в узком замере итога) и ограниченное число ключей, которые выдаёт стенд.
2. Счёт стенда: перед каждым ходом он проверяет, что худший случай хода помещается в остаток с запасом на последнее чтение квоты. Не помещается первая попытка хода — ход не начинается и прогон не пройден; не помещается повторная попытка исхода, зависящего от модели, — попытки этого исхода кончаются, прогон идёт дальше.
3. Жёсткая стена — `live-guard.mjs`, загруженный через `--import` в каждый процесс, который может дойти до провайдера (роль `llm`, `core`, команда оператора), и в сам стенд. Он подменяет `net.Socket#connect`: loopback проходит, соединение с `api.z.ai:443` сначала записывается в общий журнал прогона и открывается, только если его место в журнале не выше предела, любой другой адрес отклоняется и записывается. Роль открывает соединение на каждый запрос, поэтому журнал считает запросы вместе с пробами квоты. Сторож, который не может писать журнал, не открывает ни одного соединения. Когда сторож отказал, стенд за полсекунды обрывает ход и останавливает прогон — в обоих стендах, одной обёрткой хода (`live.watched`).

Репетиция стенда шлюза доказывает это на фейке: модель, которая вызывает инструменты без конца, роль останавливает на потолке ключа; с поднятым потолком прогон обрывается ровно на двадцатом запросе. Репетиция стенда контента до предела не доходит: его поток по построению укладывается в предел, пока роль держит потолок ключа (1 + 1 + 3 · 8 + 1 = 27 из 30).

**Что стенд видит без сценария.** Между `sandbox-gw` и ролью `llm` стоит наблюдатель стенда (`startLlmObserver`): он пересылает байты как есть и хранит тело запроса CLI, ответ, статус и времена — без заголовков, то есть без ключа хода. По нему проверяются объявленные инструменты и формы потока. Формы — закрытый список из пяти (`STREAM_FORMS` в `live.mjs`): `tool_calls` без вызова, `stop` с пустым ответом, поток без причины завершения, поток без `[DONE]` — их не даёт ни один сценарий синтетического Z.ai — и текст рядом с вызовом инструмента в одном ответе: эту форму показала настоящая модель, и с G7 синтетический Z.ai отвечает ею, только когда сценарий просит (`beside` у сценария `tools`; ход с ней есть в группе Z.ai детерминированного прохода, в репетициях её нет). Формы вне списка строка отчёта не назовёт. Расход сверяется по двум независимым сторонам: строки `llm_calls` со `state = 'completed'` не оценочные и в сумме равны записям `step_finish`, которые напечатал CLI.

**Ответ вместо роли — только в репетиции.** Наблюдатель репетиции (`scripted: true`) умеет ещё одно: ответить на очередной запрос песочницы сам, не пересылая его роли (`answerNext`). Наблюдатель живого прогона такой ответ не принимает — `answerNext` у него бросает исключение. Этим репетиция замера (`--rehearsal --measure`) измеряет реакцию закреплённого OpenCode на HTTP 400 `raditi_body` — отказ слишком большому телу (вопросы П23 и П42; до G8 ответом был 413, который CLI читал как переполнение контекста). Настоящие байты отказа стенд берёт у самих сторон: у `sandbox-gw` — запросом из контейнера CLI с телом на байт больше предела, у роли `llm` — тем же запросом CLI, объявленным на байт длиннее; CLI получает их через `sandbox-gw` на месте ответа роли. Три таких хода: один отказ `sandbox-gw`, один отказ роли, отказ на каждый запрос. Четвёртый ход шлёт тело действительно больше 16 МиБ сам: синтетическая модель перед вызовом инструмента «думает» ровно столько байт, сколько шлюз принимает (параметр сценария `filler` в `fake-zai.mjs`), CLI возвращает это рассуждение со следующим запросом, и `sandbox-gw` отклоняет его сам. Измеренное 11.10.2026 закреплено в `BODY_REFUSAL_MEASURED` (`verify-llm-live.mjs`), и репетиция сверяет его точно: в каждом из четырёх ходов CLI печатает ошибку `APIError 400 raditi_body` и кончает ход тем же запросом — код 1, итога нет, запроса сжатия и повтора нет; в четвёртом до провайдера дошёл один запрос — шаг перед отклонённым. Числа и то, как `sandbox-gw` отвечает на загрузку сверх предела, — [отчёт 48](../../../docs/plan/48-removal.md); замер прежнего ответа — [отчёт 47](../../../docs/plan/47-common-scenarios-zai.md).

**Жёстко и долей.** Обязательства платформы проверяются в каждой попытке и проваливают прогон: расход, объявленные имена инструментов, MCP-запросы только с токеном хода; у контента — снимок раньше записи, ни одной записи на сайт без строки журнала, ни одного маркера `[[raditi:` на публичной странице после применённой записи, аренда, версия MCP `2025-11-25`, отсутствие ключа хода, токена MCP, пароля сайта и контакта в запросах и событиях. Исходы, зависящие от модели (итог валиден, файл записан, инструмент вызван, страница изменена), получают до трёх попыток и идут в отчёт долей: прогон они не решают: на прежнем тексте контракта настоящий GLM оформлял итог так, что драйвер принимал его в двух ходах из трёх (отчёт G6, вопрос П30), и прогон, зависящий от этого, был бы красным без единого нарушения на платформе. На новом тексте узкий замер из десяти ходов дважды дал 10 из 10 ([отчёт 46](../../../docs/plan/46-turn-result-glm.md)); это две короткие серии, и исход остаётся делом модели. «Итог валиден» во всех живых потоках с G7 — чтение продукта (`readTurnResult` супервизора, решение П38): объект, обёрнутый фразой, считается итогом, как его засчитал бы продукт; строгое чтение драйвера печатается рядом в строке каждого хода и отдельной долей (`resultReadings` и `readingShares` в `verify-llm-live-results.mjs` — одни и те же функции у приёмки шлюза, замера, узкого замера и приёмки контента). Читайте строки `REPORT`: `… the model's outcome reached in N of M attempt(s)` и `results of N turns: taken by the reading of the product … in X; valid by the strict reading of the driver in Y` у шлюза, `content edit: the page was changed in N of M attempt(s); the result was valid in … by the reading of the product …, in … by the strict reading of the driver` у контента. Код возврата 0 говорит об обязательствах платформы, а не о модели; последняя строка прогона это повторяет.

У стенда шлюза сначала идёт по одному ходу каждого вида — инструмент, MCP, текст, продолжение сессии; первая попытка каждого обязана поместиться в бюджет запросов. Повторы недостигнутых исходов берут то, что осталось, начиная с продолжения: оно возобновляет сессию, которую домашний каталог CLI хранит только до хода другого вида; повтор, на который бюджета не хватает, попытки заканчивает. Кончиться на счёте стенда без нарушения на платформе прогон шлюза теперь может, только если бюджет исчерпают сами первые попытки — три хода по пять вызовов до четвёртого; при измеренных одном–трёх запросах на ход до этого далеко. У стенда контента три попытки, каждая на своей странице; их число своё и от числа строк CLI детерминированного прохода не зависит. Репетиция оба правила исполняет и показывает оба чтения на сценарных промахах. Сценарная модель шлюза в ходе «текст» все три раза отвечает объектом без `files_changed` (его не принимает ни одно чтение), в продолжении — сначала им же, затем объектом после фразы (продукт принимает, строгое чтение нет): 3 итога из 7 по чтению продукта и 2 по строгому. Сценарная модель контента дважды пропускает ключ и в третьей попытке оборачивает объект фразой: 1 из 3 по чтению продукта, 0 по строгому. В репетиции замера второй и третий из десяти ходов с итогом отвечают теми же двумя формами: 9 из 10 и 8 из 10. С этими долями репетиции проходят. Повтор записи без двойной правки и отказ запрещённому маршруту вживую не проверяются: они детерминированы только на сценарной модели.

**Узкий замер итога хода** (`--results`, [отчёт](../../../docs/plan/46-turn-result-glm.md)). Десять ходов из `apps/orchestrator/scripts/verify-llm-live-results.mjs`, каждый на новой сессии: семь не меняют файлов (три из них кончаются вопросом клиенту, один перед ответом читает файл одной командой), три меняют файл. Половина промптов просит «the final result» словами, как все промпты первых живых прогонов; вторая половина оставляет итог контракту из инструкций: как в задании клиента, итога словами они не просят. Классы идут по кругу: `standard`, `light`, `heavy`.

- Предел в 20 запросов считается от потолков ключей: ходу без инструмента роль даёт один вызов, ходу с одним чтением — два, ходу с записью файла — три (`LLM_MAX_CALLS_PER_KEY`, роль перезапускается дважды, когда потолок растёт). Худший случай — импорт, проба, 6 · 1 + 2 + 3 · 3 и последнее чтение квоты — ровно 20; это закрепляет тест `verify-llm-live-results.test.mjs`. До первого хода поток сам сверяет, что прогон открыт под видом `results` и под его пределом: пределы берутся по виду прогона, и под видом замера те же ходы шли бы под пределом 40. Ход, который модель растянула дальше потолка, роль обрывает отказом `budget`, и он идёт в отчёт как «the turn failed».
- Каждый ответ оценивается дважды. Строгое чтение драйвера (`extractResult`: всё последнее сообщение — один объект JSON либо один блок кода с ним) — его считает приёмка П30, не меньше 9 из 10. Чтение продукта (`readTurnResult` супервизора: после отказа драйвера — ещё раз по одному кандидату, от первой `{` до последней `}` либо из единственного блока кода) — оно принимает объект, который модель обернула фразой. Блок кода рядом со скобками вне его и сообщение, которое драйвер обрезал по размеру, оно не принимает. Объект без обязательного поля не принимает ни одно.
- Строки `REPORT`: по каждому ходу — вердикт строгого чтения, принял ли ответ продукт и что в итоге не так, как просил ход (`files_changed` не пуст, вопроса нет, файл не записан); затем доли — всего, по промптам «с просьбой об итоге» и «без неё», по видам ходов — и строка `acceptance of П30 … reached / not reached`. Доли прогон не решают: код возврата 0 говорит об обязательствах платформы, которые проверяются в каждом ходе, как в приёмке.
- Репетиция (`--rehearsal --results`) на сценарной модели отвечает тремя формами настоящей — фраза перед объектом, фраза после него, объект без `files_changed` — и одним вызовом инструмента в ходе с потолком в один вызов; она сверяет вердикты и доли точно (6 из 10 строго, 8 из 10 для продукта), затем доходит до предела в 20 запросов и проверяет, что сторож его удержал и что это предел вида прогона. Отказы запуска и поиск ключа — те же, что у приёмки.

**В конце каждого прошедшего прогона** стенд ищет значение ключа в логах сервисов и ролей, аудите OpenBao, дампе PostgreSQL, объектах S3 и раскрытых снимках, событиях CLI, записанных обменах, состоянии управляющего порта, `docker inspect` своих контейнеров, файлах песочницы (после каждого хода, поток `tar` из контейнера) и во временных каталогах стенда. Поиск идёт в процессе стенда (`searchPlaces`, `createStreamSearch`): значение не передаётся ни одному процессу. Вывод каждого процесса ищется одним текстом на канал — чтение канала может кончиться посреди значения. Перед поиском стенд подкладывает случайную метку и требует её найти; репетиция подкладывает синтетический ключ в каждое место по очереди, в вывод процесса — разрезанным на два чтения.

**После неудачи или прерывания** полного поиска нет: контейнеров у такого прогона может уже не быть. Перед уборкой стенд ищет ключ в том, что ещё держит, — вывод ролей и команд оператора, события и вывод CLI, обмены наблюдателя, каталог прогона, каталог стенда — и печатает строку `REPORT after the failure the plan key was searched for …` (с `--api` — `the API key`) с именами мест; место, которое уже не читается, названо отдельно. Первая строка ошибки печатается, только если ключа нет во всём её тексте; вывод команды оператора в сообщение не цитируется.

**После SIGKILL.** Стенд убирает за собой после успеха, ошибки, SIGINT и SIGTERM. Убитый сигналом SIGKILL, он оставляет контейнер OpenBao с настоящим ключом плана в памяти — до удаления контейнера. Убрать остатки:

```sh
docker ps -a --filter name=raditi-p3verify- --format '{{.Names}}'            # проекты стенда
docker ps -aq --filter name=raditi-p3verify- | xargs docker rm -f -v          # вместе с OpenBao
docker network ls -q --filter name=raditi-p3verify- | xargs docker network rm
rm -rf "${TMPDIR:-/tmp}"/raditi-p3verify-* "${TMPDIR:-/tmp}"/raditi-live-*
```

OpenBao стенда хранит всё в памяти (`storage "inmem"`), тома у него нет: с контейнером ключ исчезает. Процессы ролей (`node …verify-llm-worker.mjs`) завершаются сами, когда теряют канал со стендом.
