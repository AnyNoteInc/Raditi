# Разведка P3.0: записывающий проход

Для синтетической проверки B13 с настоящими CLI, одноразовыми PostgreSQL/OpenBao и без подписки пользователя используйте `pnpm verify:llm-gateway`. Команда, состав стенда и ограничения описаны в [отчёте B13](../../../docs/plan/20-p3-synthetic-gateway.md). Ниже описаны отдельные инструменты разведки P3.0 на настоящем провайдере.

Как стенд запускает CLI:
- **Образ** — production-среда агента (`infra/sandbox/Dockerfile`, цель `runtime`, CLI из lock-файла); `cli.Dockerfile` только добавляет `cli.mjs` и проверяет версии `npm ls`.
- **Ходы как в продукте** (`apps/orchestrator/scripts/verify-llm-gateway-drivers.mjs`): конфигурация, `AGENTS.md`, схема итога, MCP-сервер, `--image` и resume берутся из `prepare` и `command` драйверов Codex и Kimi и проходят проверки исполнителя хода (`preparedFilesSchema`, отсутствие ключей в файлах, env и argv). Секреты ложатся в tmpfs `/run/raditi/secrets`, вложения — в `/workspace/inbox`. У каждого CLI — exec и resume через `sandbox-gw`, роль `llm` с политикой тела и маршрут `/mcp`.
- **MCP** — синтетический сервер в `fake-subscriptions` (порт 8788 только во внутренней сети стенда). Список инструментов — production-профиль роли `mcp` (`site_info` из собранного `McpToolsController`, схема — как у mcp-nest), токен — MCP-токен хода из `issue`.
- **Ошибки внутри потока** (`verify-llm-gateway-stream.mjs`, сценарий `stream_failed` фейка для Codex и Kimi) тоже идут ходами драйвера, то есть с настройками повторов production. Окончательный отказ должен завершить ход после одного запроса к провайдеру: Codex получает код, на котором закреплённый CLI не переподключается, Kimi — выбор, остановленный фильтром (`finish_reason: content_filter`), потому что любой объект ошибки в потоке Kimi CLI повторяет до 10 раз. Кратковременный сбой остаётся повторяемым, ход завершается со вторым запросом.
- **Настоящая роль `mcp` вместо синтетического сервера** — стенд `pnpm verify:agent-content` ([отчёт](../../../docs/plan/30-agent-content-stand.md)). `startVerificationStack({ content: true })` передаёт `sandbox-gw` адрес роли на хосте (`VERIFY_MCP_UPSTREAM`, по умолчанию прежний `http://fake-subscriptions:8788`) и добавляет S3 для снимков (профиль Compose `content`), AppRole `mcp` с политикой `mcp-content` и токены `sites-writer`, `workspace-provisioner` и `core-transit` (доступ сайта, ключ рабочего пространства и чтение снимка самим стендом — без root-токена). Роль запускается штатно, из сборки: `node dist/main.js` с окружением одной роли (`apps/orchestrator/scripts/verify-agent-content-role.mjs`), а не через `startWorker` ([отчёт](../../../docs/plan/33-mcp-role-content-resolver.md)). Модель ведут сценарии фейка `content_edit` (чтение страницы, запись с ключом идемпотентности, та же запись ещё раз, итог) и `content_forbidden` (один вызов `wp_rest`, который платформа должна отклонить: чтение чужого маршрута либо, при заданном `body`, запись без ключа). `{{contact}}` в тексте правки заменяется первым маркером контакта из разговора: фейк, как модель, переносит маркер и ничего не придумывает. `verify:llm-gateway` профиль и параметр не включает и остаётся прежним.
- **Рукописная конфигурация** (`compileCodexConfig`, `cliInvocation`, каталог `/agent-home/b13`) осталась только в сценариях протокола и жизненного цикла (`verify-llm-protocol.mjs`, `verify-llm-lifecycle.mjs`), которым нужны фиксированные повторы, ответ простым текстом или `--output-last-message`.
- **Синтетический Z.ai** (`fake-zai.mjs`, переход на OpenCode и GLM, [отчёт G2](../../../docs/plan/41-zai-backend.md)) — два адреса плана GLM Coding Plan: чат `POST /api/coding/paas/v4/chat/completions` и квота `GET /api/monitor/usage/quota/limit`. Кадры и ответы повторяют записи `docs/research/2026-10-opencode-glm/samples`, коды ошибок — таблицу решения 9 плана перехода (статусы у неизмеренных кодов — допущение, константа `ZAI_ERROR_STATUS`). Фейк встроен в `fake-subscriptions.mjs`: запросы на эти два пути обслуживает он; имя `api.z.ai` есть в сертификате, в псевдонимах сети `providers` и в списке прокси стенда.
  - Управление — `POST /zai` управляющего порта с телом `{reset?, scenario?, quota?, key?}`; чтение — `GET /zai` или ключ `zai` в `GET /state`; общий `POST /reset` сбрасывает и его.
  - Сценарии чата: `text`, `tools` (вызовы инструментов: `calls` — один раунд, `rounds` — список раундов; номер раунда — число шагов с инструментами после последнего сообщения пользователя; после последнего раунда и на запрос без `tools`, каким CLI просит сжать контекст, — текст), `finish` (любой `finish_reason`), `error` (код и статус, `retryAfter`, `failures` — только первые N запросов; дальше обычные ответы с текстом сценария и обычным расходом), `stream_error` и «враждебные» ответы для проверок шлюза: `envelope200`, `plain200`, `no_usage`, `no_done`, `done_only`, `no_finish`, `no_finish_no_done`, `empty`, `cut`.
  - Сценарии стенда `verify:agent-content` (G5, [отчёт](../../../docs/plan/44-agent-content-opencode.md)): `content_edit` — чтение страницы, запись с ключом идемпотентности, та же запись ещё раз, текст; `content_forbidden` — один вызов, который платформа должна отклонить (чтение заданного маршрута, а с `body` — запись без ключа), затем текст. Параметры — `route`, `idempotencyKey`, `body`. Что именно просит модель, описывает `content-scenario.mjs`, общий с `fake-subscriptions.mjs`; раунд выбирается тем же правилом, что у `tools`. Вызывается функция, которую CLI объявил для инструмента MCP `wp_rest`: закреплённый OpenCode называет её `<сервер>_<инструмент>`, в записи `34-run-c-mcp` это `raditi_wp_rest`. Если такой функции в запросе нет или их две, либо правке нужен маркер контакта, а в разговоре его нет, фейк отвечает 400 и ничего не выдумывает.
  - Квота живая: окно пяти часов не начато, первый запрос его начинает (`remaining` на единицу меньше, `currentValue` ещё 0 — как в записях 60 и 62), каждый следующий — один кредит. `quota.fiveHour.exhausted` исчерпывает окно (чат отвечает 429 с кодом 1308), `idle` возвращает в «не начато», `resetInMs` задаёт сброс, `mode: 'broken'` и `mode: 'envelope'` отдают нечитаемый ответ и конверт HTTP 200.
  - В записях запросов нет значений заголовков с учётными данными: только признак `credential` (`plan-key`, `other`, `none`) и имена заголовков.
  - Ключей плана два, принимается один: `key: 'rotated'` заставляет фейк отказывать первому ключу (401 на пути чата, конверт с кодом 401 на пути квоты) и принимать второй, `SYNTHETIC_ZAI_ROTATED_KEY`; сброс возвращает первый.
  - Отдельным процессом: `node infra/dev/llm-verify/fake-zai.mjs --tls-key <файл> --tls-cert <файл>` печатает `{ready, port, controlPort}`. Так его запускает интеграционный тест роли `llm` (`apps/orchestrator/src/llm-gateway/gateway.integration.test.ts`, `pnpm verify:db`).
- **Группа Z.ai стенда** (`apps/orchestrator/scripts/verify-llm-zai.mjs`, [отчёт G4](../../../docs/plan/43-zai-gateway-stand.md)) идёт третьей, после Codex и Kimi. Настоящий OpenCode 1.18.34 запускается только через `prepare` и `command` драйвера; рукописной конфигурации OpenCode в стенде нет.
  - Путь: песочница → `sandbox-gw` → роль `llm` → фейк Z.ai **напрямую**. Роль перезапускается без четырёх переменных `LLM_EGRESS_*` и с `LLM_BACKEND_URL_ZAI_CODING=https://localhost:<порт>`: порт TLS фейка опубликован на loopback, в сертификате фейка есть имя `localhost`. Один ход до этого идёт через прокси стенда: заданный прокси остаётся путём ко всем провайдерам.
  - Аккаунт создаёт команда оператора `subscription-login.mjs --backend zai-coding --plan lite` с синтетическим ключом на stdin, тоже без прокси. Строки провайдера, профиля `glm-5.3-standard`, стендовой ставки и драйвера включает скрипт; окна пишет только проба.
  - Домашний каталог драйвера OpenCode в контейнере CLI — tmpfs (`/agent-home/opencode`), как весь `/agent-home` в песочнице: обёртка драйвера закрывает каталоги конфигурации правами 0555, а смонтированный с рабочей машины каталог Docker Desktop этих прав не соблюдает. Родитель рабочей копии `/workspace` — тоже tmpfs: обёртка держит там файлы OpenCode сайта, пока идёт CLI. Перед каждым ходом в домашнем каталоге остаются только два файла базы сессии — как после восстановления снимка.
  - Роль `llm` перезапускается между сценариями, которым нужна её чистая память: паузы аккаунта и правило «одна проба на аккаунт в пять минут» живут в процессе.
  - Общее со стендом `verify:agent-content` вынесено в `apps/orchestrator/scripts/verify-llm-zai-setup.mjs`: окружение роли без прокси, команда оператора и импорт ключа плана, включение строк провайдера, профиля, ставки и драйвера, очистка домашнего каталога OpenCode между ходами.

`record-proxy.mjs` — инструмент разведки P3.0 ([p3-design.md](../../../docs/research/2026-09-subscriptions/p3-design.md) §0.1, шаг 4; roadmap, P3). Разведка отвечает до кода шлюза на вопрос, принимает ли бэкенд ChatGPT схему A. Схема A — свой провайдер `raditi` в Codex CLI, `requires_openai_auth=false`, наш `Authorization` и `ChatGPT-Account-ID`.

Штатный проход с отдельным аккаунтом — где и на чём:
- только на одноразовой ВМ `spike-1` у того же провайдера и в той же стране, что `egress-1`;
- только синтетические промпты и репозиторий;
- не на `egress-1` и не на ВМ платформы.

После разведки ВМ удаляется.

Штатный проход на ВМ: временный файл входа и очищенный журнал живут только на `spike-1` до уборки. Они не являются хранилищами платформы. Данные клиентов и рабочие токены платформы здесь не используются. Гейт P3.0 проверяется через `egress-1`; прямой запрос допустим только для сравнения при диагностике и не закрывает гейт.

## Локальная проверка, разрешённая 29.09.2026

Владелец явно разрешил использовать текущую локальную подписку Codex без покупки отдельного аккаунта и подготовки ВМ. Аккаунта Kimi нет: настоящий Kimi в этом проходе не проверяется. Это узкое исключение из штатного порядка ниже; оно не меняет production-правила и не закрывает P3.0 или P3. Прямой локальный выход не подтверждает работу удалённого `egress-1`, mTLS до него, канал из России или изоляцию полного стенда.

1. Создать временные каталоги для синтетического репозитория, журнала и отдельного `CODEX_HOME` с правами 0700. Использовать только синтетический промпт и минимальный тестовый файл. Личные конфиг, сессии и `auth.json` в этот `CODEX_HOME` не копировать и не подключать ссылками.
2. `RECORD_CODEX_AUTH` у `record-proxy` направить на существующий файл входа текущей подписки. Файл читается только прокси; токены и id не выводятся. Вход, обновление и отзыв токенов, `codex logout` и изменения файла запрещены. При истёкшем токене либо 401 на подписочном маршруте остановить проход, без автоматического повторного входа или обновления.
3. Запустить прокси на loopback и CLI с провайдером `raditi`, `requires_openai_auth=false` и временным `CODEX_HOME`, как в шаге 4 штатного порядка. CLI получает только локальный ключ прокси. Переменные временного окружения задавать только дочерним процессам проверки.
4. Провести короткие `exec` и `resume`, прочитать `/wham/usage`; сохранить очищенные формы ответов, usage, заголовки и фактическую версию локального CLI. Не исчерпывать лимиты искусственно. Отсутствие Kimi не подменять заявлением о его успешной проверке.
5. Остановить только процессы этого прохода, удалить его временные каталоги после проверки очищенного отчёта. **Шаг 6 штатного порядка с `codex logout` здесь не выполнять.** Существующий файл входа владельца и его основной `CODEX_HOME` остаются без изменений со стороны проверки.

Измеренный результат и оставшиеся гейты фиксируются в `docs/research/2026-09-subscriptions/spike.md`; в репозиторий не попадают токены, id, локальные журналы и личные данные.

Готовый локальный запуск из корня репозитория (потребляет текущую подписку). Файл входа задаётся только явно через `RECORD_CODEX_AUTH` (абсолютный путь), а живой проход — только с флагом `--confirm-live-subscription`. Без переменной или без флага скрипт завершается с ошибкой до чтения файла; пути по умолчанию нет:

```sh
RECORD_CODEX_AUTH=/абсолютный/путь/к/auth.json \
  node infra/dev/llm-verify/local-spike.mjs --model gpt-6.1-sol --local-egress --confirm-live-subscription
```

Проверка реализованного адаптера B7 на той же подписке:

```sh
RECORD_CODEX_AUTH=/абсолютный/путь/к/auth.json \
  node infra/dev/llm-verify/local-spike.mjs --model gpt-6.1-sol --local-egress --backend-adapter --confirm-live-subscription
```

`--backend-adapter` подключает настоящий `codexBackend`: каждый запрос CLI проходит `normalizeBody` и `upstream`, каждый чанк ответа — `usageMeter`. Весь проход использует один временный installation id и ключ кэша. Два вызова `probe` идут через тот же mTLS-транспорт к точному GET `/backend-api/wham/usage`; редиректы запрещены, ответ ограничен 64 КиБ. У CLI доступен только POST `/codex/responses`; дополнительные маршруты записи и `RECORD_KEEP` в этом режиме запрещены. Нормализованные счётчики токенов должны совпасть с usage провайдера во всех модельных ответах, оба ответа `probe` должны содержать окна лимитов. Отдельный флаг `backend_adapter_passed` подтверждает эти условия вместе с обычными проверками сценария и уборки. Refresh, login и revoke этот транспорт вызвать не может.

Модель задаётся явно: это модель фактической проверки 29.09.2026, её доступность у других аккаунтов не предполагается. `--codex /путь/к/codex` выбирает существующий CLI без установки или обновления. Файл входа читает только прокси в процессе скрипта и только по `RECORD_CODEX_AUTH`; флага `--auth-file` и пути по умолчанию нет. `--local-egress` поднимает локальный mTLS-прокси с временным CA и пробой 1 МиБ (нужен `openssl`); без флага проверка идёт напрямую через записывающий прокси. Ни один вариант не проверяет зарубежную ВМ.

`local-spike.mjs` создаёт временное окружение, дважды читает `/wham/usage`, выполняет синтетические `exec` и `resume`, проверяет файл и JSON Schema, сверяет неизменность файла входа и удаляет свои каталоги. Токен подписки остаётся у host-прокси; CLI получает случайный локальный ключ. Личный `HOME` не меняется: у дочернего CLI и запущенных им команд `HOME` и `CODEX_HOME` временные, поэтому `~/.codex` владельца им не виден. В stdout выводится только отчёт о форме протокола: статусы, имена полей, числовой usage, без идентификаторов и содержимого; из заголовков квот сохраняются только разрешённые числовые поля. Ошибка проверки даёт ненулевой код выхода. Отсутствующие проценты квот не считаются подтверждением отсутствия расхода. При ошибке подписки нет автоматического refresh или повторного входа.

Результат 29.09.2026: оба сценария прошли на CLI 0.154.0, через локальный mTLS получены пять `response.completed` с usage. Подробности и ограничения — [spike.md](../../../docs/research/2026-09-subscriptions/spike.md).

Результат 30.09.2026 с `--backend-adapter`: CLI 0.159.1, оба сценария прошли, пять завершённых ответов, точное совпадение usage и успешный разбор лимитов. Исправлены Responses Lite и недельные планы. [Отчёт B7](../../../docs/plan/14-p3-codex-live.md).

## Что делает

CLI обращается к прокси с локальным ключом, как песочница — с ключом хода. Прокси подставляет токен подписки и отправляет запрос провайдеру. Заголовки и поля он обрабатывает так же, как шлюз (p3-design.md §3.4). Каждый обмен, в том числе отказанный, записывается в журнал.

| Путь на прокси | Куда | Кто вызывает |
| --- | --- | --- |
| `POST /codex/responses` | `https://chatgpt.com/backend-api/codex/responses` | Codex CLI |
| `GET /codex/models` | `https://chatgpt.com/backend-api/codex/models` | Codex CLI, если спросит |
| `GET /wham/usage` | `https://chatgpt.com/backend-api/wham/usage` | `curl`: лимиты без расхода токенов |
| `POST /kimi/v1/chat/completions` | `https://api.kimi.ai/coding/v1/chat/completions` | Kimi Code CLI |
| `GET /kimi/v1/usages`, `GET /kimi/v1/models` | `https://api.kimi.ai/coding/v1/…` | `curl` |

- **Остальное** — 403 и запись в журнал. Так видно, куда ещё ходит CLI. Например, `/disabled/…` — побочные вызовы ChatGPT через `chatgpt_base_url`.
- **Как шлюз:**
  - к провайдеру уходят только разрешённые заголовки клиента;
  - вырезаются `x-codex-turn-metadata`, `x-codex-window-id`, `x-codex-routing-hint`, а в теле — `client_metadata` и `service_tier`;
  - сжатое тело (gzip, br, deflate, zstd) распаковывается до удаления полей; размер после распаковки — не больше 16 МиБ, неизвестное или повреждённое сжатие отклоняется;
  - ставятся `Authorization`, `ChatGPT-Account-ID`, `accept: text/event-stream` и `accept-encoding: identity`;
  - назад уходят только `content-type`, `content-encoding`, `x-codex-turn-state` и `retry-after`.
- **Не как шлюз:**
  - `x-codex-installation-id` приходит от CLI, а шлюз поставит свой для аккаунта;
  - тело не проверяется;
  - бюджета и учёта нет;
  - `x-msh-*` от Kimi CLI проходят как есть: не больше 8, до 256 символов.
- **`RECORD_KEEP`** пропускает вырезанное по одному, например `RECORD_KEEP=client_metadata`. Так видно, без чего бэкенд не работает.
- **Журнал** — `RECORD_DIR/exchanges.jsonl` с правами 0600. Без `RECORD_DIR` прокси создаёт новый закрытый каталог `raditi-spike-records-…` во временном каталоге системы и печатает его путь при запуске: в рабочую копию репозитория журнал по умолчанию не попадает. Каталог `spike-records/` (прежнее место по умолчанию) внесён в `.gitignore`. Каталог журнала внутри рабочей копии git (каталог с `.git` у него или у любого родителя, в том числе по символьной ссылке) прокси отклоняет до создания и не запускается — и явно заданный `RECORD_DIR`, и временный каталог системы, если он сам лежит в рабочей копии. Указывайте каталог вне рабочей копии, как `$HOME/spike` в примерах ниже, или не задавайте переменную. В журнале:
  - заголовки запроса и тело; значения `authorization`, `proxy-authorization`, `cookie`, `x-api-key` и `chatgpt-account-id` скрыты, значения заголовков установки, устройства, сессии, состояния, аккаунта и пользователя (`x-codex-installation-id`, `x-msh-device-id`, `session-id` и т. п.) заменены на `[id]`. Как есть сохраняются только значения протокольных заголовков и названия клиента (`content-type`, `content-encoding`, `accept`, `user-agent`, `originator`, `x-openai-subagent`, `x-msh-platform`, `x-msh-version` и т. п.) и числовые или логические значения `x-*`; у остальных, в том числе у `x-codex-turn-metadata` (id хода, пути рабочих каталогов, адреса git), остаётся только имя со значением `[value]`;
  - что ушло к провайдеру — с той же заменой;
  - статус, заголовки ответа без `set-cookie`, события SSE. Значения заголовков ответа сохраняются только у протокольных (`content-type`, `retry-after` и т. п.) и у числовых или логических `x-codex-*`/`x-ratelimit-*`; у остальных остаётся только имя со значением `[value]`.

  `encrypted_content` и data URL заменены длиной. Токены, JWT и адреса почты заменены метками. Поля, называющие объект, аккаунт, пользователя, организацию или рабочее пространство (`id`, `*_id`, `*-id`, `*Id` и `*ID` в записи camelCase, `*identifier`, `user`, `email`, `account`, `org*`, `organization*`, `workspace*`), ключ кэша `prompt_cache_key` (id ветки) и метаданные клиента (`client_metadata`, `metadata`) заменены на `[id]` вместе с вложенными значениями: форма ответа остаётся, чей он — нет. Независимо от имени поля значение-строка вида `user-…`, `org-…`, `acct_…`, `resp_…`, `req_…` заменяется на `[id]` целиком. Любой UUID и такой же id провайдера внутри более длинного текста — в сообщении об ошибке с id организации, в пути запроса, в строке потока или теле не в формате JSON — заменяются во всей строке журнала и в stdout. Внутри текста id распознаётся по сгенерированному виду: после префикса не меньше восьми букв и цифр, среди них цифра или заглавная буква; слова вроде `user_instructions` остаются. В stdout — строка на обмен с usage, если он пришёл.
  Очистка известных токенов обоих настроенных аккаунтов работает и при отказе до маршрутизации (401/403); структурные поля токенов и аккаунтов заменяются метками независимо от их значения.
  Ответ записывается целиком только до 32 МиБ, в том числе после распаковки. Для большего или повреждённого ответа сохраняются статус, заголовки и отметка об ограничении или ошибке разбора; передача ответа CLI продолжается. Обрыв читателя прерывает запрос к провайдеру.
  Потоковые ответы распознаются и без `Content-Type`, если запрос ожидает SSE; явный JSON остаётся JSON. Полные кадры сохраняются также при обрыве и таймауте. `response.transport_end` описывает завершение транспорта, `response.terminal_event` и `response.outcome` — результат потока. У Codex `response.usage` берётся из полного terminal; у Kimi — из последнего полученного usage-чанка, в том числе до `[DONE]`, поэтому наличие usage само по себе не доказывает успешное завершение. Закрытие клиента после `response.completed` не превращает успех в `ABORT_ERR`; неполный кадр и усечение записи не считаются успешным terminal.
- **Выход** — прямо с `spike-1`. С `RECORD_EGRESS` — через `egress-1`, как у шлюза:
  - внутри mTLS идёт `CONNECT`, внутри туннеля — TLS до провайдера;
  - провайдер видит адрес узла, узел не видит токенов;
  - нужен каталог `RECORD_EGRESS_TLS_DIR` с `root.pem`, `client.pem` и `client-key.pem` — например, копии `op-1`;
  - адрес `spike-1` добавляется в `PROXY_CLIENTS` на `egress-1` на время разведки ([infra/egress/README.md](../../egress/README.md)).
  Установка соединения (TLS к узлу, CONNECT, TLS к провайдеру) ограничена 10 секундами.
- **Слушает** только `127.0.0.1` (`RECORD_PORT`, по умолчанию 8090). Без локального ключа — 401.

`pnpm test:infra` запускает синтетические тесты, без текущей подписки. `record-proxy.test.mjs` проверяет:

- отказы без ключа, вне таблицы путей и с чужим `Host`;
- что в журнале нет секретов и идентификаторов провайдера и клиента (поля `*_id`, `user`, организация, заголовки ответа и устройства), в том числе id установки, ветки и хода из `client_metadata`, `x-codex-turn-metadata`, `prompt_cache_key` и `safety_identifier`, полей в записи camelCase (`userId`, `accountID`) и id организации, пользователя и запроса внутри сообщения об ошибке, пути и строки потока не в формате JSON;
- что без `RECORD_DIR` журнал создаётся в новом закрытом каталоге вне рабочей копии, `spike-records/` есть в `.gitignore`, а каталог журнала внутри рабочей копии git (явный `RECORD_DIR` или временный каталог системы) отклоняется;
- SSE без `Content-Type`, сохранение terminal и usage после закрытия клиента, обрыв до terminal, неполный кадр и ограничение размера;
- Kimi, редирект и `inspect`;
- путь через настоящий `llm-egress.mjs` с синтетическим CA.

`local-spike.test.mjs` проверяет очистку итогового отчёта, ошибки launcher, отказ без `RECORD_CODEX_AUTH` или `--confirm-live-subscription` до чтения файла и временный `HOME` у CLI — без обращения к настоящему аккаунту. Live-проход не включён в `pnpm test:infra` или `pnpm gates`.

`sanitize-samples.mjs` к разведке P3.0 не относится. Это единственный путь, которым записи пробы перехода на OpenCode и GLM попадают в `docs/research/2026-10-opencode-glm`: команды `scan`, `copy` и `check`, правила и пределы — в шапке скрипта и в [README каталога исследований](../../../docs/research/2026-10-opencode-glm/README.md), «Как записи очищены». Скрипт работает по форме и ключа не требует. `sanitize-samples.test.mjs` проверяет правила на синтетических значениях и при каждом прогоне — весь каталог исследований: в записях нет заголовка вне разрешающего списка, нигде нет строки вида ключа, bearer-значения, токена MCP платформы и неочищенного идентификатора. Находка секрета выводится правилом, строкой и длиной, без единого знака значения.

Для стенда B13: `fake-subscriptions.test.mjs` проверяет синтетический MCP (только зарегистрированный токен хода, токен не попадает в состояние) и сценарий `mcp` (вызов `site_info` объявленной функцией у Kimi и ячейкой `exec` в code mode Codex); `cli.test.mjs` — что подготовленный драйвером ход попадает в контейнер только через stdin `docker exec`, пути файлов и секретов ограничены `/agent-home` и `/run/raditi/secrets`, а образ CLI собирается из production-среды агента; `stack.test.mjs` — что прокси выхода стенда пускает роль `llm` по отпечатку сертификата.

Уборка стенда B13 не полагается на права хоста. На обычном Linux файлы, которые CLI записал в смонтированные каталоги, принадлежат uid 10001 контейнера, и пользователь хоста не может их ни перечислить, ни удалить. Поэтому `close()` сессии сначала очищает `/agent-home` и `/workspace/repo` изнутри контейнера (`docker exec … find … -delete`), затем удаляет контейнер и каталог. Если контейнера уже нет или хост всё же получил отказ, каталог очищает одноразовый контейнер того же образа от root без сети, после чего хост удаляет его; так же удаляется каталог всего стенда. Сбой такого контейнера — ошибка уборки, а не молчаливый пропуск. Это проверяют `cli.test.mjs` (порядок вызовов Docker, недоступный хосту подкаталог) и `stack.test.mjs`. На Docker Desktop запасной путь не срабатывает; на обычном Linux порядок подтверждён отдельной проверкой с настоящими uid 1001 и 10001, а полный проход стенда на раннере GitHub остаётся после отправки ветки.

По той же причине стенд драйверов (`verify-llm-gateway-drivers.mjs`) читает файлы, которые CLI записал в рабочий каталог, сначала с хоста, а при отказе в доступе — через `docker exec … cat` в том же контейнере. На macOS эта ветка не срабатывает и не проверена.
