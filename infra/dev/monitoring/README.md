# Локальный мониторинг

Из корня репозитория запустите инфраструктуру с профилем мониторинга:

```sh
docker compose --env-file .env -f infra/dev/docker-compose.yml --profile monitoring up -d
pnpm dev
```

Prometheus: http://localhost:9090, Grafana: http://localhost:3030. В Grafana используется
пользователь `admin`, пароль — `GRAFANA_ADMIN_PASSWORD`. Источник Prometheus и дашборд
«Радити — обзор» загружаются из файлов. Приложения опрашиваются на стандартных портах:
web — 3000, core — 8081, MCP — 8082, шлюз подписок (роль `llm`) — 8084. При смене портов
обновите `prometheus.yml`.
Токен в нём должен совпадать с `METRICS_TOKEN` приложений; исходное значение подходит
для локальной `.env.example`. Prometheus не подставляет переменные окружения в этот файл.

На macOS нужен Docker Desktop, передающий `host.docker.internal` в loopback хоста.
На Linux `host-gateway` указывает на адрес Docker bridge: для приложений, слушающих
только `127.0.0.1`, понадобится отдельная настройка доступа контейнеров к хосту.

## Обязательные и дополнительные цели

Для базовой проверки B5 нужны инфраструктура, профиль `monitoring` и `pnpm dev`.
Обязательные цели не имеют метки `compose_profile`: Prometheus, web, core, шлюз подписок
(`llm`), PostgreSQL, Redis, SeaweedFS, OpenBao, Gitea и blackbox-exporter. Blackbox проверяет
health web, core, MCP, Gitea, OpenBao и SeaweedFS. У MCP нет `/metrics`: порт доступен
песочницам, поэтому проверяется только его `/health`.

Роль `llm` отдаёт метрики `raditi_llm_*` из собственного реестра только на своём порту
`:8084/metrics`, на 8081 их нет. Prometheus обращается к ней как `host.docker.internal:8084`:
это имя должно быть в `LLM_GATEWAY_HOSTS`, а адрес контейнера — в `LLM_GATEWAY_CLIENTS`
(значения `.env.example` подходят). Docker Desktop доставляет такие запросы на loopback хоста с
адресом 127.0.0.1; на Linux `host.docker.internal` — адрес моста Docker, и роль, которая по
умолчанию слушает 127.0.0.1 (`LLM_GATEWAY_LISTEN_HOST`), для Prometheus недоступна. Если роль
убрана из `ORCHESTRATOR_ROLES`, цель `llm` остаётся down. Health шлюза в dev без прокси выхода
с G4 отвечает 200; degraded (HTTP 503) он бывает, когда задан прокси выхода без рабочего канала,
когда провайдер недостижим на прямом пути (три соединения роли подряд не открылись) или
недоступны база и Vault. Роль в dev необязательна, поэтому проба её health помечена профилем
`llm` и в обязательные не входит.

Дополнительные цели всегда присутствуют в статическом конфиге и помечены профилем:

| Профиль | Цель | Условия проверки |
| --- | --- | --- |
| `site` | WordPress через blackbox | WordPress доступен, MariaDB запущена |
| `llm` | Health шлюза подписок через blackbox | Заданы четыре `LLM_EGRESS_*`, проба канала прошла |
| `ci` | Метрики Gitea runner | Раннер зарегистрирован с `GITEA_RUNNER_TOKEN` |
| `monitoring-host` | cAdvisor | Только Linux; также включён `monitoring` |

Чтобы включить профиль, добавьте `--profile site`, `--profile ci` или другое имя
в команду запуска. Профиль `monitoring` сам их не включает. Пока профиль выключен,
его `up` или `probe_success` равен `0`; это ожидаемо. Такие цели находятся в отдельных
панелях Grafana и не вызывают алерты доступности. После включения профиля проверяйте
его панель отдельно: алерты доступности для дополнительных профилей по-прежнему
выключены. Метка `llm` — не профиль compose: она появится у него вместе с фейками подписок
и локальным прокси выхода, а до тех пор отмечает пробу, зависящую от прокси.

Для шлюза подписок на дашборде есть две панели (запросы, отказы и завершённые вызовы;
активные запросы и учёт расхода) и алерт `LlmUsageNotPersisted` — шлюз не смог записать
расход. Алерты здоровья пула (аккаунты по состояниям, запас окон, ошибки выхода) — M9.

## Критерий готовности B5

1. В Grafana открывается «Радити — обзор» и доступен источник Prometheus.
2. В Prometheus запрос `up{compose_profile=""} == 0` не возвращает рядов, а запрос
   `up{compose_profile=""}` показывает все обязательные цели из списка выше, в том числе
   `llm`; запрос `raditi_llm_requests_total` возвращает ряд.
3. Запрос `probe_success{compose_profile=""} == 0` не возвращает рядов; все шесть
   обязательных health-проверок имеют `probe_success = 1`. Сам `up` для blackbox
   показывает доступность экспортёра, а результат проверки сайта — `probe_success`.
4. Для каждого включённого дополнительного профиля его `up` и, где есть, `probe_success`
   равны `1`. Выключенные профили не входят в критерий. Для `site` нужен именно
   `probe_success{compose_profile="site"} = 1`.

В отчёте проверки указывайте включённые профили. Успешный запуск контейнеров или
`up = 1` экспортёра не доказывает здоровье зависимостей: проверяйте также
`pg_up = 1`, `redis_up = 1` и health приложений. Проверка WordPress из B5 требует
отдельного запуска профиля `site`; выключенный профиль не считается проверенным.

PostgreSQL-exporter использует ту же учётную запись `raditi` и тот же пароль, что
локальные приложения. На старом томе выполните команду из комментария в
`infra/dev/postgres-init.sql`: она удаляет прежние роли и их права в транзакции,
сохраняя данные. Если прежняя роль владеет объектом данных или имеет зависимости
в другой базе, скрипт остановится без изменений — сначала нужно разобрать эти
зависимости вручную. Init-скрипт образа автоматически работает только на пустом
томе. Для S3 подтвердите успешное завершение `s3-init`: он проверяет все шесть
бакетов `raditi-*` через `head-bucket` и после повторных ошибок завершается с ненулевым
кодом. Повторный запуск безопасен: существующие бакеты повторно не создаются.

После изменения `prometheus.yml` или правил перечитайте конфигурацию:

```sh
curl -X POST http://localhost:9090/-/reload
```

Алерты видны в Prometheus. Доставка уведомлений через Alertmanager относится к M9.
