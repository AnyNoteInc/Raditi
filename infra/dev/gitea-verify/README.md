# Локальная проверка git хода на настоящей Gitea

```sh
P2_GITLEAKS_BINARY=/абсолютный/путь/gitleaks pnpm verify:gitea
```

Проход поднимает одноразовую Gitea 1.27.3 (свой контейнер `raditi-gitea-verify-<id>`, встроенный HTTPS с сертификатом собственного CA стенда, порт только на `127.0.0.1`), создаёт организацию `sites`, бота `raditi-bot` и второго участника `stand-writer` с правом записи, владельца организации `stand-owner` (команда Owners, токен только с `write:repository`) и приватные репозитории `sites/demo` и `sites/other`, затем проверяет собранный `apps/orchestrator` так, как его собирает `GitWorkspaceModule`: `CoreConfig.git` из `GITEA_URL`, `GITEA_TOKEN` и `GIT_CA_FILE`, провайдер Gitea из `packages/git-providers`, `GitWorkspaceService` с транспортом HTTPS.

Что проверяется:

- `getRepository`: приватный репозиторий найден, отсутствующий — `null`;
- голова ветки (`readBranchHead`): `main` совпадает с сервером, несуществующая ветка задачи — `null`;
- клон по доступу на чтение на 120 секунд; тем же доступом push невозможен — отказывает сама Gitea;
- push в `agent/<taskId>` по доступу на запись на 120 секунд; на сервере — коммит бота поверх базы;
- доступом на запись нельзя ни создать, ни перечислить токены (Gitea отвечает 403): выданный доступ не может продлить себя другим токеном;
- повторная публикация того же хода ветку не двигает; следующий ход двигает её от прежней головы;
- ход без изменений файлов публикует один пустой коммит бота в `agent/<taskId>`;
- дифф с `.gitea/` или защищённым путём сайта отклонён до выдачи доступа на запись;
- доступ на 5 секунд работает сразу, а после срока его не принимают ни git, ни API;
- новый экземпляр провайдера («перезапуск core») удаляет 55 просроченных доступов по имени — список токенов при этом длиннее одной страницы — и не трогает живой;
- подметание при старте (`sweepCredentials`) удаляет просроченный доступ без единой выдачи; остановка (`revokeCredentials`) сразу удаляет доступ на 120 секунд, выданный этим экземпляром, и не трогает чужой живой;
- без `GIT_CA_FILE` git отказывается от сертификата стенда: проверка TLS не выключается. Обратное стенд не проверяет: `GIT_CA_FILE` добавляет CA и системный набор не отключает.

Методы выпуска (`release-scenario.mjs`, [план 53](../../../docs/plan/53-chat-preview-release.md), Р26–Р29, Р35) — адаптер из исходников `packages/git-providers`: в orchestrator их ещё не подключили (R8b):

- секрет Actions репозитория (`setActionsSecret`, `deleteActionsSecret`) пишется, заменяется и удаляется токеном владельца организации; бот получает от Gitea 403 и на запись, и на список; у второго репозитория организации секрета нет — это секрет репозитория, а не организации; повторное удаление проходит; без токена владельца провайдер отказывает до запроса (`GIT_PROVIDER_NOT_CONFIGURED`);
- защита тегов `v*` (`protectTags`): прежнее правило, называющее бота, сужается до учётной записи токена владельца организации (её имя адаптер берёт из `GET /token`), повтор ничего не меняет; без токена владельца — `GIT_PROVIDER_NOT_CONFIGURED`; бот сам защитить теги не может (403);
- под защитой тег `v*` не могут ни создать, ни сдвинуть с `--force`, ни удалить второй участник и доступ бота на запись — ни git, ни API (422); `createTag` создаёт лёгкий тег через API учётной записью владельца, а на занятое имя — даже с другим коммитом — отвечает тегом как есть, не сдвигая его; сама эта учётная запись через git с `--force` тег двигает: Gitea 1.27.3 защищает тег от других, неизменность — дело кода (Р26), у `createTag` силы нет;
- `getTag`: у лёгкого тега объект — сам коммит, у аннотированного — объект тега; отсутствующий — `null`;
- вебхук репозитория на процесс сценария: тег, созданный `createTag`, Gitea объявляет так же, как push тега, — событие `tag` с коммитом (у аннотированного, отправленного git, — с объектом тега); запуск, созданный тегом, — `workflow_run` с `ref` `refs/tags/v1.0.0`, файлом и путём workflow, событием `push`, без ветки и с попыткой 1; задача запуска — `workflow_job`;
- `listWorkflowRuns` по коммиту и событию и `getWorkflowRun` показывают тот же запуск — без пути файла, его знает только вебхук; несуществующий запуск — `null`;
- `dispatchWorkflow` ботом: файл workflow репозитория на теге запускается, у запуска событие `workflow_dispatch` и `ref` тега, приходит его вебхук; файл без триггера `workflow_dispatch`, отсутствующий файл или ref и репозиторий, который не источник scoped workflows этого, — `NOT_SUPPORTED`.

Рабочий набор, зеркало и «Обновить» (`working-set-scenario.mjs`, план 53, Р10–Р12, Р27) — последними, потому что двигают `main` у `sites/demo`:

- в `main` ложатся ядро и медиатека, как их импортирует мастер подключения (план 39);
- первый бандл с `workingSet` заполняет пустое зеркало одним `fetch` с доступом на чтение, повтор и публикация сеть не трогают; бандл — один корневой коммит рабочего набора, тот же при повторе; в песочнице нет ядра, `wp-config.php` и медиатеки, кроме папки `uploads/raditi/`;
- патч, снятый против рабочего набора, ложится на полное дерево (ядро и медиатека на месте, новая картинка добавлена), push — один доступ на запись; то же изменение полного дерева вне набора отклонено до доступа на запись;
- после сдвига `main` `rebaseCandidate` переносит кандидата одним коммитом бота на новый `main` по CAS с проверкой ограждения перед push; повтор даёт тот же коммит, `treeOf` — его дерево.

Раннеров у этой Gitea нет: запуски создаются и остаются в очереди. `[actions] WORKFLOW_DIRS` здесь не задан, файлы workflow репозитория запускаются — на них стенд и меряет теги и dispatch. Обязательные workflow из `platform/ci`, `WORKFLOW_DIRS` и запуск scoped workflow по тегу и через `workflow_dispatch` (`scoped_workflow_source_repo_id`) проверяет стенд пайплайна (`pnpm verify:pipeline`, R8c).

Чего здесь нет: PR, обязательного workflow, раннеров Actions, песочницы и супервизора хода. Ход целиком с локальным git-репозиторием проверяют `pnpm --filter orchestrator verify:publication` и `pnpm verify:opencode-supervisor`.

Нужны локальный Docker с уже загруженным образом `gitea/gitea:1.27.3-rootless` (стенд образы не скачивает), `git`, `openssl` и Gitleaks 8.30.1. Корневой `.env`, dev-Gitea (`raditi-dev-gitea-1`) и настоящие токены не используются; опций у стенда нет. Пароли учётных записей стенда генерирует сама Gitea (`gitea admin user create --random-password`), стенд читает их из вывода: в аргументах процессов их нет. Сценарий идёт в отдельном процессе с синтетическим `HOME` внутри временного каталога стенда: CA доходит до git через `GIT_CA_FILE`, до REST-клиента — через `NODE_EXTRA_CA_CERTS`, как в production. Контейнер и временный каталог удаляются в конце и при SIGINT/SIGTERM; о каждом — своя строка `PASS`. Повторный сигнал уборку не обрывает. Сигнал, посланный `pnpm verify:gitea`, доходит до стенда: строка скрипта заменяет оболочку стендом (`exec node …`), и pnpm возвращает его код после уборки.

Приёмник вебхуков — процесс сценария: Docker Desktop и Colima ведут `host.docker.internal` на loopback хоста, на хосте Linux приёмник слушает шлюз моста `bridge` (на Linux стенд не запускался). Gitea шлёт вебхуки только на частные адреса (`[webhook] ALLOWED_HOST_LIST = private`).

Файлы: `verify-gitea.mjs` — стенд, `scenario.mjs` — проверки хода, `release-scenario.mjs` — проверки выпуска, `stand.mjs` и `stand.test.mjs` — параметры контейнера и окружение сценария (`pnpm test:infra`); тот же тест держит `[actions] WORKFLOW_DIRS` dev-Gitea (`infra/dev/docker-compose.yml`).
