# Стенд проектов: файлы, инструкции, память, репозиторий GitLab и GitHub

```sh
pnpm verify:projects                    # сборка копии дерева и образов, затем все сценарии
pnpm verify:projects -- --no-build      # те же сборки ещё раз; отказ, если дерево изменилось после них
pnpm verify:projects -- --keep          # оставить стенд поднятым после сценариев (и после провала) до Ctrl-C
pnpm verify:projects -- --only F,I      # только названные сценарии и те, без которых они не идут
pnpm verify:projects -- --runtime=runsc # песочница хода под gVisor (только Linux; «Linux и CI»)
```

Стенд проходит проекты [плана 84](../../../docs/plan/84-projects.md) (§6, срез 84.23) на этой машине — Docker Desktop на macOS или Docker Engine той же машины Linux (ВМ Colima, раннер GitHub Actions; «Linux и CI»), песочница хода под `runc`, на Linux — и под `runsc` — только на одноразовых сервисах. Агент — настоящий OpenCode CLI в песочнице на сценарной модели (`programs.mjs`), репозиторий клиента — подделки GitLab (`fake-gitlab.mjs`) и GitHub (`fake-github.mjs`) с настоящим git smart HTTP. Каждая строка `PASS` — факт, прочитанный из состояния продукта (база, ответы web, запросы к синтетическому Z.ai) или из того, что держит подделка: её голые репозитории, запросы, запросы на слияние, запущенные задания. Строка `NOTE` — не проверка. В конце печатается таблица сценариев с числом проверок.

## Что поднимается

Всё одноразовое, со своим именем `raditi-projects-verify-<run>-…` и меткой `io.raditi.projects-verify=<run>`:

- PostgreSQL 17, Redis 8, SeaweedFS, OpenBao с политиками `infra/vault` и AppRole на процесс (`core` — с `core-git`, web — `sites-writer`) — модули стенда браузера (`../browser-task-verify/services.mjs`), как и сборка копии (`build.mjs`), время выполнения (`runtime.mjs`), регистрация и модель (`setup.mjs`, `model.mjs`).
- Процессы платформы из сборки приватной копии дерева (`$TMPDIR/raditi-projects-verify-build`): `git-worker` (`node dist/git-worker/main.js` — единственный, кто запускает `git` и `gitleaks` этой машины, только с томом зеркал), `llm`, `mcp`, `core` (`GIT_MIRROR_DIR`, `GIT_CA_FILE`, `GIT_ALLOW_LOOPBACK`, `RADITI_FAKE_GITLAB_COM_URL`, приложение OAuth и `REPO_CONFIRM_SECRET`) и web `next build` (то же и `NODE_EXTRA_CA_CERTS` с CA стенда). Браузера чата, `preview` и `browser` здесь нет.
- Образы песочницы хода, её шлюза и сторожа этого дерева под своими именами, по digest.
- Синтетический Z.ai в процессе стенда; аккаунт плана импортирует `subscriptions:login`, ставки и курс пишет `billing:rates`.
- Подделка GitLab в процессе стенда на своём порту (127.0.0.1 и ::1) с сертификатом CA стенда на `localhost`, `gitlab.localhost` и `gitlab.com`. Она отвечает двум GitLab по `Host`: `gitlab.localhost` — свой сервер клиента по токену, `gitlab.com` — по OAuth с PKCE; API gitlab.com приложения достают через `RADITI_FAKE_GITLAB_COM_URL`. git ходит к репозиторию только по `https://<хост>/<путь>.git` на 443 с закреплённым адресом, а порт 443 на loopback пользователь машины открыть не может, демон Docker — может: контейнер-пересыльщик (node образа шлюза песочницы, только чтение, без возможностей) публикует `127.0.0.1:443` и `[::1]:443` и передаёт TCP подделке — TLS сквозной; на Linux и в ВМ — через пересыльщик стенда на шлюзе моста («Linux и CI»). Свой сервер разрешается по имени `gitlab.localhost` (на macOS — в `::1`, в ВМ Colima — в `127.0.0.1`), gitlab.com — в адрес `localhost` (правка `fakedGitlabCom` в `core`, только при подделке). `core` получает `APP_URL` `https://raditi.localhost`: хук проекта GitLab делается только для `https` (web остаётся на своём адресе), а подделка доставляет события хука на адрес web.
- Подделка GitHub в процессе стенда на своём порту: REST API приложения (токен установки — только по JWT приложения RS256, с репозиториями и правами запроса, и каждый запрос токена сверяется с ними; права человека, защита ветки с обязательной проверкой `test`, запросы на слияние, слияние с `sha`, наборы проверок, запуски, задания, журнал — переадресацией, `workflow_dispatch`), страницы установки (возврат на Setup URL) и входа пользователя приложения с PKCE (`RADITI_FAKE_GITHUB_API_URL`, `RADITI_FAKE_GITHUB_WEB_URL`), доставки вебхука приложения с `X-Hub-Signature-256`. git `github.com` идёт на 443 через тот же пересыльщик: подделка GitLab отдаёт запросы с `Host: github.com` подделке GitHub. Хук `pre-receive` её голых репозиториев отклоняет коммит с `.github/workflows/` от токена без `workflows`, как GitHub. Ключ приложения — файл прогона (`GITHUB_APP_PRIVATE_KEY_FILE`), подделка знает только открытую половину.

Docker Desktop или Docker Engine 29.1 и новее этой машины Linux, с хранилищем образов containerd (`--runtime=runsc` — ещё среда `runsc` демона), свободный порт 443 на loopback, интернет (в C — `webfetch` песочницы на `https://example.com/`), Node 26.10, pnpm, `git` (с `git http-backend`), `gitleaks` 8.30, `rsync`, `openssl`, на macOS — `ps` и `lsof` (N; на Linux N читает `/proc`) и уже загруженные образы стенда браузера (`chrislusf/seaweedfs:4.47`, `postgres:17.11-alpine3.24`, `redis:8.10.2-alpine`, `ghcr.io/openbao/openbao:2.7.0`). Не рядом с другим стендом Docker, `pnpm dev` или `pnpm e2e`. `.env` и dev-инфраструктура не используются. Сборку держите в своём каталоге (`PROJECTS_VERIFY_BUILD_DIR`), если стенд в то же время идёт из другого рабочего дерева: каталог по умолчанию у них общий.

`PROJECTS_VERIFY_STALE_COPY=allow` вместе с `--no-build` пускает прогон на копии другого состояния дерева: такой прогон печатает `NOTE` и ничего не доказывает о дереве. `PROJECTS_VERIFY_BUILD_DIR` и `PROJECTS_VERIFY_LOG_DIR` — свои каталоги сборки и журналов упавшего прогона.

## Linux и CI

Стенд идёт на Docker Desktop (macOS) и на Docker Engine этой же машины Linux — в ВМ Colima и на раннере GitHub Actions (`projects.yml`). Каким хост видят контейнеры, стенд читает перед запуском, а не по `process.platform` (`hostOf` в `../browser-task-verify/stand.mjs`, `probeHost` в `../browser-task-verify/services.mjs`): строку `docker info` (`OperatingSystem`), шлюз моста `bridge` и адрес, в который `host-gateway` разрешается в пробном контейнере (закреплённый образ PostgreSQL печатает свой `/etc/hosts`, только чтение, без возможностей). Вид решают сами адреса; строка `PASS host of the daemon` его называет. Демон Linux на другой машине (Mac на сокете ВМ) стенд отклоняет: ВМ не видит loopback Mac.

| Вид | Как узнаётся | Контейнеры к `llm`, `mcp` и подделке GitLab | Куда идут контейнеры |
| --- | --- | --- | --- |
| `desktop` | `docker info` говорит Docker Desktop | Docker Desktop сам ведёт `host.docker.internal` на loopback Mac | `host.docker.internal` |
| `linux` | `host-gateway` равен шлюзу моста | пересыльщики стенда на шлюзе моста | `host.docker.internal` (это и есть шлюз моста) |
| `vm` | `host-gateway` — другой адрес (Colima ведёт его на Mac) или `host-gateway-ip` демона | как `linux` | шлюз моста по адресу |

- Процессы платформы, как и на Docker Desktop, слушают `127.0.0.1`. На Linux и в ВМ стенд в своём процессе поднимает TCP-пересыльщики `<шлюз моста>:<порт>` → `127.0.0.1:<порт>` для `llm`, `mcp` и подделки GitLab (`projectRelays`, `startRelays` в `../browser-task-verify/services.mjs`): шлюз песочницы хода и пересыльщик 443 встречают их на мосту, процесс видит соединение с `127.0.0.1` (`LLM_GATEWAY_CLIENTS` остаётся `127.0.0.1/32`). В виде `vm` `SANDBOX_LLM_UPSTREAM` и `SANDBOX_MCP_UPSTREAM` у `core` называют шлюз моста по адресу, а `LLM_GATEWAY_HOSTS` и `MCP_ALLOWED_HOSTS` его принимают (`appEnvironment` стенда браузера, `context.host`); без `context.host` окружения — прежние, Docker Desktop, — поэтому стенд браузера их не меняет.
- Пересыльщик 443 — тот же контейнер, что на Docker Desktop: мост по умолчанию, только чтение, `--cap-drop ALL`, публикует только `127.0.0.1:443` и `[::1]:443`; на Linux к нему добавлено одно `--add-host host.docker.internal:host-gateway`, в ВМ он идёт на шлюз моста по адресу. Ни сети хоста, ни `NET_BIND_SERVICE`, ни правки `net.ipv4.ip_unprivileged_port_start`: порт 443 публикует демон.
- Правила хоста песочницы не менялись. Песочница хода стоит на internal-сети попытки без адреса хоста: под `runc` — в сетевом пространстве сторожа (`SANDBOX_NETWORK_GUARD_IMAGE`), который пропускает только шлюз, под `runsc` — за правилом хоста моста попытки. Пересыльщики видны только контейнерам моста по умолчанию — доверенному шлюзу хода и пересыльщику 443. E это проверяет на каждом виде хоста: из песочницы хода — TCP к каждому адресу хоста для контейнеров (`host-gateway` и шлюз моста) на каждый порт, который стенд там открывает (`hostProbes`), — ни одного соединения; контроль — та же проба к шлюзу хода, она соединяется.
- `--runtime=runsc` — песочница хода под gVisor (только на Linux, у демона должен быть `runsc`); шлюз хода и его сторож — под `runc`, как в продукте. По умолчанию — `runc`. Что песочница идёт именно под этой средой, E проверяет по ядру, которое она видит.
- N читает окружение и соединения `git-worker` так, как их отдаёт система: на Linux — `/proc/<pid>/environ`, дескрипторы и таблицы TCP его сетевого пространства (`procRemotePorts`), на macOS — `ps -E` и `lsof -i`; контроль — тем же чтением соединение самого стенда с базой.
