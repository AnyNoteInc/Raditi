# Стенд проектов: файлы, инструкции, память и репозиторий GitLab

```sh
pnpm verify:projects                    # сборка копии дерева и образов, затем все сценарии
pnpm verify:projects -- --no-build      # те же сборки ещё раз; отказ, если дерево изменилось после них
pnpm verify:projects -- --keep          # оставить стенд поднятым после сценариев (и после провала) до Ctrl-C
pnpm verify:projects -- --only F,I      # только названные сценарии и те, без которых они не идут
```

Стенд проходит проекты [плана 84](../../../docs/plan/84-projects.md) (§6, срез 84.23) на этой машине — macOS, Docker Desktop, `runc` — только на одноразовых сервисах. Агент — настоящий OpenCode CLI в песочнице на сценарной модели (`programs.mjs`), репозиторий клиента — подделка GitLab с настоящим git smart HTTP (`fake-gitlab.mjs`). Каждая строка `PASS` — факт, прочитанный из состояния продукта (база, ответы web, запросы к синтетическому Z.ai) или из того, что держит подделка: её голые репозитории, запросы, запросы на слияние, запущенные задания. Строка `NOTE` — не проверка. В конце печатается таблица сценариев с числом проверок.

## Что поднимается

Всё одноразовое, со своим именем `raditi-projects-verify-<run>-…` и меткой `io.raditi.projects-verify=<run>`:

- PostgreSQL 17, Redis 8, SeaweedFS, OpenBao с политиками `infra/vault` и AppRole на процесс (`core` — с `core-git`, web — `sites-writer`) — модули стенда браузера (`../browser-task-verify/services.mjs`), как и сборка копии (`build.mjs`), время выполнения (`runtime.mjs`), регистрация и модель (`setup.mjs`, `model.mjs`).
- Процессы платформы из сборки приватной копии дерева (`$TMPDIR/raditi-projects-verify-build`): `git-worker` (`node dist/git-worker/main.js` — единственный, кто запускает `git` и `gitleaks` этой машины, только с томом зеркал), `llm`, `mcp`, `core` (`GIT_MIRROR_DIR`, `GIT_CA_FILE`, `GIT_ALLOW_LOOPBACK`, `RADITI_FAKE_GITLAB_COM_URL`, приложение OAuth и `REPO_CONFIRM_SECRET`) и web `next build` (то же и `NODE_EXTRA_CA_CERTS` с CA стенда). Браузера чата, `preview` и `browser` здесь нет.
- Образы песочницы хода, её шлюза и сторожа этого дерева под своими именами, по digest.
- Синтетический Z.ai в процессе стенда; аккаунт плана импортирует `subscriptions:login`, ставки и курс пишет `billing:rates`.
- Подделка GitLab в процессе стенда на своём порту (127.0.0.1 и ::1) с сертификатом CA стенда на `localhost`, `gitlab.localhost` и `gitlab.com`. Она отвечает двум GitLab по `Host`: `gitlab.localhost` — свой сервер клиента по токену, `gitlab.com` — по OAuth с PKCE; API gitlab.com приложения достают через `RADITI_FAKE_GITLAB_COM_URL`. git ходит к репозиторию только по `https://<хост>/<путь>.git` на 443 с закреплённым адресом, а на macOS порт 443 на loopback может открыть только Docker Desktop: контейнер-пересыльщик (node образа шлюза песочницы, только чтение, без возможностей) публикует `127.0.0.1:443` и `[::1]:443` и передаёт TCP подделке — TLS сквозной. Свой сервер разрешается в `::1` по имени `gitlab.localhost`, gitlab.com — в адрес `localhost` (правка `fakedGitlabCom` в `core`, только при подделке).

## Что нужно

Docker Desktop с хранилищем образов containerd, свободный порт 443 на loopback, Node 26.10, pnpm, `git` (с `git http-backend`), `gitleaks` 8.30, `rsync`, `openssl` и уже загруженные образы стенда браузера (`chrislusf/seaweedfs:4.47`, `postgres:17.11-alpine3.24`, `redis:8.10.2-alpine`, `ghcr.io/openbao/openbao:2.7.0`). Не рядом с другим стендом Docker, `pnpm dev` или `pnpm e2e`. `.env` и dev-инфраструктура не используются; workflow CI нет (`projects.yml` — после первого прохода на Linux, план 84, §6).

`PROJECTS_VERIFY_STALE_COPY=allow` вместе с `--no-build` пускает прогон на копии другого состояния дерева: такой прогон печатает `NOTE` и ничего не доказывает о дереве. `PROJECTS_VERIFY_BUILD_DIR` и `PROJECTS_VERIFY_LOG_DIR` — свои каталоги сборки и журналов упавшего прогона.

## Что не проверено

- Сценарии плана, которых в этом проходе нет: C (память: «запомни», «Предложено» после `webfetch` и команды, внедрение из README, переключатель памяти аккаунта), L (запуск по расписанию — Э5 другой работы), гонка отправки с клиентом и конфликт (F), «когда сборка пройдёт» (I), сдвиг головы перед выкладкой (J), переадресация и смена адреса между запросами, pack на 1 ГБ (K), `kill -9` `core` между снимком и публикацией (E), корзина проекта, отказ из-за непроверенной учётной записи (H), открытая ссылка на репозиторий (D).
- Linux и gVisor (`runsc`), настоящая модель, настоящие gitlab.com и сервер GitLab, исполняет ли gitlab.com быстрые действия из описания (ПР14) — живые проверки плана 84, §6.
- Кабинет в браузере: клиент здесь действует через HTTP, как кабинет; экраны — `test:site`.

Файлы: `verify-projects.mjs` — сборки, порядок запуска и уборка; `stand.mjs` и `stand.test.mjs` — параметры, окружения процессов, аргументы пересыльщика (`pnpm test:infra`); `fake-gitlab.mjs` и `fake-gitlab.test.mjs` — подделка GitLab; `programs.mjs` — сценарная модель; `scenarios.mjs` — сценарии.
