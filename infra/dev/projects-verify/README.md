# Стенд проектов: файлы, инструкции, память, репозиторий GitLab и GitHub

```sh
pnpm verify:projects                    # сборка копии дерева и образов, затем все сценарии
pnpm verify:projects -- --no-build      # те же сборки ещё раз; отказ, если дерево изменилось после них
pnpm verify:projects -- --keep          # оставить стенд поднятым после сценариев (и после провала) до Ctrl-C
pnpm verify:projects -- --only F,I      # только названные сценарии и те, без которых они не идут
```

Стенд проходит проекты [плана 84](../../../docs/plan/84-projects.md) (§6, срез 84.23) на этой машине — macOS, Docker Desktop, `runc` — только на одноразовых сервисах. Агент — настоящий OpenCode CLI в песочнице на сценарной модели (`programs.mjs`), репозиторий клиента — подделки GitLab (`fake-gitlab.mjs`) и GitHub (`fake-github.mjs`) с настоящим git smart HTTP. Каждая строка `PASS` — факт, прочитанный из состояния продукта (база, ответы web, запросы к синтетическому Z.ai) или из того, что держит подделка: её голые репозитории, запросы, запросы на слияние, запущенные задания. Строка `NOTE` — не проверка. В конце печатается таблица сценариев с числом проверок.

## Что поднимается

Всё одноразовое, со своим именем `raditi-projects-verify-<run>-…` и меткой `io.raditi.projects-verify=<run>`:

- PostgreSQL 17, Redis 8, SeaweedFS, OpenBao с политиками `infra/vault` и AppRole на процесс (`core` — с `core-git`, web — `sites-writer`) — модули стенда браузера (`../browser-task-verify/services.mjs`), как и сборка копии (`build.mjs`), время выполнения (`runtime.mjs`), регистрация и модель (`setup.mjs`, `model.mjs`).
- Процессы платформы из сборки приватной копии дерева (`$TMPDIR/raditi-projects-verify-build`): `git-worker` (`node dist/git-worker/main.js` — единственный, кто запускает `git` и `gitleaks` этой машины, только с томом зеркал), `llm`, `mcp`, `core` (`GIT_MIRROR_DIR`, `GIT_CA_FILE`, `GIT_ALLOW_LOOPBACK`, `RADITI_FAKE_GITLAB_COM_URL`, приложение OAuth и `REPO_CONFIRM_SECRET`) и web `next build` (то же и `NODE_EXTRA_CA_CERTS` с CA стенда). Браузера чата, `preview` и `browser` здесь нет.
- Образы песочницы хода, её шлюза и сторожа этого дерева под своими именами, по digest.
- Синтетический Z.ai в процессе стенда; аккаунт плана импортирует `subscriptions:login`, ставки и курс пишет `billing:rates`.
- Подделка GitLab в процессе стенда на своём порту (127.0.0.1 и ::1) с сертификатом CA стенда на `localhost`, `gitlab.localhost` и `gitlab.com`. Она отвечает двум GitLab по `Host`: `gitlab.localhost` — свой сервер клиента по токену, `gitlab.com` — по OAuth с PKCE; API gitlab.com приложения достают через `RADITI_FAKE_GITLAB_COM_URL`. git ходит к репозиторию только по `https://<хост>/<путь>.git` на 443 с закреплённым адресом, а на macOS порт 443 на loopback может открыть только Docker Desktop: контейнер-пересыльщик (node образа шлюза песочницы, только чтение, без возможностей) публикует `127.0.0.1:443` и `[::1]:443` и передаёт TCP подделке — TLS сквозной. Свой сервер разрешается в `::1` по имени `gitlab.localhost`, gitlab.com — в адрес `localhost` (правка `fakedGitlabCom` в `core`, только при подделке). `core` получает `APP_URL` `https://raditi.localhost`: хук проекта GitLab делается только для `https` (web остаётся на своём адресе), а подделка доставляет события хука на адрес web.
- Подделка GitHub в процессе стенда на своём порту: REST API приложения (токен установки — только по JWT приложения RS256, с репозиториями и правами запроса, и каждый запрос токена сверяется с ними; права человека, защита ветки с обязательной проверкой `test`, запросы на слияние, слияние с `sha`, наборы проверок, запуски, задания, журнал — переадресацией, `workflow_dispatch`), страницы установки (возврат на Setup URL) и входа пользователя приложения с PKCE (`RADITI_FAKE_GITHUB_API_URL`, `RADITI_FAKE_GITHUB_WEB_URL`), доставки вебхука приложения с `X-Hub-Signature-256`. git `github.com` идёт на 443 через тот же пересыльщик: подделка GitLab отдаёт запросы с `Host: github.com` подделке GitHub. Хук `pre-receive` её голых репозиториев отклоняет коммит с `.github/workflows/` от токена без `workflows`, как GitHub. Ключ приложения — файл прогона (`GITHUB_APP_PRIVATE_KEY_FILE`), подделка знает только открытую половину.

## Почему нет workflow CI

`projects.yml` не добавлен: стенд как есть на Linux (раннер GitHub Actions, `runc`) не идёт, а сделать его таким — работа над общими модулями стенда браузера, не этого стенда:

- процессы платформы слушают `127.0.0.1`, а шлюз песочницы хода ходит к `llm` и `mcp` по `host.docker.internal` (`SANDBOX_LLM_UPSTREAM`, `SANDBOX_MCP_UPSTREAM`, `LLM_GATEWAY_HOSTS`, `MCP_ALLOWED_HOSTS` в `../browser-task-verify/stand.mjs`). Docker Desktop ведёт это имя на loopback хоста; на Linux его нет без `--add-host …:host-gateway`, а там это адрес моста Docker, где ничего не слушает, — процессам пришлось бы слушать адрес моста, а правилам хоста песочницы (`SANDBOX_NETWORK_GUARD_IMAGE`) — его пропускать;
- пересыльщик порта 443 соединяется с подделками на `host.docker.internal`, а они слушают только loopback; на Linux ему нужна сеть хоста и право на порт ниже 1024 (`NET_BIND_SERVICE`), что расходится с его `--cap-drop ALL` и публикацией только `127.0.0.1:443`;
- поэтому предварительная проверка сама отказывает вне Docker Desktop.

Это то же ограничение, что у стендов `verify:browser-task` и `verify:release` (у них тоже нет workflow). Путь на Linux — вместе с ними: адрес хоста для песочницы из окружения стенда, пересыльщик в сети хоста.

`PROJECTS_VERIFY_STALE_COPY=allow` вместе с `--no-build` пускает прогон на копии другого состояния дерева: такой прогон печатает `NOTE` и ничего не доказывает о дереве. `PROJECTS_VERIFY_BUILD_DIR` и `PROJECTS_VERIFY_LOG_DIR` — свои каталоги сборки и журналов упавшего прогона.

## Что не проверено

- Сценарии плана, которых в стенде нет: смена адреса имени между двумя запросами (K) — `core` разрешает имя системным резолвером (`dns.lookup`), а подменить его ответ между двумя запросами без своего DNS-сервера и без прав на `/etc/hosts` этой машины нельзя; держат модульные тесты закрепления адреса (`public-host.test.ts`, транспорт `@repo/git-providers`). Pack на 1 ГиБ в самом fetch (K; стенд проверяет отказ по размеру, который называет провайдер, квоту fetch — `git-workspace.service.test.ts`). Задача, которую агент создал по внедрённому тексту, — стенд проверяет паузу `unconfirmed` любой задачи агента в проекте с репозиторием. «Предложено» после `webfetch` проверено на открытом `https://example.com/` (нужен интернет; без него вызов падает, а признак внешнего текста остаётся).
- Журнал задания GitHub по разрешённой переадресации (`*.actions.githubusercontent.com`): имя разрешается настоящим DNS, и чтение ушло бы в настоящий GitHub. P проверяет обратное — на другой хост переадресация не идёт.
- Вход истёк у запуска по таймеру (L): стенд жмёт «Запустить сейчас» — тот же `startRun`, что у тика расписания.
- Шлюз хода, чей `core` убит посреди удаления песочницы (E), здесь убирает не платформа: `core` ведёт ходы в своём Docker (`TURN_EXECUTOR=local`), где нет сторожа песочной ВМ. M зовёт сторож этого дерева (`infra/sandbox/watchdog.mjs`, `reapExpired`) только над ресурсами чатов прогона и проверяет, что шлюз ушёл после своего срока.
- Linux и gVisor (`runsc`), настоящая модель, настоящие gitlab.com, GitHub и сервер GitLab, исполняет ли gitlab.com быстрые действия из описания (ПР14) — живые проверки плана 84, §6.
- Кабинет в браузере: клиент здесь действует через HTTP, как кабинет; экраны — `test:site`.
