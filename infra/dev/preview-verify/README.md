# Стенд сети предпросмотра

`pnpm verify:preview-network` ([план 58](../../../docs/plan/58-preview-single-container.md); [план 53](../../../docs/plan/53-chat-preview-release.md), Р18, Р21) строит настоящей средой `createDockerPreviewRuntime` два предпросмотра (A с базой и B без неё) — каждый одним контейнером на своём мосту — и браузер предпросмотра A и проверяет пути: с хоста, из контейнера предпросмотра (от PHP и от root контейнера), из контейнера браузера и из самого Chromium. Шлюз предпросмотров играет маленький HTTP-сервер стенда на `PREVIEW_GATEWAY_PORT` (8090, если порт свободен, иначе любой свободный); службы хоста на 5432, 8200, 8085 и 8090, которых нет, стенд поднимает сам на время проверки.

Интернет предпросмотра открыт (ответ владельца от 26.10.2026), поэтому PHP должен доставать публичный адрес (`1.1.1.1:443`) и публичное имя (`example.com:443`), а хост, мост по умолчанию, чужой предпросмотр, браузер и его пересыльщик, порт управления браузером и подсеть платформы — нет. Подсеть платформы стенд задаёт публичную (`--refuse 1.0.0.0/24`), чтобы контроль её достал: `1.0.0.1:443` закрыт, соседний `1.1.1.1:443` открыт.

Прогон проходит, только если прошла каждая строка (`PASS`), иначе код 1:

- у каждой строки «закрыто» есть контроль — та же цель из контейнера на мосту по умолчанию, для опубликованного на loopback — с самого хоста, для чужого предпросмотра — изнутри него самого; цель, которую не достал и контроль, ничего не доказывает (`VACUOUS` — провал);
- имя (`host.docker.internal`, `example.com` у браузера), которое внутри не разрешилось (`dns`), засчитывается закрытым, если контроль его разрешил; разрешившееся — только если пакет не нашёл пути, а контроль цель достал;
- проба, которая не выполнилась (`error`: контейнер упал, нет `php` или `node`), — провал, а не «закрыто»;
- строки «доступно» с каждой стороны (свой сервер `127.0.0.1:8081`, свой шлюз `127.0.0.1:8080`, своя база `127.0.0.1:3306`, интернет, пересыльщик браузера): сломанная проба видна сразу;
- пользователи внутри: PHP (33) не читает пароль root своей базы и не входит в неё root через сокет, не шлёт сигнал шлюзу (10001) — у каждой строки контроль от того пользователя, которому это можно; root контейнера предпросмотра держат те же правила моста, что и PHP;
- строка `check` помощника правил хоста (`host-firewall.mjs check <мост> --refuse …`) — правила моста A на месте и целы;
- файл платформы: `writeFiles` предпросмотра A получает `platform` — `raditi-stand/platform.php`, и этот шаг идёт от root настоящей средой (`writePlatformFiles` в `infra/preview/files.mjs`). Файл отдаётся через шлюз A, им владеет root с правами 0444, PHP его не перезаписывает, а новый файл в том же корне создаёт (контроль), и не подменяет его переименованием своего файла из папки платформы — это держит бит sticky папки 1775, — а свой файл в той же папке переименовывает (контроль). У B поля `platform` нет, и строка стенда читает, что его корнем владеет PHP (33). Под `runsc` до Э0а ([план 62](../../../docs/plan/62-site-stacks.md)) этот шаг падал на `EPERM`, и стенд кончался на стадии `previews`: `chmod` сразу после `chown` на том же дескрипторе; `stat` между ними лечит, причина не подтверждена.

Нужны Docker и базовые образы `infra/preview/Dockerfile` и `infra/sandbox/Dockerfile`; стенд собирает `raditi-preview-tools:local`, `raditi-preview-browser:local`, `raditi-preview-site:8.3-local` (цель `site` без аргументов — PHP 8.3 на стадии `php-base`, срок сборки 30 минут) и `raditi-network-guard:local` (`--no-build` — взять собранные; `SANDBOX_NETWORK_GUARD_IMAGE` — взять этот образ правил). Стенд ходит в интернет (`1.1.1.1`, `1.0.0.1`, `example.com`) и к DNS `77.88.8.8`; `.env` не читает, сам ничего не тянет (сборка `site` при пустом кеше берёт основу `php`, пакеты apt, PECL, установщик расширений и архив ionCube), по окончании удаляет всё своё (`--keep` — оставить). `--runtime=runsc` — то же под gVisor на Linux.

Службы стенда слушают там, куда контейнеры ходят как на хост (`host-gateway`): на macOS — loopback (Docker Desktop ведёт туда `host.docker.internal`), на Linux — сам адрес `host-gateway`. Если он не принадлежит этой машине (Colima ведёт `host-gateway` на Mac), службы и шлюз слушают адрес моста `docker0`, а пересыльщику браузера среда передаёт этот адрес (`gatewayHost`) — стенд печатает об этом строку.

## Образы `site`

`pnpm verify:site-images [-- --only 7.4,8.3] [--image=<образ>] [--no-build] [--build-only] [--keep] [--runtime=runsc]` ([план 62](../../../docs/plan/62-site-stacks.md), Э1.2, ступень М1) собирает цель `site` на стадии `php-base` для каждой строки `infra/preview/site-bases.json` (`raditi-site-verify:<версия>`, аргументы — `siteImageBuildArgs`, срок сборки 30 минут) и проверяет образ снаружи настоящей средой `createDockerPreviewRuntime`: предпросмотр с базой по рецепту стенда на общих файлах рецепта стека — `infra/preview/site-apache.conf` (на месте `# RADITI_SITE_RULES` — одно правило стенда) и `infra/preview/prologue.php` — и с ini стека `raditi-stack.ini` (`max_input_vars = 4321`) через `PHP_INI_SCAN_DIR=:/run/raditi/preview`. Запросы идут изнутри контейнера к его шлюзу (`php -r`, `http://127.0.0.1:8080/<путь>` с `Host` предпросмотра), поэтому стенд одинаково работает на Docker Desktop, в CI и с Mac на демоне Colima. Образы `tools` и правил хоста собираются, как у стенда сети, но под своими метками — `raditi-site-verify-tools:local` и `raditi-site-verify-guard:local` (`SANDBOX_NETWORK_GUARD_IMAGE` — взять этот образ правил). Digest локальной сборки даёт только хранилище образов containerd: без него стенд отказывает словами о containerd. `--build-only` собирает и выходит, `--image` берёт готовый образ одной версии (`--only`) вместо сборки, `--no-build` — собранные образы, `--keep` оставляет предпросмотры. `.env` стенд не читает, ничего не отправляет; основы `php@sha256:…` таблицы и образ `wordpress@sha256:8ae73d59…` должны быть уже загружены (`docker pull`), сборка `php-base` ходит в интернет (установщик, ionCube, PECL, apt).
