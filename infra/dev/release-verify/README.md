# Стенд выпуска: чат → предпросмотр → /release

```sh
pnpm verify:release              # сборка копии дерева и образов, затем сценарии S1–S10
pnpm verify:release -- --no-build   # те же сборки ещё раз; отказ, если дерево изменилось после них
pnpm verify:release -- --keep       # оставить стенд поднятым после сценариев (и после провала) до Ctrl-C
```

Стенд проходит запрос владельца целиком ([план 53](../../../docs/plan/53-chat-preview-release.md), R12) на этой машине — macOS, Docker Desktop, `runc` — только на одноразовых сервисах. Владелец сайта пишет в чат web, агент (настоящий OpenCode CLI 1.18.34 в песочнице на сценарной модели) меняет сайт в предпросмотре, предпросмотр показывает изменение, `/release` выпускает версию: тег, Gitea Actions, `deploy-step` образа `core`, SFTP, плагин «Радити», проверка, при сбое — возврат. Каждая строка `PASS` — факт, прочитанный из состояния продукта, его страниц или того, что держат Gitea, OpenBao, S3, Docker и хостинг. Строка `NOTE` — не проверка: предусловие стенда (ожидание предпросмотра перед ответом модели) или то, что на этой машине не доказать (метаданные облака: на Docker Desktop их нет и у контроля). В конце печатается таблица сценариев с числом проверок и заметок.

## Что поднимается

Всё одноразовое, со своим именем `raditi-release-verify-<run>-…` и меткой `io.raditi.release-verify=<run>`:

- PostgreSQL 17 (данные в памяти), Redis 8, SeaweedFS с бакетами `raditi-*`, OpenBao (инициализация через API, mounts и политики `infra/vault/bootstrap.mjs`, AppRole на каждый процесс: `core` — `core-turns`, `core-transit`, `core-site-import`, `core-release`; `mcp` — `mcp-content`; `llm` — `llm-subscriptions`; web — `sites-writer` и `workspace-provisioner`).
- Gitea 1.27.3 по HTTPS с CA стенда и `[actions] WORKFLOW_DIRS`; администратор экземпляра, бот платформы (`GITEA_TOKEN`) и учётная запись выпуска — владелец организации `sites`, чей токен лежит в OpenBao `kv/platform/gitea-org-owner`; `platform/ci` с `check.yml` и `deploy.yml` из `ci/` — источник scoped workflows.
- gitea/runner 4.0.0 — раннер выкладки, метка `deploy` — образ `core` из этого дерева (`raditi-release-verify/core:local`).
- Синтетический «прод»: MariaDB с базой WordPress, WordPress 7.1.2 (тема стенда, страница «Контакты», запись, плагин «Радити» в `mu-plugins`, одна картинка медиатеки, `WP_ENVIRONMENT_TYPE=local` — иначе WordPress не даёт паролей приложений по http), SFTP-хостинг (`linuxserver/openssh-server` по digest) над тем же томом документов. Адрес сайта — `http://localhost:<порт>`, база — на loopback для копии.
- Репозиторий сайта `sites/site-<siteId>`: всё дерево документов без `wp-config.php` (ядро и медиа — как оставляет импорт плана 39), первый коммит `main` от бота и тег `v0.0.0` от учётной записи выпуска.
- Процессы платформы из сборки приватной копии дерева (`$TMPDIR/raditi-release-verify-build`, как у `verify:billing`): приложения `llm`, `mcp` (`MCP_CONTENT_PROFILE=local`, `MCP_BROWSER_PROFILE=local`), `preview` и `core` — `node dist/main.js` в каталоге приложения, каждое своим процессом, `TURN_EXECUTOR=local` и `PREVIEW_EXECUTOR=local` под `runc`; предпросмотр — один контейнер образа `preview-site` этого дерева, его мост закрывают правила хоста образа `network-guard` ([план 58](../../../docs/plan/58-preview-single-container.md)); web — `next build` (standalone). `NODE_ENV=production` у всех: ни один процесс не ищет `.env`.
- Синтетический Z.ai — `infra/dev/llm-verify/fake-zai.mjs` в процессе стенда за TLS сертификатом стенда; аккаунт плана импортирует настоящая команда оператора `subscriptions:login`. Ответы модели на каждый ход — `MODEL_TURNS` в `stand.mjs`. Первый запрос раунда хода может ждать условия (`fake-model.mjs`, «ворота»): у диалогов A и B — пока построен предпросмотр на ревизии 0, у диалога C — только появления строки предпросмотра; это предусловие стенда (строка `NOTE`), а что продукт делает без него, показывает C: его первый `wp_rest` приходит до готовности предпросмотра. Ответы первого хода сообщают большой расход токенов (`LARGE_USAGE`): списание выходит выше минимума задачи.
- Владелец сайта регистрируется через web (адрес подтверждается в базе — письма проверяет `verify:billing`), сайт и его личное рабочее пространство стенд пишет строками сам (рабочее пространство — штатной `ensurePersonalWorkspaceWithGift`, сайт `onboarding` без этапа `code_import`: мастер плана 39 проверяет `verify:site-import`); доступы хостинга, базы и плагина стенд пишет так, как их оставляет мастер подключения: Vault токеном `sites-writer`, `credential_refs`, `site_code_sources`, `site_databases`, ключ рабочего пространства токеном `workspace-provisioner`. Дальше стенд делает то, чего мастер не делает (это подключение сайта, M4 и P11): `activateSite` и `sites.installed_version = v0.0.0` с `installed_sha` начального коммита. Сайт, который оставил мастер, — `onboarding` с пустым `installed_*`: диалогов он не принимает, а путь пустого `installed_*` (предложение номера, выпуск, отмена) держат интеграционные тесты `candidate-builder`, `candidate-rebase`, `pass-settlement`, `release-skill` и `preview-manager`, не стенд. Тариф «Агентство» оплачен строками заказа и подписки с начислением `grantTariffCredits`, рядом — два оплаченных пакета (`grantPackCredits`; путь денег — у `verify:billing`): сценарии ставят десять диалогов за день (A–J), держат по нескольку сразу и повторяют один в `heavy` — больше 300 кредитов тарифа, которые «Агентство» даёт московскому дню (решение владельца от 17.10.2026), а пакеты дневным лимитом не ограничены, поэтому каждый резерв — полный шаг своего класса; сам дневной лимит проверяют `verify:billing` и тесты `@repo/billing`. Оператор включает профили `glm-5.3-standard` и `glm-5.3-heavy` («Попробовать ещё» идёт в классе `heavy`); их учётные ставки и курс кредита пишет настоящая команда оператора `billing:rates` (`STAND_RATES`, 6 ₽ за кредит, `--confirm-exposure`) — одним моментом начала; стенд проверяет, что у обоих профилей ставка этого момента.
- Контроль сети (S2, S6a): контейнер образа `preview-tools` на мосту Docker по умолчанию и в сети сайта — там, где стоит любой доверенный контейнер платформы; он же называет адрес хоста (`host-gateway`, на Docker Desktop — 192.168.65.254).

### Сеть заданий выкладки

Задания раннера идут в сети ВМ Docker (`container.network: host`). На Docker Desktop все контейнеры этой сети делят один loopback, и на нём же прокси Docker слушает каждый порт, опубликованный контейнером на `127.0.0.1` (замер 17.10.2026, Docker Desktop 29.8.2): Gitea, OpenBao, S3, хостинг и сайт видны заданию по тем же адресам, что и `core` на Mac. Процесс платформы на Mac (API выпуска приложения `core`) там не виден: контейнер-«зеркало» в той же сети слушает его порт на `127.0.0.1` и пересылает на тот же порт Mac через `host.docker.internal`. Поэтому `sites.url`, доступы хостинга и плагина, адрес API выпуска и `gitea.server_url` у `core` и у задания одни и те же.

Стенд убирает всё своё после успеха, провала и Ctrl-C: процессы, свои контейнеры, тома и сети по метке, песочницы ходов, их шлюзы и предпросмотры — по меткам сайта прогона (`io.raditi.sandbox.siteId`, `io.raditi.gateway.siteId`, `io.raditi.preview.site`), тома заданий — по uuid раннера; в конце проверяет, что ничего не осталось. Если прошедшему прогону пришлось убрать что-то с метками сайта — то, что должен был убрать `core`, — прогон падает. Ресурсы Docker без единой метки, появившиеся за прогон и оставшиеся после уборки, печатаются строкой `NOTE` (их мог создать другой сеанс). Логи упавшего прогона (с вычеркнутыми секретами) остаются в `$TMPDIR/raditi-release-verify-logs-<run>`.

После `kill -9` стенда уборки нет; его ресурсы находятся по метке прогона (`<run>` — восемь знаков из имён контейнеров), а песочницы и предпросмотры — по сайту прогона:

```sh
docker ps -aq --filter label=io.raditi.release-verify=<run> | xargs docker rm -fv
docker volume ls -q --filter label=io.raditi.release-verify=<run> | xargs docker volume rm
docker network ls -q --filter label=io.raditi.release-verify=<run> | xargs docker network rm
docker ps -aq --filter label=io.raditi.preview.site=<siteId> | xargs docker rm -fv
rm -rf "$TMPDIR"/raditi-release-verify-run-<run>-*
```

## Что не проверено

- Linux и gVisor (`runsc`): стенд отказывается запускаться не на Docker Desktop — сеть заданий выкладки держится на поведении его прокси портов.
- Настоящая модель: ходы — сценарные ответы синтетического Z.ai; что настоящий GLM сделает из такого запроса, стенд не говорит.
- Настоящий хостинг: SFTP — OpenSSH в контейнере, FTP(S) не проверяется (его проверяют тесты `@repo/site-connections`), сайт по http, без TLS и без CDN.
- Попытка «только возврат» (`workflow_dispatch`), исход `unknown`, `releases:resolve`, долгие фазы задания без отчётов и продление токена по запуску провайдера — их проверяют интеграционные тесты `releases` и стенд `verify:pipeline`.
- Хостинг, чей opcache не смотрит время файла (`validate_timestamps=0`) или смотрит реже чем раз в 117 с и не даёт плагину сбросить файл (`opcache.restrict_api`, отключённая функция): `deploy-step` отказывает такому выпуску до первой записи (`code_cache`) — это проверяют тесты `deploy.test.ts`, а прод стенда — образ WordPress с opcache по умолчанию (раз в 2 с, сброс разрешён). Удалённый выпуском PHP-файл из кеша не сбросить (его нет в дереве): при `validate_timestamps=0` он остаётся в кеше, пока его кто-то включает.
- Метаданные облака: на Docker Desktop их нет и у контроля, цель печатается строкой `NOTE`. Интернет доказывается, только пока машина в сети (контроль `1.1.1.1:443` открыт).
- `fetch` из JavaScript страницы к чужому источнику без CORS видит только отказ; что именно ответил шлюз, стенд читает переходом страницы (статус и тело).
- «Сбросить» (`/reset`), переменные окружения клиента и прокси выхода — не входят в сценарии; «Обновить» (`/update`) — только перенос без пересечений и конфликт файла (S4b), без плана БД и без переноса, после которого в `main` уже всё изменение.
- Запросы на подтверждение (`request_approval`), медиа кандидата (`wp-content/uploads/raditi/`), вебхуки Gitea (core следит за запуском отчётами и опросом).
- «Отменить выпуск» (S9): прод, изменённый между показом плана и записью задания, новая запись выпуска с комментариями или пунктами меню (`kept_dependents`), отмена файлов (выпуск G файлов не менял), окно отмены в браузере, отказ после 7 дней — интеграционные тесты `releases/undo.integration.test.ts`, `deploy-step/deploy-undo.test.ts`, tRPC (`chat-db.test.ts`) и компонентов web; время продукта стенд не двигает.
- «Попробовать ещё» (S10) — только после причины `technical`: повтор, упавший так же, отказы `class_unavailable` и `TASK_NOTHING_TO_RETRY`, откат повтора при отказе резерва и повтор вне дневного лимита (ответ владельца от 19.10.2026: день повтор не отклоняет и не урезает, а занятое им идёт в день) — тесты `@repo/billing` (`holds.charge.test.ts`, `holds.test.ts`), tRPC (`chat-db.test.ts`) и `pass-settlement.integration.test.ts`.
- Workflow GitHub Actions для стенда нет.

## Что стенд нашёл в продукте (17–18.10.2026; второй круг — по ревью 18.10.2026)

- Проход планировался с репозиторием вместе с веткой по умолчанию — строгие схемы `GitWorkspaceService` отвечали `BAD_REQUEST` на каждый ход (`candidateGitOf` теперь передаёт службе ссылку на репозиторий и ничего больше).
- Локальный исполнитель не записывал контейнер хода в `turn_assignments`: синхронизация предпросмотра каждого хода отказывала `no_turn` (теперь `TurnAttempt.created` записывает контейнер хода исполнителя `local`).
- Проверка сайта сразу после записи видела старый код: opcache PHP проверяет время файла раз в 2 с, сломанный выпуск считался установленным (теперь `deploy-step` проверяет сайт дважды, через 5 с после записи и ещё через 5 с, — `deployLimits.verifySettleMs`; то же у повторной проверки после возврата).
- Ход, встретивший занятый сайт, ставился снова только к сроку аренды — после выкладки диалог ждал до 10 минут. Теперь тот, кто отпускает сайт, будит ждущие ходы его диалогов: конец выпуска (`endWithoutInstall`, `endInstalled` — в той же транзакции, что снимает барьер и аренду) и конец прохода (`PassRunner`) пишут их задания в outbox (`enqueueSiteWaitingPasses`); собственный повтор хода — запасной, не позже 2 мин (первый круг поставил 30 с, но каждый повтор переводит задачу `queued → preparing → queued` и поднимает её в списке диалогов).
- Предпросмотр выполнял старый код до 2 с после синхронизации: opcache образа WordPress смотрит время файла раз в 2 с, и проверка браузера агента сразу после правки могла пройти на прежнем подвале. Теперь `preview-apache.conf` задаёт `opcache.revalidate_freq 0` (S3 открывает страницу, правит подвал и сразу проверяет его).
- Пауза проверки после записи — эвристика. Теперь `deploy-step` на шаге конфликтов читает opcache прода через плагин «Радити» (`GET /raditi/v1/code-cache`): пауза — время проверки файлов плюс 3 с, не меньше 5 с; после записи файлов и после возврата плагин сбрасывает записанный PHP из кеша (`POST /raditi/v1/code-cache`, `opcache_invalidate`); кеш, который не смотрит время и не даёт сбросить, — отказ до первой записи `code_cache`, после записи — возврат, после возврата — `unknown`. Доступ плагина задание получает теперь всегда, не только с планом БД: доступ хостинга, который у него и так есть, пишет любой файл сайта.

Файлы: `verify-release.mjs` — сборки, порядок запуска и уборка; `stand.mjs` и `stand.test.mjs` — параметры контейнеров, окружения процессов, конфигурация раннера и зеркала, ответы модели, процедуры tRPC в запросах страницы кабинета (`trpcProcedures`; `pnpm test:infra`); `services.mjs` — сервисы; `setup.mjs` — сайт, репозиторий, владелец, подключение, тариф, модель; `fake-model.mjs` — синтетический Z.ai с воротами раундов; `scenarios.mjs` — S1–S10; `isolation.mjs` — атаки из PHP, браузера агента и JavaScript страницы с контролем; `runtime.mjs` — процессы, HTTP, клиент web, строки `PASS` и `NOTE`.
