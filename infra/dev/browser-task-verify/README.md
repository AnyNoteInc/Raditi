# Стенд задачи в браузере: сайт без кода, вход клиента, новость с файлами

```sh
pnpm verify:browser-task                     # сборка копии дерева и образов, затем сценарии A–M
pnpm verify:browser-task -- --no-build       # те же сборки ещё раз; отказ, если дерево изменилось после них
pnpm verify:browser-task -- --keep           # оставить стенд поднятым после сценариев (и после провала) до Ctrl-C
pnpm verify:browser-task -- --only F,K       # только названные сценарии и те, без которых они не идут
pnpm verify:browser-task -- --web-dev        # web — `next dev` копии вместо `next build`
pnpm verify:browser-task -- --stream-only    # без кабинета: клиент действует только по потоку шлюза
```

Стенд проходит приёмку [плана 57](../../../docs/plan/57-browser-tasks.md) (§5) на этой машине — macOS, Docker Desktop, `runc` — только на одноразовых сервисах. Владелец добавляет сайт без доступа к файлам, ставит задачу с двумя картинками и PDF, агент (настоящий OpenCode CLI в песочнице на сценарной модели) работает в админке синтетического WordPress 7.x через инструменты `web_*`, клиент входит на сайт сам в том же облачном браузере — по потоку шлюза и в кабинете, — агент публикует новость один раз и проверяет её на сайте. Каждая строка `PASS` — факт, прочитанный из состояния продукта (база, лента, API процесса `browser`, поток шлюза, страница кабинета) или того, что держат WordPress, S3 и Docker. Строка `NOTE` — не проверка: то, что на этой машине не доказать, или режим, который проверяет меньше. В конце печатается таблица сценариев с числом проверок.

## Что поднимается

Всё одноразовое, со своим именем `raditi-browser-task-verify-<run>-…` и меткой `io.raditi.browser-task-verify=<run>`:

- PostgreSQL 17 (данные в памяти), Redis 8, SeaweedFS с бакетами `raditi-*`, OpenBao с mounts и политиками `infra/vault/bootstrap.mjs` и AppRole на процесс (`core`, `mcp`, `llm`, web) — сервисы стенда выпуска (`release-verify/services.mjs`).
- Синтетический сайт: MariaDB и WordPress 7.1.2 (редактор блоков) в своей сети, веб-сервер — в своей сети и в сети Docker по умолчанию, для стенда — ещё на опубликованном порту loopback. WordPress установлен по адресу `http://wp.raditi.test`: этого имени не знает никакой DNS, его знает только прокси выхода браузерной сессии — `BROWSER_LOCAL_SITES` процесса `browser` отображает это происхождение на адрес веб-сервера сайта в сети Docker по умолчанию (`<IP>:80`, Б11, только вне production): контейнер прокси выхода стоит в ней же. Через опубликованный порт Mac (`host.docker.internal`) путь ненадёжен — пересылка портов Docker Desktop теряет соединения, когда страница открывает много коротких (у локального маршрута прокси каждый запрос — своё соединение), и редактор блоков не загружался. Учётные записи: редактор `anna-redaktor` и автор `boris-avtor` (роль contributor) с паролями прогона — пароли уходят в WP-CLI через stdin, не в аргументы. Три must-use плагина стенда (`fixture/mu-plugins`), каждый за файлом-переключателем вне корня документов: `stand-cookie-tap.php` пишет значения cookie входа, которые ставит сайт, в `/var/stand/cookies` (стенд ищет их там, где их быть не должно), `stand-upload-limit.php` — отказ сайта в PDF больше 20 КБ (сценарий I), `stand-publish-delay.php` — одна публикация через REST задерживается на 30 с (сценарий J).
- Процессы платформы из сборки приватной копии дерева (`$TMPDIR/raditi-browser-task-verify-build`, как у `verify:release`): `llm`, `browser` (облачный браузер, Б10), `mcp` (семейство `web`), `preview` (шлюз трансляции на `BROWSER_STREAM_PORT`, Б12), `core` — `node dist/main.js`, каждый своим процессом, `TURN_EXECUTOR=local` под `runc`; web — `next build` (standalone) или `next dev` копии (`--web-dev`). У `core` нет ни `GITEA_*`, ни `GIT_*`, ни предпросмотров: задаче в браузере git не нужен (Б7). `NODE_ENV=production` у всех: ни один процесс не ищет `.env`.
- Образы этого дерева под своими именами, по digest: песочница хода, её шлюз и сторож (`infra/sandbox/Dockerfile`), прокси выхода `client-egress`, инструменты и браузер предпросмотров (`infra/preview/Dockerfile`) — три контейнера браузерной сессии.
- Синтетический Z.ai (`model.mjs`) в процессе стенда за TLS сертификатом стенда; аккаунт плана импортирует настоящая команда оператора `subscriptions:login`, ставки и курс кредита пишет `billing:rates`. Ответы модели — программы `programs.mjs`: программа хода читает наблюдения так, как их читает модель (текст дерева доступности, элементы по роли и имени), и действует по найденным там ссылкам; на каждый запрос CLI она прогоняется заново по уже сделанным вызовам и ответам и отдаёт следующий вызов или итог хода. Все запросы к модели хранятся целиком — в них стенд ищет пароли и cookie.
- Кабинет — Chromium Playwright 1.63 копии (`~/Library/Caches/ms-playwright`) с cookie сессии владельца, окно 1440×1000 — шире `lg` (1200 px): только там браузер задачи открывается сам и у панели есть «Скрыть панель» ([план 59](../../../docs/plan/59-dialog-tools-panel.md), И3, И14). «Новый диалог», страница диалога — сначала один чат, — «+» и меню «Инструменты», панель «Инструменты диалога» на вкладке «Браузер», её canvas и её собственный WebSocket (`cabinet.mjs`). Рядом стенд считает вызовы tRPC страницы (по процедурам), ответы её ленты (`task.feed`) и — сценарием страницы, который идёт раньше её собственных, — каждое появление панели и каждый заход фокуса в неё.

После `kill -9` стенда уборки нет; его ресурсы находятся по метке прогона (`<run>` — восемь знаков из имён контейнеров), сессии и песочницы — по сайту прогона:

```sh

docker volume ls -q --filter label=io.raditi.browser-task-verify=<run> | xargs docker volume rm
docker network ls -q --filter label=io.raditi.browser-task-verify=<run> | xargs docker network rm
docker ps -aq --filter label=io.raditi.browser.site=<siteId> | xargs docker rm -fv
docker network ls -q --filter label=io.raditi.browser.site=<siteId> | xargs docker network rm
rm -rf "$TMPDIR"/raditi-browser-task-verify-run-<run>-*
```

## Что нужно

Docker Desktop с хранилищем образов containerd (ссылки на собранные образы — по digest), Node 26.10, pnpm, `git`, `rsync`, `openssl` и уже загруженные образы (стенд ничего не тянет): `wordpress:7.1.2-php8.3-apache`, `mariadb:11.4.13`, `wordpress:cli-php8.3`, `chrislusf/seaweedfs:4.47`, `postgres:17.11-alpine3.24`, `redis:8.10.2-alpine`, `ghcr.io/openbao/openbao:2.7.0` (digest — в `release-verify/stand.mjs` и `billing-verify/stand.mjs`) и базовые образы `infra/sandbox/Dockerfile` и `infra/preview/Dockerfile`; браузеры Playwright 1.63. Корневой `.env`, dev-инфраструктура, настоящие модели и ключи не используются. Одновременно с другими стендами Docker и без `pnpm dev`/`pnpm e2e` стенд не запускается: любой другой `core` с `TURN_EXECUTOR=local` на том же Docker видит песочницы ходов этого стенда (метка владельца у песочниц одна на все развёртывания) и его сборщик (`TurnReconciler`, раз в 30 с) удаляет их — в его базе нет аренды этого сайта; ход тогда кончается `SANDBOX_COMMAND_FAILED` и `destroy_failed` (замечено 23.10.2026, когда параллельно шли чужие стенды). Пока идёт прогон, Mac не должен засыпать — `caffeinate -i -s pnpm verify:browser-task`.

`BROWSER_TASK_VERIFY_STALE_COPY=allow` вместе с `--no-build` пускает прогон на копии, собранной из другого состояния дерева (работа над самим стендом, пока дерево меняется): такой прогон печатает `NOTE` и ничего не доказывает о дереве.

## Что не проверено

- Linux и gVisor (`runsc`): стенд идёт только на Docker Desktop; путь `runsc` облачного браузера и правила хоста проверяют тесты `@repo/sandbox-providers` и шаги `preview.yml`.
- Настоящая модель: ходы — программы сценарной модели; что настоящий GLM сделает из таких наблюдений, стенд не говорит.
- Настоящий сайт: WordPress по `http://` под локальным именем, без TLS, CDN и плагинов безопасности; Classic Editor и сайт на русском языке админки — не в сценариях (их называет справка агента).
- Команды, которые агент запускает в песочнице: локальный исполнитель их не журналирует, поэтому «в песочнице не было git» доказывают пустые SHA ходов и манифесты снимков без части `git`.
- Узкий экран (ниже `lg`): кабинет стенда — только 1440×1000. Что запуск браузера там лишь ставит точку на «+», область инструмента вместо диалога и «К диалогу» ([план 59](../../../docs/plan/59-dialog-tools-panel.md), И3, И14) проверяют тесты компонентов web и `test:site`.
- Срок простоя и жёсткий срок сессии (30 мин и 4 ч), потеря процесса `browser`, размер окна браузера из меню, диалоги JavaScript и окно выбора файла в ручном режиме — тесты `apps/browser`, `@repo/browser-providers` и компонентов web; сборщик неотправленных вложений — тесты `core` и `@repo/db` (на базе — с подделкой S3).
- Список сохранённого в запросе хода (новый сеанс агента после неуспешного хода): сценария с новым сеансом после неуспешного хода у стенда нет, и сценарная модель списка не читает — что настоящая модель продолжит сохранённое, а не создаст объект заново, стенд не говорит; запрос проверяют тесты планировщика `core`.
- Workflow GitHub Actions для стенда нет.
