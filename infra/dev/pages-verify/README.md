# Стенд `pnpm verify:pages`

Опубликованные страницы со стороны зрителя ([план 69](../../../docs/plan/69-pages.md), §7, срез 69.10).

Что запускается:
- одноразовая PostgreSQL 17; миграции стенд отдаёт `psql` в контейнере по порядку, без Prisma: её настройки читают
  корневой `.env`;
- настоящий слушатель страниц `apps/preview` из сборки (`PAGES_BASE_DOMAIN=pages.localhost`);
- Chromium из Playwright этого дерева (`packages/browser-providers`);
- маленький «другой сайт» стенда на loopback, у него два origin: `127.0.0.1` и `neighbour.pages.localhost`. Он
  считает каждый запрос, который страница смогла сделать.

Страницы стенд пишет теми же функциями `@repo/db`, которые вызывают `core` и кабинет: `reservePagePublication`,
`applyPageVersion`, `setPagePassword`, `takeDownPage`, `restorePage`. Все страницы синтетические.

```
pnpm verify:pages [-- --no-build] [--keep]
```

- `--no-build` — не собирать `apps/preview`, взять текущий `dist`.
- `--keep` — оставить контейнер PostgreSQL и каталог с логом `preview.log`.

Нужен загруженный образ PostgreSQL стенда выпуска (`docker pull` — в `infra/dev/release-verify/README.md`).
`.env`, dev-инфраструктура, модель и ключи не используются.

## Сценарии

- **A. Путь страницы.**
  - Адрес — свой поддомен, метка — 26 знаков base32 (128 бит).
  - Заголовки ответа — константы `@repo/domain` байт в байт.
  - Новая версия — по тому же адресу, номер вырос. Содержимое хранится только у текущей версии.
  - `/v1`, `/v2`, `/v/` и любой другой путь — 404, `robots.txt` запрещает индексацию, POST и другие методы — 405.
  - Снятие — 410 без содержимого, «Вернуть на публикацию» возвращает страницу.
  - Снятую оператором страницу клиент не вернёт.
  - Несуществующая страница, вторая метка, корень `pages.localhost` и чужой домен — 404.
- **B. Пароль.**
  - Форма вместо содержимого; неверный пароль ничего не открывает.
  - Верный пароль ставит cookie: только этого хоста, `HttpOnly`, `Secure`.
  - Cookie переживает новую версию и перестаёт действовать после смены пароля.
  - Cookie одной страницы не открывает другую страницу с паролем. Контроль: собственная cookie её открывает.
  - Попытки одного адреса ограничены, ответ — с `Retry-After`.
- **C. Защиты в Chromium.**
  - Скрипт страницы не читает cookie с `Domain=pages.localhost` — так стояла бы cookie с `Domain=raditi.ru` — и не
    видит хранилища. Контроль: обычная страница соседнего поддомена эту cookie читает.
  - `fetch`, XHR и WebSocket отклоняются, политика сообщает о нарушении.
  - Ни один запрос не дошёл до другого сайта. Контроль: тот же запрос со страницы соседнего origin без политики
    доходит.
  - Форма страницу не уводит.
  - Страница не открывается во фрейме другого сайта: стенд ждёт, пока фрейм загрузится или получит отказ. Контроль:
    обычная страница соседнего origin в том же фрейме открывается.

## Что не проверено

Стенд печатает это строкой `NOTE`:
- путь агента на OpenCode и синтетическом Z.ai: `page_publish`, `doc_*`, отказы публикации (ключ хода, значение
  переменной клиента, форма пароля наружу, JWT, размер);
- «Скачать .md» целиком;
- страница для чтения документа и «Опубликовать по ссылке» — пакет `@repo/doc-render` (срез 69.5), он ждёт слияния
  плана 67;
- хост кабинета: на нём нет страницы, а хост страницы не отдаёт ни кабинет, ни `/v/` web;
- что кабинет не ставит cookie с `Domain=raditi.ru`;
- проверка `Origin`, когда со страницы переходят на изменяющий маршрут кабинета;
- браузер задачи: открывает страницу и не открывает корень `pages.raditi.ru`;
- оба сценария постановки в dev.

Эти места держат модульные и интеграционные тесты срезов 69.2–69.9.

Срока у страницы нет (Ст14), поэтому и сдвигать часы стенду нечего.
