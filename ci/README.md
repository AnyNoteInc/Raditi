# Обязательный пайплайн сайта

Каталог синхронизируется в репозиторий `platform/ci` Gitea платформы (spec §10). Файлы из `.gitea/scoped_workflows/` Gitea 1.27 выполняет в каждом репозитории сайта, в его собственном контексте: его коммит, его секреты и переменные Actions. В самих репозиториях сайтов файлов CI нет.

| Файл | Когда запускается | Что делает сейчас |
| --- | --- | --- |
| `check.yml` | pull request | Подмена: печатает ветки и коммит, ставит статус `platform/ci: check / check (pull_request)` |
| `deploy.yml` | push тега выпуска `v*` (кроме `v0.0.0`); `workflow_dispatch` по `refs/tags/<тег>` — повтор выпуска («только возврат», Р31) | Команда `deploy-step` образа orchestrator: `match` сверяет секрет `RADITI_DEPLOY_WRAP` с тегом и коммитом запуска, `run` вскрывает обёртку и выкладывает через API выпуска — конфликты, бэкап, файлы по SFTP/FTP(S), записи через плагин, проверка сайта, возврат ([план 53](../docs/plan/53-chat-preview-release.md), Р28–Р31) |

`check.yml` — результат спайка N18, а не готовая проверка: настоящие проверки (PHP lint, сборка, запрещённые пути и секреты в диффе) — P8. Пайплайн выкладки по push в `main` из спайка живёт только в стенде (`infra/dev/pipeline-verify/workflows/deploy-spike.yml`). Файл с пометкой `SPIKE` в `platform/ci` настоящей Gitea не синхронизируется, если его шаги передают токен Vault аргументом процесса или ходят в Vault без TLS (так делает подмена спайка: busybox `wget` иначе не умеет). Что проверено на настоящей Gitea 1.27.3 и что разошлось со spec §10 — [отчёт](../docs/plan/34-gitea-pipeline-spike.md); выкладка по тегу — стенд `pnpm verify:pipeline` (вторая Gitea, `WORKFLOW_DIRS`).

Что в этих файлах уже не подмена и должно сохраниться:

- `if: gitea.repository_owner == 'sites'` у каждого задания. Организация `sites` может зарегистрировать источником только собственный репозиторий, поэтому `platform/ci` регистрируется на весь экземпляр и запускается в каждом репозитории Gitea, включая себя. У выкладки к нему добавлено `startsWith(gitea.ref, 'refs/tags/v') && gitea.ref_name != 'v0.0.0'`: тег импорта уже установлен, а повтор запускается только по ссылке тега.
- `permissions: contents: read`. Без этого токен задания по умолчанию пишет в репозиторий сайта.
- `concurrency` с `cancel-in-progress: false`: одна выкладка сайта за раз.
- `timeout-minutes: 150` у выкладки: дальше всех собственных сроков команды (час записи, 20 минут возврата, 25 минут на то, чтобы `core` принял конец), чтобы раннер не оборвал возврат.
- Возврат делает сама команда `deploy-step` после любого сбоя за первой записью, по бэкапу своей попытки и на своём соединении с хостингом; в пайплайне спайка тот же смысл держал шаг `rollback` с условием `(failure() || cancelled()) && steps.backup.outcome == 'success'` — шаг с одним `failure()` при отмене пропускается.
- Текст коммита попадает в шаг только переменной окружения, не подстановкой в скрипт.
- Адрес Vault (`RADITI_VAULT_ADDR`), адрес API выпуска (`RADITI_RELEASE_API_URL`), CA (`NODE_EXTRA_CA_CERTS`) и `APP_ENV` задаёт конфигурация раннера `deploy` (`runner.envs`), а образ задания — его метка, а не переменная, секрет или файл репозитория сайта: то, что лежит в репозитории, не решает, куда уйдёт обёртка и чем её вскроют.
- Остальное окружение команды `deploy-step` задаёт сам `deploy.yml`: сведения о запуске из контекста Gitea — `RADITI_RUN_EVENT`, `RADITI_RUN_REF`, `RADITI_RUN_REF_NAME`, `RADITI_RUN_SHA`, `RADITI_RUN_SERVER`, `RADITI_RUN_REPOSITORY`, — токен задания `RADITI_JOB_TOKEN` (`gitea.token`: только чтение файлов коммита выпуска) и секрет репозитория `RADITI_DEPLOY_WRAP`. Это переменные задания, не сервисов платформы: в `.env.example` и `turbo.json` их нет.
- Из прочитанного в Vault и полученного от API выпуска в лог задания не пишется ничего — только постоянные строки `deploy-step:` с шагом, состоянием, кодом и числами.
- Actions из сети не берутся. Сейчас в файлах нет ни одного `uses:`: actions из своей Gitea (`platform/actions/*`, зеркало `actions/checkout`, `DEFAULT_ACTIONS_URL = self` — spec §10) спайк не проверял, они появятся вместе с настоящими шагами (N25, P9). До тех пор контракт запрещает любой `uses:`.

Проверка: `pnpm verify:pipeline` ([стенд](../infra/dev/pipeline-verify/README.md)) и `pnpm test:infra` (контракт этих файлов — `infra/dev/pipeline-verify/stand.test.mjs`).
