# Обязательный пайплайн сайта

Каталог синхронизируется в репозиторий `platform/ci` Gitea платформы (spec §10). Файлы из `.gitea/scoped_workflows/` Gitea 1.27 выполняет в каждом репозитории сайта, в его собственном контексте: его коммит, его секреты и переменные Actions. В самих репозиториях сайтов файлов CI нет.

| Файл | Когда запускается | Что делает сейчас |
| --- | --- | --- |
| `check.yml` | pull request | Подмена: печатает ветки и коммит, ставит статус `platform/ci: check / check (pull_request)` |
| `deploy.yml` | push в `main` | Подмена: `vault-login` → `backup` → `deploy` → `verify` → `rollback` → `vault-logout` над файлом-меткой на томе раннера `deploy` |

Это результат спайка N18, а не готовый пайплайн. Файл с пометкой `SPIKE` в `platform/ci` настоящей Gitea не синхронизируется: подменные шаги передают токен Vault аргументом `wget` (busybox иначе не умеет) и ходят в Vault без TLS. Настоящий `vault-login` должен отдавать токен клиенту файлом или через stdin и требовать `https:` с CA Vault (P9). Настоящие шаги (drift, архив в S3, rsync или git-ftp, проверка страниц по HTTP) — P8–P10; способ выкладки ждёт ответа владельца о подключении сайта. Что проверено на настоящей Gitea 1.27.3 и что разошлось со spec §10 — [отчёт](../docs/plan/34-gitea-pipeline-spike.md).

Что в этих файлах уже не подмена и должно сохраниться:

- `if: gitea.repository_owner == 'sites'` у каждого задания. Организация `sites` может зарегистрировать источником только собственный репозиторий, поэтому `platform/ci` регистрируется на весь экземпляр и запускается в каждом репозитории Gitea, включая себя.
- `permissions: contents: read`. Без этого токен задания по умолчанию пишет в репозиторий сайта.
- `concurrency` с `cancel-in-progress: false`: одна выкладка сайта за раз.
- `rollback` с условием `(failure() || cancelled()) && steps.backup.outcome == 'success'`: отменённую выкладку тоже нужно вернуть, а шаг с одним `failure()` при отмене пропускается. Бэкап назван по номеру запуска и попытки: повторный запуск не должен восстановить чужой бэкап.
- Текст коммита попадает в шаг только переменной окружения, не подстановкой в скрипт.
- Адрес Vault задаёт конфигурация раннера `deploy` (`runner.envs`, переменная `RADITI_VAULT_ADDR`), а не переменная или секрет репозитория сайта: то, что лежит в репозитории, не решает, куда уйдёт обёртка токена.
- Из прочитанного в Vault в лог задания и в лог на томе сайта не пишется ничего — только отметка, что доступ прочитан.
- Actions из сети не берутся. Сейчас в файлах нет ни одного `uses:`: actions из своей Gitea (`platform/actions/*`, зеркало `actions/checkout`, `DEFAULT_ACTIONS_URL = self` — spec §10) спайк не проверял, они появятся вместе с настоящими шагами (N25, P9). До тех пор контракт запрещает любой `uses:`.

Проверка: `pnpm verify:pipeline` ([стенд](../infra/dev/pipeline-verify/README.md)) и `pnpm test:infra` (контракт этих файлов — `infra/dev/pipeline-verify/stand.test.mjs`).
