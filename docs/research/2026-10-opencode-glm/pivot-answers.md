## Что это значит для плана

- **П9, ключ плана.** Ключ остаётся в корневом `.env` как `ZAI_API_KEY`: это тестовый локальный ключ. Предусловие G0 «владелец убирает ключ из `.env`» снято. Скрипты и стенды могут брать ключ из окружения, в том числе загружая корневой `.env` (`node --env-file`, как уже делают `verify:runner` и `verify:snapshots`). Агентам читать `.env` инструментом чтения по-прежнему нельзя (запрет настроек проекта) и незачем: значение ключа не печатается, не попадает в argv, логи, записи и репозиторий. Решение 16 («ключ только в одноразовом OpenBao стенда, `--key-file`») упрощается: живой режим берёт `ZAI_API_KEY` из окружения; в одноразовый OpenBao стенда роль `llm` получает его прежним путём импорта. Решение 17 («ключ плана вне роли `llm` не используется») остаётся для продуктового пути: в песочницу ключ не попадает (правило 5).
- **Одинаковые переменные окружения у всех образов (допущение MVP).** У сервисов платформы — web, `core`, `mcp`, `llm`, раннер — один набор переменных окружения; раздельные каталоги секретов по ролям на стадии MVP не обязательны. Песочница в это не входит: в неё по-прежнему попадают только ключ хода и токен MCP. В плане перехода это снимает требование «`pnpm test:infra` проверяет, что `.env.example` и `turbo.json` не называют ни одной `ZAI_*`»: `ZAI_API_KEY` объявляется в `.env.example` (без значения) и в `turbo.json`. Переделка `infra/app` под один файл окружения — отдельная задача, в переход не входит.
- **П2, узел выхода.** Для OpenCode с GLM на Z.ai узел выхода за рубежом не нужен: роль `llm` ходит к `api.z.ai` напрямую. Возможность идти через узел выхода остаётся в коде для других провайдеров. Решение 10 меняется: путь к провайдеру выбирается конфигурацией роли (прокси задан — через него, не задан — напрямую), без имён бэкендов в коде роли; точный список хостов и запросов остаётся в описании бэкенда. В G4 это шов «прямой путь», в стендах `zai-coding` идёт к фейку напрямую.
- **П1, получатель данных.** Сведения ищутся в открытых источниках (условия и политика Z.ai, условия GLM Coding Plan); результат — `docs/research/2026-10-opencode-glm/zai-terms.md`. Вывод о 152-ФЗ остаётся за юристом.
- **П11.** Риск блокировки аккаунта за работу плана через шлюз и расход квоты на проверки приняты.
- **Отправка ветки.** Согласие дано: черновой PR после G3 и полный прогон workflow в G7.
- **Остальные вопросы (П3–П8, П10, П12–П14)** — приняты значения по умолчанию из раздела 7 плана. П14 с поправкой на П9: ключ dev получает из `.env`; класс данных вне production остаётся `synthetic`.
