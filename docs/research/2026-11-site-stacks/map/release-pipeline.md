# Выпуск `/release` и откат: что нейтрально к стеку, что требует плагина

Клон: `raditi-stacks`, коммит `c811abf1`. Пути — от его корня. Код не менялся. Прочитано целиком: `deploy-step/deploy.ts`, `content.ts`, `site-check.ts`, `command.ts`, `cli.ts`, `tree-source.ts`, `releases/release-skill.ts`, `undo-planner.ts`, `release-api/release-api.service.ts`, `infra/wordpress/raditi-content.php`, адаптеры WordPress и Битрикса, порты домена, spec §10, Р10–Р35 и договоры Д, Е, Ж плана 53.

## 0. Главное

1. **Выпуск из одних файлов работает без плагина целиком**: бэкап, запись, проверка, возврат, «только возврат», «Отменить выпуск». Ни одной ветки по имени стека в `apps/core/src/releases`, `release-api`, `deploy-step` нет. Это проверено стендом `verify:pipeline` (`content: null`, настоящий `deploy-step` по SFTP, возврат сломавшего сайт выпуска) и прогоном 27.10.2026 на живом хостинге по FTP (`v0.0.1`, затем отмена `v0.0.2`).
2. **Сегодня это единственный путь выпуска и для WordPress.** Плагин на прод не ставит никто, доступ `wp` продукт не пишет, а `MCP_CONTENT_PROFILE` в production разрешён только `off` (`apps/mcp/src/config/config.ts:197-199`). План БД на проде родиться не может. Весь протокол плагина работает только на стендах и в предпросмотре.
3. **Без плагина выпуск не отказывает, а молчит об opcache.** При `revalidate_freq` больше 10 с или `validate_timestamps=0` обе проверки идут на старом коде, исход — `installed`, сайт ломается позже, и отката уже нет. С плагином этот случай — честный отказ `code_cache`. Закрывается 60 строками нейтрального PHP, их можно загружать на время попытки.
4. **Плагин проверке сайта не нужен.** Проверка — обычный HTTP GET. Плагин нужен только для opcache, `runtime` и плана БД.
5. **Общий коннектор возможен: около половины плагина нейтральна по смыслу** (716 из 1420 строк). Общий исходник, отдельная сборка на стек. Записи объектов остаются свои у каждой CMS. Запросы сейчас не подписаны: это пароль приложения WordPress в Basic и заголовок.
6. **Главный риск новых стеков не в выпуске, а в том, что нейтральный по коду выпуск не видит кешей CMS и шаблонов в базе.** Шага сброса кеша CMS нет, и `HostingSession` не умеет листинг. У MODX шаблоны, чанки и сниппеты в базе, поэтому файловый выпуск там почти пуст.

## 4. Плагин `infra/wordpress/raditi-content.php`

### Как попадает на сайт

В продукте — **никак**.

- Мастер пишет только `ssh`, `ftp`, `db`. `activateSite` зовётся с видом источника файлов (`apps/core/src/site-provisioning/stage-store.ts:464`), а не с `wp`.
- В `apps/web/src`, `packages/trpc/src` и `site-provisioning` строка `wp` есть только в списке показа (`packages/trpc/src/routers/project.ts:121`).
- Кладут файл стенды: `infra/dev/release-verify/setup.mjs:63-64`, `infra/dev/docker-compose.yml:195`.
- В предпросмотр он идёт как `generatedFiles` (`wordpress-preview.ts:44-48`), встроенный скриптом `packages/site-adapters/scripts/embed-wordpress-files.mjs`.
- Обновления нет: номер версии `2` «ещё не выпускался» (spec §10), старый плагин даёт `plugin_outdated` и текст «Напишите нам».

### Установка и привязка (только стенд)

`infra/dev/site-verify/connect-local.mjs`, через WP-CLI:

1. Берётся первый администратор, создаётся пароль приложения (`:252-268`).
2. Секрет `{v, origin, username, applicationPassword}` пишется в `kv/sites/<id>/wp`, затем строка `credential_refs` (`:542-556`).
3. Только после этого опция `raditi_content_site_id` (`:30`, `bind` на `:231`), чтобы оборванный запуск не оставил привязку без доступа.
4. Сброс ограды при перепривязке (`:523-527`).

### Чем подписаны запросы

**Не подписаны.**

- HTTP Basic паролем приложения и заголовок `x-raditi-site` (`wordpress-content.ts:227,561-565`), поверх TLS.
- Проверка: `application_password_did_authenticate`, совпадение заголовка с опцией, право `edit_posts` или `edit_pages` (`raditi-content.php:12-18`).
- `requestHash` считает вызывающий (`deploy-step/content.ts:191-203,300-312`); плагин проверяет формат и повторяет его в квитанции, не пересчитывает. Свой `digest` плагин считает от тела (`:328`).
- Ответ сверяется по хешу полей (`deploy.ts:397-401`), чтобы фильтр сайта не подменил текст.

**Режимы.** `edit` — текст агента, через фильтр, разметка не должна пострадать (только предпросмотр). `release` — точные байты, которые фильтр оставляет как есть, даже у `unfiltered_html`, потому что предпросмотр исполнял код агента (`:373-377`). `restore` — точные байты, бывшие на сайте; без `unfiltered_html` только то, что фильтр не меняет (`:369-372`).

**Где живёт правда о новых записях.** Соответствие «номер предпросмотра → номер прода» — только на проде: квитанция и мета `_raditi_create` (план 53, Е8). Поэтому `deploy-step` не вызывает `forgetOperation`, вызывает её только обслуживание `mcp` (`mcp-content-maintenance.ts:176`), и квитанции выпусков копятся в `wp_options`.

**Требование к базе.** Таблицы должны быть InnoDB, иначе `unavailable` (`:532-539`): контракт порта требует атомарно сравнить, записать и сохранить квитанцию (`published-content.ts:133`).

**Побочный эффект mu-plugin.** Файл загружается на каждом запросе сайта: ошибка разбора в нём кладёт весь сайт.

## 5. Проверка сайта и opcache

**Проверке сайта плагин не нужен.** `checkSite` (`site-check.ts:57-116`) — GET через закреплённый транспорт: каждая страница плана должна дойти до 2xx (не более 3 редиректов внутри сайта) и не содержать маркеров сбоя; две попытки, предел 180 с. Плагин не участвует. Запись `VerifyPlan.pages` говорит «2xx or 3xx», а задание требует итоговый 2xx.

**opcache для прохождения пути не нужен, для честности результата нужен.**

| Состояние кеша | С плагином | Без плагина |
| --- | --- | --- |
| выключен | пауза 5 с | пауза 5 с |
| `revalidate_freq` до 10 с | сброс или `N+3` с | верно по случайности |
| `revalidate_freq` больше 10 с | сброс или `N+3` с (до 120 с) | **обе проверки на старом коде** |
| `validate_timestamps=0` | сброс, иначе отказ `code_cache` до записи (`deploy.ts:807`) | **`installed`, сайт на старом коде неопределённо долго** |

Стенд R12 такой сбой измерил: проверка сразу после записи прошла на старом подвале, а сайт сломался через 2 с (`deploy.ts:145-151`). Для Битрикса есть форумное свидетельство, что его проверка системы требует `opcache.revalidate_freq` в `off`, поэтому там риск может быть меньше; на общем хостинге его определить нельзя.

**Эфемерная проба.** Код уже нейтрален: `raditi-content.php:433-487`, 55 строк без обращений к базе и WordPress, кроме `ABSPATH` и класса ответа. `deploy-step` пишет доступ к файлам и может положить пробу сам.

- Файл со случайным именем без точки в начале: `raditi-<32 hex>.php`. Точечные имена закрывает типовая конфигурация nginx.
- Токен на попытку, в ответе только версия PHP, расширения и настройки кеша.
- Удаление на любом выходе, включая возврат; отказ пробы даёт текущий `defaultPlan`.
- Вход для `SiteCodeCacheGateway` уже есть: `DeployContext.codeCache` (`deploy.ts:299-302`). Менять придётся условие `access.content === null` (`:227`).
- Новых прав нет: комментарий `release-api.service.ts:402-405` уже признаёт, что доступ к хостингу шире плагина.
- `runtime` для предпросмотра тем же приёмом может делать `core`: у него есть доступ к файлам.

Если PHP на сайте выполнить нельзя (запрет на уровне сервера), остаётся поднять паузу без плагина до 65 с: это закрывает типовые 60 с, но не `validate_timestamps=0`.

## 6. Общий однофайловый коннектор

**Да, с уточнением: общий исходник и отдельная сборка на стек, а не один файл со всеми драйверами.** Сейчас файл 92 КиБ; пять драйверов упрутся в предел `generatedFiles` 192 КиБ (`packages/domain/src/preview/recipe.ts:123`), и на сайте лежал бы чужой код. Сборка конкатенацией `core.php + driver-<стек>.php` повторяет уже работающий `embed-wordpress-files.mjs`.

### Что общее и что своё

| Общее | Своё у CMS |
| --- | --- |
| кадры хеша, `callId`, `digest`, срок, ограда, квитанции, `reconcile`, `forget`, `fence` | таблицы записей, поля, статусы |
| режимы `edit`, `release`, `restore` как правило | **фильтр**: `wp_kses_post` и `sanitize_option` (`:100-102,934`) |
| opcache, `runtime` | адрес: `sanitize_title`, `wp_unique_post_slug` (`:668-681`) |
| словарь таблиц и `information_schema` | права: `current_user_can` |
| разбор запроса, ответы | сброс кеша: `clean_post_cache`, `wp_cache_delete` |
| | корзина и зависимые: `_wp_trash_meta_*`, меню, комментарии (`:782-790,808-852`) |
| | доступ к базе: `$wpdb->dbh` (`:35-39`) |
| | настройки: `wp_options` против `b_option`, `oc_setting` |

### Решения, которые придётся принять

1. **Точка входа вне CMS.** Отдельный PHP-файл с HMAC вместо mu-plugin. Плюсы: ошибка разбора не кладёт сайт, не нужен пользователь CMS, снимается вопрос `unfiltered_html` (spec §20, O43), а откат записей не зависит от здоровья CMS. Сейчас плагин отвечает, «только когда код сайта снова работает» (`deploy.ts:84-85`).
2. **Подпись.** HMAC над методом, маршрутом, хешем тела и одноразовым числом. Ключ — в Vault и в файле на сайте, закрытом через `protectedPaths`. Порт это допускает: `accessSchema` своя у адаптера (`site-adapter.ts:158-164`). Нужны новый вид доступа и правка политик (§2).
3. **Своя таблица вместо `wp_options`.** `<префикс>raditi_state`, InnoDB, для ограды и квитанций. Создаётся один раз.
4. **Загрузка CMS.** Протокол работает без неё, а драйвер поднимает CMS там, где сырой SQL ломает инварианты. Без загрузки CMS нет её фильтра, а он — защита от хранимого XSS из предпросмотра (`:373-377`).
5. **Доступ к базе.** Прямого соединения не будет: на тестовом хостинге MySQL снаружи закрыт и SSH нет (spec §20, «Прогон 27.10.2026»). Значит, PHP на сайте — единственный путь записей.

### Ловушки переноса

- `strlen` в кадрах (`:59`): при `mbstring.func_overload=2` вернёт знаки, а не байты, и хеши разойдутся. Настройка устарела с PHP 7.2, но встречается на старом Битриксе. Нужен `mb_strlen($v, '8bit')`.
- База не в UTF-8: кадры считаются в UTF-8 у платформы, значит, коннектор обязан перекодировать до хеша.
- Движок: OpenCart 3.0.x создаёт почти все таблицы как MyISAM (проверено, кроме `oc_cart`), транзакции там нет.
- PHP: плагин требует PHP 7.0 (`??`, `Throwable`). Для отдельного файла ошибка разбора означает отказ коннектора, а не падение сайта.
- `DB_CREATED_ID_MAX` 9 999 999 999 больше верхней границы `INT` (2 147 483 647). Номера от базы 1 000 000 000 в `INT` влезают, но запас меньше, чем обещает схема.
- `dbPlanLimits.valueBytes` 32 КиБ мал для шаблонов MODX и описаний товаров.

## 7. Медиа и `addOnlyPaths`

`SiteAdapter.mediaRules()` даёт `addOnlyPaths` (до 8 папок), расширения с сигнатурами, запрещённые части имени и предел файла (`wordpress-working-set.ts:53-76`, схема `candidate.ts:291`; предел 8 МиБ, `git/media.ts:10`). Сквозной путь:

| Этап | Что проверяется | Ссылка |
| --- | --- | --- |
| Песочница | папки не попадают, даже если набор их называет: они только растут | `git-workspace.service.ts:1799-1801` |
| Агенту | инструкция называет папки и типы | `turn-instructions.ts`, `filesSection` |
| Публикация | только добавление, имя и сигнатура | `git-workspace.service.ts:2041`, `git/publication.ts:252` |
| Приоритет | побеждают `protectedPaths`, кроме шаблонов `**/` | `publication.ts:83-88`, `policies/diff-paths.ts:71` |
| Готовность | вторая линия правила 6 | `release-skill.ts:680-695` |
| Задание | замена или удаление под папкой — `source_mismatch` | `deploy.ts:574-578` |
| Откат после сбоя | добавленный файл удаляется | `deploy.ts:1677-1681` |
| Отмена | медиа остаются | `undo-planner.ts:238-242`, `release-skill.ts:1159-1174` |

Механика нейтральна, новому стеку нужны только значения: папка (Битрикс `upload/raditi/`, Joomla `images/raditi/`, MODX `assets/raditi/`, OpenCart `image/catalog/raditi/`) и `refusedNameParts`. Если адаптер бросает `NOT_IMPLEMENTED`, медиа закрыты, и инструкция хода говорит класть файлы «где сайт их держит» (`turn-instructions.ts`, `inboxSection`), что противоречит выпуску.

## 8. `agentWorkingSet` и шаблоны в базе

**Откуда режется.** Каждый ход из дерева текущей базы публикации: `git ls-tree -r` по `expectedBaseSha`, файл входит, когда его принимает `include` и не принимает `exclude` (`git/working-set.ts:41-44`, `git-workspace.service.ts:1775-1820`). Ссылка или подмодуль в наборе — отказ хода (`:1806`). Предел — `maxBytes`, до 256 МиБ. Срез становится детерминированным корневым коммитом `sandboxBaseSha`; патч агента накладывается на полное дерево, и изменения вне набора, кроме новых медиа, отклоняются.

**Запасной путь в полное дерево — только на словах.** Для стека без набора бандл ограничен 64 МиБ (`publication.ts:21`, `git-workspace.service.ts:1870,1880`). Если ядро в репозитории, ход не стартует. Битрикс-заглушка уходит от этого, исключая `bitrix/` из импорта (`bitrix.ts:18,43`), но тогда предпросмотру нечем работать: `no_core` (`preview-builder.ts:621`). Рабочий набор фактически обязателен.

**Что значит для CMS с шаблонами в базе.** Выпуск и песочница видят только дерево git. Всё, что в базе, недоступно агенту как файл.

| CMS | Где шаблоны | Что видит рабочий набор |
| --- | --- | --- |
| Битрикс | файлы (`local/templates`, старые сайты — `bitrix/templates`), контент в инфоблоках и в файлах корня | много, но заглушка закрывает весь `bitrix/` (`bitrix.ts:18,21`) |
| Joomla | файлы, переопределения в `templates/<имя>/html`; модули и настройки стиля в базе | хорошо для вёрстки |
| OpenCart | файлы Twig, но база и кеш могут перекрывать их (см. §9) | хорошо, с риском «правка без эффекта» |
| MODX | **`site_templates`, `site_htmlsnippets`, `site_snippets`** (проверено по схеме 2.x); файлами только при `static=1` | почти ничего: `assets/` и своё в `core/components/` |

### Варианты для MODX и подобных

| Вариант | Плюс | Минус |
| --- | --- | --- |
| Задача в браузере (план 57) | уже есть, без плагина | мимо предпросмотра и отмены, нужна политика менеджера MODX |
| Новый вид операции `element_update` | предпросмотр и отмена работают | нужны коннектор и инструмент; значение — код, поэтому `protectedPaths`, gitleaks и `php_lint` его не видят |
| Включить статичные элементы | рабочий набор начинает работать | меняет настройки сайта на проде: без решения владельца нельзя |
| Виртуальные файлы в репозитории | агент видит файлы | задание должно превращать пути в операции, это ломает правило `main` = файлы |

Предлагаю первый вариант на старте и второй на следующем этапе. Запись PHP-сниппета через базу обходит все файловые проверки, поэтому без своей проверки значений её выпускать нельзя.

## 9. Что нужно каждой CMS

**Минимум у всех** (только файлы): значение в `siteStacks` и `SiteStack` (отдельной миграцией, как `20261018100000_db_operation_kinds_enum`), регистрация в `registry.ts:7-10,33`, затем `importRules`, `rootMarkers`, `configSecrets`, `protectedPaths`, `agentWorkingSet`, `mediaRules`, `verify` с маркерами, `dbOperationKinds: []`, `dbSettings: []`, `dbPlanGuide: ''`, предпросмотр (`databaseSettings`, `previewRecipe`, `databaseCopyPolicy`), `browserRequestDenied`.

Необязательно для выпуска: `publicOriginals` и методы браузера задачи. `browserGuide` уже терпит `NOT_IMPLEMENTED` (`pass-facts.ts:381-384`); остальные методы браузера на этот случай не проверялись.

Факты о CMS ниже — из памяти, если не сказано иное: перед реализацией их проверяют на настоящих сайтах.

| CMS | Минимум: особенности | Максимум: план БД |
| --- | --- | --- |
| **1С-Битрикс** | Открыть `local/`, файлы страниц корня (`.section.php`, `.*.menu.php`), `bitrix/templates/`, `bitrix/php_interface/` без `dbconn.php`; `bitrix/.settings.php` закрыт. Сейчас `protectedPaths` закрывает весь `bitrix/`, и правка шаблона на старом сайте невозможна. Симлинки многосайтовости (разрыв 6). Файлы в `windows-1251`: хеши верны, но правка агента может их испортить. Композитный кеш (разрыв 3), кеши `bitrix/cache`, `managed_cache`, `html_pages`. Исходников для `publicOriginals` нет. | Элементы инфоблока: `iblock_element:<id>`, поля `NAME`, `PREVIEW_TEXT`, `DETAIL_TEXT`, запись через API ядра ради индексов и кешей. `b_option` с составным ключом не ложится в `option:<имя>`. |
| **Joomla** | `templates/`, `media/templates/`; ядро и сторонние расширения лежат в одних папках `components/`, `modules/`, `plugins/`, поэтому их разделяют списком. `configuration.php`: пароль, `secret`, `smtppass`. Кеши `cache/`, `administrator/cache/`. Режим «сайт выключен» отвечает ошибкой и даст `site_broken_before`. | `#__content` (`title`, `introtext`, `fulltext`), `#__modules`. Создание — только через модель ядра: у статьи есть записи в `#__assets` и потоке работ, а сырой SQL их не создаст. |
| **MODX** | Файловый выпуск почти пуст: только сайты со статичными элементами и `assets/`. Папки `core/` и `manager/` часто вынесены или переименованы, поэтому маркер корня — `config.core.php`. | `site_content` (`pagetitle`, `content`, `introtext`), элементы как отдельный вид операции. Обязателен сброс `core/cache/` после записи в базу. |
| **OpenCart** | `catalog/view/theme/<тема>/`, в 4.x `extension/`. Копии в `system/storage/modification/` перекрывают исходный файл, и правка не даст эффекта. Кеш Twig, правки темы в `oc_theme` тоже перекрывают файл. `storage` может лежать вне корня (разрыв 7). В 2.x шаблоны `.tpl` исполняются как PHP (разрыв 5). Папка `admin/` может быть переименована. | **MyISAM в 3.0.x (проверено)**: нет атомарной квитанции. Многоязычные строки описаний: ссылка `<тип>:<id>` не называет язык. Цены — деньги: правило 9, отдельное решение. Заказы и клиенты — только список разрешённого. |

## 10. Как меняется архитектура выпуска

Сам конвейер менять не нужно. Нужны точечные расширения, по приоритету:

1. **Эфемерная проба opcache** в `deploy-step`: снимает ложный `installed` у всех стеков, включая сегодняшний WordPress.
2. **`VerifyPlan`:** адреса в обход кеша, кодовые расширения вместо `CODE_PATH` и `linters`. Убрать или начать читать `logFiles`.
3. **Сброс кеша CMS.** Новое поле манифеста и `HostingSession.list`, удаление только внутри объявленных адаптером папок, без бэкапа: кеш восстанавливается сам. Сейчас удаляются только пути диффа.
4. **Хранимая версия CMS:** `sites.stack_version` и подстановка в `SiteFacts` вместо литералов в трёх местах.
5. **Определение на подключении:** ссылки, каталоги вне корня, кодировка, движок таблиц; результат — уровень возможностей сайта рядом с `siteCapabilities`.
6. **Обобщение контента:** `publishedObjectRefSchema` по типам адаптера, поля записи от адаптера, ссылка с языком.
7. **Инструмент контента от адаптера** вместо `wp_rest` в `apps/mcp` (правило 8). `SiteAdapter.mcpTools` уже есть, но не вызывается.
8. **Коннектор** (§6): новый вид доступа, политики Vault, этап установки в `site_provisioning_stages`.
9. **Стенды:** `verify:release` на каждый стек и модульный тест `runDeploy` с `content: null`.

Предлагаемые уровни сайта:

| Уровень | Что умеет | Что нужно на сайте |
| --- | --- | --- |
| 0 | файлы, бэкап, откат, отмена | ничего, работает сейчас |
| 1 | + достоверный opcache, `runtime` | эфемерная проба |
| 2 | + сброс кешей CMS | только правки платформы |
| 3 | + план БД | постоянный коннектор |

## 11. Вопросы владельцу

| Вопрос | Значение по умолчанию |
| --- | --- |
| Подключать новые CMS с выпуском только файлов на первом этапе? | Да, уровень 0–2 |
| Разрешить временный PHP-файл на проде на время попытки выпуска? | Да: это файл платформы внутри попытки, файлы сайта он не меняет |
| Заменять ли плагин WordPress коннектором? | Новые стеки сразу на коннекторе, WordPress переводить вторым шагом: его установку всё равно ещё не сделали |
| Разрешать ли `/release` без работающего предпросмотра (разрыв 8)? | Нет: без предпросмотра нет `php -l` и смотра |
| MODX: шаблоны в базе? | Через задачу в браузере; статичные элементы молча не включать |

| Цены товаров в плане БД OpenCart и Битрикса? | Не входят: сначала отдельное решение |

Юридический вопрос: ядро Битрикса в репозитории платформы и в образе предпросмотра — вопрос лицензии. На выпуск он не влияет, но определяет предпросмотр.

## 12. Что проверено и что нет

**По коду:** всё со ссылками `путь:строка`.

**Проверено по первоисточникам:**

**Слабые источники:**
- Требование Битрикса к `opcache.revalidate_freq`: только сообщение на форуме ([linux.org.ru](https://www.linux.org.ru/forum/development/15515209)).
