# Разбор рекомендации «Redis не нужен, основной движок — DBOS»

## Вердикт: принять с изменениями

- **Принимаю направление.** Redis не нужен. Координация задач живёт в PostgreSQL 17. Истина о задаче — `tasks.status`, долгие ожидания — это статус плюс таймер. Поток событий в браузер строится на `task_events` и LISTEN/NOTIFY.
- **Не принимаю выбор основного движка.** Для MVP основным должен быть pg-boss 12.x, а DBOS — запасным вариантом. К DBOS можно вернуться, когда ветка 5.x стабилизируется и спайк с Prisma 7 пройдёт. Причины: в предложенной схеме DBOS почти не даёт своих преимуществ, а его минусы проявляются как раз на нашей нагрузке (раздел 3).
- **В наброске кода есть ошибки.** Их нужно исправить при любом движке (раздел 4).

Ниже `$SP` — это папка `<scratchpad>`. Исходники DBOS 5.1.10 и pg-boss 12.34.0 я читал там сам.

## 1. Что подтвердилось

- **Версии и лицензии** (`npm view`, 2026-09-26): `@dbos-inc/dbos-sdk` 5.1.10 MIT, `@dbos-inc/prisma-datasource` 5.1.10, `@dbos-inc/otel` 5.1.10, `pg-boss` 12.34.0 MIT, `@pg-boss/dashboard` 1.9.0, `@wavezync/nestjs-pgboss` 7.0.2 (peer `@nestjs/core ^12`, `pg-boss >=12.6`), `bullmq` 6.3.9, `@nestjs/bullmq` 12.0.0, `@nestjs/core` 12.1.0, `@prisma/client` 7.10.0, `better-auth` 1.7.6, `graphile-worker` 0.18.0. `nestjs-temporal-core` 3.4.0 поддерживает Nest только до 11.
- **API DBOS** — всё названное есть в 5.1.10:
  - `globalConcurrency`, `partitionConcurrency`, `queuePartitionKey` (`$SP/dbos-inc-dbos-sdk-5.1.10/package/dist/src/wfqueue.d.ts`);
  - `enqueueOptions.delaySeconds`, `StepConfig.timeoutMS`, `stepStatus.timeoutSignal` и `cancelSignal`. `cancelSignal` работает между процессами: он опрашивает `workflow_status` в базе (`system_database.js` ~2100–2160);
  - `DBOSClient.send(..., idempotencyKey)`, `applySchedules` с `cronTimezone`, `enablePatching` → версия `'PATCHING_ENABLED'` (`dbos.js:220-229`);
  - фильтр восстановления по `executor_id` и `application_version` (`system_database.js:1126-1151`).
- **Conductor в своём контуре — только на тарифе Enterprise.** Pro и Teams — облачный SaaS ([pricing](https://www.dbos.dev/dbos-pricing)). Звонков «домой» в исходниках SDK я не нашёл: без `conductorKey` внешних подключений нет.
- **Без Conductor экземпляр восстанавливает только свои workflow.** Про навсегда потерянный экземпляр документация молчит ([recovery](https://docs.dbos.dev/production/workflow-recovery)).
- **Limiter better-auth умеет хранить счётчики в базе:** `rateLimit.storage: "memory" | "database" | "secondary-storage"`, по умолчанию `memory` (`$SP/ba/core/package/dist/types/init-options.d.mts:219`). При нескольких репликах web значение `"database"` обязательно.
- **LiteLLM:** Redis нужен, «as soon as you run more than one proxy instance» ([prod](https://docs.litellm.ai/docs/proxy/prod)).
- **Цифра 2,9 тыс. записей в секунду** взята из [блога DBOS](https://www.dbos.dev/blog/postgres-listen-notify-scalability). В статье [Recall.ai](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale) этой цифры нет, там только описан механизм глобальной блокировки при COMMIT.

## 2. Ошибки и натяжки в отчёте

1. **Свежесть DBOS 5.x сильно недооценена.** Стабильных релизов ветки 5.x всего два: 5.0.2 (2026-09-16) и 5.1.10 (2026-09-24). Всё остальное — `-preview`, тег `preview` уже на 5.2.6. Мажорные версии выходили часто: 2.x (2025-01), 3.x (2025-07), 4.x (2025-09), 5.x (2026-09). Совет «следить за 5.1.x» означает следить за одним релизом двухдневной давности.
2. **«Атомарность с Prisma 7: да» — верно только для бэкенда.** `DBOSClient.enqueueInTransaction` требует сырой `pg`-клиент с открытой транзакцией (`client.d.ts:115-128`). Prisma 7 с `PrismaPg` не отдаёт pg-соединение своей интерактивной транзакции. Поэтому в web атомарно «создать задачу + поставить в очередь» нельзя, отсюда и нужен reaper. У pg-boss есть `send(..., { db: fromPrisma(tx) })` (`dist/adapters/prisma.js`), и он работает прямо внутри Prisma-транзакции.
3. **pg-boss описан слабее, чем он есть.** «Выполнение — хотя бы раз, шагов с чекпоинтами нет» — неполная картина. В 12.34 есть:
   - `transactional: true`: обработчик и завершение задачи в одной транзакции (`types.d.ts:880`);
   - `complete`, `cancel`, `resume` с `{ db }`;
   - heartbeat задач (`heartbeatSeconds`, `types.d.ts:471`);
   - `groupConcurrency` с тирами по всем узлам (`types.d.ts:842`).

   Главное: в схеме самого отчёта точность «ровно один раз» для денег даёт не движок, а условный `UPDATE … WHERE status IN (…)` плюс уникальный ключ в `credit_ledger`. Чекпоинт DBOS здесь лишний.
4. **«Приоритет через `priority`» на партиционированной очереди не работает между сайтами.** Порядок внутри партиции — `ORDER BY priority, created_at`. А какие партиции взять, решается так: `ORDER BY random()`, когда бюджет исчерпан (`system_database.js:3001`), или `shuffled(...)` в пофрагментном пути (`wfqueue.js:691`). Итог: между сайтами нет ни FIFO, ни приоритета. При этом в spec §17 (строка 587) приоритет обещан тарифу «Агентство». В pg-boss выборка идёт `ORDER BY j.priority desc, j.created_on` и только потом применяется лимит на группу (`plans.js:1803`). Приоритет и FIFO между сайтами там сохраняются.
5. **Про Temporal «4 сервиса» — преувеличение.** Роли сервера можно запускать в одном процессе ([docs](https://docs.temporal.io/temporal-service/temporal-server)). Вывод «для нас избыточно» от этого не меняется.
6. **Ссылка на Yandex не подтверждает тезис про LISTEN.** В [документации Yandex о пулере](https://yandex.cloud/en/docs/managed-postgresql/concepts/pooling) LISTEN/NOTIFY не упоминается, а режим по умолчанию там — session. К тому же по spec §19 PostgreSQL стоит на своей ВМ `app`, а не в управляемом сервисе, так что пункт скорее всего неактуален. У DBOS на такой случай есть самопроверка LISTEN с откатом на опрос (`system_database.js:4753-4783`).
7. **Лицензия Redis 7.4 — не ловушка для нас.** RSALv2/SSPLv1 запрещают предлагать Redis как сервис, а внутреннее использование разрешают ([redis.io](https://redis.io/legal/licenses/)). Valkey всё равно лучше, но аргумент в отчёте звучит сильнее, чем есть.
8. **LiteLLM `--num_workers 1` противоречит совету документации.** Для одной ВМ LiteLLM советует «set NUM_WORKERS to the machine's vCPU count». Решение осознанное (счётчики не делятся между процессами), но это ещё и единая точка отказа для всего LLM-трафика. Проверить, держит ли один процесс, можно только нагрузочным тестом.

## 3. Скрытые проблемы DBOS в этой схеме

- **Слот песочницы занят, пока workflow ждёт CI.** Лимит считается по всем workflow очереди в статусе `PENDING` (`system_database.js:2848-2894`). `turn` после выкладки PR сидит в `recv('ci')` до 20 минут: контейнер уже уничтожен, а слот `globalConcurrency = SANDBOX_SLOTS` и слот сайта заняты. На практике половина слотов простаивает, и следующий ход того же сайта ждёт лишние 20 минут.
- **Нагрузка на базу.** Когда у партиционированной очереди задан `globalConcurrency`, диспетчер обходит сайты по одному. Для каждого сайта с задачей в очереди он открывает SERIALIZABLE-транзакцию с `FOR UPDATE NOWAIT` (`system_database.js:2817-2822`, `wfqueue.js:688-705`), и так каждую секунду. Сотня сайтов в очереди при занятых слотах — это ~100 пустых serializable-транзакций в секунду на общей базе, где живут и деньги. Быстрый пакетный путь включается только без `globalConcurrency` (`wfqueue.js:677-686`), то есть нужно брать `workerConcurrency`.
- **Две реплики с одним `DBOS__VMID` выполнят одни и те же workflow дважды.** Идентификатор исполнителя по умолчанию — `'local'` (`dbos.js:221`). Восстановление при старте переводит все `PENDING` своего исполнителя обратно в очередь, аренды нет (`dbos-executor.js:808-816`, `system_database.js:1138-1151`). Если при выкладке через GitHub Actions новый контейнер с тем же VMID стартует раньше, чем остановился старый (blue-green, `--scale`, `restart` с перекрытием), тот же ход выполнится дважды — и контейнер агента тоже запустится дважды. Нужна строгая схема «остановили, потом запустили» или fencing.
- **Потерянный узел оставляет workflow в `PENDING` навсегда.** Без Conductor их надо восстанавливать руками, через `dbos workflow resume`. У pg-boss есть `heartbeatSeconds` и `expireInSeconds`: чужую упавшую задачу подберёт любой узел.
- **Без `enablePatching` даже патч-обновление DBOS ломает восстановление.** В хеш версии входит `dbosVersion` (`dbos-executor.js:950`). Обновление 5.1.10 → 5.1.11 меняет версию, и после этого незавершённые и отложенные workflow не восстанавливаются и не забираются из очереди: `application_version = $3` для не-последней версии (`system_database.js:2901-2905`). Значит, `enablePatching` обязателен с первого дня. Но тогда весь старый код воспроизводится новым кодом без replay-тестов, и защита держится только на дисциплине (`DBOS.patch`). Документация при версионировании требует «retain some processes running your old code version» до конца старых workflow ([upgrading](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows)). Для одной ВМ, которую выкладывают через GitHub Actions, это неудобно.
- **`prisma-datasource` тестируют на Prisma 5.15** (devDependencies). Транзакции он открывает через `$transaction(fn, { isolationLevel })`, без `timeout`, поэтому действует таймаут интерактивной транзакции Prisma по умолчанию — 5 секунд. Сериализация идёт через собственный `superjson ^1.13`.
- **Автоочистки таблиц DBOS в конфиге нет.** В 5.1.10 есть только внутренний `garbageCollect(...)` (`system_database.d.ts:532`), а удержание данных — функция Conductor. Значит, нужен свой cron. У pg-boss очистка встроена.
- **Бесплатной UI нет.** Страницу «Процессы» придётся писать самим; у pg-boss есть `@pg-boss/dashboard` (MIT).

**Где DBOS реально сильнее.** Три настоящих плюса:
- после сбоя шаги `merge` → `revoke` продолжаются (одноразовый секрет выкладки гарантированно отзывается);
- `recv`/`send`;
- `listWorkflowSteps` для отладки.

Но самый дорогой шаг — ход агента на 20 минут — после сбоя всё равно перезапускается целиком: чекпоинт стоит только на границе шага.

## 4. Ошибки в наброске кода (при любом движке)

1. **`workflowID: apply:${taskId}` не даст выкладывать повторно.** После `failed` или `rolled_back` и нового хода повторное «Применить» вернёт старый завершённый workflow, и новая выкладка не произойдёт. Нужно `apply:${taskId}:${turnNo}`. То же касается будущей «Отменить» (revert): её тоже надо выкладывать.
2. **Незавершённые задачи зависают.** Исключения из `prepare` (после 3 попыток), `pr`, `transition` и `merge` не перехвачены. Workflow уходит в `ERROR`, задача остаётся в `preparing` или `running`, резерв квоты не возвращается. Reaper должен ловить все незавершённые статусы, у которых workflow в `ERROR` или `CANCELLED`, а не только осиротевшие `queued`.
3. **Нет общего замка на сайт.** `agent` и `apply` — разные очереди, а партиция действует только внутри своей очереди. Ход агента с правками контента напрямую на проде может идти во время выкладки и автооткат того же сайта. По spec §10 (строка 397) откат — это «возврат файлов из бэкапа», так что сделанные в это время правки файлов и медиа могут пропасть. Нужна одна аренда на сайт (`sites.active_op` или строка аренды) на ход, выкладку и revert.
4. **Сайт разблокируется при неизвестном состоянии прода.** Если после таймаута `recv('deploy')` прод в неизвестном состоянии, workflow кончается эскалацией и освобождает сайт. Следующая выкладка поедет поверх неизвестного прода. Нужен флаг «сайт заморожен до решения оператора». Кроме того, одних вебхуков мало: нужен опрос API запусков Gitea/GitHub/GitLab как запасной путь. Гарантирует ли Gitea 1.27 повторную доставку вебхуков, я не проверял.
5. **Перезапуск хода после сбоя бэкенда.** Контейнер — отдельный процесс, после падения бэкенда он живёт дальше. Повторный запуск шага создаст второй контейнер: двойные правки контента, двойной push и двойной расход токенов (а тарификация идёт в токенах). Что нужно:
   - детерминированное имя контейнера `raditi-turn-<taskId>-<turnNo>` как fence: Docker не даст запустить второй;
   - модель «запустить или подключиться»;
   - учёт токенов с идемпотентным ключом (request id из LiteLLM);
   - `retryLimit: 0` для хода и сверка вместо автоповтора.
6. **Отмена после правок контента.** «Отменить задачу» в `running` возвращает квоту, но правки контента, уже сделанные на проде, остаются. Нужно либо откатывать снимки, либо запрещать бесплатную отмену после первой правки. Это доменное решение, его надо принять явно.
7. **Мелочь:** `DBOS.cancelWorkflow` сам по себе уже шаг, заворачивать его в `runStep` не нужно.

## 5. Риски объединённого бэкенда

- **Каждая выкладка платформы рвёт ходы агентов.** MCP-шлюз живёт в одном процессе с оркестратором, поэтому выкладка бэкенда обрывает MCP-соединения всех идущих ходов. Нужны плавная остановка и повторное подключение, иначе каждая выкладка — массовые `failed` и возвраты квоты.
- **Шлюз с полным доступом к базе.** «Реплики MCP-шлюза того же образа с `listenQueues: []`» всё равно получают полный доступ к БД и к схеме `dbos`. Шлюз — единственный сервис, к которому ходят песочницы, так что при побеге из песочницы до платформенной базы один шаг. Шлюзу нужна своя роль в PostgreSQL (без `dbos`, `credit_ledger`, `users`) и своя AppRole в Vault.
- **Точка отказа и сроки восстановления.** PostgreSQL становится единственной точкой отказа ещё и для оркестрации. Ежедневного бэкапа из spec §19 мало: нужен WAL-архив (WAL-G или pgBackRest в российский S3) с RPO в минуты. Gitea и LiteLLM стоит держать в отдельных базах того же экземпляра, со своим `statement_timeout` на роль.

## 6. Что проще и надёжнее для MVP

pg-boss 12.x за доменным портом `TaskRuntime`, без долгоживущих workflow.

- **Один шаблон вместо двух.** Каждый переход — задача в очереди. Её обработчик делает `prisma.$transaction(tx => { условный updateMany; запись в ledger; boss.send(next, …, { db: fromPrisma(tx) }); boss.complete(…, { db: fromPrisma(tx) }) })`. Вебхуки CI и выкладки тоже делают переход и ставят следующую задачу. Таймауты — задачи с `startAfter`, которые ничего не делают, если статус уже сменился. Отчёт сейчас смешивает `recv` на минуты и таймеры на дни; здесь для всех ожиданий один шаблон.
- **Очереди:**
  - `agent-turn`: `groupConcurrency: 1` по `siteId` (глобально по узлам), приоритет по тарифу, `localConcurrency` = числу слотов песочниц на хосте, `expireInSeconds` ≥ 25 минут (по умолчанию 900 секунд, `types.d.ts:421`), `heartbeatSeconds: 60`, `retryLimit: 0`;
  - `deploy`: `groupConcurrency: 1` по `siteId`.
  - Ограничения: `expireInSeconds` не больше 24 часов (`attorney.js:5`), задачи в `created` удаляются через 14 дней. Для таймера на 7 дней этого хватает.
- **Замок на сайт и слоты песочниц — в своих таблицах.** Аренды с fencing-версией лежат в домене, а не в движке. Тогда замена движка действительно стоит дёшево.
- **Минусы pg-boss, честно:**
  - bus factor ≈ 1: у timgit 1515 коммитов, у следующего участника 100; за последние полгода 86 из ~100 коммитов — его;
  - пакет только ESM, Node ≥ 22.12. С Node 24 и `require(esm)` это не проблема;
  - частые минорные релизы: 34 за 10 месяцев;
  - повторы шагов и идемпотентность внутри хода пишем сами. Но и в DBOS шаг длиной 20 минут всё равно перезапускается целиком.

Если позже понадобятся настоящие durable-workflow (многошаговые сценарии Битрикса, сложные откаты), DBOS можно подключить как второй адаптер `TaskRuntime` после 5.2+ и спайка.

## 7. Что изменить (итоговый список)

1. Основной движок — pg-boss 12.34.x (закрепить точную версию), с `@wavezync/nestjs-pgboss` 7.0.2 или тонкой обёрткой. DBOS — запасной вариант после спайка с Prisma 7.10 и `PrismaPg`.
2. Если всё же DBOS, то:
   - `enablePatching: true` с первого дня;
   - `workerConcurrency` вместо `globalConcurrency`;
   - ожидание CI вынести из очереди `agent` (отдельный workflow или событие);
   - выкладка бэкенда только по схеме «остановили, потом запустили» с уникальным `DBOS__VMID`;
   - свой cron на `garbageCollect`;
   - приоритет «Агентства» решать отдельно: партиции его не дают.
3. Замок на сайт — одна аренда на ход, выкладку и revert. Плюс флаг «заморожен» при неизвестном исходе выкладки.
4. Слоты песочниц — аренды в PostgreSQL, не лимит очереди.
5. Ход агента: имя контейнера как fence, модель «запустить или подключиться», `retryLimit: 0`, учёт токенов по request id.
6. Уникальный ключ `credit_ledger (task_id, kind, turn_no)`. Reaper охватывает все незавершённые статусы.
7. Отдельные роли PostgreSQL и AppRole в Vault для MCP-шлюза. WAL-архив с RPO в минуты.
8. SSE — как в отчёте (`task_events` + NOTIFY только с id задачи + `Last-Event-ID`). Это принимаю без изменений.
