# P3 B6: таблицы шлюза и права PostgreSQL

30.09.2026. Продолжение [B5](09-p3-vault-and-local-site.md). Вся реализация и проверка выполнены локально; рабочая база и облачные серверы не изменялись.

**Уточнение от владельца, 30.09.2026:** разделение пользователей PostgreSQL, описанное и проверенное в этом отчёте, заменено единым пользователем `raditi` для всех сервисов. Результаты ниже сохраняются как история B6; действующая конфигурация и её проверка — [единый пользователь PostgreSQL](11-postgres-single-user.md). Схема данных и ограничения B6 сохранены.

## Что готово

Новая миграция `20260929130000_subscription_gateway` добавляет `llm_keys`, `llm_calls`, `task_account_bindings`, `cross_border_clearances`, состояние пула в `subscription_accounts` и класс данных рабочего пространства. `token_usage` связывается с ключом, вызовом и аккаунтом; оценочный расход имеет причину и признак billable. Составной внешний ключ не позволяет взять цену другой модели. Старые API-модели, история цен и переходные поля остаются до отдельного сужения схемы.

Миграция транзакционная. При непустых прежних `subscription_accounts` или `token_usage` она останавливается до преобразования данных: автоматически очистить строки или догадаться об их новых связях нельзя. Оператору потребуется отдельный план переноса. Guard и отсутствие частично применённой схемы проверены тестами.

Сиды добавляют два выключенных провайдера подписок и четыре выключенных профиля: Codex `light`, `standard`, `heavy`; Kimi `standard`. Цен в сидах нет. Резерв выхода Codex — 32 000, Kimi — 32 768. ID моделей Codex оставлены `null` до подтверждения доступных upstream ID; проверенная ранее модель spike не подменяет проектный каталог автоматически. Повторный seed сохраняет все настройки оператора и историю цен; совпадение slug с API-провайдером откатывает весь seed.

`raditi_llm` создаётся вне `raditi_app`. Web не видит шесть таблиц шлюза. Core управляет ключами и привязками, операторскими полями аккаунта и закрывает зависшие вызовы. Llm пишет учёт и состояние аккаунта, но не может поднять бюджет, снять отзыв ключа, включить аккаунт, изменить его план, статус или лимит одновременности. Данные пользователей, сайтов, credentials и биллинга ему недоступны.

Bootstrap и миграция согласованы: роль создаётся до B6, права выдаются сразу в миграции и повторно при bootstrap. Общая выдача DML группе app и отзыв защищённых таблиц выполняются в одной транзакции, без промежутка с открытым доступом. Скрипт работает и на прежней схеме B3, где новых колонок ещё нет. Добавлен `llm-password` в шаблоны секретов, preflight и локальный edge verifier; порядок обновления описан в runbook. Сам сервис `llm` пока не запускается.

## Уточнения спецификации

- Бюджет ключа в БД: `0 < budget_rub ≤ 750`. Прежний черновой минимум 1 ₽ расходился с проверенным B4, который допускает положительный остаток меньше рубля. Резерв первого вызова остаётся отдельным условием выдачи ключа. Уточнение от 04.10.2026: условие реализовано в `issue` (B11) — бюджет ключа сверяется с потолком класса или резервом «Оплаты за действие» и с резервом первого вызова ([отчёт B11](18-p3-turn-keys.md)). Шлюз держит бюджет ключа; расход по всем ключам одной попытки считает P12.
- Core и llm могут обновлять `subscription_accounts.updated_at`: Prisma пишет его автоматически вместе с разрешёнными изменениями. Остальные права по колонкам сохранены.
- Исправлено объяснение advisory lock: он сериализует выбор по пулу; для PostgreSQL `FOR UPDATE` достаточно UPDATE хотя бы на одну колонку. Рабочая схема блокировок не менялась.

Изменения отражены в spec §16–17 и проекте P3 §10. При сверке реальной БД с Prisma найдено и исправлено только несовпадение имени индекса `token_usage_task_attempt_idx`.

Проверки прав выполнены непосредственно после миграции и после повторного bootstrap. Отдельные проверки `has_table_privilege`/`has_column_privilege` не дают отсутствию SELECT замаскировать ошибочно выданный INSERT или UPDATE. Независимое ревью также нашло и закрыло два дефекта проверочного скрипта: пропущенную очистку при частично успешном `docker run` и отмену только родительского pnpm без его дочерних процессов. Финальное независимое ревью схемы, сидов и ACL подтверждённых замечаний не выявило.

БД гарантирует существование связанных строк, но согласованность task/model/account между ключом, вызовом и расходом должна обеспечиваться сервисами шлюза по проекту. Это остаётся обязательной проверкой B9/B11. Полный `pnpm gates`, сборки и настоящий WordPress в рамках B6 повторно не запускались: изменённый слой проверен отдельными гейтами выше. Коммитов и облачной выкладки не было.

## Изменения после ревью 02–04.10.2026

Применённые миграции не редактировались. Добавлены три новые, каждая только дополняет схему и не меняет строк:

| Миграция | Что делает |
| --- | --- |
| `20261002100000_subscription_accounts_retired_identity` | Метка и пара (провайдер, внешний ID аккаунта) уникальны только среди невыведенных аккаунтов (`WHERE status <> 'retired'`). Выведенная строка остаётся для истории, тот же аккаунт можно импортировать снова новой строкой |
| `20261003100000_llm_calls_estimated_input` | `llm_calls.estimated_input_tokens` (nullable, `CHECK >= 0`): оценка входа, по которой считался резерв вызова. По ней оценивается потерянный вызов; у прежних строк — запасной расчёт по `request_bytes` |
| `20261003110000_task_events_policy_flagged_idx` | Частичный индекс `task_events_llm_policy_flagged_idx (task_id) WHERE type = 'llm.policy_flagged'`. Флаг отказа по содержанию проверяется при каждом поиске ключа, допуске и выдаче ключа; прежде проверка читала все события задачи. Обычный `CREATE INDEX`, без `CONCURRENTLY` |

В `schema.prisma` предикат индекса записан с приведениями (`type::text = 'llm.policy_flagged'::text`): без них `prisma migrate diff` показывает расхождение. Запросы шлюза и выдачи ключа используют индекс — проверено `auto_explain` на одноразовой PostgreSQL.

**Выход из остановленной миграции B6.** Если `pnpm db:deploy` остановился на `20260929130000_subscription_gateway` с сообщением `subscription_accounts is not empty` или `token_usage is not empty`, транзакция миграции откатилась и объектов B6 в базе нет. Но Prisma записала миграцию как неуспешную, и следующий deploy отказывает (P3009). После устранения причины (историю без решения владельца не удалять) выполните с тем же `DATABASE_URL`:

```sh
pnpm --filter @repo/db exec prisma migrate resolve --rolled-back 20260929130000_subscription_gateway
pnpm db:deploy
```

Какую базу видит команда, показывает строка `[db] target <user>@<host>/<db>: DATABASE_URL from the repository .env` (или `from the environment`): её печатает любой `pnpm db:*` до подключения. Порядок воспроизведён на одноразовой базе.

**`pnpm verify:db` сейчас.** Все 15 миграций на пустой PostgreSQL; сравнение базы с `schema.prisma`; наборы четырёх пакетов отдельными командами — база, orchestrator, tRPC и web, у каждой предел 15 минут (`VERIFY_DB_TEST_TIMEOUT_MS`), при превышении печатается хвост вывода. Скрипт проверяет, что тесты `@repo/db` не оставили строк в `public` и чужих схем, и сам запускает сиды перед набором orchestrator. Результат 04.10.2026: база 320, orchestrator 2 139 без пропусков, tRPC 249, web 247; 394 проверки единого пользователя и обновления. То же сравнение схемы с миграциями — шаг `Schema matches migrations` в job `gateway-db` (`ci.yml`); прогон GitHub ещё не выполнялся.

Мёртвый блок GRANT/REVOKE в конце миграции B6 остаётся: применённую миграцию не правим, прежних ролей нет, и блок ничего не делает.

Отложено: колонки `subscription_accounts.revoke_failures` и `revoke_failed_at` — вместе с писателем и читателем, M9; неиспользуемые `agent_drivers.image`, `subscription_accounts.status_reason` и `llm_calls.upstream_response_id` — контрактная миграция B16; составной внешний ключ `tasks(site_id, workspace_id) → sites(id, workspace_id)` — P12.
