## 1. Что сейчас в коде

Опись сделана четырьмя разборами кода 14.11.2026; главное:

- **Поле закрыто, пока агент работает.** Решает `dialog-view.tsx:1200-1217`: поле открыто только в `awaiting_user` и `awaiting_approval`; `task.message` (`postDialogMessage`, `packages/trpc/src/services/chat/tasks.ts:466-548`) в `queued`, `preparing`, `running` отвечает `TASK_BUSY`. «Остановить» (`stopDialog`, `tasks.ts:961-1023`) кончает чат статусом `cancelled` — он конечный; пути «прервать проход и оставить чат открытым» нет.
- **В идущий ход OpenCode слова не добавить.** Ход — `opencode run` с запросом из файла; протокол раннера несёт только `abort` (`apps/runner/src/sandbox-runner/sandbox-runner.ts:466-482`). «Направить ход» поэтому значит «прервать проход и сразу начать следующий с новыми словами», а не дописать в идущий.
- **Следующий проход берёт все слова клиента с начала сессии** (`promptOf`, `apps/core/src/tasks/turn-planner.ts:297-318`), поэтому несколько сообщений очереди сливаются в один запрос сами.
- **Конец прохода — одно место:** `PassSettlement.settle()` (`apps/core/src/tasks/pass-settlement.ts:295`), каждый исход — одна транзакция с `settleTurn` (`packages/db/src/task-settle.ts:213`) и строками `feed.result | feed.question | feed.failure | feed.candidate`. Outbox для уведомлений там не пишется.
- **Уведомлений о чатах нет.** Каталог `packages/notifications/src/catalog.ts` — 7 писем (вход и биллинг), канал только почта, отписки нет. Service worker, manifest, VAPID, `web-push` нет. Живого потока нет: лента опрашивает сервер (`use-dialog-feed.ts`, 2–30 с, только при видимой вкладке), что клиент видел, не хранится.
- **Режима плана нет.** У драйвера один агент `raditi` с правами на всё (`packages/agent-drivers/src/opencode.ts:58, 147-176`), инструменты MCP разрешены шаблоном `raditi_*`; «ничего не меняй» у `/init` держат только слова. Вопрос агент задаёт через `result.questions` → `feed.question`, ответ — обычным сообщением.
- **Голоса нет вовсе.** `Permissions-Policy: microphone=()` (`apps/web/next.config.ts:53`), аудио нет среди вложений. Распознавание в браузере (Web Speech API Chrome) шлёт звук в Google — правило 1 это запрещает. Ключ Яндекса в Vault (`subs/search/yandex`) — для поиска, читает его только `mcp`; web ключей не читает (правило 2).
- **Список чатов:** `listDialogs` (`packages/trpc/src/services/chat/dialog-list.ts:104-204`), удаление мягкое (`deleted_at`), у `tasks` нет полей закрепления и архива, поиска по чатам нет (поиск проектов — только на `/projects` при больше 6).
- **Поле ввода:** вставка файла из буфера есть (`composer.tsx:499-505`), перетаскивания и истории стрелкой нет; приветствие — только на «Новом чате» (`new-chat.tsx`, план 66). `/undo` возвращает слова последнего запроса в поле (`dialog-view.tsx:880-896`).

## 2. Решения

Слова владельца — только выбор восьми возможностей. Остальное — значения по умолчанию (указание от 09.10.2026): записываются в spec §20, блок «Ввод и вывод чата — решения 14.11.2026», и действуют, пока владелец не скажет иначе.

### Очередь и «Отправить сейчас»

- **ВВ1.** Пока агент работает (`queued`, `preparing`, `running`), поле открыто. Сообщение встаёт в очередь чата — новая таблица `task_queued_messages` (id, `task_id`, текст, вложения, порядок, автор, время). Очередь видна под лентой карточками «В очереди»: текст можно поправить или убрать, пока проход не взял его.
- **ВВ2.** Когда проход закончился успешно (`feed.result`, `feed.question`, `feed.candidate` — чат ждёт клиента), `PassSettlement` в той же транзакции переносит очередь в строки `feed.request` (вид `answer` или `revision`, как сейчас у `postDialogMessage`) и ставит следующий проход с новым резервом (`nextPassAttempt`, переносится из `trpc` в `@repo/billing` или `@repo/db`, чтобы его звал и `core`). Если резерва не хватает, очередь остаётся, а в ленте — обычный текст о кредитах; клиент отправит её сам.
- **ВВ3.** После сбоя, предела кредитов, вопроса «Продолжить?» и недельного лимита очередь сама не уходит — иначе сбой может крутиться по кругу. У карточек очереди тогда кнопка «Отправить».
- **ВВ4.** «Отправить сейчас» у карточки очереди — прервать идущий проход и сразу начать следующий с этими словами. Это новый исход прохода `interrupted`: `core` останавливает проход (`live.abort`), как при «Остановить», но чат остаётся открытым, а очередь уходит следующим проходом. Работа прерванного прохода **списывается** по расходу токенов: проход прервал клиент, не сбой платформы (правило 7 — «упавший проход бесплатен» относится к сбоям). Правки файлов прерванного прохода не публикуются: кандидат прежний.
- **ВВ5.** Во время выпуска (`deploying`, `verifying`) и отмены очередь закрыта, как сейчас поле.

### Уведомления

- **ВВ6.** Повод — исход прохода, после которого чат ждёт клиента: ответ, вопрос, кандидат готов к `/release`, сбой, предел кредитов, недельный лимит; а также конец выпуска. `PassSettlement` пишет в той же транзакции событие outbox `chat.notify` с ключом идемпотентности `<taskId>:<eventId>`.
- **ВВ7.** Уведомление идёт, только если клиент не смотрит этот чат: лента при опросе отмечает присутствие (`task_presence`: пользователь, чат, время; запись не чаще раза в 30 с), а доставка через 45 с после исхода проверяет отметку моложе 60 с. Смотрит — уведомления нет.
- **ВВ8.** **Браузер — Web Push** (RFC 8291, VAPID, библиотека `web-push`). Подписки — таблица `push_subscriptions`. Пара ключей VAPID: открытый — переменная `WEB_PUSH_VAPID_PUBLIC` (не секрет; её читают web и `core`), закрытый — `WEB_PUSH_PRIVATE_KEY`, только `core`. В production закрытый ключ лежит в OpenBao (`platform-secrets.mjs`, `app/core`) и попадает в `core/app.env` рендером секретов на хосте — так же, как `LEADS_TELEGRAM_BOT_TOKEN` и `SENDSAY_API_KEY`. Отдельного пути `kv/platform/web-push` и политики Vault нет (отступление от первой редакции плана: рендер секретов уже держит правило 2 для ключей служб). Push-сервисы браузеров зарубежные (Google, Mozilla, Apple), поэтому в теле уведомления — только id записи `chat_notifications`, без названия чата и слов: текст показывает service worker (`/sw.js`), получив его с нашего сервера (`GET /api/notifications/<id>` с cookie). Так ни слова клиента за рубеж не уходит даже в шифре. Браузер, отказавшийся от подписки (404, 410), забывается.
- **ВВ9.** **Почта** — новое письмо `chat.waiting` каталога `packages/notifications`: «Агент ответил в чате «…»» / «…задал вопрос» / «…изменения готовы» / «…не смог закончить» со ссылкой на чат. Не чаще одного письма на чат за 30 минут; в подвале — ссылка на настройки уведомлений.
- **ВВ10.** Настройки — на `/settings` («Общее»), блок «Уведомления»: «В браузере» (включение просит разрешение браузера; по умолчанию выключено) и «Письма о работе агента» (по умолчанию включено). Хранятся в новой таблице `notification_settings`.
- **ВВ11.** Заголовок вкладки показывает, что чат ждёт: «● Агент ответил — Радити», пока вкладка не в фокусе. Telegram — позже, P13.

### Режим плана

- **ВВ12.** У поля рядом с «Размышлением» — переключатель «Сначала план». Запомненный выбор — в `localStorage`, как уровень размышления (план 66); в сообщение он уходит флагом `plan: true` строки `feed.request`.
- **ВВ13.** Проход плана идёт вторым агентом OpenCode — `raditi-plan` в той же конфигурации: `edit`, `bash`, `todowrite` и все инструменты MCP, которые пишут, — `deny`; разрешены чтение (`read`, `glob`, `grep`, `list`), `webfetch`, `raditi_site_info`, `raditi_search_web` и `web_*` только для чтения (открыть, посмотреть). Вторая линия — `core`: у прохода плана изменения файлов не публикуются вовсе (кандидата нет), а `mcp` по признаку прохода плана в назначении отказывает в записи. Признак — поле `plan` в `TurnInput` и `turnPlanSchema`.
- **ВВ14.** Инструкции прохода плана дописывают раздел «Только план»: план — нумерованные шаги по-русски для владельца сайта, что изменится и как это проверить; ничего не менять. Ответ — обычный `client_message`; карточка в ленте — «План» с кнопками «Выполнить план» и «Поправить» (поле с пометкой «к плану»).
- **ВВ15.** «Выполнить план» — команда агенту `plan_execute` (как `/init`, `AGENT_COMMANDS`): следующий проход обычным агентом в той же сессии со словами «Выполните согласованный план». Проход плана оплачивается как любой проход (правило 7).

### Голосовой ввод

- **ВВ16.** Кнопка микрофона в поле. Запись — в браузере, AudioWorklet в PCM 16 кГц моно (у всех браузеров одинаково, без перекодирования), до 30 секунд за раз; кнопка — «нажмите, чтобы начать / остановить», текст встаёт в поле, клиент правит его и отправляет сам.
- **ВВ17.** Распознавание — Yandex SpeechKit, синхронное распознавание (до 30 с, до 1 МБ), сервера в России — правило 1 соблюдено. Звук не хранится: идёт в памяти web → `core` → SpeechKit, в базе — только строка учёта (`speech_calls`: пользователь, длительность, время, исход).
- **ВВ18.** Ключ — отдельный от поиска: API-ключ сервисного аккаунта с ролью `ai.speechkit-stt.user` и id его каталога. Читает их только web, маршрут `POST /api/speech` (сессия, `Origin`, согласия, заявленная длина не больше 30 секунд PCM — 960 000 байт): ключ `YANDEX_SPEECHKIT_API_KEY` — секрет в `web/app.env`, в production его кладёт рендер секретов из OpenBao (`platform-secrets.mjs`, `app/web`), как `SMARTCAPTCHA_SERVER_KEY`; id каталога `YANDEX_SPEECHKIT_FOLDER_ID` — не секрет, в `.env` ВМ. Отступление от первой редакции плана: ни пути `subs/speech/yandex`, ни слушателя `core`, ни команды `subscriptions:speech-key` нет — у web уже есть ключ Яндекса тем же путём, а лишний переход через `core` ничего не закрывает. Маршрут вынесен из общего предела тела Traefik (512 КиБ), как вложения.
- **ВВ19.** Бесплатно для клиента, с пределом: 60 распознаваний в час на пользователя. Без ключа в Vault микрофона в поле нет (web узнаёт это по `SPEECH_API_URL`). `Permissions-Policy` — `microphone=(self)`.
- **ВВ20.** **Ждёт действия владельца:** создать в Yandex Cloud сервисный аккаунт с ролью `ai.speechkit-stt.user`, выпустить API-ключ и положить его: `printf %s "<ключ>" | ssh … platform-secrets.mjs set app/web YANDEX_SPEECHKIT_API_KEY`, id каталога — в `.env` ВМ, затем рендер `web` и пересоздание его контейнера. До этого микрофона в поле нет.

### Мелочи

- **ВВ21. Поиск, архив, закрепление.** У `tasks` — `pinned_at` и `archived_at` (миграция только добавляет столбцы). Меню строки чата: «Закрепить» / «Открепить», «В архив» / «Из архива». Закреплённые — сверху списка, архивные — в разделе «Архив» внизу списка; новое сообщение в архивном чате возвращает его из архива. Поиск — поле над списком: по названию и по словам клиента (`feed.request`), `ILIKE` по чатам рабочих пространств пользователя, до 50 находок, в «Архиве» тоже. Индекса `pg_trgm` нет: индекс по выражению `payload->>'text'` схема Prisma описать не может, и сверка схемы с миграциями его бы отвергла; поиск ограничен чатами пользователя и идёт по индексу ленты `task_events_feed_idx`. Закреплённые приходят отдельным списком `pinned` на первой странице, следующие страницы их не повторяют; архивный чат не закрепляется.
- **ВВ22. Перетаскивание.** Файл, брошенный на поле или на ленту, становится вложением тем же путём, что вставка (`attachments.add`); подсветка зоны — «Отпустите, чтобы прикрепить».
- **ВВ23. История стрелкой.** Стрелка вверх в пустом поле (или с курсором в начале первой строки) подставляет прошлые запросы клиента этого чата, новее — раньше; стрелка вниз — обратно, до пустого поля. В новом чате — последние 50 запросов из `localStorage` этого браузера.
- **ВВ24. Стартовые подсказки.** На «Новом чате» под приветствием — 4 подсказки по виду чата (`chatRequirements`): с кодом сайта, с браузером на сайте, без проекта. Тексты — константы в `@repo/domain`. Нажатие ставит текст в поле, не отправляет.
- **ВВ25. Правка отправленного.** У последнего сообщения клиента, когда чат ждёт и `/undo` доступен, — карандаш «Изменить»: это `/undo` (слова возвращаются в поле, файлы откатываются), клиент правит и отправляет. Пока агент работает, правится не отправленное, а сообщение очереди (ВВ1).

## 4. Проверки

- Модульные тесты рядом с кодом: очередь (перенос при каждом исходе, ВВ3, гонка правки и взятия), `interrupted` (списание, кандидат не меняется), присутствие и задержка уведомления, тело push без слов клиента, права `raditi-plan`, отказ `mcp` в записи проходу плана, предел распознаваний.
- `pnpm verify:db` — новые миграции и наборы `core`, tRPC, web.
- `pnpm verify:opencode` — строка: агент `raditi-plan` не может править файл, запускать команды и звать инструмент записи.
- `pnpm --filter e2e test:site` — поле во время хода, очередь, закрепление и архив, поиск, перетаскивание, подсказки, «Изменить».
- `pnpm verify:release` — S1 с очередью и «Отправить сейчас» и проход плана → «Выполнить план» → `/release`.
- Живой SpeechKit и настоящие push-сервисы — вручную, после ключа владельца (ВВ20).

## 5. Ждёт владельца

- Ключ SpeechKit (ВВ20).
- Значения по умолчанию ВВ1–ВВ25, особенно: прерванный «Отправить сейчас» проход списывается (ВВ4); очередь не уходит сама после сбоя (ВВ3); письма включены по умолчанию (ВВ10); голос бесплатен с пределом 60 в час (ВВ19).
- Юристу: письма о работе агента — транзакционные (без отдельного согласия), push-подписка браузера — данные устройства.
