## 0. Что просил владелец (кратко)

- Обычная задача агента (те же `Task`, `TaskTurn`, сессия, статусы, события, очередь и биллинг) выполняется через облачный браузер. Браузер — инструмент агента, а не отдельный продукт: ни `BrowserTask`, ни своего чата, ни параллельного оркестратора.
- Первый сценарий: «добавьте новость на WordPress» с текстом, изображениями и другими файлами; агент открывает сайт, пользователь при необходимости входит сам, агент делает работу в интерфейсе WordPress, работа браузера видна в правой панели окна задачи.
- Кодовая база необязательна: у задачи явные требования к окружению — нужен ли репозиторий, нужна ли браузерная сессия; это не взаимоисключающие возможности.
- Изолированный browser worker владеет Chromium через Playwright; агент управляет им ограниченными инструментами доверенного шлюза (MCP); песочнице агента интернет не открывается; сырой CDP/Playwright клиенту и модели не выдаётся.
- Трансляция: Chromium → `page.screencast` (Playwright 1.63) → worker → авторизованный шлюз WebSocket → WSS → canvas; обратно — мышь и клавиатура тем же путём в тот же Chromium. Управление потоком, heartbeat, первый кадр, переподключение.
- Окно задачи как ChatGPT Work: общение слева, просторный браузер справа, изменение ширины, полный экран, переключатель на телефоне. Действия «Взять управление», «Продолжить работу агента», «Остановить».
- Ручное управление с эпохой управления, вход пользователя прямо в облачной странице, секреты входа не попадают ни модели, ни в журналы; авторизация живёт только в эфемерном контексте браузера.
- Настоящий путь вложений: выбор → `raditi-inbox` → подтверждение → привязка к задаче → worker → WordPress.
- Gutenberg (заголовок, текст, изображения, файлы, изображение записи, черновик или публикация, проверка, ссылка), Classic Editor — проверяемо или честная передача управления; checkpoint с post ID; без дубликатов после неясного исхода; `done` подтверждается результатом на сайте.

Задаче с репозиторием — как раньше `active`. | Владелец («отсутствие импорта или git не должно блокировать браузерную возможность») |

Шлюз пересылает сообщения worker'у по внутреннему WebSocket с токеном; Playwright он не знает. | По умолчанию (схема — владелец) |
| Б13 | Кадры: `page.screencast.start({ onFrame, size: 1280×800, quality: 70 })`; доставку ограничивает worker сам — не больше 12 кадров в секунду (`BROWSER_STREAM_MAX_FPS`), окно неподтверждённых кадров 2 (`BROWSER_STREAM_WINDOW`), один самый свежий ожидающий кадр, ACK клиента после отрисовки, предел `bufferedAmount` 1 МиБ; ~~неподтверждённый кадр старше 3 с считается потерянным~~ — отступление от 23.10.2026 (ревью, spec §20): место в окне освобождает только подтверждение, а не время — сокет кадры не теряет, он только медленный, и место, освобождённое по часам, копило бы кадры перед зрителем на слабой связи; кадр, который шлюз не отдал из-за полного сокета, подтверждает worker'у сам шлюз и держит самый свежий такой кадр, пока сокет не освободится; подтверждение, освобождающее место, предел сообщений в секунду не отбрасывает — ни в шлюзе (не больше одного на переданный кадр), ни в worker'е; устаревшие кадры (другая страница или версия окна) отбрасываются до отправки. `onFrame` возвращает обещание, которое задерживает подтверждение Chromium до следующего слота, поэтому сам Chromium не снимает больше. | Б15 | Управление: одна страница, один `BrowserContext`; `controller ∈ {agent, user}` и `controlEpoch`. «Взять управление» → `controller = user`, эпоха +1, ожидающие команды агента отклоняются (`BROWSER_USER_IN_CONTROL`), текущая дожидается своего короткого таймаута (до 10 с), затем ручной ввод разрешается (`manualReady`). | Б16 | «Продолжить работу агента»: если ход идёт — сообщение шлюзу `release` (`controller = agent`, эпоха +1); если задача ждёт (`awaiting_user`) — `task.resumeAgent` (та же попытка, без нового резерва), а ход при старте сам забирает управление у пользователя (эпоха +1) и получает новое наблюдение. | Б17 | Обрыв связи при ручном управлении: пауза сохраняется (`controller = user`) до переподключения или срока сессии; зажатые клавиши и кнопки отпускаются сразу. ## 3. Контракты (обязательны для всех срезов)

### 3.1 Требования и план хода

```ts
// packages/domain/src/tasks/task-requirements.ts
export const taskRequirementsSchema = z.strictObject({ repository: z.boolean(), browser: z.boolean() })
  .refine((r) => r.repository || r.browser)
export type TaskRequirements = z.infer<typeof taskRequirementsSchema>
export const REPOSITORY_ONLY: TaskRequirements = { repository: true, browser: false }
export const BROWSER_ONLY: TaskRequirements = { repository: false, browser: true }
export const requirementsOf = (plan: { requirements?: TaskRequirements }) => plan.requirements ?? REPOSITORY_ONLY
```

`turnPlanSchema`: `requirements: taskRequirementsSchema.optional()`, `workspace: publicationSourceSchema.optional()`; refine: `requirementsOf(plan).repository === (plan.workspace !== undefined)`; без репозитория запрещены `rebased`, `replacesTurn`. `TurnRequest`, `UnkeyedTurnRequest` — те же поля. `TurnPrepareInput.bundle?`. `TurnExecution.capture({ home, baseSha?, sandboxBaseSha?, addOnlyPaths? })` → `CapturedTurn { homeBytes; patch?: Uint8Array; untracked?: Uint8Array }` (без `baseSha` — без `patch` и `untracked`).

### 3.2 Снимок

`snapshotMetadataSchema.git` — необязателен; `snapshotPlanSchema.git` — необязателен; `snapshotManifestSchema.parts` — 3 части при `git`, ровно `home` без `git`; `SNAPSHOT_SCHEMA_VERSION = 1`. `snapshotAad`: при `git` — прежний массив байт в байт; без `git` — на местах git четыре `null` и в конце `'workspace', 'none'`. `SnapshotArchives` для git-less — только `home`. Восстановление git-less снимка не трогает `/workspace/repo`, кроме `mkdir`.

### 3.3 Протокол раннера

`prepare.bundle?`; `capture.baseSha?` (с ним — `sandboxBaseSha?`, `addOnlyPaths?`; без него — ни того ни другого); отчёт `captured { homeBytes, patch?, untracked? }` — части есть ровно тогда, когда в `capture` был `baseSha`.

### 3.4 Браузерная сессия (данные)

```prisma

enum BrowserController   { agent user }
model BrowserSession {          // browser_sessions
  id, taskId (FK, одна незакрытая на задачу — частичный уникальный индекс), siteId, workspaceId,
  status, controller @default(agent), controlEpoch Int @default(0), viewportVersion Int @default(1),

}
model BrowserStreamTicket { id, sessionId FK, userId FK, tokenHash unique, expiresAt, usedAt? }   // browser_stream_tickets

  id, taskId FK, sessionId FK, kind ('post'), objectId String(≤64), editUrl String(≤2048),
  state (seen|unverified|verified|missing), verified Json?, createdAt, updatedAt; @@unique([taskId, kind, objectId])

```

`tasks.needs_repository boolean NOT NULL DEFAULT true`, `tasks.needs_browser boolean NOT NULL DEFAULT false`, CHECK `needs_repository OR needs_browser`, триггер неизменяемости. `sites.agent_notes varchar(2000) NULL`. `attachments`: `task_id` NULL, новые `workspace_id`, `site_id`, `status` (`uploading|ready|bound|deleted`), `expires_at`, `bound_at`; ключ `inbox/<wsId>/<id>`.

### 3.5 API worker'а (HTTP JSON, `Authorization: Bearer BROWSER_WORKER_TOKEN`)

| Метод | Кто | Что |
| --- | --- | --- |
| `POST /v1/sessions/ensure` `{ sessionId, taskId, siteId, takeControl: boolean }` | core | создать или найти живую сессию; адрес и стек сайта worker читает из базы по `siteId` (`sites.url`, `sites.stack`) — разрешённые хосты, политика стека и стартовая страница строятся только из них, адреса от вызывающего схема не принимает; подсказки `sites.agent_notes` агент получает в тексте хода, а не через worker; `takeControl` — забрать управление агенту (эпоха +1); ответ — состояние |
| `POST /v1/sessions/:id/close` `{ reason }` | core | закрыть, удалить контейнеры, очистить файлы |
| `POST /v1/sessions/:id/verify` `{}` | core, mcp | проверить все checkpoint'ы задачи, записать и вернуть факты |
| `GET /v1/sessions` | core | список живых для сверки |
| `POST /v1/sessions/:id/actions` `{ taskId, assignmentId, action }` | mcp | действие агента (`action` — объединение `web_*`); ответ — результат или код отказа |
| `WS /v1/sessions/:id/stream?viewer=<uuid>&user=<uuid>` | шлюз | поток кадров, состояния и ввода |

### 3.6 Поток (WSS клиент ↔ шлюз ↔ worker)

Бинарное сообщение кадра: `magic 0x52 'R'` (u8), `version 1` (u8), `kind 1` (u8), `flags` (u8), `frameSeq` u32, `pageId` u32, `viewportVersion` u32, `controlEpoch` u32, `width` u16, `height` u16, `timestamp` f64 (мс), `sessionId` 16 байт → 48 байт, далее JPEG. Текст — JSON, `t`:

- клиент → сервер: `hello { ticket }` (первым, только шлюзу), `ack { frameSeq }`, `pong`, `take`, `release`, `input { pageId, controlEpoch, viewportVersion, event }` (`event`: `mouse { type: move|down|up, x, y, button, clickCount }`, `wheel { x, y, dx, dy }`, `key { type: down|up, key, code, modifiers }`, `text { text }`), `navigate { url }`, `tab { pageId }`, `dialog { id, accept, text? }`, `files { chooserId, attachmentIds }`, `viewport { width, height }` (из списка).
- сервер → клиент: `viewer { viewer }` (первым — шлюз сообщает вкладке её id зрителя; вкладка держит управление, когда `state.controller = user` и `state.holder = viewer`), `state { session, controller, controlEpoch, manualReady, holder, pageId, viewportVersion, viewport, url, title, tabs[], dialog?, chooser?, help?, status }`, `ping { ts }`, `refused { reason }`, `closed { reason }`.

Путь шлюза — `/v1/browser/stream` (`BROWSER_STREAM_PATH`), коды закрытия — `browserStreamCloseCodes` (4000 сессия закончилась, 4400 протокол, 4401 нужен новый билет, 4403 нельзя, 4503 переподключиться позже), оба в `@repo/domain/browser/stream-messages`. Координаты: клиент переводит точку canvas в точку окна браузера с учётом масштаба и полей (`toViewportPoint`, domain), вне изображения — не отправляет.

### 3.7 Инструменты агента (MCP, семейство `web`)

Аргументы и ответы — zod в domain (`browser/tools.ts`), ответ ≤ 64 КиБ. Общие коды: `BROWSER_SESSION_UNAVAILABLE`, `BROWSER_USER_IN_CONTROL`, `BROWSER_STALE_OBSERVATION`, `BROWSER_ACTION_DENIED`, `BROWSER_ADDRESS_DENIED`, `BROWSER_TIMEOUT`, `BROWSER_ACTION_FAILED`, `BROWSER_CHECKPOINT_UNVERIFIED`, `BROWSER_ATTACHMENT_UNKNOWN`, `BROWSER_UPLOAD_REFUSED`. Тексты кодов для агента — по-английски, ни адреса, ни значения поля в отказе.

### Отличия от договора (§3)

1. **Поток (§3.6).** События ввода различаются полем `kind` (`mouse`, `wheel`, `key`, `text`), кнопка мыши `none` — только у `move`; `files.attachmentIds` может быть пустым (отмена выбора файла); `pong` может нести `ts`. Шлюз первым сообщением называет вкладке её id зрителя (`viewer`) — без него вкладка не знала, держит ли она управление (проверка стыков C). Путь и коды закрытия живут в domain (`browser/stream-messages`), код 4403 назван `forbidden` (отказ при входе и при перепроверке). Место в окне кадров освобождает только подтверждение, а не 3 с (отступление от Б13, ревью).
2. **API worker'а (§3.5).** Отказ действия — не 200 `{ok:false}`, а `{code}` со статусом кода (клиент принимает оба); `verify` отвечает `{checkpoints: [...]}` без `editUrl` — его `core` берёт из `browser_checkpoints`; `assignmentId` worker не использует; `viewport_version` в базу не пишется (функции записи нет); внутренних `task_events` (`browser.control`, §2) worker не пишет — передачи управления видны только в строке `browser_sessions` (`controller`, `control_epoch`).
3. **Политика стека (§3.7, Б21).** `browserTaskPolicy` принимает `{ url }` (у сайта в браузере нет `SiteFacts`); `browserCommitAction` возвращает `'publish' | 'save' | null`; чтение проверки — `verified | missing | unreadable`, шаг может брать заголовок из предыдущего (`fromStep`); WordPress читает объект как запись, затем как страницу, через `?rest_route=` (работает и без «красивых» адресов), 401 и 403 — `unreadable`, публичный адрес — только у опубликованных и личных.
4. **Конфигурация.** Во всех трёх приложениях, которые зовут worker (`core`, `mcp`, `preview`): адрес требует токена, токен без адреса не действует; в production `http://` к worker'у — только на частный адрес или loopback. Значения токена по умолчанию в `.env.example` нет: без него `browser` не стартует. `BROWSER_SESSION_MAX_HOURS` читает и `core` (срок строки сессии).
5. **tRPC и web.** Добавлены `attachment.bind` (файл, загруженный из окна выбора файла, привязывается к идущей задаче), коды `ATTACHMENT_REFUSED`, `ATTACHMENT_SENT`, `ATTACHMENTS_LIMIT` (больше 50 неотправленных файлов), `TASK_NOTHING_TO_RESUME`, `BROWSER_UNAVAILABLE`, `PROJECT_NOTES_*`, `SITE_ADDRESS_NOT_SECURE`, `WORKSPACE_KEY_UNAVAILABLE`; `project.create` без `access` — прежний вариант с файлами; задача в браузере на сайте `paused`, `disconnected` или `archived` — `site_not_active`. В панели нет кнопок «Назад» и «Вперёд» (в протоколе нет такого сообщения) — только «Обновить страницу»; мастер — третья вкладка, а не карточки макета (сценарии импорта ищут вкладки по роли); размер окна и вкладки меняет только вкладка, которая держит управление; на телефоне нет масштаба двумя пальцами в режиме агента.
6. **`mcp`.** Сверх договора: контентные инструменты только задаче с репозиторием, `web_open` принимает путь сайта, код `CONTENT_PRIVACY_LIMIT` (413), ключ хода отклоняется в любом аргументе.
7. **Стенд.** Консоль закрыта (Б31), поэтому агент после отказа открывает `/wp-admin/edit.php`; долгая публикация — must-use плагин стенда держит REST-запрос 30 с; браузер ходит к сайту по адресу веб-сервера в сети Docker по умолчанию, а не через `host.docker.internal` (пересылка портов Docker Desktop теряла соединения); «в песочнице не было git» доказывают пустые SHA ходов и манифесты без `git` (локальный исполнитель команды песочницы не журналирует — строка `NOTE`).

Закрыты пять пунктов:

1. **Дубликат после «Продолжить»** (Б22; отклонённое замечание ревью `lifecycle-continue-after-ceiling-duplicates-object`). Запрос каждого хода задачи в браузере — и нового сеанса агента, и продолженного — перечисляет под словами клиента, что задача уже сохранила на сайте: `readPassFacts` читает `browser_checkpoints` всех сессий задачи, кроме `seen`, а `browserContextOf` пишет до 40 последних (о более ранних — числом): подтверждённый — заголовок и статус, неподтверждённый — «сначала `web_verify`», не найденный последней проверкой — «не создавать заново, спросить клиента `web_help`»; checkpoint `verified`, чьи данные проверки не читаются, назван неподтверждённым. Правила `browserTaskInstructions` называют этот список. Worker новый объект после подтверждённого по-прежнему не запрещает (ниже, «Открыто»).
2. **Сборщик неотправленных вложений** (Б26). `TaskSweep.collectAttachments` — последний шаг каждого такта сборщика задач `core` (раз в минуту), до 50 файлов за такт: `listExpiredAttachments` (`@repo/db`) находит файлы `uploading` и `ready`, не отправленные ни с одним сообщением, чей срок истёк больше 15 минут назад (`ATTACHMENT_COLLECT_GRACE_MINUTES`: загрузку, начатую перед сроком, сборщик не обрывает), — сначала самые старые; `collectExpiredAttachments` удаляет объект в `raditi-inbox`, затем `markExpiredAttachmentDeleted` условно отмечает строку `deleted`. Удаление, которое не удалось, оставляет строку следующему такту, остальные файлы пачки идут дальше; лог — не чаще раза в минуту и только код ошибки. Отправленный файл сборщик не трогает. Ключу S3 `core` в production нужно право удаления в `raditi-inbox` (M10).
3. **Путь политики `workspace-provisioner`** (Б32, правило 2). Путь — `transit/keys/+` вместо `transit/keys/ws-*`, по-прежнему `update` с единственным параметром `type=aes256-gcm96`: на OpenBao 2.7.0 создание и повтор — 200, `rotate`, `config`, `trim`, `soft-delete-restore` и `import_version` — 403 с параметрами и без, а повторное создание мягко удалённого ключа оставляет его выключенным. Запрет под glob не работает — проверено на одноразовом OpenBao 2.7.0: `transit/keys/ws-*/*` не действует (`*` внутри пути OpenBao читает буквально), а `transit/keys/+/*` и `transit/keys/+/+` проигрывают `ws-*` (приоритет у правила, у которого первый `+` или `*` стоит дальше от начала). Цена — имя ключа сервер больше не проверяет: web может создать ключ Transit с любым именем — `aes256-gcm96`, неэкспортируемый и неудаляемый, — но ни одна роль им не пользуется: у `core-transit` и `mcp-content` пути только `ws-*`; имя `ws-<uuid>` проверяет клиент (`transitEnsureKey`) до запроса. `verify:vault` проверяет отказы под ключом у `workspace-provisioner` и у токена web, выключенный ключ и ключ с чужим именем (роли `core` и `mcp` на нём — 403); путь политики поправлен и в тесте стенда биллинга (`infra/dev/billing-verify/stand.test.mjs`).
4. **Секретные части адресов страниц** (правило 2, Б20). `@repo/domain/browser/addresses.ts`: значение параметра, в имени которого есть `key`, `token`, `nonce`, `pass`, `pwd`, `secret`, `code`, `hash`, `auth`, `sig`, `reset`, `sess`, `otp`, `jwt`, `ticket` или `credential` (без учёта регистра, и внутри длинного имени: `password`, `signature`, `session`; `author`, `keyword(s)` и `preset` — безвредны), становится `[hidden]`, фрагмент адреса — `#[hidden]` целиком; значение, которое само адрес с секретом (и экранированный до трёх раз, как `redirect_to`), скрывается целиком; повтор ничего не меняет; адрес, который с метками стал бы длиннее 2 048 знаков, получает `?[hidden]` вместо всей строки запроса (`redactBrowserAddress`). Ссылки дерева (`- /url:`) — так же, но фрагмент ссылки сохраняет маршрут и теряет только секретные пары: якоря в тексте записи — содержимое, которое агент правит (`redactTreeAddresses`). Процесс `browser` скрывает адреса в дереве до обрезки и в каждом ответе инструмента (страница, вкладки, адреса `web_verify`), а своё состояние, распознавание checkpoint'ов и результат проверки, который сохраняет `core`, держит с полными адресами; роль `mcp` скрывает их ещё раз перед маскированием контактов (`redactResultAddresses`). Сообщения диалогов, заголовки и текст страницы не меняются.
5. **Описания инструментов `web_*` без WordPress** (правило 8). `web_open`, `web_observe`, `web_fill` и `web_type` больше не называют `/wp-admin/post-new.php` и «редактор блоков» — эти примеры есть в справке WordPress (`browserGuide`); `web_observe` говорит агенту, что секретные части адресов показаны как `[hidden]`; тест `mcp-web-tools.test.ts` не даёт описанию `web_*` назвать `wp-`, `wordpress`, `bitrix` или «block editor».

Остальные расхождения проверки ждут владельца или остаются открытыми (ниже): экраны плагинов со списками после `#`, массовая правка — отказ, а не `request_approval`, управление браузером любым участником рабочего пространства, Битрикс с браузером `ready` в возможностях.

### Интеграция с main `7ef249d` (#12, 23.10.2026)

Работа сделана на `c706a11`; пока она шла, в `main` пришёл #12 (`7ef249d`, [план 56](56-nest-modules.md)): пять приложений — Nest из модулей по разделам (`AppModule.forRoot`, `src/config/` с токеном `<ПРИЛОЖЕНИЕ>_CONFIG`, один раздел — один каталог со своим модулем), код одного приложения — в нём самом: `@repo/runner-engine` растворён в `apps/runner`, `@repo/preview-gateway` — в `apps/preview`, `@repo/turn-keys` разделён по протоколу `core` ↔ `llm` (выдача ключей хода — `apps/core/src/llm`), стенды одного приложения — в его `scripts/`, модуль метрик Nest — из `@repo/service-runtime` в `core`. ### Открыто

- Дубликат после неуспешного хода (например, «Продолжить» после потолка денег посреди хода) держат теперь только запрос и инструкции: новый сеанс агента получает список того, что задача уже сохранила (выше, «Пункты проверки документов», пункт 1), но подтверждённый объект worker создать заново не запрещает — агент, который не последует списку, может сделать вторую такую же запись (из отклонённого замечания `lifecycle-continue-after-ceiling-duplicates-object`).
- Сборщик убирает только неотправленные просроченные вложения: `attachment.remove` отмечает строку `deleted` до удаления объекта, и если удаление в web не удалось, а клиент его не повторил, объект остаётся в `raditi-inbox` — сборщик такие не повторяет; отправленные файлы после срока хранения бакета (90 дней) никто не удаляет; удаления EXIF и детектора ПД в файлах нет (M2); worker читает вложения целиком в память — до 10 × 20 МиБ на вызов.
- Checkpoint знает только вид `post`: объект в ленте — всегда «запись»; записи своих типов темы проверка читает как `missing`. Запись, которую клиент создал руками, остаётся `seen`, если он не работал в её редакторе после появления адреса; правки клиента в редакторе идут в предел 20 объектов агента; запрет после ухода страницы из редактора снимает только клиент, взяв управление.
- Перерыв worker'а дольше примерно 45 с в начале прохода кончает задачу `failed` («Попробовать ещё» у задачи без кандидата нет).
- Политика `workspace-provisioner` у AppRole web (Б32) с путём `transit/keys/+` (выше, «Пункты проверки документов», пункт 3) не проверяет на сервере имя ключа: web может создать ключ Transit с любым именем — неэкспортируемый, неудаляемый и ни одной роли не нужный; имя `ws-<uuid>` проверяет только клиент. Путь и то, кто создаёт ключ — web или `core`, — spec §20, «Путь политики `workspace-provisioner`» (P7) и «Кто создаёт ключ рабочего пространства».
- Экраны плагинов, которые показывают свои списки по адресу после `#` (FluentCRM, `page=fluentcrm-admin`), закрытый список по словам не ловит.
