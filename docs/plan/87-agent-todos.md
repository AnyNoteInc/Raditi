# План 87. План работы агента рядом с чатом

Запрос владельца от 19.11.2026 (дословно): «когда модель вызывает механихм todo давай тамже где и файлы выводятся в случае их создания справа в диалоговом окне добавим карточку с пунктами исполнения по todo для того чтобы показывать агентский прогресс, ознакомся с тем, как устроены todo в других агентах, как они сделаны в opencode и предложи дизайн реализации».

Ответ владельца того же дня — «все по умолчанию, приступай к реализации»: решения ТД1–ТД16 и
значения по умолчанию §11 приняты (spec §20, «План работы агента — решения 19.11.2026»). Сделано в
ветке `feat/agent-todos`; что сделано, чем проверено и что открыто — «Результат» в конце.
Исследование 19.11.2026 шло в четыре линии: OpenCode изнутри по тегу `v1.18.34`
(`anomalyco/opencode`, коммит `aec0b9a6`), механизмы todo у 20 агентов и протоколов, их интерфейс,
путь в коде Радити. Несущие факты перепроверены отдельно: §2 и §3 — уже проверенное. Затем три
независимых дизайна («минимальный», «состояние чата», «опыт клиента») оценили два судьи
(правила и код; клиент и цена). Этот план собран из их выводов.

## 1. Что сейчас

- **Агенту список разрешён, клиенту не виден.** Права драйвера разрешают `todowrite`
  (`packages/agent-drivers/src/opencode.ts:158`), но разбор строки CLI превращает вызов в безымянный
  `tool_call` (`packages/agent-drivers/src/opencode-events.ts:85-138`): вход вызова со списком
  отбрасывается. В «Ходе работы» клиент видит только «Инструмент · `todowrite` · выполнен»
  (`apps/web/src/components/chat/turn-activity.tsx:200-208`): имена инструментов там показаны так,
  как их дал агент (spec §20, «Ход работы»), но о плане эта строка клиенту не говорит ничего.
  Неудачный вызов `todowrite` так и остаётся этой строкой (ТД3). В перечне
  возможностей агентов это строка OW-113, «частично: клиенту список не показывается»
  (`docs/research/2026-11-agent-features/features.md:884`).
- **«Там же, где файлы»** — карточка «Результаты» справа вверху чата
  (`apps/web/src/components/chat/results-card.tsx`, 280 px, липкий блок в правом поле ленты,
  `dialog-view.tsx:1402-1437`). Она показана, только когда сошлись все условия:
  - окно от `lg` (1200 px);
  - есть документ (`documentCount > 0`: только `.html`, `.htm`, `.md`, `.markdown` и документы по
    разделам, `packages/domain/src/tasks/chat-documents.ts:10-15`);
  - область ленты не уже 1008 px (`RESULTS_MIN_AREA`);
  - клиент не скрыл её (`localStorage['raditi.chat.results.hidden']`).

  В чате, где агент сделал только `.xlsx`, карточки нет. Открытая панель «+» сужает ленту и тоже её
  прячет.
- **Путь события хода:**
  1. драйвер превращает строку CLI в `AgentEvent` (`packages/domain/src/ports/agent-driver.ts:352-400`);
  2. исполнитель маскирует строку до разбора (`packages/local-turns/src/turn-output.ts:43-54`);
  3. `core` пишет журнал `task_events` `turn.output` (`client_visible = false`,
     `apps/core/src/turns/turn-journal.ts:69-139`) после `maskTurnEvents`;
  4. `task.activity` отдаёт события по белому списку `shownEvent`
     (`packages/trpc/src/services/chat/activity.ts:23-64`);
  5. страница рисует «Ход работы» (`turn-activity.tsx`, `use-turn-activity.ts`).

  Каждая вставка `turn.output` уже шлёт сигнал `activity` (миграция `20261118140000_task_signals`).
- **Telegram.** Сообщение прогресса берёт последнее событие строки (`#lastEvent`,
  `apps/core/src/telegram/telegram-jobs.ts:592-606`) и строку `activityLine`
  (`apps/core/src/telegram/progress-text.ts:54-74`).

## 2. Как это устроено в OpenCode 1.18.34

- **Инструмент.** В 1.18.34 только `todowrite`, `todoread` нет (`tool/registry.ts`; `todoread` был
  в v1.0.0). Код — `packages/opencode/src/tool/todo.ts:6-45`.
  - Вход — `{ todos: [{ content, status, priority }] }`, и это **весь список целиком**: каждый вызов
    стирает прежний и пишет новый (`session/todo.ts:29-51`).
  - `status` и `priority` — просто строки (`packages/schema/src/session-todo.ts:7-15`). Значения
    «pending, in_progress, completed, cancelled» и «high, medium, low» названы только в описании, а
    модель получает JSON-схему без `enum`. Значит, GLM может прислать любую строку.
  - У пункта нет `id`: пункт узнаётся по месту в массиве.
  - Ответ модели — `output`: тот же список JSON-ом; `title` — «N todos» (не `completed`);
    `metadata` — `{ todos, truncated }`, а при обрезке ещё `outputPath`.
  - Описание инструмента у нас то же, что в `todowrite.txt` (2012 знаков совпали). Оно само велит
    модели «Use proactively when… 3+ distinct steps», держать ровно один `in_progress` и обновлять
    статус сразу.
- **Хранение.**
  - В обычном OpenCode список — таблица `todo` в `opencode.db`, один на сессию, со своим событием
    `todo.updated` и `GET /session/:id/todo`.
  - **В Радити таблица пуста в начале каждого хода.** Обёртка переносит сессию через
    `opencode export` → удаление `~/.local` → `opencode import`, а экспорт и импорт таблицу `todo` не
    несут (`packages/agent-drivers/src/opencode-wrapper.ts:604-646`; OpenCode `cli/cmd/export.ts:287`,
    `import.ts:187-215`). Прежний список модель видит только в истории своих вызовов. После `/undo`
    его нет и там: снимок отменённого хода не восстанавливается.
  - Значит, **последний список хранит и показывает платформа**, из своего журнала.
- **Что печатает `opencode run --format json`.** Строка `tool_use` появляется только по завершении
  вызова (`completed` или `error`, `cli/cmd/run.ts:678-691, 720-726`):

  ```json
  {"type":"tool_use","sessionID":"ses_…","part":{"type":"tool","tool":"todowrite","callID":"call_…",
   "state":{"status":"completed",
     "input":{"todos":[{"content":"…","status":"in_progress","priority":"high"}]},
     "output":"[\n  {\n    \"content\": …", "title":"2 todos",
     "metadata":{"todos":[…],"truncated":false}, "time":{"start":…,"end":…}}}}
  ```

  Источник списка — `input.todos`, а не `output`: `output` режется по 50 КиБ. Строку длиннее
  256 КиБ раннер не разбирает вовсе (`packages/local-turns/src/turn-output.ts:19-25`), поэтому
  предел пунктов ставит драйвер.
- **Интерфейсы самого OpenCode.**
  - TUI: раздел «Todo» в правой колонке стоит над «Modified Files» — ровно схема запроса владельца
    (`packages/tui/src/feature-plugins/sidebar/todo.tsx`). Раздел виден, пока есть хоть один пункт не
    `completed`; отметки `[✓]`, `[•]`, `[ ]`.
  - Веб и десктоп: «док» над полем ввода со счётом «Выполнено 2 из 5» и текстом текущего пункта; в
    ленте `todowrite` скрыт. Док закрывается, когда всё сделано, а список, оставшийся после конца
    работы, стирается: «Keep stale turn todos from reopening if the model never clears them»
    (`packages/app/src/pages/session/composer/session-composer-state.ts:13-24`).
- **Субагенты** (`task`) у нас запрещены (`opencode.ts:161`), поэтому вопроса о чужих списках нет.
- **Не подтверждено:** вызывает ли GLM-5.3 `todowrite` на настоящих многошаговых заданиях и на
  каком языке пишет пункты. В записях и фикстурах репозитория нет ни одного такого вызова. Замер —
  срез 87.0.

## 3. Как у других

**Механизм.** Почти все присылают список целиком и не присылают правку: последний снимок побеждает.

| Агент или протокол | Механизм | Пункт | Статусы |
| --- | --- | --- | --- |
| OpenCode 1.18.34 | `todowrite`, целиком | content, status, priority | pending, in_progress, completed, cancelled (только в тексте) |
| Claude Code | `TodoWrite`, целиком; с v2.1.268 у новых моделей — `TaskCreate`/`TaskUpdate` по id | content, status, activeForm | pending, in_progress, completed (+ deleted у Task*) |
| Codex | `update_plan`, целиком (`codex-rs/protocol/src/plan_tool.rs`) | step, status; explanation у плана | pending, in_progress, completed |
| Gemini CLI | `write_todos`, целиком | description, status | + cancelled, blocked |
| Kimi Code | `TodoList`, целиком; `/undo` откатывает | title, status | pending, in_progress, done |
| Copilot (VS Code) | `manage_todo_list`, целиком | id, title, status | not-started, in-progress, completed |
| Cursor | `todo_write` с `merge` | id, content, status | + cancelled |
| ACP v1 / v2 | `session/update` `plan` / `plan_update` — «Agent MUST send a complete list… Client MUST replace» | content, priority, status | v2 — + cancelled |

Общее у всех — упорядоченный список «текст + статус». Приоритет показывают только OpenCode и ACP, а
адаптеры ACP ставят постоянное `"medium"`; `id` нужен только тем, кто правит по одному пункту. Новые
модели всё чаще обходятся без списка: Claude Code с v2.1.268, Amp убрал его 12.01.2026. Карточка
должна спокойно жить и без списка. Подробная таблица 20 агентов с источниками — в отчёте
исследования, строка OW-113 перечня возможностей.

**Интерфейс.** Повторяются пять решений:

1. **Одно место по ширине окна.**
   - На широком экране — боковая колонка рядом с файлами. Так у Claude Cowork («Progress» рядом с
     файлами и контекстом), ChatGPT Work («It can surface the agent's plan, sources, generated
     files», https://learn.chatgpt.com/docs/artifacts-viewer.md), Devin («Progress» —
     https://docs.devin.ai/release-notes/overview), OpenCode TUI.
   - На узком — одна строка над полем ввода, которая раскрывается вверх: VS Code, OpenCode desktop,
     Gemini, Coze, OpenClaw (https://docs.openclaw.ai/tools/progress-card).
2. **В свёрнутом виде** — счёт сделанного и текущее дело: «Выполнено 2 из 5» (OpenCode),
   «Todos (3/5)» (VS Code), «第 X/Y 步» (Coze). Счёт «номер текущего шага» прыгает, когда модель
   добавляет пункты; честнее «сделано 2 из 5».
3. **Отметки.** Пустой кружок — впереди; пульсирующая точка или выделение — сейчас; галочка и
   приглушённый перечёркнутый текст — сделано; пропущенное — отдельно.
4. **Один снимок на одном месте**, а не блок на каждое обновление. TUI OpenCode повторяет «# Todos»
   на каждый вызов; Factory такие строки убрал.
5. **Конец работы.** Незаконченное не отмечают сделанным (OpenClaw); спиннер без работы не крутят;
   сделанный список свёрнут до следующего запроса (VS Code); незаконченный старый список не
   всплывает в новой работе (OpenCode desktop).

**Чего избегать.** Ошибки Claude Cowork, исправленные по жалобам:
- панель открывается пустой, и выбор не запоминается (#81972);
- панель закрывает ответ и поле ввода в узком окне (v4.4212.0);
- шаги не отмечаются (#67516);
- после переоткрытия чата список пуст, а пункт без текста превращается в «Task #15» (#93910).

Для нашего клиента к этому добавляются ещё две вещи:
- приоритеты, английские пункты, пути и команды — жаргон;
- выдуманные проценты.

## 4. Решения

- **ТД1. Название — «План работы».** «Задачи» уже занято рейкой (запланированные задачи), «Ход
  работы» — живой лентой прохода, а «План» один легко спутать с режимом «Сначала план», который
  владелец убрал.
- **ТД2. Новое общее событие `todo_list` — снимок всего списка.**
  - Пункты `{ text, status }`, четыре статуса ACP v2: `pending`, `in_progress`, `completed`,
    `cancelled`.
  - Каждое событие заменяет прежнее; `items: []` — списка нет.
  - Без `id`, `priority` и `activeForm`: их нет у OpenCode или их не показывает никто.
  - Правило 8: имя `todowrite` живёт только в адаптере; `core`, tRPC, web и Telegram знают одно
    `todo_list`.
  - Будущие драйверы ложатся на это событие без изменений: Claude `TodoWrite` один к одному, Codex
    `step` → `text`, ACP `entries` → `items`, а `Task*` по id драйвер сам сводит в снимок, как
    адаптер Claude для ACP.
- **ТД3. Драйвер выпускает `todo_list` вместо `tool_call` у удачного `todowrite`.**
  - Источник — `input.todos`, запасной — `metadata.todos`.
  - Статус драйвер приводит к одному из четырёх, неизвестный считает `pending`.
  - Текст чистит по правилам ленты: `feedText` и `hasVisibleText` из домена — без невидимых,
    bidi-знаков и меток `[[raditi:…]]`.
  - Пределы (50 пунктов, 300 знаков) драйвер ставит **до** схемы: `events()` молча роняет событие,
    не прошедшее её (`packages/agent-drivers/src/jsonl.ts:76-80`).
  - Вызов с ошибкой и вход без списка остаются прежним `tool_call`.
- **ТД4. Список хранится в журнале хода, отдельного состояния нет.**
  - Читается последний `todo_list` засчитанных ходов: `undone_at IS NULL`. Поэтому `/undo` и
    `/redo` работают без нового кода — они меняют только `undone_at`.
  - Чтение — по новому частичному индексу `task_events_todo_list_idx`: `(turn_id, id)` только по
    строкам `turn.output` с событием `todo_list`.
  - Столбца в `task_turns` нет: он правил бы горячий оператор журнала под оградой аренды
    (`turn-journal.ts:89-139`) и давал бы второй источник истины. Головы `task.feed` тоже нет:
    spec §8 держит проекцию ленты независимой от событий оболочки.
- **ТД5. Какое состояние показывать, решает чистая функция домена `chatTodoOf`** по двум последним
  засчитанным ходам (§5.4). Вопрос решается по последнему ходу:
  - **Нет списка — нет карточки.** Ход, закончившийся без списка, убирает прежний список: та же
    защита, что «Keep stale turn todos» у OpenCode.
  - **Исключение — `carried`.** Пока идёт ход после удачного хода с незаконченным списком, а своего
    списка ещё не записал, показан прошлый: модель продолжает ту же сессию. После сбоя сессия новая
    (`apps/core/src/tasks/turn-planner.ts:497`), поэтому `carried` там нет.
  - **Порог показа — два пункта.** Список из одного пункта карточкой не показывается.
- **ТД6. Широкий экран — отдельная карточка «План работы» над «Результатами»**, в той же липкой
  колонке справа, той же ширины 280 px.
  - Колонка показана при `wide && (documentCount > 0 || plan !== null)`: план появляется и в чате
    без документов.
  - Значок в шапке чата прячет и показывает всю колонку.
  - Выбор хранится под новым ключом `raditi.chat.side.hidden`. Если оставить
    `raditi.chat.results.hidden`, клиент, который когда-то скрыл «Результаты», план не увидел бы
    никогда. Цена нового ключа: прежний выбор «скрыть» один раз сбрасывается.
- **ТД7. Узкое окно, планшет и телефон — строка над полем ввода.** Это всё, где колонка не
  помещается: ниже `lg`, лента уже 1008 px, открыта панель «+».
  - Одна строка «Сделано 2 из 5 · Сейчас: …» в липком блоке поля ввода.
  - Видна только пока идёт ход (`working`, `carried`).
  - Стартует свёрнутой; нажатие раскрывает список вверх, до 40vh.
  - Поле ввода и последний ответ она не закрывает.
  - Вкладки в «+» нет: план — не инструмент, правило плана 59 «по умолчанию только чат» остаётся.
- **ТД8. «Ход работы».**
  - Вместо «Инструмент · `todowrite`» — строка «План работы · сделано 2 из 5», которая
    раскрывается в снимок списка на тот момент.
  - Новая строка — только когда сменился счёт сделанного или текущий пункт: переписывание списка на
    каждом шаге не плодит строк.
  - У закончившегося хода так остаётся история его списков.
  - `/thinking` на план не влияет: план — не мысли.
- **ТД9. Telegram.** `case 'todo_list'` в `activityLine` даёт строку «План: сделано 2 из 5 · сейчас:
  <пункт>», пункт обрезается до 80 знаков. Строка берётся из самого события, нового чтения нет.
  Без этого `case` сообщение прогресса после вызова сменилось бы на «Разбирается в задаче»: это
  регрессия, а не возможность.
- **ТД10. Инструкции хода говорят, как писать пункты, а не просят вести список.** Описание
  инструмента уже велит вести его на работе от трёх шагов. Каждый лишний вызов — лишний запрос
  модели с полным контекстом, то есть кредиты клиента (правило 7). Одна строка в `## How you work`
  (`apps/core/src/tasks/turn-instructions.ts:337`), по-английски, как весь файл:
  - пункты по-русски, простыми словами для клиента, до 7;
  - без путей, команд, кода, имён инструментов, секретов и значений переменных;
  - обновлять список, когда шаг начат и когда кончен, а не чаще;
  - перед ответом отметить сделанное `completed`, а брошенное `cancelled`; если ход кончается
    вопросом клиенту, пункты впереди оставить как есть — иначе `carried` и шапка «Ждём вашего
    ответа» не случились бы никогда (второе ревью 19.11.2026).
- **ТД11. Список не по-русски** — если ни в одном пункте нет кириллицы, карточка, строка над полем
  и Telegram показывают только счёт «Шаг 2 из 5», без текста пунктов. Кнопки «Показать как написал
  агент» нет: это было бы новое исключение из правила 10 рядом с мыслями, и решает его владелец
  (§11, вопрос 3). Проверка — по всему списку: поштучная замена на «Шаг N» дала бы клиенту список
  из «Шаг 1, Шаг 2…».
- **ТД12. Живое обновление без новых сигналов.**
  - Страница перечитывает `task.todo` по сигналу `activity` (не чаще раза в секунду), пока ход
    идёт, и при смене хода или статуса чата.
  - Без живого потока SSE — опрос раз в 5 с, пока ход идёт.
  - Закончившийся ход не опрашивается.
- **ТД13. Флага возможности драйвера нет**, пока драйвер один: инструкция говорит «your to-do tool»
  без имени. Флаг `AgentCapabilities.todoList` — со вторым драйвером, по образцу `compaction`.
- **ТД14. Проверка безопасности текста — та же, что у остального вывода агента.**
  - Значения переменных клиента маскирует исполнитель до разбора и `maskTurnEvents`; ключ хода в

## 5. Договоры

### 5.1. Событие — `packages/domain/src/ports/agent-driver.ts`

```ts
export const agentTodoStatuses = ['pending', 'in_progress', 'completed', 'cancelled'] as const
// agentOutputLimits: todoItems: 50, todoText: 300; the bound of `omitted` (10 000) is
// agentTodoLimits.omitted of tasks/agent-todo.ts, which builds the fields (agentTodoListShape)
z.object({
  type: z.literal('todo_list'),
  /** The agent's whole list at this moment; it replaces the one before. [] — no list. */
  items: z
    .array(z.object({
      text: z.string().min(1).max(limits.todoText),
      status: z.enum(agentTodoStatuses),
    }))
    .max(limits.todoItems),
  /** Items the driver left out over the limit: completed ones from the head, the rest from the tail. */
  omitted: z
    .object({
      completed: z.number().int().min(0).max(agentTodoLimits.omitted),
      other: z.number().int().min(0).max(agentTodoLimits.omitted),
    })
    .optional(),
})
```

Это двенадцатое событие: тест `agent-driver.test.ts:57-75` требует ровно этот набор. Список событий
меняется и в spec §8 (`docs/spec.md:504`), и в правиле 8 `CLAUDE.md`.

### 5.2. Драйвер — `opencode-events.ts`, ветка `todowrite` в `toolEvents`

1. **Источник.** `state.status === 'completed'` и `input.todos` — массив; иначе берётся
   `metadata.todos`. Если массива нет и там, остаётся прежний `tool_call`.
2. **Статус.** Строка приводится к нижнему регистру, затем:
   - `completed`, `complete`, `done`, `finished` → `completed`;
   - `in_progress`, `in-progress`, `active`, `blocked` → `in_progress`;
   - `cancelled`, `canceled`, `skipped` → `cancelled`;
   - остальное → `pending`.
3. **Текст.**
   - Сначала `feedText` (он убирает U+0000, половины суррогатных пар, невидимые и bidi-знаки и
     метки `[[raditi:…]]`), затем пробелы и переводы строк — в один пробел и `trim`. Порядок
     обратный первому замыслу: `text()` из `jsonl.ts` заменил бы половину пары видимым U+FFFD, а
     убранные после схлопывания знаки оставили бы двойные пробелы.
   - Пункт без `hasVisibleText` отбрасывается.
   - Длиннее 300 знаков — 299 знаков и «…».
4. **Больше 50 пунктов.**
   - Сначала с головы снимаются `completed`, их число идёт в `omitted.completed`.
   - Затем режется хвост: пункты не `cancelled` идут в `omitted.other`, а `cancelled` в хвосте не
     считаются.
   - Текущий пункт так остаётся виден.
5. **Что выпускается.** Только `todo_list`, без `tool_call 'todowrite'`. Память это не задевает:
   `memoryPassEvidence` и так считает `todowrite` внутренним (`packages/domain/src/memory/evidence.ts:28-29`).

### 5.3. Чтение — `@repo/db` и tRPC

- **Миграция `20261119200000_task_events_todo_list`** — один частичный индекс:

  ```sql
  CREATE INDEX task_events_todo_list_idx ON task_events (turn_id, id)
    WHERE type::text = 'turn.output'::text
      AND payload @> '{"events": [{"type": "todo_list"}]}'::jsonb;
  ```

  - Тот же индекс объявляется в `schema.prisma` через `@@index(..., where: raw(...))` с приведениями
    типов, как PostgreSQL хранит предикат. Без этого сверка схемы в `verify:db` упадёт. Предикат
    запроса пишется дословно как в индексе.
  - Затраты: в production около 22 500 строк `task_events` (61 МБ, план 86, §6). Частичный индекс
    `task_events_feed_xact_idx` на вчетверо большей базе строился 16,5 мс; записи ждут построения под
    `SHARE`.
- **`readChatTodo(db, taskId)`** в `packages/db/src/agent-todo.ts` — один `$queryRaw`:

  ```sql
  WITH recent AS (
    SELECT id, turn_no, status, rejected_at FROM task_turns
    WHERE task_id = $1 AND undone_at IS NULL ORDER BY turn_no DESC LIMIT 2)
  SELECT r.turn_no, r.status, r.rejected_at IS NOT NULL AS rejected, e.list
  FROM recent r LEFT JOIN LATERAL (
    SELECT (SELECT ev FROM jsonb_array_elements(t.payload->'events') WITH ORDINALITY a(ev, n)
            WHERE ev->>'type' = 'todo_list' ORDER BY n DESC LIMIT 1) AS list
    FROM task_events t
    WHERE t.turn_id = r.id AND t.type = 'turn.output'
      AND t.payload @> '{"events": [{"type": "todo_list"}]}'
    ORDER BY t.id DESC LIMIT 1) e ON true
  ORDER BY r.turn_no DESC
  ```

  Найденное событие проверяется `agentEventSchema.safeParse`: событие, не прошедшее схему, считается
  отсутствующим.
- **`task.todo({ taskId })`** — `packages/trpc/src/services/chat/todo.ts`:
  - доступ — `accessibleTask`;
  - выход — строгая `chatTodoSchema.nullable()`: `{ turn, state, items, omitted? }`, не больше
    50 × 300 знаков;
  - курсора нет, это снимок.
- **`task.activity`.** Вариант `todo_list` в `shownEvent` и `shownActivity`; `textOf` считает тексты
  пунктов. Комментарий `activity.ts:9-11` поправить: у строк `turn.output` теперь второй читатель.

| Последний засчитанный ход | Его список | Состояние |
| --- | --- | --- |
| `pending`, `running` | есть | `working` |
| `pending`, `running` | ещё нет; предыдущий — `completed`, не `rejected`, со списком, где остался `pending` или `in_progress` | `carried` (список предыдущего) |

| любой | нет (кроме `carried`), меньше двух пунктов или меньше двух неотменённых шагов — кроме списка, отменённого целиком | `null` |

## 7. Крайние случаи

| Случай | Что видно |
| --- | --- |
| `[]` или один пункт | карточки и строки нет; в «Ходе работы» — строка: у `[]` «План работы · агент убрал план», у одного пункта — счёт |
| Один шаг и отменённые пункты | карточки нет: считаются неотменённые шаги; список, отменённый целиком, показан как «Агент отменил этот план» |
| Список по-английски с `[скрыто]` в пункте | только счёт: слова, которые вставляет платформа, русским списком его не делают |
| 100 пунктов | драйвер режет, «и ещё N шагов», счёт честный (с `omitted`) |
| Два `in_progress` | текущий — первый, у остальных точка без пульса |
| Всё `cancelled` | «Агент отменил этот план», свёрнута |
| Список переписан на каждом шаге | снимок заменяется; в «Ходе работы» строка — только при смене счёта или текущего пункта |
| Ход без списка после хода со списком | пока ход идёт — `carried`, если прошлый удачный и не закончен; после хода — карточки нет |
| `/undo`, `/redo` | считаются ходы с `undone_at IS NULL`: отменённый список уходит, возвращённый приходит |
| `/compact` | строк `tool_use` нет; во время сжатия — `carried`, после — карточки нет |
| Сбой, «Попробовать ещё» | `failed`, незаконченное не отмечено; следующий ход — новая сессия, не `carried` |
| «Остановить» | `stopped` |
| Чат открыт через несколько дней | состояние читается из базы, карточка на месте (жалоба Cowork #93910 — у нас нет) |
| Запуск запланированной задачи без надзора | так же; клиент видит `ended`, когда откроет чат |
| Строка `tool_use` больше 256 КиБ | её заменяет `SKIPPED_LINE_MESSAGE`, карточка держит прежний снимок |
| Первый список посреди хода в чате без документов | колонка появляется, лента сужается на 304 px — как с первым документом |

## 8. Правила

- **1.** Пункты лежат в PostgreSQL в России (`task_events`), модели ничего нового не уходит. В
  Telegram они идут только чатам, привязанным к нему: это исключение Т1, тот же класс данных, что
  ответы агента.
- **2.** Секретов пункты не несут: значения переменных маскируются, ключ хода роняет ход,
  инструкция запрещает секреты. Vault не участвует.
- **7.** Показ кредитов не стоит. Стоят вызовы `todowrite`: модель, скорее всего, делает
  отдельный шаг на каждый вызов. Поэтому список не навязываем (ТД10), а цену меряем (87.0).
- **8.** Имя `todowrite` — только в драйвере OpenCode (`opencode-todo.ts`, ветка в
  `opencode-events.ts`, разрешение в `opencode.ts`). Исключение было и до плана: список
  «внутренних» инструментов памяти в `packages/domain/src/memory/evidence.ts` (план 84) — неудачный
  вызов остаётся `tool_call 'todowrite'` и не должен переводить память прохода в «Предложено».
- **10.** Все подписи по-русски. Пункты — слова агента клиенту: русский язык держит инструкция, а
  список без кириллицы показывается только счётом (ТД11).
- **zod на границах:** `agentEventSchema` (драйвер, протокол раннера, журнал), строгие `shownEvent`
  и `chatTodoSchema`.
- **dependency-cruiser.** Новых пакетов и правил нет:
  - `db` зависит от `domain`;
  - `trpc` — от `db` и `domain`;
  - `core` — от `db`;
  - web берёт подпуть домена без ввода-вывода.

## 9. Срезы

- **87.0. Замер, только чтение.** Запрос к production считает ходы, ходы от пяти вызовов
  инструментов, ходы с `todowrite` и число таких вызовов на ход. Текст из базы не выгружается: в
  `payload` ищется событие `tool_call` с `tool = 'todowrite'` (строки до выпуска плана 87) или
  событие `todo_list` (после него — удачный вызов пишется только так). Строки после выпуска
  считаются отдельно: инструкция ТД10 меняет поведение модели. Плюс один многошаговый синтетический
  чат в dev на плане: язык пунктов и разница входных токенов с инструкцией ТД10 и без неё.
  - Если в ходах от пяти инструментов `todowrite` встречается реже чем в каждом пятом, — к
    владельцу с вопросом «просить ли агента вести план» и ценой.
- **87.1. Домен.**

## 11. Вопросы владельцу

У каждого — значение по умолчанию; владелец принял все 19.11.2026 («все по умолчанию, приступай к
реализации»).

1. **Название — «План работы»?** По умолчанию да.
2. **Просить ли агента вести план на работе от трёх шагов?** По умолчанию нет: инструкция говорит
   только, как писать пункты, а вести список агента просит само описание инструмента. Каждый вызов —
   кредиты клиента. Вернуться к вопросу после замера 87.0.
3. **Список, записанный не по-русски?** По умолчанию только счёт «Шаг 3 из 5», без кнопки «Показать
   как написал агент». Кнопка была бы новым исключением из правила 10, как мысли по `/thinking`.
4. **С какого числа пунктов показывать карточку?** По умолчанию — от двух.
5. **Что видно после хода?** По умолчанию:
   - на широком экране выполненный план свёрнут в строку до следующего хода, незаконченный
     развёрнут;
   - на узком строка над полем уходит, план остаётся в «Ходе работы».
6. **Переключатель в шапке?** По умолчанию прячет всю колонку — план и результаты — под новым
   ключом. Прежний выбор «скрыть результаты» один раз сбросится.
7. **Строка плана в сообщении прогресса Telegram?** По умолчанию да.
8. **Лента сужается на 304 px, когда первый список приходит посреди хода в чате без документов?** По
   умолчанию так и оставить — как с первым документом. Альтернатива — держать место колонки с
   начала хода.
9. **Клик по пункту?** По умолчанию в первой версии ничего; позже — переход к месту в «Ходе работы».

## 12. Не подтверждено

- **Модель.** Зовёт ли GLM-5.3 `todowrite` — замер 87.0: редко, в 7 % ходов от пяти инструментов. На каком языке пишет пункты — по событиям `todo_list` после выпуска.
- **Сжатие.** Что из списка попадает в сводку `/compact`: сводку пишет модель по шаблону
  «Work State / Next Move» OpenCode.

  `doom_loop: 'deny'` (`packages/agent-drivers/src/opencode.ts:165`).
- **Цена.** Цена списка во входных токенах следующих запросов: весь список повторяется в истории
  сессии и на следующих ходах.
