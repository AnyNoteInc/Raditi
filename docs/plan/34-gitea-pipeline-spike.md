# N18 (линия B; P8, P9, P14): спайк пайплайна сайта на настоящей Gitea 1.27.3

04.10.2026 на настоящей Gitea 1.27.3 с двумя раннерами gitea/runner 4.0.0 и настоящим OpenBao 2.7.0 проверено то, на чём стоят правила 3 и 6 и критерии 4–5 локального гейта: обязательный workflow из `platform/ci`, очередь выкладок, вебхуки, одноразовая обёртка токена, автооткат, границы контейнера задания. До этого дня ничего из этого ни разу не запускалось.

Это спайк: он отвечает на вопросы и показывает доказательства. Шаги выкладки — подмены над файлом-меткой, настоящих `backup`, `deploy` и `verify` нет. Замен тому, что в Gitea устроено иначе, чем записано в spec §10, спайк не строит: расхождения перечислены ниже, решения по ним — у владельца.

Всё проверено локально, на одноразовых контейнерах и синтетических данных. Корневой `.env`, dev-инфраструктура (в том числе профиль `ci`), настоящие токены и подписки не использовались. Образ `gitea/runner:4.0.0` (`sha256:7b5aa113…689f`) — тот же, что в `infra/dev/docker-compose.yml`; его один раз загрузил ведущий (по его записи — с разрешения владельца от 04.10.2026). Стенд сам ничего не скачивает и сверяет digest.

## Расхождения со spec §10

Каждый пункт — что записано, что делает Gitea 1.27.3 и что из этого следует. Запросы и ответы — из прогона стенда.

1. **Источник уровня организации — только её собственный репозиторий.** Spec: обязательные workflow организации лежат в отдельном репозитории `platform/ci`. Gitea: `POST /org/sites/settings/actions/scoped-workflows/add` с `repo_name=platform/ci` (и `ci`) — 400 «Repository not found.», с `repo_name=other` (репозиторий самой `sites`) — 200. Отдельный `platform/ci` можно зарегистрировать только на весь экземпляр: `POST /-/admin/actions/scoped-workflows/add` — 200. Тогда workflow запускается в каждом репозитории Gitea, включая сам `platform/ci`. Поэтому у каждого задания стоит `if: gitea.repository_owner == 'sites'`; запуск в `platform/ci` получает `skipped`.
2. **Регистрация — только веб-форма администратора.** REST API для scoped workflows нет: в описании API (308 путей) нет ни одного. Форма принимает сессию администратора: без сессии — 303 на вход, от бота — 403, с заголовком `Sec-Fetch-Site: cross-site` — 403. CSRF-токена у форм Gitea 1.27 нет. Следствие: регистрация источника и отметка «обязательный» — шаг оператора при установке Gitea (M10), а не вызов `GitProvider`.
3. **«Обязательный нельзя отключить» верно только для настроек workflow.** Пока workflow не отмечен обязательным, его можно отключить в репозитории сайта (200; в стенде — сессией администратора). После отметки — 400 «This scoped workflow is required and cannot be disabled.». Отметка требует хотя бы один шаблон статуса; у `deploy.yml` это статус `check`, иначе pull request в защищённую ветку нельзя было бы слить: свой статус `deploy` ставит только после merge. Но владелец организации может выключить Actions в репозитории целиком (`PATCH /repos/sites/other` с `has_actions=false` — 200; участнику с правом записи — 403): push за это время не даёт ни одного запуска.
4. **Файл workflow в репозитории сайта отменяет идущую выкладку.** Файл `.gitea/workflows/attack.yml` на ветке `attack/1` с той же группой `concurrency` и `cancel-in-progress: true` отменил обязательный `deploy` посреди шага выкладки: запуск — `cancelled`. Метка сайта в этот момент была в состоянии `deploying`.
5. **Файл workflow в репозитории сайта встаёт рядом с обязательным.** `.gitea/workflows/deploy.yml` (и `.github/workflows/deploy.yml`) с тем же именем `deploy` даёт второй запуск того же коммита. Он идёт на раннере `deploy`, видит том сайта и секрет Actions с обёрткой. В REST API оба запуска неотличимы: `path` у обоих `deploy.yml@refs/heads/main`. Отличает их только поле `workflow.path` в теле вебхука: `.gitea/scoped_workflows/deploy.yml` против `.gitea/workflows/deploy.yml`.
6. **Шаг отката с `if: failure()` при отмене не выполняется.** В отменённом запуске шаг с `if: failure()` — `skipped`, шаги с `failure() || cancelled()` и `always()` — `success`. Пример из spec оставил бы сайт наполовину выложенным. В `ci/` условие — `(failure() || cancelled()) && steps.backup.outcome == 'success'`: отменённая выкладка возвращена, метка прежняя, токен отозван.
7. **`concurrency` — не очередь.** Spec: «выкладки одного сайта идут строго по очереди». Одновременно двух выкладок сайта действительно нет, но ждать может только одна: следующая её отменяет. Порядок держит аренда сайта в PostgreSQL, как и записано в spec; `concurrency` — страховка.
8. **Бот с правом записи не может поставить секрет выкладки.** Spec: бот — пользователь с правом записи в `sites`. Gitea: `PUT /repos/sites/demo/actions/secrets/…` от участника команды с правом `write` — 403 «user should be the owner of the repo»; запись переменной (`POST …/actions/variables/…`) — тоже 403. Тот же токен (`write:user`, `write:repository`) получает 201, когда бот входит в команду Owners организации. Тогда этим же токеном выключаются и Actions (пункт 3).
9. **Токен задания по умолчанию пишет в свой репозиторий.** Чужие репозитории закрыты, как и записано: другой сайт и `platform/ci` — 404; список секретов и запись переменной — 403. Но запись кода в свой репозиторий — 201: режим по умолчанию у Gitea — `permissive`. С `permissions: contents: read` в файле workflow — 403. В `ci/` это объявлено в обоих файлах.
10. **Порт не различает обязательный workflow и файл сайта.** `parseGiteaWebhook` отдаёт для обоих запусков из пункта 5 одно и то же имя `deploy`: в `WorkflowRun` порта нет пути файла workflow. `workflow_job` парсер не знает (`null`): в `GitWebhookEvent` нет события задания, а только оно называет упавший шаг. Запасной путь — опрос `listWorkflowRuns` — отличить запуски не сможет вовсе.

Наблюдение вне вопросов плана, вручную на Gitea разведки (стенд этого не утверждает — зависит от времени). Gitea обрабатывает push после ответа клиенту, и запуск берёт голову ветки на момент обработки. Четыре push подряд дали четыре запуска, все — с `head_sha` последнего коммита; три получили `cancelled`. Искать запуск выкладки по коммиту merge надёжно, пока в `main` до обработки события не попал другой push; при аренде сайта так и есть.

### Настройка, которая закрывает пункты 4, 5 и 10

`[actions] WORKFLOW_DIRS` задаёт каталоги, где Gitea ищет файлы workflow в репозитории; каталог scoped workflows задаётся отдельно (`SCOPED_WORKFLOW_DIRS`). Вторая Gitea стенда запущена с `WORKFLOW_DIRS = .git/raditi-no-repository-workflows`. Путь внутри `.git` закоммитить нельзя: API отвечает 422. Результат: три push в репозиторий сайта, где лежат `.github/workflows/deploy.yml` и `.gitea/workflows/deploy.yml`, дали ровно по одному запуску; `GET …/actions/workflows` — 0. Какой файл дал запуск, говорит вебхук: у всех трёх `workflow.path` — `.gitea/scoped_workflows/deploy.yml`, то есть обязательный `deploy.yml` из `platform/ci`. На первой Gitea такой push даёт два запуска.

Раннера у второй Gitea нет: её запуски создаются и остаются в очереди, шаги на ней не выполнялись. Отмену выкладки файлом с ветки на ней отдельно не повторяли.

С этой настройкой запуск по файлу из репозитория сайта не создаётся — значит, ни отменить выкладку, ни встать рядом ему нечем, и правило 6 держится самой Gitea, а не только `DiffPolicy`. Цена: на этом экземпляре Gitea не работает ни один обычный workflow, в любом репозитории. Включать ли её — вопрос владельцу.

Без неё правило 6 держится на двух вещах. Первая — `DiffPolicy` отклоняет дифф агента с `.gitea/` и `.github/`; это проверяет `pnpm verify:gitea`. Вторая — импорт сайта (P11) не должен занести такие каталоги из кода клиента; этого кода ещё нет.

## Контейнер задания

Раннеров два, как в spec §10, у каждого своя сеть Docker.

| Что | `check` | `deploy` |
| --- | --- | --- |
| Пользователь, права | uid 0, capabilities Docker по умолчанию (`00000000a80425fb`), `no_new_privs` нет, корень доступен на запись | то же |
| Сокет Docker | нет (`docker_host: '-'`) | нет |
| Том сайта | нет | есть |
| OpenBao | недоступен | доступен |
| Gitea | доступна | доступна |
| Выход наружу | маршрут по умолчанию есть, порт на хосте достигнут; в интернет стенд не ходил | то же |
| Секрет Actions репозитория | виден любому workflow репозитория | то же |

«Недоступен» у OpenBao значит: порт `openbao:8200` в сети Docker раннера `check` закрыт. При этом задания обоих видов достигли порта на loopback хоста (приёмник вебхуков), а порт OpenBao стенд публикует там же, для себя; обращение к нему из задания `check` стенд не пробовал. Отделить `check` от Vault на деле должна сеть машин раннеров (M10); стенд показывает только разделение сетей Docker.

Раннеру нужен сокет Docker — это root на его машине. Задания создаёт раннер через тот же демон: на общей с чем-либо машине они соседи остальных контейнеров. Ограничения контейнера задания (`cap-drop`, `no-new-privileges`, gVisor, закрытый выход наружу) задаются в `container.options` раннера и сетью машины; стенд их не настраивал и не проверял — это M10.

## Что проверяет стенд

- Источник: организация принимает только свой репозиторий; регистрация на экземпляр — только сессией администратора; REST API нет.
- Обязательность: необязательный workflow отключается, обязательный — нет; REST о scoped workflow не знает.
- Права бота: секрет и переменная Actions — только владелец организации.
- Push в `main` без живой обёртки: выкладка останавливается на `vault-login`, сайт не тронут.
- Q1: `check` на pull request со статусом коммита; `deploy` после merge; `GET …/actions/workflows` сайта — 0; запуск в самом `platform/ci` — `skipped`.
- Q4: три вебхука `workflow_run` и вебхуки `pull_request` и `push` через `parseGiteaWebhook`; `workflow_job` подписан, несёт шаги с итогами, парсер отвечает `null`.
- Q5: вторая распаковка — 400; токен выкладки жив до пайплайна и отозван в его конце; обёртки нет в логе задания; повторный запуск сайт не трогает.
- Q6: сбой `verify` → `rollback`, метка прежняя.
- Q3: одна идущая и одна ждущая выкладка; другой сайт не ждёт; контейнер задания несёт метку запуска стенда и стоит в сети своего раннера.
- Q2: выключение Actions владельцем; отмена выкладки файлом на ветке и её откат; файл `deploy.yml` в репозитории сайта рядом с обязательным; условные шаги отменённого запуска.
- Q7: таблица «Контейнер задания» и права токена задания, в том числе с `permissions: contents: read`.
- Вторая Gitea с `WORKFLOW_DIRS`: один запуск на push, по вебхуку — из `platform/ci`.

## Ревью

Независимое ревью 04.10.2026 перечитало стенд, его логи и образцы и исправило:

## Ограничения

- Подменные шаги передают токен Vault аргументом `wget` внутри контейнера задания и ходят в OpenBao без TLS. Файлы с пометкой `SPIKE` в настоящую Gitea не синхронизируются; настоящий `vault-login` — P9.
- Шаги выкладки — подмены. Actions из своей Gitea (`uses: platform/actions/…`, `DEFAULT_ACTIONS_URL = self`) и `actions/checkout` не проверялись: в `ci/` только шаги `run:`.
- Обязательный шаблон статуса и защита ветки: стенд ставит шаблон, но не проверяет, что pull request без пройденного `check` не сливается. Это N25.
- Стенд шёл на Docker Desktop (macOS), задания — под `runc`. На хосте Linux приёмник вебхуков слушает адрес шлюза сети `bridge`; этот путь не выполнялся.
- Workflow GitHub Actions для стенда нет: стенду нужен сокет Docker для раннера и образ раннера.
- Токен выкладки и политика `site-<имя>-deploy` — синтетические, их создаёт стенд. Настоящие — P7 и P9, ждут ответа о способе подключения сайта.
- Наблюдение о голове ветки сделано вручную, стендом не закреплено.

## Вопросы владельцу

1. **Где лежит источник обязательных workflow.** `platform/ci` в отдельной организации регистрируется только на весь экземпляр Gitea и только администратором через веб-форму. Альтернатива — репозиторий внутри `sites`: регистрирует владелец организации, но бот-владелец получает право записи в источник. По умолчанию — `platform/ci` на весь экземпляр, условие по организации в каждом задании, регистрация — шаг оператора в runbook M10.
2. **Выключать ли обычные workflow на экземпляре Gitea** настройкой `[actions] WORKFLOW_DIRS`. По умолчанию — да: иначе файл workflow в репозитории сайта отменяет выкладку и получает секрет выкладки и раннер `deploy`, а защищает от этого только проверка диффа и импорта.
3. **Кто ставит секрет выкладки.** Нужен владелец организации `sites`. Сделать владельцем самого бота или завести вторую учётную запись только для секретов и переменных Actions, а боту оставить право записи? По умолчанию — вторая учётная запись: короткие токены git хода тогда не получают прав владельца.
