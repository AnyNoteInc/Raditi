## Инцидент с `~/.codex/auth.json`

Условие ревью — не читать файл входа владельца. Оно было нарушено один раз, тестовым прогоном.

**Что произошло.** Находка R102: `infra/dev/llm-verify/local-spike.mjs` по умолчанию брал путь `~/.codex/auth.json`, не требовал подтверждения и запускал CLI с настоящим `HOME`. Инженер линии стендов написал тест на исправление и по правилу «сначала красный» запустил его на коде до правки. Прежний путь по умолчанию сработал: тестовый процесс дважды открыл настоящий файл.

**Что было с содержимым.** Файл хешировался и разбирался как JSON внутри процесса теста. `fetch` был подменён, CLI — синтетическая заглушка. Ничего не выведено, не записано, не отправлено и не использовано у провайдера; токен процесс не покидал.

**Что изменено.**

- Пути по умолчанию в коде больше нет. Файл входа задаётся только абсолютным путём в `RECORD_CODEX_AUTH`, живой проход — только с флагом `--confirm-live-subscription`. Обе проверки стоят до любого чтения. Флаг `--auth-file` удалён.
- CLI и запущенные им команды получают временный `HOME`.
- Тесты закрепляют `HOME` на синтетических каталогах: возврат дефекта не дотянется до настоящего файла. Ревьюер перезапустил набор и проверил, что ни один путь теста не ведёт к нему.
- Во втором проходе правило стало общим: любой тест или стенд, который мог бы заглянуть в домашний каталог, запускается с синтетическим `HOME`.

**Что осталось.** Владелец поставлен в известность (вопрос 3 ниже). Действие по умолчанию — ничего не делать; перевыпуск входа Codex — только для перестраховки.

## Что этот отчёт не меняет

- Ни одного коммита нет: вся работа ветки по-прежнему только в рабочем дереве, upstream у ветки нет.
- Супервизор хода, выдача ключей, контентные инструменты MCP и драйверы работают в verify-скриптах; в запускаемых ролях они не подключены — это P12.
- Гейты P3.0, «схема A», проверка владельца на настоящих подписках, настоящий Kimi и полный локальный e2e с WordPress открыты. Все проверки этого отчёта шли на фейках подписок и синтетических данных.
