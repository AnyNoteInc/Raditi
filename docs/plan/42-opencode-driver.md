# G3: образ и драйвер OpenCode, его стенды

05.10 и 09.10.2026 выполнен инкремент G3 [плана перехода на OpenCode и GLM](../research/2026-10-opencode-glm/pivot-plan.md): в образ песочницы вошёл OpenCode CLI 1.18.34, драйвер `opencode` получил `prepare` и `command`, а настоящий CLI проходит ход и продолжение через супервизор и pull-раннер под gVisor. Провайдера изображает сценарный фейк самого стенда. Ключ плана не использовался, к `api.z.ai` никто не ходил, корневой `.env` не читался. Codex и Kimi не тронуты: их драйверы и стенды проходят на том же образе и на том же `sandbox-gw`.

Работа шла в два приёма: 05.10 её оборвал недельный лимит на первом зелёном проходе стенда, 09.10 она закончена. Инкремент следует плану с поправками [отчёта разведки](40-opencode-spike.md) и ответов владельца от 05.10.2026 ([pivot-answers.md](../research/2026-10-opencode-glm/pivot-answers.md)). Отступления собраны в разделе «Отступления от плана».

Главное:

- **Закреплённый CLI исполняет код репозитория сайта, и выключателя у этого нет.** Со всеми выключателями драйвера, с `OPENCODE_PURE=1` и с `--pure` он при старте импортирует в свой процесс файлы из пяти мест рабочей копии. Нашёл это стенд; разведка не заметила: её плагин оставлял метку только при инициализации. Код чужого репозитория оказался бы в процессе, который держит в памяти оба ключа хода, — раньше, чем модель скажет слово. Обёртка драйвера убирает три имени из рабочей копии на время жизни любого процесса CLI и возвращает их после. Так же CLI импортирует код из собственного домашнего каталога — из каталога конфигурации и из `~/.opencode` (нашло ревью); туда до старта CLI пишет только драйвер, и обёртка это проверяет. Раздел «Код репозитория сайта в процессе CLI».
- **Перенос сессии — экспорт, фильтр, импорт**, как решила разведка. Восстановленную базу читает только `opencode export`, без ключей и без конфигурации с провайдером; ход идёт на базе, которую CLI создал заново из девяти полей строки сессии и сообщений.
- **Ключи хода CLI получает по одному разу, из именованных каналов.** Значений нет в файлах, окружении, argv, `/proc/*/environ`, выводе и снимке — стенд ищет их после каждого хода как есть, в hex и в base64.
- **Стенды зелёные.** `pnpm verify:opencode` — 12 сценариев в контейнерах без сети: 69 секунд под `runc` и 92 секунды под gVisor; `pnpm verify:opencode-supervisor` — два хода под gVisor со снимком, восстановлением и публикацией в Git за 67–69 секунд. Исполнитель прошёл каждый дважды подряд и один раз с SIGTERM (тогда сценариев было одиннадцать), ревью — по одному разу на конечном дереве.
- **x64 не исполнялся.** Путь `opencode-linux-x64-baseline` написан по плану и не доказан: всё шло на arm64. Первый запуск — job `verify-opencode` чернового PR.

### Драйвер

Всё лежит под `/agent-home/opencode`; файлы пишутся с режимом 0600.

| Файл | Что в нём |
| --- | --- |
| `.config/opencode/opencode.json` | Конфигурация хода: `JSON.stringify` из фиксированных ключей |
| `.config/opencode/AGENTS.md` | Инструкции хода. CLI перечитывает файл на каждом запросе, поэтому продолженная сессия получает текущие |
| `io-config/opencode/opencode.json` | Конфигурация экспорта и импорта: ни провайдера, ни MCP, ни ссылки на секрет |
| `run.mjs` | Обёртка запуска |
| `cli-args.json`, `prompt.txt` | Аргументы CLI и prompt; их пишет `command` |

Конфигурация:

- свой провайдер `raditi` на пакете `@ai-sdk/openai-compatible`, модель профиля с `limit` (контекст 1 000 000, ответ 131 072), `reasoning`, `tool_call`, `interleaved`; `model` и `small_model` указывают на неё же; `enabled_providers: ["raditi"]`;
- оба ключа — ссылки `{file:/run/raditi/secrets/llm}` и `{file:/run/raditi/secrets/mcp}`; других подстановок в файле нет. CLI подставляет `{env:}` и `{file:}` в сыром тексте конфигурации, поэтому фигурная скобка в модели или в адресе шлюза отклоняется (`BAD_REQUEST`), а инструкции лежат отдельным файлом — в нём такие ссылки остаются текстом, это проверено на настоящем CLI;
- MCP `raditi`: `type: remote`, `oauth: false`, `timeout` 60 секунд (запись через роль `mcp` отвечает в пределах своих 15 секунд, срок CLI по умолчанию — 5);
- агент `raditi` (`mode: primary`): ссылка на файл инструкций и контракт итога. Текст контракта переехал в `output-schema.ts` (`RESULT_CONTRACT`), драйвер Kimi берёт его оттуда же;
- права — только `allow` и `deny`: файлы, поиск, `bash`, `todowrite` и `raditi_*` разрешены; `webfetch`, `websearch`, `task`, `skill`, `question`, `lsp`, `doom_loop` запрещены; `external_directory` — `{"*": "deny", "/workspace/inbox/*": "allow"}`, порядок ключей закреплён тестом. `experimental.continue_loop_on_deny: true`;
- выключено: `autoupdate`, `share`, `snapshot`, `lsp`, `formatter`, `plugin: []`. Уровня рассуждения, `variants` и `thinking` в конфигурации нет: уровень ставит шлюз по профилю ключа хода.

`command` возвращает `['node', '/agent-home/opencode/run.mjs']`. Аргументы CLI: `run --format json --agent raditi --model raditi/<модель> --title raditi-turn --print-logs --log-level WARN [--session <id>]`; prompt — «Client request:», текст клиента и список вложений — идёт через stdin. Без уровня рассуждения запуск отклоняется; допустимые уровни — `low`, `high`, `max`. `sessionState` — `opencode.db` и `opencode.db-wal`, больше ничего.

### Обёртка `run.mjs`

Обёртка — отдельный модуль `opencode-wrapper.ts`; тесты запускают настоящий `run.mjs` против подставного CLI и локального MCP. Порядок:

1. Читает оба файла секретов и сразу удаляет их.
2. Убирает из рабочей копии `.opencode`, `opencode.json` и `opencode.jsonc` и проверяет места, откуда CLI импортирует код: рабочую копию, каталоги над ней и собственный домашний каталог CLI (раздел ниже). Проверка повторяется перед каждым процессом CLI и перед первым использованием ключа.
3. Делает каталоги конфигурации недоступными для записи (0555): иначе CLI ставит в них пакет плагина.
4. На ходе с продолжением: `opencode export <id>` с конфигурацией `io-config` → проверка формы → файл импорта собирается заново из девяти полей `info` (`id`, `slug`, `projectID`, `title`, `version`, `summary`, `cost`, `tokens`, `time`; каждое — своего типа) и `messages`; права, агент, модель, каталог и путь задаются заново → каталоги `.local` и `.cache` удаляются → `opencode import`. Файл экспорта не больше 128 МиБ, на каждую команду — 120 секунд.
5. Проверяет MCP: `initialize` с токеном хода в отдельном коротком процессе. Токен приходит ему через stdin, и строка с ним живёт только там; обёртка держит значение в буфере и обнуляет его, как только отдаст CLI.
6. Создаёт на месте файлов секретов именованные каналы и запускает CLI с окружением, собранным с нуля: `PATH`, `HOME`, `LANG`, `NO_COLOR`, `BUN_ENABLE_CRASH_REPORTING=0` и девять выключателей `OPENCODE_*`. Каждое значение отдаётся один раз, канал сразу удаляется. CLI остаётся в группе процессов рантайма песочницы.
7. Следит за stderr CLI: строка `level=WARN … message="server unavailable" … key=raditi` означает, что собственное подключение CLI к MCP не удалось, — CLI останавливается, ход завершается ошибкой.
8. По выходу CLI возвращает каталогам права, а рабочей копии — убранные файлы.

Свой отказ обёртка печатает строкой `error` в формате CLI (`RaditiWrapperError`), поэтому разбор событий сообщает о нём как об отказе хода.

### Разбор событий и итог хода

`opencode-events.ts` читает вывод 1.18.34: `error` четырёх видов (`APIError` с телом ответа, `UnknownError` с JSON в сообщении, `ContentFilterError`, `ContextOverflowError`) — причина называет вид, HTTP-статус и код `raditi_<вид>`, но не адрес шлюза; шаг с `reason` `length`, `content-filter`, `unknown` и любым другим, кроме `stop` и `tool-calls`, — `failed`; `write` и `edit` — `file_change` с путём внутри рабочей копии; инструмент `invalid` — неуспешный вызов того инструмента, которого у CLI не оказалось.

Строки конца хода CLI не печатает. `step_finish` с `reason: "stop"` даёт `completed`, но итог у хода есть, только если вывод кончается шагом ответа: `started`, собственный текст шага, `completed` — и ничего после. Так отсекаются сжатие контекста (после его `stop` идут служебная реплика CLI и новые шаги), код 0 без итогового текста и ход, оборванный на отклонённом запросе разрешения. Фикстуры — десять ходов, записанных разведкой (`src/fixtures/opencode-turns.json`).

### Список драйверов

`ENABLED_AGENT_DRIVERS` — `codex`, `kimi`, `opencode`. Строка драйвера в базе остаётся выключенной: ключ хода для него не выдаётся, пока оператор не включит драйвер и аккаунт провайдера.

## Код репозитория сайта в процессе CLI

### Что делает CLI

Служба конфигурации «v2» закреплённого CLI при старте идёт от рабочего каталога вверх до корня Git-репозитория и на каждом уровне ищет три имени: `.opencode`, `opencode.json`, `opencode.jsonc`. Выключателя у неё нет: `OPENCODE_DISABLE_PROJECT_CONFIG=1` действует на прежнюю службу — с ним инструменты из `.opencode/tool` не импортируются, а `AGENTS.md` и `CLAUDE.md` репозитория не попадают в запрос, — но эту не трогает. Прочитано в исполняемом файле и исполнено.

Контроль стенда — репозиторий с меткой в семи местах, обёртка ничего не убирает. Каждый подложенный файл первой же строкой дописывает метку, в которой называет себя и процесс:

| Место в рабочей копии | Импортирован в процесс хода |
| --- | --- |
| `.opencode/plugin/*.js` | да |
| `.opencode/plugins/*.ts` | да |
| файл из списка `plugin` в `opencode.json` | да |
| файл из списка `plugins` в `opencode.jsonc` | да |
| файл из списка `plugin` в `.opencode/opencode.json` | да |
| `.opencode/tool/*.js`, `.opencode/tools/*.ts` | нет |

Ход при этом кончается кодом 0, в событиях ничего не видно. Символическая ссылка на месте `.opencode` или `opencode.json` работает так же: CLI идёт по ней. Файлы `.env` и `bunfig.toml` репозитория среда Bun не читает: предзагрузка из `bunfig.toml` не исполняется, переменные из `.env` в окружении CLI не появляются (сценарий 1).

Чего CLI не делает (тоже исполнено):

- каталоги выше рабочей копии он не читает: обход кончается на корне Git-репозитория;
- во время хода он ничего не перечитывает. Команда модели записала девять файлов во все места, откуда CLI импортирует, — в рабочую копию, в каталог над ней, в каталог конфигурации CLI и в `.opencode` его домашнего каталога, — после чего ход сделал ещё пять запросов за семь секунд; ни один файл не исполнен;
- имена, отличные от трёх, он не читает. В корне рабочей копии лежали `.Opencode/plugin`, `Opencode.json`, `config.json`, `tui.json`, `tui.jsonc`, `.opencode.json` со списками `plugin`, каталоги `.config/opencode/plugin`, `.agents/plugin`, `.claude/plugins`, `plugin`, файлы `package.json` и `tsconfig.json`, пакеты `node_modules/@opencode-ai/plugin` и `node_modules/@ai-sdk/openai-compatible` — ничего не исполнено (опыт ревью, в стенд не вошёл);
- подкаталоги рабочей копии он не обходит, даже когда на подкаталог указывает база сессии: продолжение из базы, где каталог сессии и корень проекта — `/workspace/repo/sub`, а в `sub` лежат `.opencode/plugin` и `opencode.json` со списком `plugin`, не исполнило ни одного файла (опыт ревью, в стенд не вошёл).

### Собственный каталог CLI

Те же загрузчики обходят и домашний каталог самого CLI, `/agent-home/opencode`. Контроль стенда (сценарий 12) — файлы лежат там до старта, обёртка их не проверяет:

| Место в домашнем каталоге CLI | Импортирован в процесс хода |
| --- | --- |
| `.config/opencode/plugin/*.js`, `.config/opencode/plugins/*.ts` | да |
| `.config/opencode/tool/*.js`, `.config/opencode/tools/*.ts` | да |
| файл из списка `plugin` в `.config/opencode/opencode.jsonc` | да |
| `.opencode/tool/*.js`, `.opencode/tools/*.ts` | да |
| `.opencode/plugin/*.js`, файл из списка `plugin` в `.opencode/opencode.json`, в `.config/opencode/config.json` | нет (опыт ревью) |
| `.bunfig.toml` и `bunfig.toml` с предзагрузкой, `.env` | нет (опыт ревью) |

`OPENCODE_DISABLE_PROJECT_CONFIG=1` на `~/.opencode` не действует: это каталог не проекта, а пользователя. Процессы `opencode export` и `opencode import` файл из `io-config/opencode/plugin` — их собственного каталога конфигурации — не импортировали (опыт ревью). Когда `~/.opencode` существует и доступен для записи, CLI ещё и ставит в него пакет `@opencode-ai/plugin`: в стенде запуск ждал реестр npm 73 секунды.

Команда хода записать туда может — и в каталог конфигурации тоже: он принадлежит тому же uid, права 0555 она снимет сама (сценарий 10). Но работающий CLI этих файлов не читает, а следующий ход их не увидит: `/agent-home` — tmpfs своего контейнера, в снимок идут только два файла базы, и перенос сессии удаляет `.local` и `.cache` перед импортом. По строкам исполняемого файла CLI читает ещё `/etc/opencode/opencode.json` и `opencode.jsonc` (корень песочницы только для чтения), каталог из `OPENCODE_CONFIG_DIR` и файл из `OPENCODE_CONFIG` (окружение CLI собрано с нуля) и конфигурацию с адреса учётной записи из базы (`…/api/config`). Последнее делает `opencode export`, когда читает переписанную базу; в песочнице ему доступен только `sandbox-gw`, а тот пропускает лишь точные пути — это вывод из кода шлюза, не прогон.

### Мера

Обёртка переносит три имени из корня рабочей копии в каталог `/workspace/.raditi-opencode-held` до первого процесса CLI — экспорта, импорта или самого хода — и возвращает их, когда CLI завершился.

- Переносится само имя (`rename`): каталог целиком, файл, символическая ссылка — как ссылка.
- Перед каждым процессом CLI и перед первым использованием ключа обёртка проверяет, что ни одного из трёх имён нет ни в рабочей копии, ни в каталогах над ней (`/workspace`, `/`). Если есть — процесс не запускается, ход завершается ошибкой. Так «CLI останавливается на корне Git-репозитория» перестаёт быть условием защиты, а файл, появившийся между экспортом и ходом, не доживает до процесса с ключами.
- Та же проверка смотрит в домашний каталог CLI: `~/.opencode` не должно быть, а в двух каталогах конфигурации — `.config/opencode` и `io-config/opencode` — лежит только то, что записал драйвер (`AGENTS.md` и `opencode.json`; `opencode.json`). Любое другое имя — отказ до запуска CLI. Так «домашний каталог новый, а до CLI в него пишет только драйвер» перестаёт быть условием защиты: файл, который оставил бы там процесс экспорта или импорта, не доживает до процесса с ключами. Вместе с кодом это закрывает и чужие агенты, команды и настройки каталога конфигурации.
- Файл с таким именем, который записала команда самого хода, остаётся в рабочей копии как обычная правка: работающий CLI его не загружает, а следующий ход уберёт его так же, как файл сайта.
- Если ход записал файл поверх убранного, они не сливаются: ход завершается ошибкой, файл хода остаётся в рабочей копии, файл сайта — в каталоге хранения. Ошибкой кончается и ход, чья команда удалила убранное из каталога хранения: иначе снимок принял бы рабочую копию без файлов сайта за правку хода.
- Каталог хранения, оставшийся от прежнего запуска, — отказ: чужое обёртка не трогает.

Снимок и публикация убранных файлов не видят: захват идёт только после выхода агента с кодом 0 и без события `failed`, а к этому моменту файлы возвращены. Обёртка, убитая по сроку или отмене, файлы не возвращает, но такой ход не захватывается и не публикуется, а контейнер удаляется.

### Чего мера не закрывает

- Пока файлы убраны, модель видит их в `git status` удалёнными. Если она «восстановит» их (`git checkout`, `git stash pop`), ход завершится ошибкой перезаписи. У сайта, где этих файлов нет, такого не бывает.
- История сообщений остаётся вводом модели: её содержимое при переносе сессии не проверяется. Это открытый пункт разведки.
- `opencode export` читает базу, которую могла переписать команда прошлого хода. В этот момент нет ни ключей, ни конфигурации с провайдером. По строке учётной записи из такой базы экспорт обращается по её адресу; в песочнице адрес недостижим, стенд видит запрос в приёмнике.
- Список мест установлен чтением исполняемого файла и исполнением. По строкам файла каталоги обходятся ради кода в трёх местах: два загрузчика `{plugin,plugins}/*.{ts,js}` и один `{tool,tools}/*.{js,ts}`; остальное приходит из списков `plugin` документов конфигурации. В рабочей копии все они лежат под тремя убранными именами, в домашнем каталоге CLI — под `~/.opencode` и каталогом конфигурации, которые проверяет обёртка. Ревью перебрало вызовы `import()` и `require()` с невычисленным аргументом — 55 мест во всём файле. Собственных у CLI семь: загрузчик инструментов, два загрузчика плагинов, три загрузчика пакета провайдера (у провайдера `raditi` пакет встроен) и чтение прежнего файла `config` в формате TOML. Загрузка конфигурации и плагинов Prettier достижима только из команды `generate`, конфигурации Babel — только из терминального интерфейса; `run`, `export` и `import` их не вызывают. Это чтение минифицированного кода, не доказательство: исполнено только то, что названо в таблицах выше.
- Всё это — свойства версии 1.18.34: список имён, обход до корня репозитория, однократное чтение при старте. Обновление CLI повторяет разведку и сценарии 9–11 стенда.

Что эта правка меняет и чего не меняет (разбор ревью по коду, режим P2 не исполнялся):

- `sweep` снимает правило, только когда моста с этим именем в ВМ уже нет; правило ставится после создания сети, поэтому правило живой попытки — своей или чужой сессии в той же ВМ — он не тронет. Тот же `sweep` на всю ВМ продукт сам делает при каждой установке правила и после каждого удаления сети попытки (`gateway/manager.ts`), стенд ничего нового в ВМ не вносит;
- проверка «правила после прогона равны правилам до него» на успешном пути стоит раньше уборки и раньше её `sweep`: правило, которое продукт оставил после последней попытки, стенд ловит как прежде. `sweep` в начале только выравнивает исходное состояние — без него чужое осиротевшее правило снимала первая же попытка, и сравнение падало ложно;
- на неуспешном прогоне последняя строка уборки («Cleanup of firewall rules failed») больше не покажет осиротевшее правило: его уже снял `sweep`. Прогон к этому моменту и так неуспешен;
- помощник стенда запускается, как у продукта, с `--runtime runc` (правка ревью): правила хоста видит только контейнер в сети хоста под `runc`, и стенд не должен зависеть от runtime, который у демона стоит по умолчанию.

## Отступления от плана

- **Перенос сессии.** По разведке: экспорт → фильтр → импорт силами обёртки. `sessionState` — по-прежнему два файла базы.
- **Аргументы CLI.** Добавлены `--model` (чтобы модель не выбрали ни строка сессии, ни сообщение истории) и `--print-logs --log-level WARN` (признак отказа MCP).
- **Сокрытие файлов репозитория и проверка домашнего каталога CLI** — меры, которых в плане нет: ответ на находки стенда и ревью.
- **Приёмник стенда супервизора.** План ставил его на internal-сеть стенда. Сеть попытки принадлежит менеджеру шлюза, посторонний контейнер в неё не входит. Приёмник есть в `verify:opencode`; в стенде супервизора вместо него — фикстура, которая отклоняет любой путь, кроме двух.
- **`pnpm --filter orchestrator verify:runner`** из списка регрессии плана не запускался: стенду нужна локальная инфраструктура из `.env`, а читать его инкременту запрещено. Тот же скрипт `verify-runner.mjs` прошёл в трёх режимах настоящих CLI. Семь сценариев P2 после правки уборки не проверены.
- **Общая уборка `verify-runner.mjs`** изменена (`sweep` правил firewall) — шире, чем «режим рядом с прежними».
- **`apps/orchestrator/src/core/core.module.test.ts`** — вне списка файлов плана: тест закреплял список драйверов.
- **`docs/spec.md` §8 и §9** исполнитель не правил: тексты переданы отдельно и внесены руководителем после ревью, отдельным коммитом документов.
- **`verify:opencode` по умолчанию идёт под `runc`** — так его исполняет и CI. Ревью добавило параметр `--runtime` и провело все двенадцать сценариев под gVisor на демоне Linux-ВМ; в CI прохода под gVisor нет.

## Что осталось открытым

- **x64.** Образ для `amd64` не собирался, `opencode-linux-x64-baseline` не исполнялся. Какие пакеты платформ `npm ci` ставит на `amd64`, не исполнено. По lock-файлу варианты `musl` несут `libc: musl` и на glibc не ставятся — в слое образа для arm64 лежит один `opencode-linux-arm64`; на `amd64` ожидаются `opencode-linux-x64` (его удаляет Dockerfile) и `opencode-linux-x64-baseline`.

- **Настоящая модель.** Сценарий задаёт вызовы так, как их описал CLI. Как GLM соблюдает контракт итога — G6.
- **История сообщений** как ввод следующего хода и подложенные в неё части — открытый пункт разведки.
- **Память CLI под `runc`** читается командой модели (разведка): планка «ключа нет в окружении, на диске и в файлах CLI» держится, под `runsc` память закрыта.
- **Семь сценариев P2** (`verify:runner`) после правки уборки.
- **Сжатие контекста** на настоящем CLI стенд G3 не повторяет: разбор проверен на записи разведки.

## Что изменило ревью

Ревью 09.10.2026 прочитало код и тесты инкремента, сверило отчёт с кодом, разобрало исполняемый файл CLI (вынут из слоя образа без запуска контейнера, SHA-256 совпал) и повторило стенды.

- **Домашний каталог CLI — тоже место импорта.** Отчёт утверждал, что все места импорта лежат под тремя убранными именами. Это не так: CLI импортирует плагины и инструменты из своего каталога конфигурации и инструменты из `~/.opencode` (раздел «Собственный каталог CLI»). Положить туда что-то до старта CLI нечем — домашний каталог новый, в снимке два файла базы, — но это держалось на свойствах песочницы и снимка, а не обёртки. Теперь обёртка перед каждым процессом CLI проверяет и эти места; девять тестов сначала падали, в стенде появился сценарий 12 с контролем, а тест списка файлов сессии закрепляет, что ни одно из этих мест в снимок не попадает.
- **`verify:opencode` под gVisor.** У стенда появился параметр `--runtime`; все двенадцать сценариев пройдены под `runsc`, первый сценарий при этом проверяет ядро, которое видит команда хода. Сценарии 9–11 исполнитель вёл только под `runc`.
- **Опубликованное дерево стенда супервизора.** Утверждение «собственные файлы сайта остались как были» держалось на списке верхнего уровня. Стенд теперь сверяет полный список под `.opencode` и отсутствие отличий от базового коммита.
- **Node обёртки.** Обёртка стартует в рабочей копии; в репозиторий сайта первого сценария добавлен `node.config.json` с предзагрузкой. Node 26.10 его без флага не читает, с флагом `--experimental-default-config-file` — читает и исполняет (опыт ревью).
- **Помощник `sweep` стенда супервизора** запускается с `--runtime runc`, как у продукта; разбор правки общей уборки — в разделе «Прогоны».
- **Попытки обойти сокрытие**, которые ничего не дали: другие имена в корне рабочей копии, подкаталог с файлами OpenCode, на который указывает переписанная база сессии, предзагрузка и `.env` в домашнем каталоге CLI. Они описаны в разделах «Что делает CLI» и «Собственный каталог CLI»; в стенд не вошли.
- **По чтению кода, без нового прогона:** ход, чей агент вышел не с кодом 0 или с событием `failed`, не захватывается (`turn-attempt.ts`); `/workspace` и `/agent-home` — tmpfs контейнера одного хода; в снимок домашнего каталога идут только пути списка сессии, ссылки отклоняются (`sandbox-snapshot.ts`); строка драйвера `opencode` в сидах выключена, а `issue` требует включённую строку. По строкам исполняемого файла у парсера аргументов CLI нет ни файла конфигурации, ни чтения `package.json`, ни переменных окружения.

Что ревью оставило открытым — это не дефекты инкремента, а его границы:

- семь сценариев P2 (`verify:runner`) после правок общей уборки не исполнены: им нужна инфраструктура корневого `.env`;
- прогоны с SIGTERM после правок ревью не повторялись;
- список мест импорта — свойство версии 1.18.34 и чтение минифицированного кода; исполнено только названное в таблицах;
- захват отклоняет рабочую копию с любой символической ссылкой (`sandbox-snapshot.ts`, так было до инкремента): сайт, у которого `.opencode` — ссылка, обёртка переносит и возвращает верно, но ход такого сайта не завершится по другой причине.

## Уборка

В обоих демонах Docker нет контейнеров, сетей и томов стендов инкремента и ревью; правил firewall попыток в ВМ не осталось — это проверяет сам стенд супервизора. Каталоги диагностики двух прерванных прогонов удалены из временного каталога, временные скрипты опытов исполнителя и ревью — из рабочей копии.

Не удалены четыре образа: `raditi-oc-runtime:g3` (оба демона), `raditi-oc-base:g3`, `raditi-oc-gateway:g3` и `raditi-oc-network-guard:g3` (ВМ). На них идут ревью и гейты партии; удалить их должен тот, кто партию закрывает. Слои кэша сборки остались в сборщиках обоих демонов.
