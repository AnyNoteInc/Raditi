# G2: бэкенд `zai-coding` и фейк Z.ai

05.10.2026 выполнен инкремент G2 [плана перехода на OpenCode и GLM](../research/2026-10-opencode-glm/pivot-plan.md): роль `llm` получила третий адаптер порта `LlmBackend` — Z.ai по подписке GLM Coding Plan, — а стенды получили синтетический Z.ai. Ключ плана не использовался, к `api.z.ai` никто не ходил, корневой `.env` не читался: всё идёт на записях пробы и на фейке. Поведение Codex и Kimi не изменилось: их адаптеры, сиды, маршруты и стенды работают как раньше.

Инкремент следует плану с поправками [отчёта разведки](40-opencode-spike.md) и ответов владельца от 05.10.2026 ([pivot-answers.md](../research/2026-10-opencode-glm/pivot-answers.md)). Отступления собраны в разделе «Отступления от плана».

Главное:

- **Все семь «шторм-форм» разведки превращаются в один окончательный отказ.** Песочница получает один объект `error` последним событием потока; до провайдера доходит один запрос. Для двух форм — поток без `finish_reason` и без `[DONE]`, пустой поток — понадобились необязательный метод `end()` у инспектора потока и десять строк в роли `llm`: такие потоки кончаются без события, и инспектор их не видел.
- **Тексты отказов проверяются по правилам самого CLI.** Списки повтора и переполнения контекста OpenCode 1.18.34 переписаны из исполняемого файла, тест сверяет переписанное с выдержками побуквенно. Ни один окончательный отказ, с любым полем политики, под них не подпадает; краткий отказ — подпадает намеренно.
- **Адрес чата и способ чтения квоты — данные описания.** Адаптер строится из описания предложения Z.ai (`ZaiOffer`): идентификатор, маршрут шлюза, origin, путь чата, путь квоты и соответствие «единица × число → окно». Вариант с оплатой за токены станет вторым описанием; роль `llm` для этого менять не нужно.
- **Окно, которое никто не начал, — известное и свободное.** Правило `usedPct = max(currentValue, usage − remaining) / usage` проверено на восьми записанных ответах квоты.
- **Фейк ведёт квоту как провайдер:** окно пяти часов начинается первым запросом, как в записях 60 и 62; исчерпанное окно отказывает кодом 1308.
- **Находка для G4:** `retry-after` провайдера на успешном ответе сегодня доходит до песочницы (решение 7(а) плана). Тест роли это закрепляет: строку с `999999` перевернёт правка 7(а).

## Что построено

### Порт (`packages/domain/src/ports/llm-backend.ts`)

- Идентификатор `zai-coding` — третий в `llmBackendIds`.
- У сигнала `unconfirmed_block` появился необязательный `code` того же разрешающего вида, что у остальных сигналов (решение 7(д)). В строку лога `llm_call` роль его ещё не пишет — это G4.
- У инспектора потока появился необязательный метод `end()`: роль зовёт его один раз, когда провайдер сам закрыл поток до события, которое адаптер счёл концом. Адаптер отвечает отказом, который нужно отправить последним событием, или `null`. Codex и Kimi метода не реализуют, и для них ничего не изменилось.

**Описание предложения.** Всё, что отличает одно предложение Z.ai от другого при том же протоколе, лежит в одном замороженном объекте:

```ts
export const zaiCodingPlan: ZaiOffer = {
  id: 'zai-coding',
  route: { method: 'POST', path: '/zai/v4/chat/completions' },
  origin: 'https://api.z.ai',
  chatPath: '/api/coding/paas/v4/chat/completions',
  quota: {
    path: '/api/monitor/usage/quota/limit',
    windows: [
      { unit: 3, number: 5, name: '5h' },
      { unit: 6, number: 1, name: 'week' },
    ],
  },
  overrideEnv: 'LLM_BACKEND_URL_ZAI_CODING',
}
```

Маршрут роли, два точных запроса `egress`, адрес `upstream`, адрес и разбор пробы берутся только отсюда. Тест строит второй адаптер из описания с другим маршрутом, путём `/api/paas/v4/chat/completions`, другим путём квоты и другой парой окна и проверяет, что всё перечисленное следует описанию, а не константам кода. Сам вариант с оплатой за токены не добавлен: у него нет окон плана, и что пул должен делать с аккаунтом без окон, решается вместе с ним (вопрос П15).

**Заголовки.** Клиентский заголовок один — `user-agent`, и он должен быть равен строке закреплённого CLI: `opencode/1.18.34 ai-sdk/provider-utils/4.0.23 runtime/bun/1.3.14`. Провайдеру уходит не значение клиента, а та же константа, так что в заголовках провайдера нет ничего, написанного клиентом. Весь набор: `authorization` с ключом плана, `user-agent`, `accept: text/event-stream`, `accept-encoding: identity`, `content-type: application/json`. `x-session-*`, `x-opencode-session-id` и cookie CLI до провайдера не доходят; `responseHeaders` пуст.

**Тело запроса.** Принимается только то, что шлёт CLI: `model`, `max_tokens`, `messages`, `tools`, `tool_choice`, `stream`, `stream_options`, а также `thinking` и `reasoning_effort`, значения которых не учитываются.

- `model` должен равняться модели профиля ключа хода.
- `stream: true` и `stream_options.include_usage: true` ставятся всегда.
- `max_tokens` — меньшее из запрошенного и 32 000; без поля уходит 32 000.
- `thinking: {type: 'enabled', clear_thinking: false}` и `reasoning_effort` из профиля ключа ставит шлюз. Разведка показала, что со своим id провайдера `raditi` CLI поля `thinking` не шлёт; `clear_thinking: false` — то же значение, с которым записаны живые обмены пробы. Профиль без уровня оставляет умолчания провайдера и убирает оба поля из запроса; уровень вне `low`, `high`, `max` — отказ.
- `tools[].type` — только `function`, `tool_choice` — только `auto`. Запрос без `tools` и `tool_choice` проходит: так CLI запрашивает заголовок сессии и сжатие контекста.
- Сообщения: `system` и `tool` — строка; `user` — строка или список текстовых частей (SDK внутри CLI пишет несколько частей списком); `assistant` — `content`, `reasoning_content`, `tool_calls`. Картинок и других частей нет.
- Имя инструмента ограничено только длиной: имя, которое модель сама написала в прошлом вызове, возвращается в истории, и отказ на нём сорвал бы ход.
- Место нарушения в отказе (`error.field`) собирается из 24 собственных имён полей схемы, без индексов и без имён из запроса: `messages[].content`, `tools[].function.unknown`.

**Отказы провайдера.** Z.ai называет ошибку числом: `{"error":{"code":"1211",…}}` на пути чата и `{"code":401,…,"success":false}` с HTTP 200 на путях монитора. Читается только число. Известный код решает независимо от статуса: статусы большинства кодов не измерены.

| Ответ | Сигнал | Откуда |
| --- | --- | --- |
| HTTP 401; код 401 | `auth` | Записи 54, 10 |
| 1302, 1305; 408, 409, 5xx | `transient`, пауза из `retry-after`, не больше 30 с | Документация |
| 1308, 1310, 1316, 1317 | `window_exhausted`, `until: null` | Документация |
| 1113, 1309, 1313 | `account_risk`, причина `zai_<код>` | 1113 — запись 21; остальные — документация |
| 1211, 1311 | `profile`, код `zai_<код>` | 1211 — запись 54; 1311 — документация |
| 1301 | `policy_flagged` | Документация |
| 1261 и любой другой 400 | `request_rejected`, код `zai_<код>` или `zai_http_400` | 1210 — запись 54 |
| Всё остальное | `unconfirmed_block`, код `zai_<цифры>` или без кода | — |

Код `unconfirmed_block` из `classify` — только `zai_` и от одной до шести цифр. Текст, число со знаком, дробь и число внутри сообщения кодом не становятся.

**Отказы шлюза** (решение 6):

| Вид | Статус | Текст |
| --- | --- | --- |
| `budget` | 403 | The budget of this turn is spent. |
| `subscription_limit` | 403 | The subscription of this turn has no capacity left. |
| `account` | 403 | The account of this turn cannot be used. |
| `provider_off` | 403 | The provider of this turn is switched off. |
| `egress` | 403 | The provider of this turn cannot be reached. |
| `policy` | 400 | The request is not allowed by the policy of this turn. |
| `policy_flagged` | 400 | The request was declined by the content policy. |
| `profile` | 400 | The request does not fit the model profile of this turn. |
| `request_rejected` | 400 | The provider declined this request. |
| `transient` | 503, `retry-after` 1–30 с | Service temporarily unavailable. |

Тело — `{"error":{"type":"invalid_request_error","code":"raditi_<вид>","message":…}}`; у краткого отказа `type` — `server_error`. У окончательных отказов нет `retry-after`. Нижняя граница паузы краткого отказа — одна секунда: с нулём CLI отправил бы пять повторов подряд. Три текста — `budget`, `policy`, `account` — те самые, с которыми разведка измерила «один запрос, код 1».

**Поток.** Инспектор пересылает `stop`, `tool_calls` и `length`. Всё остальное заканчивает поток одним событием `data: {"error":{…}}` с текстом отказа шлюза; ни отклонённый чанк, ни `[DONE]`, ни текст провайдера до песочницы не доходят.

| Что пришло от провайдера | Сигнал | Что читает песочница | Запросов CLI по разведке |
| --- | --- | --- | --- |
| `finish_reason: sensitive`, `content_filter` | `policy_flagged` | `raditi_policy_flagged` | 1 вместо шторма |
| `finish_reason: model_context_window_exceeded` | `request_rejected` | `raditi_request_rejected` | 1 вместо шторма |
| Неизвестный `finish_reason`, не строка | `unconfirmed_block`, `zai_finish_reason` | `raditi_account` | 1 |
| `[DONE]` до `finish_reason`: один `[DONE]`, текст и `[DONE]` | `unconfirmed_block`, `zai_stream_unfinished` | `raditi_account` | 1 вместо шторма |
| Конец потока без `finish_reason`: текст без `[DONE]`, пустой поток | то же, через `end()` | `raditi_account` | 1 вместо шторма |
| Объект `error` с кодом таблицы; конверт `{code, msg, success:false}` | по таблице кодов | `raditi_<вид>` | 1 |
| `finish_reason: network_error`; объект `error` с кодом 1302, 1305 | `transient` | `raditi_transient` | до шести, с паузами |
| `finish_reason` получен, `[DONE]` нет | — | ответ как есть | не измерялось |

Последний столбец — что разведка измерила для формы, которую читает песочница: объект `error` с текстом окончательного отказа — один запрос, с текстом повтора — шесть. Поток с `finish_reason`, но без `[DONE]`, разведка не исполняла: шлюз отдаёт его как есть, а как его читает CLI, покажет стенд G4 (сценарий `no_done` фейка).

Чанк, отклонённый за `finish_reason`, несёт `usage` провайдера, и измеритель его сохраняет: вызов провайдер посчитал. Ошибка после `finish_reason` отбрасывается, как у Kimi; повторный `finish_reason` из разрешённых пересылается, противоречащий — отбрасывается; объект, который не чанк и не ошибка, отбрасывается.

**Проба.** `GET /api/monitor/usage/quota/limit` с ключом плана; заголовки — `authorization`, `accept: application/json`, `accept-encoding: identity` и `user-agent` закреплённого CLI.

- Окно — запись `CREDIT_LIMIT` с парой из описания. Запись другого типа, с другой парой, повтор окна, нечисловые или отрицательные числа — ответ `unknown` целиком: непрочитанный предел не должен стать свободной ёмкостью.
- Нет `nextResetTime`, `currentValue` равен 0 и `remaining` равен `usage` — `{usedPct: 0, resetsAt: null}`. Нет `nextResetTime` при ненулевом расходе — `unknown`.
- `usedPct` = `max(currentValue, usage − remaining) / usage`; `remaining <= 0` или расход не меньше размера — 100. Поле `percentage` не читается.
- `nextResetTime` дальше длины окна с запасом — `unknown`. `nextResetTime` в прошлом не дальше длины окна — окно кончилось, `{usedPct: 0, resetsAt: null}`; дальше — `unknown` (секунды, прочитанные как миллисекунды, иначе выглядели бы свободным окном).
- Конверт HTTP 200 с кодом 401 и HTTP 401 — `auth`; коды 1113, 1309, 1313 — `suspended`; коды исчерпанного окна — `unknown`; HTTP 403 без объекта ошибки провайдера — `region`. Остальное — отказ пробы без изменений в пуле: 5xx, 429, код 1001 на запрос с ключом, код 500 «404 NOT_FOUND».
- `plan` всегда `null`. Уровень плана из ответа (`level`, в записях — `lite`) никуда не пишется: проба с другим значением `plan` приостановила бы аккаунт.

Восемь записей дают: шесть ответов активного окна — 1,05 %, 1,05 %, 1,2 %, 1,2 %, 1,25 % и 1,3 % окна пяти часов; запись 60 — окно пяти часов `{0, null}`, неделя 0,26 %; запись 62 — 0,05 % и сброс через пять часов после запроса.

### Роль `llm`

`apps/orchestrator/src/llm-gateway/server.ts`: после чистого конца потока без терминала роль спрашивает `inspector.end?.()` и, получив отказ, отправляет его событие, запоминает сигнал и завершает ответ штатно. Раньше такой поток кончался обрывом соединения с кратким отказом в журнале: CLI повторил бы запрос пять раз с паузами, то есть шесть запросов провайдеру вместо одного. Обрыв самого соединения с провайдером, превышение предела и молчание идут прежним путём.

Больше в роли ничего не менялось. Два закреплённых списка в тестах получили третий идентификатор: `llm-app.module.test.ts` и `llm-config.test.ts`.

### Команда оператора, сид, окружение

- `apps/orchestrator/src/subscriptions/cli.ts`: запись импорта `zai-coding` → драйвер `opencode`, один ход и два запроса одновременно. Карта экспортирована как `subscriptionImports`; тест требует запись для каждого зарегистрированного бэкенда. Справка `subscriptions:login --help` строится из карты.
- `packages/db/prisma/seed/data.ts`: провайдер `zai-coding` («Z.ai GLM Coding Plan») и профили `glm-5.3-light`, `glm-5.3-standard`, `glm-5.3-heavy` с `provider_model_id: 'glm-5.3'` и резервом 32 000. Всё выключено, ставок нет. Миграции нет.
- `.env.example` и `turbo.json`: `LLM_BACKEND_URL_ZAI_CODING` и, по ответу владельца, `ZAI_API_KEY` без значения. Сервисы платформы `ZAI_API_KEY` не читают: роль `llm` берёт ключ плана из Vault.

### Фейк Z.ai (`infra/dev/llm-verify/fake-zai.mjs`)

Два адреса: чат и квота. Кадры потока, ответы на запрос без ключа, с чужим ключом, с неизвестной моделью и с недопустимым `max_tokens`, конверты HTTP 200 и готовый ответ без потока повторяют записи пробы по форме. Статусы кодов, которых проба не видела, — допущение (`ZAI_ERROR_STATUS`).

- Сценарии чата: `text`, `tools`, `finish`, `error`, `stream_error` и «враждебные» — `envelope200`, `plain200`, `no_usage`, `no_done`, `done_only`, `no_finish`, `no_finish_no_done`, `empty`, `cut`; `retryAfter` добавляет заголовок, `failures` ограничивает сбой первыми запросами.
- Квота живая: окно пяти часов не начато; первый запрос его начинает; каждый следующий — один кредит в обоих счётчиках обоих окон. Режимы и поля задают исчерпанное окно, окно с прошедшим сбросом, нечитаемый ответ и конверт HTTP 200.
- В записях запросов нет значений учётных данных: признак `credential` и имена заголовков.
- Фейк встроен в `fake-subscriptions.mjs` (два пути, `POST /zai` управляющего порта, общий сброс, ключ `zai` в `/state`) и запускается отдельным процессом. Имя `api.z.ai` добавлено в сертификат, в псевдонимы сети `providers` и в список прокси стенда.

## Отступления от плана

1. **Роль `llm` изменена** — метод `end()` и его вызов. План относил правки роли к G4, задача разрешала минимальный код роли, если без него адаптер не подключить. Без него две формы шторма из семи заканчивались бы обрывом и шестью запросами провайдеру, а не одним отказом.
2. **Разрешающий список `finish_reason` — три значения, как в плане.** Разведка предлагала пропускать и `content_filter`. Он заменяется отказом `policy_flagged`: ход кончается так же за один запрос, а в журнале остаётся сигнал шлюза.
3. **`network_error` не пересылается как есть.** Вместо чанка провайдера песочница получает объект `error` краткого отказа; CLI повторяет его с паузами так же, как повторил бы сам `network_error`.
4. **`thinking` и `reasoning_effort` ставит шлюз** — предложение отчёта разведки. В запросе оба поля допускаются, значения не учитываются.
5. **Список хостов прокси стенда получил `api.z.ai:443`**, хотя по ответу владельца путь к Z.ai прямой. Прямого пути в роли ещё нет (шов G4), и до него фейк достижим ролью только через прокси стенда.
6. **`packages/db/prisma/seed/apply.test.ts`** не входил в список файлов: тест на PostgreSQL закреплял «два провайдера, четыре модели» для настоящих сидов. Три литерала заменены длинами списков сидов.
7. **`apps/orchestrator/src/llm-gateway/llm-app.module.test.ts`** не входил в список: закреплённый список идентификаторов получил третий.
8. **Фейк написан раньше своего теста.** Вместо «сначала красный» тесты фейка проверены четырьмя мутациями фейка: каждая роняла от одного до четырёх тестов.
9. **Документация Z.ai перед G2 не перечитывалась.** В партии разрешена только загрузка пакета `opencode-ai`; таблица кодов и список `finish_reason` — по чтению руководителя от 05.10.2026, то есть того же дня.
10. **`pnpm verify:llm-gateway` шёл с `--no-build`**, на образе CLI, собранном для PR #2. Dockerfile песочницы и lock-файл CLI в рабочей копии в это время меняет инкремент G3; пересборка скачала бы пакеты всех трёх CLI.
11. **`infra/dev/llm-verify/README.md`** получил раздел о синтетическом Z.ai. Файл лежит в каталоге стенда. Общих документов (`docs/spec.md`, roadmap, `CLAUDE.md`) исполнитель не правил: их обновил руководитель перед коммитом, отдельным коммитом.
12. **Коды сигналов, которые адаптер выносит сам, — его собственные имена.** План называл для `unconfirmed_block` только вид `zai_<цифры>`. У отказа по `finish_reason` и по концу потока числа провайдера нет: `zai_finish_reason`, `zai_stream_unfinished`, а у `policy_flagged` и `request_rejected` — `zai_finish_sensitive`, `zai_finish_content_filter`, `zai_finish_context_window`. Это постоянные строки кода; текста провайдера в них нет.

## Что осталось открытым

- **Коды и статусы Z.ai, кроме пяти измеренных** (401, 1001, 1113, 1210, 1211), взяты из документации. Ответ на исчерпанное окно, на превышение частоты и на истёкший план не наблюдался. Живой проход G6 покажет настоящие коды в логе роли — после того как G4 начнёт писать `code` сигнала в строку `llm_call`.
- **`nextResetTime` в прошлом** не наблюдался. Правило «окно кончилось и свободно» — предположение плана; ошибку исправит отказ провайдера с кодом окна и следующая проба.
- **Другие типы пределов.** В записях только `CREDIT_LIMIT` уровня `lite`. Если у другого уровня плана в ответе есть предел другого типа, проба ответит `unknown`, и импорт ключа не пройдёт — это видно сразу, при `subscriptions:login`.
- **`max_tokens` 32 000 и резерв профиля 32 000** связаны тестами по обе стороны границы пакетов: сид не может импортировать адаптер. Число записано дважды, оба теста называют друг друга.
- **Строка `user-agent` закреплена целиком**, вместе с версиями SDK и Bun. На x64 она не измерялась; если она там другая, шлюз откажет первому же запросу отказом `raditi_client` — это покажет первый прогон G4 на x64.
- **Параллельность плана.** Один ход и два запроса на аккаунт — осторожное значение до замера G6 (вопрос П4).
- **Аккаунт без окон.** Вариант с оплатой за токены потребует решения, что отвечает проба и как пул допускает аккаунт без окон. Описание предложения к этому готово, пул — нет.
- **Узел выхода.** `subscriptions:login` и роль по-прежнему требуют канал mTLS; прямой путь для этого бэкенда — шов G4.
- **Переполнение контекста у провайдера.** `finish_reason: model_context_window_exceeded` заканчивает ход отказом `request_rejected`, как решено планом. Другой путь не делался: отдать CLI текст, который он читает как переполнение, — тогда он сожмёт контекст и продолжит ход. При пределе модели в миллион токенов CLI сжимает контекст сам задолго до отказа провайдера.
- **Отказ 402.** По плану статус вне таблицы — `unconfirmed_block`. У Kimi 402 — пауза оплаты; для Z.ai такой ответ не наблюдался и в документации не назван.

## Что изменило ревью

Ревью 09.10.2026 прочитало код и тесты инкремента, сверило отчёт с кодом и повторило проверки.

- **Правка роли `llm`** прочитана отдельно. `end()` вызывается только после чистого конца потока, когда не было ни терминала, ни отказа; у инспекторов Codex и Kimi метода нет, и для них ветка пуста. Проверено мутацией на копии файла роли, общий файл не менялся: без вызова падают ровно три теста `server.test.ts` из 73 — две формы «поток кончился без `finish_reason`» и тест вызова. Остальные 70, среди них все тесты Codex и Kimi, проходят.
- **Новая проверка:** обрыв соединения с провайдером посреди ответа — не конец потока. Тест роли требует, чтобы адаптер при обрыве не спрашивался, песочница получала такой же обрыв, а в журнал ключа шёл краткий отказ. Тест сначала падал — на копии роли, которая принимает обрыв за конец.
- **Исправлено в тестах.** Утверждение о заголовках провайдера в `server.test.ts` проходило, пока до песочницы не дошли все три заголовка сразу. Теперь каждый проверяется отдельно; тест падал на адаптере, который пропускает `set-cookie`. Комментарий там же утверждал, что `retry-after` провайдера на успешном ответе не пересылается; он пересылается, и тест это теперь утверждает (находка для G4).
- **Исправлено в отчёте.** Находку о `retry-after` закрепляет тест роли, а не интеграционный тест. Строку таблицы потока «`finish_reason` получен, `[DONE]` нет» разведка не измеряла. Заполнены итоги стендов и гейтов; добавлены отступления 11 и 12.
- **Фейк против записей.** Фейк написан раньше своего теста, поэтому тест проверен мутациями на копии фейка. Тринадцать правок — ключи `usage`, заголовки провайдера, значение `authorization` в записи запроса, начало окна первым запросом, формы «шторма», код неизвестной модели, лишнее поле чанка, конверт квоты, `content-type` потока — роняют от одного до четырёх тестов каждая.

Что ревью оставило открытым — это не дефекты инкремента, а его границы:

- Документация Z.ai перед G2 не перечитана и на ревью: таблица кодов и список `finish_reason` — по чтению 05.10.2026.
- Поле `id` чанков — идентификатор запроса Z.ai — доходит до песочницы в теле потока: заголовки с идентификаторами шлюз срезает, чанки пересылает как есть. Если проверка G4 «до песочницы не доходят id запросов Z.ai» относится и к телу, инспектору понадобится правка.
