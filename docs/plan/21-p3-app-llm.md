# B14: профиль llm для app-ВМ

Локальная реализация подготовлена 30.09.2026. Роль `llm` запускается из production-образа orchestrator отдельным профилем Compose: одна реплика, uid 10008, опубликованный частный порт 8084, отдельные сети и каталог секретов. Общий PostgreSQL использует владельца `raditi`; Redis и S3 роли не нужны. Облачная выкладка и полный P3 этим этапом не закрываются.

## Реализация

- `infra/app/docker-compose.yml`: профиль `llm`, PostgreSQL в `llm-data`, отдельные `llm-edge`/`llm-out`, контроль из core через частный опубликованный порт. Health требует HTTP 200, read-only root, запрет capabilities, отдельный tmpfs. Внешний DNS закрыт, Vault закреплён по IP с проверкой TLS-имени, провайдеры доступны через mTLS-прокси.
- `llm-preflight.mjs` и `preflight.sh`: конфигурация профиля, частные адреса, допустимые клиенты, общий пароль БД, раздельные AppRole, общий управляющий токен, сертификаты и ключ, права файлов и действующая сетевая политика. Секреты `llm/app.env` ограничены четырьмя полями; токены подписок остаются в Vault.
- `llm-firewall.mjs`: атомарная таблица nftables `inet raditi_llm`, INPUT/FORWARD до правил Docker, выход только к прокси :443, Vault :8200 и PostgreSQL :5432 в своём мосту. Доступ к портам хоста, произвольным адресам, Redis и IPv6 закрыт.
- systemd устанавливает правила до автоматического старта контейнеров и проверяет их при каждом запуске Docker. Выключенный профиль устанавливает запрет для всех трёх мостов. Production-префикс `rd` фиксирован: смена имени не может вывести старый контейнер из-под защиты после перезагрузки. Preflight запускает проверку до обращения к хосту, отвергая wildcard `COMPOSE_PROFILES=*` и конфликты окружения. CLI-проверки выполняются также при запуске через symlink.
- Образцы секретов, [runbook app-ВМ](../../infra/app/README.md), spec §19 и проект P3 приведены к этому контракту. Добавлен workflow `llm-app.yml` с production-образом и Docker без userland-proxy; удалённый CI в этой сессии не запускался.

Для сетевой границы выбран самостоятельный ранний hook nftables вместо зависимости от DOCKER-USER: правила должны существовать ещё до запуска dockerd и автоматического восстановления `restart: unless-stopped`.

## Проверки

Перед повтором пересоберите образ из текущего дерева первой командой ниже. Образ `raditi-p3verify-orchestrator:b14`, оставшийся в демоне с 30.09.2026, старше правок ревью; с ним стенд проверял бы прежний код. Так уже случилось на первом проходе ревью: шаг потери выхода ждал 503 `raditi_busy` для запроса без ключа, а текущий сервер сначала проверяет ключ и отвечает 401.

```sh
docker build -f apps/orchestrator/Dockerfile --target runtime -t raditi-p3verify-orchestrator:b14 .
pnpm verify:llm-app
pnpm verify:llm-firewall
pnpm test:infra
pnpm --filter orchestrator typecheck
pnpm --filter orchestrator lint
pnpm --filter orchestrator test
pnpm check-env
pnpm check-architecture
```

Рабочий production-образ собран. `verify:llm-app` прошёл 9 групп в Docker Desktop: реальный сервис из Compose, PostgreSQL, HTTPS OpenBao, mTLS-проба, отдельный AppRole и реальные ACL, запрет чтения старой версии подписочного секрета, безопасные отказы без ключей, недоступный egress после перезапуска → 503, восстановление → 200. В логах нет синтетических секретов и запросов к провайдерам. Override меняет logging и имена зависимостей на собственные fixtures; рабочие `.env`, БД, Vault и файлы входа не используются.

Дополнительный `--hairpin-only` в локальной Colima (Ubuntu 24.04, Docker 29.5.2) прошёл 2 группы: клиент в отдельной сети core достигает опубликованного частного порта контейнера с тремя сетями llm, источник на стороне сервера — точный адрес шлюза `llm-out`. Это подтверждает адрес для `LLM_GATEWAY_CLIENTS`. Сам адрес не отличает `core` от web или Traefik: после SNAT Docker любой контейнер app-ВМ выглядит для шлюза одинаково. Различает их firewall хоста по мосту-источнику (см. «Изменения после ревью»). Отдельный повтор увеличил счётчики соответствующих DNAT и FORWARD-правил с 0 до 1: запрос шёл через kernel NAT, а не процесс docker-proxy. Конфигурация демона Colima не менялась; полный native Linux проход production-образа с явно выключенным userland-proxy включён в CI. Docker Desktop не может опубликовать порт на адресе моста Linux-ВМ, поэтому эту часть проверяли отдельно.

Проверка firewall прошла 7/7, включая реальные пакеты в одноразовом контейнере `--network none` с внутренними сетевыми пространствами. Сначала подтверждается доступность запрещаемых адресов, затем — их блокировка; проверяются разрешённые маршруты, ответы входящих запросов, INPUT, IPv6, повторное применение, выключенный профиль после потери таблицы и обнаружение ослабленных правил. Прерывание SIGTERM также удаляет принадлежащие стенду контейнер и образ. Сетевые правила хоста не менялись.

Orchestrator: 65 файлов, 1 251 тест пройден; 113 интеграционных тестов без БД пропущены. Полный проход с одноразовой БД выполнен в [B13](20-p3-synthetic-gateway.md). Проверки типов, линтер, окружение и границы пакетов прошли. Итог `pnpm test:infra`: 214 пройденных, 2 пропущенных проверки; пакетная проверка firewall из этого opt-in набора отдельно выполнена успешно. Проверка форматирования и `git diff --check` прошли.

## Исправления после ревью

Закрыты оба замечания P2:

- Systemd использует автономную установленную копию `/usr/local/lib/raditi/llm-firewall.mjs`. Она переживает возврат `/opt/raditi/app` к релизу до B14; выключенный профиль сохраняет deny-all. Обновлены установка, обновление и порядок отката, preflight сравнивает установленный helper с выбранным релизом. Регрессионный тест удаляет каталог нового релиза и проверяет применение и проверку deny-all оставшимся helper. Настоящая перезагрузка systemd остаётся границей M10.
- `verify:llm-firewall` до создания ресурсов проверяет Docker endpoint и отвергает удалённые подключения. Локальный сокет закрепляется для сборки, запуска и уборки, даже если текущий context изменился. Семь проверок с подставным Docker CLI покрывают удалённые адреса, приоритет context/host, ошибку определения адреса и уборку после ошибки сборки; эти проверки добавлены в CI.

После исправлений: `pnpm test:infra` — 222 пройденных, 2 пропущенных проверки, ошибок нет. Реальная проверка пакетов отдельно повторена успешно, ресурсы стенда удалены. `check-env`, `check-architecture`, синтаксис preflight, линтер изменённых JS-файлов, форматирование и `git diff --check` прошли. Независимое повторное ревью исправления отката новых замечаний не выявило.

## Изменения после ревью 02–04.10.2026

- **Цепочка `to_llm`.** Таблица `inet raditi_llm` получила цепочку для входящих: новые соединения к :8084 принимаются только с моста `rd-core` и из подсетей песочных ВМ (`LLM_GATEWAY_CLIENTS`), остальные отбрасываются. Диапазон, который накрывает подсеть другого моста Docker этой ВМ, firewall не распознаёт: сравнение с сетями демона — preflight на настоящей app-ВМ, M10. Будущий Prometheus (M9), опрашивающий `/metrics` роли `llm`, потребует отдельного правила.
- **Vault для web и core.** У web и core теперь `extra_hosts` `vault.raditi.internal` → `VAULT_PRIVATE_IP` и `vault-ca.pem` в их каталогах секретов. `VAULT_PRIVATE_IP` обязателен в `.env` app-ВМ и без профиля `llm`. Без этого цепочка «выдача ключа → шлюз» на app-ВМ не собралась бы.
- **Preflight.** Проверяет `vault-ca.pem` у web, core и llm; требует, чтобы `METRICS_TOKEN` web отличался от управляющего токена `core` и `llm`; отвергает нулевой digest-заглушку у всех образов. Помощники требуют Node 26 и запускаются юнитами через `/usr/bin/node`. Юнит firewall: `PartOf=` и `ReloadPropagatedFrom=nftables.service`.
- **Стенд `verify:llm-app`.** 10 групп (было 9): новая — `core` доверяет CA Vault и разрешает закреплённое имя. Прокси выхода стенда закрепляет клиентский сертификат `llm` (`EGRESS_CLIENT_SHA256`). Закрытый допуск после потери выхода проверяется управляющим endpoint: 503 `raditi_busy`, после восстановления — 204. Запрос к провайдеру без ключа получает 401 до проверки допуска. Проверка firewall дополнена источниками входящих.
- **Результат 04.10.2026** на образе из текущего дерева: `verify:llm-app` — 10 групп в Docker Desktop (управляющий hairpin пропущен по дизайну), `--hairpin-only` — 2 группы в Colima, `verify:llm-firewall` — прошёл.

Отложено: отдельный секрет управляющего канала `core → llm` (`LLM_CONTROL_TOKEN`) вместо `METRICS_TOKEN` — M9/M10; периодическая проверка таблицы `raditi_llm` с алертом — M9; закрепление сертификата сервера выхода — M10.

## Оставшиеся границы

- Production host preflight, реальная загрузка systemd и полный рестарт целевой app-ВМ — M10. Здесь проверены код правил, реальные пакеты и структура зависимостей systemd.
- Проверка egress при работающем процессе выполняется раз в пять минут; runtime-проход B14 проверяет потерю канала при перезапуске, без искусственного ускорения production-таймера.
- Настоящие подписки Codex/Kimi, учётные ставки и приёмка владельца остаются открытыми. B14 не отправлял запросы в настоящие подписки.
- Следующий локальный шаг — подготовка драйвера Codex в P4. Сужение схемы B16 по проекту P3 относится к отдельному релизу после приёмки P3; до него активная цепочка миграций сохраняет старые поля. Старые Prisma-клиенты ещё могут читать `subscription_accounts.limits`, поэтому удалять колонку при работающих старых образах нельзя.
- До облака нужен полный продуктовый e2e с настоящим локальным WordPress: задача → агент → изменение → применение → бэкап → выкладка → проверка → откат. Подготовительный `verify:site` его не заменяет.
- Изменения не закоммичены и не отправлены в удалённый репозиторий.
