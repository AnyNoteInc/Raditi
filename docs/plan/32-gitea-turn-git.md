# N4 (часть P8): git для хода — два метода Gitea и HTTPS с файлом CA

04.10.2026 реализована часть P8, без которой не идёт ни один ход: супервизор всегда клонирует репозиторий сайта и всегда публикует ветку `agent/<taskId>`. `GitWorkspaceService` — реализация порта `TurnWorkspace`, через который супервизор это делает, — теперь работает с настоящей Gitea 1.27.3 по HTTPS, без транспорта `local-test`. Сам супервизор с Gitea не запускался: модуль git к `CoreModule` ещё не подключён (N11). Остальные восемь методов `GitProvider`, PR, вебхуки, обязательный workflow и раннеры остаются в P8 (инкременты N18 и N25 плана).

Всё проверено локально, на одноразовой Gitea и синтетических данных. Корневой `.env`, dev-Gitea (`raditi-dev-gitea-1`), настоящие токены и подписки не использовались.

## Шаг 0: как Gitea 1.27.3 выдаёт короткие учётные данные

`GitWorkspaceService` принимает от провайдера доступ со сроком от 5 до 125 секунд. На одноразовой Gitea 1.27.3 выяснено:

- **Срока у токена нет.** `POST /api/v1/users/{username}/tokens` принимает только `name` и `scopes`.
- Запросы управления токенами (создать, перечислить, удалить) Gitea принимает только с Basic-авторизацией. `Authorization: token …` получает 401. Паролем в Basic может быть сам токен; имя пользователя при этом Gitea не сверяет. Токену нужна область `write:user`: выданный адаптером доступ (`read:repository` или `write:repository`) таких запросов сделать не может — 403, проверено стендом.
- Область нового токена не может быть шире области токена, которым он создан («cannot create an access token with a broader scope than the authenticating token»). Наименьший набор для токена бота — `write:user` и `write:repository`.
- `read:repository` — клон проходит, push получает 403. `write:repository` — push проходит.
- Удаление токена действует сразу: следующий запрос git получает 401. Удалить уже удалённый — 404.
- **Токен не привязан к одному репозиторию.** Он открывает все репозитории, доступные боту.
- `GET /api/v1/token` отдаёт логин владельца токена. Список токенов — до 50 на страницу, порядок — по времени использования.
- Переименованный репозиторий API отдаёт как 301. `clone_url` в ответе Gitea строит из заголовка Host запроса.

Вывод: срок обеспечивает адаптер — удалением токена. Допустимо ли это, спрашивал вопрос В8 плана; решение по умолчанию «да». Вопрос и новая находка о границе токена — ниже, в «Вопросах владельцу».

### Гарантия порта `GitProvider.issueCredentials`

После `expiresAt` учётные данные не работают. Срок обеспечивает сам провайдер либо адаптер. У Gitea это гарантия адаптера, и она держится, пока жив выдавший процесс и Gitea подтверждает удаление; что происходит иначе — в «Ограничениях». `GitWorkspaceService` сам после `expiresAt` доступом не пользуется. Адаптер Gitea делает так:

1. Создаёт от имени бота токен с одной областью: `read:repository` для клона и чтения головы ветки, `write:repository` для push. Имя — `raditi-git-<r|w>-<срок в секундах Unix>-<16 hex>`.
2. Удаляет токен в момент `expiresAt` по таймеру. Если Gitea не подтвердила удаление — повторяет каждые 30 секунд, до 20 раз.
3. При старте процесса (`sweepCredentials`), перед выдачей и затем не чаще раза в 5 минут удаляет все токены бота с таким именем и истёкшим сроком («подметание»). Пока просроченные токены удалить не удалось, новые не выдаются. Список токенов читается до конца, но не дальше 40 страниц (около 2 000 токенов); если он длиннее, адаптер удаляет увиденные просроченные и в выдаче отказывает.
4. Живому токену с таким именем, которого этот процесс не выдавал, подметание ставит таймер на его срок: доступ процесса, которого уже нет, удаляется вовремя и без новых выдач. Срок дальше 900 секунд адаптер своим не считает и не трогает.
5. При остановке процесса (`revokeCredentials`) сразу удаляет всё, что выдал сам, не дожидаясь срока. Чужие живые токены не трогает.

Пункты 3 (старт) и 5 вызывает `GitCredentialRuntime` в `GitWorkspaceModule`: подметание — в `onApplicationBootstrap`, не дожидаясь ответа Gitea; удаление своих — в `onApplicationShutdown`, когда остальное уже остановлено. Сбой — строка `warn`, старту и остановке он не мешает. Обе операции — методы `GitCredentialLifecycle` пакета `@repo/git-providers`, порт `GitProvider` в domain не менялся; у GitHub и GitLab до P8 они ничего не делают.

Срок записан в имени, поэтому подметание отличает просроченный токен от живого и не мешает второй реплике `core`. `expiresAt` считается от момента до запроса создания: токен не живёт дольше запрошенного. Значение токена есть только в памяти `core` и в окружении процесса git; после остановки процесса оно нигде не сохранено.

Ограничения:

- доступ не сужен до одного репозитория (свойство Gitea);
- доступ живёт весь запрошенный срок, даже если операция git заняла секунду: отзыва у порта нет. `GitWorkspaceService` просит 120 секунд; на ход уходит не меньше четырёх доступов: чтение головы ветки, клон для базы, клон для публикации и push;
- таймеры не держат процесс. При штатной остановке токены удаляются сразу. Токен процесса, убитого `kill -9`, удаляет следующий процесс: просроченный — при старте, живой — в момент срока. Если после падения `core` не запущен, токен остаётся в Gitea до его старта; значения такого токена уже ни у кого нет;
- если Gitea в момент срока, старта или остановки недоступна либо не подтверждает удаление, токен живёт до удачного повтора (каждые 30 секунд, около 10 минут), а после — до подметания перед следующей выдачей. Проверено только unit-тестами: стенд Gitea не останавливает;
- подметание и таймер чужого живого токена сравнивают срок со своими часами. Если часы реплики `core` спешат, она удалит токен другой реплики раньше его срока на величину сдвига — операция git, которая шла в эти секунды, упадёт и повторится.

## Что сделано

**`packages/git-providers`.** `gitea-client.ts` — REST-клиент с инъецируемым `fetch`, zod на каждом ответе, пределом ответа 256 КиБ и таймаутом 10 секунд. Перенаправления не выполняются. Ошибки — `GIT_PROVIDER_FAILED` без токена, адреса и тела ответа. API вызывается только по `https:` и только с токеном бота; иначе — `GIT_PROVIDER_NOT_CONFIGURED`. Разбор вебхуков по-прежнему работает с любым адресом и без токена.

`gitea.ts` — `getRepository` и `issueCredentials`; остальные восемь методов — заглушки P8. Адрес клона адаптер строит сам: `<GITEA_URL>/<owner>/<repo>.git`. В `ref` ответа — имена, которые вернула Gitea: запрос `Sites/DEMO` даст `sites/demo`, и `GitWorkspaceService` откажет как в чужом репозитории. Срок доступа — от 5 до 900 секунд.

**`apps/orchestrator`.**

- `CoreConfig.git` из `GITEA_URL`, `GITEA_TOKEN` и новой `GIT_CA_FILE`. Адрес `http:` вне production — git не настроен (`git: null`), `core` стартует. В production `http:` — ошибка конфигурации. `https:` без токена — ошибка везде.
- `GitWorkspaceOptions.transport.caFile`: абсолютный путь к существующему файлу проверяется в конструкторе и передаётся git как `GIT_SSL_CAINFO`. Проверка `https:` и сертификата не ослаблена: тест подтверждает, что в окружение и аргументы git не попадает ничего, что её выключает. Файл добавляет доверенный CA, а не заменяет системный набор: в образе orchestrator (Debian, git 2.47.3, libcurl-gnutls) сервер с сертификатом CA из системного набора остаётся доверенным и при `GIT_SSL_CAINFO` с другим CA (проверено на ревью офлайн, в одноразовом контейнере без сети).
- `readBranchHead({ repo, branch })` — голова ветки одним `ls-remote` с доступом на чтение, без клона; отсутствующая ветка — `null`. Это источник `expectedBaseSha` для планировщика (N11). Имя ветки проверяется до обращения к провайдеру.
- `git-config.ts` — две обычные функции: провайдер и параметры транспорта из `CoreConfig.git`. `git-workspace.module.ts` — провайдеры `GIT_PROVIDER` и `GitWorkspaceService`; пока git не настроен, оба `null`.
- REST-клиент доверяет CA через `NODE_EXTRA_CA_CERTS`, как клиент Vault.

**Стенд `pnpm verify:gitea`** (`infra/dev/gitea-verify`): одноразовая Gitea 1.27.3 со встроенным HTTPS и сертификатом собственного CA стенда, организация `sites`, бот, приватный репозиторий. Сценарий идёт в отдельном процессе с синтетическим `HOME` и собирает git так же, как модуль. [Описание стенда](../../infra/dev/gitea-verify/README.md).

## Ход без изменений файлов

Супервизор публикует всегда. При пустом патче `preparePublication` создаёт коммит бота с тем же деревом, что у базы, и сообщением `Raditi task <taskId>, turn <N>`; `publish` отправляет его в `agent/<taskId>`. Стенд это подтверждает: ветка появляется, у коммита один родитель — база, деревья совпадают (сравнивает сам git: API Gitea в поле `commit.tree.sha` отдаёт id коммита). Контентная задача оставляет в репозитории по пустому коммиту на ход. Нужна ли ей ветка вообще — вопрос к N11 и N26, поведение не менялось.

Теперь строка скрипта заменяет оболочку стендом (`exec node …`): оболочки между pnpm и стендом нет, pnpm ждёт конца уборки и возвращает код стенда. Повторный сигнал уборку не обрывает: обработчики остаются до её конца. `kill -9` стенда оставляет контейнер `raditi-gitea-verify-<id>` и каталог `raditi-gitea-verify-*` во временном каталоге — их убирают вручную.

## Отступления от плана

- Функции композиции вынесены в новый `git-workspace/git-config.ts`. Иначе стенду пришлось бы импортировать модуль Nest или повторять композицию.
- `GitWorkspaceModule` не подключён к `CoreModule`: супервизор хода подключает N11, файл `core.module.ts` в этот инкремент не входил. Модуль проверен отдельным тестом.
- В production отсутствие `GITEA_URL` — не ошибка, git просто не настроен. Compose app-ВМ эту переменную ещё не передаёт; обязательной её делает подключение обработчика хода (N11, N23).
- Подметание идёт не только при старте, а ещё перед выдачей, не чаще раза в 5 минут, и только по токенам с истёкшим сроком в имени.
- Workflow GitHub Actions для стенда не добавлен: `.github/` в этот инкремент не входил.

## Что остаётся открытым

- Ход из `pnpm dev` на dev-Gitea невозможен: она слушает HTTP (вопрос В7 плана). Гейту это не нужно.
- В production токен бота должен приходить из Vault (правило 2); сейчас `GITEA_TOKEN` читается из окружения, как остальные локальные ключи. Это P7 и M10.
- Создание организации `sites`, бота и его токена в рабочей Gitea — ручная подготовка, runbook нет (N10, P11).
- Остальные методы Gitea, вебхук, обязательный workflow, GitHub и GitLab — P8 (N18, N25).
- Подметание при старте и удаление при остановке заработают в `core`, когда N11 подключит `GitWorkspaceModule`: до этого модуль проверен только своим тестом и стендом.
