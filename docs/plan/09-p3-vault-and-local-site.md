# P3 B5: KV v2 и локальный стенд настоящего сайта

30.09.2026. Продолжение [B4](08-p3-domain.md). Решение владельца: вся работа локально, полный e2e на настоящем локальном сайте — до выкладки в облако.

## Vault

В `packages/vault` реализован KV v2: чтение данных вместе с версией, CAS-запись, однократное создание ключа хода, чтение метаданных, LIST, мягкое удаление текущей версии и полное удаление метаданных со всеми версиями. Порт `SecretStore` расширен соответствующими типами. Прежнее чтение-заглушка не имело потребителей данных; новая форма `{data, version}` нужна обновителю подписок, у которого нет права читать metadata.

`session.ts` обслуживает общий вход AppRole и HTTP для KV и Transit. Одновременные запросы используют один вход, токен кэшируется с учётом срока; отказ 403 очищает кэш для следующего запроса. Записи автоматически не повторяются после сетевого сбоя: Vault мог успеть их принять. После исправления по ревью лимиты разделены: запросы и ответы AppRole/Transit/записи — 64 КиБ, чтение KV и metadata — 1 МиБ, полный ответ LIST — 16 МиБ. UTF-8 проверяется строго, редиректы запрещены. Ошибки не включают секреты, исходный ответ, путь и `cause`. Пути, CAS и строковые поля проверяются до запроса; проверка структуры не выполняет геттеры и отвергает опасные собственные ключи.

`kvCreateOnce` сначала пишет данные с `cas=0`, затем custom metadata. После конфликта или запрета перезаписи метод проверяет живую запись и повторяет только запись метаданных. Это восстанавливает прерванный второй шаг и не возвращает мягко удалённый ключ к жизни. Будущий `deletion_time` ещё не означает удаление. `kvDestroyAll` — `DELETE metadata`, а не операция `POST destroy` отдельной версии. LIST сортируется и фильтруется по курсору на клиенте; это один снимок, не серверная пагинация.

В `infra/vault` добавлены четыре политики: `core-turns`, `llm-subscriptions`, `subscriptions-writer`, `subscriptions-admin`. Core создаёт ключ хода один раз; шлюз читает и CAS-обновляет существующие подписки; импорт пишет без права чтения данных; вывод аккаунта уничтожает версии без чтения токена. Core может обновлять только `custom_metadata`, а не настройки хранения ключа.

Явный bootstrap оператора настраивает `turns/` (`max_versions=1`, CAS, удаление чтения через 25 минут) и `subs/` (`max_versions=1`, CAS). Runtime их не создаёт. Повторный bootstrap сохраняет записи и отклоняет несовместимые существующие mounts. Команда проверки — `pnpm verify:vault`; она создаёт отдельный OpenBao в памяти, инициализирует его через HTTP и держит root/unseal/scoped-токены только в памяти процесса. Разрешены локальный Docker и числовой loopback-адрес, образы не скачиваются. [Инструкции](../../infra/vault/README.md).

## Настоящий локальный WordPress

`pnpm verify:site` поднимает одноразовые WordPress 7.1.2, MariaDB 11.4.13 и WP-CLI 2.12.0 из уже имеющихся закреплённых образов. Проверяется настоящая опубликованная страница: снимок содержимого → изменение → HTTP-проверка → восстановление → HTTP-проверка исходного текста. Дополнительно применяются существующие запреты MCP и защищённых путей.

У стенда свои случайные пароли, Compose-проект, сеть, тома и закрытый временный каталог. WordPress, база и WP-CLI изолированы от внешней сети; фиксированный TCP-forwarder публикует только HTTP на loopback. Рабочие контейнеры `raditi-dev`, его база и сайты не затрагиваются. Содержимое, пароли и вывод WP-CLI не попадают в журнал. После завершения удаляются только ресурсы этого стенда. [Команда, состав и границы](../../infra/dev/site-verify/README.md).

Это первый исполняемый проход на реальном сайте. Полный продуктовый e2e остаётся открытым: нужно подключить шлюз и CLI (P3–P5), MCP (P6), git/pipeline (P8), операции WordPress (P10), жизненный цикл задач (P12) и чат с действиями (M2). Успех проверки страницы не закрывает путь «задание → агент → Применить → бэкап → проверка → откат».

## Исправление лимитов после ревью

Единый предел ответа 64 КиБ не позволял прочитать успешно записанные крупные данные после добавления служебных полей Vault, а LIST падал до клиентской пагинации на каталоге из 1500 ключей. Исправление задаёт отдельные ограниченные бюджеты для чтения KV и LIST; предел запроса сохранён. Запас чтения учитывает совместный возврат данных и custom metadata, а также JSON-экранирование `<>&` сервером. Лимиты закреплены в spec §15 и инструкции Vault; LIST по-прежнему читает весь префикс, каталог больше 16 МиБ требует разбиения по префиксам.

Новые регрессии сначала дали 8 падений на прежнем клиенте. После исправления и дополнения защитных проверок прошли `@repo/vault` typecheck, lint и **178/178 тестов** (19 новых), 9/9 инфраструктурных тестов Vault, проверка архитектуры (653 модуля, 2033 зависимости). Проверены точные границы и превышение на один байт, отмена потока без Content-Length, сохранение малого лимита при AppRole-входе и записи, LIST на 1500 и 30 000 ключей, неизвестные варианты лимитов.

`pnpm verify:vault` повторно прошёл на отдельном локальном OpenBao: **52 ACL/API + 20 проверок клиента**, включая точную запись 64 КиБ с `<>&`, чтение и обход 1500 настоящих ключей через курсор без потерь. `cleanedUp=true`: одноразовый контейнер удалён. Независимое ревью этой правки новых дефектов не нашло. Полный `pnpm gates` и WordPress-проход в рамках этой правки повторно не запускались; их предыдущие результаты приведены выше. Облако не использовалось.

## Изменения после ревью 02–04.10.2026

- **Bootstrap при `pnpm infra:up`.** Команда после `docker compose up -d` вызывает `pnpm vault:bootstrap` (`infra/vault/bootstrap.mjs --wait`): ждёт готовности dev-OpenBao, создаёт `turns/` и `subs/` и четыре политики. Повторный запуск ничего не меняет. `pnpm vault:bootstrap` выполняет тот же шаг отдельно для уже запущенного контейнера `vault`. Хранилище dev-OpenBao — в памяти: пересоздание контейнера стирает секреты, и в аккаунты подписок нужно войти заново (`subscriptions:login`).
- **Прерванный bootstrap.** Сразу после включения KV v2 mount недолго отвечает 400; запись настроек повторяется. Mount, оставшийся пустым и ненастроенным, донастраивается на месте. Mount с ключами и другими настройками по-прежнему требует решения оператора.
- **Клиент.** Ожидаемый 403 от однократного создания ключа (`kvCreateOnce`) больше не сбрасывает кэш токена AppRole. Лимиты `custom_metadata` проверяются до записи данных: не больше 64 ключей, ключ до 128 байт, значение 1–512 байт, печатные символы. Каждое строковое значение KV — не длиннее 32 768 символов; более длинное отклоняется до сетевого запроса.
- **Health.** `core`, `mcp` и `llm` проверяют каждый KV mount, с которым процесс уже работал (`sys/internal/ui/mounts/<mount>`): пропавший mount или потерянное право дают `degraded`.
- **`pnpm verify:vault`.** Теперь 69 проверок политик, CAS и write-once и 30 проверок клиента на OpenBao 2.7.0. Добавлены: прерванный mount, серверные лимиты метаданных, одноразовый SecretID и проба mount для health. `@repo/vault` — 217 тестов.

Не сделано и отнесено к P7: запись только метаданных в порте `SecretStore` для восстановления метаданных ключа хода (сейчас повторяется write-once, долговременная отметка отзыва побеждает поздний ремонт) и объявление лимитов KV в самом порте.
