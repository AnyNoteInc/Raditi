# P6: сохранённый ход и откат перед заменой

01.10.2026. Локальный блок продолжает [контентный протокол WordPress](26-p6-wordpress-content.md), §8 и §11 спецификации.

## Реализация

- `PostgresTaskTurnAssignmentStore` подключён к `TURN_ASSIGNMENTS` роли core. Назначение, `TaskTurn.running` и увеличение `tasks.turn_no` сохраняются одной транзакцией под арендой сайта. Номер завершённого хода не используется повторно. Операционный адаптер P2 сохранён для отдельных PoC исполнителя.
- Закрытие назначения и перевод `TaskTurn` в `completed`, `failed`, `lost`, `cancelled` или `timed_out` атомарны. Устаревшая эпоха не меняет статус. Пока внешняя запись не подтверждена или сайт удержан для оператора, назначение и ход остаются открытыми. Ход раннера, который ни один раннер не забрал и который брошен по отмене клиента или по сроку, получает `cancelled` или `timed_out` по причине, переданной в `abandon`; её передают и `RunnerHub`, и восстановление (`TurnExecRecovery`).
- Журнал атомарно сохраняет события и метаданные текущего `TaskTurn`: native session, кандидат коммита, префикс снимка и модель выданного ключа. Тексты ошибок CLI в `failure_reason` не попадают — только фиксированная причина супервизора.
- В доверенном запросе и сохранённом плане появился `replacesTurn`. Замена получает новый последовательный номер и восстанавливает вход заменяемого хода: его базовый коммит и прежний checkpoint. Это отличается от обычного продолжения, которое берёт результат последнего завершённого хода. Для замены первого хода checkpoint отсутствует, сессия начинается заново. Раннер принимает restore любого более раннего хода своей сессии: продолжение — ход n−1, замена — точка, с которой начинал заменяемый ход. До ревью 02–04.10.2026 раннер принимал только n−1, и любая замена после первого завершённого хода падала на раннере с `SNAPSHOT_LOAD_FAILED`; локальный исполнитель такой проверки не имел, поэтому стенды проходили.
- Для Git замена закрепляет `expectedBranchSha` последнего завершённого продуктового хода; отсутствие опубликованной ветки обозначается `null`. Продуктовый адаптер проверяет значение по истории задачи. Новая рабочая копия и кандидат строятся из входного коммита, а публикация заменяет прежнее предложение только через `--force-with-lease` с сохранённым SHA. Внешняя правка ветки, включая сброс к базовому коммиту, останавливает публикацию; повтор уже применённого push остаётся идемпотентным.
- Супервизор выдаёт ключ нового хода, затем вызывает `TurnContentRollback` под своей эпохой. Только после успешного отката он готовит Git и контейнер. Отсутствующая зависимость отката, чужой токен, конфликт состояния, истёкший снимок или неизвестный результат записи останавливают запуск.
- Локальная композиция `McpTurnContentRollback` использует действующий MCP-токен и существующие снимки, журнал и условные записи. Она проходит цепочку незавершённых замен от нового хода к старому; уже восстановленные снимки пропускаются. Повтор после частичного отката возвращает оставшиеся объекты, не запуская агента между ними. Доверенный откат идёт с признаком `hostUndo`: он может восстанавливать снимки прежних ходов (агент — только своего хода) и не расходует лимит двадцати объектов нового хода. Конфликт содержимого останавливает откат кодом `CONFLICT`; любой другой сбой — `CONTENT_RESTORE_FAILED` (503), его повторяет следующая попытка.

## Проверка

Финальный проход успешен: 1 483 теста orchestrator на настоящей PostgreSQL, 238 тестов БД и 394 проверки обновления/общего пользователя. Тесты domain — 601; Node-сценарии orchestrator — 33. Инфраструктура — 224 успешных и два штатно пропущенных теста. Типы, линтер, форматирование, проверка окружения и архитектуры прошли; сборка orchestrator и дополнительный WordPress-сценарий тоже прошли. Одноразовые сервисы удалены.

```sh
pnpm verify:db
pnpm verify:mcp-content
pnpm --filter @repo/domain --filter @repo/db --filter orchestrator typecheck
pnpm --filter @repo/domain --filter @repo/db --filter orchestrator lint
pnpm --filter @repo/domain --filter @repo/db --filter orchestrator test
pnpm check-architecture
```

Новые проверки PostgreSQL покрывают конкурирующий запуск, атомарный отказ сохранения, неизменность номера, восстановление правильного checkpoint, завершение и потерю хода, устаревшую эпоху, отмену, таймаут и удержание внешней записи. Супервизор проверяется с обоими исполнителями. Настоящие Git-репозитории проверяют замену предложения из старого коммита, отсутствие прежней ветки, идемпотентный push и конфликт до/после последней проверки аренды. Контентный стенд дополнен двумя настоящими страницами WordPress: один объект успешно возвращается, второй получает синтетический окончательный отказ; следующий ход завершает откат, и только затем проходит к подготовке исполнителя. База, S3 и OpenBao настоящие; выдача ключей и исполнение агента в этом дополнительном сценарии синтетические.

Логи текущего прохода: `/tmp/raditi-p6-turn-db-final.log`, `/tmp/raditi-p6-turn-content-final.log`, `/tmp/raditi-p6-turn-typecheck-final.log`, `/tmp/raditi-p6-turn-lint-final.log`, `/tmp/raditi-p6-turn-tests-final.log`. Проверки используют собственные одноразовые сервисы без рабочего `.env`, подписок или облачных серверов.

Числа раздела — прогон 01.10.2026. Итог 04.10.2026: `pnpm verify:db` — 2 139 тестов orchestrator без пропусков и 320 тестов базы; `pnpm verify:mcp-content` — 30 строк PASS ([отчёт ревью](29-review-2026-10.md)).

## Границы и продолжение

Это локальная основа сохранённого хода и допуска замены. Кнопки чата, постановка действий в очередь, состояние задачи, расчёты и сообщения клиенту подключаются в P12. Серверного пути «Отменить» для уже завершённой задачи нет: `restore` работает внутри живого хода, а откат завершённой задачи проектируется в P12. Транспорт core → отдельная роль MCP и штатный resolver доступов к сайту ещё не реализованы; контентный профиль запрещён в production.

Восстановление без квитанции, завершение подготовок и очистка истёкших внешних данных реализованы следующим [локальным блоком P6](28-p6-content-recovery-retention.md). Далее — согласование, публичный браузер и инфраструктура MCP. Согласование, публичный браузер, инфраструктура MCP, юридический гейт, полный пользовательский WordPress e2e и приёмка настоящего Kimi остаются открытыми. Изменения локальные, без коммита и отправки.
