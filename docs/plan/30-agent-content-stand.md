# Стенд-склейка `verify:agent-content`: настоящий CLI правит страницу через настоящую роль `mcp`

04.10.2026. Инкремент N2 плана следующих работ: P12 (пункт ревью «настоящий `tools/list` роли `mcp` в стенде»), проверка P6, сценарии фейка B13. Всё локально: одноразовые сервисы, фейки подписок, синтетический сайт. Настоящие подписки, корневой `.env` и `~/.codex` не используются.

## Что построено

Одна команда проводит правку страницы настоящего WordPress одной цепочкой, ниже очереди:

```
аренда сайта и продуктовое назначение → ключ хода из настоящего issue → CLI в образе песочницы
→ sandbox-gw → роль llm на фейке подписки → роль mcp с контентным профилем → плагин WordPress
```

```sh
pnpm verify:agent-content            # со сборкой образов и orchestrator
pnpm verify:agent-content --no-build # повтор на готовых образах
```

- **Стенд** — `apps/orchestrator/scripts/verify-agent-content.mjs` (сервисы, роли, уборка) и `verify-agent-content-turns.mjs` (ходы и проверки). WordPress и MariaDB — `verifySiteFoundation` из `infra/dev/site-verify` с тем же переходом на loopback. PostgreSQL, OpenBao, фейки, прокси выхода и `sandbox-gw` — стек `infra/dev/llm-verify/stack.mjs`.
- **Допуск хода — как в продукте.** `PostgresSiteLeaseStore.acquire` → `PostgresTaskTurnAssignmentStore.open` (создаёт `TaskTurn`) → `GatewayTurnCredentials.issue` с `requireAssignment: true` под AppRole `core-turns`. Аккаунты подписок заведены штатными путями входа, как в B13; ставка модели синтетическая.
- **CLI** — Codex 0.158.0 и Kimi 2.1.1 в образе стенда на production-среде агента (`infra/sandbox/Dockerfile`, цель `runtime`), как в B13. Запуск — `prepare` и `command` драйверов с проверками исполнителя (`preparedFilesSchema`, нет ключей в файлах, env и argv). Сеть контейнера — только `sandbox-gw` под сетевым сторожем.
- **Роль `llm`** — отдельный процесс (`verify-llm-worker.mjs`, AppRole `llm-subscriptions`), как в B13.
- **Роль `mcp`** — отдельный процесс `verify-agent-content-mcp-worker.mjs`: production-модуль `McpAppModule` с локальным контентным профилем. Композиция та же, что в `verify-content-worker.mjs`: фикстурный resolver одного сайта и root-токен стенда. Разрешённый Host — только `host.docker.internal`. Логгер — штатный `ConsoleLogger` роли, как в `startMcp`: проверка логов читает настоящий вывод роли. Процесс считает запросы (метод JSON-RPC, имя инструмента, статус ответа) и обращения к сайту; содержимое и токены не сохраняет.
- **Фейк подписок** (`infra/dev/llm-verify/fake-subscriptions.mjs`) — два сценария:
  - `content_edit`: чтение страницы, запись с ключом идемпотентности, та же запись с тем же ключом, итог хода с `change_type: content`;
  - `content_forbidden`: один вызов `wp_rest`, который платформа должна отклонить, затем итог. Без `body` — чтение заданного маршрута (`/wp/v2/comments/1`), с `body` — запись без ключа идемпотентности.
  - Для Codex вызов — ячейка `exec` с `tools.mcp__raditi__wp_rest(…)`, для Kimi — вызов объявленной функции. `{{contact}}` в тексте правки заменяется первым маркером контакта из разговора: фейк переносит маркер, как это должна делать модель. Без маркера сценарий падает и контакт не выдумывает.
- **Стек** (`compose.yml`, `stack.mjs`): адрес MCP для `sandbox-gw` — параметр `VERIFY_MCP_UPSTREAM`. По умолчанию прежний синтетический сервер, поэтому `verify:llm-gateway` не изменился. `startVerificationStack({ content: true })` добавляет S3 (профиль Compose `content`, образ закреплён тем же digest, что в остальных стендах), свободный порт роли `mcp` и бакет снимков. `startWorker('mcp', …)` запускает worker роли.
- **CI** — `.github/workflows/agent-content.yml`. **Не подтверждён до отправки ветки.** Контракт workflow (фильтр путей покрывает скрипты стенда и их импорты, список загружаемых образов равен закреплённым в `verify-site.mjs`, команды запуска) проверяет `infra/dev/llm-verify/agent-content.test.mjs`.

## Что проверяет стенд

Для каждого CLI — три хода, каждый отдельной задачей на одном сайте.

**Ход A, правка (`content_edit`):**

- роль ответила на `initialize` и `tools/list`; три вызова `wp_rest` приняты (чтение и две одинаковые записи);
- на повторённый ключ — одна строка `mcp_calls` (`result = ok`, привязана к назначению), один снимок, одна квитанция плагина (`raditi_content_call_*`), одна запись на сайт;
- снимок лежит в бакете артефактов под ключом `snapshots/<siteId>/<id>.json` до того, как запись уходит на сайт. Основное доказательство: worker роли в момент отправки записи видит подтверждённый снимок, объект в настоящем S3, выставленный `mcp_calls.write_started_at` и аренду с этим вызовом. Сравнение `LastModified` объекта с `write_started_at` — грубое: S3 хранит целые секунды, поэтому оно ловит только перестановку больше секунды. Что `write_started_at` не ставится без подтверждённого снимка, проверяют тесты журнала, а не этот стенд;
- объект зашифрован (исходного текста и контакта в нём нет) и расшифровывается ключом рабочего пространства в исходный текст страницы;
- публичная страница отдаёт новый текст. Контакт посетителя вернулся на страницу из маркера: модель видела только `[[raditi:email:…]]`;
- вторая аренда сайта не выдаётся, пока ход держит свою (проверка — после выхода CLI, до закрытия хода); после закрытия у ключа хода выставлен `llm_keys.revoked_at`;
- ключа хода, токена MCP, пароля приложения сайта и контакта нет ни в запросах провайдеру, ни в событиях CLI; ключа и токена нет на странице.

**Ход B, запрещённый маршрут** (`wp_rest` на `/wp/v2/comments/1`) и **ход C, запись без ключа идемпотентности:**

- ни один запрос, дошедший до роли, не принят: каждый получил HTTP 400 на допуске;
- строки журнала и снимка нет, запросов к сайту нет, квитанций не прибавилось, страница не изменилась;
- CLI получил отказ, модель о нём узнала, ход завершился штатным итогом в пределах срока (180 секунд; фактически около секунды).

**В конце:** в S3 ровно по одному объекту снимка на правку, во всём журнале `mcp_calls` — две строки (по одной на правку). Ключей хода, токенов MCP, значений подписок, пароля сайта, ключа S3, root-токена стенда и контактов нет в логах ролей и сервисов, аудите OpenBao и дампе PostgreSQL; пустой лог роли `mcp` стенд не принимает. Все собственные контейнеры, сети, тома, процессы и временные каталоги удаляются; при SIGTERM, в том числе повторном, это проверено в четырёх точках прохода (раздел «Проверка»).

## Наблюдения

Формулировки отказов принадлежат CLI и контрактом стенда не являются. Стенд печатает их строками `OBSERVED`. Где вывод сделан по тексту сообщения, а не измерен, это сказано.

1. **Codex 0.158.0 не называет провайдеру инструменты платформы.** Измерено в каждом проходе, стенд печатает это двумя строками `OBSERVED`: в первом запросе хода нет строк `wp_rest`, `site_info` и `restore`; во всех запросах хода правки объявлены только `exec`, `wait`, `request_user_input`, `request_user_input_async` и `sleep`. Вызов `tools.mcp__raditi__wp_rest(…)` из ячейки `exec` при этом работает, то есть список роли CLI принял. По тексту описания `exec`, вложенные инструменты перечислены в переменной `ALL_TOOLS`; её содержимое стенд не читал. Следствие: настоящая модель узнает имена инструментов только из инструкций платформы или из `ALL_TOOLS`. Kimi 2.1.1 объявляет все три инструмента функциями `mcp__raditi__*` рядом со своими (`AskUserQuestion`, `Bash`, `Edit`, `Glob`, `Grep`, `Read`, `Write`): имена стенд проверяет в каждом запросе. Схему `wp_rest` с шаблоном маршрута показал один отладочный снимок запроса, обычный проход её не печатает.
2. **У Kimi вызов на `/wp/v2/comments/1` до роли не доходит.** Измерено: запросов `tools/call` у роли ноль, модель получила `Invalid args for tool "mcp__raditi__wp_rest": /route must match pattern …`. Судя по тексту, CLI сам проверяет аргументы по схеме из `tools/list`. Codex тот же вызов отправил, роль отклонила его на допуске.
3. **На один отклонённый вызов модели Kimi шлёт роли три запроса.** Измерено в одиннадцати проходах, без исключений: три `tools/call` с ответом 400 при двух запросах к провайдеру, то есть повторяет сам CLI. Модель получила `Tool "mcp__raditi__wp_rest" failed: Streamable HTTP error: Error POSTing to endpoint: {"jsonrpc":"2.0","id":2,"error":{"code":-32000,"message":"Invalid MCP request"}}`. Причина повторов (HTTP 400 как сбой транспорта) — предположение по этому тексту, код CLI не разбирался.
4. **Codex показывает отказ роли как ошибку инструмента:** `tool call error: tool call failed for raditi/wp_rest … Mcp error: -32000: Invalid MCP request`, с `isError: true`; ячейка `exec` при этом завершается (`Script completed`). Запрос к роли один.
5. **Запросы CLI к роли за ход правки** стенд печатает строкой `OBSERVED` в каждом проходе (метод HTTP, метод JSON-RPC, статус). Codex: `initialize` 200, `notifications/initialized` 202, `tools/list` 200, три `tools/call` 200. Kimi: то же, но после `notifications/initialized` идёт `GET /mcp` (ответ 405), а в конце — два `notifications/cancelled` (ответ 202). Все эти запросы дошли до роли через `sandbox-gw`.
6. **Процесс роли `mcp` печатает предупреждение `pg`:** `DeprecationWarning: Calling client.query() when the client is already executing a query is deprecated and will be removed in pg@9.0`. Снято один раз с `--trace-deprecation`: в стеке (10 кадров) только `PgTransaction` из `@prisma/adapter-pg` 7.10.0 и интерпретатор запросов Prisma. Какой запрос роли его вызывает, не разбиралось; в `apps/orchestrator/src/mcp` одновременных запросов в одной транзакции (`Promise.all`) нет. На работу стенда не влияет; при переходе на `pg` 9 станет ошибкой.
7. При остановке или падении внутри сценария основа WordPress печатала `FAIL local real-site foundation at restoring and verifying content snapshot` — название своего последнего этапа, а не место остановки. При проверке партии это исправлено: сценарий стенда — отдельный этап основы, строка теперь `FAIL local real-site foundation at scenario of the calling stand`. Место остановки по-прежнему называет строка стенда `Agent content verification failed at: …` или `interrupted at: …`.

Дефектов продуктового кода стенд не нашёл: `apps/orchestrator/src/mcp`, `infra/sandbox/gateway.mjs`, `packages/site-adapters` и `packages/agent-drivers` не менялись.

## Ревью

Независимое ревью 04.10.2026 нашло и исправило в скриптах стенда:

1. **Проверка логов роли `mcp` читала пустой лог.** Worker запускал Nest с `logger: false`, поэтому строка «секретов нет в логах ролей» о роли `mcp` ничего не доказывала. Теперь роль пишет штатным логгером, а стенд отказывает при пустом логе. Красный проход: с новой проверкой и прежним `logger: false` стенд упал на `The role mcp logged nothing`.
2. **Повторный сигнал обрывал уборку.** Обработчики стояли через `process.once`: второй сигнал (повторный Ctrl-C; отмена workflow в GitHub Actions шлёт SIGINT, затем SIGTERM) завершал процесс посреди уборки. Красный проход в 06:56–06:57: два SIGTERM через секунду оставили 7 контейнеров, 5 сетей и 2 тома. Теперь обработчик стоит до конца прохода; зелёные проходы — в таблице выше.
3. **Строка `OBSERVED` отклонённого хода печаталась до проверок отказа.** Теперь она печатается после проверок «ничего не принято, запросов к сайту нет»: до них текст CLI мог бы содержать ответ сайта.
4. **Усилены проверки:** `llm_keys.revoked_at` после закрытия хода (раньше «ключ отозван» значило только, что `revoke` не упал), общий счёт строк журнала, root-токен стенда среди искомых секретов. Наблюдения 1 и 5 теперь печатает каждый проход, а не один отладочный.

Продуктовый код ревью не меняло. Тот же приём `process.once` стоял в `verify-llm-gateway.mjs` (B13). При проверке партии он заменён так же: обработчик остаётся до конца прохода. Проверено двумя SIGTERM через секунду посреди ходов драйверов: код 1, остатков нет. В `verify-content.mjs`, `verify-site.mjs`, `verify-db.mjs` и `verify-edge.mjs` приём остался.

## Отступления от плана

- **Ход C добавлен сверх плана.** Запрещённый маршрут до роли через Kimi не доходит (наблюдение 2), поэтому отказ самой роли на настоящем Kimi проверяет запись без ключа: плоская схема инструмента её допускает, CLI отправляет. Сценарий фейка `content_forbidden` получил необязательный `body`.
- **Ключ хода выдаёт сам процесс стенда**, а не worker `core` из B13: существующий `verify-core-worker.mjs` создаёт `GatewayTurnCredentials` без `requireAssignment`, а менять чужие скрипты инкремент не должен. Издатель — продуктовый класс под AppRole `core-turns`; роли `llm` и `mcp` — отдельные процессы, как требует план.
- **«Объявлен провайдеру» проверяется только для Kimi.** У Codex объявлять нечего (наблюдение 1): стенд проверяет наличие `exec` и сам вызов.
- **CLI запускает собственный код стенда**, а не `createDriverRunner` из `verify-llm-gateway-drivers.mjs`: тот регистрирует токен MCP хода у синтетического сервера фейка. Шаги те же: `prepare`, `command`, проверки исполнителя, `runPrepared`.
- **S3 — сервис Compose под профилем**, а не отдельный контейнер стенда: уборка и проверка остатков остаются в одном `compose down`.
- Флаг `--no-build` стенд убирает из `process.argv` до запуска основы WordPress: `verify-site.mjs` читает тот же argv и отказывает при любом параметре.

## Что остаётся открытым

- **Инструкции для Codex должны называть инструменты платформы** (наблюдение 1). Иначе модель не знает о `wp_rest` до перебора `ALL_TOOLS`. Место — инструкции хода (`agentGuide` адаптера, P10) и планировщик (N11); проверить на стенде гейта.
- **Отказ на допуске как HTTP 400** (наблюдения 3 и 4) работает, но Kimi шлёт три запроса вместо одного и показывает модели текст ошибки транспорта, а не отказа инструмента. Отвечать ли на отклонённый `tools/call` результатом инструмента с `isError` — решать в N21 (политика адаптера в шлюзе). До решения поведение закреплено стендом: ничего не принято, ход не завис.
- Роль `mcp` в стенде — локальная композиция с root-токеном; штатная роль с resolver из Vault и своей AppRole — N5. Доверенный откат, очередь, «Отменить» и интерфейс — N7–N17.
- Режим pull-раннера под gVisor для этого стенда не делался: план требует его перед закрытием N12 и N17.
- Workflow `agent-content.yml` не подтверждён до отправки ветки. На Linux роль `mcp` слушает `0.0.0.0` (на хост `sandbox-gw` ходит через мост Docker), на macOS — `127.0.0.1`; ветка для Linux ни разу не исполнялась.
- Уборка при сигнале строго во время `compose up` стека ролей не проверена (раздел «Проверка»). Предупреждение `pg` в роли `mcp` (наблюдение 6) не разобрано.
- Модель сценарная. Живая подписка в стенде не используется; засчитывать ли сценарную модель в гейт — решает владелец.

Изменения применены локально, без коммита и отправки.
