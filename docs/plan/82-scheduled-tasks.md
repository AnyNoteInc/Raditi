# План 82. Запланированные задачи и уведомление о выполнении

Запрос владельца от 15.11.2026 (два снимка экрана — страница «Запланированные задачи» и окно «Новая запланированная задача» приложения Claude):

> давай реализуем функционал запланированных задач
> 1. иконка с таймером должна быть перед страницами и после чата
> 2. дизайн как на картинке, оформи его с учетом радити
> 3. задачу можно настроить вручную как на второй картинке
> 4. должна быть возможность настройки задачи через чат
> 5. в рамках этой задачи давай реализуем уведомления через web push в чате, чтобы приходила информация о том, когда задача исполнилась
> 6. механизм изучи от OpenAI и Claude code и давай реализуем

Работа — в ветке `feat/scheduled-tasks` (дерево `raditi-sched`, от `main` `cef48b03`). Решения без слов владельца — значения по умолчанию по указанию от 09.10.2026; они помечены «по умолчанию» и записываются в spec §20, блок «Запланированные задачи — решения 15.11.2026». До кода план прошёл ревью с трёх сторон (правила, сверка с кодом, продукт): 61 замечание, все учтены ниже.

## 1. Как это сделано у OpenAI и Anthropic

Разведка 15.11.2026 — документы learn.chatgpt.com, code.claude.com, support.claude.com, webkit.org, RFC 8030/8291/8292; `help.openai.com` закрыт для чтения, сведения оттуда — по вторичным источникам, описание инструмента `automations` ChatGPT — по утёкшим системным подсказкам.

- **Запуск — новый чат.** ChatGPT: «отдельная задача начинает новый чат на каждый запуск и сообщает результат в Scheduled»; режим «возвращаться в тот же чат» у OpenAI есть и даёт видимые сбои. У Claude каждый запуск — своя сессия, история запусков — на странице задачи.
- **Расписание — заготовки и время в поясе.** Claude: каждый час, ежедневно, по будням, еженедельно (дни), вручную, своё; чаще раза в час нельзя; время — в местном поясе; запуск ровно в 9:00 может начаться на несколько минут позже. OpenAI хранит правило RRULE (RFC 5545). «Один раз» после запуска выключается и помечается завершённым.
- **Пропуски.** Claude догоняет один последний пропущенный срок, более ранние показывает одной строкой «Пропущено» с причиной; запуск не начинается, пока идёт предыдущий.
- **Настройка в чате.** OpenAI, инструмент `automations` (`create`/`update`): название — коротко, без даты; инструкция — «как будто это сообщение клиента»; относительное время («через 15 минут») считает сервер, не модель; ошибку инструмента — объяснить и не говорить об успехе. Claude: уточняющие вопросы, затем название, расписание и инструкция на подтверждение; каждое создание — с кнопкой «Запланировать».
- **Без надзора.** Claude: «запущенная инструкция — не живые слова клиента и не согласие на действия во время запуска»; предупреждение в окне; «ничего не выходит наружу, пока вы не посмотрели и не одобрили».
- **Уведомления.** Когда запуск закончился, упал, ждёт клиента или не начался; одна строка, ведущая с результата; нажатие открывает чат запуска; не слать, когда клиент уже смотрит.
- **Пределы.** OpenAI — 3/5/10/15 активных задач по тарифам; Claude — 100 запусков в час на аккаунт, «Запустить сейчас» — 30 в час на задачу.

## 2. Что уже есть в коде

- **Web Push** (план 75, ВВ8): `push_subscriptions`, `notification_settings`, `chat_notifications` (виды `answered|question|ready|failed|limit`, без `attempt` и `turn_no`, без уникальности), `ChatNotify` в `core` (`apps/core/src/tasks/chat-notify.ts`, `web-push@4.0.0`), service worker `apps/web/public/sw.js` (текст — по `GET /api/notifications/<id>`), переключатель на `/settings`. В полезной нагрузке push — только id (правило 1). Дыры (аудит 15.11.2026): нет манифеста — на iPhone и iPad push не работает; переключатель «В этом браузере» на деле общий на все браузеры и через `notification_settings.push` глушит все; у отправки нет предела времени; в dev отправка падает на `http://` в subject VAPID; без сессии service worker открывает `/chats`, а не чат.
- **Создать чат может только web**: `createDialog` (`packages/trpc/src/services/chat/tasks.ts:262`; Vault, затем своя транзакция), а `core` не импортирует `@repo/trpc` (`core-no-trpc-ui`). Образец обхода — Telegram (план 80, Т9): `core` передаёт работу web через Traefik по `TELEGRAM_INTAKE_URL` с секретом, web вызывает `createDialog` с детерминированным UUID v7 (`updateUuid`, `packages/trpc/src/services/telegram/intake.ts:79`); 400 и 413 — окончательно, остальное повторяется.
- **Инструменты агента, которые применяются в конце хода**: семейство `pages` (план 73) — `mcp` резервирует (`page_reservations`, права — `authorManages`), `core` после `PassSettlement.settle` применяет (`PageChanges`), упавший проход отклоняет резервы сразу (`failPages`).
- **Браузер задачи узнаёт нажатие «Сохранить»/«Опубликовать»** на сайте (`SiteAdapter.browserCommitAction`, `apps/browser/src/sessions/worker-session.ts:1272`) — на нём держится предел 20 объектов (Б34).
- **Периодические задания `core`**: планировщики BullMQ (`leads-scheduler.ts`, `telegram-scheduler.ts`), проход по строкам с `FOR UPDATE SKIP LOCKED` (`packages/billing/src/renewal.ts`).
- **Часовой пояс клиента нигде не хранится**, всё — по Москве; в Node 26.10 есть `Temporal`, но в браузерах его нет, а domain собирается и в web — считаем через `Intl` (образец — `isPlanPeak`).
- **Значки** `app-icon.tsx`: из нужных есть только `search` и `clock`.

### Расписание

| № | Решение | Откуда |
| --- | --- | --- |
| Зп11 | **Частоты** — Зп8; чаще раза в час нельзя: «Каждый час» — только одно расписание у задачи, а сроки всех расписаний за ближайшие 7 дней — не ближе 60 минут друг к другу («Запуски одной задачи — не чаще раза в час»). «Только вручную» — без расписания, запуск только «Запустить сейчас». Своего RRULE и cron у клиента нет | По умолчанию (Claude, OpenAI) |
| Зп12 | **Часовой пояс — у задачи** (IANA). Пояс браузера web запоминает в `users.timezone` при входе в кабинет; по умолчанию задача берёт его, иначе `Europe/Moscow`; выбор — в «Дополнительных настройках» (список поясов России и СНГ, и пояс задачи или браузера, если его там нет). Проверка — `new Intl.DateTimeFormat('en-US', { timeZone })`, хранится `resolvedOptions().timeZone`. Подписи без пояса — Москва, другой назван рядом («по времени Новосибирска») | По умолчанию |
| Зп13 | **`next_run_at`** пересчитывается только при смене расписания, пояса или включении — от «сейчас», всегда в будущее; пауза ставит `NULL`; правка названия, инструкции, «Размышления» и уведомлений его не трогает. Каждая запись строки задачи — под `FOR UPDATE` строки | По умолчанию |
| Зп14 | **Пропуски.** Подошедшая задача запускается один раз — за последний срок не позже текущего; если сроков набралось несколько (платформа стояла), ранние — одной строкой «Пропущено» (`missed`). Срок старше 6 часов не догоняется — «Пропущено». Не запускается, пока у задачи есть запуск `pending` или его чат в работе (`queued`, `preparing`, `running`) — «Пропущено: предыдущий запуск ещё идёт». Разброса времени нет: очередь `agent-turns` выравнивает всплеск в 9:00 | По умолчанию (Claude) |
| Зп15 | **«Один раз»** с прошедшим временем не сохраняется («Это время уже прошло — выберите другое»; окно проверяет сразу). Когда после захвата у задачи не остаётся сроков, она выключается: `enabled = false`, `paused_reason = 'completed'`, в списке — «Завершена <дата>» и исход последнего запуска. Сохранение новой будущей даты включает её снова. «Один раз» от агента со сроком от сейчас (`inMinutes`) хранит готовый момент; если ход закончился позже этого момента, но не позже 6 часов, задача запускается на ближайшем такте | По умолчанию (Claude, OpenAI) |
| Зп16 | **Предел** — 20 включённых задач на рабочее пространство, у всех тарифов одинаково; до пяти расписаний у задачи. Предел проверяется при создании, включении и переносе задачи в другой проект — под замком строки рабочего пространства | По умолчанию |

### Запуск

| № | Решение | Откуда |
| --- | --- | --- |
| Зп17 | **Запуск — новый чат** тем же `createDialog`, что и кабинет: автор — создатель задачи, проект, инструкция, «Размышление» и название — из снимка в строке запуска; название чата — название задачи (`title_source = 'client'`, модель его не переименовывает). Чат запуска — обычный чат: код меняется только в предпросмотре и ждёт `/release` владельца, вопрос оставляет чат ждать ответа, кредиты резервируются и списываются как у любого прохода (правила 3, 7) | По умолчанию (OpenAI, Claude) |
| Зп18 | **Предпросмотр чата запуска не строится заранее** (иначе каждый запуск копирует базу с хостинга): `createDialog` получает `preview: 'on_demand'` — строка предпросмотра есть, сборка — при первой нужде (кандидат, браузер агента на предпросмотре, правка контента, просмотр клиентом) тем путём, что уже есть для предпросмотра по запросу | По умолчанию (ревью) |
| Зп19 | **Кто запускает.** `core` раз в минуту (планировщик BullMQ `schedule.tick`, очередь `schedules`) по одной задаче под `FOR UPDATE SKIP LOCKED` пишет строку запуска со снимком полей задачи, событие outbox `schedule.start` и сдвигает `next_run_at`. Задание `schedule.start` передаёт `{runId}` web на `SCHEDULE_INTAKE_URL` (`/api/webhooks/scheduled-runs`, через Traefik, как Telegram) с секретом `SCHEDULE_INTAKE_SECRET` в заголовке `x-raditi-schedule-secret`; web вызывает `startScheduledRun`. Без обеих переменных `core` планировщик не заводит и пишет об этом в лог; страницы работают, запуски не идут | По умолчанию (образец — Т9) |
| Зп20 | **Строки запуска создаются только под `FOR UPDATE` строки задачи** — тактом и «Запустить сейчас»; под замком же — отказ, если у задачи есть запуск `pending` или чат запуска в работе. Повтор доставки начинается со снимка, а не с отредактированной задачи. Id чата — детерминированный UUID v7 от id запуска и срока, поэтому повтор не создаёт второго чата | По умолчанию (ревью) |
| Зп21 | **Отказ при запуске** — строка «Не запустилась» с причиной (§4.1, `scheduledRunReasons`). Проекта нет (`sites.deleted_at`) или автор больше не владелец и не администратор — пауза `project_gone` или `member_gone`; это проверяется чтением, а не по `NOT_FOUND` от `createDialog`. Ошибка платформы (web, Vault, состояние каталога моделей) — повтор задания: до 8 попыток, от 30 с вдвое; после последней — «Не запустилась: сбой платформы». Запуск, который ждёт дольше 75 минут, такт закрывает так же | По умолчанию |

```prisma
  @@index([nextRunAt], where: enabled AND deleted_at IS NULL AND next_run_at IS NOT NULL)  // scheduled_tasks_due_idx
  @@index([createdById, workspaceId]), @@index([siteId])
}
/// Запуск запланированной задачи; поля задачи — снимком на миг захвата.
model ScheduledRun {             // @@map("scheduled_runs")
  id, scheduledTaskId (ScheduledTask, Cascade), dueAt Timestamptz,
  trigger VarChar(8) CHECK IN ('schedule','manual'), status VarChar(8) CHECK IN ('pending','started','refused','skipped'),
  reason VarChar(24)? CHECK IN (<scheduledRunReasons>), taskId? @unique (Task, Restrict),
  siteId? , name VarChar(80), instructions Text, effort VarChar(8), missedCount Int @default(0),
  attempts Int @default(0), createdAt, startedAt?
  @@unique([scheduledTaskId, dueAt, trigger])
  CHECK ((status = 'started') = (task_id IS NOT NULL)); CHECK ((status IN ('refused','skipped')) = (reason IS NOT NULL))
  @@index([scheduledTaskId, createdAt]), @@index([status, createdAt], where: status = 'pending')
}
/// Изменение задачи, которое агент зарезервировал за ход (как page_reservations).
model ScheduleReservation {      // @@map("schedule_reservations")
  id, workspaceId (Cascade), taskId (Task, Cascade), turnNo Int, kind CHECK IN ('create','update','delete'),
  scheduleId? (ScheduledTask, Cascade), payload Json, outcome VarChar(8)? CHECK IN ('done','refused','failed'),
  createdAt, closedAt?
  @@index([taskId, turnNo], where: outcome IS NULL)
}
// users.timezone VarChar(64)? — пояс браузера (Зп12)
// push_subscriptions.vapid_key VarChar(128)? — открытый ключ VAPID, под которым оформлена подписка (Зп41)
// chat_notifications: task_id → необязательный; новые scheduled_task_id (ScheduledTask, Cascade)? и scheduled_run_id (ScheduledRun, Cascade)?,
//   attempt Int?, turn_no Int?; CHECK (task_id IS NOT NULL OR scheduled_task_id IS NOT NULL); CHECK видов — notificationKinds
//   (DROP и ADD в BEGIN … COMMIT); уникальные индексы (task_id, kind, attempt, turn_no) WHERE task_id IS NOT NULL
//   и (scheduled_run_id, kind) WHERE scheduled_run_id IS NOT NULL
```

Функции — `packages/db/src/scheduled-tasks.ts` (экспорт из `index.ts`): создание, правка, пауза, включение, удаление, список и чтение задачи с запусками (Зп13, Зп16, Зп25 — все под `FOR UPDATE` строки и замком рабочего пространства, где считается предел); `claimDueSchedule(tx, scheduleId, now)` (повторная проверка подошедшего срока, Зп14, Зп20; `INSERT … ON CONFLICT DO NOTHING`; outbox `schedule.start` с ключом `schedule.start:<runId>`; сдвиг `next_run_at`; «Один раз» без сроков → `completed`); `stalePendingRuns`; `passUnattended(db, taskId)` (Зп27); резервы агента — `reserveScheduleChange`, `pendingScheduleChanges`, `applyScheduleChange`, `refuseScheduleChanges`, `staleScheduleReservations`; права — общая `chatAuthorManages` (из `pages.ts`, экспортом). `pauseSiteSchedules(tx, siteId)` — для `site-delete.ts`.

### 4.3. Протокол `core` → web

- `core`, задание `schedule.start`: `POST SCHEDULE_INTAKE_URL` с телом `{"runId": "…"}` и заголовком `x-raditi-schedule-secret`, предел 60 с. 200 с телом `scheduleIntakeResponseSchema` — готово; 400 и 413 — окончательно («сбой платформы»); 401, 404, 5xx и обрыв — повтор BullMQ (8 попыток, от 30 с вдвое), после последней — «сбой платформы». Исход `refused` — `ScheduleNotify` (Зп22, Зп38, Зп39).
- web: `apps/web/src/app/api/webhooks/scheduled-runs/route.ts` → `apps/web/src/server/schedule-intake.ts` — как `telegram-intake.ts`: без `SCHEDULE_INTAKE_SECRET` — 404; секрет — сравнение за постоянное время (sha256); тело не больше 1 КиБ, zod; затем `startScheduledRun(db, chatServices(), { runId, now })` из `packages/trpc/src/services/schedule/runs.ts`. Неизвестный запуск — 200 `skipped/paused`.
- `startScheduledRun` без долгой транзакции: (а) запуск не `pending` — вернуть записанный исход; (б) чат с id `deterministicUuidV7('schedule', runId, dueAt)` уже есть (удалённый тоже) — записать `started` с ним; (в) запуск опоздал — есть более поздний запуск задачи или прошло больше 6 часов — `skipped/missed`; задача удалена или выключена — `skipped/paused`; (г) прочитать `sites.deleted_at` снимка и роль создателя — пауза `project_gone`/`member_gone`; обязательные согласия создателя (`loadLatestConsents`, `missingRequiredConsents`) — `refused/consent`; (д) `createDialog(db, chat, { userId, siteId, taskId, text: instructions, effort, now, title: name, preview: 'on_demand' })` из снимка; (е) исход — короткой транзакцией `WHERE status = 'pending'`. Отказ `createDialog`: `BILLING_NOT_ENOUGH_CREDITS` → `no_credits`, `BILLING_TASK_NEEDS_SUBSCRIPTION` → `needs_tariff`, `BILLING_CREDITS_HELD` → `credits_held`, `BILLING_WINDOW_LIMIT_REACHED` → `weekly_limit`, `BILLING_DAILY_LIMIT_REACHED` → `daily_limit`, `TASK_NOT_ACCEPTED` по `details.reason`: `site_not_active` и `not_synthetic` → `project_unavailable`, `class_unavailable`, `browser_unavailable`, `browser_insecure` → `platform`; `BILLING_CREDIT_RATE_MISSING` → `platform`; `TASK_TEXT_*` → `text_refused`; прочая `DomainError` 4xx → `platform` (200, без повтора); `WORKSPACE_KEY_UNAVAILABLE`, 503 и не `DomainError` — ответ 503, повтор `core`.
- `deterministicUuidV7(namespace, salt, at)` — общий помощник trpc из `updateUuid` Telegram (sha256, биты версии и варианта); Telegram переходит на него.
- «Запустить сейчас» (`schedule.runNow`) — строка `manual` под замком задачи (Зп20, Зп24), затем та же `startScheduledRun`; `DomainError` — исход `refused` с причиной и ошибка в кабинет, без уведомления; 503 — строка удаляется, `WORKSPACE_KEY_UNAVAILABLE`.
