# Мастер подключения сайта: первоначальный импорт (M4, P11)

Составлен 17.10.2026. Срез делает рабочим путь «мастер создания проекта → outbox → фоновое скачивание файлов по SFTP или FTP → приватный репозиторий Gitea → первый коммит и тег `v0.0.0`». Основа лежала в дереве с 04–16.10.2026 без исполнителя: доменные контракты `packages/domain/src/site-connection/*`, миграция `20261004200100_site_connection` (таблицы `site_code_sources`, `site_databases`, `site_provisioning_stages`, `site_database_schemas`), очереди `site-import` и `site-provisioning`, `enqueueSiteProvisioningStage`, порт `SiteRepositoryProvisioner` с адаптером Gitea, политика Vault `core-site-import`, тестовые сертификаты пакета `@repo/site-connections`. Ни адаптеров SFTP, FTP и баз, ни процедур мастера, ни воркера, ни публикации первого коммита не было; `project.create` создавал только строку `sites`.

## Решения владельца (17.10.2026)

Действуют поверх прежних решений spec:

1. Первоначальный доступ к файлам — SSH или FTP. SSH — это SFTP поверх SSH: вид источника `sftp`, вид доступа `ssh`. Выполнения команд оболочки нет.
2. Подключение базы данных необязательно; поддерживаются PostgreSQL и MySQL.
3. В первоначальный снимок входят ядро WordPress и медиа.
4. Начальный тег — `v0.0.0`.
5. Секреты подключения — в Vault (OpenBao).
6. Вопрос «плагин или SSH/FTP» первоначальный импорт не блокирует; платформы — по действующему реестру (`connectableStacks`, сейчас WordPress).

## Что делаем

**Мастер.** «Добавить проект» на `/projects` ведёт на отдельную страницу `/projects/new`; встроенная форма в списке убирается. Степпер из трёх шагов:

1. «Основные данные» — название и адрес сайта, «Далее». Серверная проверка без записи (`siteConnection.checkBasics`): нормализация адреса, правило публичного адреса в production, дубль, технический потолок, лимиты тарифов, не больше трёх подключений в работе. Платформа — единственная подключаемая; при нескольких появится выбор.
2. «Доступ к файлам» — вкладки «SSH» и «FTP». SSH: сервер, порт (22), пользователь, вход по паролю или ключу (с необязательной парольной фразой), папка сайта. FTP: сервер, порт (21), пользователь, пароль, папка, защита соединения (по умолчанию FTPS с проверкой сертификата; без проверки и без шифрования — только явным выбором, автоматических переходов нет). «Далее» — настоящая проверка на сервере (`siteConnection.checkSource`): DNS и допустимость адресов, соединение и вход, папка, список файлов и корень WordPress, ограниченное чтение одного файла. На сервер ничего не пишется.
3. «База данных» — «Без базы данных» (по умолчанию), «PostgreSQL», «MySQL»; поля — только у выбранной. Проверка — `SELECT 1` и число таблиц выбранной базы по каталогу, в транзакции только на чтение, строки таблиц не читаются. Финальная кнопка — «Добавить проект».

**Ключ сервера SSH.** Первая проверка без ключа не входит на сервер: она узнаёт ключ сервера и отвечает `host_key_unknown` с отпечатком (`ssh-ed25519 SHA256:…`). Клиент сверяет отпечаток и подтверждает; следующие проверки и создание идут с этим ключом, и другой ключ даёт `host_key_changed` с новым отпечатком — принять его можно только отдельной явной кнопкой. Подтверждённый ключ закрепляется в секрете и в строке `site_code_sources.host_key`; воркер соединяется только с ним.

**Создание** (`project.create`) — единственный путь создания проекта: без доступа к файлам проект не создаётся. Шаги:

1. Идентификатор сайта выводится из пользователя и ключа запроса мастера (`requestKey`, UUID на одно открытие мастера): UUID версии 8 от SHA-256. Повтор после потери ответа находит тот же сайт и возвращает его без новых проверок и записей.
2. Захват `site_creation_claims` на 120 секунд (`createClaimMs`): второй такой же запрос, пока идёт первый, получает отказ «уже добавляем», а не пишет в Vault параллельно.
3. Повторные проверки файлов (с обязательным ключом SSH) и базы — параллельно, не дольше 25 секунд: успешный шаг мастера бессрочным доказательством не считается.
4. Запись секретов в Vault с CAS — до транзакции, вне её. Путь `kv/sites/<siteId>/ssh|ftp|db`, версия — из ответа Vault.
5. Одна транзакция PostgreSQL (READ COMMITTED, замок строки пользователя): захват ещё наш, дубль, потолок, лимиты тарифов, `ensurePersonalWorkspaceWithGift`, `sites` (`onboarding`), `credential_refs` с версиями, `site_code_sources`, `site_databases` (только если база выбрана), `site_provisioning_stages` (`code_import`, `queued`), событие outbox через `enqueueSiteProvisioningStage`, запись `audit_log`.

Если транзакция не прошла, секреты остаются в Vault без ссылок; роль пишет `site_connection_orphan site=<id>` в лог, следующий повтор с тем же ключом перезаписывает их новой версией. Задачи (`tasks`) импорт не создаёт и кредитов не списывает. Этап `database_schema` в этом срезе не ставится.

**Импорт** — роль `core`, очередь `site-import`, задание `site.provision` с `{ siteId, stage }`. Истина — строка этапа:

- захват `queued → running` с `lease_epoch + 1`, не больше одного импорта на рабочее пространство и двух на процесс; пульс каждые 15 секунд, потеря аренды останавливает работу;
- сборщик раз в минуту: `running` без пульса 120 секунд возвращается в `queued` (`enqueues + 1`, новое событие outbox) или после пяти возвратов за попытку завершается `interrupted`; `queued` дольше 5 минут получает пробуждение прямо в BullMQ;
- при остановке `core` идущий импорт отпускается в `queued` с задержкой 45 секунд;
- кратковременные сбои (`unreachable`, `transfer_failed`, недоступная Gitea) возвращают этап в очередь тем же счётчиком `enqueues`; остальные отказы завершают этап `failed` с кодом из `provisioningErrorCodes`; «Повторить» — следующая попытка (`attempt + 1`), не чаще шести раз в час вместе с заменой доступа.

Шаги импорта: доступ из Vault (ссылка, путь, версия, схема, совпадение со строкой), разрешение адреса по тому же правилу, репозиторий `sites/site-<siteId>` (`SiteRepositoryProvisioner`, приватный, `main`, пустой), сверка с тем, что уже опубликовано, скачивание дерева по правилам импорта адаптера стека, проверка секретов (точные значения доступа и `wp-config.php`, gitleaks), первый коммит без родителя, публикация `main` и тега `v0.0.0` без `--force`, сверка удалённых ссылок, фиксация результата в `site_initial_versions` и `succeeded`.

**Восстановление публикации.** Коммит, который будет опубликован, записывается в `site_initial_versions` (с `lease_epoch` держателя) до push. Повтор сверяется с удалённым `main` и тегом: `main` нет — коммит строится заново (план до публикации можно заменить); `main` равен записанному коммиту — скачивания нет, доводится тег и фиксация; `main` или тег указывают на другое — безопасная ошибка `repository_mismatch`, без force push и перетегирования. Второго репозитория, второго начального коммита и другой версии `v0.0.0` повтор не создаёт.

**Экран «Настраиваем сайт».** После создания мастер ведёт на страницу проекта. Пока `code_import` не `succeeded`, страница показывает только экран настройки и ссылку «Проекты»; рейка разделов скрыта, прямые адреса разделов перенаправляются на сервере (после проверки доступа: чужой сайт — «не найдено»). Состояние — с сервера, опрос раз в 3 секунды: «Ожидаем начала настройки», «Копируем файлы сайта», «Сохраняем первоначальную версию» или причина ошибки с «Повторить» и «Изменить доступ». Индикатор без процентов, `prefers-reduced-motion` учитывается, смена состояния объявляется в живой области. После успеха — «Обзор» с карточкой «Первоначальная версия сайта сохранена», тегом `v0.0.0` и временем импорта. В списке проектов — состояние настройки. Сайты без строки этапа (созданные до среза) живут как раньше.

## Как это устроено

- **Мастер** — `apps/web/src/components/projects/wizard/`. Ключ запроса (`requestKey`) создаётся один раз на открытие мастера; пароли и ключи живут только в состоянии React и в теле POST, мутации с ними — с `gcTime: 0` и сбрасываются после ответа. Пройденная проверка шага действует, пока поля шага не менялись; смена сервера или порта сбрасывает подтверждённый ключ SSH. Отказ проверки файлов при создании возвращает на шаг 2, отказ базы — оставляет на шаге 3, отказы адреса и платформы — на шаге 1; `PROJECT_CREATION_IN_PROGRESS` мастер переспрашивает с тем же ключом, `PROJECT_REQUEST_CONFLICT` предлагает список проектов или «Начать заново» с новым ключом.
- **Проверки** — `packages/site-connections`. Каждое соединение идёт на один адрес, закреплённый `resolvePinnedAddress`; TLS сверяется с именем (`tlsIdentity`). SFTP: отпечаток `<тип> SHA256:<base64>` из `hostVerifier` до входа; ключ с числом раундов bcrypt больше 64 отклоняется до разбора. FTP: явный FTPS, кодировка `latin1` для сырых имён (UTF-8, иначе windows-1251), данные — пассивно и только на закреплённый адрес, сеанс TLS данных продолжает сеанс управления, не больше двух управляющих соединений на сеанс, замена сломанного — после того, как сервер его отпустил. Базы: свой сокет с подсчётом байт до 256 КиБ, `SELECT 1` и число таблиц по каталогу в транзакции только на чтение; MySQL без шифрования входит через RSA-ключ сервера (`caching_sha2_password`), без пароля открытым текстом.
- **Создание** — `packages/trpc/src/routers/project.ts`, `services/site-basics.ts`, `services/site-access.ts`, `services/site-request-id.ts`, `services/site-connection-gate.ts`.
- **Импорт** — `apps/orchestrator/src/site-provisioning/`: `stage-store.ts` (захват под замком рабочего пространства, аренда, пульс, ограждение каждой записи, отказы и возвраты), `site-import.runner.ts` (пульс с пределом, остановка), `tree-walk.ts`, `exact-values.ts`, `import-scan.ts` (gitleaks с отчётом JSON по пронумерованным копиям), `initial-version.ts` (git), `site-import.ts` (шаги и восстановление), `site-import.sweeper.ts`, `wake.ts`. Метрика `raditi_site_imports_total{outcome}` без id.
- **Экран настройки** — `apps/web/src/components/site/site-setup.tsx`, `replace-access.tsx`, `setup-text.ts`; закрытие разделов — `site-nav.ts` (`inSiteSetup`) и `lib/site.ts` (`loadSiteSection`, после проверки «не найдено»).

- **Восстановление:** `kill -9` роли `core` во время скачивания — этап вернулся через сборщик через 129–130 секунд и завершился; SIGTERM — этап отпущен в очередь с задержкой 45 секунд и доведён новым процессом; хостинг остановлен — этап вернулся в очередь, а не упал; тег удалён после публикации `main` — «Повторить» довёл тег на тот же коммит без нового входа на хостинг; тег на чужом коммите — `repository_mismatch`, тег не тронут; пароль на хостинге сменился — «Изменить доступ» записал версию 2 секрета, `key_version` совпал с Vault, импорт прошёл.
- **Снаружи по каждому сайту:** строки этапа (попытка, число постановок, сводка — по манифесту фикстуры), `site_initial_versions`, одна строка `git_repositories`, канонические пути и версии `credential_refs`, опубликованные события outbox с payload `{siteId, stage}`, запись `site.create`; репозиторий приватный, один коммит без родителя от `Raditi Bot`, только `main` и лёгкий `v0.0.0`, дерево по манифесту до байта (ядро и медиа есть; `wp-config.php`, `.git`, `.github`, кэш, журналы, дамп, вложенная установка, ссылка и файлы с секретами — нет).
- **Секреты и запись:** ни одного секрета стенда в дампе базы платформы, в Redis, в журналах `core` и `next dev`, в объектах git; в журналах MySQL и PostgreSQL нет ни чтения строк, ни записи; хостинги не изменились до байта; в OpenBao — доступы ровно тех сайтов, на которые ссылается `credential_refs`; захватов создания не осталось.

## Ревью

Состязательное ревью по шести направлениям (секреты и безопасность, конкурентность воркера, путь создания, интерфейс, адаптеры, сверка с постановкой) подтвердило 30 замечаний из 33; все исправлены, у каждого исправления — тест, который без него падает. Главное:

- ssh2 синхронно выполнял `bcrypt_pbkdf` с числом раундов из присланного ключа: один запрос мог на часы остановить процесс web — теперь ключ с числом раундов больше 64 отклоняется до разбора;
- FTP-сервер, принявший `AUTH TLS` и замолчавший, держал импорт до конца часового предела — теперь каждый шаг входа ограничен сигналом и сроком;
- push `main`, переживший свой прогон, навсегда уводил сайт в `repository_mismatch` — новый прогон принимает прежний записанный коммит;
- пароль базы не входил в точную проверку секретов; импорт читал последнюю версию секрета, а не названную ссылкой; «Изменить доступ» не сверял ключ SSH с закреплённым;
- вложения форм, файлы покупателей, аватары и вложения комментариев внутри `uploads` попадали в репозиторий;
- проверка на соответствие spec и правилам (агент `spec-reviewer`) добавила: папки файлов посетителей у сайтов мультисайта (`uploads/sites/<N>/…`, `blogs.dir/<N>/files/…`) и счета WooCommerce (`wpo_wcpdf/`) теперь исключены; транспорт больше не сравнивает вид источника с литералом — «предлагается ли вид» отвечает реестр сервисов (`offersSource`), сверка закреплённого ключа идёт по строке источника и `endpoint` адаптера (правило 8); `connect-local.mjs` отказывает сайту мастера, пока его импорт не сохранил первую версию (`SITE_SETUP`); тексты о пределах связаны тестом с константами;
- мелкое: пульс мог зависнуть, короткий сбой базы завершал этап окончательно, имена, которые HFS читает как `.git`, роняли импорт на Linux, медленный длинный список файлов считался застоем, «Изменить доступ» предлагался при исчерпанных попытках, тексты двух отказов говорили неправду, фокус и устаревшие уведомления на экране настройки.

## Отступления от постановки

- **Ключ SSH.** Контракт допускал вход при первой проверке без ключа; сделано строже: первая проверка не входит на сервер и только показывает отпечаток (`host_key_unknown`), пароль уходит после подтверждения.
- **Защита FTP и базы.** Три режима — с проверкой сертификата (по умолчанию), без проверки и без шифрования — доступны явным выбором с предупреждением; автоматических переходов нет.
- **Медиа.** По решению владельца медиатека входит в снимок; папки, где плагины держат присланное посетителями, исключены по правилу 1 (§11). Получает ли песочница хода медиа, решается до P12 (spec §20).
- **Создание проекта для тестов.** Прежний `project.create` без доступов удалён целиком; тесты пакетов создают сайт той же процедурой с фейками, стенды и браузерные проверки — настоящим мастером.
- **Тест вебхука ЮKassa.** Под полной нагрузкой `pnpm test` первый тест файла не укладывался в 5 секунд из-за холодного импорта маршрута; маршрут срез не менял, импорт прогревается один раз перед тестами файла.

## Что не доказано и что остаётся

- **Узкое окно восстановления.** Если прогон B умер между своей записью плана и отказанным push, а в это окно приземлился push предыдущего прогона A, следующий прогон не знает коммит A и отвечает `repository_mismatch`; закрыть его можно историей записанных коммитов (новая таблица).
- **Хостинги.** Проверено на OpenSSH 10 и vsftpd 3.0.5; ProFTPD, Pure-FTPd, IIS, IPv6, ключи PuTTY и настоящий DNS не проверялись. OpenSSH 9.8 и новее (`PerSourcePenalties`) штрафует подключения без входа — частые проверки ключа с адреса платформы хостинг может задержать; в стенде штраф выключен. Хостинг с пределом в два соединения на пользователя — замена сломанного соединения ждёт, пока сервер отпустит прежнее; на настоящем хостинге не проверено.
- **Сертификат, которому платформа не доверяет** (`certificate_untrusted`), в стенде не воспроизводится: у стенда один CA; покрыто тестами адаптеров.
- **Пределы проверок мастера** — в памяти процесса web; при нескольких репликах — на каждую.
- **Трассы браузерных проверок биллинга.** `playwright.billing.config.ts` хранит трассу упавшего теста, а сценарии теперь вводят пароль тестового SFTP-сервера; пароль синтетический и новый на каждый прогон, трассы остаются в `apps/e2e/test-results`. У стенда импорта трассы выключены.
- **CI.** Workflow для `pnpm verify:site-import` не написан; `billing.yml` получил образ OpenBao и фильтр путей Vault, на GitHub не исполнялся.
- **Не входит в срез:** этап `database_schema`, вход WordPress, перевод в `active`, переменные выкладки, AGENTS.md, эталон, полный бэкап, AppRole web в production.

## Вопросы владельцу

Записаны в spec §20, блок «Первоначальный импорт сайта»; у этих трёх нет значения по умолчанию, которое не задевает другое решение или правило:

1. **Медиа в песочнице хода.** Медиатека теперь в репозитории, а база хода — всё дерево `main`. По умолчанию предлагаю до P12 отфильтровать базу хода по `snapshotExcludes` (медиатека в песочницу не идёт), а `v0.0.0` оставить полной точкой возврата.
2. **Политика `core-site-import`** открывает доступы всех сайтов общей AppRole `core`, сужение — в коде. Оставить так до production или вынести импорт в отдельную роль.
3. **AppRole web и П9.** Решение П9 даёт сервисам один набор переменных, а с парой AppRole `core` web получил бы и чтение доступов всех сайтов. По умолчанию предлагаю в production отдельную AppRole web только с `sites-writer` — вопреки П9 для этой пары переменных (M10).
