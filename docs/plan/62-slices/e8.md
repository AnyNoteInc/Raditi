**Общее для всех срезов.**
- Срез — один коммит, Conventional Commits на английском, только свои пути. После него `pnpm gates` зелёный, WordPress работает как раньше, кроме изменений, названных в «Договоре».
- Правило 8: ни одного сравнения имени стека вне `packages/site-adapters`.
- Правки `cloud-browser.ts` и `worker-session.ts` (срезы Э8.7–Э8.15) ведёт один исполнитель, по очереди. Эти два файла трогает почти каждый срез платформы.
- Docker-стенды — не рядом со стендами других сессий (§5.3). `verify:browser-task` — только Docker Desktop.
- Настоящая модель не вызывается. На настоящие CMS стенд ходит только локально, из архивов по sha256 (`fetch-cms.mjs`, Э3.8). Битрикс не запускается.
- Журнал запросов пишется только с настоящей установки (Т67). Списки экранов и полей в этом файле не сочиняются: у срезов стеков здесь есть порядок съёмки и что считать готовым, а строки списка рождаются из журнала.
- Срезы, запертые вопросом владельца, не пишутся до ответа. Они отмечены словом **Заперт**.

  `readPhpRequest` отвечает `null`:
  - путь не с одного `/`, не разбирается, `segmentsOf` дал `null`;
  - метод не GET, HEAD, OPTIONS и `postData === null`: тело с файлом сюда не попадает (Т54);
  - тело есть, а `contentType` `null` или не один из `application/x-www-form-urlencoded`, `multipart/form-data`, `application/json`;
  - multipart без `boundary`, с преамбулой перед первой границей, с именем без кавычек, с частью без имени (A17);
  - multipart, где в части `name` назван дважды или строк `Content-Disposition` больше одной: PHP берёт последнее `name`, а разбор по образцу взял бы первое (по умолчанию);
  - multipart с частью `filename=`, без исключений. Коннектор MODX вливает `$_FILES` в свойства процессора под именем части (`modConnectorResponse.php:146-147`), поэтому часть `name="tv7"; filename="@EVAL …"` пишет поле, которого в `fields` нет. Загрузку ведёт только `uploadRequest` (Э8.15, по умолчанию);
  - JSON не объект;
  - одно имя с разными значениями в адресе и в теле: порядок `$_REQUEST` зависит от хостинга (Т52);
  - одно имя без `[]`, повторённое с разными значениями внутри адреса или внутри тела: PHP берёт последнее, а чтение могло бы взять первое (`route=catalog/information&route=sale/order`, `id=5&id=6`, `source=1&source=2`; по умолчанию);
  - два имени, равные без учёта регистра, с разным написанием;
  - байт `\0` в имени или в значении поля: PHP `trim` его снимает, а `String.trim` нет, поэтому `\0@SELECT …` прошло бы проверку `@`.

  Настоящая форма со скрытым полем и флажком на одном имени (`x=0&x=1`) покажется в журнале. Тогда исключение получает только это поле, строкой договора стека с причиной, и читается последнее значение, как у PHP (по умолчанию).

  Имя как у PHP: `%5B` и `[` равны; неоткрытая `[` даёт `_`; пробел и точка до первой `[` дают `_`, внутри скобок не трогаются. `valuesOf` отдаёт все значения имени из обоих источников: они все равны, иначе чтение уже ответило `null`, поэтому `screenOf` и `objectId` значения не выбирают.

  Что приходит в `postData` на теле с файлом, снимает журнал настоящей установки. Playwright склеивает только текстовые куски (`postDataEntries`), поэтому рамка multipart с `filename=` может прийти и без содержимого файла. Закрыты оба вида: `postData: null` пунктом о методе, рамка пунктом о `filename=`. Если журнал покажет, что страничная загрузка нужна, `PhpRead` получает `files: string[]`, а `sentOf` включает эти имена: так выходит `unknown_field`.

  Запрещено: менять `readLooseRequest` и таблицы WordPress; вызывать `readPhpRequest` из кода WordPress до Э8.23.

  ```ts
    read: BrowserFieldRead | null
    ruleOf(field: string): FieldRule | null

    fixedValues(field: string, current: Readonly<Record<string, string>>): readonly string[]

    sameRefusal(field: string): BrowserWriteRefusal

    resetWhenAbsent(field: string): boolean
    /** Переход состояния. `state` одного объекта без потомков: agent — опубликовано или черновик. */
    stateChange(field: string, from: string | undefined, to: string, by: BrowserController):
      BrowserWriteRefusal | null
    /** Новые исполняемые значения в `text` и `markup`: стек сравнивает до и после. `after` — все значения поля из `sent`. */
    executable(field: string, before: string | undefined, after: readonly string[],
      current: Readonly<Record<string, string>>): BrowserWriteRefusal | null
    /** Формат цены стека. null — верный. */
    priceFormat(value: string): 'money_format' | null
    /** Торговые поля открыты агенту? До ответа на вопрос 2 — `false`. */
    agentWritesPrice: boolean
  }
  export function fieldGuard(spec: FieldGuardSpec): FieldGuard
  ```

  `violation(current, sent, by)`, по порядку, первый отказ выигрывает:
  1. Поле `sent` без правила — `unknown_field`.
  2. `same`: значения поля есть в `current` и значения `sent` поэлементно равны им, иначе `sameRefusal`. Поля нет в `current` — `current_unreadable`: сравнивать не с чем. `fixed`: значение обязано входить в `fixedValues(field, current)`, иначе `sameRefusal`.
  3. Поле с `resetWhenAbsent`, в `current` не пустое, а в `sent` его нет — `sameRefusal` (по умолчанию). Такое поле агент снимает обычным флажком на открытой форме, подделывать запрос не нужно.
  4. `state`: `stateChange`.
  5. `price`: сначала `priceFormat` для всех, в том числе у клиента (правило 9). Затем при `agent` и `!agentWritesPrice`: значение не равно текущему — `trade_field`.
  6. `text`: `<?` вне текущего значения — `code_in_content`. `markup`: то же и `executable`. У агента в обоих правилах новые вне текущего значения `<script`, `<iframe`, `<object`, `<embed`, `<form`, `<meta`, `<base`, `<link`, `<style`, атрибуты `on*=`, `srcdoc=`, `formaction=`, схемы `javascript:` и `data:` в `href` и `src` — `code_in_content`; у клиента за управлением это разрешено (по умолчанию). Перед сравнением значение проходит нормализацию: сущности HTML декодируются (`&#106;avascript:`), управляющие символы и пробелы внутри схемы убираются (`java&#x09;script:`). Иначе страница с указанием для модели приводит к скрипту или перенаправлению посетителей работающего магазина, и держит это одна инструкция (Т70).

  Значения сравниваются строкой, после обрезки пробелов с концов. Многозначное поле: поэлементно, порядок значим; `current` хранит его значения через `\n` (`currentValues(current, field)`), поэтому чтение обязано отдать отмеченные флажки и пустую строку у неотмеченного, а ключ поля `resetWhenAbsent` есть в чтении всегда. Цены только строкой, без `Number` (правило 9).

  Новый объект (по умолчанию). Правило «поле журнала без строки — `same`» и `violation` сходятся на одном: текущего значения у нового объекта нет, поэтому `current` даёт доверенное чтение формы добавления, `new_object.guard.read`. `same` сверяется со значением по умолчанию этой формы (`jform[access]`, `jform[language]`, `information_store[]`). Поля выбора значениями сайта (`jform[catid]`, `jform[parent_id]`) в спеке не перечислить: они идут правилом `fixed`, варианты чтение кладёт в `<поле>#options`. **Э8.11. Вход при двух условиях.**
- *Цель.* Т52, A07, З6: сохранённый вход вводится только при адресе внутри панели и поле стека. Закрывает обе поломки запуска: `signIn` у Joomla и MODX отвечал `refused` при удачном входе, страница уходила на `about:blank` (`gap-no-cms-ever-booted`, п. 1).
- *Файлы.* `packages/browser-providers/src/cloud/cloud-browser.ts:1302-1393`, `cloud-browser.integration.test.ts`, `packages/domain/src/browser/ports.ts:176-183` (комментарий), `packages/site-adapters/src/wordpress-browser-task.ts:520-525`, `CLAUDE.md` (правило 2), `docs/spec.md` §11.
- *Договор.*

  ```ts
  /** Адрес внутри панели, источник сайта, ровно одно поле пароля, `action` формы — в панели. */
  async #signInFormShown(entry: PageEntry, form: BrowserSignInForm): Promise<boolean>
  ```

  `action` читается `page.locator(form.form).getAttribute('action')`: пусто — адрес страницы; иначе `new URL(action, page.url())`, источник сайта и `form.isSignInPage(путь с запросом)`. Сбой чтения — `false`.

  - `signIn`: вход `absent`, пока `#signInFormShown` ложно. Успех — `!(await #signInFormShown)`, а не адрес. `#forgetSignIn` работает только при показанной форме: на вошедшей странице он не уводит на `about:blank`.
  - `#signingIn` снимается после `#forgetSignIn`, а не перед ним: `siteOnly` держится до конца навигации формы (A07).
  - Когда `sent` не дождался навигации, форма осталась: `refused`, поля чистятся, потом снимается запрет.

  Адаптеры новых стеков: `isSignInPage` — путь внутри `adminPath ?? connection.adminPathDefault`. На переименованной панели без `adminPath` путь не совпал, вход вводит клиент. WordPress оставляет `isWordpressSignInPage`: его форма стоит на `/wp-login.php`, вне `/wp-admin/`, и условие «адрес внутри панели» у него и есть этот адрес (`wordpress-browser-task.ts:512`). На другом `adminPath` (Р21) вход вводит клиент.

  Правило 2 дописывается текстом §6: «Сохранённый вход `SITE_ADMIN_*` браузер задачи вводит только при двух условиях сразу: адрес внутри панели и поле стека на странице. На публичном адресе сайта он не вводится никогда.»

  Запрещено: вводить вход по одному условию; значение логина или пароля в ошибке; второй запрос к сайту ради проверки формы.
- *Тесты.* `cloud-browser.integration.test.ts`, падают до правки: (а) форма на том же адресе, что страница после входа, вход удался — `signed_in`, страница цела; (б) публичная страница с теми же селекторами пароля не получает — проверяется журналом запросов страницы; (в) `action` на другой путь — `absent`; (г) скрипт страницы уводит на другой сайт сразу после отправки — запрос оборван; (д) уже вошедшая страница — `absent`, ждать 10 с не приходится; (е) форма вернулась — `refused`, поля пусты. Существующие сценарии входа WordPress не меняются.
- *Стенды.* `pnpm gates`, `pnpm verify:browser-task` (сценарии входа), локальный Chromium.
- *Готово.* WordPress входит как вошёл. Синтетическая панель с формой на любом адресе входит и не теряет страницу.
- *Зависит.* Э8.2.
- *Параллельно.* С Э8.4–Э8.6. После Э8.9 по файлу.

**Э8.15. Загрузку ведёт платформа.**
- *Цель.* Т54, A12: тело с файлом приходит к политике как `postData: null` или рамкой с `filename=`, а нечитаемое тело закрыто всегда (Э8.4). Поэтому загрузку multipart шлёт сама платформа, с полями адаптера. Источник и корень агент не выбирает. Заменить файл, положить скрипт или страницу в корень медиа агент не может.
- *Файлы.* `packages/browser-providers/src/cloud/cloud-browser.ts:979-1023`, `cloud-browser.integration.test.ts`, `packages/domain/src/browser/ports.ts` (комментарий), `apps/browser/src/sessions/worker-session.ts:1122-1136`, `session-manager.test.ts`, `packages/site-adapters/src/php-hosting.ts` (`imageFileExtensions`, его берёт и Э12.2).
- *Договор.* `#upload`, при `policy.uploadRequest !== null`, для каждого файла по одному:

  ```text
  request = uploadRequest({ name: file.name }); null — BROWSER_UPLOAD_REFUSED
  existing: runFieldRead(request.existing); не прочиталось или имя уже есть — BROWSER_UPLOAD_REFUSED
  token: pattern ищется в HTML показанной страницы, значение проходит HEADER_VALUE, иначе BROWSER_UPLOAD_REFUSED
  context.request.post(#withValues(new URL(path, источник)), {
    multipart: { ...fields, [token.field]: значение, [fileField]: файл }, maxRedirects: 0, timeout })
  ответ ≤ 64 КиБ, accepted(status, body) — иначе BROWSER_UPLOAD_REFUSED
  ```

  `uploadRequest` отвечает `null` на имя с расширением вне `imageFileExtensions` и на `svg`: коннектор MODX по умолчанию принимает `html`, `htm`, `js`, `svg`, `zip` (`upload_files`), а файл `.js` или `.html` в корне медиа — код сайта мимо выпуска (по умолчанию). `existing` закрывает замену (по умолчанию): `move_uploaded_file` OpenCart молча пишет поверх файла с тем же именем, а отката у этого нет. `existing: null` допустим только при записи в файле стека, что журнал не показал чтения папки.

  Страница должна быть на источнике сайта и `panelScreen` её не `null`, иначе `BROWSER_UPLOAD_REFUSED`. `ref` и окно выбора файла не нужны: `web_upload` без `ref` работает и без ждущего окна. Загрузка не объект и в предел 20 не идёт. `#markWrote` остаётся.

  Запрещено: поля из аргументов агента; повтор загрузки; запрос к хосту вне источника сайта; `uploadRequest` у WordPress.
- *Тесты.* `cloud-browser.integration.test.ts`, падают до правки: синтетический приёмник получил поля адаптера и токен страницы; `success: false` — `BROWSER_UPLOAD_REFUSED`; токена нет на странице — отказ; публичная страница — отказ; `a.js` и `a.html` — отказ, запроса нет; имя, которое уже есть в папке, — отказ. Настоящий Chromium: страница шлёт multipart с файлом, запрос оборван политикой, в каком бы виде ни пришёл `postData`. Литерал `postData: null` этого не доказывает.
- *Стенды.* `pnpm gates`, `pnpm verify:browser-task`, локальный Chromium.
- *Готово.* Механизм есть. На MODX его решает журнал (Э8.19): не заработает — `Browser/File/Upload` закрыт агенту, картинку загружает клиент (Т54).
- *Зависит.* Э8.8, Э8.9, Э8.10, Э8.12.
- *Параллельно.* С Э8.4–Э8.6.

  ```ts
   * обрезка набором PHP (пробел, \t, \n, \r, \0, \x0B).
   */
  export function modxStoredValue(value: string | readonly string[], prefix: string | undefined): string
  /** Исполняемые теги строки, без `[[~id]]`. */
  export function modxTagsOf(text: string): ReadonlySet<string>
  /** Новых тегов нет: набор после входит в набор до. */
  export function modxNewTags(before: string | undefined, after: string): boolean
  /** Значение TV начинается с `@` после обрезки набором PHP. */
  export function modxBindingValue(value: string): boolean
  ```

  `executable` у `tv*`: `@` в новом или в текущем значении — `executable_value`. У всех текстовых полей: `modxNewTags` — `executable_value`. Страницу с уже стоящим `[[!AjaxForm]]` можно сохранить, новый вызов нельзя.

  Значение судится дважды (по умолчанию): как прислано и как его сохранит процессор (`modxStoredValue`). У TV типа `url` процессор убирает `http://` (`update.class.php:704-707`, `Update.php:741-744`), поэтому `tv7=http://@EVAL return 1;` не начинается с `@`, а в базу ложится `@EVAL return 1;`, и тем же путём проходит `[http://[!Snippet]]` мимо `modxTagsOf`. Тип TV в запросе не виден, поэтому так судится каждое `tv*`.

  Между запросом и процессором стоят ещё два преобразования (по умолчанию). `sanitizeRequest` (`modRequest.php:425-432`, `modrequest.class.php:371`) чистит `$_GET` шаблонами `sanitizePatterns`: `&#N;`, `[[…]]`, голые `[[` и `]]`, `<script…></script>`, а `array_merge($_GET, $_POST)` отдаёт уже чистое значение. `$_POST` чистится только при `allow_tags_in_post = 0`: контекст `mgr` держит 1, но настройку платформа не знает, поэтому чистка идёт у всех полей. Иначе `tv7=&#1;@EVAL return 1;`, `tv7=[[~5]]@EVAL…` и `tv7=]]@EVAL…` проходят сторож, а в базу ложится `@EVAL`. `Update.php:772` выбрасывает пустые элементы массива до склейки: `tv7[]=&tv7[]=@EVAL…` ложится как `@EVAL…`, поэтому массив судится целиком (`executable` получает все значения поля). Вторая линия: поле адреса у `Resource/*` — `unknown_write`.

  `FieldGuard.read`: шаг страницы менеджера, токен `pattern` из `MODx.siteId` в заголовок `modAuth`, затем `Resource/Get`. Значения TV — по журналу. Не читается — запись закрыта.

## Расхождения с проектом

Код сверен по `raditi-chats`, поведение CMS — по отчётам и `research/src`, ничего не запускалось. Р1–Р17 вошли в итоговый проект: §2.4 называет «Договор типов» этого файла рабочим договором, Р12 стоит в правиле 4 §6, Р14 в строке Э8 §5.1, Р15 в §5.5. Р18–Р21 появились при сверке с потоком мастера, в проекте их нет: это значения по умолчанию.

**Р1. `violation` получает `sent`, а `writeOf` его не отдаёт.** §2.4: `violation(current, sent, by)`, но `BrowserWrite` несёт только `ref` и `guard`. Вызывающий — `cloud-browser.ts` в `packages/browser-providers`: разбирать тело PHP-правилами он не может, адаптеры зависят только от домена, а этот код не должен знать стеков. Предложение: `sent` в значении `writeOf`.

**Р2. `ref` у `writeOf` не построить.** `BrowserCheckpointRef.editUrl` — абсолютный адрес (`checkpoint.ts:52-64`), а `SiteBrowserRequest.path` относителен, метод чистый и начала адреса не знает. Предложение: `BrowserWriteObject` с `editPath`, адрес собирает сессия. `new_object.type` — `BrowserCheckpointKind`, а не `string`: иначе он не дойдёт до ленты.

**Р3. `fields: Record<string, FieldRule>` не выражает `tv<id>`, а отказ `same` не назван.** Номера TV заранее неизвестны, поля `jform[attribs][…]` тоже. И из `same` не следует причина: `jform[rules]` — `permission_change`, `static_file` и `class_key` — `file_binding`. Предложение: `ruleOf(field)`, `sameRefusal(field)`. `FieldGuard.read` — `null` у нового объекта: читать нечего.

**Р4. `panelScreen` назвал экран, но нечем спросить, открыт ли он.** `verdict` принимает запрос, а не экран, `landing` отвечает только за панель. Предложение: `screenOpen(screen, by)`. Поле `panelScreen` может быть `null`: иначе WordPress читает HTML каждой страницы ради ответа, который не нужен.

**Р5. Токен нечем достать.** `{ fromStep }` кладёт в заголовок всё тело шага (`verification.ts:52-68`): это слепок `admin-ajax.php?action=rest-nonce`. У MODX токен внутри HTML. `tokenFrom: string` у `BrowserUploadRequest` не называет ни поля, ни способа, ответ загрузки никто не читает, имя поля файла не задано. Отчёт `browser-mcp` §10 п. 4 это предлагал, в §2.4 не дошло. Предложение: `{ fromStep, pattern }`, `token: { field, pattern } | null`, `fileField`, `accepted`.

**Р6. `action` формы сверять не с чем.** Т52 требует, но `BrowserSignInForm` не называет форму. Предложение: поле `form`.

**Р7. Что отвечать, когда чтение не прошло.** Т52: «не прочиталось — запись закрыта», а в `browserWriteRefusals` такого значения нет, и `unknown_write` сказал бы агенту неправду. Предложение: `current_unreadable`. Предел: действие агента живёт 10 с (`agentActionTimeoutMs`), чтение — до 4 шагов по 10 с. Предложение: `guardReadMs: 8_000` на всё чтение, действие ждёт судей после себя.

**Р8. Для кнопок OpenCart 3 нет поля в порту.** Т52 называет `aria-label` из `data-original-title`, §2.4 молчит, правило 8 запрещает решать это вне адаптера. Предложение: `nameAttribute`. Не скрипт инициализации, а проход перед снимком дерева: подсказка Bootstrap появляется позже загрузки.

**Р9. Строка `editor <путь>` пуста на единой точке входа.** `savedObjectOf` берёт `pathname`: у Joomla это `/administrator/index.php` на любой объект. Отчёт `browser-mcp` §10 п. 6 просил поле адаптера, проект его не записал. Предложение: `editHint(ref)`, у WordPress строка байт в байт.

**Р10. Счётчику Т69 негде жить, а `closedAs` обязан отвечать.** Т69 и Э13.2 говорят о счётчике закрытых экранов по имени компонента, §2.4 его не называет, новых таблиц для него нет. WordPress не классифицирует экраны, и `'unknown'` дал бы ему новый текст. Предложение: `closedAs` может быть `null`; `screenName(request)`; счётчик Prometheus с пределом 64 имени. Имя компонента не идентификатор человека, поэтому правило о метках не нарушено.

**Р11. Виды объектов не покрывают Т41.** §2.6 называет `page`, `product`, `category`, `resource`, а `mod_custom`, чанк MODX и баннер OpenCart тоже объекты задачи: без вида они не считаются в предел и не видны в ленте. Предложение: вид `block`, подпись «Блок». `resource` идёт в ленту как `page`.

**Р12. Правило 4 говорит о всех стеках, а WordPress считает по кнопке.** §6: «Предел 20 считается по запросам записи». У WordPress `writeOf` содержания не имеет: блочный редактор пишет через REST, и перевод счёта на запрос — отдельная работа и смена поведения. Отчёт `gap-live-store-rules` §4.2 тоже ставит её вторым шагом. Предложение: у WordPress `service`, новый текст правила: «У стека с разрешённым списком предел 20 считается по запросам записи; групповые действия и правка в строке агенту закрыты и в предел не входят…», остальное как в §6.

**Р13. Новый объект без адреса запирает задачу, а `objectField` из отчёта в проект не попал.** `#pendingCommit` снимается, только когда адрес назвал объект. OpenCart 3 после добавления шлёт 302 на список, номера нет нигде. Отчёт предлагал `objectField`, но у OpenCart 3 нет ни поля, ни адреса. Чтение списка не годится: у `catalog/information` нет ни фильтра, ни сортировки по номеру (чтение кода, проверить журналом). Предложение: `createdTitle(sent)`: первый редактор, открытый после такой записи, становится объектом удержания, а `#verifyAll` сверяет заголовок. У Joomla проще: кнопки, теряющие адрес, закрыты при `id=0`.

**Р14. WooCommerce первым — и вопрос 2 его запирает.** §5.1 ставит сторож на WooCommerce перед списками, Т55 объясняет почему, а §7 говорит: «До ответа: WooCommerce как сейчас», значения по умолчанию нет. Значит, при открытом вопросе первым сторож видит Joomla. Предложение: так и идти, при ответе раньше Э8.17 Э8.23 идёт первым. §5.1 считает вопросы 2 и 4 условием всего Э8, а держат они только четыре среза.

**Р15. Имя `<cms>-browser.test.ts` занято.** §5.5 называет так М0б, а Э3.4 и Э4 уже завели `joomla-browser.ts` и его тест для браузера предпросмотра. Предложение: `<cms>-panel.test.ts`, `<cms>-writes.test.ts`.

**Р16. Загрузка платформой нужна не только MODX.** Т54 пишет «у MODX», комментарий §2.4 тоже. Но `common/filemanager` OpenCart и `com_media` Joomla 3 шлют файл multipart через `FormData`, `postData` может быть `null`, а нечитаемое тело закрыто всегда. Предложение: поле общее, решает журнал стека.

**Р17. `requestDenied` не выводится из `panelScreen`.** §2.4: «у новых стеков выводятся из `verdict` и `panelScreen`». `requestDenied` — синхронный суд по запросу, HTML у него нет. Предложение: он выводится из `verdict`, панель судится отдельно после загрузки страницы (Э8.12).

**Р18. Строку «Закрыто для агента» проект велит заполнить рядом со списком и вычитать, а чем сверять, не говорит.** §2.3: `terms.closed`, «сверяется с файлом доказательств Т64». Т26 и `62-onboarding.md` §1, п. 4: ошибка в поле будет ложным обещанием на экране условий. В файле доказательств такой строки нет, З1–З16 её не называют, а глазами список из сотен экранов с фразой не сверить. Предложение: две линии. Код: `TermsProof` в тесте стека и `termsViolations` (Э8.16) на журнале настоящей установки, каждое слово строки опирается на обход. Вычитка: полнота строки, строка файла доказательств (Э11.6). Значения стоят с Э3.2, Э4.1 и Э5.1: нарушение 14 контракта Э2.3 не пропускает пустой `closed`, поэтому слова «рядом со списком» здесь значат сверку, а не первую запись. У WordPress журнала нет, его строку держат тесты закрытого списка `wordpress-browser-task.test.ts`.

**Р19. Строки панели написаны по рекомендации, а экраны за ними заперты.** §4 проекта: «при ответах на вопросы 2, 4 и 25 по рекомендации». `liveDetail` Joomla и MODX называет «текстовые блоки», OpenCart — «Описание и фото товаров», а до ответов эти экраны закрыты агенту (Т41, Т55). Э3.2, Э4.1 и Э5.1 ставят значения Т27 дословно: клиент их не читает до `on`, а `on` требует ответов (З14). Значит, отдельная редакция «до ответа» не нужна, но и молча оставить обещание нельзя: стек с ответом «да» и не сделанным срезом ушёл бы в `on` с ложной строкой. Предложение: кусок стоит в `TermsProof.awaits`, `termsViolations` отказывает при `on` и непустом `awaits`. При ответе «нет» строки правят запертые срезы по `62-onboarding.md` §7. `alwaysShop: 'open'` у OpenCart остаётся по той же причине.

**Р20. Закрытую панель шаг 2 видит не всегда, а у сессии нет ни статуса, ни страницы.** Т2: панель проверяется на шаге 2, «если адрес панели переименован, отказ придёт позже, из `readLayout`: для этого текста нет» (вопрос Он7). Э9.3: такие сайты «узнаются только на старте сессии», `recognitionVerdict` пишется в `session-manager.ts#site`. Но `#site` работает до браузера, страницы там нет, `cloud-browser.ts` в срезе не назван, а `open` (`cloud-browser.ts:380-383`) статус старта не хранит и ошибку глотает. Агент увидел бы страницу 401 и стал бы гадать. Предложение: `CloudBrowserSession.firstPage()` для статуса и HTML первой страницы, чистая `panelClosedBy` на шаг 2 и сессию, причина `panel_closed` (Э8.12). Сессия не закрывается: она стартует отдельным заданием (К11), и отказ на старте дошёл бы до агента общим `BROWSER_SESSION_UNAVAILABLE` без слов Т29. Статус страницы входа на настоящих CMS не проверен: поэтому он лежит в журнале.

**Р21. У WordPress поле «Адрес панели управления» есть, а политика его не читает.** `62-onboarding.md` §4 и `O-noaccess-foreign` показывают `/wp-admin/`, Э2.3 ставит `adminPathDefault: '/wp-admin/'`, подсказка обещает «Если панель открывается по другому адресу, укажите его.». Но `wordpressBrowserTaskPolicy` значения не читает. А условие Э8.11 «путь внутри `adminPath`» WordPress сломало бы: его форма стоит на `/wp-login.php`, вне `/wp-admin/`. Предложение: `startPathOf` берёт значение, отличное от `/wp-admin/`, закрытый список и `isWordpressSignInPage` не меняются. Сегодня `adminPath` ни у кого нет, поэтому WordPress ведёт себя как раньше.

**Р22. Загрузка не закрывала замену и чужие расширения.** Договор Э8.15 принимал любое имя файла, а `uploadRequest` не умел отказать. Круг 1 разбора показал: коннектор MODX по умолчанию берёт `html`, `js`, `svg`, `zip`, `move_uploaded_file` OpenCart пишет поверх файла, `com_media` заменяет файл полем `override`. Сделано: внутренний `null` у `uploadRequest`, поле `existing`, список `imageFileExtensions` без `svg`, все по умолчанию.
