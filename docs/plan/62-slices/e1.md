## Mac (arm64) и x64

- В `site-bases.json` стоит digest **индекса**, а не образа одной платформы. Одна строка таблицы даёт arm64 на Mac и amd64 в CI. Индекс проверяется при заполнении таблицы (Э1.1).
- ionCube — единственное, что различается по архитектуре в самом `Dockerfile`: два архива, две sha256, выбор по `TARGETARCH`. Установщик, MariaDB, Node и PECL выбирают архитектуру сами.
- На Mac собирается нативный arm64, CI — нативный amd64. QEMU нигде не нужен. Сборка под чужую архитектуру не идёт.
- Digest собранного образа у каждой машины и архитектуры свой, поэтому значения `PREVIEW_SITE_IMAGES` нет ни в `.env.example`, ни в репозитории. На Mac достаточно версий, которые нужны в работе: `pnpm verify:site-images --only 8.3`.
- Что доказывает каждая сторона. Mac и Colima: arm64 под `runc` и `runsc`. CI: amd64 под `runc`. **amd64 под `runsc` не доказывается нигде до M10.** Production — `linux/amd64` под `runsc`, поэтому это записанный остаток M10, а не закрытый гейт. Замер по одной архитектуре не переносится на другую: 8.5 и PECL на amd64 первым соберёт CI в Э1.3.

  Верх `Dockerfile` вместо строк 6–8. Все три `ARG` стоят до первого `FROM`, в комментариях нет слова `FROM ` с пробелом: так считает `site.test.mjs:64`.

  ```dockerfile
  # The base of the `site` target: the image of WordPress until docs/plan/62 moves it over;
  # `php-base` — the stage below, on the official image of one PHP version.
  ARG BASE=wordpress@sha256:8ae73d594a154e30b112e8d085afbc0895acf7651d8f53ef63aefb42e30822d5
  # The official image of one PHP version, by the digest of its index: amd64 and arm64 alike.
  # site-bases.json lists them; the default is PHP 8.3.
  ARG PHP_BASE=php@sha256:<digest строки 8.3>
  ARG TARGETARCH
  ```

  Новые стадии — между `browser` и `site`:

  ```dockerfile
  # The extension installer of the official PHP images, by version and sha256; a stage of its own,
  # so nothing of it stays in an image.
  FROM scratch AS php-extension-installer
  ADD --chmod=0755 --checksum=sha256:<sha256 файла> \
      https://github.com/mlocati/docker-php-extension-installer/releases/download/<версия>/install-php-extensions \
      /install-php-extensions

  # ionCube Loader 15.5.1 (18.09.2026). The address has no version: a new release of the vendor
  # fails the checksum and stops the build until the version and both sums change together.
  FROM scratch AS ioncube-archive-amd64
  ADD --checksum=sha256:739962bd012e77ee82bf01f77a9641f050e4be057f0a5d1a95fe59ce11fd62ba \
      https://downloads.ioncube.com/loader_downloads/ioncube_loaders_lin_x86-64.tar.gz /ioncube.tar.gz
  FROM scratch AS ioncube-archive-arm64
  ADD --checksum=sha256:b091974aa80a76bd798d71fd5209797d93749b0be13eaff978a3dbe0106b9e1f \
      https://downloads.ioncube.com/loader_downloads/ioncube_loaders_lin_aarch64.tar.gz /ioncube.tar.gz
  FROM ioncube-archive-${TARGETARCH} AS ioncube-archive

  # What every stack of a preview runs on (docs/plan/62, Т21). Nothing here knows a stack.
  # ionCube has no Loader for PHP 8.0 on any architecture. Its first ini name loads it before
  # OPcache, as its README asks. status is off: the entry forwarder comes from the loopback, and
  # Debian opens /server-status to `Require local`. PHP_PECL_PINS names the version of every PECL
  # extension: an empty cache and the monthly rebuild give the same imagick, redis and apcu.
  FROM ${PHP_BASE} AS php-base
  ARG PHP_EXTENSIONS_SKIP=
  ARG PHP_PECL_PINS="<строка pecl версии 8.3 из site-bases.json>"
  RUN --mount=type=bind,from=php-extension-installer,source=/install-php-extensions,target=/usr/local/bin/install-php-extensions \
      --mount=type=bind,from=ioncube-archive,source=/ioncube.tar.gz,target=/tmp/ioncube.tar.gz \
      set -eu; \
      . /etc/os-release; \
      php_version=$(php -r 'echo PHP_MAJOR_VERSION, ".", PHP_MINOR_VERSION;'); \
      names=; \
      for name in apcu bcmath bz2 calendar exif gd gettext gmp imagick intl ldap mcrypt memcached \
        mysqli opcache pdo_mysql redis shmop soap sockets sysvmsg sysvsem sysvshm xmlrpc xsl zip; do \
        pinned=$name; \
        for pin in $PHP_PECL_PINS; do case "$pin" in "$name"-*) pinned=$pin ;; esac; done; \
        case " $PHP_EXTENSIONS_SKIP " in *" $name "*) ;; *) names="$names $pinned" ;; esac; \
      done; \
      install-php-extensions $names; \
      install -d -m 0755 /usr/local/lib/raditi; \
      if [ "$php_version" != 8.0 ]; then \
        install -d -m 0755 /usr/local/lib/raditi/ioncube; \
        tar -xzf /tmp/ioncube.tar.gz -C /usr/local/lib/raditi/ioncube --strip-components=1 \
          --no-same-owner ioncube/LICENSE.txt "ioncube/ioncube_loader_lin_${php_version}.so"; \
        chmod -R a+rX /usr/local/lib/raditi/ioncube; \
        printf 'zend_extension=/usr/local/lib/raditi/ioncube/ioncube_loader_lin_%s.so\n' "$php_version" \
          > /usr/local/etc/php/conf.d/00-ioncube.ini; \
      fi; \
      case "$VERSION_CODENAME" in \
        trixie) heif='libheif-plugin-aomenc libheif-plugin-x265' ;; \
        *) heif= ;; \
      esac; \
      apt-get update; \
      DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends ghostscript $heif; \
      rm -rf /var/lib/apt/lists/* /var/cache/apt/*; \
      a2enmod rewrite expires remoteip headers; \
      a2dismod -f status
  COPY --chmod=0644 preview-php.ini /usr/local/etc/php/conf.d/50-raditi.ini
  COPY --chmod=0755 no-sendmail /usr/local/lib/raditi/no-sendmail
  ```

  Стадия `site` не меняется ни одной строкой: весь новый код стоит в `php-base`, поэтому `FROM ${BASE}` на прежнем значении остаётся рабочим путём отката. `install -d` идёт до `COPY`: иначе `COPY --chmod` дал бы папке режим файла (`Dockerfile:77`).

  Версия и sha256 установщика: последний выпуск `mlocati/docker-php-extension-installer` на день среза, файл скачивается один раз, сумма считается `shasum -a 256`.

  Архив ionCube берётся с адреса производителя без версии: новый выпуск роняет сборку до правки трёх строк. Этого не исправить без своего хранилища, а до M10 его нет: выбор — вопрос О1 (§7 проекта). До ответа остаётся адрес производителя, сбой громкий, цена названа в Р2.

  Адрес ionCube в отчёте сокращён многоточием: путь `loader_downloads` подтверждается тем, что `ADD --checksum` проходит с суммами отчёта. Если не проходит на обеих архитектурах, вышел новый Loader: взять новую версию, новые суммы, заменить комментарий, номер записать в PR. Имена внутри архива — из эскиза отчёта, который целиком не собирался; при расхождении `tar` откажет сам, имена сверяются `tar -tzf`.

  `infra/preview/no-sendmail`:

  ```sh
  #!/bin/sh
  # Nothing leaves a preview by mail(): the letter is read to its end and dropped. mail() answers
  # true, so a form behaves as on the site (docs/plan/62, Т21).
  cat >/dev/null
  exit 0
  ```

  Правило `without`. Девять имён обязательны на всех версиях и в `without` не попадают: `bcmath exif gd imagick intl mysqli zip pdo_mysql opcache`. Если другое имя из 26 не собирается на версии, оно вписывается в `without` этой строки, а причина, версия и строка ошибки идут в PR и в вопрос В5. Запрещено: подменять версию расширения, ставить другой пакет, менять основу, держать `without` у 8.3. Иначе сборка считается неудачной, и срез стоит.

  Запрещено: `packages.sury.org`; `install-php-extensions` или архив ionCube в итоговом образе; `latest` в адресе установщика; `ioncube_loader` в списке установщика; `amqp` и `memcache` (Т21: 27 имён без них); `RUN a2dismod` в стадии `site`; правка `init.sh`.

В локальном `.env` и в любом окружении, где образ уже указан, — одна строка `PREVIEW_SITE_IMAGES=8.3=<digest старого образа>`. Остальные семь версий откатывать не нужно: на старой основе их не было. Э1.1–Э1.4, `site-images.yml` и `verify:site-images` остаются: они WordPress не задевают.

  Запрещено в этом PR: правка `init.sh`, `preview-apache.conf`, `preview-wp-config.php`, рецепта, кроме комментария; `ready`; любое слово о Joomla, OpenCart, MODX и Битриксе. Запрещено удалять `ARG BASE` и прежний digest из комментария.
- *Тесты.* `site.test.mjs:63` ждёт `/^ARG BASE=php-base$/m`; до правки значение другое, тест падает. Новых тестов нет: срез меняет значение, проверенное Э1.2–Э1.4.

## Э1.6. `ready` у WordPress

**Э1.6. Мёртвый предпросмотр WordPress больше не считается готовым.**

- *Цель.* Рецепт WordPress объявляет `ready`, сгенерированный `wp-config.php` ставит заголовок. Закрывает Т33 в части WordPress и строку 3 таблицы §5.2 для него. Идёт после зелёной регрессии Э1.5, отдельным PR: откат образа и откат этой правки независимы.
- *Файлы.*
  - `infra/wordpress/preview-wp-config.php` — после строки 24.
  - `packages/site-adapters/src/wordpress-preview-files.ts` — пересборка `node packages/site-adapters/scripts/embed-wordpress-files.mjs`.
  - `packages/site-adapters/src/wordpress-preview.ts` — поле `ready` после `healthPath`.
  - `packages/site-adapters/src/wordpress-preview.test.ts`, `packages/site-adapters/src/wordpress-preview.integration.test.ts`.
  - `apps/core/src/previews/preview.docker.integration.test.ts`.
  - `docs/spec.md` — абзац «Готовность», который вводит Э0д.
- *Договор.*

  `preview-wp-config.php`, сразу после закрытия `$raditi_preview`:

  ```php
  // The mark of a page this configuration served: `ready.header` of the recipe (docs/plan/62, Т33).
  if (PHP_SAPI !== 'cli' && !headers_sent()) {
      header('X-Raditi-Preview: 1');
  }
  ```

  Рецепт:

  ```ts
  healthPath: '/',
  // A dead WordPress answers 5xx or fails `content.access` first; a text would only mark a live
  // site that quotes it as dead.
  ready: { header: 'x-raditi-preview', absent: [] },
  ```

  Логику `pageVerdict` и `previewBootOf` срез не меняет: они из Э0д. Что меняется у WordPress: главная с 5xx, с сообщением PHP (`… in <файл> on line <n>`) или без заголовка, если нет кандидата, — `unavailable`, `boot_failed`, текст «Предпросмотр не запустился: сайт не заработал в нашей копии. На настоящий сайт это не влияет.». Кандидат не прошёл — предпросмотр остаётся, `preview_smoke` даёт `failed`. Перенаправление на другой хост — `suspect`, `redirects_away`. Закрытая главная (401, 403, 404 с заголовком) и главная, которая дважды не ответила за 30 секунд, предпросмотра не отнимают: `suspect`. Слова «Fatal error:» в тексте записи ничего не значат.

  Предел, который срез не меняет: сайт без таблиц или без соединения с базой падает раньше, на `content.access` (`preview-builder.ts:751`, команда `wp eval`), и даёт `failed`, а не `boot_failed`. Правка меняет только то, что идёт после него.

  Запрещено: второе имя заголовка; проверка `Warning`; условие по стеку в `core`; `ready` без заголовка в `wp-config.php`.
- *Тесты.*
  - `wordpress-preview.test.ts`, `says how a live page differs from a dead one` — `recipe.ready` равно договору, `sources.previewWpConfigPhp` содержит `header('X-Raditi-Preview: 1');`. Падает до правки.
  - `wordpress-preview.integration.test.ts` — ответ главной содержит заголовок `x-raditi-preview: 1`. Падает, если строку убрать из `wp-config.php`.
  - `preview.docker.integration.test.ts`, новый `it('a base that answers 200 without the mark is boot_failed')` — настоящий WordPress, в дереве `index.php` равен `<?php exit(0);`; итог: `unavailable`, `boot_failed`. Это случай факта 4: 200 и мёртвый сайт. Падает до правки: сегодня такой предпросмотр готов.
  - Там же: на здоровом дереве запись предпросмотра получает `passport.boot = 'not_compared'`, отличий нет.
  - Там же: главная статического сайта с текстом `Fatal error: Allowed memory size` и заголовком — `ready`, не `boot_failed`.
  - Сверка вшитых файлов (`wordpress-preview.test.ts:46`) и `php -l` в `ci.yml` проходят без правок теста.
- *Стенды.* `pnpm gates`, `pnpm verify:db`, `pnpm verify:release`, Docker-наборы №4 и №5 таблицы Э1.5.
- *Готово.* Мёртвая главная WordPress даёт `boot_failed`, а не пустой кадр. `verify:release` как прежде.
- *Зависит.* Э1.5, Э0д.
- *Параллельно.* С Э2–Э5 и остальными срезами, кроме правок `wordpress-preview.ts`.
