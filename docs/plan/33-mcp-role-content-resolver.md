# P6: штатная роль `mcp` с контентом вне production — resolver из Vault, адаптер по стеку, AppRole

04.10.2026. Инкремент N5 плана следующих работ: правку контента выполняет запущенная роль (`ORCHESTRATOR_ROLES=mcp`), а не композиция verify-скрипта; доступ сайта роль читает из Vault под AppRole `mcp`. Всё локально: одноразовые PostgreSQL, S3, OpenBao 2.7.0 и WordPress, синтетика, без подписок и облака. Корневой `.env`, dev-инфраструктура и `~/.codex/auth.json` не использовались. В production контентный профиль по-прежнему запрещён кодом. P6 остаётся открытым.

До этого блока контент включался только аргументом `McpAppModule.forRoot(config, { storage, resolve })`: хранилище и шлюз сайта давал verify-скрипт, роль в стендах шла под root-токеном OpenBao, пароль приложения WordPress приходил ей по IPC. Запущенная роль (`node dist/main.js`) объявляла только `site_info`.

## Что сделано

**Порт адаптера** (`packages/domain/src/ports/site-adapter.ts`). Добавлены виды доступа сайта (`ssh`, `ftp`, `wp`, `browser`), единственный путь доступа `siteAccessPath(siteId, kind)` = `kv/sites/<siteId>/<вид>`, транспорт `SiteHttpTransport` (один запрос, без перенаправлений, пределы времени и размера задаёт адаптер) и `SiteContentAdapter`: стек, вид доступа, zod-схема секрета и фабрика `PublishedContentGateway`. Вход фабрики — идентификатор и origin сайта, разобранный секрет, транспорт, флаг loopback.

**WordPress** (`packages/site-adapters`). Транспорт шлюза стал инъецируемым; прежний глобальный `fetch` вынесен в `fetchSiteTransport` и остаётся значением по умолчанию. Схема секрета `kv/sites/<siteId>/wp`: `v` (`"1"`), `origin`, `username`, `applicationPassword` — только строки, лишние поля отклоняются. `origin` принимается в одном виде — как его даёт `new URL(адрес).origin`: кириллическое имя записано в punycode, порта по умолчанию и заглавных букв нет. В реестре — `getSiteContentAdapter(stack)`; стек без контента отвечает «не реализовано».

**Resolver** (`apps/orchestrator/src/mcp/site-content-resolver.ts`). Сайт берётся из допуска вызова, не из аргументов. Цепочка: адаптер по стеку → строка `credential_refs` вида, который назвал адаптер (ровно одна, рабочее пространство совпадает с задачей) → её путь равен каноническому → `kvRead` → версия секрета равна `key_version` строки → схема адаптера → `origin` секрета равен origin адреса сайта → фабрика. Любой отказ — одна ошибка `CONTENT_SITE_ACCESS_UNAVAILABLE` (503); причина — одно слово для оператора (`stack`, `reference`, `path`, `vault`, `secret`, `version`, `format`, `origin`, `adapter`), в лог роли оно попадает не чаще раза в минуту на причину, без сайта и без секрета. Агент видит прежние фиксированные коды: у записи — `CONTENT_PREPARATION_FAILED`, у чтения — `CONTENT_CALL_REJECTED`. Ссылка читается на каждом вызове, Vault — один раз на ссылку и версию; копия используется 60 секунд, кэш ограничен 256 сайтами. Сменился `key_version`, строка, путь или адрес сайта — прежний шлюз не используется. Изменение только в Vault (новая версия, удаление) роль замечает, когда копия истекла.

**Конфигурация** (`apps/orchestrator/src/config/config.ts`). Новая переменная `MCP_CONTENT_PROFILE`: `off` (по умолчанию) или `local`. При `local` роль читает из настроек S3 только подключение и `S3_BUCKET_ARTIFACTS` (`McpConfig.storage`); имена других бакетов и `S3_RUNNER_ENDPOINT` она не читает и не проверяет. В production любое значение, кроме `off`, — ошибка конфигурации. Переменная добавлена в `.env.example` и `turbo.json`.

**Модуль роли** (`mcp-app.module.ts`, `content-storage.ts`, `roles.ts`). Профиль берётся из конфигурации: роль сама создаёт клиент S3 и resolver. Клиент S3 видит один бакет: все виды бакетов в его настройках указывают на бакет артефактов, а обёртка `artifactsOnly` отклоняет обращение к другому виду до сети. Отказ в production остался и в модуле: он не полагается на загрузчик конфигурации. Второй аргумент `forRoot` теперь только тестовый шов `{ wrapResolver }` — обёртка над штатным resolver для инъекции сбоев; без профиля и в production он отклоняется. Health роли с профилем проверяет бакет артефактов. Строка запуска роли называет профиль.

**`mcp-content.ts`.** Сравнения `scope.stack !== 'wordpress'` убраны: есть ли у стека контент, решает реестр внутри resolver. Имя `wp_rest` и разбор маршрута остаются до N21.

**Имя ключа Transit** — одна функция `workspaceTransitKey(workspaceId)` в `packages/domain/src/sessions`. На неё переведены все пять мест в коде: два в `content-snapshots.ts`, два в `sessions/snapshot.service.ts`, одно в `snapshot-manifest.ts`.

**Зависимость.** `apps/orchestrator` зависит от `@repo/site-adapters`; правило слоёв менять не пришлось.

**Стенд `pnpm verify:mcp-content`.** Запускающий скрипт выполняет `infra/vault/bootstrap.mjs`, создаёт AppRole `mcp` с политикой `mcp-content` и токены `sites-writer`, `workspace-provisioner` и наблюдателя стенда (политика стенда: только чтение `kv/metadata/content-masks/*`). Ключ рабочего пространства создаёт токен `workspace-provisioner`, доступ сайта пишет токен `sites-writer` с CAS. Процесс роли получает `VAULT_ROLE_ID` и `VAULT_SECRET_ID`; root-токена в его окружении нет (worker проверяет это при старте), пароля приложения нет ни в окружении, ни в файле фикстуры. Шлюз сайта и для роли, и для собственных проверок стенда строит штатный resolver. Фикстурный resolver остался только обёрткой `wrapResolver`: проверка «снимок в S3 до записи» и потеря подтверждения записи. Обработчики сигналов в `verify-content.mjs` и `verify-site.mjs` стоят до конца уборки (`process.on`).

**Стенд `pnpm verify:agent-content`.** Роль `mcp` — штатный процесс `node dist/main.js` (`verify-agent-content-role.mjs`): `ORCHESTRATOR_ROLES=mcp`, `MCP_CONTENT_PROFILE=local`, AppRole `mcp`, окружение только этой роли, `HOME` — каталог внутри каталога стенда. `NODE_ENV=production` задан, чтобы `load-env.ts` не открывал корневой `.env`; `APP_ENV` остаётся `test`. Роль слушает `127.0.0.1`. Файл `verify-agent-content-mcp-worker.mjs` удалён, роли `mcp` в `workers.mjs` больше нет. Наблюдения вынесены из роли в два узла стенда: перед `/mcp` (метод JSON-RPC, имя инструмента, статус) и перед WordPress (счётчики по маршрутам плагина; на записи — проверка, что снимок подтверждён и лежит в S3, запись допущена, аренда называет этот вызов). Нарушение узел не пропускает к сайту и записывает; ход с нарушением не проходит. Сайт в базе и в секрете записан по адресу второго узла. Снимок для сравнения стенд открывает токеном `core-transit`; root-токен стека используется только при его подготовке. На Linux узел перед `/mcp` слушает адрес шлюза моста Docker, а не `0.0.0.0`.

## Границы доверия

- Доступ сайта читает только роль `mcp`: из Vault, под своей AppRole. В базе — путь и версия.
- Строка базы не может увести роль к чужому секрету: путь сравнивается с каноническим до обращения к Vault.
- Пароль, выданный для одного адреса, не уходит на другой: origin секрета сверяется с адресом сайта при чтении и при каждом вызове из кэша.
- Установка плагина привязана к сайту платформы: шлюз называет сайт допуска, чужая установка отвечает отказом.
- Песочница, `core`, web и роль `llm` не менялись.

## Что выяснено

- Аудит OpenBao хранит значения секрета хешами: пароля приложения, записанного в `kv/sites/…`, в журнале аудита нет. Это проверяет стенд `verify:agent-content`.
- Процесс роли останавливается по SIGTERM штатно и при работающем ходе: стенд считает принудительное завершение роли ошибкой уборки.
- CLI, который завершился сразу после последнего уведомления, обрывает запрос до ответа. Узел стенда такой запрос ответом не считает; прежний счётчик внутри роли вёл себя так же.

## Отступления от плана

- **Версия секрета.** Сверх плана resolver требует, чтобы версия секрета в Vault совпала с `key_version` строки. При замене доступа (сначала Vault, затем строка) роль не берёт из Vault ни прежний, ни новый пароль, пока они не согласованы. Копия прежнего доступа, прочитанная до замены, служит до истечения — до 60 секунд; это закреплено тестом.
- **Конфигурация worker стенда контента** собирается в скрипте, а не через `loadConfig`: фильтр путей `wordpress-content.yml` не включает `apps/orchestrator/src/config/**`, а workflow этому инкременту править нельзя. Путь `loadConfig` → `main.js` проверяет `verify:agent-content`.
- **Наблюдения стенда агента** перенесены из процесса роли в два узла стенда: у штатной роли нет тестового шва. Проверки ходов прежние.
- **Файлы вне списка плана:** новые `apps/orchestrator/src/mcp/content-storage.ts`, `packages/site-adapters/src/http-transport.ts`, `apps/orchestrator/scripts/verify-agent-content-role.mjs`. `packages/site-adapters/src/wordpress.ts` и `packages/domain/src/ports/published-content.ts` не менялись.
- **Сигналы.** `process.once` заменён в двух скриптах стенда контента — пункт из остатка первой партии.

## Что остаётся открытым

- **Production.** Профиль контента в production запрещён; включение ждёт решения владельца о гейте приложения 3 оферты.
- **Адрес сайта.** Штатный транспорт соединяется по имени и не проверяет, в какой адрес оно разрешилось; loopback по HTTP разрешён всему профилю `local`. Проверка адреса — N6.

Шаг подключения должен записать в секрет `origin` как `new URL(адрес).origin`: для сайта на кириллическом домене это punycode, иначе роль ответит отказом `format` или `origin`.
