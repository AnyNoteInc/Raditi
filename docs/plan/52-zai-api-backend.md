# П15: бэкенд Z.ai API с оплатой за токены

17.10.2026 выполнена задача roadmap «Бэкенд Z.ai API с оплатой за токены (П15)». Роль `llm` получила второй бэкенд порта `LlmBackend` — `zai-api`, API Z.ai с оплатой за токены (`https://api.z.ai/api/paas/v4`, chat completions). Он встал рядом с планом GLM Coding Plan (`zai-coding`), который остаётся бэкендом стендов и синтетики (П11). Путь production выбрал владелец 16.10.2026: «П15 давай сделаем API за токены» ([spec §20](../spec.md), П15).

Срезы и итоговый прогон шли без ключа API и без обращений к `api.z.ai`, корневой `.env` не читался: всё проверено на синтетическом Z.ai. Затем, 17.10.2026 в 12:04 МСК, прошла живая проверка на настоящем API — `pnpm verify:llm-gateway --live --api`, код 0, 10 запросов провайдеру из 20 (раздел «Живая проверка»). Ключ — настоящий ключ общего с production аккаунта Z.ai с балансом для проверок, который владелец передал в чате 17.10.2026 (ответы владельца от 17.10.2026, П83); запустил прогон руководитель задачи. Работа шла в ветке `feat/zai-api-backend` четырьмя срезами: A — домен, адаптер, пул, `core` и роль; B — команда оператора и сиды; C — `sandbox-gw` и стенды; D — документы. По указанию владельца от 09.10.2026 на каждый вопрос задачи сразу принято значение по умолчанию; по П77 и П83 владелец 17.10.2026 ответил сам. Это двадцать решений П65–П84 (spec §20, блок «Бэкенд API с оплатой за токены, 17.10.2026»), в плане задачи они назывались D1–D20.

Главное:

- **Второй бэкенд — второе описание `ZaiOffer` и правки без имён бэкендов.** Протокол, политика тела, счётчик расхода, заголовки и тексты отказов у двух предложений общие. Разное — путь чата, способ узнать ёмкость аккаунта и два ответа провайдера, которые на API значат другое. Порт получил одно поле — `LlmBackend.capacity`: `windows` у плана, `none` у API.
- **Аккаунт без окон годен, пока его не держит пауза.** Пул, выдача ключа и допуск роли читают ёмкость из объявления бэкенда. У `none` окна не спрашиваются, не обновляются и не делают аккаунт «неизвестным».
- **Код 1113 на API — пустой баланс, а не риск аккаунта.** Новый сигнал `balance_exhausted` даёт окончательный отказ `subscription_limit` и долговременную паузу аккаунта: 5, 15, 45 и 60 минут за сутки. Оператор получает строку лога. Аккаунт возвращается сам: после пополнения следующий вызов просто проходит. На плане 1113 по-прежнему `account_risk`.
- **Роль `llm` изменилась**, хотя документы до задачи этого не ожидали. Изменения нейтральны к провайдеру: роль читает объявленную ёмкость и новый сигнал, имени бэкенда в её коде нет. Вариант без правки роли существует, но он выдумывает окно и молчит перед оператором. Почему он отвергнут — П69 ниже.
- **Проба ключа API бесплатна и без содержимого, но баланса не видит.** Она читает путь монитора, который уже знает план, только как проверку ключа. Как этот путь отвечает ключу API, живой прогон 17.10.2026 проверил первым запросом: как ключу, который провайдер принимает, — импорт прошёл (П66).
- **Стенд шлюза получил группу API — 8 проверок, всего их стало 58.** Живой режим `pnpm verify:llm-gateway --live --api` прошёл на настоящем API 17.10.2026 (10 проверок), его репетиция идёт шагом CI. Строку API в `verify:agent-content` задача не добавила — это отступление от текста roadmap (П78).

## Что построено

### A. Порт, адаптер, пул, `core` и роль

**Порт** (`packages/domain/src/ports/llm-backend.ts`):

- `llmBackendIds = ['zai-coding', 'zai-api']`; новый id стоит после прежнего — в том же порядке идут реестр `llmBackends`, таблица импорта и сиды провайдеров (П65).
- `llmCapacitySchema` — `windows | none` — и обязательное поле `LlmBackend.capacity`. `windows`: провайдер отчитывается окнами, и аккаунт без прочитанного отчёта — неизвестная ёмкость. `none`: окон у провайдера нет, аккаунт ограничен только паузами, записанные окна ничего не значат.
- Сигнал `balance_exhausted` — «у аккаунта у провайдера кончились деньги». `refusalForSignal` отображает его в `subscription_limit`.

**Адаптер** (`packages/llm-backends/src/zai-coding/`). Каталог тот же: оба предложения — описания одного адаптера, и пути импорта стендов не изменились.

```ts
export const zaiApiOffer: ZaiOffer = {
  id: 'zai-api',
  route: { method: 'POST', path: '/zai/paas/v4/chat/completions' },
  origin: 'https://api.z.ai',
  chatPath: '/api/paas/v4/chat/completions',
  capacity: { kind: 'none', authPath: '/api/monitor/usage/quota/limit' },
  answers: { codes: { '1113': 'balance_exhausted' }, codeless429: 'transient' },
  overrideEnv: 'LLM_BACKEND_URL_ZAI_CODING',
  direct: true,
}
```

- `ZaiOffer.quota` стал `capacity`: `{kind: 'windows', path, windows}` у плана или `{kind: 'none', authPath}` у API. Фабрика `createZaiBackend` строит разбор окон только для `windows`.
- `ZaiOffer.answers` — где предложение читает ответ иначе, чем общая таблица кодов (`ZaiAnswers` в `errors.ts`). Это данные описания, а не ветка по нему. `zaiClassifier(answers)` даёт оба чтения: ответа со статусом и ошибки внутри начатого потока. Инспектор потока получает чтение своего предложения. Прежние свободные функции `classifyZai` и `classifyZaiStreamError` заменены на `zaiClassifier(answers)` в адаптере (`classify` и проба) и в инспекторе потока; их тесты перенесены на классификатор.
- `egress` предложения объявляет ровно его запросы: `POST …/api/paas/v4/chat/completions` и `GET …/api/monitor/usage/quota/limit`.
- `zaiApiBackend` — второй элемент реестра `llmBackends`.

Чем таблицы кодов двух предложений отличаются (остальное — общая таблица [отчёта G2](41-zai-backend.md)):

| Ответ | План, `zai-coding` | API, `zai-api` |
| --- | --- | --- |
| Код 1113 «Insufficient balance or no resource package» | `account_risk`, причина `zai_1113` — у ключа нет плана | `balance_exhausted` — у аккаунта нет денег (запись 21: HTTP 429) |
| HTTP 429 без кода | `unconfirmed_block`: ход кончается, роль пробует аккаунт | `transient`: пауза из `retry-after`, не больше 30 с, без пробы |
| HTTP 429 с незнакомым кодом | `unconfirmed_block`, `zai_<код>` | так же |

**Проба API** (`probeKey`): один `GET` пути монитора с ключом аккаунта, те же заголовки, что у пробы квоты.

| Ответ | Результат пробы |
| --- | --- |
| HTTP 401; код 401, 1000, 1001 или 1003 в конверте или в объекте ошибки | `auth` |
| HTTP 200 с JSON-объектом, у которого `success` — `true` или `false` | `{status: 'ok', windows: null, plan: null}` — что бы ни было внутри |
| HTTP 403 без объекта ошибки провайдера | `region` |
| Всё остальное: 200 не конвертом, 429, 404, 5xx, редирект | отказ пробы, пул ничего не меняет |

**Пул** (`packages/domain/src/llm/pool.ts`). У `pickAccount` новое обязательное поле входа `capacity`. С `none` окна аккаунта не читаются: запас 100, неизвестных окон нет. Охлаждение, размыкатель и пауза держат аккаунт как раньше.

**`core`** (`apps/orchestrator/src/llm/`):

- `backends.ts` — новый файл с двумя чистыми помощниками. `backendCapacities(llmBackends)` — ёмкость по id; id без адаптера в процессе — ошибка, и выдача ключа отказывает закрыто. `llmGatewayBaseUrl(gateway, backend)` — адрес `sandbox-gw` с префиксом единственного маршрута бэкенда без `/chat/completions`: так строится `RunContext.llm.baseUrl` (П80). Код раннера оба помощника не достаёт (правило `runner-no-platform-access` dependency-cruiser).
- `GatewayTurnCredentials` получает обязательное `capacityOf`. Композиция — `llm.module.ts`; конструктор без функции падает с понятной ошибкой: стенды на JS тип не проверяют. Выбор аккаунта передаёт ёмкость в `pickAccount`. У бэкенда без окон нет устаревшего снимка: `staleAccountId` — только у `windows`.

**Роль `llm`** (`apps/orchestrator/src/llm-gateway/`):

| Файл | Что изменилось |
| --- | --- |
| `server.ts` | Перед первым вызовом ключа устаревший снимок обновляется только у бэкенда с окнами; в допуск идёт `capacity` бэкенда маршрута |
| `types.ts`, `store.ts` | `GatewayAdmitInput.capacity` обязателен; у `none` допуск не читает окна и не отвечает «окна неизвестны» — аккаунт держат только выключатели, размыкатель и охлаждение |
| `pool-health.ts` | Сигнал `balance_exhausted` не идёт на подтверждающую пробу. Он ставит долговременную паузу и один раз на паузу пишет `{"event":"llm_pool_health","reason":"balance_exhausted","checks":N}` |
| `pool-health-store.ts` | Метод `balance(accountId)`: под замком строки аккаунта считает проверки баланса за сутки по `llm_calls.signal`. Ответы, пришедшие внутри одной паузы, — одна проверка. Пауза пишется в `cooling_until`: 5, 15, 45 минут, четвёртая и дальше — 60. Вызов, на который ответили, пока аккаунт уже стоит на паузе, новой паузы не начинает |
| `../config/llm-config.ts` | Проверка при старте: один origin — одна переменная подмены стенда, иначе `LLM backends name two stand variables for <origin>` |

Миграции нет. `llm_calls.signal` (`VarChar(32)`) и `health_reason` значений не ограничивают.

### B. Команда оператора и сиды

- `subscriptions:login --backend` принимает `zai-coding` и `zai-api`. Вторая запись таблицы импорта (`apps/orchestrator/src/subscriptions/cli.ts`): `zaiApiBackend`, драйвер `opencode`, один ход и два запроса одновременно — как у плана (П74). У записи новое поле `planExample`: `lite` у плана, `payg` у API. Справка собирается только из таблицы: `--backend zai-coding|zai-api`, строка `--plan — метка тарифа нового аккаунта, например: zai-coding — lite, zai-api — payg.`, а примечание об узле выхода — из объявлений адаптеров: `(zai-coding и zai-api он не нужен)`.
- Ключ API импортируется, если проба ответила `ok`, в том числе при нулевом балансе (П75). Окон импорт не пишет. Повторный вход в аккаунт `zai-api` под `--backend zai-coding` отклоняется. Вывод аккаунта и `subscriptions:token` от бэкенда не зависят и не менялись.
- Сиды (`packages/db/prisma/seed/data.ts`): провайдер `zai-api` «Z.ai API», вида `subscription`, выключен; три выключенных профиля `glm-5.3-light`, `glm-5.3-standard`, `glm-5.3-heavy` с моделью `glm-5.3` и резервом выхода 32 000, имена — как у профилей плана. Ставок нет, миграции нет (П76). Новая база получает 2 провайдеров и 6 профилей. Каталог стенда `pnpm verify:db` (`infra/dev/db-verify/switch-to-opencode.mjs`) и тест переключения `packages/db/prisma/switch-to-opencode.test.ts` выросли вместе с сидами.
- Биллинг не менялся. Читатели ставок смотрят только включённые модели, а `billing:rates` находит профиль по паре «провайдер, slug». Новый тест на PostgreSQL проверяет это на двух предложениях (`packages/billing/src/credit-rate-approval.test.ts`).
- Необязательные поля, которые срез A оставил ради компиляции `src/subscriptions`, стали обязательными: `capacityOf` и `GatewayAdmitInput.capacity`. Образцовая ёмкость тестов — `sampleBackendCapacity = 'windows'` в `apps/orchestrator/src/testing/ids.ts`, тест сверяет её с реестром. `sampleBackendId` остаётся `zai-coding`: «бэкенд вообще» в тестах пула и допуска — бэкенд с окнами. Тест бэкенда без окон называет `zai-api` или свой синтетический адаптер.

### C. `sandbox-gw`, синтетический Z.ai и стенды

- **`sandbox-gw`** (`infra/sandbox/gateway.mjs`): `llmPaths` — `/zai/v4/chat/completions` и `/zai/paas/v4/chat/completions`. Запрещённые пути теста шлюза дополнены `/api/paas/v4/chat/completions` и `/zai/paas/v4/models`. Тест-контракт `sandbox-routes.contract.test.ts` прошёл без правки. Новый тест `apps/orchestrator/src/llm/backends.test.ts` сверяет `llmGatewayBaseUrl` каждого бэкенда с `llmPaths`. `gateway.mjs` стал входом задачи `test` в `turbo.json`, `infra/app/ci.test.mjs` называет оба теста, которые его читают.
- **Синтетический Z.ai** (`infra/dev/llm-verify/fake-zai.mjs`) отвечает на путь API `/api/paas/v4/chat/completions`:
  - два синтетических ключа API, принимается один; состояние баланса `funded` или `empty`;
  - с деньгами — тот же поток и тот же расход, что на пути плана, окна не тратятся;
  - пустой баланс или ключ другого предложения — 1113 под HTTP 429 с типом содержимого записи 21; отклонённый ключ — 401; без ключа — 1001; сценарий `error` со статусом без кода — 429 без кода;
  - путь монитора отвечает ключу API конвертом `{code: 1113, success: false}`. Такой ответ не записан — это допущение (форма конверта записей 10 и 14, код записи 21); проба API читает его как принятый ключ.
- **Стенд шлюза.** Общие функции группы плана вынесены в `apps/orchestrator/scripts/verify-llm-zai-harness.mjs`, поведение группы плана не изменилось. Новая группа API — `apps/orchestrator/scripts/verify-llm-zai-api.mjs`. Она идёт после группы плана на аккаунте провайдера `zai-api`, так что пулы друг друга не видят. Восемь проверок:
  1. импорт настоящей командой `subscriptions:login --backend zai-api --plan payg` при пустом балансе: чужой ключ отклонён, окон никто не пишет;
  2. допуск без пробы окон — и тогда, когда у аккаунта лежит пустой снимок десятиминутной давности;
  3. ход настоящего OpenCode по маршруту `/zai/paas/v4/chat/completions`: расход каждого вызова записан один раз и равен записям CLI; ключ API на маршруте плана — 403 `raditi_backend`;
  4. 1113 — окончательный `subscription_limit` за один запрос, пауза 5 минут в `cooling_until`, строка алерта, ни одной пробы; новая задача ждёт;
  5. второй пустой баланс за сутки — пауза 15 минут; после паузы и пополнения ход идёт;
  6. отклонённый ключ — `auth`: одна проба подтверждает, `needs_relogin`, `--relogin` возвращает аккаунт;
  7. 1302 OpenCode повторяет; 429 без кода — кратковременный, без пробы;
  8. итоговая сверка того, что дошло до провайдера: ни ключа хода, ни заголовков сессии и cookie, ни одного запроса на путь плана.
- Стенд целиком — 58 проверок (50 группы плана и 8 группы API) и 42 завершённых вызова (37 и 5). Нижняя граница `MIN_COMPLETED_CALLS` поднята с 30 до 38.
- **Живой режим.** Флаг `--api` есть только у `pnpm verify:llm-gateway` и только вместе с `--live` или `--rehearsal`; с `--measure`, `--results` и у стенда контента он отклоняется. Ключ — тот же `ZAI_API_KEY`, что у живого режима плана (решение владельца от 17.10.2026, П77): стенд читает его один раз и передаёт только на stdin импорта `--backend zai-api --plan payg`. Пределы — 20 запросов и 10 минут, без запаса на чтение квоты; шаги, которые есть только у плана (окна при старте, прирост окна, чтение квоты), пропускаются. Что прогон утверждает и как прошёл — раздел «Живая проверка».
- **CI.** Сторож `infra/app/ci.test.mjs` по-прежнему запрещает workflow `--live` и `ZAI_API_KEY` и сверяет, что живой режим берёт ключ из этой переменной. В `.github/workflows/llm-gateway.yml` — четвёртая репетиция: `pnpm verify:llm-gateway --rehearsal --api --no-build`.
- Находка критика G1 исправлена: `live.test.mjs` и `verify-llm-worker.mjs` убирают повторы origin — два предложения стоят на одном `https://api.z.ai`. `verify-llm-live.mjs` ищет профили по провайдеру и slug: slug `glm-5.3-*` теперь есть у двух провайдеров.
- Стенды, которые строят `GatewayTurnCredentials` сами (`verify-core-worker.mjs`, `verify-agent-content.mjs`), передают `capacityOf: backendCapacities(llmBackends)`.
- `infra/dev/llm-verify/README.md` описывает путь API синтетического Z.ai, группу API, `--api` с ключом `ZAI_API_KEY`, запуск живого прогона и его итог 17.10.2026.

## Решения

Двадцать вопросов задачи владельцу отдельно не задавались: по его указанию от 09.10.2026 по каждому сразу принято значение по умолчанию. Номера — продолжение вопросов перехода в spec §20; в плане задачи — D1–D20, номер D равен номеру П минус 64.

- **П65. Id и провайдер — `zai-api`, «Z.ai API».** Slug провайдера обязан равняться id бэкенда: по нему выдача ключа, вход, вывод, шлюз и сборщик находят строку `llm_providers`. Id стоит после `zai-coding` во всех четырёх списках, порядок держат тесты.
- **П66. Проба API — проверка ключа на пути монитора.** Проба шлюза зовётся при импорте, на подтверждение сигнала (не чаще раза в 5 минут на аккаунт) и при перепроверке блока региона по таймеру. Платная проба была бы неучтённым расходом по таймеру, а генерация несла бы содержимое. Публичного пути баланса у Z.ai нет, а путь `/models` не записан. Путь монитора роль уже знает, и его конверт отказа ключа записан (записи 10 и 10d). Чего проба не видит: баланса — его показывает только 1113 на вызове (П70); ключа, импортированного не под тем бэкендом (П83); подтверждения риска аккаунта — на API сигналы `account_risk` (коды 1309, 1313) и `unconfirmed_block` проба не подтверждает, ход кончается, аккаунт остаётся `ok`. Для ключа без плана ответ до задачи не был записан; живой прогон 17.10.2026 проверил его первым запросом: путь монитора ответил ключу API как ключу, который провайдер принимает, импорт прошёл — допущение подтверждено на настоящем провайдере. Запасной путь — запрос генерации с `max_tokens: 1` только при импорте, никогда по таймеру — не понадобился.
- **П67. Описание: `capacity` вместо `quota` и таблица ответов предложения.** Общими остаются схема секрета, политика тела, инспектор потока, счётчик расхода, тексты отказов и строка клиента. Наружу пакета форма описания не выходит.
- **П68. Маршрут — `POST /zai/paas/v4/chat/completions`.** Дефис в маршруте запрещают оба тест-контракта путей. Маршрут повторяет `/api/paas/v4` так же, как `/zai/v4` — путь плана. Маршрут и бэкенд в роли один к одному, поэтому ключ одного бэкенда на маршруте другого получает 403 `raditi_backend`. Общий маршрут на два бэкенда отвергнут: он переписал бы роль.
- **П69. Ёмкость — поле порта, и роль меняется.** `LlmBackend.capacity` объявляет адаптер; `core` и роль читают его, имени бэкенда нигде не сравнивают (правило 8). Пул намеренно читает пустой снимок окон как «неизвестно»: для плана это верно, поэтому «окон нет по устройству» должно быть словом бэкенда. Без правки роли можно было обойтись: проба API отвечала бы окном «месяц, 0 %», а 1113 читался бы как исчерпанное окно без срока, и закрытие вызова, проба и охлаждение на час сработали бы сами. Это проверено критиком по коду, но отвергнуто. Такой путь выдумывает окно, которого у провайдера нет, — spec §9 говорит «окна лимитов — из ответа квоты плана, других источников нет». Он не даёт оператору алерта: строка лога называет исчерпанное окно, а не деньги. И он держит паузу ровно час, что бы ни было с балансом. Ещё одна мелочь: проба без окон пишет `limit_windows = []` и `limits_seen_at`, и читатели устаревшего снимка срабатывали бы через 10 минут после каждой пробы; правка роли закрывает их по ёмкости.
- **П70. 1113 на API — сигнал `balance_exhausted`.** Отказ `subscription_limit` — окончательный 403: для P12 это «нет мощности», а не «аккаунт сломан». Пауза — долговременная, в `cooling_until`: её видит и выбор аккаунта в `core`. Нет подтверждающей пробы, `suspended` и повторного входа: баланс не видит ни проба, ни вход. Отвергнуты три других пути. Пауза оплаты по HTTP 402 держит паузу в памяти роли, которую `core` не видит, ключена на статус, которого Z.ai не шлёт, и кончается `suspended` с повторным входом. `account_risk` дал бы ложный алерт о блокировке и суточное удержание оператором. `window_exhausted` — П69.
- **П71. Таблица кодов — у каждого предложения своя поверх общей.** API отличается двумя ответами: 1113 и 429 без кода (кратковременный — по стороннему описанию ответа «Too much concurrency»). Таблица плана не изменилась, её закреплённые тесты и строки стенда тоже. 1302 и 1305 остаются кратковременными у обоих; 1313 — риском аккаунта у обоих. Коды окон 1308, 1310, 1316 и 1317 и на API читаются общей таблицей как исчерпанное окно (`window_exhausted` без срока), 1311 — `profile`, как у плана. У аккаунта без окон (`capacity: none`) такой сигнал значит одну подтверждающую пробу — проба API окон не возвращает, срока сброса нет — и охлаждение на час через `cool(null)` хранилища; паузы баланса и её счёта нет. Это закрепляет тест роли в `pool-health.test.ts` (добавлен 17.10.2026 по пункту 5 проверки по спецификации).
- **П72. Вид провайдера — `subscription`.** Значит «обслуживается пулом шлюза»; вид `api` — история прежних прямых провайдеров. Смена вида потребовала бы правок в шести местах кода без пользы.
- **П73. Переменная подмены адреса — общая для origin.** Предложение API объявляет ту же `LLM_BACKEND_URL_ZAI_CODING`. Подмена стенда действует на origin, а не на бэкенд; второе имя дало бы только молчаливое «побеждает последнее». Новая проверка при старте не даёт одному origin двух имён. `.env.example`, `turbo.json`, preflight и стенды не менялись. Переименование в `LLM_BACKEND_URL_ZAI` — косметика, можно позже.
- **П74. Импорт ключа API — один ход и два запроса, `--plan payg`.** Параллельность API не измерена; поднять её — правка данных оператора в пределах ограничений таблицы (1–8 ходов, 1–16 запросов). Колонка `plan` обязательна, а читает её только оператор.
- **П75. Ключ с нулевым балансом импортируется.** Проба проверяет только ключ. Первый вызов получает 1113, аккаунт встаёт на паузу, алерт называет причину. Так путь проверяется целиком и на ключе без денег.
- **П76. Сиды — выключенный провайдер и три выключенных профиля без ставок, без миграции.** Те же slug, что у плана: уникальность в `llm_models` — по паре «провайдер, slug».
- **П77. Живая проверка — флаг `--api` у стенда шлюза, ключ `ZAI_API_KEY`.** Решение владельца от 17.10.2026: формулировки правил 1 и 2 `CLAUDE.md` о живой проверке API утверждены («а — да»), отдельной переменной ключа API нет («в — [вторую переменную ключа API] убирай, используй только ZAI_API_KEY»). Стенд берёт ключ так же, как живой режим плана: один раз, из окружения команды, только на stdin импорта в свой одноразовый OpenBao. Сторож CI запрещает workflow `--live` и `ZAI_API_KEY`. Репетиция `--rehearsal --api` — шаг CI, иначе код живого флага не исполнялся бы нигде.
- **П78. Стенды — группа API в `verify:llm-gateway`; общие сценарии — один раз, на плане; строки API в `verify:agent-content` нет.** Roadmap называл и стенд контента. Довод тот же, что в П46. - **П79. Кто выбирает бэкенд в production — P12, по конфигурации.** Бэкенд хода — включённый провайдер драйвера, без `if`. В production включается только `zai-api`, а провайдер и профили `zai-coding` остаются выключенными: биллинг читает `llm_models.enabled` у любого провайдера. Задача держит бэкенд между ходами; привязка к аккаунту чужого провайдера и сейчас кончается `binding_missing`. Решение записано, кода нет — он в P12.
- **П80. Адрес шлюза для CLI — помощник в `core`.** `llmGatewayBaseUrl` отрезает `/chat/completions` от единственного маршрута бэкенда и отказывает при другой форме. Лежит в `apps/orchestrator/src/llm/`, куда код раннера не дотягивается; поля порта не нужно. Им уже пользуются стенды, в продукте его возьмёт P12.
- **П81. Ставка не записывается.** Шаблон файла `billing:rates` с опубликованной ценой — раздел «Оператору». Пересчёт в рубли и НДС — за владельцем и бухгалтером. Курс кредита утверждается тем же запуском команды.
- **П82. Политика тела общая.** `thinking`, `reasoning_effort` (`low`, `high`, `max`), `max_tokens` до 32 000 и `stream_options.include_usage` на пути API описаны в документации или косвенно подтверждены. - **П83. Аккаунт Z.ai для живой проверки — общий с production.** Решение владельца от 17.10.2026 («б — общий с production, он уже указан в ZAI_API_KEY»): ключ в `ZAI_API_KEY` настоящий, с небольшим балансом для проверок, и живая проверка API 17.10.2026 прошла на нём. Ключ аккаунта без плана под `zai-coding` импорт отклоняет: проба плана читает ответ пути монитора такому ключу как `suspended` или `unknown` — это допущение синтетического Z.ai, на настоящем провайдере не проверено. ## Что не доказано

Живая проверка 17.10.2026 сняла три пункта прежнего списка (раздел «Живая проверка»): проба ключа API на ключе без плана прошла на настоящем провайдере (П66); форма расхода на пути API прочитана — `prompt_tokens`, кэшированные и токены рассуждения, расход роли равен записям CLI, в каждом ответе он пришёл в кадре с `finish_reason`; уровни `low` и `max` меняют число токенов рассуждения (П82). По числам прогона кэшированные токены входят в `prompt_tokens`, как на пути плана: у хода `max` при том же входе, что у хода `low` (4 406), роль насчитала 2 102 некэшированных и 2 304 кэшированных. Осталось:

- **Пустой баланс на настоящем провайдере.** У аккаунта живой проверки есть баланс, поэтому 1113 на вызове ключа хода и пауза `balance_exhausted` проверены только на синтетическом Z.ai; с настоящего пути API записан один ответ 1113 без потока (запись 21).
- **Параллельность ключа API и пределы частоты.** Предел провайдера скрыт за входом в консоль; один ход и два запроса — осторожное значение (П74). 429 без кода как ответ на превышение известен только из стороннего описания; живой прогон шёл одним ходом за раз и в пределы частоты не упирался.
- **Коды 1308–1317 на API.** Как настоящий путь API отвечает кодами окон и риска аккаунта, не записано: их чтение (П71) проверено только на синтетическом Z.ai.
- **Пауза по балансу — на ключ или на аккаунт Z.ai.** Баланс принадлежит аккаунту Z.ai, а пауза — аккаунту пула, то есть ключу. Несколько ключей одного аккаунта Z.ai в пуле узнают о пустом балансе каждый сам, своим 1113.
- **Ключ, импортированный не под тем бэкендом.** Отличить его продукт не умеет (П83): ключ под `zai-api` списывает с баланса аккаунта, под `zai-coding` — с плана, а аккаунт без денег под `zai-api` получает 1113 на каждом вызове и встаёт на паузы. Ключ аккаунта без плана под `zai-coding` импорт отклоняет: проба плана читает конверт пути монитора такому ключу как `suspended` или `unknown`. Это допущение синтетического Z.ai, на настоящем провайдере не проверено. Живая проверка не проверила и обратного — ключа плана, импортированного под `zai-api`.
- **Риск аккаунта на API не подтверждается.** Проба видит только ключ: коды 1309 и 1313 и неподтверждённая блокировка кончают ход, но аккаунт не становится `suspended`.
- **Цены.** Опубликованная цена прочитана 16.10.2026 на странице без даты; хранение кэша там «временно бесплатно». Как Z.ai считает токены рассуждения, документация не говорит; допущение — по цене выхода в составе `completion_tokens`.
- Всё прочее, чего не доказывает путь плана: канал из России (P14), профиль `llm` app-ВМ без узла выхода (П21, M10), получатель данных (П1).

## Оператору

Порядок — как в «Что включает оператор» [отчёта G8](48-removal.md), с другим провайдером; ставка — только командой `billing:rates`.

0. **Аккаунт.** Ключ API — ключ аккаунта Z.ai с балансом; один ключ работает на обоих путях (П83). Сейчас это аккаунт, общий с production, его ключ — в `ZAI_API_KEY` (решение владельца от 17.10.2026). Раздельные ключи по назначению — для стендов и для production — выпускать можно, но не обязательно. Баланс пополняется в консоли Z.ai; биллинг Z.ai показывает расход с задержкой в сутки.
1. **Импорт ключа.** Ключ уходит в Vault `subs/zai-api/<UUID>`, аккаунт создаётся выключенным:

   ```sh
   pnpm --filter orchestrator subscriptions:login -- --backend zai-api --label <метка> --plan payg \
     --vault-token-file <абсолютный путь>
   ```

   Импорт проходит и при нулевом балансе (П75).

2. **Провайдер и профили.** В production включается только `zai-api`; провайдер и профили `zai-coding` не включаются никогда.

   ```sql
   UPDATE llm_providers SET enabled = true, updated_at = clock_timestamp()
    WHERE slug = 'zai-api' AND kind = 'subscription';
   UPDATE llm_models SET enabled = true, updated_at = clock_timestamp()
    WHERE provider_id = (SELECT id FROM llm_providers WHERE slug = 'zai-api')
      AND slug IN ('glm-5.3-light', 'glm-5.3-standard', 'glm-5.3-heavy');
   ```

3. **Учётная ставка и курс кредита — одним запуском `billing:rates`** (spec §17). Без ставки `issue` отвечает `LLM_PRICE_MISSING`, без пригодного курса резерв отвечает `BILLING_CREDIT_RATE_MISSING`. Команда пишет ставки трёх профилей и строку курса с одним моментом начала, поэтому курс утверждается заново тем же запуском — даже если его значение не меняется.

   Опубликованная цена GLM-5.3 на API, доллары США за 1 млн токенов, без НДС: вход — 1,40; кэшированный вход — 0,26; выход — 4,40. Источник — <https://docs.z.ai/guides/overview/pricing>, прочитано 16.10.2026, у страницы нет даты; то же даёт реестр models.dev. Одна модель — одна цена для трёх профилей, поэтому подтверждение `--confirm-mixed-models` не нужно, пока профили `zai-coding` выключены.

   ```json
   {
     "rubPerCredit": "<курс кредита: ₽ учётной стоимости в одном кредите>",
     "basis": "<корзина, модель zai-api glm-5.3, ставки, курс доллара и его дата, кто утвердил>",
     "prices": [
       {
         "provider": "zai-api",
         "model": "glm-5.3-light",
         "inputPer1m": "<₽ с НДС за 1 млн токенов входа>",
         "cacheReadPer1m": "<₽ с НДС за 1 млн токенов кэша>",
         "cacheWritePer1m": null,
         "outputPer1m": "<₽ с НДС за 1 млн токенов выхода>",
         "vatRate": "0.2200",
         "sourceUrl": "https://docs.z.ai/guides/overview/pricing"
       },
       { "provider": "zai-api", "model": "glm-5.3-standard", "…": "те же числа" },
       { "provider": "zai-api", "model": "glm-5.3-heavy", "…": "те же числа" }
     ]
   }
   ```

   - Рубли — цена в долларах, пересчитанная по курсу, который выберет владелец, с НДС. Курс и НДС решают владелец и бухгалтер. `vatRate` — `0.2200` по правилу spec §17, пока бухгалтер не скажет иначе.
   - `cacheWritePer1m: null` — записи в кэш у Z.ai нет; кэш неявный.
   - Строки `standard` и `heavy` в файле повторяют все поля строки `light`, кроме `model`: схема файла закрытая, `"…"` в шаблоне — только сокращение.
   - Числа в шаблоне не записаны: их утверждает владелец (П3, П81).

   ```sh
   APP_ENV=<окружение> DATABASE_URL=<адрес базы> \
     pnpm --filter orchestrator billing:rates -- --file <rates.json> --reason "Ставки API Z.ai и курс кредита"
   ```

4. **Аккаунт.** До этого `issue` отвечает `SUBSCRIPTION_WAIT`.

   ```sql
   UPDATE subscription_accounts SET enabled = true, updated_at = clock_timestamp() WHERE id = '<UUID аккаунта>';
   ```

5. **Гейт 152-ФЗ.** Запись в `cross_border_clearances` — только для провайдера `zai-api` и последним пунктом чек-листа гейта (spec §18). Для `zai-coding` записи нет: гейт проверяется по провайдеру, и запись открыла бы реальные данные личному плану.

Пустой баланс виден строкой лога роли `{"event":"llm_pool_health","reason":"balance_exhausted","checks":N}`. После пополнения ничего делать не нужно: следующий вызов после паузы проходит сам. Отклонённый ключ — `needs_relogin`, лечится `--relogin` с новым ключом.

## Живая проверка

Единственный разрешённый путь к настоящему API вне продукта — живой режим стенда шлюза (правило 1 CLAUDE.md). Запускается он вручную, не в CI. Прогон 17.10.2026 прошёл — подраздел «Прогон 17.10.2026» ниже.

Ключ — настоящий `ZAI_API_KEY` общего с production аккаунта Z.ai; баланс для проверок на аккаунте есть (решения владельца от 17.10.2026, П77 и П83). Порядок запуска, в том числе для повторов:

1. Экспортировать `ZAI_API_KEY` в своей оболочке, не набирая значение в командной строке. Например, в zsh или bash: `read -rs ZAI_API_KEY; export ZAI_API_KEY`. Агенты `.env` не читают.
2. Запустить из той же оболочки:

   ```sh
   pnpm verify:llm-gateway --live --api
   ```

Пределы — не больше 20 запросов провайдеру и 10 минут; сторож соединений `live-guard.mjs` не выпускает запрос сверх предела. Модели уходят только синтетические данные. Стенд отказывается стартовать (код 2) без ключа, при заданном `CI` и при подмене адреса, прокси или переключателе CA в окружении. Вход запроса в токенах платформа не ограничивает: живые ходы G6 слали по 7–40 тысяч. При 40 тысячах худший случай — 20 запросов: до 0,8 млн токенов входа, до 1,12 $ без кэша, и до 0,64 млн токенов выхода (32 000 на запрос — предел политики тела), до 2,82 $, по опубликованной цене; всего около 4 $. Живые ходы G6 к пределу выхода не приближались.

Прогон утверждает:

- импорт проходит на пробе ключа (П66) — если Z.ai ответит пути монитора иначе, прогон кончается на импорте строкой о пробе ключа;
- первый ключ хода выдаётся без запроса провайдеру и без записи окон;
- ходы на уровнях `low` и `max` (профили `glm-5.3-light` и `glm-5.3-heavy` провайдера `zai-api`) насчитывают разное число токенов рассуждения;
- каждый запрос провайдеру — проба импорта или вызов ключа хода;
- те же четыре хода приёмки, что у плана, — с инструментом, с MCP, текст и его продолжение, — на маршруте и ключе API.

Где приходит расход — в кадре с `finish_reason` или отдельным кадром после него — прогон сообщает строкой отчёта (`usage in the finish chunk k of n`) и на этом не падает: счётчик роли читает обе формы.

Если баланс всё же кончится, прогон этого не скроет: вызов получит 1113, и ход кончится отказом `subscription_limit`. Порядок, отказы запуска и уборка — `infra/dev/llm-verify/README.md`, «Живой режим».
