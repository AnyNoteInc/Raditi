# G5: `verify:agent-content` на OpenCode и синтетическом Z.ai

09.10.2026 выполнен инкремент G5 [плана перехода на OpenCode и GLM](../research/2026-10-opencode-glm/pivot-plan.md): стенд `pnpm verify:agent-content` получил третью строку — настоящий OpenCode 1.18.34 через свой драйвер правит страницу настоящего WordPress через штатную роль `mcp`. Это первый контакт закреплённого CLI с настоящим `tools/list` роли: до сих пор OpenCode видел только синтетический сервер MCP стенда шлюза. Провайдера изображает синтетический Z.ai. Ключ плана не использовался, к `api.z.ai` никто не ходил, корневой `.env` не читался. Codex и Kimi не удалены и не сломаны: их строки того же стенда проходят как раньше.

Инкремент следует плану с ответом владельца П2 от 05.10.2026 ([pivot-answers.md](../research/2026-10-opencode-glm/pivot-answers.md)): к Z.ai роль `llm` ходит без узла выхода. Отступления собраны в разделе «Отступления от плана».

Главное:

- **Продуктовый код не менялся.** Строка OpenCode прошла с первого запуска стенда; дефектов роли `mcp`, роли `llm`, `sandbox-gw` и драйвера стенд не нашёл. Изменены только синтетический провайдер, скрипты стенда, их тесты, workflow и документы стенда.
- **OpenCode и роль `mcp` договорились о протоколе MCP `2025-11-25`**: эту версию CLI просит в `initialize` и называет в каждом запросе после ответа роли. Три инструмента роли CLI объявляет провайдеру функциями `raditi_site_info`, `raditi_wp_rest` и `raditi_restore`.
- **Запрещённый вызов OpenCode отправляет.** Аргументы по схеме из `tools/list` он сам не проверяет, как это делает Kimi: маршрут вне профиля уходит роли, и роль отвечает HTTP 400 на допуске. Запрос один, без повторов; ход продолжается и завершается итогом.
- **HTTP 400 роли модель видит как текст ошибки транспорта** — без статуса, с телом ответа роли дословно. Точные строки трёх CLI — в разделе «Как CLI показывают модели отказ роли»; они нужны N21.
- **`notifications/cancelled` OpenCode шлёт после каждого вызова** — три за ход правки. Роль принимает каждое (202) и ничего по нему не меняет: стенд читает завершённые строки журнала до того, как уведомление дойдёт до роли, и после её ответа — они совпадают. О каком вызове уведомление, стенд не записывает: то, что оно о запросе, на который CLI уже получил ответ, известно из записи разведки (наблюдение 3).
- **Роль `llm` перезапускается перед строкой OpenCode**: один процесс роли ходит к провайдерам одним путём. Codex и Kimi идут через прокси стенда, Z.ai — напрямую, как решено для него в П2 (профиль `llm` app-ВМ пока только с прокси).
- **Стенд — 27 проверок за 66–72 секунды** (с двумя строками сегодня же было 18 проверок за 54–57 секунд). Дважды подряд и с SIGTERM на конечном дереве — остатков нет; после правок ревью все три прогона повторены с тем же итогом.
- **Ревью нашло, что стенд утверждал больше, чем проверял:** о повторе записи он знал только HTTP 200, а печатал «повтор получил сохранённый ответ». Теперь ход правки читает, что CLI передал модели. Продуктовый код ревью не меняло; раздел «Что изменило ревью».

## Что построено

### Синтетический провайдер

`infra/dev/llm-verify/fake-zai.mjs` получил два сценария чата, как у фейка Codex и Kimi:

- `content_edit` — чтение страницы, запись с ключом идемпотентности, та же запись ещё раз, затем текст итога;
- `content_forbidden` — один вызов, который платформа должна отклонить: чтение заданного маршрута либо, при заданном `body`, запись без ключа идемпотентности; затем текст.

Параметры те же, что у фейка Codex и Kimi: `route`, `idempotencyKey`, `body`. Что именно модель просит у `wp_rest`, описывает новый модуль `infra/dev/llm-verify/content-scenario.mjs` (`contentOptions`, `contentCall`): код перенесён из `fake-subscriptions.mjs` без изменений, оба фейка его импортируют. `fake-zai.mjs` не может импортировать `fake-subscriptions.mjs` — тот сам импортирует его.

Раунд выбирается существующим правилом фейка Z.ai — числом шагов с инструментами после последнего сообщения пользователя. Отчёт G4 был прав: `rounds` хватает, нового состояния в фейке нет. Своих сценариев потребовало одно: текст правки несёт `{{contact}}`, а подставить вместо него маркер контакта можно только из разговора — это делает `contentCall`, а не список раундов, заданный заранее.

**Имя инструмента не угадывается.** Фейк вызывает функцию, которую запрос сам объявил для инструмента MCP `wp_rest`. Закреплённый OpenCode называет инструмент сервера MCP `<сервер>_<инструмент>`; сервер в конфигурации драйвера — `raditi` (`packages/agent-drivers/src/opencode.ts`, `mcpServer`). Откуда это известно:

- запись настоящего прогона `docs/research/2026-10-opencode-glm/samples/34-run-c-mcp` (копия — фикстура адаптера): CLI объявил `raditi_site_info` и `raditi_wp_rest`, настоящая модель вызвала `raditi_wp_rest`;
- разведка G1 и стенд G4 вызывали `raditi_site_info`;
- строка `OBSERVED` этого стенда в каждом проходе: `bash, edit, glob, grep, raditi_restore, raditi_site_info, raditi_wp_rest, read, todowrite, write`.

Если функции с именем `…_wp_rest` в запросе нет или их две, фейк отвечает 400: CLI потерял подключение к платформе, и сценарий ничего не выдумывает. Так же он отвечает, когда правке нужен маркер контакта, а в разговоре его нет. Запрос без `tools` — так CLI просит сжать контекст — получает текст.

Тесты `fake-zai.test.mjs` закреплены на записи `34-run-c-mcp`: запрос собирается из записанных `tools` и сообщений, имя вызванной функции и набор ключей вызова сравниваются с записанным вызовом модели, форма каждого кадра — с записанными формами, а поток проходит production-инспектор адаптера.

### Стенд

Ходы стенда — таблица `ROWS` в `apps/orchestrator/scripts/verify-agent-content-turns.mjs`, по строке на CLI. Всё, чем CLI отличаются для стенда, — данные строки: драйвер, бэкенд, путь роли `llm` к провайдеру, адрес и модель, уровень рассуждения, формат запроса (объявленные инструменты и выводы инструментов), ожидаемые объявления, откуда брать запросы провайдера, как задать сценарий. Сами ходы одни и те же для всех строк. Сравнений по имени CLI в скрипте больше нет: прежние `driver === 'kimi'` и `driver === 'codex'` стали полями строк. Удаление в G8 — две строки таблицы.

Строка OpenCode:

**Аккаунт и ключ хода — как в G4.** Аккаунт создаёт команда оператора `subscription-login.mjs --backend zai-coding --plan lite` с синтетическим ключом на stdin, без прокси в окружении. Строки провайдера, профиля, стендовой ставки (10 / 1 / 30 ₽ за миллион) и драйвера включает скрипт. Окна аккаунта стенд не пишет: при первом `issue` издатель ключей просит пробу у роли `llm` — для этого издатель стенда получил тот же клиент проб, что у `core` (`createPoolProbeClient`). Стенд проверяет, что окна `5h` и `week` в базе появились, а все запросы к синтетическому Z.ai пришли с ключом плана.

**Допуск хода — как в продукте,** без изменений: аренда сайта, продуктовое назначение (`TaskTurn`), ключ хода из `GatewayTurnCredentials.issue` с `requireAssignment: true` под AppRole `core` (политика `core-turns`).

**Общее с группой Z.ai стенда шлюза** вынесено из `verify-llm-zai.mjs` в новый модуль `apps/orchestrator/scripts/verify-llm-zai-setup.mjs`, оба стенда его импортируют: окружение роли без прокси (`zaiDirectEnvironment`), команда оператора на прямом пути (`zaiOperator`, `zaiLogin`), включение строк (`switchOnZai`), очистка домашнего каталога OpenCode (`resetOpencodeHome`), константы бэкенда, модели, профиля и адреса. Запуск хода и проверки исполнителя в модуль не вошли: стенд шлюза выдаёт ключи через worker `core` и ведёт синтетический сервер MCP, стенд контента — продуктовый допуск и настоящую роль.

**Наблюдатели стенда** (`verify-agent-content-role.mjs`). Узел перед `/mcp` теперь записывает версию протокола MCP: из `params.protocolVersion` запроса `initialize` и из заголовка `mcp-protocol-version` остальных запросов. Для `notifications/cancelled` он вызывает проверку стенда дважды — до того, как запрос уйдёт роли, и после её ответа; расхождение записывается нарушением, а `settled()` ждёт проверок, которые ещё идут. Учётные данные и ответы узлы по-прежнему не хранят, из аргументов — только название версии протокола из запроса `initialize` (до 64 символов).

### Что проверяет строка OpenCode

Три хода, каждый отдельной задачей на одном сайте, как у Codex и Kimi.

| № | Проверка | Итог |
| --- | --- | --- |
| 1 | `tools/list` роли принят CLI и объявлен провайдеру | роль ответила 200 на `initialize` и `tools/list`; версия MCP во всех запросах хода — `2025-11-25`; в каждом из четырёх запросов провайдеру объявлены `raditi_site_info`, `raditi_wp_rest`, `raditi_restore`; три вызова `wp_rest` приняты (200) |
| 2 | Одна строка журнала на повторённый ключ | одна строка `mcp_calls` (`ok`, привязана к назначению), один снимок, одна квитанция плагина, одна запись на сайт; ответы на запись и на её повтор, которые CLI передал модели, называют снимок этой строки (добавлено ревью) |
| 3 | `notifications/cancelled` не меняет журнал и не блокирует аренду | три уведомления, каждое принято (202); завершённые строки журнала до и после каждого совпадают; на одно из них роль ответила между ответами на запись и на её повтор, и повтор получил сохранённый ответ той же строки — дословно тот же текст, что и запись: объект, снимок строки, `updated` (сверка ответа добавлена ревью); аренда не называет незавершённой записи |
| 4 | Снимок раньше записи | в момент отправки записи на сайт снимок подтверждён и лежит в S3, запись допущена, аренда называет этот вызов; объект зашифрован и открывается в исходный текст |
| 5 | Новый текст на публичной странице | страница отдаёт новый текст, контакт посетителя вернулся из маркера; модель видела только маркер; ключа хода, токена MCP, пароля сайта и контакта нет в запросах провайдеру и событиях CLI |
| 6 | Вторая аренда не выдаётся | пока ход держит аренду, вторая не выдана; после закрытия ключ хода отозван |
| 7 | Запрещённый маршрут (`/wp/v2/comments/1`) | вызов дошёл до роли один раз и получил 400; строк журнала и снимка нет, запросов к сайту нет, страница не изменилась; ход завершился итогом за 2 секунды, код 0 |
| 8 | Запись без ключа идемпотентности | то же: один запрос, 400, ничего не записано, ход завершился |

Проверки стенда в целом: в S3 ровно три объекта снимка, во всём журнале три строки — по одной на правку; в журнале прокси стенда есть туннели к `chatgpt.com` и `api.kimi.ai` и нет ни одного к `api.z.ai`; ключей хода, токенов MCP, значений подписок, ключа плана и текста отказов синтетического Z.ai, пароля сайта и контактов нет в логах ролей и сервисов, аудите OpenBao и дампе PostgreSQL.

Для строк Codex и Kimi добавлено общее: аренда после хода правки не называет незавершённой записи; каждое `notifications/cancelled` принято, и журнал вокруг него сравнён (у Kimi в прогонах исполнителя их два или три в конце хода, в одном из прогонов ревью — одно; у Codex — ни одного). Запрещённый маршрут у Codex теперь обязан дойти до роли — раньше это только наблюдалось. После ревью у всех трёх строк сверяется и то, что роль ответила на запись и на её повтор: в выводах инструмента, которые CLI передал модели, оба ответа называют снимок строки журнала. Дословно текст сравнивается только у OpenCode: Kimi ставит перед текстом роли своё время вызова, Codex заворачивает его в вывод ячейки `exec`.

## Как CLI показывают модели отказ роли

Роль отвечает на вызов, не прошедший допуск, HTTP 400 с телом `{"jsonrpc":"2.0","id":2,"error":{"code":-32000,"message":"Invalid MCP request"}}`. Текст фиксированный: аргументов и содержимого сайта в нём нет. Что из этого получается у трёх CLI — измерено в каждом проходе, стенд печатает строками `OBSERVED`.

| CLI | Запросов к роли на один отклонённый вызов | Что получила модель | Что сообщил драйвер |
| --- | --- | --- | --- |
| OpenCode 1.18.34 | 1 | сообщение `role: tool` с текстом `Streamable HTTP error: Error POSTing to endpoint: {"jsonrpc":"2.0","id":2,"error":{"code":-32000,"message":"Invalid MCP request"}}` | `tool_call`: `raditi_wp_rest`, неуспех |
| Codex 0.158.0 | 1 | вывод ячейки `exec`: `Script completed`, затем результат инструмента с `isError: true` и текстом ``tool call error: tool call failed for `raditi/wp_rest` … Mcp error: -32000: Invalid MCP request`` | `tool_call`: `wp_rest`, неуспех |
| Kimi 2.1.1 | 3 при записи без ключа; 0 при запрещённом маршруте — CLI сам отклонил аргументы по схеме | `<system>ERROR: Tool execution failed.</system> Tool "mcp__raditi__wp_rest" failed: Streamable HTTP error: Error POSTing to endpoint: {…}`; при запрещённом маршруте — `Invalid args for tool "mcp__raditi__wp_rest": /route must match pattern …` | событий инструмента нет |

Что это значит для OpenCode:

- **Статуса HTTP модель не видит.** В тексте — слова клиента MCP и тело ответа роли дословно. Значит, всё, что роль напишет в теле отказа, дойдёт до модели как есть: сейчас это фиксированная фраза, и менять её можно только с этим в виду.
- **Запрещённый вызов и вызов с неверными аргументами неразличимы:** оба дают «Invalid MCP request». Что именно запрещено, модель из отказа не узнаёт.
- **Повторов нет:** один запрос к роли, один к провайдеру после него. Kimi на тот же отказ шлёт три запроса.
- **Подключение CLI к MCP после 400 живо.** Ход идёт дальше и кончается кодом 0 с итогом; признак «сервер недоступен», по которому обёртка драйвера обрывает ход, не срабатывает.
- **Схему аргументов CLI не проверяет.** Шаблон `route` из `tools/list` его не останавливает: вызов уходит роли. Для этого CLI, как и для Codex, допуск роли — единственная проверка маршрута.
- **В формате chat completions у вывода инструмента нет признака ошибки.** Модель отличает отказ от ответа только по тексту; драйвер — по событию CLI (`tool_call` с `ok: false`).

Решение N21 — отвечать ли на отклонённый `tools/call` результатом инструмента с `isError` вместо HTTP 400 — этот инкремент не принимает. Наблюдение для него: при нынешнем отказе OpenCode ведёт себя лучше Kimi (один запрос вместо трёх), а текст для модели одинаково неинформативен у всех трёх.

**Вторая форма отказа — результат инструмента с `isError` — стендом не исполняется.** Вызов, который прошёл допуск, роль отклоняет иначе: HTTP 200 и результат инструмента с `isError: true`, в тексте которого один код — `MCP_CALL_IN_FLIGHT`, `CONTENT_CONFLICT`, `MCP_APPROVAL_REQUIRED`, `CONTENT_PRIVACY_*`, `CONTENT_OBJECT_UNAVAILABLE`, `CONTENT_CALL_REJECTED` (`mcp-content.controller.ts`). Именно её N21 взвешивает против HTTP 400, а ходы стенда дают только принятые вызовы и отказы допуска. Как закреплённый OpenCode показывает её модели, измерило ревью — вне стенда: тот же стенд запускался из временного файла, который в своём процессе подменял один вызов; файлы дерева не менялись. У Codex и Kimi это не измерялось.

- **Чтение страницы, которой нет** (`/wp/v2/pages/999999` вместо запрещённого маршрута; два независимых прогона). Запрос к роли один, роль один раз спросила сайт и ответила HTTP 200 с `isError` и текстом `{"code":"CONTENT_OBJECT_UNAVAILABLE"}`. Модель получила сообщение `role: tool` ровно с этим текстом: ни слов клиента MCP, ни конверта JSON-RPC. Событие CLI — `tool_use` со `status: error`; драйвер сообщил `tool_call`: `raditi_wp_rest`, неуспех — то же событие, что при HTTP 400. За вызовом пришло `notifications/cancelled` (202). Запросов провайдеру два, ход завершился итогом, код 0, stderr пуст.
- **Отказ на повтор записи.** В одном прогоне повтор с тем же ключом идемпотентности ушёл роли с изменённым телом, и роль ответила `{"code":"CONTENT_CALL_REJECTED"}`; в другом ответ роли на повтор заменён на `{"code":"MCP_CALL_IN_FLIGHT"}`. В обоих модель получила код третьим выводом инструмента, и ход завершился с кодом 0; во втором записаны и события драйвера — два успешных вызова и один неуспешный. Второй записи на сайт и второй строки журнала нет.

По строкам исполняемого файла 1.18.34 клиент MCP внутри CLI на `isError` бросает ошибку, текст которой собран из текстовых частей результата. Вывод для N21: в этой форме модель видит код роли без слов транспорта, запрос один, драйвер так же сообщает неуспех. Стендом это не закреплено — сценария, где роль отвечает `isError`, у строки OpenCode нет (раздел «Что осталось открытым»).

## Наблюдения

1. **Запросы OpenCode к роли за ход правки:** `initialize` 200 (обёртка драйвера проверяет токен до запуска CLI), `initialize` 200 (сам CLI), `notifications/initialized` 202, `GET /mcp` 405, `tools/list` 200, затем трижды `tools/call` 200 и `notifications/cancelled` 202. Порядок одинаков во всех проходах. Это порядок ответов роли: узел стенда записывает запрос, когда ответ на него закончился.
2. **Версии MCP у трёх CLI:** OpenCode и Kimi называют `2025-11-25`, Codex 0.158.0 — `2025-06-18`. Роль отвечает каждому. Проверяется версия только у OpenCode: её требует план.
3. **`notifications/cancelled` у OpenCode — про уже отвеченный запрос.** Это запись разведки (`docs/research/2026-10-opencode-glm/opencode-protocol.md`): уведомление несёт `requestId` вызова и причину `AbortError: The operation was aborted.` — CLI отменяет свой запрос после того, как получил ответ. Стенд этого сам не сверяет: номеров запросов его узел не хранит. Роль работает без сессий (`statefulMode: false`), уведомление приходит отдельным запросом, и стенд видит, что по нему ничего не меняется.
4. **Ход с отказом у OpenCode идёт 2 секунды** против 0–1 у Codex и Kimi. Отдельно это время стенд не разбирал; повторов и пауз в ходе нет — запрос к роли один, запросов провайдеру два.
5. **У Kimi уведомлений в конце хода от одного до трёх.** В четырнадцати прогонах исполнителя со строкой Kimi узел стенда записал два в одиннадцати и три — в трёх; в одном из прогонов ревью — одно. Причина, скорее всего, та, что названа в отчёте 33: запрос CLI, который вышел сразу после уведомления, обрывается до ответа, и узел его ответом не считает. Стенд принимает оба исхода: сравнивается каждое уведомление, на которое роль ответила. Поэтому строка `OBSERVED` о запросах Kimi в двух проходах подряд может отличаться.
6. **Сигнал после последней проверки.** Первый прогон с SIGTERM послал сигнал по таймеру, и тот пришёл, когда все проверки уже прошли и шла уборка: стенд доубрал за собой и вышел с кодом 0 и строкой «passed». Так стенд вёл себя и раньше; остатков нет. Засчитан прогон, где сигнал послан по строке лога внутри строки OpenCode.

## Решения

1. **Перезапуск роли `llm`, а не второй процесс.** Путь к провайдерам — свойство процесса роли: с заданным прокси через него идёт всё, без прокси роль сама соединяется только с Z.ai. У `sandbox-gw` один адрес LLM, а роль в продукте — одна реплика. Второй процесс рядом потребовал бы второго адреса и второго `sandbox-gw` и дал бы конфигурацию, которой в продукте нет: два процесса роли над одной базой с отдельной памятью проб и пауз. Перезапуск — то, что уже делает стенд шлюза (G4). Каким путём идти, говорит строка таблицы (`path`); скрипт запускает роль заново, когда путь следующей строки другой. Каким путём роль пошла, стенд читает из её строки `llm_egress_path` при старте, а в конце сверяет журнал прокси.
2. **Сценарии фейка названы, а не собраны из `rounds` в стенде.** Причина — маркер контакта из разговора (раздел «Синтетический провайдер»). Заодно строка таблицы ходов задаёт сценарий всем трём CLI одними параметрами.
3. **Имя функции фейк берёт из запроса, точное имя закрепляет стенд.** Фейк ищет объявленную функцию `…_wp_rest` и отказывает, если её нет или их две. Точные имена `raditi_*` сверяет стенд — в каждом запросе провайдеру.
4. **Окна аккаунта Z.ai пишет проба.** Строкам Codex и Kimi стенд по-прежнему пишет окна сам: их пробы — дело стенда шлюза. Клиент проб у издателя им не мешает: свежий снимок пробу не вызывает.
5. **Сравнение журнала вокруг уведомления — прямое.** Косвенное доказательство было (строка `ok`, одна запись на сайт, одна квитанция), но план требует «не меняет журнал» буквально. Что повтор получил сохранённый ответ, в это доказательство до ревью не входило: стенд видел у повтора только HTTP 200 (раздел «Что изменило ревью»). Сравниваются только завершённые строки: вызов, начатый после уведомления, вправе добавить свою.
6. **Уровень рассуждения строки OpenCode — `high`:** это уровень профиля `standard`. Его ставит шлюз из ключа хода; драйвер только отказывается запускаться без уровня.
7. **Предел времени workflow оставлен 45 минут.** С двумя строками прогон `agent-content.yml` на GitHub занял 5 минут 8 секунд и 5 минут 16 секунд (09.10.2026, черновой PR #3) и один раз 21 минуту (05.10.2026). Третья строка вместе с импортом ключа плана и перезапуском роли добавила на этой машине около десяти секунд: 66 секунд против 54–57.
8. **Сигнал для проверки уборки — по строке лога, а не по таймеру:** стенд идёт 66 секунд, строка OpenCode — считаные секунды в его конце, и таймер промахнулся с первой попытки.

## Что осталось открытым

- **N21.** Как отвечать на вызов, не прошедший допуск: HTTP 400, как сейчас, или результат инструмента с `isError`. Наблюдения трёх CLI для HTTP 400 записаны выше; вторая форма измерена только у OpenCode и только вне стенда.
- **Результат инструмента с `isError` ни один стенд не показывает ни одному CLI.** Так роль отдаёт каждый отказ журнала контента — конфликт, запись в полёте, нужное согласование, отказ маскирования, недоступный объект. В `verify:opencode`, стендах супервизора и шлюза и в записях разведки у сервера MCP только `isError: false`; здесь — принятые вызовы и отказы допуска (400). Третий ход с отказом — чтение страницы, которой нет, — в G5 не добавлен: план его не называет. По умолчанию его добавляет N21, когда закрепит форму отказа, либо N19, чей `MCP_APPROVAL_REQUIRED` — ответ того же вида.
- **Workflow со строкой OpenCode на GitHub не выполнялся.** На x64 эта строка впервые пойдёт в `agent-content.yml` после отправки ветки. Там же впервые исполнится перезапуск роли на Linux, где узел стенда перед `/mcp` слушает адрес моста Docker.
- **Модель сценарная.** Настоящая модель может вызвать инструмент иначе, повторить его или не вызвать вовсе; повтор без двойной правки и отказ запрещённому детерминированы только на сценарной модели. Живой проход — G6.
- **Отменённый вызов в полёте не проверялся.** В ходах стенда CLI ничего не обрывает, а о каком вызове каждое уведомление, стенд не записывает: узел перед `/mcp` не хранит номеров запросов, и то, что OpenCode шлёт уведомление о вызове, на который уже получил ответ, взято из записи разведки. Что CLI шлёт, когда сам обрывает ожидание инструмента (в конфигурации драйвера — 60 секунд), не измерялось; обрыв записи посередине остаётся за сценариями потери ответа `verify:mcp-content`, где CLI нет.
- **Сигнал после последней проверки** даёт код 0 (наблюдение 6).
- **Pull-раннер под gVisor** для этого стенда не делался, как и раньше: план требует его перед закрытием N12 и N17.
- **Предупреждение `pg`** в процессе роли `mcp` (отчёт 30, наблюдение 6) не разбиралось.

## Что изменило ревью

Ревью 09.10.2026 читало незакоммиченный дифф инкремента тремя взглядами — стенд, безопасность продукта, сверка с планом и spec — и запускало тот же стенд из временных файлов, которые в своём процессе подменяли один вызов или печатали ответы роли; файлы дерева при этом не менялись. Каждое замечание пытался опровергнуть второй читатель; ниже — то, что устояло. Продуктовый код ревью не меняло: правки — в скрипте ходов стенда, тестах и документах.

Исправлено:

- **Стенд печатал «повтор записи получил сохранённый ответ», а знал о повторе только HTTP 200** (замечание всех трёх взглядов). Ход правки судил о трёх вызовах по паре «инструмент, статус», а узлы стенда ответов не хранят. Но с HTTP 200 роль отвечает и на вызов, который отклоняет после допуска: это результат инструмента с `isError` и одним кодом. Утверждение было верным — ответы роли на запись и на её повтор совпадали, — но стенд не заметил бы, перестань оно быть верным. Теперь ход правки читает то, что CLI передал модели в последнем запросе провайдеру (`replayProblem` в `verify-agent-content-turns.mjs`). У всех трёх строк ответы на запись и на её повтор должны называть снимок строки журнала: его называет только сохранённый ответ записи. У строки OpenCode, который передаёт модели текст роли как есть, ответ на повтор должен дословно совпасть с ответом на запись и состоять ровно из объекта, снимка строки и `updated: true`. У Codex и Kimi дословной сверки нет: в их выводах перед текстом роли стоит время вызова, у каждого вызова своё.
- **Слова строки PASS, README стенда и отчёта приведены к тому, что стенд видит.** Узел перед `/mcp` записывает запрос, когда ответ роли на него закончился, и номеров запросов не хранит. Поэтому «повтор отправлен после уведомления» заменено на «роль ответила на уведомление между ответами на запись и на её повтор», а слова «о первой записи» и «о завершённых вызовах» убраны: о каком вызове уведомление, известно из записи разведки, а не из стенда. Записывать номера запросов в узле ревью не стало — это новое наблюдение, а не исправление; оно понадобится тому, кто будет проверять отмену вызова в полёте.
- **Происхождение сборки orchestrator.** Отчёт называл сборку всех прогонов сборкой руководителя от 18:25; на деле `dist` в 19:32 пересобрал регрессионный `pnpm verify:mcp-content` самого инкремента (раздел «Проверки», последний абзац). Исходники между сборками не менялись.
- **Вторая форма отказа роли — результат инструмента с `isError`** — записана в разделе «Как CLI показывают модели отказ роли» как измеренная вне стенда, а в «Что осталось открытым» — как не закреплённая ни одним стендом. Отчёт предлагал N21 одно наблюдение HTTP 400.

Что и как краснело:

- **Сам дефект — прогоном стенда.** Временный файл запускает стенд дерева как есть и в своём процессе дописывает один пробел в тело повтора записи OpenCode на пути от узла стенда к роли; роль отвечает на такой повтор HTTP 200, `isError`, `{"code":"CONTENT_CALL_REJECTED"}`. До правки (20:51:58–20:53:09): строка «…the repeat of the write got the stored answer, the lease is not blocked», 27 проверок, код 0. После правки (20:59:41–21:00:43): код 1, «failed at: OpenCode content edit», в закрытой диагностике — «the repeat of the write was not answered from the journal row»; уборка полная.
- **Новый тест `verify-agent-content-turns.test.mjs`** написан до кода: на заглушке, которая всегда отвечает «всё в порядке», — 2 красных из 2. Случаи теста — три формы вывода инструмента, как их записали синтетические провайдеры стенда (текст роли как есть, время вызова перед ним, ячейка `exec` вокруг него), с отказом на повтор, отказом на запись, ответом чужой строки и лишним или недостающим выводом. Тест же поймал ошибку самой правки — повторное имя переменной в ходе — до первого прогона стенда.
- **Контракт стенда** (`agent-content.test.mjs`, тест «the edit turn reads what the write and its repeat were answered…») — до кода: 1 красный из 9. Он держит порядок: сначала сверка ответов, потом строка PASS о них.
- На записях прогонов ревью новая проверка даёт: три строки без подмены — замечаний нет; дословная сверка проходит только у OpenCode; прогон с отказом на повтор — «the repeat of the write was not answered from the journal row».

Что ревью оставило открытым — это не дефекты инкремента, а его границы:

- **Третьего хода с отказом — результатом инструмента с `isError` — в стенде нет** («Что осталось открытым»): план G5 его не называет, по умолчанию его добавляет N21 либо N19.
- **События драйвера в ходе правки не сверяются.** Ревью предлагало требовать, чтобы ни один `tool_call` хода не был неуспешным. Отказ на повтор ловит сверка ответов, а увидеть вторую проверку красной без снятия первой было нечем; она не добавлена.
- **О каком вызове `notifications/cancelled`, стенд не записывает** (выше).

## Уборка

Стенды убирают за собой сами: после двух прогонов подряд и прогона с SIGTERM на конечном дереве, как и после прогонов до них, в обоих демонах нет ни одного контейнера, сети или тома стенда. За время работы в списках появились два контейнера других сессий — `raditi-m512-…` и `raditi-db-verify-…` (чужой `pnpm verify:db`); они не тронуты. Каталогов `raditi-p3verify-*`, `raditi-site-verify-*` и `raditi-agent-content-*` во временном каталоге после прогона с SIGTERM нет, процессов ролей нет. Одноразовая PostgreSQL инкремента (`raditi-oc-g4-pg-g5-…`) удалена.

После прогонов на дереве с правками ревью — двух подряд, с подменой повтора записи и с SIGTERM — списки контейнеров, сетей и томов обоих демонов до и после каждого совпали; каталогов стенда во временном каталоге и процессов ролей нет, закрытая диагностика прогона с подменой удалена.

Образы не удалялись и не пересобирались: `raditi-oc-*:g3`, `raditi-p3verify-runtime:b13`, `raditi-p3verify-cli:b13`, `raditi-p3verify-guard:b13`, `raditi-p3verify-orchestrator:b14`.
