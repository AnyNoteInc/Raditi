# P2: локальный Docker и супервизор хода

Проверено 26.09.2026 на macOS, Node 26.10.0, pnpm 12.6, Docker Desktop 29.6.2, runtime `runc`. Это проверка локальной части P2. Сеть под gVisor проверена 27.09.2026 в Linux-ВМ (раздел «Гейт 1»), пилотный pull-runner и восстановление незавершённого exec — там же 27.09.2026 (раздел «Гейты 2 и 3»). Открытыми остаются только интеграция следующих задач (P3–P12) и проверки на целевой платформе (M10) — раздел «Незакрытые гейты».

## Реализовано

- `packages/sandbox-providers`: настоящий Docker provider через локальный Unix socket. Образ закреплён digest, uid 10001, read-only rootfs, cap-drop ALL, no-new-privileges, ограниченные tmpfs/CPU/RAM/PID, без host mounts и опубликованных портов. Создание, поиск, повторное подключение и удаление сверяют точные ID, метки, эпоху и настройки контейнера.
- До передачи любых данных задачи доверенный bootstrap один раз выполняется как uid 0 без дополнительных capabilities и сохраняет PID/starttime служебного процесса в отдельном root-owned tmpfs. Файл доступен агенту только для чтения; подмена argv или pid не делает процесс исключением для quiesce. Агент и все обычные exec работают как uid 10001.
- Обёртка exec сохраняет ограниченные бинарные stdout/stderr, отдельные байтовые оффсеты и результат. Команды, stdin и файлы проходят через exec; archive API и `docker cp` не используются. Проверены timeout, cancel, потомок с `setsid`, quiesce и переподключение новым экземпляром provider. Deadline exec хранится также в неизменяемых аргументах Docker Exec.
- Для `runc`: internal bridge на попытку, отдельный служебный сетевой фильтр, шлюз с точным списком маршрутов. Разрешены POST `/v1/responses`, POST `/v1/chat/completions`, GET/POST/DELETE `/mcp`. DNS, прямой доступ к адресам, произвольные Host/пути/методы, redirect, CONNECT и upgrade не разрешены. Служебные контейнеры имеют собственные PID-пространства; агент не получает `NET_ADMIN`.
- Для `runsc`: песочница подключается к сети попытки напрямую, а доверенный помощник на хосте закрывает мост попытки правилом `INPUT DROP`. Подробности и проверка — раздел «Гейт 1».
- Отдельный deadline watchdog работает без процесса core, удаляет просроченные контейнеры и ресурсы шлюза. Есть отдельный compose-файл; сокет Docker подключён только к этому доверенному сервису. Watchdog необходимо запустить до приёма ходов.
- `PostgresSiteLeaseStore`: атомарный захват, эпоха, продление, проверка и освобождение по полному fence; неоднозначная запись удерживает аренду. Сроки проверяются по часам PostgreSQL, включая повторную проверку после ожидания row lock. Проверены 12 конкурентных претендентов и восстановление только точной удержанной эпохи.
- Аренда супервизора и recovery выдаётся один раз на лимит операции плюс 90 секунд: 60 секунд на начатую команду публикации и 30 секунд на завершение. Она не продлевается: после падения core сайт освобождается по этому сроку. Во время хода супервизор раз в 30 секунд сверяет fence и прерывает ход только при явной потере аренды; ошибка чтения PostgreSQL даёт предупреждение в лог (не чаще раза в минуту), а к истечению аренды ход остановит локальный таймер. Лимит отсчитывается от запроса аренды, поэтому медленная выдача его не продлевает. Вызовы S3 и `GitProvider` тоже не могут задержать ход дольше лимита. Регрессии проверяют push в последний момент, в том числе при выдаче аренды через 40 секунд; неоднозначный результат удерживает аренду.
- Доверенные Git-команды запускает отдельный Node-супервизор с абсолютным монотонным deadline: timeout сохраняется при SIGSTOP core, разрыв IPC при SIGKILL core завершает группу native-процесса. Восемь регрессий проверяют эту границу и точность двоичного ввода/вывода; переполнение вывода имеет свой код `PROCESS_OUTPUT_LIMIT`, отличный от сбоя команды. CAS защищает Git-ref, но не является общей транзакцией PostgreSQL и Git; неоднозначный ответ сервера требует проверки кандидата и recovery.
- `TurnSupervisor`: аренда → чистая рабочая копия → restore → подготовка драйвера → exec → quiesce → кандидат Git → снимок → удаление контейнера → fenced push. Нормализованные события и фазы пишутся в `TaskEvent` под проверкой аренды; известные секреты не принимаются в журнал. SQL-схема не менялась.
- Доверенная публикация: Git bundle без credentials передаётся в контейнер через stdin; на хосте отдельный чистый index, ограничение патча/архивов/объектов, запрет опасных путей и типов файлов, gitleaks, детерминированный коммит от бота, push с проверкой исходного SHA. Настройки и hooks `.git` агента не используются на хосте.
- Снимок содержит полный патч кандидата, его `headSha` и пустой `untracked`. Опциональные `git.publication.taskId/committedAt` защищены AAD; старые снимки P1 сохраняют прежний формат AAD. Capture сравнивает с доверенным исходным SHA, включая самостоятельно закоммиченные агентом изменения.
- `TurnPublicationRecovery.recover({ heldFence, snapshot, workspace })` восстанавливает публикацию только из завершённого проверенного снимка. Новая эпоха, удаление старых контейнеров по точным ID, повторная сборка и проверка SHA, fenced CAS push, журнал и освобождение аренды. Неоднозначность снова удерживает аренду.

### Доработки после ревью (27.09.2026)

Ошибки проверки метаданных и архивов снимка теперь `SNAPSHOT_NOT_WRITTEN`: ничего не записано, аренда освобождается. Метаданные снимка, известные до хода, включая версию драйвера, проверяются схемой манифеста до аренды. Брошенное супервизором сохранение получает сигнал отмены и не пишет резервирование и манифест. `protectedPaths` стали обязательными. Слишком большой патч кандидата — `PUBLICATION_TOO_LARGE` (413); лимит патча общий со снимком. Файлы `prepare` проверяет `preparedRunSchema`: только `/agent-home` и tmpfs секретов. Периодическая сверка аренды не прерывает ход из-за ошибки чтения. `renew` оставлен для выкладки и отката в P12.

Третий раунд. Перед записью вывода агента в журнал аренда сверяется так же мягко, как периодически: ход прерывается только при явной потере, а сама вставка в журнал проверяет fence; недоступная база — `run_failed`, вставка без своей аренды — `lease_lost` (`LEASE_LOST`). Ключ LiteLLM, токен MCP и значения файлов секретов не допускаются в файлы драйвера и в env до записи в песочницу; секреты хода ограничены размером своего tmpfs (одна константа в domain и в Docker provider). Все лимиты размера и числа в публикации и снимке — 413: `PUBLICATION_TOO_LARGE`, `SNAPSHOT_TOO_LARGE`, `REPOSITORY_TOO_LARGE`; коды ходов и снимков получили русские тексты для клиента. Прерванное до резервирования сохранение больше не удерживает сайт: супервизор ждёт его ответа до 90 секунд (не дольше аренды) и при `SNAPSHOT_NOT_WRITTEN` освобождает аренду. Занятый сайт — `SITE_BUSY`. `withTimeout` перенесён в domain, в `observability` остался один `throttledLogger`.

Четвёртый раунд. 20 минут — лимит всего хода вместе с публикацией: exec агента заканчивается на `TURN_FINALIZE_RESERVE_MS` (3 минуты) раньше, а контейнер живёт весь лимит. Агент, закончивший за 10 секунд до своего срока, всё равно проходит capture, сохранение снимка и push; если к запуску агента осталось меньше резерва, агент не запускается (`timeout`). Списки файлов git читаются с пределом по байтам, выведенным из лимита числа файлов, поэтому большой сайт получает 413, а не 502. Лимит изменений агента за ход (10 000 файлов, патч и новые вместе) отделён от лимита базового дерева сайта (100 000). Сбои вывода агента, `prepare`, служебных команд песочницы и совпадение нового файла с файлом репозитория больше не 400: это `TURN_OUTPUT_REJECTED`, `TURN_OUTPUT_TOO_LARGE` (413), `DRIVER_PREPARE_INVALID` и `SANDBOX_COMMAND_FAILED` с русскими текстами. Учётные данные хода не допускаются и в argv команды драйвера, и в env контейнера (проверка до аренды). Capture ищет их точные значения в именах и содержимом файлов обоих архивов снимка и в патче: находка — `SNAPSHOT_NOT_WRITTEN` с причиной `snapshot_credential` в журнале, ничего не записано, аренда освобождается. Сбой удержания аренды для разбора пишется в лог (только эпоха и фаза). Сайт, удержанный для оператора, отвечает `SITE_HELD`, а не `SITE_BUSY`. Помощники разбора env в domain внесены в spec §6 и CLAUDE.md.

Пятый раунд. Кандидат публикации больше не запускает процессы на каждый файл: новые файлы пишутся в объекты одним `hash-object --stdin-paths`, изменённое содержимое читается несколькими `cat-file --batch` (до 32 МиБ за чтение), gitleaks — один `gitleaks dir` на кандидат по закрытому каталогу с копиями, которые хост нумерует сам. Настоящий gitleaks 8.30.1 проверен на тех же образцах через stdin и через `dir`: исход одинаковый — оба пропускают файл, чьи первые байты похожи на архив, PDF или программу (закрыто в шестом раунде); `.gitleaksignore` проверяемого каталога gitleaks учитывает, поэтому имена агента в каталог не попадают. Замер на Apple M1 Max с синтетическим репозиторием (файлы около 500 байт): прежний код — 467 секунд на 1 000 новых файлов и 399 секунд на 1 000 изменённых; новый — 2 секунды на 1 000, 10,6 и 9,4 секунды на 10 000 новых и изменённых, push — 1,4 секунды, три двоичных файла по 32 МиБ — 2,9 секунды. Лимит в 10 000 файлов оставлен: он с запасом укладывается в резерв в 3 минуты. Отказы работы агента больше не 400 и не 403: особый файл, ссылка или setuid при capture, путь с `-` или `.git`, испорченный двоичный патч — `TURN_OUTPUT_REJECTED`; пути CI и `protectedPaths`, ссылки и смена прав — `PUBLICATION_FORBIDDEN`; находка gitleaks — `PUBLICATION_SECRET`; ссылка или сабмодуль в самом репозитории сайта — `REPOSITORY_UNSUPPORTED` (422), у всех свои русские тексты. Кандидат повторяет точный поиск учётных данных хода в каждом изменённом файле целиком, двоичные тоже: находка — `SNAPSHOT_NOT_WRITTEN` с причиной `snapshot_credential`. Если последнюю запись журнала сделать не удалось, сайт удерживается только после начала сохранения снимка или push; иначе аренда освобождается, а при недоступной базе истекает по сроку. Вебхук ЮKassa без `Content-Length` читает тело потоком и прекращает чтение после 64 КиБ. `pnpm gates` проходит: 1599 тестов, 61 проверка PostgreSQL/Docker пропущена; orchestrator с `DATABASE_URL` — 391 из 391. `verify:publication` с настоящим gitleaks 8.30.1 проходит; синтетический токен теперь ищется одним запуском среди 51 нового файла, рядом с собственным `.gitleaksignore` агента.

Шестой раунд. Находкой gitleaks считается только код выхода 99 (`--exit-code=99`): кодом 1 он отвечает и на собственные ошибки, например на испорченный конфиг, — это `GIT_OPERATION_FAILED`, а не «нашёлся секрет». Каждую копию для проверки хост начинает заголовком картинки GIF: иначе текст, начатый с `%PDF-` или с `ustar` на смещении 257, gitleaks пропускал, а перевод строки лишь сдвигал сигнатуру; заголовок получают и двоичные копии, чтобы один неверный байт UTF-8 не прятал текст. Новый файл, который `update-index` молча не внёс в индекс (`git~1`, `.git.`, потоки NTFS), и отказ самого `git apply` по патчу агента — `TURN_OUTPUT_REJECTED`; такие имена отклоняет и `isPublicationPath`. Поле `credentials` публикации обязательное, повтор из снимка передаёт пустой список явно. Под `runsc` повторное принятие песочницы заново ставит правило на хосте (установка идемпотентна) и проверяет его; сбой помощника — ошибка инфраструктуры, а не «песочницы нет»; неверная настройка демона (`runtimeType`, `options`, опасные `runtimeArgs`) — 502. Docker-интеграция в Linux-ВМ повторена: 10/10 под `runsc` (с удалением правила на хосте и его возвратом) и 10/10 под `runc`; `verify:publication` с настоящим gitleaks 8.30.1 проходит, включая текст за сигнатурами PDF и tar, неверный байт UTF-8 и испорченный конфиг сканера.

Собрать локальные образы из корня репозитория:

```sh
docker build --target runtime -f infra/sandbox/Dockerfile -t raditi-sandbox-runtime:p2 .
docker build --target gateway -f infra/sandbox/Dockerfile -t raditi-sandbox-gateway:p2 .
docker build --target network-guard -f infra/sandbox/Dockerfile -t raditi-sandbox-guard:p2 .
docker build --target watchdog -f infra/sandbox/Dockerfile -t raditi-sandbox-watchdog:p2 .
```

Закрепить именно результаты сборки, затем запустить реальные Docker-тесты:

```sh
export RADITI_DOCKER_TEST_IMAGE="$(docker image inspect raditi-sandbox-runtime:p2 --format '{{index .RepoDigests 0}}')"
export SANDBOX_GATEWAY_IMAGE="$(docker image inspect raditi-sandbox-gateway:p2 --format '{{index .RepoDigests 0}}')"
export SANDBOX_NETWORK_GUARD_IMAGE="$(docker image inspect raditi-sandbox-guard:p2 --format '{{index .RepoDigests 0}}')"
pnpm --filter @repo/sandbox-providers exec vitest run src/docker.integration.test.ts src/gateway/gateway.integration.test.ts
pnpm test:infra
```

На Docker с классическим image store локальная сборка может не иметь `RepoDigests`: сначала загрузить образ в локальный реестр и получить digest оттуда. Не заменять его изменяемым тегом в `SandboxSpec`.

Проверены десять Docker-тестов: девять для provider/runtime и один для полной сети. Watchdog проверен и отдельным Node-процессом, и реально собранным контейнером compose. Временные контейнеры, сети, записи тестов и запущенные для проверки сервисы удаляются/останавливаются; собранные локальные образы оставлены для повтора.

Запуск независимого watchdog:

```sh
export SANDBOX_WATCHDOG_IMAGE="$(docker image inspect raditi-sandbox-watchdog:p2 --format '{{index .RepoDigests 0}}')"
docker compose --env-file .env -f infra/sandbox/docker-compose.yml up -d
```

`SANDBOX_DOCKER_SOCKET` по умолчанию `/var/run/docker.sock`. TCP и `DOCKER_HOST` не используются. Настройки шлюза — единая группа: `SANDBOX_GATEWAY_IMAGE`, `SANDBOX_NETWORK_GUARD_IMAGE`, `SANDBOX_LLM_UPSTREAM`, `SANDBOX_MCP_UPSTREAM`. Последние два значения — доверенные HTTP(S) origins без credentials, пути и query; внутри шлюза они должны быть достижимы через его служебную сеть. При отсутствии группы разрешён только `network: none`.

Проверен настоящий Gitea registry: отдельная синтетическая учётная запись и token только на время проверки, push → удаление локальной ссылки → pull по точному digest → сверка. Учётная запись, пакет и локальные registry-ссылки удалены. Повтор при запущенной локальной Gitea:

```sh
node packages/sandbox-providers/scripts/verify-registry.mjs raditi-sandbox-runtime:p2 <gitea-container-id> http://127.0.0.1:3300
```

Для проверки доверенной публикации нужен gitleaks на доверенном хосте. Использован официальный v8.30.1 для darwin_arm64, архив SHA-256 `b40ab0ae55c505963e365f271a8d3846efbc170aa17f2607f13df610a9aeb6a5`, сверенный с checksums релиза. Проверены обычная публикация, реальный синтетический секрет, попытка подавления через `gitleaks:allow` и отказ без раскрытия секрета. Скрипт повторной проверки — `apps/orchestrator/scripts/verify-publication.mjs`; пути задаются `P2_GITLEAKS_BINARY` и `P2_SANDBOX_IMAGE`, сначала нужен build orchestrator. Он работает с временным локальным bare-репозиторием и Docker, не с репозиторием пользователя.

## Гейт 1: сеть под gVisor (27.09.2026)

Проверено в Linux-ВМ Colima (Ubuntu 24.04, ядро 6.8, aarch64, Docker 29.5.2, gVisor release-20260921.0, systrap, backend iptables — nft).

Сначала воспроизведена проблема: под `runsc` фильтр в общем сетевом пространстве имён не действует — из песочницы открывался sshd хоста ВМ через адрес моста. Затем принят дизайн из spec §8 «Сеть»:

- сеть попытки без адреса хоста: мост `rdx<12 hex>`, `gateway_mode=isolated`; провайдер проверяет по факту, что в `IPAM.Config` нет `Gateway`, иначе удаляет попытку;
- к сети подключены ровно шлюз и сторона песочницы; третий участник делает песочницу непризнанной — трафик внутри моста не фильтруется;
- под `runsc` песочница подключается к сети напрямую, фильтр-контейнер не создаётся; `host-firewall.mjs` (runc, сеть хоста, только `NET_ADMIN`, без сокета Docker) ставит и проверяет `INPUT -i <мост> -j DROP` для IPv4 и IPv6 до запуска кода; правила мостов, которых уже нет, снимаются при каждой установке и освобождении, просроченные контейнеры помощника удаляет watchdog;
- при каждом повторном принятии песочницы (`get`, recovery) правило ставится заново и проверяется; сбой помощника — ошибка инфраструктуры, а не пропавшая песочница; гонка двух уборок и сбой уборки чужих правил не ломают ход и освобождение (сбой уборки — предупреждение процесса `RADITI_SANDBOX_FIREWALL_SWEEP`);
- `runsc` зарегистрирован в демоне путём к бинарю `runsc`, без `runtimeType` и `options` (так работает shim `containerd-shim-runsc-v1` с флагами в toml); `runtimeArgs` не могут включать `net-raw`, `allow-flag-override` и `network`, кроме `sandbox`; неверная настройка демона — 502, а не ошибка ввода.

Отдельный агент атаковал этот дизайн из песочницы (uid 10001, cap-drop ALL): адрес моста, хост ВМ и Lima, `docker0`, metadata `169.254.169.254`, интернет, DNS `127.0.0.11`, broadcast и multicast, соседняя попытка, IPv6, маршруты и raw-сокеты, сокет Docker, а также обходы HTTP-шлюза (Host, absolute-form, CONNECT, upgrade, redirect, smuggling, CRLF). Выхода, кроме `sandbox-gw:8080`, нет. Мост без адреса хоста и правило INPUT закрывают хост каждый сам по себе; правила переживают перезапуск dockerd; при остановке шлюза связность пропадает без утечки.

Попутно найдено: gVisor, в отличие от Linux, открывает симлинк на каталог даже с `O_DIRECTORY | O_NOFOLLOW`. Через подменённый каталог помощник файловых операций мог прочитать `/run/raditi/secrets`. Теперь каталог принимается, только если имя само является им (тот же inode, не симлинк); интеграционный тест это проверяет под обоими runtime.

Повтор (образы собираются в демоне ВМ; из macOS ВМ видит хост по `192.168.5.2`):

export RADITI_DOCKER_TEST_UPSTREAM_HOST=192.168.5.2
# RADITI_DOCKER_TEST_IMAGE, SANDBOX_GATEWAY_IMAGE, SANDBOX_NETWORK_GUARD_IMAGE — digest из демона ВМ

Результат: 10/10 под `runsc` и 10/10 под `runc` в той же ВМ. Сетевая проба ходит с двумя попытками по 6 секунд: у netstack gVisor первый пакет к живому соседу может задержаться на ARP. Позитивный контроль — порт 8080 шлюза.

## Гейты 2 и 3: раннер пилота и восстановление незавершённого хода (27.09.2026)

Реализовано по плану гейтов (spec §8 «Раннер на песочной ВМ» и «Восстановление незавершённого хода», §14, §15, §19, §20):

- Роль `runner` (`apps/orchestrator/src/runner`) — Nest application context без HTTP-сервера. Она сама забирает ходы у `core` long-poll'ом и ведёт Docker ВМ через локальный сокет. Доступов к PostgreSQL, Redis, Vault, S3 и Git у неё нет; в проде раннер запускается только со своими переменными (`RUNNER_*`, `SANDBOX_*`, `APP_ENV`, `NODE_ENV`, `ORCHESTRATOR_ROLES`) и системными. Токен ВМ читается из файла, `core` хранит только его SHA-256 (`RUNNER_TOKENS`), ротация — `scripts/runner-token.mjs`.
- API раннеров в `core` (`src/runner-api`) слушает отдельный порт `RUNNER_API_PORT`: опрос, отчёты, git bundle, ключ данных, загрузка кандидата, reconcile. Каждый запрос проходит цепочку токен → раннер → сессия → эпоха. Отказы — 409 `FENCE_SUPERSEDED`, `LEASE_LOST`, `SESSION_RETIRED` (с 28.09.2026), `CURSOR_MISMATCH`.
- `turn_assignments` (новая миграция): назначение открывается до контейнера, раннер забирает его через `FOR UPDATE SKIP LOCKED`. `ObjectStorage.presign` работает только для `raditi-sessions`: GET частей хода n−1 и create-only PUT `home.tar.zst` хода n, подписанные под адрес S3, каким его видит ВМ (`S3_RUNNER_ENDPOINT`).
- Супервизор работает через порт `TurnExecutor`: `LocalTurnExecutor` для PoC и `RemoteTurnExecutor` для раннера, код супервизора один. Весь набор его тестов гоняется через оба исполнителя.
- `TurnExecRecovery` при старте и раз в 30 секунд разбирает незавершённые назначения по таблице фаз из spec §8. Принятие контейнера для работы и для удаления разделены: сайт удерживается, пока не удалён контейнер хода, найденный по меткам.

### Проверка на Linux-ВМ под gVisor

`apps/orchestrator/scripts/verify-runner.mjs` (`pnpm --filter orchestrator verify:runner`). `core` — отдельный процесс Node на macOS (`verify-runner-core.mjs`): супервизор, API раннеров и recovery над локальными PostgreSQL, SeaweedFS и OpenBao, собранные из тех же классов, что подключит P12. Раннер — роль `runner` в ВМ Colima из раздела «Гейт 1». Он запущен с флагами сервиса compose (профиль `runner`): root без capabilities, read-only, без портов, сокет Docker ВМ, токен root 0400 в томе только для чтения. Сборка оркестратора смонтирована только для чтения, `.env` закрыт `/dev/null`. Проверка убеждается, что в окружении раннера нет `DATABASE_URL`, `REDIS_URL`, `VAULT_*` и `S3_*`. Песочницы работают под `runsc` с сетью `gateway`: шлюз, мост без адреса хоста, правило `INPUT DROP` на хосте ВМ. ВМ видит loopback macOS по адресу 192.168.5.2 (сеть Lima), поэтому API раннеров и SeaweedFS остаются на 127.0.0.1, а `S3_RUNNER_ENDPOINT=http://192.168.5.2:8333`.

Модели нет. Синтетический агент печатает JSONL codex, который разбирает настоящий `parseCodexEvent`; `prepare` и argv драйвера синтетические (настоящие — P4). Агент пишет сессию в home, меняет отслеживаемый файл, создаёт новый и может ждать у «ворот» — файла, который проверка создаёт через `docker exec`.

1. **Два полных хода одной сессии.** Ход 2 восстанавливает снимок хода 1 по presigned GET. Его агент сам проверяет, что сессия и правка хода 1 на месте, и иначе завершается с ошибкой. Home каждого хода раннер шифрует ключом хода и кладёт create-only presigned PUT. Кандидат, gitleaks 8.30.1, снимок и push выполняет `core`, во временный локальный bare-репозиторий. Проверены ветка и дерево публикации, home снимка хода 2 (сессии обоих ходов), запись `restored` с сессией драйвера, удаление контейнера и освобождение аренды.
2. **`kill -9` `core` во время вывода агента.** Агент и раннер продолжают работать. Новый `core` при старте запускает recovery: она забирает ход под новой эпохой и переподключает тот же exec с курсора журнала. Каждое событие попадает в журнал ровно один раз, ход опубликован. Отчёт с прежней эпохой получает 409 `FENCE_SUPERSEDED` с новым fence, другая сессия раннера — 409 `SESSION_RETIRED`, закрытое назначение — 409 `LEASE_LOST`. Ключи хода остались у раннера и ему не отправлялись; `core` взял их у источника учётных данных для своей проверки вывода (до 28.09.2026 источник не вызывался, а вывод в `core` проверялся по пустому списку).
3. **`kill -9` раннера (SIGKILL init контейнера) в той же точке при живом `core`.** Новая сессия раннера снимает прежнюю, и супервизор отказывается от хода. Удалить контейнер без раннера он не может, поэтому удерживает сайт (`recovery{destroy_failed}`). Recovery забирает ход, удаляет контейнер через новую сессию и только затем освобождает сайт. Назначение закрыто как `lost`, ничего не опубликовано; отчёт старой сессии — `SESSION_RETIRED` (до 28.09.2026 — `LEASE_LOST`).
4. **`kill -9` и `core`, и раннера.** Recovery возобновляет ход на новой сессии раннера (принятие контейнера из Docker, повторная установка правила хоста) с ключами из источника учётных данных и публикует его. Отчёт старой сессии — `SESSION_RETIRED` (до 28.09.2026 — `LEASE_LOST`), прежней эпохи — `FENCE_SUPERSEDED`.
5. **Отмена, пока раннер создаёт контейнер** (добавлен 28.09.2026, раздел «Правила аренды хода»). Раннер забрал `prepare`, и сразу приходит отмена. Супервизор пишет `vacating` и аренду не освобождает. Поздний `created` приводит к удалению контейнера через раннер. Только после `destroyed` идут `failed`, освобождение аренды и назначение `failed`. Пока контейнер виден в Docker, аренда за ходом; ничего не опубликовано.
6. **`kill -9` `core` сразу после записи `checkpointed`, раннер тоже убит и не возвращается** (добавлен 28.09.2026, решение 4). Новый `core` удерживает сайт на эпохе хода и один раз пишет `recovery{awaiting_runner}`. Четыре прохода recovery ничего не меняют: попытка не засчитана, запись под новой эпохой не появляется, ветка не опубликована, контейнер на месте. Раннер вернулся — recovery забирает ход под новой эпохой и удаляет контейнер через раннер по ID из журнала. Только потом идут `publishing` и `publication_recovered`; попытка засчитана одна, сайт свободен.

После сценариев проверка убеждается, что в ВМ не осталось контейнеров хода, шлюзов, сетей, помощников и правил хоста. Затем удаляются строки базы, объекты S3, ключ Transit и том с токеном. Клоны публикации, которые оставляет убитый `core`, лежат во временном каталоге проверки (`TMPDIR` процессов `core`) и удаляются вместе с ним. Если прогон упал, логи `core` и раннера и журнал ходов (`journal.json`) остаются во временном каталоге, путь печатается.

Результат: все сценарии проходят, полный прогон — около 90 секунд. Сценарии с возобновлением (2 и 4) прошли 95 раз из 97. Дважды, в первых прогонах, возобновлённый ход закончился `failed`: раннер ответил `SANDBOX_COMMAND_FAILED` на `quiesce` после вывода агента. Контейнер удалён, сайт освобождён, ничего не опубликовано — отказ безопасный, но ход потерян. Причина — время старта процесса под gVisor, а не нагрузка; разобрано 28.09.2026 и исправлено (список ниже).

Облачная ВМ x86_64 и файрвол ВМ (с неё — только `core`, S3, реестр, NTP) — M10; API раннеров — HTTP на частный IP app-ВМ с токеном, привязанным к адресу ВМ (решение владельца от 27.09.2026, spec §19), шифрование при необходимости — WireGuard. В сети Lima ВМ достаёт до любого порта loopback macOS, в том числе до PostgreSQL; эту границу закроет файрвол.

Раннер — та же сборка `dist` в контейнере из стадии `base` (Node 26.10 и tini). `APP_ENV=development`: в проде `http://` к `core` допускается только на частный IP (spec §19).

Найдено проверкой и исправлено, с тестами:

- Следующий ход на том же раннере ждал до 25 секунд. Опрос, ждавший в `core`, нёс число свободных мест, посчитанное, пока прошлый ход ещё занимал место. Теперь освобождённое место сразу отправляет новый опрос (с 28.09.2026 — не прерывая прежний, раздел ниже). Хаб отвечает сразу и на опрос, прерванный, пока он забирал назначения. Полный прогон сократился примерно со 165 до 85–95 секунд.
- `core`, который останавливается, отвечал раннеру 500. Сессию, снятую при закрытии, он мог назвать `LEASE_LOST`, и раннер бы перезапустился. Теперь ответ — 503 `UNAVAILABLE`, и раннер повторяет запрос к следующему `core`.
- Песочница, которая загружалась в момент перевода часов ВМ назад, не проходила ни одного `quiesce`. gVisor считает время старта процесса в `/proc/<pid>/stat` от времени своей загрузки по часам реального времени. Keepalive стартует вскоре после загрузки, и шаг часов назад в этом промежутке давал отрицательное значение (−5…−16). Bootstrap записывал его как есть, а `quiesce` принимал только неотрицательное число и сразу завершался с ошибкой. Часы ВМ Colima переводят назад сразу два источника времени — синхронизация Lima (`SyncTime`, 0,1–0,2 с) и systemd-timesyncd; в спокойном режиме это около 0,11 с каждые 20 секунд. По журналу ВМ, который потом ротировался и не сохранился, оба сбоя пришлись на песочницы, запущенные незадолго до такого шага; в тот час шаги шли чаще, чем позже, поэтому следующие 70 прогонов прошли. Отдельная проверка это подтверждает: из 20 возобновлённых ходов со старым помощником упали ровно те 4, у которых время старта было отрицательным. Загрузка CPU без шагов часов сбой не воспроизводит. Теперь время старта — целое со знаком: его только сравнивают. Bootstrap не записывает значение, которое `quiesce` не примет (`runtime.test.ts`). Воспроизведение: часы ВМ переводятся на ±0,19 с каждые 0,25 с, в ВМ четыре контейнера нагружают CPU. До исправления не прошли 14 из 40 возобновлённых ходов, после — 0 из 80. Для прода (M10) на ВМ нужен один источник времени с плавной подстройкой: chrony с `makestep` только при загрузке.

## Правила аренды хода (28.09.2026)

Решения владельца от 27.09.2026 (spec §8 «Время и сбои», «Восстановление незавершённого хода»). Инвариант: аренду освобождают раньше срока только с доказательством, что контейнера хода нет и не будет, иначе она истекает сама — не раньше, чем watchdog удалил контейнер.

- **Срок контейнера не позже срока хода.** `core` пересчитывает остаток `prepare` и `adopt` для работы в момент выдачи опросом и не выдаёт команду, чей срок вышел. Раннер отсчитывает остаток от отправки опроса, провайдер Docker — от начала `create`, и после срока контейнер не создаёт.
- **`vacating`.** Владелец отказался от хода после выдачи `prepare`, а контейнера ещё нет. Тогда аренда не освобождается и не удерживается, в журнале — `vacating{reason}`, назначение открыто. Доказательства: `prepare` не ушёл из `core` (`abandon`, снятие из очереди, отказ при выдаче), подтверждённое удаление известного контейнера, `failed{absent}` раннера. `absent` раннер шлёт, только если создание не начиналось или провайдер пометил ошибку `leftNothing`. Поздний контейнер удаляется сразу, затем `failed`, освобождение и `finish`. Если сайт удержан на эпохе хода, назначение закрывает восстановление.
- **Восстановление хода без контейнера** (последний шаг `leased`) только удаляет: попытки не считаются, драйвер не нужен. Назначение, не забранное раннером, закрывается `abandon`. Контейнер из журнала или найденный по меткам удаляется по ID, если раннер на связи; иначе — ожидание без удержания до `deadline_at + grace`. После этого удержание снимается, а назначение закрывается и тогда, когда аренду занял другой владелец. Итог — `failed` после `vacating`, иначе `lost`.
- **Публикация после подтверждённого удаления.** Режимы: `confirmed` (`destroyed`, `publishing`), `adopt` (контейнер журнала по ID, затем по меткам) и `expired` (после `deadline_at + grace`, `destroyed{timeout}`). Раннер не на связи — нет сессии или она молчит дольше `pollHoldMs + 15 с` — значит удержание и одна запись `recovery{awaiting_runner}` без попытки. Попытка засчитывается после удаления контейнеров. Чужая идентичность контейнера — оператор. Бюджет восстановления публикации — 6 минут.
- **Хаб.** Выдача считается один раз. Команда снимается из очереди по `commandId`. Старая эпоха не снимает назначение новой. `destroyed` для контейнера, которого `core` не знал, не доказательство, и новая эпоха спрашивает раннер снова. Опрос, чьё соединение закрылось, пока шёл захват, команд не забирает, а сервер возвращает в очередь ответ опроса, который уже некому отдать.
- **Освобождение эпохи и удержания-сироты** (28.09.2026, ревью). Recovery освобождает эпоху одним запросом (`free`), без промежуточного удержания. Незабранное назначение после падения `core` закрывается `lost`.

## Доработки раннера после spec-check (28.09.2026)

Замечания проверки spec-check гейтов 2 и 3 и находки разбора сбоя после возобновления. Замечания 1 и 3 закрыл раздел «Правила аренды хода»; замечание про HTTP на всех интерфейсах — выкладка app-ВМ (порт опубликован только на `APP_PRIVATE_IP`).

- **Окружение раннера — белый список.** Раньше в проде отклонялись только `DATABASE_URL`, `REDIS_URL`, `VAULT_*` и `S3_*`, а `GITEA_TOKEN`, ключи моделей и секреты web проходили. Теперь разрешены только `APP_ENV`, `NODE_ENV`, `ORCHESTRATOR_ROLES`, `RUNNER_*`, `SANDBOX_*` и системные переменные (`PATH`, `HOME`, `HOSTNAME`, `TZ`, язык, `NODE_VERSION`). Любая другая непустая переменная — отказ старта с её именем, без значения.
- **Presigned-ссылки только по https в проде.** `core` не стартует, если адрес, под который он подписывает ссылки (`S3_RUNNER_ENDPOINT`, иначе `S3_ENDPOINT`), не `https://`. Раннер и раньше принимал ссылки только на `https://`-origin `RUNNER_S3_ORIGIN`.
- **Адреса в плане хода.** `turnPlanSchema` отклоняет `llm.baseUrl` и `mcp.url` с логином, паролем, query-строкой или фрагментом: ключ внутри адреса иначе попал бы в `turn_assignments.plan`.
- **`SESSION_RETIRED`.** Отчёт снятой сессии раньше получал `LEASE_LOST`: зомби убивал exec и удалял контейнер, который могла уже принять новая сессия. Теперь `core` отвечает `SESSION_RETIRED` снятой сессии, сессии, брошенной по молчанию, любой не текущей сессии раннера и сессии, которой не принадлежит назначение этого раннера. Раннер останавливается, не трогая контейнеров. `LEASE_LOST` теперь значит только одно: аренды этого хода больше нет.
- **Ключи после рестарта `core`.** Recovery хода, чей раннер пережил `core`, ключей не брал, и `core` проверял вывод агента по пустому списку. Теперь recovery всегда берёт их у `TurnCredentialSource.recover` и проверяет ими вывод и кандидата в `core`. Раннеру, который их держит, они не отправляются (`TurnAdoptInput.holdsCredentials`). Нет ключей — отказ от хода.
- **Итог в записи `failed`.** Если после отказа recovery от хода (`lost`) не прошло обновление назначения, следующий проход закрывал его как `failed`. Теперь запись `failed` несёт `outcome`, и назначение закрывается с ним.
- **Ответ опроса не теряется.** Освободившееся место прерывало ждущий опрос. Если `core` уже записал ответ, он считал команды доставленными (событие `finish`, без возврата в очередь), а раннер ответ отбрасывал. Тест в `sandbox-runner.test.ts` («carries out what a poll brought…») воспроизводил потерю на прежнем коде. Теперь новый опрос уходит, не прерывая прежний: хаб по поколению сессии сразу отвечает прежнему, и раннер выполняет всё, что тот принёс.
- **Повторный attach закрывает прежний handle exec.** После возобновления в той же сессии прежний читатель вывода продолжал запускать `read-exec` в песочнице до следующего вывода агента, а таймер прежнего handle оставался взведённым до срока exec. Теперь `DockerSandbox.attach` закрывает handle, который заменяет: его вывод обрывается при следующем чтении, таймер снят. Тест в `docker.test.ts` на прежнем коде зависал.
- **Один раннер на демон Docker.** Сверка раннера удаляла любой контейнер хода, которым не владеет его `core`, поэтому два раннера на одном демоне удаляли контейнеры друг друга — например, две проверки на общей ВМ. В проде на песочной ВМ один раннер. Кроме того, теперь раннер помечает свои контейнеры id из токена ВМ (`io.raditi.runner`, вне проверяемой идентичности песочницы) и берёт в инвентарь и сверку только их. `verify:runner` запускает раннер с уникальным id на каждый прогон. Контейнеры без метки (локальный исполнитель `core`, прежние версии) раннер не видит, их удаляет watchdog по сроку.
- **Токены раннеров.** `runner-token issue|hash … --ip <частный IP ВМ>` печатает запись `id:sha256@ip`, которую принимает `core` в проде; имя и публичный адрес отклоняются. Выпуск на ВМ, ротация, отзыв и смена адреса — `infra/app/README.md`, «Токены раннеров».
- **Места раннера.** `core` доверяет числу свободных мест из опроса, пока `RUNNER_MAX_TURNS=1` (spec §8); свой лимит мест на раннер — этап 2.
- **Нестабильные тесты.** Тест health в `core.module.test.ts` иногда получал 401 вместо 503. Причина: supertest слушал все адреса, а подключался к 127.0.0.1. На macOS сервер другого тестового файла, привязанный к 127.0.0.1 на том же временном порту, отвечал вместо него; это был API раннеров, отсюда 401. Теперь приложения Nest в тестах слушают 127.0.0.1 сами. Тесты, которые тратят секунды CPU (граница распаковки zstd, надзор за процессами, проверка настроек web), получили свой таймаут 30 секунд, общий по умолчанию остался 5 секунд.

Результат 28.09.2026:
- `pnpm gates` проходит: 2099 тестов, 75 пропущено (PostgreSQL и Docker без opt-in).
- С `DATABASE_URL`: orchestrator — 795 из 795, `@repo/db` — 96 из 96.
- `verify:runner` в ВМ Colima под gVisor прошёл дважды подряд, все пять сценариев. Раннер запускался с уникальным id и меткой контейнеров. Старая сессия получала `SESSION_RETIRED`, `core` брал ключи из источника и в сценарии 2.
