# P6: доступ к MCP по токену хода

01.10.2026 реализован первый локальный блок P6: проверка токена на каждом MCP-запросе и инструмент `site_info`. Он возвращает зарегистрированный публичный адрес и стек назначенного сайта. Изменяющие HTTP-инструменты, откат и согласование ещё не подключены; P6 остаётся открытым. Следующий локальный блок — [основа снимков и журнала](25-p6-content-journal.md).

По указанию владельца работа продолжается с доступной локальной подпиской Codex. Этот блок проверяется на синтетических данных без обращений к моделям. Приёмка настоящего Kimi в P3 остаётся отдельным открытым пунктом.

## Токен и границы доступа

`GatewayTurnCredentials.issue` создаёт случайный токен `mcp_` с 32 байтами в hex и сохраняет его только в write-once Vault `turns/` вместе с ключом модели. В той же SQL-транзакции, которая допускает ключ модели, в `llm_keys.mcp_token_hash` записывается SHA-256 токена MCP. Миграция проверяет формат хеша и его уникальность. Сроки и отзыв у пары общие; роль `mcp` читает хеш из базы и не получает доступ к Vault `turns/` или `subs/`.

`recover` сверяет оба хеша для новых ключей. Старые строки с `mcp_token_hash=NULL` сохраняют прежнее восстановление ключа модели, но к MCP не допускаются. Автоматического переноса живых старых ключей нет: MCP доступен новым ходам после обновления `core` и миграции.

Проверка на каждом запросе требует:

- текущую попытку задачи, совпадающие сайт и рабочее пространство;
- то же назначение хода: задача, номер хода, сессия и исходная эпоха;
- незавершённое назначение с будущим deadline;
- действующую аренду этого сайта, принадлежащую задаче, с текущей эпохой назначения и операцией `turn`, без удержания оператором;
- активный сайт, незавершённую задачу, будущие `expires_at` и `valid_until`, отсутствие запроса отзыва и самого отзыва.

При смене эпохи токен закрыт, пока доверенное восстановление не перепривяжет назначение к новой аренде. Отзыв закрывает новые запросы сразу после сохранения `revoke_requested_at`, даже если удаление Vault ещё не закончено. Отдельная привязка к IP в MCP не добавлена; адрес раннера проверяет шлюз модели, а сеть MCP должна ограничиваться `sandbox-gw` при подключении инфраструктуры.

Сайт и задача берутся из базы. В запросе инструмента нельзя передать другой сайт; контекст хранится на исходном HTTP-запросе под Symbol, недоступным для JSON и заголовков.

## HTTP и инструмент

Раньше библиотека сама монтировала незащищённый маршрут. Теперь `/mcp` принадлежит Nest-контроллеру с guard; транспорт сам маршруты не добавляет. Проверка действует для initialize, списка и вызова инструментов, уведомлений, GET и DELETE. Инициализация не создаёт долгоживущую авторизованную сессию: состояние доступа перечитывается для каждого запроса.

Реализован Streamable HTTP с протоколом 2025 года (`legacy-only`, без серверных сессий). `tools/list` объявляет только `site_info` с пустыми аргументами и признаком чтения. Версии WordPress, темы, плагины и ключевые страницы пока не собираются. Ответ содержит только `{url, stack}`; доступов, внутренних идентификаторов, данных владельца и содержимого посетителей в нём нет.

Вход ограничен 100 КиБ JSON, глубиной 16 и 5 000 узлами. Пакетные запросы, ключи `__proto__`, `constructor`, `prototype`, неизвестные методы и инструменты, лишние аргументы `site_info`, повторные Authorization/Host/Origin/MCP-Protocol-Version, неизвестная версия протокола и дополнительные параметры маршрута отклоняются. Неизвестная `MCP-Protocol-Version` получает тот же ответ, что даёт SDK: 400, `id: null`, код `-32000`, текст `Bad Request: Unsupported protocol version (supported versions: …)`, без повтора присланного значения — так `server/discover` у Codex может откатиться к `initialize`. Неподдерживаемый HTTP-метод на `/mcp` — 405 с заголовком `Allow`; неподдерживаемые charset тела или `Content-Encoding` — 415; остальные ошибки клиента сохраняют свой 4xx с фиксированным текстом; 500 дают только ошибки сервера. Ошибки проверки доступа, параметров, сырого JSON и базы имеют фиксированные сообщения, не повторяющие входные значения. Ошибки разбора JSON также очищаются для вариантов `/mcp/` и `/MCP`, которые маршрутизатор может распознать до проверки точного пути. Ответы получают `Cache-Control: no-store`.

`MCP_ALLOWED_HOSTS` — точные имена или IP upstream роли `mcp`, без портов, схемы и wildcard. `sandbox-gw` заменяет Host именем своего MCP upstream, поэтому в контейнерной сети это, например, `mcp`, а на отдельной машине — её частный адрес. Вне production по умолчанию разрешены `localhost`, `127.0.0.1`, `[::1]` и `host.docker.internal` — Host, который `sandbox-gw` отправляет на Docker Desktop; те же имена в `.env.example`. Локальный Origin допустим. В production список обязателен и любой Origin отклоняется. Запуск роли в production теперь возможен с этой настройкой; подключение её сети и сервиса в Compose ещё впереди.

## Журнал и health

Добавлено после ревью 02–04.10.2026. Отказы допуска MCP (уровень warn) и неожиданные 500 (уровень error) пишутся в журнал не чаще раза в минуту на источник — только класс ошибки и коды: код Prisma, SQLSTATE, вид адаптера, отсутствующая таблица или колонка. Содержимого запроса в строках нет. Неоднозначная или не проходящая схему строка допуска — 503 с кодом журнала `MCP_ACCESS_SCOPE_INVALID`, а не молчаливый 401. Журналирование `mcp-nest` намеренно выключено: оно писало бы тексты ошибок инструментов.

`/health` роли `mcp` выполняет сам запрос допуска с заведомо невыданным токеном. База без миграций P6 даёт `degraded`. Поэтому `pnpm e2e` (smoke «orchestrator MCP starts and reports healthy») требует мигрированной базы.

Форматы токена MCP и ключа хода и их sha256-хеш роль `mcp` берёт из `llm/turn-key.ts` (`MCP_TOKEN_PATTERN`, `turnKeyHash`, `TURN_KEY_IN_TEXT`); собственных копий нет.

## Проверки

Числа ниже — прогон 01.10.2026. Итог 04.10.2026: `pnpm verify:db` — 2 139 тестов orchestrator без пропусков и 320 тестов базы ([отчёт ревью](29-review-2026-10.md)).

Прицельные тесты проверяют настоящий HTTP-сервер и библиотечный транспорт, хеш вместо сырого токена в SQL, отсутствие обхода guard, повторную авторизацию, ограничения входа и ошибки без отражения секретов. Интеграционный набор на PostgreSQL проверяет допуск и отказы при истечении срока, отзыве, завершении хода, смене сессии/эпохи/попытки, потере аренды, удержании оператором, паузе сайта и отмене задачи. Отдельный HTTP-вызов использует настоящий SQL-поиск и перестаёт допускаться сразу после отзыва.

Финальный проход `pnpm verify:db` прошёл: 228 тестов `@repo/db`, 1 408 тестов orchestrator, включая 17 интеграционных проверок MCP, и 394 проверки общего пользователя/обновления базы. Все миграции применились, различий между схемой и базой нет, временные контейнер и данные удалены. Лог — `/tmp/raditi-p6-db-verification.log`. Отдельный прицельный проход без базы: 77 пройденных, 17 интеграционных пропущены; они выполнены в `verify:db`. Typecheck, линтер затронутого кода, сборка orchestrator, архитектурные слои, окружение и форматирование кода прошли.

Повтор:

```sh
pnpm verify:db
pnpm --filter orchestrator exec vitest run src/mcp src/llm/turn-credentials.test.ts src/config/config.test.ts src/roles.test.ts
pnpm --filter orchestrator typecheck
pnpm --filter orchestrator build
pnpm check-env
pnpm check-architecture
```

`verify:db` создаёт собственную PostgreSQL в локальном Docker, применяет миграции, сверяет схему и запускает наборы базы и orchestrator с интеграционными тестами. Рабочий `.env` не читается, свои контейнер и данные удаляются после прохода. Здесь нет WordPress, настоящего CLI через MCP или полного продукта от задания до отката.
