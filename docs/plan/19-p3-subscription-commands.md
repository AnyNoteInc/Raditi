# P3 B12 — операторские команды подписок

Дата: 30.09.2026. B12 реализован и проверен локально: вход, повторный вход и вывод аккаунта через команды `orchestrator`. Следующий этап основного сценария — B13, проверка шлюза с CLI и локальными провайдерами.

Порядок ниже приведён к коду после ревью 02–04.10.2026: вывод требует `--label`, появилась отмена запроса вывода `--cancel`, вход сначала проверяет токен writer и метку. Что изменилось — в разделе «Изменения после ревью».

## Окружение и права

Команды не запускают приложение Nest и не загружают `.env` автоматически. Оператор явно задаёт окружение процесса:

| Переменная | Для чего нужна |
| --- | --- |
| `APP_ENV` | `development`, `test` или `production` |
| `VAULT_ADDR` | Origin OpenBao/Vault без пути, query и учётных данных; в production — HTTPS |
| `DATABASE_URL` | Для `subscriptions:login` и `subscriptions:retire` |
| `LLM_EGRESS_PROXY_URL` | HTTPS origin прокси для входа |
| `LLM_EGRESS_CA_FILE`, `LLM_EGRESS_CLIENT_CERT_FILE`, `LLM_EGRESS_CLIENT_KEY_FILE` | Абсолютные пути к CA и клиентскому сертификату mTLS |

Этого окружения достаточно и в production: других переменных команды не требуют. Список оболочек команды берут из реестра `llmBackends` пакета `@repo/llm-backends`. Тексты отказов выводятся по-русски.

Вход сначала проверяет канал выхода, токен writer и метку — до того, как провайдер что-либо выдаст: недействительный токен или занятая метка иначе обнаружились бы только после 15-минутного device-flow. Device-flow Codex и проверка ключа Kimi идут через существующий mTLS CONNECT-транспорт с точными разрешёнными маршрутами; прямого выхода при ошибке настройки нет. Замены адресов провайдеров на loopback HTTPS и `LLM_UPSTREAM_CA_FILE` разрешены только вне production для проверок.

`--vault-token-file`, `--turns-token-file` и `--out` принимают абсолютные пути. Секрет читается только из обычного файла текущего пользователя без прав группы и остальных; симлинк и файл больше 8192 байт отвергаются. Новые файлы токенов создаются с правами `0400`, без перезаписи существующего пути. Чтение также допускает закрытый файл с правами `0600`. Содержимое — одна строка печатных ASCII-символов; завершающий перевод строки допустим.

Права разделены:

- `subscriptions-writer`: запись `subs/data/*` и чтение metadata ради CAS. Данные подписки обратно не читаются.
- `subscriptions-admin`: уничтожение всех версий через удаление metadata; данных подписки и ключей хода эта политика не читает.
- `core-turns`: отдельный токен для раннего отзыва ключей хода при компрометации. Токен admin не заменяет его.

## Короткоживущий токен оператора в dev

```sh
pnpm --filter orchestrator subscriptions:token -- --policy writer --out /absolute/private/subscriptions-writer.token
pnpm --filter orchestrator subscriptions:token -- --policy admin --out /absolute/private/subscriptions-admin.token
```

Эта команда доступна только при `APP_ENV=development` или `test` и числовом loopback `VAULT_ADDR`: `127.0.0.1` или `[::1]`. `localhost`, удалённый Vault и production для неё запрещены. Токен dev-root поступает через stdin либо скрытый ввод в интерактивном терминале; аргумента для его значения нет.

Выпускается только выбранная политика, без `default` и унаследованных политик root. Срок и максимальный срок — 15 минут, продление запрещено. Команда проверяет эти свойства ответа и сохраняет токен в новый закрытый файл; в stdout попадает только подтверждение записи. В production токен оператора получают через штатный вход Vault с MFA; этот вход относится к P7/M10.

## Новый аккаунт

Codex:

```sh
pnpm --filter orchestrator subscriptions:login -- --backend openai-chatgpt --label codex-test-a --paid-until 2026-10-30 --vault-token-file /absolute/private/subscriptions-writer.token
```

`--label` — одна строка до 255 символов без управляющих символов Unicode (класс Cc, включая C1 U+0080–U+009F); правило — `subscriptionLabelSchema` в `subscriptions/login.ts`.

Команда требует интерактивный stdin и открывает управляющий `/dev/tty`. Только туда выводятся фиксированный адрес `https://auth.openai.com/codex/device` и код подтверждения; обычные stdout/stderr и журнал их не получают. Перенаправление stdout не превращает код в запись журнала. Контейнер, `auth.json` и существующие файлы входа CLI не используются.

Оператор подтверждает вход в браузере. Поллинг соблюдает интервал провайдера, весь device-flow ограничен 15 минутами, отдельный HTTP-запрос — 20 секундами. План и внешний идентификатор берутся через адаптер из полученных учётных данных; `--plan` не может подменить известный провайдеру план. Неясный результат обмена кода не вызывает автоматического повторного обмена. Срок входа и Ctrl-C обрывают только опрос: уже отправленный обмен кода доводится до ответа (до 20 секунд). Если провайдер выдал учётные данные, а сохранить их не удалось, команда отзывает их у провайдера и сообщает, удался ли отзыв.

Kimi:

```sh
pnpm --filter orchestrator subscriptions:login -- --backend kimi-code --label kimi-test-a --plan kimi-code --paid-until 2026-10-30 --vault-token-file /absolute/private/subscriptions-writer.token
```

API-ключ вводится без эха либо передаётся одной строкой через stdin. При вводе из pipe команда ждёт EOF, отвергает дополнительные строки и ограничивает размер 8192 байтами. Скрытый ввод ограничен двумя минутами; при отмене, ошибке или разрыве терминала восстанавливаются режим ввода и его обработчики. Значение ключа не передаётся аргументом команды и не печатается.

Адаптер проверяет ключ через `GET /coding/v1/usages`. Импорт разрешён только при результате `ok`; неизвестный результат, ошибка авторизации или недоступный канал не создают аккаунт. Для нового Kimi `--plan` обязателен: текущий проверочный маршрут не возвращает подтверждённое название плана. `kimi-code` в примере — операторская метка плана, а не результат его определения провайдером.

Для нового аккаунта сначала атомарно создаются `credential_refs` и выключенная строка `subscription_accounts` с `health='needs_relogin'`, причиной `import_pending` и версией 0. Затем writer сохраняет общий конверт `{credential: <JSON>}` по пути `subs/<backend>/<accountId>` с `cas=0`. Подтверждённая запись обновляет версии аккаунта и ссылки, сроки токена и `health='ok'`. Идентификаторы установки и устройства генерируются один раз и сохраняются в БД; имя устройства — 12 случайных шестнадцатеричных цифр на аккаунт, без названия платформы. Секреты остаются в Vault и памяти процесса.

Успешная команда печатает только `accountId`, `backend`, `credentialVersion` и `enabled`. Аккаунт остаётся выключенным. Начальная одновременность — Codex: 1 ход / 2 запроса, Kimi: 2 хода / 3 запроса.

До ручного включения оператор проверяет:

1. Успешный вход, согласованные версии и отсутствие `import_pending`/`relogin_pending`.
2. Настройки аккаунта из [чек-листа проекта §6.3](../research/2026-09-subscriptions/p3-design.md#63-чек-лист-152-фз-и-аккаунтов): обучение, автодокупка и дополнительный расход выключены; требуемые подтверждения сохранены; аккаунт используется только пулом.
3. `paid_until`, план, статус, лимиты одновременности и устойчивую идентичность устройства.
4. Доступную модель и профиль класса, резерв токенов, действующую учётную ставку и ручные выключатели провайдера/профиля. Одного включения аккаунта для выдачи ключей недостаточно.
5. Для реальных данных — действующую запись `cross_border_clearances`; синтетическая локальная проверка этот гейт не закрывает.

Отдельной команды включения в B12 нет: настройка каталога и ручных флагов остаётся доверенной операторской работой с БД.

## Повторный вход и частичный сбой

```sh
pnpm --filter orchestrator subscriptions:login -- --backend openai-chatgpt --relogin <accountId> --vault-token-file /absolute/private/subscriptions-writer.token
pnpm --filter orchestrator subscriptions:login -- --backend kimi-code --relogin <accountId> --vault-token-file /absolute/private/subscriptions-writer.token
```

Здесь `<accountId>` заменяется полным UUID аккаунта из результата входа или безопасного сообщения об ошибке. Повторный вход не принимает `--label`, `--plan` или `--paid-until`.

Операция берёт тот же session advisory lock по аккаунту, что обновитель B10. Существующий `client_identity` сохраняется. Учётные данные другого внешнего аккаунта Codex отвергаются до записи Vault: его нужно импортировать отдельно. Аккаунт с запрошенным выводом, отозванными учётными данными или статусом `retired` повторно войти не может. Тот же аккаунт ChatGPT или ту же метку после вывода можно импортировать снова — новой строкой: уникальность метки и пары (провайдер, внешний ID) действует только среди невыведенных аккаунтов (миграция `20261002100000`).

CAS берётся из metadata Vault; writer не читает предыдущий секрет. Удалённая или уничтоженная запись не восстанавливается. Отсутствующая запись допускает `cas=0` только у незавершённого нового импорта с версией 0. Перед записью сохраняется `needs_relogin/relogin_pending`: процесс, умерший между Vault и БД, оставляет аккаунт закрытым для работы.

После подтверждённого CAS SQL-финализация повторяется до трёх раз в текущем процессе. Потерянный ответ COMMIT распознаётся по согласованным версиям и состоянию. Успешный повторный вход сбрасывает `health`, причину и поля обновления, записывает новые сроки и план из свежих учётных данных. Ручные `enabled`/`status`, ярлык, дата оплаты, идентификаторы устройства и лимиты одновременности сохраняются; выключенный или `banned` аккаунт автоматически не включается.

Если команда остановилась после частичной записи, сохраните указанный UUID и выполните свежий `--relogin` с тем же аккаунтом. Неясная запись Vault автоматически не повторяется; metadata служит только для следующего CAS. B12 не обещает автоматическое восстановление такой операции таймером B10: это особенно важно для выключенных аккаунтов и Kimi. Не убирайте `import_pending`/`relogin_pending` вручную ради включения аккаунта.

## Штатный и аварийный вывод

Запрос штатного вывода:

```sh
pnpm --filter orchestrator subscriptions:retire -- --account <accountId> --label <метка>
```

`--label` подтверждает, что UUID принадлежит нужному аккаунту: значение сравнивается с сохранённой меткой как есть (1–255 символов, `retirementLabelSchema` в `subscriptions/retire.ts`). Правило здесь мягче, чем при входе, чтобы аккаунт со старой меткой можно было вывести. При несовпадении — отказ «Метка не совпадает с аккаунтом».

Команда под общим транзакционным замком пула сохраняет `retire_requested_at` до любых обращений к Vault. Новые ключи на аккаунт больше не выдаются, включая уже привязанные задачи. Действующие ключи и `recover` могут завершить ход; команда сообщает текущий этап и возвращается.

Для завершения должны работать фоновые процессы `core` и `llm`:

1. Минутный сборщик `core` ждёт истечения/отзыва активных ключей и закрытия открытых `llm_calls`, затем выключает аккаунт.
2. Минутный таймер `llm` на здоровом канале отзывает Codex refresh-токен и сохраняет `credentials_revoked_at`. Только роль `llm` читает токен подписки.
3. У Kimi автоматического отзыва через API нет: оператор отзывает ключ в консоли провайдера.

Повтор команды показывает текущий этап и продолжает незавершённые отзывы. Таймеры используют долговременные отметки и продолжают работу после рестарта.

Отмена запроса вывода, пока учётные данные не отозваны:

```sh
pnpm --filter orchestrator subscriptions:retire -- --account <accountId> --cancel
```

Команда снимает `retire_requested_at` только при `credentials_revoked_at IS NULL` и статусе не `retired`. Флаг `enabled` она не меняет: аккаунт, уже выключенный сборщиком, включает оператор.

При компрометации:

```sh
pnpm --filter orchestrator subscriptions:retire -- --account <accountId> --label <метка> --compromised --turns-token-file /absolute/private/core-turns.token
```

Допуск закрывается сразу: в SQL аккаунт выключается, ключи получают `revoke_requested_at`, затем вне SQL выполняется их отзыв. Отказ Vault не открывает допуск обратно. Токен `core-turns` предоставляется отдельно через закрытый файл; B12 не выпускает его командой `subscriptions:token`. Admin имеет права только на `subs/` и для этого шага не подходит.

Если показано ожидание отзыва ключей, повторите запрос с тем же `--turns-token-file`; `--compromised` допустимо повторять. Открытые вызовы всё равно должны завершиться или быть закрыты восстановлением до окончательного удаления.

Окончательное удаление Codex:

```sh
pnpm --filter orchestrator subscriptions:retire -- --account <accountId> --label <метка> --finalize --vault-token-file /absolute/private/subscriptions-admin.token
```

Для обычного Codex требуется подтверждённый `credentials_revoked_at` от роли `llm`; ручной флаг `--console-revoked` для него отвергается. Финализация проверяет закрытый допуск, отсутствие незавершённого отзыва ключей, активных ключей и открытых вызовов. Затем admin уничтожает metadata со всеми версиями `subs/<backend>/<accountId>`, и только после этого SQL записывает `status='retired'`.

Окончательное удаление Kimi после ручного отзыва:

```sh
pnpm --filter orchestrator subscriptions:retire -- --account <accountId> --label <метка> --finalize --console-revoked --vault-token-file /absolute/private/subscriptions-admin.token
```

`--console-revoked` — явное подтверждение уже выполненного действия в консоли. Отметка сохраняется до обращения к Vault, поэтому его временный отказ не требует повторного отзыва у провайдера. Если Vault уже удалил запись, а SQL-финализация не завершилась, повторите `--finalize`; удаление отсутствующей записи допускается. Завершённый `retired` возвращается идемпотентно. SQL-ссылка и история учёта сохраняются.

Исключение для Codex — незавершённый первый импорт: обе SQL-версии (`subscription_accounts.credential_version` и `credential_refs.key_version`) равны 0, `health='needs_relogin'`, причина — `import_pending` либо `relogin_pending` после неудачного повторного входа. Такой аккаунт сообщает `console_revocation_required`. Отсутствие записи в Vault не доказывает отсутствие действующего OAuth-входа: токены могли быть выданы до сбоя, а первая запись могла сохраниться без подтверждения. Оператор сначала отзывает созданные входы у провайдера, затем выполняет приведённую выше команду `--finalize --console-revoked`. Подтверждение сохраняется до уничтожения Vault; замок обновителя, проверки завершения ходов и ограничение точным путём аккаунта действуют и для этого случая. Без явного подтверждения запись не удаляется. У успешно импортированного Codex ручной флаг по-прежнему не заменяет отзыв ролью `llm`.

## Изменения после ревью 02–04.10.2026

- `subscriptions:retire` требует `--label` для запроса и для `--finalize`; добавлен `--cancel`.
- Вход: предварительная проверка токена writer и метки до device-flow; отзыв выданных учётных данных, если сохранение не удалось, с сообщением об исходе; обмен кода не обрывается сроком входа и Ctrl-C.
- Имя устройства — нейтральное, на аккаунт; у строк, созданных до 03.10.2026, прежнее общее имя `raditi` заменяется при повторном входе.
- Выведенная метка или внешний ID снова доступны для импорта; повторный вход в выведенную строку по-прежнему отвергается.
- Приглашение скрытого ввода проверяется на управляющие символы Unicode, а не только ASCII.
- Замок пула команды берут через `lockSubscriptionPool`, путь в Vault строят через `subscriptionCredentialPath` (`llm/turn-key.ts`).

Открыто, вопросы владельцу: можно ли оператору завершить вывод успешно импортированного Codex, когда автоматический отзыв невозможен (по умолчанию — нет, аккаунт остаётся в `provider_revocation_pending`); считать ли ответ провайдера «токен уже недействителен» подтверждённым отзывом (по умолчанию — нет). Команд для учётных ставок, включения аккаунта и `cross_border_clearances` по-прежнему нет.

Ввод проверяется при отмене, SIGINT, разрыве и таймауте; сообщения об ошибках не содержат токенов, кода подтверждения и тел HTTP-ответов.

Ревью исправило порядок блокировок аварийного вывода: ключи до аккаунта, как в шлюзе. В интеграционных проверках роли `core` и `llm` владеют разными соединениями; тест утраты session lock ждёт фактического снятия блокировки сервером после закрытия TCP. Отдельное исправление закрывает вывод незавершённого импорта Codex после ручного отзыва: добавлены 11 модульных и 4 SQL-проверки, включая отсутствие записи Vault, неясный результат CAS и неудачный повторный вход. Финальный общий проход после исправлений завершился успешно. Все одноразовые PostgreSQL/OpenBao-контейнеры и их данные удалены.

## Границы результата

- Текущая локальная подписка владельца в пул не импортировалась. Реальные ключи и входы в аккаунты не использовались.
- Пользовательская `.env`, рабочая БД и облачные серверы не менялись; проверки используют только локальную синтетику и одноразовые сервисы.
- Операторский вход с MFA в production остаётся P7/M10; автоматическое включение аккаунтов и UI управления пулом не входят в B12.
- Следующий B13 проверяет шлюз вместе с Codex/Kimi CLI в контейнерах; B14 подключает роль `llm` к инфраструктуре приложения.
- Приёмка P3/P3.0 на настоящих подписках, настоящая проверка Kimi и полный продуктовый e2e с WordPress остаются открытыми.
