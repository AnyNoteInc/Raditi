# План 96. Порядок после ревью проекта

Задачи roadmap — P30–P35. Запрос владельца от 26–27.11.2026: «проведи полноценное ревью проекта, найди примеры оптимизации», затем «давай приведём всё в порядок». Ревью шло по пяти областям (web, core и песочница, база/tRPC/биллинг, шлюзы, сборка и инфраструктура); сделанное в планах 86 и 92–95 не повторяется. Каждая задача — своя ветка и свой коммит (или несколько), слияние в `main` — через PR.

## P30. Шлюзы `llm` и `mcp` (ветка `perf/gateways`)

1. **Ошибка.** Таймаут блокировки при допуске вызова (`55P03`, `lock_timeout` 1 с в `call-ledger`) уходит в общий `catch` `gateway/server.ts` и превращается в отказ `transient` с паузой `platformRetryMs` = 30 с. Ловить `55P03` у `store.admit` и ждать слот дальше (до `waitUntil`), как при `waitForSlot`.
2. Ожидание слота не пишет `last_refusal` на каждом повторе; повтор — с нарастающей паузой.
3. `lookup` — одним запросом без интерактивной транзакции.
4. SSE: событие разбирается один раз (inspector отдаёт разобранное, счётчик usage его принимает), без двойного прохода декодеров; неизменённое событие пересылается исходными байтами.
5. Тело запроса: `estimateLlmInputTokens` без путей — по длине уже закодированного тела, без копии дерева; модель vision — без лишнего `JSON.parse`.
6. `mcp`: `unattended` прохода — кэш в процессе по `(taskId, answeredAt)`; проверка ключа — без кэша. `SkillSecrets.read` — общий promise для параллельных промахов.
7. Наследие: удалить `ContentPrivacy.mask` и лимит `CONTENT_PRIVACY_LIMIT`, оставить `rehydrate`; описание `web_observe` больше не обещает маркеры контактов.

## P31. База, tRPC и биллинг (ветка `perf/db-queries`)

1. **Ошибка.** `artifact.list` без пагинации: после 200 артефактов остальные не видны. Курсор по `(updatedAt, id)`; выдержки трёх первых блоков — одним запросом (`LEFT JOIN LATERAL`, `left(…, 2000)`), а не запросом на артефакт; индекс блоков под порядок выдержки.
2. Чтения `feed.*` — с `client_visible`, чтобы работал частичный индекс ленты: `chat/files`, `dialog-list` (`ENDING` один раз), `notifications`, `git/branches`, `scheduled-tasks`, `artifact-comments`, `project-trash`.
3. «Использование»: график активности и история списаний не перебирают всю историю — отсечение до группировки, индексы `task_events (task_id, created_at) WHERE type = 'feed.request'` и `credit_holds (account_id, created_at)`; `total` — только на первой странице.
4. tRPC: согласия и личное пространство — один раз на HTTP-запрос (ленивые значения контекста), а не в каждой процедуре пакета. better-auth — `session.cookieCache` на 60 с.
5. Активность хода — по `turn_id` (индекс `(turn_id, id)`), старые строки без `turn_id` — прежним путём.
6. Списки без широких полей: `projects` (`instructions` → признак), запуски расписаний (`select` вместо `include`).
7. Индекс `project_merge_requests (project_repository_id, source_branch, number DESC)`.
8. `dto.ts`: кредиты окна — через `Money`, не `Number`.

## P32. `core`: путь хода (ветка `perf/core-turn-path`)

1. Подготовка хода под арендой (`turn-supervisor`): независимые шаги — восстановление снимка, бандл, вложения, файлы проекта — параллельно, цепочка адреса и учётных данных — своя.
2. Сбор фактов прохода (`pass-facts`) — одним `Promise.all`, порядок только у зависимых пар.
3. Outbox: полная пачка — сразу следующий проход; таймер — страховка (10 с).
4. Файлы чата: известные `fileId` — одним запросом, загрузки — с небольшой параллельностью, порядок ленты прежний.
5. Неудачный ход закрывает изменения (страницы, память, репозиторий, расписания) параллельно.
6. Части снимка `patch`/`untracked` — параллельно, манифест последним.
7. Кэш бандла: sha256 и размер — рядом с файлом, чтение — потоком; обход тома зеркал — параллельный.
8. Наследие: пять мёртвых очередей BullMQ (`deploys`, `timers`, `site-provisioning`, `site-import`, `previews`) удаляются из `domain` и `core`.

## P33. `web` (ветка `perf/web-bundle`)

1. `next/dynamic` для панелей и окон чата, которые видны не всегда: артефакты (и каждый вид артефакта), браузер, документы, расписание, перенос в проект, публикация.
2. Лендинг без MUI и emotion: `Providers` — в layout групп кабинета, входа и онбординга; плашка cookie — на CSS-модуле.
3. Лента: `memo` строк, `useMemo` для записей и ревизий документов, общий тик времени, стабильные `actions`; редьюсер сохраняет прежний `head`, если он не изменился.
4. Первая страница ленты приходит с сервера вместе с чатом (без лишнего запроса после гидрации).
5. Опросы: очередь чата при живом SSE — раз в 15 с; присутствие в артефакте — без `refetchInterval`; список чатов — опрос только первой страницы.
6. Подсветка кода — загружается, только если в тексте есть блок кода.
7. Старые строки ленты (кандидаты, выпуски, обновления сайта) — одной компактной строкой; `release/chat-commands` — из нового пути `domain`.

## P34. `preview`: отдача страниц (ветка `perf/preview-serve`)

1. Метаданные страницы и её байты читаются раздельно; 304 — до чтения байтов; файлы — без HTML домашней страницы; `servedFile` — сначала sha256.
2. Сжатие в самом приложении (brotli/gzip по `Accept-Encoding`, `Vary`), с кэшем сжатого по версии; в Traefik не включаем — он ослабляет ETag.
3. Файлам — короткий `max-age` вместо `no-cache`.

## P35. Сборка, CI и наследие плана 83 (ветка `chore/build-cleanup`)

1. `next build` не проверяет типы второй раз (`typescript.ignoreBuildErrors`, типы — у `turbo typecheck`).
2. Приложения не пересобирают `@repo/service-runtime` в своём `build`.
3. `turbo.json`: без `.env` в `globalDependencies`; в `globalEnv` — общее, остальное — в `env` задач; `check-env` проверяет объединение.
4. `infra/dev/docker-compose.yml`: без Gitea, CI-раннера Gitea и стенда WordPress; `.env.example` и мониторинг — тоже.
5. `domain`: удалить код переменных сайтов, сайтовую часть `egress-hosts` и `site-address`; `release/` → `workspace-env/` и `chat/`, `preview/` → `egress/`; фикстуры ленты — не из рабочего бареля; `"sideEffects": false`.
6. Осиротевшие скрипты, устаревший README `infra/preview/`, неверные комментарии; неиспользуемые зависимости.
7. `gates`: `typecheck`, `lint`, `build` — одним вызовом turbo.

## Отложено — нужны решение владельца или проверка на сервере

- **Проверка снимка после загрузки раннером.** Сейчас `core` перечитывает часть `home` целиком до ответа клиенту. - **Триграммный поиск** (`pg_trgm`) по чатам и артефактам: нужно подтвердить расширение у провайдера базы.
- **Переименование `site_id`** в `turn_assignments` и `site_leases`: трогает сырой SQL `core` и `mcp`; отдельной миграцией после P31–P32.
- **Smoke E2E в CI**: стоит минут раннера; по запросу.
- **Разделение `DialogView`** (1737 строк) — после P33, отдельным рефакторингом.
