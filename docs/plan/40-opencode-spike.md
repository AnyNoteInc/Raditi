# G1: разведка OpenCode — блокеры драйвера, формы отказов, окно после простоя

05.10.2026 пройден инкремент G1 [плана перехода на OpenCode и GLM](../research/2026-10-opencode-glm/pivot-plan.md): настоящий OpenCode CLI 1.18.34 запускался в контейнере с монтированиями песочницы и пределами стенда супервизора (1 vCPU, 1024 МиБ, 128 процессов) под `runc` (Docker Desktop) и под `runsc` (Linux-ВМ, gVisor, ядро `4.19.0-gvisor`). Провайдера изображал сценарный фейк в соседнем контейнере. Ключ плана не использовался, к `api.z.ai` никто не ходил, корневой `.env` не читался. Единственный шаг с ключом — пункт 8 — сделан раньше, его три записи разобраны ниже.

Главное:

- **Bun под gVisor работает.** Запасная ветка «стоп и вопрос владельцу» не нужна.
- **Одноразовая доставка ключей работает** на ходе из пяти запросов и на продолжении. Пересыльщик на loopback не нужен.
- **База сессии перекрывает конфигурацию драйвера.** Права, модель и каталог из строки сессии сильнее `opencode.json`. Переносить базу между ходами как есть нельзя. Запасной путь плана — экспорт и импорт — сам по себе не помогает: импорт восстанавливает те же права и модель. Помогает экспорт, фильтр поля `info` и импорт; либо сброс строки обёрткой. Это меняет G3.
- **Отказ, после которого ход кончается за один запрос, есть и внутри потока:** объект `error`. Правило 7(е) не вводится.
- **Два из шести документированных значений `finish_reason` Z.ai вызывают шторм запросов.** После `sensitive` и `model_context_window_exceeded` CLI повторяет запрос без паузы, как и после потока без `finish_reason`. Инспектор потока в G2 обязан их не пропускать.
- **Отказ собственного подключения CLI к MCP молчалив:** код 0, ход идёт без инструментов сайта. Признак один — строка уровня WARN, и только при `--print-logs`.

## Стенд

Скрипты — в [docs/research/2026-10-opencode-glm/scripts/g1](../research/2026-10-opencode-glm/scripts/g1/README.md). Каждое наблюдение отчёта воспроизводится командой `node spike.mjs <runc|runsc> <пункт>`; пункт 5 — `strings.mjs`.

- **Образ** `raditi-oc-spike:1.18.34` (`scripts/g1/image/`): локальный `raditi-p5verify-sandbox:local` плюс `npm ci --ignore-scripts` по lock-файлу пробы. Установлено два пакета; npm сверил целостность: `opencode-ai` — `sha512-9WUS2T0t…QYnySA==`, `opencode-linux-arm64` — `sha512-ZSjqcH0M…JhouvA==`. SHA-256 исполняемого файла — `415487fc…0b15351`, как у пробы. В ВМ с `runsc` образ перенесён через `docker save | docker load`, второй загрузки не было.
- **Контейнер CLI** — по образцу провайдера песочницы (`packages/sandbox-providers/src/docker.ts`): read-only корень, `cap-drop ALL`, `no-new-privileges`, uid 10001, tmpfs `/workspace` (512 МБ), `/agent-home` (256 МБ), `/tmp` (64 МБ) и `/run/raditi/secrets`, internal-сеть, `--add-host sandbox-gw`. Команды идут через `docker exec`. Отличия от продукта: нет tmpfs `/run/raditi/exec` и `/run/raditi/control`, tmpfs секретов — 64 КБ вместо 2 МиБ, скрипты стенда смонтированы в `/spike` только для чтения, а резолвером служит приёмник (в продукте DNS нет).
- **Фейк** (`fake.mjs`) отвечает на `POST /s/<запуск>/zai/v4/chat/completions` по шагам сценария, держит заглушку MCP и приёмник: DNS на 53, SNI на 443, HTTP на 80. Он же единственный резолвер контейнера CLI. Ключ хода и токен MCP фейк узнаёт по SHA-256 и значений не хранит.
- **Ключи** — синтетические, формы `core`: `sk-rdt-<43 знака base64url>` и `mcp_<64 hex>`, новые на каждый запуск.
- **Обёртка** (`wrapper.mjs`) — прототип `run.mjs` драйвера: читает и удаляет два файла tmpfs, создаёт на их месте именованные каналы, отдаёт каждое значение один раз, запускает CLI с окружением, собранным с нуля, убивает группу процессов по завершении.

Отступления от текста плана:

- Провайдер — не прокси пробы (он пересылал запросы в Z.ai с ключом плана), а свой фейк без upstream. Так велено задачей: ключа у инкремента нет.
- Пределы стенда применены и под `runc`: план требовал их только под `runsc`.
- Пункт 3 шире плана: проверены ещё `session.directory`, строки учётных записей, триггер в базе и обе меры защиты.
- Пункт 4 шире плана: добавлены контроли (`field` с индексом, слова переполнения, слова повтора), `finish_reason: length`, пустой поток и два отказа посреди хода.

Во всех запусках одинаково: баннер `Bun v1.3.14 … panic(main thread): Segmentation fault … oh no: Bun has crashed`, сигнал SIGTRAP, код обёртки 133, в stdout ничего. Под обоими runtime результат один.

Вывод: на Linux выгрузка выключена по умолчанию. Включают её две переменные, и `BUN_CRASH_REPORT_URL` сильнее выключателя. Убийство группы процессов отчёт не останавливает: `curl` успевает уйти. Поэтому защита — окружение CLI, собранное обёрткой с нуля: в нём `BUN_ENABLE_CRASH_REPORTING=0` и нет `BUN_CRASH_REPORT_URL`. `DO_NOT_TRACK=1` в таблице сети плана выключателем не является; строку таблицы нужно заменить.

Контроли показывают, что проверки находят значения, когда они есть:

- ключи в обычных файлах — команда модели читает оба файла, `inspect.mjs` находит оба значения в `/run/raditi/secrets`;
- ключи в окружении — оба значения в окружении команды модели и в `/proc/<pid>/environ` CLI.

CLI, который не прочитал канал:

| Случай | Отдано | Код | Обёртка жила | Что осталось |
| --- | --- | --- | --- | --- |
| Конфигурация — не JSON | ничего | 1 | 0,9 с (`runsc` 1,5 с) | каналов нет, запросов нет |
| `{file:}` на несуществующий файл | только ключ хода | 1 | 0,9 с (1,4 с) | то же |
| Вместо CLI `sh -c 'sleep 1; exit 3'` | ничего | 3 | 1,0 с | то же |

При ошибке конфигурации stdout пуст, в stderr — текст с управляющими кодами цвета (`NO_COLOR=1` на него не действует): `Error: Configuration is invalid at … bad file reference: "{file:…}" … does not exist`. Если файл не разбирается как JSON, CLI печатает в stderr его текст (`--- JSONC Input ---`). Секретов в конфигурации нет, только ссылки `{file:}`, но промпт агента в ней есть: stderr CLI клиенту не показывается.

Выводы для G3:

- доставка через `{file:}` и именованные каналы читается CLI ровно один раз за процесс: на ходе из пяти запросов, на продолжении и на ходе со сжатием контекста (раздел 7) второго чтения не понадобилось;
- собственную проверку MCP обёртке лучше делать отдельным коротким процессом: строка с токеном остаётся в памяти `node` до конца хода;
- под `runc` ключ в памяти CLI доступен команде модели. Это локальная разработка на macOS; под `runsc` доступа нет. `ptrace` не проверялся: в образе нет инструмента;
- локального API у `opencode run` нет: команда модели (`in/listeners.mjs`) перебрала все порты loopback и не нашла ни одного, который принимает соединения, и ни одного unix-сокета (`samples/70-g1-runtime/<runtime>.p2ports.json`). Спросить у работающего CLI его конфигурацию с ключами команда модели не может.

Выводы:

1. Условие решения 5 не выполнено: права, модель и каталог из базы перекрывают конфигурацию драйвера. База между ходами как есть не переносится.

3. Сброс обёрткой дешевле на эти два запуска, но держится на знании схемы базы версии 1.18.34 и обязан удалять триггеры и представления. Это запасной вариант, если экспорт и импорт окажутся дороги.
4. История сообщений остаётся вводом модели при любом способе: её содержимое платформа не проверяет.
5. Строки учётных записей не дают модели чужого ключа: все запросы второго хода шли с ключом хода. Фильтр и сброс эти строки убирают.
6. `session.directory` и неизвестная модель — способ сорвать следующий ход. Ход с подложенным каталогом не печатает ни одного события и не выходит: его снимает только срок хода.

Что из этого следует:

- **Окончательный отказ.** До потока — HTTP 400, 402 или 403 с телом решения 6; `error.field` без индекса (`messages[].content`) не мешает. Внутри потока — `data: {"error":{…}}` первым событием, после текста или перед `[DONE]`. Во всех случаях один запрос, код 1, одно событие `error`. То же после выполненного шага с инструментом.
- **Что видит драйвер.** Отказ до потока: `error.name = "APIError"`, `data.statusCode`, `data.isRetryable: false`, `data.responseBody` с телом шлюза и `data.metadata.url` с адресом шлюза. Отказ в потоке: `error.name = "UnknownError"`, а `data.message` — JSON объекта `error`. Код `raditi_<вид>` читается в обоих случаях; клиенту ни тело, ни адрес не показываются.
- **Краткий отказ.** 503 с `retry-after: 3` — пять повторов с паузой ровно 3 секунды, затем код 1. Другие значения не исполнялись; по правилу из исполняемого файла (`opencode-cli/strings/ctx-retry.txt`: пауза равна заголовку, повторов пять) `retry-after: 30` держит ход около 150 секунд.
- **Правило 7(г) обязательно.** Тот же отказ 400 с `field: "messages[502].content"` повторяется пять раз за 73 секунды: в теле есть «502».
- **Слова переполнения.** Отказ 400 с текстом «too many tokens» — `ContextOverflowError` и сразу второй запрос: это запрос сжатия, без `tools` и с системным промптом «You are a context summarization agent…» (`requests/http-400-overflow-words.requests.json`). Затем код 1. Тексты отказов проверяются и по списку раздела 5.
- **Шторм.** Поток с `finish_reason` `sensitive` или `model_context_window_exceeded`; поток без `finish_reason` (с `[DONE]` и без); поток из одного `[DONE]`; пустой поток с HTTP 200. CLI пишет шаг `reason: "unknown"` и тут же повторяет запрос: 13 запросов, между ними не больше 0,1 секунды. В четырёх формах с текстом каждый запрос длиннее предыдущего на 86–95 байт: частичный ответ остаётся в истории (с 17 716 до 18 748–18 856 байт за 13 запросов). В трёх формах без текста — `sensitive` без текста, один `[DONE]`, пустой поток — запрос повторяется без изменений, 17 716 байт. Размеры — в `samples/72-g1-refusals/requests/`. Из шести значений документации Z.ai два — `sensitive` и `model_context_window_exceeded` — попадают сюда; другие значения вне `stop`, `tool_calls`, `length`, `content_filter`, `network_error` не исполнялись.
- **`finish_reason: length`** — ход «успешно» кончается кодом 0 с обрезанным текстом; `content_filter` — один запрос, `ContentFilterError`, код 1; `network_error` CLI знает сам и повторяет с паузами.

Без флагов stdout и stderr чисты, событий об MCP нет, ход идёт до конца и кончается кодом 0. Файл `log/opencode.log` признаком служить не может: CLI не дописывает его перед выходом. В записи под `runc` без флагов в нём 12 строк, последняя — `loop … step=0`, строки WARN нет; под `runsc` с теми же флагами `--print-logs --log-level WARN` строка WARN в файле есть у отказа 500 и нет у отказа 401. Повторы дают другое: в прогоне ревью строка WARN оказалась в файле ещё в двух случаях под `runc` и в пяти под `runsc`, в том числе без флагов. С `--print-logs` на уровне INFO в stderr 22 строки INFO за ход из одного запроса (и строка WARN при отказе), на уровне WARN — ноль при исправном MCP.

Решение для G3: аргументы CLI получают `--print-logs --log-level WARN`; обёртка читает stderr CLI и на строке с `message="server unavailable"` и `key=raditi` убивает группу процессов и завершает ход ошибкой. Строки лога клиенту не уходят. Признак — свойство версии 1.18.34.

## 7. Конфигурация

Скрипт `p7.mjs`, итог — `samples/74-g1-config/<runtime>.p7.json`.

**`deny` и `ask`.** Правило стоит на шаблоне команды (`permission.bash = {"*": "allow", "echo denied-marker*": …}`); команда не трогает ничего вне рабочего дерева, чтобы сработать могло только оно.

| Правило | `continue_loop_on_deny` | Вызов | Ход |
| --- | --- | --- | --- |
| `deny` | нет | `error`: «The user has specified a rule which prevents you from using this specific tool call…» | продолжается: второй запрос, итог, код 0 |
| `deny` | `true` | то же | то же |
| `ask` | нет | в stderr `! permission requested: bash (echo denied-marker); auto-rejecting`; `error`: «The user rejected permission to use this specific tool call.» | **обрывается:** один запрос, последний шаг `tool-calls`, итога нет, код 0 |
| `ask` | `true` | то же | продолжается: второй запрос, итог, код 0 |

Флаг `continue_loop_on_deny` относится к отклонённому запросу разрешения, а не к правилу `deny`. Держим его включённым: правило `ask` может прийти не из нашей конфигурации — встроенный набор CLI содержит `external_directory: ask`, а строка сессии способна добавить своё (раздел 3). Код 0 без итогового текста драйвер считает неуспехом.

**Необъявленный инструмент.** Вызов `webfetch`, которого нет среди объявленных: событие `tool_use` с инструментом `invalid`, статус `completed`, текст «Model tried to call unavailable tool 'webfetch'. Available tools: …». Ход продолжается, с флагом и без.

**`/workspace/inbox`.** Запросы по порядку: `read` вложения, `read /etc/hostname`, `bash cat` вложения, `bash cat /etc/hostname`, `glob`, `read` из вложенного каталога, `write` во вложение.

| `permission.external_directory` | Вложения | `/etc/hostname` |
| --- | --- | --- |
| `"deny"` | все семь вызовов отклонены | отклонено |
| `{"*": "deny", "/workspace/inbox/*": "allow"}` | чтение, `cat`, `glob`, вложенный каталог и запись проходят | отклонено |
| `{"*": "deny", "/workspace/inbox": "allow", "/workspace/inbox/**": "allow"}` | то же | отклонено |

Порядок ключей важен: побеждает последнее совпавшее правило. Это проверено на ревью (`p7order.mjs`, `samples/74-g1-config/<runtime>.p7order.json`): те же два правила в обратном порядке — сначала `allow` для вложений, потом `"*": "deny"` — отклоняют все семь вызовов под обоими runtime. Правило открывает и запись во вложения; это каталог вне репозитория, в публикацию он не попадает.

**Prompt через stdin.** `/init`, `/compact`, `/workspace/inbox/brief.txt — что в этом файле?`, `/нет-такой-команды …`, `-`, `--help`: в каждом запуске один запрос, последнее сообщение пользователя равно prompt дословно, код 0.

**Сжатие контекста.** Фейк сообщает расход 990 000 токенов при пределе модели 1 000 000. Следующий запрос CLI — сжатие:

- поля тела: `model`, `max_tokens` (32 000), `messages`, `stream`, `stream_options`; `tools` и `tool_choice` нет;
- системное сообщение — «You are a context summarization agent…» (630 знаков), без промпта агента платформы и без `AGENTS.md`; одно сообщение пользователя с пересказом разговора и шаблоном итога;
- модель — основная (`glm-5.3`), хотя в конфигурации `small_model` указывал на другую;
- третий запрос — снова обычный: промпт платформы, история заменена на три сообщения: «What did we do so far?», итог сжатия, «Continue if you have next steps, or stop and ask for clarification if you are unsure how to proceed.»

В stdout за этот ход: `tool_use`, `step_finish (tool-calls)`, `text` с итогом сжатия, **`step_finish (stop)`**, **`text` со служебной репликой «Continue if you have next steps…»**, затем шаг с настоящим итогом. С `compaction: {auto: false}` запроса сжатия нет.

Выводы:

- G2: политика тела принимает запрос без `tools` и `tool_choice`; это не признак чужого клиента.
- G3: `step_finish` с `reason: "stop"` не означает конец хода. Ход кончается выходом процесса, итог — последнее событие `text`, и оно должно пройти схему итога: служебная реплика CLI — тоже `text`.
- Сжатие оставляем включённым: при контексте в миллион токенов оно редкость, а без него переполнение кончает ход.

**`thinking`.** С id провайдера `raditi` поля нет (раздел 5). Его ставит либо шлюз в политике тела — вместе с `reasoning_effort` по решению 3, — либо `options.thinking` модели в конфигурации. Предлагаю шлюз: тогда поле не зависит от версии CLI.

## 8. Окно после простоя

Сделано до инкремента, с ключом плана: три вызова, один кредит. Записи — `samples/60-quota-idle-before.json`, `61-chat-first-after-idle.json`, `62-quota-idle-after.json`; скрипт — `scripts/probe-idle-window.mjs`.

| Запись | Время (UTC) | Окно 5 часов (`unit 3 × number 5`) | Окно недели (`unit 6 × number 1`) |
| --- | --- | --- | --- |
| 60, квота до запроса | 06:14:53 | `usage` 2000, `currentValue` 0, `remaining` 2000, `percentage` 0, **`nextResetTime` нет** | `currentValue` 25, `remaining` 9974, `percentage` 1, `nextResetTime` 1791740593998 |
| 61, первый запрос после простоя | 06:14:55 | HTTP 200, `usage`: 19 + 64 токена | — |
| 62, квота после запроса | 06:14:56 | `currentValue` 0, `remaining` 1999, `percentage` 1, **`nextResetTime` 1791198895596** (11:14:55 UTC — запрос плюс 5 часов) | без изменений |

Правило для `probe` бэкенда `zai-coding` (решение 8):

1. У окна нет `nextResetTime`, `currentValue` равен 0 и `remaining` равен `usage` — окно не начато: `{usedPct: 0, resetsAt: null}`. Это известное свободное окно, а не «неизвестное»: иначе пул закроет допуск навсегда, ведь начать окно может только запрос.
2. У окна нет `nextResetTime`, а расход ненулевой — не наблюдалось; окно считается неизвестным.
3. `nextResetTime` в прошлом не наблюдалось: предыдущее окно кончилось в 22:47 UTC, и к 06:14 Z.ai уже не отдавал его время. Правило плана — считать такое окно не начатым — остаётся предположением.
4. После первого запроса `currentValue` ещё 0, а `remaining` уже 1999. `usedPct` стоит считать как большее из `currentValue / usage` и `(usage − remaining) / usage`. Что означает эта единица, неизвестно: в шести записях активного окна (`46-quota-limit-*`) `currentValue + remaining` тоже равно `usage − 1`, так что это может быть постоянный сдвиг начатого окна, а не кредит первого запроса. Правило с максимумом завышает расход не больше чем на один кредит. Полю `percentage` доверять нельзя: оно равно 1 и при 0,05 %, и при 1,25 %.
5. Окно недели от одного короткого запроса не изменилось.

Записи 60 и 62 — фикстуры фейка Z.ai в G2: «окно не начато» и «окно начато».

**G3 (образ и драйвер):**

## Утечки

После каждого хода оба значения искались в stdout, stderr, логе CLI и во всех файлах `/agent-home`, `/tmp`, `/workspace`, `/run/raditi` — как есть, в hex, UTF-16 и base64 во всех выравниваниях. Около 95 запусков CLI на каждый runtime; находки только в двух контролях пункта 2 с ключами в обычных файлах — оба файла в `/run/raditi/secrets`, как и задумано. В событиях CLI есть адрес шлюза и тело его отказа (`data.metadata.url`, `data.responseBody`), ключа хода в них нет.

Фейк значений не хранит: он знает только их SHA-256. Перед переносом в репозиторий `collect.mjs` проверил отобранные файлы на строки вида `sk-rdt-…` и `mcp_…` — ни одной, — затем их обработал `sanitize-samples.mjs`: 89 файлов, 0,9 МБ (до ревью — 58); правила секретов не сработали ни разу, 441 идентификатор CLI заменён заглушками (1 231 замена), значения заголовков оставлены только у `content-type` и `retry-after`.

Что здесь нашло и закрыло ревью:

- Записи фейка и приёмника — то, что уходит в `samples/` как `*.records.json`, `*.requests.json` и `*.sink.json`, — в прогонах исполнителя по значению не искались, только по форме в `collect.mjs`. Теперь `lib.mjs` при каждом чтении ищет в них каждое выданное стендом значение, и пункт с находкой завершается ошибкой. Повтор всех пунктов под обоими runtime находок не дал.
- Поиск по значению находит и часть значения — любые 20 знаков подряд: ключ, обрезанный логом, разорванный переводом строки или ставший частью имени.

Пределы, которые остаются:

- На ревью `sanitize-samples.mjs` не знал формы токена MCP платформы (`mcp_` и 64 hex): вне заголовка, слова `Bearer` и свойства с именем секрета такой токен проходил очистку и её `check`, останавливала его только проверка формы в `collect.mjs`. Гейты партии добавили правило в сам скрипт — раздел «После гейтов партии».
- Значение в base64, hex или разрезанное переводом строки не видят ни очистка, ни проверка формы — только поиск по значению во время прогона. Значение в другом регистре или перевёрнутое не видит никто.
- Проверено подстановкой 25 синтетических образцов в оба скрипта; в репозиторий образцы не попали.

- x64: всё шло на arm64. Первый запуск на x64 — job чернового PR после G3.

## Что решить перед G2 и G3

1. **Состояние сессии.** Экспорт → фильтр → импорт в начале хода (раздел 3, вывод 2) или сброс обёрткой с удалением триггеров (вывод 3). Отчёт предлагает первое.
2. **Кто ставит `thinking`.** Шлюз в политике тела или `options.thinking` модели в конфигурации драйвера. Отчёт предлагает шлюз.
3. **Чем шлюз заменяет «шторм-формы».** Объект `error` в потоке кончает ход за один запрос. Замена `finish_reason` на `content_filter` тоже кончает ход, но выдаёт отказ шлюза за фильтр провайдера. Отчёт предлагает объект `error`.
4. **`retry-after` краткого отказа.** CLI делает ровно пять повторов (измерено при 3 секундах): при 30 секундах ход провисит две с половиной минуты и всё равно упадёт. Возможно, пауза должна быть короче.
