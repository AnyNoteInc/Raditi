# План 58. Предпросмотр одним контейнером

Запрос владельца от 26.10.2026: «после preview остаются в работе докер контейнеры, они должны очищаться и для одного preview должен запускать один докер контейнер со своим gateway внутри». На вопрос, как это устроить, владелец выбрал «Всё в одном, без DinD»: один контейнер на предпросмотр, внутри PHP с Apache, MariaDB и свой шлюз. Docker-in-Docker отвергнут: на macOS он требует `--privileged`.

Уборка (остановка после простоя, снос закрытого диалога) — отдельная работа того же дня, этот план её не касается. Здесь — как свести предпросмотр к одному контейнеру и не ослабить правило 5 и spec §8 («Предпросмотр диалога»). Код по плану не менялся; ниже замеры 26.10.2026, варианты, рекомендация, срезы и вопросы владельцу.

## Решение владельца (26.10.2026)

Ответ на вопросы раздела 9: «А, но выходы наружу закрывать не нужно». Это меняет вариант А так:

- **Интернет открыт.** PHP предпросмотра ходит в открытый интернет напрямую, как агент хода с 26.10.2026 (spec §20, «Интернет агента»). Правила хоста на мосту `rpv…` (`host-firewall.mjs`) пропускают пересылку на публичные адреса и закрывают остальное: адреса хоста (`INPUT` — только ответы на соединения хоста), частные, link-local, CGNAT, loopback, подсети платформы (`SANDBOX_EGRESS_REFUSED_SUBNETS`) и чужие мосты. Это вариант замера З7 «пересылка наружу разрешена только на публичные адреса». Прочтение «выходы наружу» как «интернет, но не хост и не платформа» — значение по умолчанию: код клиента в предпросмотре не должен доставать Vault, базу, Gitea и чужие предпросмотры.
- **DNS.** Имена разрешают серверы из настройки `PREVIEW_DNS_SERVERS` (`Dns` контейнера). Под `runsc` встроенного DNS Docker нет (З8), а под `runc` он разрешал бы и имена закрытых адресов — поэтому он не используется ни там, ни там. На деле (§11) под `runc` отвечает DNS Docker, но спрашивает он те же серверы, а под `runsc` имена разрешает пересыльщик в самом контейнере.
- **Прокси выхода не нужен.** Переменные клиента (Р13) предпросмотр получает, как прежде, а его запросы к их хостам идут напрямую: контейнер `egress` и `ExtraHosts` уходят, предпросмотр — всегда один контейнер (вопрос 2 снят).
- **Вопросы 3–5** — значения по умолчанию по указанию владельца от 09.10.2026: браузер агента — отдельная пара контейнеров по требованию; `lease` остаётся созданным, не запущенным контейнером-меткой; команды платформы идут внутри `preview` через обёртку `setpriv` + `setsid`, которая убивает их группу процессов.
- **Чем А слабее сегодняшнего** (раздел 4) — пункты 2 и 3 остаются и приняты ответом; пункт 1 теперь о хосте и платформе, а не об интернете: без правила `DOCKER-USER` PHP достал бы частные сети, поэтому правила ставятся и проверяются до старта контейнера и перепроверяются сборщиком.

Срезы раздела 8 остаются, срез 58.3 проще на прокси выхода, срез 58.4 — на строки `egress` стенда `verify:preview-network`. Работа идёт в отдельном дереве ветки `feat/preview-single-container`.

## 1. Что сейчас

`createDockerPreviewRuntime` (`packages/sandbox-providers/src/preview`) строит предпросмотр из нескольких контейнеров:

| Роль | Живёт | Образ | Сеть | Что делает |
| --- | --- | --- | --- | --- |
| `web` | всё время | `PREVIEW_WEB_IMAGES` (WordPress с Apache, по версии PHP) | только `rpv…` (internal, без адреса хоста) | PHP сайта, не root (33), `runsc` в production |
| `db` | всё время, если есть база | `PREVIEW_DB_IMAGE` (MariaDB 11.4) | только `rpv…` | база-копия, пароли файлами tmpfs |
| `forwarder` | всё время | `PREVIEW_FORWARDER_IMAGE` (`tools`) | мост по умолчанию + `rpv…` | вход: опубликованный порт → PHP, проверка `Host` (421) |
| `egress` | только если клиент дал предпросмотру переменные | `PREVIEW_EGRESS_IMAGE` | мост по умолчанию + `rpv…` | прокси выхода к хостам переменных (Р13, `client-egress.mjs`) |
| `lease` | создан, не запущен | `tools` | `none` | метка срока для сторожа: метки не меняются, продление — новый `lease` |
| `files-helper` | секунды, на запись дерева | `tools` | `none` | пишет в том docroot (`files.mjs`) |
| `cli` | секунды, на команду | `PREVIEW_CLI_IMAGE` (WP-CLI) | как у `web` | `wp eval`, `php -l` — команды платформы |
| `relay` + `browser` | по требованию, гаснут в простое | `tools`, `PREVIEW_BROWSER_IMAGE` | `rpb…` + мост по умолчанию | браузер агента на предпросмотре |
| `firewall` | секунды, только `runsc` | `SANDBOX_NETWORK_GUARD_IMAGE` | `host` | правило хоста `INPUT -i <мост> -j DROP` |

Почему контейнеров несколько: граница — сеть. PHP и база стоят на internal-мосту без адреса хоста, и Docker не выпускает с него ничего никуда. Наружу смотрят только доверенные пересыльщики: у каждого вторая нога на мосту по умолчанию. Опубликовать порт контейнера, который стоит только на internal-сети, Docker не умеет (замер З6 ниже). Поэтому вход — отдельный двудомный контейнер.

В покое у предпросмотра три работающих контейнера (`web`, `db`, `forwarder`) и один созданный (`lease`); с переменными — четыре работающих. На dev-машине владельца 26.10.2026 так и было: `docker stats` — `web` 81–90 МиБ, `db` 122–126 МиБ, `forwarder` 13–16 МиБ, около 220 МиБ на предпросмотр.

## 2. Что должно остаться верным

Правило 5 и spec §8 для одного контейнера:

1. PHP клиента не достаёт интернет, хост, подсети платформы, чужие предпросмотры и DNS: имя снаружи не разрешается.
2. Наружу ходит только прокси выхода и только к хостам из списка (Р13); его проверки (`forbidden_host`, `forbidden_address`, SNI) не меняются.
3. Вход — только через пересыльщик входа с проверкой `Host`. Пересыльщик — доверенный код, PHP его не трогает: иначе PHP чужого предпросмотра принял бы запрос со старым портом и cookie другого диалога (ради этого и есть 421).
4. Не root, `no-new-privileges`, read-only rootfs, пределы; ни сокета Docker, ни путей хоста; `runsc` в production.
5. Пароли базы — файлами tmpfs, не в окружении; PHP их не читает, кроме своего пароля из файла настроек.
6. Сторож хоста убирает предпросмотр по сроку без `core`.

## 4. Варианты

### А. Один контейнер, границу держат правила хоста — рекомендуется

**Контейнер `preview`** — один на предпросмотр, образ на версию PHP. Внутри, у каждой службы свой uid:

- Apache с PHP (33), слушает `127.0.0.1:8081`;
- MariaDB 11.4 (999), только сокет и `127.0.0.1:3306`, `skip-name-resolve`;
- пересыльщик входа `forward.mjs --http-host=<hostname>` (10001), `0.0.0.0:8080` → `127.0.0.1:8081`, — «свой шлюз внутри»;
- WP-CLI — для команд платформы (`exec`).

Запуск: `tini` → init — доверенный короткий скрипт из образа. Init ждёт файлы паролей и настроек в tmpfs (как `WAIT_FOR_SETTINGS` и `WAIT_FOR_DATABASE_SECRETS` сейчас) и запускает каждую службу через `setpriv --reuid=<uid> --regid=<gid> --clear-groups --bounding-set=-all --inh-caps=-all --no-new-privs`. Затем сам отказывается от возможностей и ждёт. Первая упавшая служба останавливает контейнер, и следующий `ensure` поднимает его заново: тот же порядок, что сейчас при перезапуске. Контейнеру нужны только `SETUID`, `SETGID` и `SETPCAP` на время старта (З1). Под `runsc` это возможности внутри песочницы gVisor, а не хоста; ни у одной службы их нет.

**Сеть** — свой мост `rpv<12hex>`, но не internal (иначе порт не опубликовать, З6), без IPv6, один контейнер на мосту. До того как контейнер запустится, помощник `host-firewall.mjs` ставит правила хоста (З7) и проверяет их (`check`); без правил контейнер не стартует:

- `INPUT -i <мост>`: `ESTABLISHED,RELATED` — `ACCEPT`, остальное — `DROP` (сейчас под `runsc` — просто `DROP`);
- `DOCKER-USER -i <мост>`: `ESTABLISHED,RELATED` и `-o <мост>` — дальше, остальное — `DROP`;
- в отличие от сегодняшнего, помощник работает и под `runc`: на Docker Desktop он проверен (З7).

`Dns: ['192.0.2.1']` закрывает встроенный DNS Docker (З8); `ExtraHosts` не нужен — база и прокси на loopback. Опубликованный порт — на `PREVIEW_UPSTREAM_HOST`, как сейчас.

**Прокси выхода.** Если клиент дал предпросмотру переменные (Р13), к контейнеру добавляется второй — `egress`, двудомный, как сейчас: мост по умолчанию + `rpv…`. PHP ходит к нему внутри моста (это правило `-o <мост>` пускает), а сам прокси выходит через свою ногу на мосту по умолчанию, где правил моста предпросмотра нет. Внутрь `preview` прокси не переносится: правила хоста не различают uid. Предпросмотров с переменными мало, а «один контейнер» сохраняется у остальных.

**Короткоживущие помощники:**

- `files-helper` остаётся как есть: только том docroot, без сети, работает и через границу gVisor;
- `cli` уходит: под `runsc` чужая песочница не достанет базу на loopback контейнера, поэтому `exec` идёт внутрь `preview` через `docker exec -u 0` с обёрткой `setpriv` (uid PHP, пустой bounding set) и `setsid`. По концу команды или по сроку обёртка убивает её группу процессов: «что команда оставила работать» раньше уходило вместе с контейнером CLI.

**Браузер агента** (`relay` + `browser`) остаётся отдельным, по требованию и с остановкой в простое. Причины: Chromium — другой образ (3,5 ГБ) и другой предел памяти, нужен минутами из часов, а в одной песочнице с PHP он стал бы ещё одним соседом недоверенного кода.

**`lease`** остаётся: метки контейнера не меняются, а пересоздавать `preview` при каждом продлении — значит перезапускать Apache и MariaDB. Он создан и не запущен: `docker ps` показывает один контейнер на предпросмотр, `docker ps -a` — два.

**Чем А слабее сегодняшнего:**

1. Мост не internal: наружу пакеты не выпускает наше правило `DOCKER-USER`, а не сам Docker. Если правила нет, PHP получает интернет. Защита: правила ставятся и проверяются до старта контейнера и при каждом `ensure`, сборщик `core` перепроверяет их у живых предпросмотров, сбой проверки — `failed`, а не предпросмотр без границы. Риск: перезагрузка хоста или `firewalld reload` снимает правила, пока `core` не перепроверил, — контейнеры с `RestartPolicy: no` сами не стартуют, но уже работающие останутся без правил до следующего прохода сборщика.
2. Пересыльщик входа и база — в одной песочнице с PHP. Их разделяют uid и пустые возможности, а не отдельные ядра gVisor. Выход PHP за пределы uid 33 внутри gVisor дал бы ему базу (свою же копию) и пересыльщик (подмену ответа своего же предпросмотра). Чужой предпросмотр ему по-прежнему закрыт правилами хоста.
3. Контейнеру при старте нужны `SETUID`, `SETGID` и `SETPCAP`, а не просто `cap-drop ALL`. Процессы `docker exec -u 0` получают их от Docker, поэтому exec платформы всегда идёт через обёртку `setpriv`.

### Б. Два контейнера: предпросмотр и его шлюз

`preview` (PHP, MariaDB; `runsc` с флагами по умолчанию, `cap-drop ALL` + `SETUID`/`SETGID`/`SETPCAP` на старт, как в А) — на internal-мосту `rpv…`, как сейчас. `gateway` (пересыльщик входа и, если нужно, прокси выхода; доверенный код под `runc`) — двудомный, как нынешний `forwarder`. Сетевая граница не меняется вовсе: стенд `verify:preview-network` переносится почти без правок, правила хоста — сегодняшние. В покое — два работающих контейнера вместо трёх-четырёх. Шлюз — рядом с предпросмотром, а не внутри: буквально запрос владельца не выполняет.

### В. Один контейнер, свой файрвол внутри gVisor

Как А, но вместо правил хоста — `iptables-legacy` с `owner` внутри песочницы (З3), и прокси выхода тоже внутри: один контейнер всегда. Цена: среда предпросмотров — отдельная запись `runsc` с `--net-raw` (сейчас `safeRunscArgs` её отвергает для всех), а init получает `NET_ADMIN` и `NET_RAW` внутри песочницы. Граница живёт в ядре той же песочницы, где работает PHP. Правила без состояния, потому что `conntrack` gVisor не умеет. Под `runc` набор тот же (З4).

### Г и Д — отвергнуты

- **Г. Без сети вовсе** (`NetworkMode: none`, вход и выход — через Unix-сокеты в общем томе). Через границу gVisor сокет ходит только с `--host-uds=all` (З5), и шлюз всё равно — второй контейнер.
- **Д. Docker-in-Docker** — отверг владелец.

## 5. Рекомендация

**Вариант А.** В покое — один работающий контейнер на предпросмотр со своим пересыльщиком входа внутри; второй (`egress`) — только когда клиент передал предпросмотру переменные. `runsc` остаётся с флагами по умолчанию, ни `NET_ADMIN`, ни `NET_RAW`, ни `--net-raw`. Граница выхода — правила хоста на мосту предпросмотра, того же рода, что сегодняшнее правило `INPUT` под `runsc`; DNS закрыт настройкой контейнера. Цена — три пункта «чем А слабее» выше, и их владелец должен принять явно: это меняет формулировки правила 5 и spec §8 («своя internal-сеть без адреса хоста», «cap-drop ALL»).

Если владелец не принимает, что мост не internal, — вариант Б: та же экономия у PHP и базы, граница как сейчас, но два контейнера. Если нужен буквально один контейнер и с прокси выхода — вариант В с `--net-raw` у среды предпросмотров.

## 6. Устройство варианта А по частям

- **Образы.** Новая цель `site` в `infra/preview/Dockerfile` с аргументом `BASE` — образ `wordpress:<версия>-php<x.y>-apache@sha256:…`. В него добавляются:
  - MariaDB 11.4 из репозитория mariadb.org с закреплённым ключом и версией (как `PREVIEW_DB_IMAGE` сейчас; пакеты есть для Debian 11–13 — образы PHP 7.4 стоят на bullseye, PHP 8.3 — на trixie);
  - `tini`, `setpriv` (util-linux);

**Образ `site`** (`infra/preview/Dockerfile`, цель `site`, аргумент `BASE` — `wordpress:<версия>-php<x.y>-apache@sha256:…`; локальная метка `raditi-preview-site:<x.y>-local`):

- Внутри: `tini`, `setpriv` (util-linux), MariaDB 11.4 (сервер и клиент `mariadb`), `/usr/local/bin/node` (бинарник Node 26.10 из образа `tools`), `/usr/local/bin/wp` (WP-CLI, phar с закреплённым sha256), `/usr/local/lib/raditi/forward.mjs`, `/usr/local/lib/raditi/init.sh`, `/usr/local/lib/raditi/run-as.sh`. Объявленных томов (`VOLUME`) нет, кроме тех, что монтирует среда: `/var/www/html` и `/var/lib/mysql`.

Затем init отказывается от своих возможностей (`setpriv --bounding-set=-all …`) и только следит: умерла любая служба — остальные останавливаются, контейнер выходит с ненулевым кодом. Ни пароли, ни настройки не попадают в аргументы процессов и в журнал.

**Правила хоста** (`infra/sandbox/host-firewall.mjs`, тот же образ `SANDBOX_NETWORK_GUARD_IMAGE`, контейнер в сети хоста только с `NET_ADMIN`):

- Для `rpv…`: `INPUT -i <мост>` — `ESTABLISHED,RELATED` пропускается, остальное `DROP`; в `DOCKER-USER` — переход в свою цепочку `RADITI-<мост>` для `-i <мост>`, в ней: `ESTABLISHED,RELATED` — `RETURN`; назначения 0.0.0.0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.168/16, 198.18/15, 224/4, 240/4 и подсети `--refuse` — `DROP`; остальное — `RETURN` (дальше — правила Docker, интернет открыт). ## 11. Результат (26.10.2026)

Срезы 58.1–58.5 сделаны в дереве `raditi-preview`, ветка `feat/preview-single-container` от `main` `f85bef69`; ничего не закоммичено и не отправлено.

**Отступления от договора §10** (исполнение показало, что иначе нельзя):

- **DNS.** Запись `/etc/resolv.conf` из `init.sh` невозможна: при read-only корне Docker монтирует этот файл только на чтение под `runc` и под `runsc` (замер 26.10.2026). Вместо неё — пересыльщик имён `infra/preview/dns.mjs` (uid 10001) на `127.0.0.11:53` внутри контейнера, куда указывает `/etc/resolv.conf`; он спрашивает `RADITI_DNS_SERVERS`. Ради порта 53 без возможностей контейнер получает sysctl `net.ipv4.ip_unprivileged_port_start=0` (он действует только в своём netns; опубликован только 8080). Под `runc` раньше пересыльщика отвечает DNS Docker с теми же серверами (`Dns`). `PREVIEW_DNS_SERVERS` принимает только публичные адреса: частный или loopback правила моста закрыли бы.
- **MariaDB 11.8.9, а не 11.4.** Для Debian 13 (trixie), на котором стоят образы PHP 8.2 и новее, 11.4 не собирается; 11.8.9 есть для bullseye, bookworm и trixie. Ключ архива mariadb.org проверяется отпечатком. Временная база дампа (`PREVIEW_DB_IMAGE`) остаётся на 11.4. Анонимных учётных записей 11.8 не создаёт; временные файлы базы — в `/run/mysqld/tmp` (tmpfs uid 999, 0700), а не в общем с PHP `/tmp`.
- **Учётные записи базы.** `preview` с `127.0.0.1` и `localhost`; root — `unix_socket` или пароль, только `localhost`: root базы — root контейнера на сокете. Готовность базы `init.sh` проверяет от root по сокету.
- **Запуск и остановка.** `STOPSIGNAL SIGTERM` (у базового образа — SIGWINCH, и каждый `docker stop` шёл до срока); на SIGTERM init останавливает базу (`SHUTDOWN`) и выходит с 0. Ещё один файл готовности — `/run/raditi-forward/dns.ready`. Данные без метки `.raditi-ready` считаются остатком упавшего первого старта и создаются заново.
- **Команды платформы** идут без домашнего каталога (`HOME=/nonexistent`): `/tmp` общий с PHP, и настройки или пакеты инструмента, подложенные туда кодом сайта, прочла бы команда платформы.

**Ревью (spec-reviewer, 26.10.2026)** — семь замечаний:

1. Правила моста ставились только при сборке, а перепроверки, обещанной «Решением владельца», не было: перезагрузка межсетевого экрана хоста оставила бы работающий предпросмотр открытым к хосту и платформе до следующей сборки. Исправлено: метод порта `PreviewRuntime.checkBoundary` (помощник `check` с тем же `--refuse`, под `runsc` — ещё правило моста браузера) и шаг `boundary` сборщика `core` — каждый работающий и никем не удерживаемый предпросмотр раз в 2 минуты, не больше 10 за проход; правила не целы — контейнер останавливается сразу, предпросмотр собирается заново как потерянный, и сборка ставит правила снова. Docker-тест среды снимает настоящий переход `DOCKER-USER` и видит отказ, затем сборку, которая возвращает правила.
2. Первая пересборка предпросмотра протокола 1 писала бы в пустой том только разницу: `inspect` отвечал состоянием по остаткам протокола 1. Исправлено: без контейнера `preview` протокола 2 `inspect` отвечает `null`, и сборка пишет дерево целиком.
3. Открытый интернет PHP и медиатека в дереве предпросмотра — вопрос владельцу (ниже).
4. Два одновременных `install` одного моста не случаются: сборки одного предпросмотра идут под его арендой; проверка `boundary` не трогает предпросмотр, который держит работа. Оставлено без изменений.
5. `PREVIEW_DNS_SERVERS` с непубличным адресом — теперь ошибка конфигурации `core`; комментарии о DNS поправлены.
6. Без образа правил предпросмотр не настроен (`not_configured`), `core` стартует — комментарий поправлен; отдельной проблемы конфигурации нет, как и без образов предпросмотра.
7. Временные файлы базы — свой tmpfs; анонимных учётных записей у 11.8 нет; `HOME` команд платформы — несуществующий каталог.

**Ждёт владельца.** Документы медиатеки сайта (папка `uploads`) лежат в дереве предпросмотра, а PHP, который пишет агент, теперь может отправить их на любой публичный хост — раньше выход был только к хостам переменных клиента.
