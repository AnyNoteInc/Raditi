# B13: локальная проверка шлюза с настоящими CLI

Стенд проверяет основной шлюз, выдачу ключей, пул и учёт на синтетических провайдерах. Он использует настоящие Codex CLI 0.158.0 и Kimi CLI 2.1.1, PostgreSQL 17, OpenBao 2.7, mTLS-прокси и `sandbox-gw`. Роли `core` и `llm` работают отдельными процессами с разными AppRole и общим пользователем БД `raditi`.

## Запуск

Из корня репозитория после установки зависимостей и генерации Prisma:

```sh
pnpm verify:llm-gateway
```

Команда собирает закреплённые образы CLI и сетевого ограничителя, собирает orchestrator, создаёт собственный стек и удаляет его после проверки. Образ CLI строится от рабочей стадии образа песочницы (`infra/sandbox/Dockerfile`, цель `runtime`, CLI из lock-файла); `cli.Dockerfile` добавляет только обвязку стенда и сверку версий `npm ls`. Для повторного прогона без сборки: `pnpm --filter orchestrator verify:llm-gateway --no-build`. Нужны локальный Docker, Node/pnpm проекта и OpenSSL.

Рабочие `.env`, PostgreSQL, OpenBao, конфиги и файлы входа пользователя не читаются. Все аккаунты и токены создаёт фейк; обращения к подпискам владельца отсутствуют. Управляющие порты публикуются только на loopback. CLI получает только ключ хода через stdin обёртки; внутри его процесса ключ передаётся через окружение. Подписочные токены доступны роли `llm` через Vault.

CLI находится во внутренней сети с запретом DNS и прямого выхода; разрешён только `sandbox-gw`. Доверенная сеть стенда соединяет контейнеры с процессами на хосте. Фейк не делает исходящих запросов; тестовая обёртка mTLS-прокси направляет разрешённые имена исключительно в контейнер фейка. Настоящие проверки прокси и шлюза используются без отключения TLS. Это локальный `runc`-стенд; он не подтверждает изоляцию под gVisor или зарубежный канал.

## Состав проверки

| Область | Проверяемый результат |
| --- | --- |
| БД и Vault | Bootstrap до и после миграций, владелец `raditi`, отдельные политики, обязательный CAS, одна версия подписочного секрета |
| Вход | Device-flow Codex, отказ чужой идентичности, Kimi со stdin |
| Ключи | Выдача, восстановление, повтор, конкуренция, ёмкость аккаунта, гейт данных клиента |
| Настоящие CLI | План и текст, два инструментальных круга, JSON-схема, resume, повтор после 503, окончательный отказ без повтора |
| Драйверы | `prepare` и `command` настоящих драйверов Codex и Kimi на рабочем образе песочницы: MCP через маршрут `/mcp` `sandbox-gw` к синтетическому MCP с рабочим списком инструментов (`site_info`), строгая схема итога, `--image`, exec и resume у каждой оболочки |
| Сбои провайдера внутри потока | После HTTP 200: Codex — четыре окончательных исхода (ход завершается за один запрос к провайдеру) и один временный (ровно один повтор); Kimi — три окончательных и один временный. Верный `last_refusal`, здоровье аккаунта не тронуто |
| Граница шлюза | Политика JSON, модель, маршруты, бэкенд, адрес источника, размер тела и запрет прямого выхода |
| Пул | Окна квоты, временная пауза, подтверждающая проба, ошибки содержимого, платёж, кредиты и размыкатель usage |
| OAuth | Два процесса и один refresh, остановка до HTTP и после CAS, недоступность Vault после ответа провайдера |
| Учёт | Точные Decimal-ставки, параллельные резервы и превышения, обрывы, потерянные потоки и недоступность БД |
| Вывод | Обычное дренирование, автоматический OAuth revoke, аварийный отзыв, уничтожение версий |
| Секретность | Проверка маркеров промпта, ключей, токенов всех ротаций и тела ошибки в журналах, аудите Vault и дампе БД |

Для длинных сроков ожидания проверка явно сдвигает только даты синтетических строк: окна квоты, время открытия размыкателя и возраст потерянного вызова. Аварийные окна refresh проверяются отдельным процессом с тестовыми барьерами вокруг настоящего HTTP/CAS; паузы PostgreSQL/OpenBao и остановки процессов настоящие. Это не проверка многоминутного ожидания по настенным часам.

CI: `.github/workflows/llm-gateway.yml`. Он запускает тот же стенд без ключей внешних сервисов; журналы CLI, запросы и дампы не публикуются как артефакты. Workflow стартует также по изменениям `packages/agent-drivers/**` и `packages/sandbox-providers/runtime/**`: стенд — единственный проход драйверов против политики шлюза.

На Linux файлы в bind mounts создаёт контейнер CLI под uid 10001, и пользователь раннера удалить их не может. Поэтому стенд опустошает свои каталоги изнутри контейнера CLI и только потом удаляет их; запасной путь — одноразовый контейнер с root. Логика владения проверена с настоящими uid 1001 и 10001 в Linux-контейнере. Файлы, записанные CLI в рабочий каталог, стенд драйверов читает с хоста, а при отказе в доступе — через `docker exec cat` в том же контейнере; эта ветка на macOS не проверяется. Прогон GitHub Actions ещё не выполнялся.

## Оставшиеся гейты

Режимы `--real` и `--record` пока не реализованы; команда отвергает их. Проверка владельца на настоящих подписках, настоящий Kimi, зарубежный `egress-1` и полный продуктовый сценарий с WordPress остаются отдельными открытыми гейтами. Синтетическая запись допуска трансграничной передачи существует только в одноразовой БД и не является юридическим разрешением.

## Результат после ревью — 04.10.2026

`pnpm verify:llm-gateway` — **53 проверки**, CLI Codex 0.158.0 и Kimi 2.1.1; пять зелёных прогонов подряд на итоговом дереве (один со сборкой образов на статической стадии, один со сборкой и три `--no-build` на стадии шлюза и драйверов). Число выросло с 43 за счёт прохода драйверов, стадии сбоев внутри потока и закрепления клиентского сертификата `llm` в прокси выхода (`EGRESS_CLIENT_SHA256`).

Что изменилось в поведении, которое проверяет стенд:

- Сбой выхода после допуска и закрытый допуск — короткий 503 с `Retry-After` 30 секунд и `last_refusal = transient`; окончательный `egress` — только при регионе, подтверждённом провайдером. Прежние ожидания окончательного `egress` и 503 `raditi_busy` с `Retry-After` 1 для закрытого допуска из стенда убраны.
- Три ответа 402 подряд считаются одной проверкой оплаты, если пришли внутри одной паузы. Шаг «три 402 переживают перезапуск `llm`» перед каждым запросом состаривает прежние строки 402 на 20 минут.
- Переполнение окна модели (`context_length_exceeded`) записывается как `request_rejected`.
- Отключение клиента после окончания потока провайдера оставляет `failed`, а не `aborted`. До исправления шаг «Kimi повторяет временный сбой внутри потока» падал примерно раз в четыре прогона.

Измеренный факт: Codex 0.158.0 в режиме code mode не объявляет инструменты MCP в теле запроса, а держит их внутри инструмента `exec` (`tools.mcp__raditi__*`). Kimi объявляет `mcp__raditi__site_info` в запросе.

Проба CLI через настоящий профиль контента MCP (`wp_rest`, `restore`) в этот стенд не входит: это полный локальный e2e и P12.

## Фактический результат — 30.09.2026

Полный `verify:llm-gateway --no-build` завершился с кодом 0: **43 группы проверок**. Образы CLI и сетевого ограничителя, а также orchestrator перед этим собраны. Проверены настоящие повторы обеих CLI после 503, отсутствие повторов при окончательном отказе, Kimi usage из последнего чанка и продолжение Codex CLI во время штатного дренирования аккаунта. Kimi запускается с явными `KIMI_MODEL_MAX_OUTPUT_SIZE=65536` и `KIMI_MODEL_THINKING_EFFORT=low`; это согласует его стандартный запрос со строгой политикой шлюза.

Дополнительные проверки:

- 193 инфраструктурных теста прошли, один существующий тест пропущен; проверки типов, lint, границ зависимостей и переменных окружения прошли.
- Регрессия исправления B12 прошла общий стенд `verify:db`: 1364 теста orchestrator и 228 тестов БД. Аккаунт с незавершённым первым импортом теперь можно вывести после явного подтверждения отзыва в консоли; обычный Codex по-прежнему требует автоматического OAuth revoke.
- Остановка SIGTERM после настоящих инструментов Codex удалила CLI, ограничитель сети, стек и оба дочерних процесса. Дополнительно устранён кэш Prisma за пределами каталога стенда; повторная остановка после миграций подтвердила отсутствие оставшихся контейнеров, сетей, временных файлов и потомков процесса.
- Для ошибок запуска дочерних процессов добавлены семь проверок: отсутствие исполняемого файла, раннее завершение, таймауты запуска и остановки, незавершённый запрос и одновременная остановка.

Списание клиенту и его окончательный потолок относятся к P12: этот стенд подтверждает расход шлюза, резервы, превышения и `billable=false` при потере потока по вине платформы. Новый CI workflow добавлен и проверен локально; удалённый запуск GitHub Actions не выполнялся.
