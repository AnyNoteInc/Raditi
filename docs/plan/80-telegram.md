# План 80. Telegram — второй канал чата

Указание владельца от 15.11.2026: «давай телеграм, пиши план для новой сессии». Это задача roadmap **P13** («Telegram через egress-прокси. Сообщения, файлы до 20 МБ, голосовые. §11, §20»). Канал назван в первой строке описания продукта: «владелец пишет в веб-чат или Telegram, что поменять на сайте».

Этот файл — задание для новой сессии. Сначала ответы владельца на вопросы §2 (у каждого есть значение по умолчанию), затем срезы §5 по порядку. Каждый срез — отдельный коммит, в конце — PR, CI, выпуск.

Работа — в отдельной ветке `feat/telegram` (своё дерево `raditi-telegram`, от свежего `main`).

## 4. Устройство (рекомендация)

- **Приём — web** (spec §3: web принимает вебхуки Telegram). Маршрут `apps/web/src/app/api/webhooks/telegram/route.ts` делает следующее:
  1. проверяет секрет и тело (zod, предел размера);
  2. пишет `telegram_updates` с уникальным `update_id`: повтор Telegram ничего не делает дважды;
  3. находит пользователя по `channel_identities`, а чат — по теме или «текущему чату»;
  4. вызывает те же сервисы, что tRPC.

  Файлы и голос web скачивает сам через `getFile` и `TELEGRAM_PROXY_URL` (тогда переменную нужно отдать и web), кладёт в `raditi-inbox` по правилам вложений. Голос распознаёт тем же кодом SpeechKit. Без привязки бот отвечает одной фразой со ссылкой на кабинет.
- **Отправка — `core`.** Новый раздел `apps/core/src/telegram` (`TelegramModule`, только при `TELEGRAM_BOT_TOKEN`) с очередью BullMQ `telegram` через outbox:
  - ответы и вопросы агента, кандидат («Готово, посмотрите и выпустите» — ссылка на чат), сбои, «Продолжить?»;
  - уведомления (`ChatNotify` получает третий канал).

  Повтор по `retry_after`, предел 30 сообщений в секунду на бота и 1 в секунду на чат. Markdown ответа превращается в разрешённый Telegram HTML, длинное режется по 4096 знаков. Страницы и документы агента идут ссылкой в кабинет, файлы `/workspace/out` — документом до 50 МБ.
- **Где ветвиться.** Канал — свойство чата (`chat_sessions` с `channel = telegram`), не `if` в сервисах. Сервисы чата не знают о Telegram: web и `core` зовут их как обычно, а доставку решает подписчик событий ленты.
- **Секреты** (правило 2): `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET` — в OpenBao сервера (`platform-secrets.mjs set app/web …` и `app/core`), в рендер — web и `core`.
- **Новые таблицы** (одна миграция):
  - `telegram_link_codes` — хеш, пользователь, срок, использован;
  - `telegram_updates` — `update_id`, статус, время, без текста или с текстом на 7 дней для разбора — решить в 80.2;
  - признаки на `channel_identities`: уведомления, текущий чат.

## 7. Решения разведки

Ответы владельца от 15.11.2026: Т1 — «да, разрешаю» (исключение из правила 1, как Л12); Т2 — один бот `@raditi_bot`, токен владелец положил в локальный `.env.telegram` (вне git) для проверки и выкладки; Т10 — пока пул бесплатных прокси; Т3–Т9 и Т11 — «да, всё по умолчанию».

Разведка 80.0 (15.11.2026, бот `@raditi_bot`):

- **Вебхук до сервера не доходит.** `setWebhook` на `https://raditi.ru/api/webhooks/telegram-probe` и сообщение боту: `getWebhookInfo` — `last_error_message: Connection timed out`, `ip_address: 45.8.250.117`. Telegram не открывает соединение к серверу в России, как и сервер — к `api.telegram.org`. Решение по Т9: приём — опрос `getUpdates` в `core` через `TELEGRAM_PROXY_URL` (тот же путь, что у бота заявок), `core` передаёт каждое обновление обработчику web `POST /api/webhooks/telegram` с заголовком `X-Telegram-Bot-Api-Secret-Token` (секрет `TELEGRAM_WEBHOOK_SECRET`); web отвечает 200, только когда записал и обработал обновление, и только тогда `core` подтверждает его следующим `offset`. Повтор после сбоя безопасен: `telegram_updates.update_id` уникален. Тот же маршрут годится и для настоящего вебхука, если сервер когда-нибудь станет достижим. Тестовый вебхук снят (`deleteWebhook`, `drop_pending_updates`).
- **Темы в личном чате есть** в Bot API: с 9.3 (31.12.2025) `message_thread_id` и `is_topic_message` в личных чатах, `User.has_topics_enabled` у `getMe`; с 9.4 (09.02.2026) бот сам создаёт тему (`createForumTopic` в личном чате), `allows_users_to_create_topics`. Режим включает владелец бота в мини-приложении @BotFather; у `@raditi_bot` 15.11.2026 он ещё выключен (`has_topics_enabled: false`). Решение по Т4: у каждого чата Радити своя тема, когда режим включён (`getMe` при старте `core`); без режима или без темы в сообщении — «текущий чат» (`/new` начинает новый, `/chats` — последние кнопками). Код ветвится по `has_topics_enabled` и `message_thread_id`, а не по настройке.

Ревью по spec (15.11.2026) нашло восемь замечаний; исправлены шесть:

- после отвязки или смены аккаунта чаты этого Telegram отвязываются, а `core` не шлёт чату, чей Telegram больше не привязан (правило 1);
- обновление, которое уже начало чат и упало до конца, при повторе идёт тем же путём `createDialog`, а не вторым сообщением, поэтому второго прохода и списания нет; `core` ждёт web до 5 минут;
- обновление бросается только тогда, когда web не может его прочитать (400, 413); пока web недоступен, оно ждёт, и слова клиента не теряются;
- распознанный голос проверяется на пароль до того, как бот его повторит;
- в правило 1 `CLAUDE.md` вписано исключение Т1;
- опрос вынесен в свою очередь и не держит ответы.

Остались известными пределами:

- альбом Telegram (`media_group_id`) приходит несколькими сообщениями — первое начинает чат, остальные идут в очередь отдельными словами;
- файл, принятый до отказа второго файла того же сообщения, остаётся неотправленным вложением и истекает через сутки.

После первой живой проверки (15.11.2026, запросы владельца того же дня; spec §20, Т14, Т15):

- «Принято…» убрано; вместо него одно сообщение о ходе работы, правка раз в 6 с — бегущая полоска, время и что агент делает сейчас — и «печатает…»; ответ прохода его удаляет;
- служебное сообщение темы («тема создана») больше не получает ответа «Напишите, что сделать.»;
- удаление в обе стороны: «Удалить» в кабинете удаляет тему, `/delete` в теме и удалённая клиентом тема удаляют чат в кабинете;
