# План 80. Ключи MCP-серверов через Vault

Запрос владельца от 15.11.2026: у MCP-сервера, который владелец добавляет в проект, может быть авторизация — ключ в заголовке или вход OAuth; «спроектируем план доставки ключей в агента через vault». Макеты окна подключения — холст «Плюс в поле чата», макеты 8 и 9.

Статус: проект, кода нет. Решения с пометкой «по умолчанию» ждут владельца (§6).

## 1. Что сейчас

- MCP-серверы проекта — таблица `site_agent_skills` (план «Навыки агента», 26.10.2026; в кабинете — «Навыки агента», на холсте — «MCP-серверы»). Адрес — `https://` на 443 или 8443, с путём, без логина, запроса и фрагмента (`parseAgentSkillUrl`). Секретов у строки нет: «a server that wants a key is not taken yet» (`packages/domain/src/agent/skills.ts`).
- `core` кладёт серверы в план хода (`turnSkillsOf` → `context.skills`), драйвер OpenCode пишет их в конфигурацию CLI как `type: 'remote'`, `oauth: false`, без заголовков (`packages/agent-drivers/src/opencode.ts`, `skillServer`).
- CLI ходит к серверу сам, через прокси выхода `client-egress.mjs`: `CONNECT` к публичному имени, TLS от песочницы до сервера сквозной. Прокси в поток не заглядывает и заголовок добавить не может.
- Образец, на который опирается план: ключ веб-поиска. Он лежит в Vault `subs/search/yandex`, его читает только `apps/mcp` (`WebSearchKey`, кеш 30 с) и ставит в заголовок запроса к Яндексу. Песочница и модель ключа не видят.

## 2. Что должно остаться верным

1. **Правило 2.** Ключ, токены OAuth и секрет клиента OAuth лежат только в Vault. В базе — `credential_refs`, в песочнице, плане хода, `turn_assignments.plan`, логах, событиях, снимках и S3 их нет. Форма пишет секрет в Vault и обратно его не читает.
2. **Правило 5.** Долгоживущих секретов в песочнице нет. В песочницу идёт только токен MCP хода — тот же, что у сервера `raditi`.
3. **Правило 8.** Ни драйвер, ни ядро не знают, какой это сервис. Ретранслятор универсален: адрес, заголовок, значение.
4. **Правило 1.** Что агент отправляет стороннему серверу, уходит из платформы. Это принято решением владельца от 26.10.2026 для навыков и не меняется. Новое только одно: платформа сама ходит к адресу, который назвал клиент (§3.4).
5. Серверы без авторизации работают, как раньше, пока владелец не решит иначе (§6, вопрос 1).

## 3. Устройство

### 3.1. Путь запроса

```
OpenCode (песочница)
  └─ http://sandbox-gw/mcp/skill/<name>         токен MCP хода в Authorization
       └─ apps/mcp  /mcp/skill/<name>           допуск по токену, как у /mcp
            ├─ Vault kv/sites/<siteId>/mcp/<name>   заголовок и значение, или токены OAuth
            └─ https://<адрес сервера>          свой TLS, заголовок клиента, ответ потоком назад
```

Сервер с авторизацией попадает в конфигурацию CLI не своим адресом, а путём ретранслятора: `url: <mcp.url>/skill/<name>`, `headers: { Authorization: Bearer {file:<канал токена MCP>} }` — тот же канал, что у сервера `raditi`. Сервер без авторизации — как сейчас, напрямую через прокси выхода.

Отвергнутый вариант — прокси выхода с подменой TLS: пришлось бы выдать песочнице доверенный CA платформы, и он подменял бы любой TLS; это ломает границу правила 5. Второй отвергнутый вариант — `apps/mcp` как клиент MCP, который отдаёт инструменты чужого сервера под именами `raditi_<name>_<tool>`. Этот путь чище для учёта, но нужны свой клиент MCP, кеш списков инструментов и перевод уведомлений и потоков. Прозрачный HTTP-ретранслятор сохраняет протокол сервера (Streamable HTTP, SSE, `Mcp-Session-Id`) как есть.

### 3.2. Ретранслятор в `apps/mcp` (раздел `src/skill-relay`)

Новый раздел приложения `mcp` со своим модулем. Подключается всегда: без строк с авторизацией ему просто нечего ретранслировать.

1. **Допуск.** Тот же `McpAccess`, что у `/mcp`: токен хода, текущее назначение и аренда. Сервер ищется по `siteId` допуска и `<name>` из пути, а не из аргументов. Строка должна быть включена, `auth_kind <> 'none'`, `auth_state = 'ok'`, и сервер должен входить в `context.skills` плана хода. Иначе — 404 без подробностей.
2. **Секрет.** Чтение `kv/sites/<siteId>/mcp/<name>` под AppRole `mcp`, кеш до 60 с, как доступ сайта. Версия ссылки (`credential_refs.key_version`) сбрасывает кеш.
3. **Адрес.** Только адрес строки, к нему ничего не дописывается. Методы `POST`, `GET` (SSE) и `DELETE`. Перенаправления не выполняются.
4. **Соединение.** Имя разрешается на каждое соединение. Адрес проверяется функциями `ipLiteral` и `isPrivateAddress` из `@repo/ip-address` и списком `SANDBOX_EGRESS_REFUSED_SUBNETS`; соединение идёт на проверенный адрес с SNI имени, в обход повторного DNS (защита от подмены DNS между проверкой и соединением).
5. **Заголовки.** Входящие `Authorization`, `Cookie` и hop-by-hop заголовки снимаются; проходят `Content-Type`, `Accept`, `Mcp-Session-Id`, `Mcp-Protocol-Version`, `Last-Event-ID`. Добавляется заголовок клиента (или `Authorization: Bearer <access_token>` у OAuth). Из ответа снимаются `Set-Cookie` и `WWW-Authenticate`.
6. **Маскирование.** Значение секрета вырезается из потока ответа (буфер с перекрытием на длину значения) — как переменные клиента в событиях хода. Значение короче 8 байт не принимается формой.
7. **Пределы.** Тело запроса — 16 МиБ (как у `sandbox-gw`), запрос — 10 минут, одновременных запросов на ход — 8. Ни тела, ни заголовков в логе: имя сервера, хост, код, байты, длительность.
8. **Сбой авторизации.** Ответ сервера 401 или 403: у OAuth — одно обновление токена (§3.4, п. 5 OAuth) и один повтор; иначе строка получает `auth_state = 'needs_login'` и `last_error`, а агенту уходит ошибка JSON-RPC с текстом для клиента: «Сервер «Меню кофейни» просит войти заново. Откройте «MCP-серверы» в настройках проекта». Сервер с `needs_login` из следующих ходов выпадает (`turnSkillsOf`).

`sandbox-gw` получает маршрут `/mcp/skill/<name>` — один шаблон пути (`SKILL_RELAY_PATH` из `@repo/domain`: одно имя навыка и ничего после него) на тот же upstream, с теми же заголовками и пределами, что у `/mcp`. Какие имена этому ходу можно, решает ретранслятор по допуску хода и строкам сервера, а не шлюз.

Токен MCP хода доходит до CLI через именованный канал, который отдаёт значение один раз, а CLI читает каждую ссылку `{file:…}` конфигурации отдельно. Поэтому у каждого сервера через ретранслятор свой канал `/run/raditi/secrets/mcp-skill.<n>` с тем же токеном: обёртка делает их из токена сама (`mcpCopies`), хост новых файлов не кладёт.

### 3.3. Хранение

- `site_agent_skills` — новые столбцы (миграция с сохранением данных): `auth_kind` (`none` | `header` | `oauth`, по умолчанию `none`), `header_name` (`VARCHAR(64)`, только у `header`), `auth_state` (`ok` | `needs_login` | `failed`), `auth_checked_at`, `auth_error` (код, не текст сервера), `oauth` (JSON без секретов: issuer, `client_id`, точка выдачи токенов, scope, `expires_at`). CHECK: у `none` нет ни заголовка, ни `oauth`, и состояние `ok`; у `header` есть заголовок; у `oauth` есть `oauth`; у навыков платформы авторизации нет. Отдельного столбца ссылки нет: путь секрета выводится из сайта и имени (`agentSkillSecretPath`), а строка `credential_refs` с этим путём нужна, чтобы «Удалить проект» затёр секрет вместе с доступами.
- `CredentialKind` получает `mcp_server`. `vault_path` — `kv/sites/<siteId>/mcp/<name>`.
- Vault KV v2, одна версия (`max_versions = 1`), CAS:
  - `header`: `{ "value": "<значение>" }` — имя заголовка в базе, значение в Vault;
  - `oauth`: `{ "access_token", "refresh_token", "client_secret"? }`.
- Политики:
  - `sites-writer` (web) — уже пишет `kv/data/sites/*`, этого хватает; чтения нет.
  - `mcp-content` (mcp) — `read` на `kv/data/sites/+/mcp/*`; `update` для обновления токенов OAuth по CAS добавит срез 80.6 (версия CAS приходит с чтением).
  - `core` к этим путям доступа не получает.
- Удаление сервера и «Удалить проект» перезаписывают значение пустой версией, как переменные сайта (приём 25.10.2026).
- Чат без проекта своих серверов не имеет (§6, вопрос 3).

### 3.4. Подключение в кабинете (макеты 8 и 9)

**Ключ.**

1. Форма шлёт адрес, имя заголовка и значение в `siteAgentSkills.add` (меняют `owner` и `admin`, как сейчас).
2. Процедура в web проверяет адрес (§3.2, п. 4), делает `initialize` и `tools/list` к серверу с этим заголовком — значение ещё в запросе, Vault читать не нужно, — и возвращает число инструментов.
3. Только после успеха: запись в Vault с CAS, затем одна транзакция — строка сервера, `credential_refs`, запись аудита. Значение не возвращается ни в ответе, ни в логах.
4. «Проверить снова» у сохранённого сервера не читает секрет: показывает `last_ok_at` и `last_error` последнего хода. Сменить ключ — ввести новое значение.

**OAuth** (спецификация MCP, авторизация: RFC 9728, RFC 8414, PKCE, RFC 8707).

1. Проверка адреса без ключа: ответ 401 с `WWW-Authenticate: Bearer resource_metadata=…` — форма сама переключается на «Вход (OAuth)».
2. Web читает метаданные защищённого ресурса и сервера авторизации (каждый адрес — через ту же проверку публичности), регистрирует клиента — динамически (RFC 7591) или документом метаданных клиента, если сервер его объявляет; `redirect_uri` — `https://raditi.ru/api/mcp-oauth/callback`.
3. Попытка входа — зашифрованная cookie web (верификатор PKCE, `state`, id сервера, 10 минут, ключ — от `BETTER_AUTH_SECRET`); в базе её нет.
4. Клиент входит в новой вкладке и разрешает доступ, callback сверяет `state`, меняет код на токены (`resource` — адрес сервера) и пишет их в Vault, как в п. 3 ключа.
5. Обновляет токены только `apps/mcp`: перед запросом, если до `expires_at` меньше 60 с, или после 401. Под замком `pg_advisory_xact_lock` по серверу, с записью в Vault по CAS: восемь параллельных ходов не обновят токен восемь раз, а ротация refresh-токена не потеряется. Отказ сервера авторизации — `needs_login`.

### 3.5. Что видит агент и клиент

- Агент видит сервер под его именем и его инструменты (`<name>_<tool>`), как сейчас. Ни ключа, ни токена в его конфигурации, файлах и окружении нет.
- В «Ходе работы» — строки вызовов сервера (макет 10); при `needs_login` — фраза в ответе агента и «Войти заново» в подменю «MCP-серверы».

## 5. Риски

- **SSRF из `apps/mcp` и web.** Платформа сама соединяется с адресом клиента и с адресами из метаданных OAuth. Защита — проверка адреса на каждое соединение и соединение на проверенный адрес (§3.2, п. 4), плюс подсети платформы `SANDBOX_EGRESS_REFUSED_SUBNETS`, обязательные в production у обоих приложений: иначе сервером владельца мог бы оказаться публичный адрес самой платформы (её Traefik).
- **Утечка значения через ответ.** Сервер может вернуть ключ в теле ответа — маскирование потока (§3.2, п. 6) это закрывает; сервер, который возвращает его в изменённом виде, не закрывает ничто.
- **Нагрузка на `apps/mcp`.** Поток каждого вызова теперь идёт через app-ВМ. Пределы §3.2, п. 7, и метрика ретранслятора без идентификаторов в метках.
- **Сервер просит ключ, которого нет у владельца.** Решается не платформой: форма говорит, что сервер не подключился, и почему.

1. Серверы без авторизации тоже вести через ретранслятор (один путь, журнал, проверка адреса платформой) или оставить напрямую? По умолчанию — напрямую, как сейчас.

3. Чат без проекта: свои серверы рабочего пространства с ключами — да или нет? По умолчанию — нет.
4. Несколько заголовков у одного сервера (например, ключ и id аккаунта) или один? По умолчанию — один.
5. Ключ из уже заведённой переменной проекта (`/projects/{id}/vault`) вместо отдельного поля? По умолчанию — отдельное поле: переменные идут в команды агента, а ключ сервера туда идти не должен.
