## 1. Запрос

Слова постановки — в описи и договорах ниже. Главное, что задаёт постановка:

- **Чистая комната.** Код htmldrop не открываем, его пакеты не ставим, тексты и разметку не переносим. Внешних
  хостингов страниц нет: правило 1. Нового приложения нет. Новая зависимость — только из каталога pnpm.
- **Агент.** Семейство MCP `pages` (`raditi_page_*`, `raditi_doc_*`):
  - инструменты: `page_publish`, `page_list`, `doc_create`, `doc_section_write`, `doc_section_remove`, перестановка,
    `doc_read`, `doc_finish`;
  - снять страницу и поставить пароль агент не может.
- **Документ.** Порядок из восьми шагов (скелет → материал → по разделу → находки в документ → «Источники» →
  проверка → одна строка → правки по разделам).
- **Клиент.** Строка `feed.page`, живая карточка документа, «Скачать .md», «Опубликовать по ссылке», список страниц
  рабочего пространства.
- **Зритель.** `https://<slug>.<PAGES_BASE_DOMAIN>/`:
  - slug не меньше 128 бит;
  - форма пароля через POST, cookie только этого поддомена;
  - 410 у снятой и истёкшей страницы, 404 у несуществующей (срока по ответу владельца нет — Ст14).
- **Безопасность.**
  - отдельный регистрируемый домен;
  - строгий хост;
  - CSP-песочница и заголовки — константой в `@repo/domain`;
  - проверки содержимого (ключ хода, значения переменных клиента, форма пароля наружу, встроенные токены);
  - лимиты;
  - метрики без id;
  - секрет cookie в Vault, медленный хеш пароля.
- **Двенадцать решений** владельцу — со значениями по умолчанию.

## 3. Что должно остаться верным

1. **Правило 1.** Содержимое страниц и документов — только в PostgreSQL и S3 в России. Внешних хостингов нет.
   Модель видит только то, что агент сам написал или прочитал обычными средствами хода.
2. **Правило 2.**
   - Секрет подписи cookie пароля — путём секретов платформы (Vault → рендер на хосте), как `PREVIEW_SESSION_SECRET`.
   - Пароль страницы не проходит через модель. В базе — только хеш `scrypt`.
   - Значения переменных клиента и ключ хода на публичную страницу не попадают (Ст8, Ст19).
3. **Правило 3.** Страница — не выкладка: на сайт клиента она ничего не пишет и `/release` не касается.
4. **Правило 5.** Песочница не получает ни S3, ни presigned-ссылок, ни новых выходов. Содержимое страницы уходит из
   песочницы только outbox законченного хода (Ст6) или разделами через MCP (Ст20).
5. **Правило 8.** Порты не знают имени драйвера. Семейство `pages` объявляется по требованиям хода, а не по стеку.
6. **Правило 10.** Тексты кабинета, заглушек и формы пароля — по-русски и на «вы».
7. **Границы приложений.**
   - `apps/preview` на пути запроса страницы достаёт только `domain` и `db` (`preview-request-path` в новом разделе —
     то же правило).
   - `mcp-minimal-packages` и `preview-minimal-packages` не расширяются.
   - Роли `mcp` не нужен S3 в production.
8. **План 66.** Путь `feed.file` для прочих файлов не меняется: файл, не названный резервом страницы, остаётся
   файлом чата и документом плана 67.
9. **План 67.**
   - `chatDocumentsOf`, вкладка «Документы» и просмотр `/v/` остаются и страниц не показывают (Ст27).
10. **Метрики.** Без `task_id`, `page_id` и slug в метках.

    сертификатов. Корень `pages.raditi.ru` — обычным HTTP-01, как `raditi.ru`. Запись DNS
    `*.pages.raditi.ru` → `45.8.250.117`.
  - **Чем платим за поддомен `raditi.ru`.** Страница теперь одного сайта (same-site) с кабинетом: браузер считает
    запрос со страницы к `raditi.ru` своим и пошлёт с ним cookie `SameSite=Lax` и `Strict`. Что держит:

      она не может, в том числе с `Domain=raditi.ru` (защита от подмены cookie);

    - изменяющие процедуры кабинета не опираются на `SameSite` одним: tRPC и маршруты web проверяют `Origin` — это
      проверка в срезе 69.7 (кабинет) и строка стенда;

    Позже — заявка `pages.raditi.ru` в Public Suffix List: тогда каждая страница станет своим сайтом и для браузера
    (вопрос 2).

### Содержимое и проверки

- **Ст5. Вид страницы — `html` или `doc`.** Markdown-файл публикуется так же, как документ: доверенный код рисует
  его в HTML для чтения (Ст11). Поле `kind` в базе: `html` | `markdown` | `doc` — откуда пришло содержимое. Отдаётся
  всегда HTML.
- **Ст6. Содержимое страницы приходит файлом outbox** (решение 1, вариант Б).
  - `page_publish({ file, title, pageId? })` проверяет, что `file` — имя для outbox (`outboxFileNameSchema`). Он
    резервирует страницу: новая строка `pages` со slug либо новая версия у `pageId`, состояние `pending`. Адрес
    возвращается сразу.
  - `core` после хода читает outbox тем же `readOutboxArchive({ refused })`. Файл, названный резервом, становится
    версией страницы, а не `feed.file`.
  - Если резерв не исполнен (файла нет, файл отклонён, проверка Ст8 не прошла, ход упал), страница новая — она
    остаётся `pending` и отвечает 404. Новая версия существующей не появляется, старая отдаётся дальше. Клиенту об
    этом говорит строка `feed.page_left` (по образцу `feed.file_left`).
  - Агент называет адрес в ответе, а ответ клиент читает после конца хода, когда страница уже ожила или строка
    сказала, почему нет.
- **Ст7. Документ — в PostgreSQL разделами, через MCP во время хода** (постановка), без outbox. Всё, что меняет
  видимое клиенту или зрителю, вступает в силу в конце хода, после проверки `core` (Ст19):
  - текст разделов;
  - версия `doc_finish`;
  - публикация `page_publish({ docId })` — её Markdown рисуется в HTML (Ст11) и становится версией страницы.

  Так же, как файл страницы из outbox (Ст6).
- **Ст8. Проверки страницы при публикации — в `core`, доверенным кодом домена** (`checkPageContent` в
  `@repo/domain/pages`):
  - UTF-8 и `pageLimits.contentBytes`;
  - ключ хода и значения переменных клиента — тем же сканером outbox;
  - форма с `<input type="password">`, у которой `action` уходит не на страницу. CSP и так закрывает `form-action` и
    `connect-src`; проверка нужна, чтобы агент не сделал фишинг-форму, которая сработала бы при ошибке в CSP;
  - встроенные токены: JWT (`eyJ…\.eyJ…\.`), частые префиксы ключей API (`sk-`, `ghp_`, `glpat-`, `xox[bp]-`,
    `AKIA…`, `-----BEGIN … PRIVATE KEY-----`);
  - отказ с понятной причиной `PAGE_CONTENT_REFUSED { reason }`.

  Список префиксов — константа с тестом, не исчерпывающий: это вторая линия рядом с инструкциями. Содержимое в логи
  не пишется, только причина и размер.
- **Ст9. CSP и заголовки — три политики и `pageResponseHeaders` в `@repo/domain/pages`** (довод среза 69.1, ответ
  владельца от 13.11.2026 «согласен»). Тест сверяет каждую строку целиком.
  - **`PAGE_CSP`** — страница агента в HTML, слово в слово по постановке:

    ```text
    sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox; script-src 'unsafe-inline';
    default-src 'none'; style-src 'unsafe-inline'; img-src data: blob: https:; font-src data: blob: https:;
    media-src data: blob: https:; connect-src 'none'; form-action 'none'; frame-src 'none';
    frame-ancestors 'none'; object-src 'none'; worker-src 'none'; manifest-src 'none'; base-uri 'none'
    ```

    (одна строка, части через `; `).
  - **`PAGE_READING_CSP`** — страница, которую платформа нарисовала из Markdown: то же без `allow-scripts`, с
    `script-src 'none'`.
  - **`PAGE_PLATFORM_CSP`** — собственные ответы платформы на хосте страницы: форма пароля, заглушки 404 и 410,
    «Документ ещё пишется». Без `sandbox` (под песочницей без `allow-forms` форма не отправится), с `form-action
    'self'`, без скриптов, запросов и фреймов.
  - **Утечка через скрипт страницы принята** (ответ владельца от 13.11.2026 «принять как есть»). У страницы нет
    `fetch`, XHR и WebSocket, но её скрипт может отправить данные адресом картинки, всплывающим окном или переходом
    (`img-src https:`, `allow-popups-to-escape-sandbox`). Страница — работа агента для клиента; пароль страницы —
    форма платформы, а не страницы.
  - Только `GET` и `HEAD` и `POST /` формы пароля, остальное — 405 (`PAGE_METHODS`).
  - `Set-Cookie` — только cookie пароля.
  - `robots.txt` — `Disallow: /` (`PAGE_ROBOTS_TXT`).
  - План 67 держал свою политику `/v/` (`PAGE_SANDBOX` в `@repo/domain/preview/hostname`,
    `pageContentSecurityPolicy`). С 14.11.2026 `/v/` идёт на этих константах: `pagePolicy('html', framedBy)` —
    та же `PAGE_CSP`, только `frame-ancestors` — origin кабинета, а картинки, шрифты и медиа — без `https:`; `PAGE_SANDBOX` — в `@repo/domain/pages`, его же
    несёт атрибут `sandbox` фрейма вкладки «Документы» (§9, «Ст9 после слияния плана 67»).
- **Ст10. Slug** — 16 случайных байт, base32 в нижнем регистре без выравнивания: 26 знаков, метка DNS до 63
  (`pageSlugSchema`, `newPageSlug`). Хост страницы — ровно `<slug>.<PAGES_BASE_DOMAIN>`, одна метка. Другие уровни,
  IP и `Host` с точкой в конце — 404 без тела страницы.
  - **Порт** (ответ владельца от 13.11.2026 «давай так и запишем»): `slugOfPageHost` принимает порт в `Host`, только
    если это настроенный публичный порт. Его передают dev и стенды, production — никогда: там любой порт — 404.
  - Базовый домен проходит `pagesBaseDomainSchema`; неверный в конфигурации — ошибка, а не 404 у каждой страницы.
- **Ст11. Markdown → HTML для чтения — один набор правил плана 67.** Правила безопасности Markdown плана 67 —
  `rehypeDocumentRules` в `apps/web/src/components/chat/document-rules.ts` (ссылки, картинки, якоря `doc-`, вычистка
  `class` и `style`) — выносятся вместе с деревом `DocumentMarkdown` в пакет `@repo/doc-render`. Пакет сервисного
  слоя: `react`, `react-dom/server`, `react-markdown`, `remark-gfm` из каталога, без MUI и без ввода-вывода.
  - Конвейер на сервере — `renderToStaticMarkup` того же дерева, не отдельный `unified`. `unified` и `rehype-*` в
    каталоге не названы, так что второй путь был бы и новой зависимостью.
  - Его берут `apps/web` (кабинет и `/v/`) и `apps/core` (публикация: HTML версии пишется в базу один раз).
  - `apps/preview` отдаёт готовые байты и Markdown не знает.
  - Стиль страницы для чтения — встроенный CSS Радити в том же пакете.
  - Новый пакет с React у `core` — ответ владельца «окей». Правило dependency-cruiser нового пакета: слой
    сервисов, из npm — только эти четыре, `llm`, `mcp`, `preview`, `browser` и раннер его не достигают.
- **Ст12. Сборка Markdown документа — одна функция** `assembleDocMarkdown(doc)` в `@repo/domain/pages`: заголовок

### Пароль, жизнь страницы, снятие

- **Ст13. Пароль.**
  - Ставит, меняет и снимает только клиент — владелец или администратор рабочего пространства (как вопрос 4 плана
    67).
  - Хеш — `scrypt` (N=2¹⁵, r=8, p=1, соль 16 байт) в `pages.password_hash`. При смене пароля растёт
    `pages.password_epoch`.
  - Форма: `POST /` с `application/x-www-form-urlencoded`, поле `password`, тело не больше 1 КиБ. В адресе пароля
    нет.
  - Верный пароль → cookie `raditi_page` только этого хоста (без `Domain`), `HttpOnly; Secure; SameSite=Lax;
    Path=/; Max-Age=43200`. Значение — HMAC-SHA256 от `PAGES_COOKIE_SECRET` над `pageId`, эпохой пароля и сроком.
    Смена пароля гасит выданные cookie.
  - Попытки: 10 в 15 минут на страницу с адреса и 100 в час на страницу — `rate_limits` через `admitInWindow`, адрес
    — HMAC, как у заявок плана 65. Сверх — 429 той же формой.
- **Ст14. Срока жизни нет: страница живёт вечно** (ответ владельца: «не удаляй страницу, пусть живет вечно»; меняет
  решение 4 постановки — 30 дней). Ни колонки срока, ни действия «Срок…», ни ответа «истекла». Платформа страницу
  не удаляет никогда.
- **Ст15. Снятие** — клиент в кабинете («Снять с публикации»). Снятая страница отвечает 410.
  - «Вернуть на публикацию» — в любое время, тот же адрес: содержимое снятой страницы не удаляется.
  - Агент снимать не может.
- **Ст16. Версии — v1, v2 и так далее, ссылка одна, хранится только последняя** (ответы владельца от 13.11.2026:
  «версии … как v1 v2 и т. д.», «всегда увеличиваем при создании новой», «хранить только последнюю версию», «давай не
  будем явные добавлять /v2, а будет одна ссылка»).
  - Номер версии страницы и документа так и называется в карточке ленты, в списке «Страниц», во вкладке
    «Страницы» кабинета и в ответе инструментов (`version: 3`, клиенту — «v3»). Документ получает версию в конце
    хода, где агент вызвал `doc_finish` (Ст19).
  - Номер растёт с каждой новой версией и не переиспользуется никогда — ни после снятия, ни после «Вернуть на
    публикацию».
  - Адрес один: `https://<slug>.pages.raditi.ru/` — всегда текущая версия. Адресов версий нет: любой другой путь —
    404. Номер версии — только подпись.
  - Хранится содержимое только текущей версии. Новая версия заменяет содержимое прежней в той же транзакции, строка
    прежней версии (номер, размер, sha256, ход) остаётся историей.
  - «Вернуть версию» не делается: возвращать нечего. Вернуть прежний вид — попросить агента, это новая версия.
  - Документ — так же: `chat_document_contents` хранит Markdown только последней версии, `chat_document_versions` —
    историю номеров и сумм.
  - Cookie пароля действует на весь поддомен и переживает новую версию: пароль закрывает страницу, а не версию.
- **Ст17. Кредиты** — публикация бесплатна, её держат лимиты (решение 6). Проход, в котором агент её сделал,
  оплачивается как любой.

### Данные людей и значения клиента

- **Ст18. Данные людей на странице.**
  - Инструкция хода: только по прямой просьбе клиента. Тогда агент советует закрыть страницу паролем и называет это
    в ответе.
  - Платформа такую страницу не узнаёт и пароль сама не ставит (ответ владельца: «нет»).
- **Ст19. Значения переменных клиента в разделах документа — проверка `core` в конце хода** (решение 9, вариант Б;
  ответ владельца: хеши значений в базе «недопустимы, пусть видит в конце хода»).
  - **С 14.11.2026 — пока ход идёт** ([план 74](74-doc-live-panel.md), Д2, ответ владельца «Да, core сразу»):
    тот же сканер с теми же ключами хода и значениями проверяет раздел через мгновение после записи, хешей в
    базе по-прежнему нет; конец хода проверяет то, что не успело, и исполняет `doc_finish`. Строки ниже о том,
    что клиент видит текст «в конце хода», — история; «Разделы: N из M» считает написанные (Д3).
  - Роль `mcp` значений не знает и их следов не получает. При `doc_section_write` она проверяет только то, что можно
    без них: размер, UTF-8, форму ключа хода, JWT и префиксы ключей API (`checkPageContent` без `refused`).
    Записанный раздел — `written` с `checked_turn` NULL.
  - Во время хода клиент видит в карточке названия разделов, их намерения и состояние: «пишется», «написан,
    покажем в конце хода». Текста раздела в кабинете нет, пока раздел не проверен; tRPC его не отдаёт.
  - В конце хода, рядом с разбором outbox, `core` проверяет каждый раздел, записанный этим ходом, тем же сканером
    (`refused` = ключи хода и `envValueForms`). Прошедший получает `checked_turn`, и карточка показывает текст.
    Отклонённый раздел возвращается в `pending` с прежним намерением и причиной, а клиенту — строка
    `feed.doc_left`.
  - Тогда же исполняются `doc_finish` и `page_publish({ docId })` этого хода — только если все разделы прошли. Иначе
    версии и публикации нет, и строка говорит, почему.
  - Ход упал до конца — разделы остаются непроверенными. Их проверит конец следующего хода того же чата: он берёт
    все непроверенные разделы чата, а не только своего хода. До него клиент их не видит.
  - Проверенным раздел отмечается по сумме того, что `core` прочитал (заголовок и текст). Раздел, записанный
    заново после чтения, остаётся непроверенным до следующего конца хода.
  - Клиенту до проверки не видны ни текст раздела, ни его заголовок: в карточке — намерение и состояние.
  - Агенту внутри хода `doc_read` отдаёт всё, что он написал сам: это его же текст.

### Агент и лента

- **Ст20. Семейство `pages`** — шестое в `mcpToolFamilies`. Объявляется каждому ходу чата: с проектом и без, с кодом
  и без, как `search`. Раздел `apps/mcp/src/pages` по образцу `src/search`. Инструменты:
  - `page_publish`, `page_list`;
  - `doc_create`, `doc_section_write`, `doc_section_remove`, `doc_section_move`, `doc_read`, `doc_finish`.

  Каждый вызов проходит обычный допуск хода. Ответ — канонический JSON, описания по-английски. `page_publish` с
  `file` и с `docId` — одна схема-объединение (ровно одно из двух).

  Документы и страницы — рабочего пространства. `page_list` и `doc_read` видят всё пространство, а не только чат:
  агент обновляет прежнюю страницу из другого чата по просьбе клиента. Чужое пространство — отказ без различия
  «нет» и «чужое».
- **Ст21. Документ — строки `chat_documents` и `chat_document_sections`**, история версий — `chat_document_versions`
  (номер, sha256, ход), Markdown текущей — `chat_document_contents`.
  - `doc_section_write` заменяет раздел целиком. С `after` вставляет новый с нейтральным намерением «Новый раздел»
    (заголовок — непроверенный текст, в намерение он не копируется).
  - `doc_finish` отказывает, пока есть `pending`, и становится версией N+1 в конце хода, когда все разделы написаны и
    проверены. Если раздел написал другой чат и он ещё не проверен, `doc_finish` ждёт конца хода того чата; если
    проверка этого хода вернула раздел в заглушку, `doc_finish` снимается, и агент узнаёт об этом из
    `feed.doc_left`.
  - Правка готового документа открывает рабочее состояние поверх версии. Ссылка на документ в кабинете та же.
- **Ст22. Живой документ в ленте — строка документа плюс строка-сигнал** (решение 12).
  - С 14.11.2026 ([план 74](74-doc-live-panel.md), Д4–Д6) сам документ — во вкладке «Документы» справа, в ленте —
    одна строка с «Открыть»; `feed.doc_touch` пишет и живая проверка `core`.
  - `doc_create` пишет строку `feed.doc` v1 (`docId`, название). Каждая запись раздела пишет `feed.doc_touch` v1
    (`docId`, `revision`) через `insertFeedEvent` — тем же путём, каким `apps/browser` пишет `feed.screenshot`. Конец
    хода с проверкой (Ст19) пишет ещё один `feed.doc_touch`, и карточка показывает проверенный текст.
  - Поток ленты кабинета видит новую строку и перечитывает карточку tRPC-запросом `pages.doc`. Лента складывает
    сигналы одного документа в одну карточку.
  - Новых доступов нет: у `mcp` уже есть PostgreSQL.
  - Текст разделов в `task_events` не дублируется: в ленте — только сигнал, текст — в строках документа.

- **Ст26. Браузер чата** открывает страницы `<slug>.pages.raditi.ru` (решение 3; ответ владельца от 13.11.2026 после
  среза 69.11 — «давай все 3 пункта сделаем»). Агент может проверить свою страницу `web_open`, клиент — открыть её в
  браузере чата. Корень `pages.raditi.ru` (`/v/` плана 67) и всё остальное под `raditi.ru` закрыты:
  `BROWSER_PLATFORM_HOSTS` закрывает имя вместе со всем, что под ним (К37), а исключение — только полный адрес
  страницы. Три части:
  1. **Имя.** Исключение — `https://<26 знаков base32>.<PAGES_BASE_DOMAIN>/` на своём порту, без учётных данных
     (`browserPageAddress` в `@repo/domain`); тот же хост на другом порту или по `http://` остаётся платформой.
  2. **Адрес в любом чате.** По адресу страница открывается и в чате с проектом, где по адресу открывается только
     сайт; политика стека её путь не судит — это не страница сайта. Для правил страниц Playwright она — другой
     сайт: её главный кадр открывается, а что она грузит, держит её CSP. В чате с проектом со страницы браузер не
     уходит никуда, кроме её собственного хоста: иначе ссылка или скрипт страницы обошли бы Ч2 («по адресу — только
     сайт») в том же контексте, где лежит вход клиента в админку (ревью; `fromAgentPage` в `page-rules.ts`).
  3. **Сеть.** Страницы живут на машине платформы, чей адрес закрывает `SANDBOX_EGRESS_REFUSED_SUBNETS`. Прокси
     выхода браузерной сессии (не песочницы хода) получает `PAGE_DOMAIN` и `PAGE_ADDRESSES` (у `apps/browser` —
     `BROWSER_PAGE_ADDRESSES`, на сервере `45.8.250.117`) и снимает закрытые подсети только с этих адресов и только
     для имени страницы на 443, по TLS с этим именем; остальное в закрытых подсетях, непубличные адреса и подсети
     самого контейнера закрыты и для неё. Отвечает там только маршрут страниц Traefik — он выбирает маршрут по `Host`, а
     Chromium ставит `Host` по адресу страницы. Риск принят владельцем: граница теперь держится и на маршрутах
     Traefik — маршрут, который ловит любой `Host`, браузер чата достанет. Только production: вне его страницы
     идут по `http://` с портом, и исключение не действует.

### База — миграция `20261113130000_pages`

Только новые таблицы; хранилище — `packages/db/src/pages.ts`.

- **`pages`**: `id` uuid7, `workspace_id`, `task_id` (чат создания, `SET NULL` — страница живёт дольше чата) и
  `turn_no`, `kind` (`html` | `markdown` | `doc`), `slug` (unique, 26 знаков `[a-z2-7]`), `title`, `state`
  (`pending` | `live` | `taken_down`), `current_version` (0 ⇔ `pending`), `password_hash`, `password_epoch`,
  `taken_down_at` и `taken_down_by` (`client` | `operator`) вместе, `document_id` (unique, одна страница на документ),
  `source_file_name`. Срока нет (Ст14). Строка появляется при первом резерве: у неопубликованного документа строки
  `pages` нет.
- **`page_versions`**: история — `no`, `size_bytes`, `sha256`, `source` (`outbox` | `doc` | `file`), `task_id`,
  `turn_no`; unique `(page_id, no)`.
- **`page_contents`**: байты только текущей версии, одна строка на страницу (`page_id` — ключ, `version_no`), не
  больше `pageLimits.contentBytes` (Ст16).
- **`page_reservations`**: публикация хода — `file_name` или `document_id` (ровно одно), `title`, `outcome`
  (`done` | `missing` | `refused` | `failed`, NULL до конца хода) и `version_no` при `done`; unique
  `(task_id, turn_no, file_name)` и `(task_id, turn_no, document_id)`.
- **`chat_documents`**: `workspace_id`, `task_id`, `title`, `revision`, `current_version`, `finish_task_id` и
  `finish_turn_no` (вместе) — `doc_finish`, ждущий конца хода.
- **`chat_document_sections`**: `section_key`, `position`, `heading`, `markdown` (до 32 КиБ), `intent`, `state`,
  `written_task_id` и `written_turn`, `checked_turn`, `refusal`. CHECK: у `pending` нет текста и хода записи, у
  `written` есть заголовок, текст и ход, `checked_turn` не раньше хода записи, отказ — только у `pending` (Ст19).
  Следов значений переменных в базе нет.
- **`chat_document_versions`** — история (`no`, `size_bytes`, `sha256`, ход); **`chat_document_contents`** — Markdown
  только текущей версии.
- `page_contents` и `chat_document_contents` связаны составным внешним ключом с версией, которую называют
  (`(page_id, version_no)` → `page_versions(page_id, no)`): номер содержимого не расходится с историей.
- Счёт страниц, документов и публикаций за час идёт под замком строки рабочего пространства (`FOR NO KEY UPDATE`:
  вставки, которые на него ссылаются, не ждут): два хода не займут одно последнее место. Под тем же замком
  проверяется, что чат — этого рабочего пространства.
- Предел `pagesPerWorkspace` считает опубликованные и снятые страницы; резерв, который так и не стал версией
  (`pending`), не считается — его убирает сборщик (срез 69.6).

## 7. Проверки

- `pnpm gates`, `pnpm check-architecture`, `pnpm verify:db` — на каждом срезе, без новых нарушений. Перед коммитом —
  `/spec-check`.
- **Стенд `pnpm verify:pages`.** Он ведёт несколько приложений (`mcp`, `core`, `preview`, web), поэтому скрипт — в
  `apps/core/scripts/verify-pages.mjs`, фикстуры — в `infra/dev/pages-verify/`. Одноразовые PostgreSQL, Redis,
  SeaweedFS и OpenBao, синтетический Z.ai, настоящий OpenCode; `.env` не читается.
- **Путь страницы.** Публикация → адрес → заголовки байт в байт; неверный пароль — отказ, верный — доступ; новая
  версия по тому же адресу, номер вырос, содержимое прежней версии в базе не осталось, `/v2` и любой другой путь —
  404; снятие → 410; «Вернуть на публикацию»; снятие оператором; несуществующая → 404; страница без срока отвечает и
  после сдвига часов стенда на год.
- **Путь документа.**
  - `doc_create` → карточка с заглушками;
  - разделы по одному → «Разделы: N из M», текст разделов в кабинете — только после конца хода;
  - значение переменной клиента в разделе → раздел снова заглушка, `feed.doc_left`, версии нет;
  - `doc_finish` с заглушкой — отказ, без заглушек — версия;
  - «Скачать .md» равно Markdown версии;
  - «Опубликовать по ссылке» → страница для чтения;
  - правка раздела → новая версия по тому же адресу.
- **Отказы публикации.** Ключ хода; значение переменной клиента в странице и в разделе; форма пароля наружу; JWT;
  размер сверх предела.
- **Защиты.**
  - Chromium на странице не читает cookie кабинета и предпросмотров;
  - `fetch`, `XMLHttpRequest`, `WebSocket` и `form` блокируются CSP — стенд ловит отчёты нарушений;
  - страница не открывается во фрейме;
  - хост кабинета не отдаёт страницу, хост страницы не отдаёт ни кабинет, ни `/v/`;
  - вторая метка и чужой домен — 404.
  - страница — один сайт с `raditi.ru` (Ст3): переход со страницы на изменяющий маршрут кабинета отклоняется по
    `Origin`, cookie с `Domain=raditi.ru` нет ни одной;
  - браузер задачи открывает `<slug>.pages.raditi.ru` и не открывает `pages.raditi.ru` (Ст26).
- **Готовность.** В dev на синтетическом Z.ai, в чате с проектом и без, — оба сценария из постановки. Только
  синтетика: ни живого режима, ни данных клиентов.

### 69.6 — core: файл outbox → версия страницы (13.11.2026)

### 69.9 — публикации клиента (14.11.2026)

Окончание среза 69.9 (Ст25, Ст32): клиент публикует сам, сразу, без хода агента.

- **База.** `publishClientPage` (`@repo/db`): страница документа или страница, которую этот чат сделал из файла
  того же имени (`pages.task_id` и `source_file_name`), получает следующую версию; нет — новая страница. Одна
  транзакция: страница без версии не остаётся. Пределы — те же `pageLimits`: `pagesPerWorkspace`,
  `publishesPerHour` (считаются резервы хода и версии клиента, `turn_no IS NULL`), `contentBytes`. Снятая клиентом
  страница — `PAGE_TAKEN_DOWN` (вернуть её — в «Страницах»), снятая оператором — `PAGE_NOT_FOUND`. Общая с
  `applyPageVersion` запись версии вынесена в `writeVersion`.
- **tRPC** (`pages`):
  - `publishDoc({ docId })` — «Опубликовать по ссылке»: текущая версия документа (`currentDocMarkdown`; её разделы
    прошли проверку конца хода) рисуется `readingPage` и проверяется `checkPageContent`; версии нет —
    `DOC_NOT_READY`;
  - `publishFile({ taskId, fileId })` — «Опубликовать как страницу»: файл чата из `raditi-artifacts`, только `.html`
    и `.md` (`PAGE_NOT_PUBLISHABLE`), `checkPageContent` файла, `.md` — `readingPage` с заголовком из самого файла
    (как у `core`) и проверка нарисованного; значения переменных клиента файл прошёл сканером outbox своего хода
    (Ст6), второго сканирования нет. Название страницы в кабинете — имя файла без расширения;
  - `canPublish({ taskId })` и поле `canPublish` у `pages.doc` — владелец или администратор и настроенный

  - тексты отказов клиенту — `MESSAGE_BY_DOMAIN_CODE`: `PAGES_OFF`, `DOC_NOT_READY`, `PAGE_NOT_PUBLISHABLE`,
