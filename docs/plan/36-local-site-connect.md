# P11: локальное подключение сайта — профиль `site`, плагин, доверенная команда стенда

04.10.2026. Инкремент N10 плана следующих работ: сайт, созданный в кабинете через «Новый проект», остаётся в статусе `onboarding`, и роль `mcp` его не допускает. Теперь одна команда делает такой сайт пригодным для хода: плагин привязан, доступ лежит в OpenBao, у рабочего пространства есть ключ Transit, у сайта — репозиторий, статус — `active`. Всё локально: одноразовые PostgreSQL, S3, OpenBao 2.7.0, Gitea 1.27.3 и WordPress 7.1.2, синтетика, без подписок и облака. Корневой `.env`, dev-инфраструктура (`raditi-dev-*`) и `~/.codex/auth.json` не использовались. P11 остаётся открытым: импорт сайта, AGENTS.md, эталон, полный бэкап и мастер впереди.

Команда — подготовка стенда, а не продукт. Она не решает вопрос «плагин или SSH/FTP» и готовит только то, что нужно контентному пути.

## Что сделано

**Перевод сайта в `active`** (`packages/db/src/site-activation.ts`, экспорт в `@repo/db`). `activateSite(db, { siteId, requiredAccess })` — один условный запрос: `onboarding → active` только если у сайта есть репозиторий и для каждого названного вида доступа — ссылка, которую примет читатель доступа: единственная строка `credential_refs` этого вида у сайта, в рабочем пространстве сайта, с путём `kv/sites/<siteId>/<вид>` и записанной версией. Виды доступа — параметр: их называет адаптер стека, сам код ни с каким стеком не сравнивает (правило 8). Итог: `activated`, `already_active` или `refused` с причиной (`not_found`, `status`, `access` со списком видов, `repository`). Из `paused`, `disconnected` и `archived` сайт так не выходит. Строка сайта блокируется на время запроса: из параллельных вызовов переводит один. Схема и миграции не менялись. Функцию переиспользуют P11 и M4; в продукте её пока никто не вызывает.

**Профиль `site`** (`infra/dev/docker-compose.yml`, только сервисы профиля). Тип окружения WordPress `local` — без него WordPress не принимает пароли приложений по HTTP; cron, обновления, внешние HTTP-вызовы и правка файлов из админки выключены, как в одноразовом стенде. Плагин `infra/wordpress/raditi-content.php` смонтирован в `mu-plugins` только на чтение — в `site` и в `wpcli`, конфигурация у них общая. У `site-db` и `site` появились healthcheck, зависимости ждут готовности. Образ `wpcli` можно назвать переменной `SITE_WPCLI_IMAGE`; по умолчанию — прежний закреплённый тег.

**Команда `infra/dev/site-verify/connect-local.mjs`.** `node infra/dev/site-verify/connect-local.mjs --site <siteId>`; окружение задаётся явно, env-файлы не читаются, токены — из собственных файлов `0600`. Отказ до первого шага: `APP_ENV=production` или не задан, PostgreSQL, OpenBao или Gitea не на loopback (строка базы с параметром `host` или `hostaddr` тоже отклоняется: клиент PostgreSQL берёт хост из параметра раньше, чем из адреса), Gitea не по `https:`. Шаги:

1. Проверки до первого изменения: сайт есть, адрес — loopback, стек — WordPress, рабочее пространство — `synthetic`, статус — `onboarding` или `active`; существующие ссылки на доступ и репозиторий — такие, какие примет роль `mcp`; OpenBao и Gitea отвечают.
2. Установка WordPress, если его нет. Пароль администратора создаёт WP-CLI, команда его не видит.
3. Сброс ограждения при смене привязки: удаляются `raditi_content_epoch` и квитанции `raditi_content_call_*`. Установку, привязанную к другому сайту той же базы, команда не отнимает.
4. Доступ. Новый пароль приложения администратора (прежний пароль команды удаляется), запись `kv/sites/<siteId>/wp` токеном `sites-writer` с CAS — `cas = 0` для нового секрета, текущая версия для существующего, — затем строка `credential_refs` с версией секрета. Формат проверяет схема адаптера сайта, `origin` — `new URL(адрес).origin`. Доступ не переписывается, если привязка не меняется, а строка называет текущую неудалённую версию секрета.
5. Привязка плагина (`raditi_content_site_id`) — последний шаг на стороне WordPress, после сохранения доступа. Пока доступ этой установки не сохранён, установка остаётся непривязанной, и следующий запуск пишет доступ заново.
6. Ключ `transit/keys/ws-<workspaceId>` токеном `workspace-provisioner`; имя — `workspaceTransitKey`.
7. Приватный репозиторий `sites/site-<siteId>` с первым коммитом и строка `git_repositories`.
8. `activateSite`.

Повторный запуск ничего не меняет. Прерванный запуск доводится следующим: секрет нельзя прочитать обратно, поэтому он заменяется новой версией. По SIGTERM команда останавливает идущий контейнер WP-CLI и выходит.

**Стенд `pnpm verify:site-connect`** (`infra/dev/site-verify/verify-site-connect.mjs`). WordPress, MariaDB и WP-CLI — профиль `site` того же dev compose под собственным проектом `raditi-site-connect-…` на случайном порту loopback; остальные сервисы одноразовые, Gitea — по HTTPS с CA стенда (помощники `infra/dev/gitea-verify`). Сайт создаётся так, как его оставляет «Новый проект»; команда идёт отдельным процессом. Роль `mcp` — штатная: `node dist/main.js`, `MCP_CONTENT_PROFILE=local`, AppRole `mcp`. Стенд не пишет ни доступ, ни ссылку, ни репозиторий, ни статус — только команда. Образы не скачиваются; локальные образы WordPress и MariaDB сверяются с закреплёнными digest.

**Документы.** Раздел «Локальное подключение сайта» в `infra/dev/site-verify/README.md`; строка `verify:site-connect` в корневом `package.json`.

## Границы доверия

- Пароль приложения читает только роль `mcp`, из OpenBao под своей AppRole. Команда пишет его токеном `sites-writer` и прочитать обратно не может; в базе — путь и версия.
- Ключ рабочего пространства создаёт только токен `workspace-provisioner`; у ролей прав на `transit/keys/*` нет.
- Root-токен одноразового OpenBao остаётся у запускающего скрипта стенда: ни команда, ни роль его не получают.
- Команда работает только вне production и только с loopback; в production контентный профиль роли по-прежнему запрещён кодом.
- Песочница, `core`, web и роль `llm` не менялись.

## Что выяснено

- **Сохранённая установка действительно ограждает новый сайт.** После пересоздания базы запись под эпохой 1 от прежней привязки получает `fenced` — стенд показывает это до переподключения. После команды та же страница правится под эпохой 1.
- **Вложенный bind-mount работает.** Файл плагина смонтирован внутрь именованного тома до первого старта образа: образ WordPress ставит ядро рядом, плагин видят и веб-сервер, и WP-CLI.
- **`WORDPRESS_CONFIG_EXTRA` действует и для WP-CLI**, если переменная есть в его контейнере: `wp_get_environment_type()` отвечает `local`.
- **Точного тега `wordpress:cli-2.12.0-php8.3` на этой машине нет.** Стенд берёт запасной образ по digest, тот же, что у `verify-site.mjs`, и проверяет версию `WP-CLI 2.12.0`. Отсюда переменная `SITE_WPCLI_IMAGE`.
- **Репозиторий в организации создаёт токен с областями `write:organization` и `write:repository`.** Проверено токеном администратора одноразовой Gitea. Токен бота платформы (`write:user`, `write:repository`) не проверялся.
- **Общий помощник уборки не понимает Docker 29.6.** `ownedContainers.close()` (`apps/orchestrator/scripts/verify-agent-supervisor.mjs`) считает отсутствующий контейнер ошибкой: он ждёт «No such object», а Docker 29.6 пишет «error: no such object». Стенд, который удалил свой контейнер до уборки, получает «FAIL cleanup» при чистой машине. Файл чужой, не менялся; этот стенд базу пересоздаёт внутри контейнера.

## Отступления от плана

- **Сброс ограждения — только при смене привязки.** План называл сброс `raditi_content_epoch` и квитанций шагом каждого запуска. При повторном запуске на том же сайте сброс стёр бы квитанции, по которым платформа восстанавливает запись после потерянного ответа, поэтому он выполняется, только когда установка привязывается к другому сайту.
- **Gitea — только `https:`.** Dev-Gitea отвечает по HTTP, и команда её отклоняет: вопрос о HTTP на loopback открыт (spec §20), git ходов с ней тоже не настроен. На dev-инфраструктуре команда сегодня остановится на проверке `GITEA_URL`.
- **Отказ отнимать установку.** Если WordPress привязан к другому сайту той же базы, команда отказывает. В плане этого не было; иначе подключение второго сайта с тем же адресом молча ломало бы первый.
- **`SITE_WPCLI_IMAGE` и healthcheck в профиле `site`.** Переменная нужна стенду, потому что точного тега WP-CLI локально нет; healthcheck — чтобы WordPress не стартовал раньше базы. В `.env.example` переменная не добавлена: файл вне этого инкремента, значение по умолчанию прежнее.
- **S3 в стенде.** План называл WordPress, PostgreSQL, OpenBao и Gitea; роли с контентным профилем нужен ещё бакет артефактов.
- **Workflow GitHub Actions для стенда не добавлен**: `.github` вне этого инкремента.

## Что остаётся открытым

- **Dev-инфраструктура.** Команда выполнена только стендом. На `raditi-dev` она не запускалась (инфраструктуру трогать было нельзя) и не дойдёт до конца, пока у dev-Gitea нет TLS или владелец не разрешил HTTP на loopback. Как оператору dev-OpenBao выпускать токены `sites-writer` и `workspace-provisioner`, в runbook не записано.
- **Кто создаёт репозиторий сайта в продукте.** Метода в порту `GitProvider` нет; команда берёт токен, которому разрешено создавать репозитории в `sites`. Имя `site-<siteId>` — выбор этого инкремента, spec имени не задаёт.
- **Действует ли уже записанный доступ, команда не знает.** Прочитать секрет она не может: пароль приложения, удалённый в админке, при неизменной привязке останется «без изменений». Выход — удалить опцию `raditi_content_site_id` и запустить команду: она выпустит новый пароль и сбросит ограждение (проверено тестом на подставных портах, не стендом).
- **Ограждение при неизменной привязке не сбрасывается.** Если базу платформы восстановили из более раннего дампа с тем же сайтом, эпоха плагина окажется выше эпохи аренды и записи получат `fenced`. Стенд проверяет только пересоздание базы с новым сайтом. Выход тот же.
- **Два одновременных запуска на одном сайте** удаляют пароли приложений друг друга; CAS в OpenBao пропустит один, но его пароль может быть уже удалён. Команда ручная, блокировки нет.
- **Профиль `site` не поднят.** Команда откажет (`SITE_NOT_RUNNING`), но `docker compose run` успеет создать пустой том `sitefiles` проекта: запущен ли сервис `site`, команда заранее не проверяет.
- **Прежние версии и прежние секреты остаются в OpenBao.** Настройки `kv/` — решение P7. После пересоздания базы секрет и репозиторий прежнего сайта остаются без строк в базе; убирает их оператор.
- **Учётная запись подключения.** Команда берёт первого администратора WordPress и не проверяет `unfiltered_html` (вопрос владельцу, M4, P11).
- **Путь политики `workspace-provisioner`** использован как есть (`transit/keys/ws-*`); вопрос владельцу остаётся.
- **Linux.** Стенд выполнялся только на Docker Desktop; ветка для хоста Linux не исполнялась.
- **Помощник уборки на Docker 29.6** — пункт для владельца `verify-agent-supervisor.mjs`.
- Мастер подключения, упаковка плагина, импорт сайта, AGENTS.md, эталон и полный бэкап — P11 и M4.

## Ревью

Независимое ревью 04.10.2026 перечитало все файлы инкремента, логи стенда исполнителя и повторило проверки. Найдено и исправлено в файлах инкремента (сначала падающий тест, затем правка):

- **Привязка писалась до доступа.** У подключённого сайта с прежней ссылкой (WordPress переустановлен или опция привязки изменена) запуск, прерванный между привязкой и записью в OpenBao, оставлял согласованные ссылку и секрет прежней установки; следующий запуск отвечал «без изменений», а роль получала недействующий пароль. Теперь привязка — последний шаг на стороне WordPress. Тест с отказом OpenBao до правки падал.
- **Параметр `host` в строке базы обходил проверку loopback.** `postgresql://…@127.0.0.1/…?host=db.example` проходил проверку адреса, а клиент PostgreSQL подключался к хосту из параметра (проверено разбором строки тем же клиентом). Такая строка отклоняется.
- **Стенд не проверял, что репозиторий приватный.** Утверждение держалось на теле запроса в тесте с подставным HTTP. Стенд теперь спрашивает Gitea: флаг `private` у администратора и 404 без токена.
- **Контракт стенда.** Команда по умолчанию работает с проектом `raditi-dev`; тест закрепляет, что стенд всегда называет собственный проект.
- В отчёт и README добавлены ограничения: сброс ограждения при неизменной привязке, параллельные запуски, пустой том при неподнятом профиле.
