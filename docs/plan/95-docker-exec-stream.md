# План 95. Потоковый вывод команд песочницы

Ветка `perf/docker-exec-stream`. Задача roadmap — P29. Запрос владельца от 25.11.2026 после оценки плана оптимизации.

## Сейчас

Команда песочницы (`DockerSandbox.exec`) идёт отдельным процессом помощника (`runtime.mjs run`), а её вывод пишется в файлы внутри песочницы, чтобы его можно было дочитать после перезапуска (`attach` с курсором). Хост читает вывод опросом: каждая страница — это новый `docker exec` с запуском Node в песочнице (`read-exec`, до 64 КиБ на поток), между пустыми страницами пауза от 50 мс до 1 с. `wait()` опрашивает `docker inspect` раз в 100 мс и в конце ещё раз запускает `read-exec` ради кода выхода.

Через этот путь идут все команды хода: подготовка, восстановление и снятие снимка (архив `tar` уходит из песочницы выводом команды), выходные файлы.

## Замеры до (Docker Desktop, `runc`, arm64; под gVisor запуск процесса дороже)

| Что | Время |
|---|---|
| один запуск помощника (`helperCommand ready`) | 44 мс |
| `docker inspect` | 1,5 мс |
| короткая команда целиком (`/bin/true`: `exec`, вывод, `wait`) | 443 мс |
| 2 МиБ вывода команды | 2,7 с (~85 мс на 64 КиБ) |
| 16 МиБ вывода команды | не уложились в 270 с |
| `fs.read` / `fs.write` 16 МиБ (одна команда с потоком) | 145 / 179 мс |

На ход приходится 30–60 команд, то есть только обвязка команд занимает 13–26 с.

## Что меняем

1. **`runtime.mjs follow-exec <id> <stdout> <stderr>`** — один процесс помощника на всё чтение. Он отдаёт вывод из тех же файлов от курсора кадрами `[тип][смещение][длина][данные]` (1 — stdout, 2 — stderr, по 64 КиБ). Новые данные он ждёт короткими паузами внутри процесса (10–100 мс), а не новым `docker exec`. Когда есть `exit.json` и всё прочитано, шлёт завершающий кадр с кодом выхода и заканчивается. Через 10 минут он шлёт кадр «продолжи» (4) и заканчивается, а хост открывает новый поток с того же курсора. Курсор за концом файла или вывод больше предела — отказ, как у `read-exec`. Если хост закрыл соединение, помощник выходит на первой же записи; жёсткий таймер завершает его не позже 10 минут и 5 секунд.
2. **`DockerExecHandle.output()`** читает этот поток. Смещение каждого кадра сверяется с курсором, размер ограничен, как у страниц. Пока поток ждёт, хост раз в секунду смотрит `docker inspect`: если процесс `run` дважды подряд не работает (OOM, агент убил его без `exit.json`), поток закрывается. Завершение и остановка handle тоже закрывают поток. Если поток кончился без завершающего кадра — образ без новой команды (контейнер из прежнего образа: тёплый, принятый recovery), помощник убит `quiesce` или упал, — хост продолжает прежним опросом страниц с того же курсора. Неверный кадр — сбой команды, как неверная страница.
3. **`wait()`** берёт код выхода из завершающего кадра и сверяет его с `ExitCode` из `docker inspect`, как сейчас сверяет страницу. Лишнего `read-exec` больше нет. Пока процесс помощника `run` досчитывает, `inspect` опрашивается раз в 10 мс, а не 100. Без завершающего кадра всё работает как прежде.
4. **Доверие то же.** Помощник работает под тем же пользователем песочницы, что и `read-exec`: вывод и `exit.json` принадлежат агенту и раньше. Код выхода, как и прежде, проверяется по Docker.

## Чего не делаем

- **Слияние `stage` и `run` в один запуск.** Тогда `run` пришлось бы держать присоединённым к соединению хоста и переживать его обрыв при перезапуске. Для этого нужна проверка под gVisor — отдельная задача.
- **`DockerFrames` с линейным разбором.** `fs.read` 16 МиБ уже идёт за 145 мс: кадры Docker приходят мелкими.

## Проверка

- Модульные тесты разбора кадров и запасного пути.
- `runtime.test.ts` для `follow-exec`.
- Существующие интеграционные тесты провайдера на настоящем Docker (`docker.integration.test.ts`, в CI джоб `sandbox-isolation` под `runc`) идут уже через поток. Запасной путь на настоящем Docker проверен замером на образе прежнего помощника; отдельного интеграционного теста на него нет.
- Замер после — тем же временным тестом.

## Итог

- **Помощник** (`runtime/runtime.mjs`): команда `follow-exec`, кадры `followFrame` (`FOLLOW_FRAME`: 1 stdout, 2 stderr, 3 конец).
- **Хост** (`src/docker-sandbox.ts`):
  - `FollowFrames` разбирает кадры Docker и помощника;
  - `DockerExecHandle.output()` сначала читает поток, при его обрыве без конца продолжает страницами;
  - `wait()` берёт код выхода из конечного кадра, проверяет его по `ExitCode` Docker и опрашивает `inspect` раз в 10 мс.
- **Замеры после** (та же машина, два раунда подряд, `runc`):

| | опрос (до) | поток (после) |
|---|---|---|
| короткая команда | 536 мс | 117–118 мс |
| 2 МиБ вывода | 4,2 с (в одном раунде завис и упал через 274 с) | 130–184 мс |

- **Тесты:**
  - модульные (52 в `docker.test.ts`): кадр «продолжи» — новый поток без страниц; процесс `run` умер без `exit.json` — поток закрыт за две проверки и команда `lost`; поток без единого `read-exec`, образ без команды уходит на страницы, смещение не по курсору — сбой, код выхода не совпал с Docker — `lost`, продолжение с курсора `attach`, разбор кадров, разрезанных как угодно, и их пределы;
  - `runtime.test.ts`: формат кадра;
  - интеграционные на настоящем Docker с образом нового помощника: 11 из 12. Тест с `git` упал только потому, что в минимальном образе для замера нет `git`; полный образ проверяет CI (`sandbox-isolation`).
- **Запасной путь проверен на настоящем Docker:** замер на образе прежнего помощника прошёл страницами.

- **`/spec-check`:** нарушений нет. Его замечания учтены: зависание до 10 минут при гибели `run`, процессы-сироты помощника, плановый конец потока ведёт к новому потоку, проверка курсора, запас в пределе кадра Docker.

## Что не проверено

- **Под gVisor.** Запуск процесса там дороже, поэтому выигрыш должен быть больше, но замера нет.
- **Доверие не изменилось.** Помощник работает под пользователем агента, как `read-exec`, а вывод и `exit.json` агент мог подменить и раньше. Код выхода по-прежнему сверяется с Docker.
