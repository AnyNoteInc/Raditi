# P4: локальный драйвер Codex

30.09.2026 реализованы `prepare` и `command` для Codex 0.158.0, подготовлен общий образ песочницы и проверено продолжение сессии в новом контейнере. Это локальная подготовка P4 до приёмки P3: миграция сужения B16 не добавлялась, работа с настоящими подписками и облаком не выполнялась.

## Реализация

- `packages/agent-drivers/src/codex.ts` пишет конфигурацию провайдера `raditi`, инструкции, JSON-схему результата и обёртку. Ключи LLM и MCP лежат только в `/run/raditi/secrets` (права 0400); обёртка читает оба файла один раз, удаляет их до запуска CLI и передаёт ключи его процессу. Команды агента файлов секретов не видят. Остаток: Codex 0.158.0 держит оба ключа в окружении собственных процессов CLI весь ход, и команда того же uid может прочитать `/proc/<pid>/environ`; другого способа передать ключи у CLI нет (измерено). `PreparedRun.env`, конфигурация и аргументы запуска не содержат ключей, `auth.json` не создаётся. Снимок включает только `codex/sessions`.
- `command` до проверки и записи подготовленных файлов добавляет текст запроса и аргументы CLI в отдельные файлы под `/agent-home/codex`. Обёртка Node подаёт текст через stdin и запускает CLI в той же группе процессов. Так запрос `-` остаётся текстом, а длинные запросы и списки вложений не превышают ограничение executor argv. Картинки передаются через `--image`, остальные пути перечисляются в запросе. Картинка с запятой в имени через `--image` не передаётся (CLI разбивает аргумент по запятым) и перечисляется в запросе вместе с другими файлами. Список вложений проверяется правилом самого плана хода (`turnInputSchema`: не больше 100 путей, каждый под `/workspace/inbox`, без управляющих символов, без пустых сегментов, `.` и `..`, не длиннее 1024 символов); своей копии правила у драйвера нет, ошибка — `Invalid attachment path`.
- Все настройки платформы повторены через runtime `--config`, выше конфигурации проекта: профиль модели, адреса провайдера и MCP, фильтрация окружения, выключенные web search, аналитика и обновления. Закреплены также `features.mcp_2026_07_28=false` (без закрепления конфигурация проекта переключала обязательный MCP-сервер `raditi` на протокол 2026 года: CLI отправлял `server/discover`, сервер не поднимался, и каждый ход Codex на таком сайте падал) и `project_doc_max_bytes` = 32 КиБ: `AGENTS.md` платформы в `CODEX_HOME` читается целиком, `AGENTS.md` репозитория обрезается. `--output-schema` получает строгое подмножество схемы, выведенное из `turnResultSchema` (пределы — описаниями, полная проверка zod после хода). Ход завершает ошибкой только `turn.failed`: строки `error` верхнего уровня несут и «Reconnecting… n/5». Для запрета подагентов нужны `multi_agent=false`, `multi_agent_v2=false` и `agents.enabled=false`: синтетический проход обнаружил, что модельный default обходит одни feature-флаги.
- `RunContext.llm.reasoningEffort` сохраняется через план и recovery. Супервизор до аренды сверяет его с политикой ключа; отсутствующее поле дополняет значением политики. Codex требует явного уровня при запуске, поскольку его неявный default несовместим с ключом без разрешённого effort. Подготовка исторического плана без поля для восстановления уже запущенного процесса допустима.
- `SANDBOX_IMAGE` принимает только `repository@sha256:<64 hex>`, один образ стека для всех драйверов. Старый `SANDBOX_IMAGE_PREFIX` удалён из активных настроек и шаблонов. В `infra/sandbox/Dockerfile` CLI добавлен только в stage `runtime`; доверенные gateway, watchdog и network guard его не получают. Оба CLI ставятся из `packages/agent-drivers/cli/package-lock.json` командой `npm ci --ignore-scripts` (sha512 каждого пакета) со сверкой версий `npm ls`. В production нулевой digest-заглушка из `env.example` отвергается. Рабочий `.env` не менялся.
- Общая для Codex и Kimi обвязка хода — схема контекста запуска, два файла секретов, размещение входных файлов и проверка вложений — вынесена в `packages/agent-drivers/src/cli-run.ts`.
- Добавлены `pnpm verify:codex` и workflow `codex-driver.yml`. Проверка отвергает удалённый Docker до операций, закрепляет локальный сокет и локальный ID образа, работает без host mounts и внешней сети. У workflow теперь два job: `verify-codex` и `sandbox-isolation` (Docker-тесты `@repo/sandbox-providers` и watchdog под `runc`, с containerd image store, чтобы у локальных сборок был digest репозитория). Фильтр путей расширен на `packages/sandbox-providers/**` и `infra/sandbox/**`. GitHub Actions не запускался.

```sh

pnpm verify:codex
pnpm --filter @repo/domain --filter @repo/agent-drivers --filter orchestrator typecheck
pnpm --filter @repo/domain --filter @repo/agent-drivers --filter orchestrator lint
pnpm --filter @repo/domain --filter @repo/agent-drivers --filter orchestrator test
pnpm test:infra
pnpm check-env
pnpm check-architecture
```

Собран и запущен по digest локальный production runtime:

`raditi-p4verify-sandbox@sha256:cd41acfa42f233ecf5105866e79abc4b8cbde335bb8648f4eb43fdf477475d53`

Smoke: uid/gid 10001, read-only, `--network none`, `cap-drop ALL`, `no-new-privileges`; Codex 0.158.0, Node, PHP, Composer и инструменты доступны. Образ оставлен для следующих локальных проверок.

Настоящий CLI через настоящий драйвер выполнил первый ход, затем продолжил тот же UUID в новом контейнере после переноса только `sessions/`, с новыми ключами и сменой effort `medium` → `high`. Проверены JSON-схема и извлечение результата, инструкции AGENTS, MCP initialize/tools/list с bearer, запрос `-`, запрос длиннее 70 000 символов, PNG и текстовое вложение. Активный конфиг проекта пытался изменить модель, effort, MCP и настройки инструментов; закреплённые настройки сохранились. У провайдера нет инструментов подагентов, дочерний shell не получает LLM/MCP токены через окружение. В снимках, stdout и stderr нет синтетических ключей. Контейнеры удалены.

После ревью 02–04.10.2026 `pnpm verify:codex` дополнительно проверяет: `strict: true` и точную схему в запросе, актуальные инструкции при resume, обрыв потока с последующим переподключением, обрезку `AGENTS.md` репозитория в 100 КБ до 32 КиБ, картинку с запятой в имени и то, что команды агента не видят файлов секретов. Прогон 04.10.2026 на образе из текущего дерева — успешно.

Unit-проверки (на 30.09.2026; сейчас agent-drivers — 251, domain — 684): domain — 601, agent-drivers — 166, orchestrator — 1 265 пройденных; 113 интеграционных без БД пропущены. Инфраструктура — 224 пройденных, 2 opt-in пропущены. Проверки типов, линтер, окружение и архитектурные границы прошли. Независимое ревью выявило края длинного ввода и запроса `-`; после перехода на файлы повторных замечаний в просмотренных `prepare`/`command` нет.

## Супервизор и снимки под gVisor

30.09.2026 прошёл дополнительный `pnpm verify:codex-supervisor`. Он расширяет сценарий двух ходов P2 настоящим драйвером Codex: `TurnSupervisor` → `RemoteTurnExecutor` → pull-раннер → `LocalTurnExecutor` → доверенная обёртка → Codex 0.158.0. Песочница использует `runsc` в локальной Colima, запросы идут через настоящий `sandbox-gw` к синтетическим LLM/MCP на хосте.

Для каждого запуска launcher создаёт свои PostgreSQL с миграциями, SeaweedFS и OpenBao Transit в Docker Desktop; значения окружения для данных и ключи создаются заново. Рабочий `.env`, существующие базы, S3/Vault и подписки не используются. Git remote — временный bare-репозиторий, публикацию проверяет настоящий gitleaks 8.30.1. Раннер получает только ключи хода и presigned-ссылки, без доступов к PostgreSQL, S3 и Vault.

Подтверждено:

- Первый ход меняет отслеживаемый `index.php` и создаёт `turn-1.txt`. Второй ход в другом контейнере проверяет предыдущие файлы и меняет их дальше; LLM-фикстура проверяет, что в восстановленной истории есть маркер ответа первого хода.
- Оба хода используют один native UUID. Effort меняется `medium` → `high`, ключи LLM/MCP новые; профиль сохраняется в назначении хода.
- Настоящий `SnapshotService` сохраняет зашифрованные части в S3 с ключом данных Transit. Раннер переносит их через presigned PUT/GET; снимок home содержит только `sessions/`. Оба ключа отсутствуют в распакованных снимках, манифестах, назначениях и журнале событий.
- Shell самого Codex проверяет ядро `4.19.0-gvisor`, uid/gid `10001:10001`, версию CLI и отсутствие LLM/MCP-токенов в окружении дочерней команды. Журнал содержит события запуска, команды, usage и завершения.
- Публикация происходит после удаления контейнера. После успешного прохода отсутствуют контейнеры, сети попыток, правила firewall, том токена раннера, временные строки, объекты и ключ Transit.
- Отдельный SIGTERM отправлен launcher, когда реальная песочница имела `Running=true` и `Runtime=runsc`. Завершение с кодом 1 заняло 1,851 с: удалены sandbox, runner, gateway, сеть попытки, том токена и три сервиса данных; правила INPUT IPv4/IPv6 вернулись к пустому baseline. Лог — `/tmp/raditi-p4-supervisor-cancel.log`, структурированные результаты — `/tmp/raditi-p4-supervisor-cancel-evidence.json`.

Новые 14 тестов проверочного стенда входят в обычный `pnpm --filter orchestrator test`: HTTP/state фикстуры, привязка Docker к локальному сокету, чистое окружение, учёт созданных ресурсов и уборка при прерывании. Сборка, тесты orchestrator, typecheck, lint, check-env и check-architecture прошли. Основной лог локального прохода: `/tmp/raditi-p4-supervisor-proof.log`.

### Повтор

Сначала пересоберите образы из текущего дерева. Digest-ы `raditi-p4verify-*` ниже — исторические: они записаны 30.09.2026 и старше правок `infra/sandbox` от 02.10.2026 (CLI из lock-файла, 11-минутный предел `sandbox-gw`). Повтор с ними проверил бы прежние образы. Прогоны ревью 03–04.10.2026 шли на свежих сборках с собственными тегами, после прогонов удалённых; подставьте digest-ы своей сборки.

Нужны запущенные Docker Desktop и локальная Linux-ВМ Colima с `runsc`, уже загруженные сервисные образы и gitleaks 8.30.1 на хосте. Launcher принимает только локальный Docker Desktop для временных данных и отдельный Unix-сокет ВМ для раннера. Сам образы не загружает. Production runtime, base, gateway и network-guard нужно собрать в демоне ВМ из текущего `infra/sandbox/Dockerfile`; их digest закрепляются явно. Пример для использованной Colima:

```sh
export P2_RUNNER_DOCKER_SOCKET="$HOME/.colima/gvisor/docker.sock"
export P2_RUNNER_HOST=192.168.5.2
export P2_GITLEAKS_BINARY=/absolute/path/to/gitleaks
export P2_SANDBOX_IMAGE=raditi-p4verify-sandbox@sha256:cd41acfa42f233ecf5105866e79abc4b8cbde335bb8648f4eb43fdf477475d53
export P2_RUNNER_NODE_IMAGE=raditi-p4verify-base@sha256:c9aa741bebc082a511708ed1eacf49e9979db7db8a10d780b77f080c6d327c7d
export SANDBOX_GATEWAY_IMAGE=raditi-p4verify-gateway@sha256:73ebae30f83e172977fef14e574456af76b46ba2f4e68dc2b08cd1057723e5b8
export SANDBOX_NETWORK_GUARD_IMAGE=raditi-p4verify-network-guard@sha256:4f09d0283b512f5ecfc1a9077ec617eb35e80e93d3e7dc34e1d140914054783d
pnpm verify:codex-supervisor
```

Эти digest относятся к локальным образам aarch64 от 30.09.2026, публикации в целевой реестр не было. Полный проход заново создаёт и удаляет свои данные. При отказе остаётся приватный диагностический файл с правами `0600`; путь печатается без содержимого. Сам сценарий раннера также сохраняет временный каталог с журналом и логами для разбора отказа. Диагностика может содержать синтетические ключи стенда и не предназначена для публикации. Сценарии P2 с `kill -9` core/раннера остаются отдельной проверкой `verify:runner` с синтетическим агентом.

## Что остаётся

- MCP здесь синтетический: handshake и обнаружение инструментов обязательны; `site_info` вызывается фикстурой, когда CLI объявляет инструмент в запросе. Codex 0.158.0 в code mode держит инструменты MCP внутри своего инструмента `exec` и в теле запроса их не объявляет ([отчёт B13](20-p3-synthetic-gateway.md)). Настоящие инструменты WordPress и их полномочия относятся к P6.
- Для P12: планировщик хода берёт `sandbox.image` из `driver.image` и отказывает при образе-заглушке; одна попытка исправить невалидный итог хода (второй exec в том же контейнере) и предел размера итога против события сообщения в 20 000 символов.
- Приёмка P3 на настоящих подписках и утверждённых ставках остаётся открытой. B16 выполняется отдельным следующим релизом: старые Prisma-клиенты ещё могут читать удаляемые колонки.
- Хранение образа в целевом реестре Gitea и облачная выкладка — после полного локального продуктового e2e с WordPress. Локальный digest не означает публикацию образа.
- Изменения не закоммичены и не отправлены в удалённый репозиторий. Следующая локальная реализация по основному сценарию — драйвер Kimi (P5); оставшиеся гейты P3/P4 сохраняются.
